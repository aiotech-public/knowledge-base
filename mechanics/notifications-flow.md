# Notifications Flow / Push / Marketing

Рассылка push в AIO собирается из двух частей: **ремаркетинг-кампания** отвечает за «кому и когда», **флоу типа `Notifications`** — за «что и по какому расписанию». Дефолтный сетап — кампания плюс флоу ровно с одним узлом **`Drip schedule`** (тип во флоу `Plan Drip`, в RU-интерфейсе «Серия рассылок»), который держит всю серию отправок внутри себя. Сборка самой кампании — [how-to/remarketing-campaigns.md](../how-to/remarketing-campaigns.md); здесь — механика узлов флоу.

Из четырёх нод-каналов (`Push` / `Telegram` / `Email` / `SMS`) рассылка реально уходит только push'ем; `Telegram` отправляется отдельным узлом-каналом, `Email` и `SMS` не отправляются вообще и отказывают молча. Старые ноды `Notifications flow` и `Push` из редактора не убраны и работают, но новые сетапы так не собирают.

---

## Кампания «из коробки» ничего не рассылает — триггер `Manual` стоит по умолчанию

Новая ремаркетинг-кампания не отправляет ничего: в форме создания по умолчанию выбран триггер `Manual`, а он ничего не запускает. Рассылка идёт только у кампании с триггером `Schedule` (по расписанию) или `Conversion` (по приходу конверсии заданного типа). Это первое, что проверяется по симптому «кампания создана, флоу собран, а пуши не приходят».

Триггеры, расписания и привязка аудитории — [how-to/remarketing-campaigns.md](../how-to/remarketing-campaigns.md).

## Что такое флоу типа `Notifications` и чем он отличается от кампанийного

Флоу типа `Notifications` — отдельный флоу рассылки, не Campaign Flow. Заводится в `Marketing → Flows → + Flow → Notifications` («A separate step that schedules notifications for users») и исполняется **параллельно** маршруту визита: рассылка не задерживает визит в его собственном флоу, а клик по самому пушу возвращает визита в его **текущий** State, а не в начало флоу.

На посеве визита во флоу создаётся сообщение (Message), и дальше узлы флоу переключают состояние именно сообщения. Концепт-модель флоу рассылки и его привода — [models/marketing-flow.md](../models/marketing-flow.md).

## Какие узлы есть во флоу типа `Notifications`

Отправляют из узлов флоу рассылки только три — `Drip schedule`, `Push` и `Telegram`; остальные узлы управляют маршрутом сообщения.

| Узел (лейбл UI) | Тип во флоу | Что делает |
|---|---|---|
| **Drip schedule** | `Plan Drip` | Вся серия push-отправок по расписанию в одном узле — основной узел новой модели |
| **Push** | `Plan Push` | Старый узел отправки пуша: контент из одиночного `Push Message Template` или дистрибуции `Remarketing Content` |
| **Telegram** | `Plan Telegram` | Отправка сообщения в Telegram-чат через Sender Provider |
| **Email** / **SMS** | `Plan Email` / `Plan Sms` | В палитре есть, но не отправляют ничего |
| **Wait** | `Plan Wait` | Задержка в секундах |
| **Check** | `Plan Check` | Проверка условия: поле визита + оператор + значение |
| **Check conversion** | `Plan Conversion Exists Check` | Развилка по факту конверсии заданного типа |
| **Repeat** | `Plan Repeat` | Цикл, макс. 10 повторов: повтор — транзишеном `Repeat`, выход — `End repeat` |
| **Start** / **Finish** | `Start` / `Finish` | Точка начала и точка завершения |

## Как разослать серию пушей одним узлом — `Drip schedule` (`Plan Drip`)

Узел `Drip schedule` держит всю серию отправок в одном узле и заменяет прежние цепочки `Wait` → `Push` → `Check conversion` → `Repeat`: расписание, контент каждого шага и условие остановки задаются его собственной формой. Доступен только во флоу типа `Notifications`.

Типовой флоу новой модели — `Start` → `Drip schedule` → `Finish`. Узел самодостаточен по выходам, так что достраивать вокруг него ничего не нужно.

### Как задаётся расписание шагов в `Drip schedule`

Смещение каждого шага отсчитывается **от входа визита в узел**, а не от предыдущего шага; шаги сортируются по возрастанию смещения, между шагами визит остаётся в узле.

Смещения выбираются кнопками-пресетами, произвольное число ввести нельзя: `Now`, `15 min.`, `1 hour`, `3 hours`, `5 hours`, `12 hours`, `1 day`, `2 days`, `3 days`, `4 days`, `5 days`. Один пресет = один шаг, дубль не добавить — из интерфейса собирается максимум 11 шагов.

Два режима формы: `Simple` — одна дистрибуция на всё расписание, `Advanced` — своя дистрибуция у каждого шага. При открытии сохранённого узла режим определяется сам: разные дистрибуции у шагов → `Advanced`. В `Advanced` откроется и расписание, у которого дистрибуции не заполнены вовсе, — это не признак того, что они разные.

### Что отправляет `Drip schedule` — только push из дистрибуции `Message Templates`

У каждого шага выбирается дистрибуция типа `Message Templates` — дерево шаблонов сообщений ([models/distributions-model.md](../models/distributions-model.md)); селектор шага показывает только дистрибуции этого типа. Из того, что вернуло дерево, узел берёт **один push случайным выбором** и отправляет его.

Отправляет узел только push. Telegram-, email- и sms-шаблоны дерева он не берёт — подробнее в «В дистрибуции лежат email/SMS/Telegram-шаблоны, а уходит всё равно push». Telegram в новой модели уходит отдельным узлом-каналом `Telegram`.

### В дистрибуции лежат email/SMS/Telegram-шаблоны, а уходит всё равно push

Дистрибуция типа `Message Templates` по устройству допускает ноды всех четырёх каналов — `Push Template`, `Email Template`, `Sms Template`, `Telegram Template`, — но узел `Drip schedule` оставляет из отобранного дерева только push-ноды и шлёт случайную из них. Не-push ноды выбрасываются **молча**, ошибки в логах нет.

Отсюда типовая ловушка: в дереве «пять языковых email-шаблонов плюс один push» на каждом шаге уходит один и тот же push, и по симптомам это похоже на «сломались веса/языки», а не на «email не поддержан». Ошибка появится, только если push-нод после отбора не осталось ни одной.

Нода `Telegram Template` внутри такой дистрибуции не читается вообще: её текст хранится в самой ноде, а узел-канал `Telegram` берёт контент из отдельной сущности `Message templates` — разбор в «Два разных объекта с именем `Message Templates`».

### Как остановить серию — `Stop conversion`

`Stop conversion` — поле самого узла `Drip schedule`: тип конверсии, обрывающий серию. Как только у визита появилась конверсия этого типа, узел прекращает рассылку и уводит визит выходом `Passed`. Поле пустое — отправляется всё расписание целиком.

Проверка не событийная: запланированный интервал приходом конверсии не прерывается, конверсия замечается непосредственно **перед очередной отправкой**. Между приходом конверсии и остановкой серии проходит остаток текущего интервала.

Если сообщение принадлежит ремаркетинг-кампании, сработавшая стоп-конверсия ещё и выносит визит из её аудитории. У сообщений вне кампании этой ветки нет — серия просто заканчивается.

### `Required conversions` — шаг уйдёт только при всех выбранных конверсиях

`Required conversions` — второе конверсионное поле узла, мультивыбор: шаг отправляется, только если у визита уже есть конверсии **всех** выбранных типов (две конверсии одного типа за два типа не считаются). Проверяется оно раньше стоп-конверсии.

Не хватает хотя бы одной — серия завершается выходом `End repeat`, но из аудитории кампании визит **не** удаляется: условие может выполниться позже. При следующем посеве создаётся новое сообщение, и серия начинается **с первого шага**, а не продолжается с места остановки. Поле пустое — проверки нет.

### `Stop conversion` узла и `Conversion Trigger` кампании — разные вещи

Оба поля выбирают тип конверсии, но смысл у них противоположный: `Stop conversion` в узле `Drip schedule` **останавливает** серию, а тип конверсии в триггере `Conversion` ремаркетинг-кампании (в фильтре таблицы кампаний он же подписан `Conversion Trigger`) **запускает** рассылку. Задаются они в разных местах — первое в форме узла флоу, второе в форме кампании ([how-to/remarketing-campaigns.md](../how-to/remarketing-campaigns.md)).

Условия остановки серии в кампании нет: искать `Stop conversion` в её настройках бесполезно.

### Какие выходы у узла `Drip schedule` — `Handle`, `End repeat`, `Passed`

В редакторе у узла три исходящих ребра: `Handle`, `End repeat` и `Passed`. Симметрии между ними нет: `Passed` — пришла стоп-конверсия, `End repeat` — расписание исчерпано или не выполнены `Required conversions`, а `Handle` рисуется как обычное ребро, но в рантайме работает **фолбэком** — по нему визит уходит тогда, когда нужного специфичного выхода в графе не нарисовано.

Из-за фолбэка граф без явных специфичных стрелок не ломается, и цепочка `Drip schedule` → `Drip schedule` через дефолтную стрелку билдера работает.

### Сколько шагов держит серия `Drip schedule`

Жёсткий потолок серии — **20 шагов**: лишние отбрасываются молча, без записи в логах. Из интерфейса этот потолок недостижим (пресетов 11, каждый добавляется один раз), упереться в него можно только расписанием, собранным не руками.

Пустое расписание завершает узел сразу — визит уходит выходом `End repeat`, ничего не отправив. Шаг без указанного смещения из расписания молча выбрасывается.

### Серия ничего не отправила — что смотреть в логах сообщения

Первым делом — логи самого сообщения в `Marketing → Messages` ([how-to/debug-with-logs.md](../how-to/debug-with-logs.md)). Две частые записи узла:

- `Drip: no push nodes selected from distribution tree` (severity `ERROR`) — в отобранном дереве не осталось ни одного push-шаблона: выбрана дистрибуция без push-нод либо правила отсекли всё подходящее.
- `Push Subscription Not Found` — у визита нет подписки на push; имя сообщения переписывается на эту же строку.

### Почему у визита может не быть ни сообщения, ни логов

Записи нет вообще и самого сообщения в `Messages` тоже — значит, оно не создавалось. Перед посевом планировщик ремаркетинга проверяет конверсионные условия узла `Drip schedule` заранее: если стоп-конверсия у визита уже есть или не хватает `Required conversions`, визит не сеется вовсе — ни сообщения, ни логов не появляется.

Работает этот ранний отсев, только когда во флоу **ровно один** неархивный узел `Drip schedule`. При двух и более сообщение создаётся, и те же проверки отрабатывают уже внутри узла, оставляя записи в логах.

### Расписание узла `Drip schedule` кампания перекрывает целиком

У кампании может быть **своё сохранённое расписание** для узла `Drip schedule`, и оно заменяет набор шагов из флоу **целиком**, а не смешивается с ним пошагово. Кампания расписание не трогала — работает набор из флоу.

В режиме `Campaign Only` стоп-конверсия и `Required conversions` от флоу **не наследуются**: их нужно задать в самой кампании, иначе серия пойдёт без проверок. Общий механизм переопределения — «Можно ли переопределить настройки узлов рассылки из кампании».

## Каналы рассылки: что реально отправляется

Рассылкой уходит только push. `Telegram` отправляется отдельным узлом-каналом, но результат отправки не проверяется; `Email` и `SMS` не отправляются вообще.

### Push — единственный рабочий канал рассылки

Push отправляется по-настоящему, и узел `Drip schedule`, и старый узел `Push` идут через один и тот же отправитель web-push, поэтому спинтакс, срок жизни и срочность у них одинаковые.

Внешнего провайдера у push нет: AIO шлёт его нативно через Service Worker (VAPID, `pushManager.subscribe`), поэтому push-гейтвея в списке Sender Providers и не будет — [reference/sdk.md](../reference/sdk.md) §II.15.

У визита должна быть подписка на push. Нет подписки — сообщение всё равно создаётся, доходит до отправки и падает с `Push Subscription Not Found`.

### Telegram отправляется, но доставка не проверяется

Telegram — единственный не-push канал с замкнутой цепочкой отправки: узел-канал `Telegram` + Sender Provider типа `Telegram` (API-ключ бота) + chat id визита в поле контакта. Контент берётся не из дерева дистрибуции, а из отдельной сущности `Message templates`.

Ответ Telegram при отправке не читается: запись `TG Message Sent` в логах сообщения означает, что AIO вызвал Telegram, а не что сообщение дошло. При заблокированном боте или неверном chat id запись будет ровно та же.

Узел `Drip schedule` telegram не шлёт — в новой модели этот канал остаётся за отдельным узлом-каналом `Telegram`.

### Email и SMS не отправляются, и отказ молчаливый

`Email` и `SMS` доведены до продукта только на уровне интерфейса: ноды в палитре есть, шаблоны заводятся, провайдеры `Mailgun` / `Twilio` / `Prelude Bridge` выбираются — но кода отправки за ними нет. Тумблера, которым это включается, тоже нет: конфигом канал не поднять.

Отказ **молчаливый и следа не оставляет**: узел не пишет ни одной записи в логи рассылки и не публикует ни `Sent`, ни `Failed` — в статистике отправок по такому визиту пусто. При этом сообщение существует и переходом `handle` уходит по графу дальше, поэтому в `Marketing → Messages` визит выглядит прошедшим узел. Симптом: узел «отработал», сообщение поехало дальше, а отправок по визиту нет вообще.

Заводить email/SMS как рабочий канал рассылки нельзя — сообщение не уйдёт; даты запуска не анонсированы. Речь именно о канале рассылок: системные письма AIO (уведомления, сброс пароля) отправляются штатно.

### Какие Sender Providers поддерживаются

`Marketing → Sender providers → + Sender provider`: `Name` / `Description` + `Integration type` (дропдаун). В дропдауне четыре типа:

- **Telegram** — Telegram-бот (API-ключ бота + имя бота). Рабочий; один и тот же провайдер обслуживает и рассылки, и `Telegram Destination`.
- **Mailgun** — email. Отправки нет.
- **Twilio** — SMS (поле учётки `Twilio Api Key`). Отправки нет.
- **Prelude Bridge** — SMS. Отправки нет.

Тип провайдера определяет, где его можно выбрать: селектор узла показывает только провайдеров своего канала — подставить Mailgun в Telegram-узел из интерфейса нельзя.

## Два разных объекта с именем `Message Templates`

В разделе `Marketing` два разных объекта с почти одинаковым именем, и путать их нельзя:

- **`Template distributions`** (`/app/remarketing/message-template-distributions`) — дистрибуции типа `Message Templates`: дерево шаблонов, контент лежит прямо в нодах дерева. Это то, что выбирается в шагах узла `Drip schedule`.
- **`Message templates`** (`/app/remarketing/message-templates`) — отдельный менеджер одиночных шаблонов. Из него берут контент узел-канал `Telegram` и старый узел `Push`.

Общего хранилища у них нет: поля называются одинаково, объекты разные. Права тоже разведены — `marketing.template-distributions.view` и `marketing.message-templates.view`. Менеджер `Message templates` жив и работает целиком, но новые тексты пушей заводят в `Template distributions` ([how-to/push-notifications.md](../how-to/push-notifications.md)).

## Где взять готовые тексты пушей — глобальные наборы `Message Templates`

Писать свои тексты не обязательно: на шаге узла `Drip schedule` выбирается готовый **глобальный набор** push-сообщений от AIO — в селекторе дистрибуции его показывает тумблер `Show global only` («Только глобальные»). Набор подключается целиком, из тенанта не редактируется и собран только из `Push Template`-нод.

Какие наборы есть, почему их нельзя скопировать себе и как собрать свою дистрибуцию — [how-to/push-notifications.md](../how-to/push-notifications.md); что такое глобальная дистрибуция вообще — [models/distributions-model.md](../models/distributions-model.md).

## Старый путь рассылки — ноды `Notifications flow` и `Push`

Старый путь остался в продукте и работает: нода `Notifications flow` в кампанийном флоу сеет визит во вложенный флоу рассылки, а узел `Push` внутри него отправляет пуш из одиночного шаблона `Push Message Template` или дистрибуции `Remarketing Content` ([models/distributions-model.md](../models/distributions-model.md)). Пометки «устаревшее» ни у одной из этих нод нет, гейта по подписке на push у ноды `Notifications flow` тоже нет — она сеет любой не-трэшевый визит.

Новые сетапы так не собирают: цепочка `Wait` → `Push` → `Check conversion` → `Repeat` целиком заменяется одним узлом `Drip schedule` в связке с ремаркетинг-кампанией. Старый путь остаётся кастомной сборкой под задачу, которую новая модель не покрывает.

### Чем сообщение старого пути отличается от сообщения кампании

Сообщение старого пути (у него нет ремаркетинг-кампании) отправляется тем же отправителем push, но проходит мимо всей обвязки кампании:

- платформенные лимиты рассылки к нему не применяются;
- событий `Delivered` / `Opened` у него нет — остаётся только лог в `Marketing → Messages`;
- недоставленные пуши не схлопываются: общей метки кампании у них нет;
- мёртвая подписка не выносит визит ни из какой аудитории.

Логи самого сообщения при этом пишутся как обычно: `Push Message Sent: <заголовок> - <текст>` при успехе и `Push Message Failed (<код>)` при отказе, и имя сообщения переписывается на текст пуша.

### Как отличить сообщение старого пути в `Marketing → Messages`

В таблице `Messages` есть колонка `Remarketing Campaign` — она пустая ровно у сообщений, порождённых старым путём (нодой `Notifications flow` или привязкой в `Conversion Types`). Тултип колонки так и говорит: `Campaign that seeded this message (empty for legacy flow-triggered messages)`. У таких сообщений при этом заполнены соседние колонки `Notification Flow` и `Notification State`.

### Привязка `Notification flow` в `Conversion Types` жива и стреляет рядом с кампанией

В `Conversion Types` осталось поле `Notification flow` (тултип `Notifications run when conversion spawn`): приход конверсии этого типа сеет визит в указанный флоу рассылки. Поле работает, и гейта по аудитории у него нет — сеется любой визит с такой конверсией ([models/conversion-model.md](../models/conversion-model.md)).

Новый триггер `Conversion` ремаркетинг-кампании поставлен **рядом**, а не вместо: на одну и ту же конверсию могут сработать оба пути и уйти два сообщения. Дублируются пуши после конверсии — проверять оба места.

## Ни один путь не гейтит рассылку по подписке на push

Ни ремаркетинг-кампания, ни нода `Notifications flow` не проверяют подписку на push при посеве: и в аудиторию, и во флоу попадает визит без подписки. Проверка стоит только в момент отправки — там сообщение и падает с `Push Subscription Not Found`.

Практическое следствие: визит, подписавшийся уже по ходу серии, дальше получает пуши штатно.

## Подписаться на push можно только на лэнде

Подписаться на push визит может **только на лэнде** (через `Push Subscribe Script`). После ухода с лэнда подписаться нельзя.

## Подписка на push привязана к домену

Подписка на push привязана к **домену**, на котором визитёр подписался. Подписаться на одном, слать с другого — **технически невозможно**.

## Как работает AIO Push Subscribe (макрос)

JS-макрос, выводящий браузерный prompt подписки на push.

- Включается через **Push Subscribe Toggle** на уровне кампании.
- Управление вызовом (по клику / автоматически) — правкой JS внутри макроса.
- После подписки факт фиксируется как конверсия типа `Push Subscribe`.

## Что трекается по пушам — Delivered / Opened только у remarketing-кампаний

Зависит от того, кто отправил пуш. У пушей **remarketing-кампании** доставка и открытие трекаются: события `Delivered` и `Opened` доезжают до аналитики и видны через метрику `Remarketing count` и группировки Remarketing (метрики — [models/metric.md](../models/metric.md)). У пушей флоу рассылки, **не привязанных к remarketing-кампании**, таких событий нет вообще — там по-прежнему только лог в `Marketing → Messages`.

Готовой колонки-процента CTR продукт не отдаёт ни на одном из путей: есть счётчики `Delivered` / `Opened`, а не посчитанный коэффициент. Процент считается своей метрикой — `Computable metric` поверх `Remarketing count` (тип метрики и её формула — [models/metric.md](../models/metric.md), сборка на remarketing-пути — [how-to/remarketing-campaigns.md](../how-to/remarketing-campaigns.md)).

## Параметр `remarketing=true` в адресе после клика ничего не доказывает

К ссылке **любого** push-сообщения безусловно добавляются `remarketing=true` и параметр сессии `sess` — не только рассылке remarketing-кампании. Считать по этому параметру, что визит пришёл из remarketing-кампании, нельзя.

## Лимиты отправки применяются только к сообщениям remarketing-кампании

Платформенные лимиты рассылки — сколько сообщений в сутки и в час на один визит (считается отдельно по каждому каналу, так что telegram не блокирует push и наоборот), минимальный промежуток между сообщениями одному визиту, потолок отправок в час на всю кампанию, возраст визита, старше которого ему не пишут, и размер пачки, которой обрабатывается аудитория — применяются **в момент отправки** и только если у сообщения есть remarketing-кампания.

Действующие значения показаны в форме кампании блоком `Sending rules`, только на чтение: из интерфейса их не изменить. Сообщения флоу рассылки, не привязанные к кампании, проходят без этих ограничений вовсе.

## Сколько живёт недоставленный пуш и что будет, если устройство офлайн

Пуш, который шлёт флоу рассылки (в том числе узел `Drip schedule`) или remarketing-кампания, живёт **сутки**: недоставленный за это время дальше не доставляется. Отправляется он как срочный — доставка не откладывается до «окна обслуживания» спящего устройства.

Недоставленные пуши **одной remarketing-кампании схлопываются до последнего**: всем сообщениям кампании проставляется общая метка, поэтому вернувшееся в сеть устройство получает по ней одно, самое свежее уведомление, а не всю накопившуюся очередь. У пушей, не привязанных к remarketing-кампании, такой метки нет — они не схлопываются.

## Бан домена не блокирует пуши

Даже если домен забанен, пуши обычно **продолжают отправляться** (полная блокировка отправки на уровне домена — редкость). При клике браузер показывает warning-страницу.

## Минимальный `Wait` во флоу рассылки — 60 сек

Узел `Wait` в редакторе флоу рассылки не принимает значение меньше **60 сек** — это валидатор формы, а не ограничение движка. В новой модели рассылки `Wait` не нужен: паузы между отправками задаёт расписание узла `Drip schedule` своими пресетами смещений.

## Как устроены Telegram-уведомления баеру

Тем же узлом-каналом `Telegram` собирают не рассылку визитёрам, а **алерт баеру**: конверсия выбранного типа приходит → флоу рассылки доходит до узла `Telegram` с TG-шаблоном («Проверь лид») → сообщение уходит в Telegram-чат владельца кампании. Номер чата берётся из кастомного поля визита (`Buyer TG Chat ID` — имя-пример, по дефолту такого поля нет), а логи отправки лежат там же, в `Marketing → Messages`.

Запускает такой флоу на конверсию поле `Notification flow` в `Conversion Types` ([models/conversion-model.md](../models/conversion-model.md)). Сборка целиком — Telegram Sender Provider, его поля и раздача чатов по баерам — [how-to/push-notifications.md](../how-to/push-notifications.md).

## Уведомление о бане рекламного аккаунта / новой конверсии — это НЕ рассылка

Если речь про алерт **тебе-медиабайеру** о твоём аккаунте — бан рекламного аккаунта Facebook (`Facebook ad account "..." disabled (...)`), новая конверсия, сбой пуллинга рекламного аккаунта, отчёт по расписанию — это **Notification Center** (колокольчик в UI, self-notification-алерты), а не Marketing/push-рассылка визитёрам из этого дока. Такой алерт наружу проксирует сам Notification Center, а не Sender Providers и ноды-каналы этого флоу; отчёт по расписанию, например, приходит в Telegram и Slack готовой картинкой-таблицей, а не текстом. Дословные тексты этих уведомлений, их триггеры и настройка — [mechanics/notification-center.md](notification-center.md). Здесь — только рассылки push/Telegram визитам.

## Не воспроизводится сессия / Replayer not enough events

Это ошибка Session Replay, не push-механики: визит длился меньше Session flush interval (10 сек), ивенты не успели сброситься. Разбор — [mechanics/visit-lifecycle.md](visit-lifecycle.md).

## Marketing-инфраструктура: Flows, Message templates, Messages

Раздел `Marketing` (`/app/remarketing`) — семь пунктов меню в таком порядке: **Campaigns · Flows · Template distributions · Messages · Sender providers · Message templates · Other**. Ниже разобраны те, что относятся к сборке рассылки: `Flows`, `Message templates` и `Messages`.

### Как устроен редактор Marketing Flows

`Marketing → Flows → + Flow → Notifications` открывает нод-граф редактор (как `Tracker → Flows`, но для рассылок). Слева — Flow details (`Name` / `Description` / `Tags` / `Show archived states`) + палитра **Nodes to create**:

- **Серия рассылок:** **Drip schedule** (тип `Plan Drip`) — целое расписание push-отправок в одном узле; основной узел новой модели, разбор — «Как разослать серию пушей одним узлом».
- **Каналы:** **Push**, **Telegram**, **Email**, **SMS** — 4 отдельные ноды-канала (`Plan Push` / `Plan Telegram` / `Plan Email` / `Plan Sms`). Отправляют только **Push** и **Telegram**.
- **Контроль:** **Wait** (задержка), **Check** (условие по полю визита), **Repeat** (цикл), **Check conversion** (развилка по факту конверсии), **Finish** — типы `Plan Wait` / `Plan Check` / `Plan Repeat` / `Plan Conversion Exists Check`.
- Канва стартует с ноды **Start** (Initial state).

Палитра ничем не гейтится — ни правом, ни фичефлагом, поэтому нерабочие `Email` и `SMS` в ней выглядят так же, как рабочие каналы.

### Что задаётся в конфиге ноды-канала

**Конфиг ноды-канала** (шестерёнка на ноде, пример `Push`): `Name` / `Description`; `Settings availability` (скоуп настройки); стратегия выбора варианта **First / Weights**; строки вариантов (аудитория `All` + **`Select distribution`** + вес) + `+ Add another variant` + `Compact`/`Control`; **`Visual settings`** (`State color` / `Collapsed by default` / `Archive state` — только оформление ноды). **Тело сообщения в ноде не задаётся** — нода выбирает дистрибуцию или шаблон, контент живёт отдельно.

У узла `Drip schedule` этой формы нет: он рисуется своей — расписание шагов, `Stop conversion`, `Required conversions`.

### Можно ли переопределить настройки узлов рассылки из кампании

Да. Настройки кампании разворачивают узлы вложенного флоу рассылки (за нодой `Notifications flow`) наравне с узлами саб-флоу, поэтому per-campaign override для них работает по общему механизму `Settings availability` ([models/flow-model.md](../models/flow-model.md) → State Settings).

У узла `Drip schedule` переопределение устроено особо — расписание заменяется целиком, см. «Расписание узла `Drip schedule` кампания перекрывает целиком».

### Какие типы `Message templates` существуют и их поля

`Marketing → Message templates → + Message template` — выбор типа (список фильтруется по `Type` / `Owner` / `Team`):

| Тип | Поля тела |
|---|---|
| **Push** | `Push title` + `Push message` + `Push icon` (из image library) |
| **Email** | `Email subject` + `Email text` (rich-text: **B / I / U** + нумерованный/маркированный список) |
| **Telegram** | `Telegram message` (текст) |
| **SMS** | `Sms text` (текст) |

У всех — `Name` / `Description` / `Tags`. Из этих шаблонов читают контент узел-канал `Telegram` и старый узел `Push`; узел `Drip schedule` берёт контент из дистрибуций `Message Templates`.

### Как сделать текст сообщения разным на каждую отправку — спинтакс

В текстах рассылки работает спинтакс — `{вариант 1|вариант 2}` (один случайный вариант) и `{Random=(100,1500)}` (случайное целое из диапазона): он разворачивается заново **на каждую отправку**, уже после подстановки плейсхолдеров `{{aio.*}}` ([reference/placeholders.md](../reference/placeholders.md)).

Разворачивают спинтакс сами отправители, поэтому он одинаково работает и в узле `Drip schedule`, и в старом узле `Push` — отправка сведена в один сендер, — и в узле-канале `Telegram`. Синтаксис, ловушки и кнопка `Test` с примерами отправок — [how-to/push-notifications.md](../how-to/push-notifications.md).

### Что такое Messages (лог отправки) и где смотреть аналитику

`Marketing → Messages` — **read-only** список фактически отправленных и запланированных сообщений (кнопки create нет — сообщения порождаются флоу). Фильтр **`Status`**: **Requested → Processing → Done / Failed**. Для рассылок, не привязанных к remarketing-кампании, это вся доступная аналитика; готовой колонки-процента CTR продукт не отдаёт нигде — процент собирают своей метрикой `Computable metric` ([models/metric.md](../models/metric.md)).
