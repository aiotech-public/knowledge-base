# Архитектура AIO

Как физически устроен AIO — какие есть слои, что где живёт, почему лэнды на CDN, почему сервера агностичны, и что реально происходит, когда сервер падает. Без этой картинки половина вопросов выглядит как магия («куда делся мой лэнд?», «почему трафик не идёт?», «почему нотификации не приходят?»).

## TL;DR

- AIO = **SaaS-приложение** на `app.aio.tech` + **AIO-агент** на серверах клиента + **CDN** для контента лэндов.
- Лэнды живут **на CDN**, а не на серверах клиента. Сервера агностичны — на них только агент. Поэтому замена сервера не требует миграции лэндов.
- Клиент = **Tenant** в AIO. У одного клиента может быть несколько тенантов (под разные вертикали или команды).
- Сервера / Домены / DNS подключаются через интеграции (`Server Provider`, `Domain Provider`, `DNS Provider`) в `Tech`.
- При падении сервера или бане домена работает **Repoint** — автоматическое перенаправление доменов на **случайный** живой сервер в той же `Repoint Group` (гео/latency при выборе не учитываются — географию задаёт сама группа). Даунтайм = только DNS-пропагация.
- Мониторинг — отдельная выделенная подсистема с двумя контурами: серверы — раз в 5 минут с нескольких точек по кворуму с подтверждением ~150 секунд (`Danger` через 5–10 минут после падения), домены — отдельный контур раз в минуту. Нотификации только в Telegram через `AIO-tech-bot`. Без привязки аккаунта к Telegram бот не пишет.

## Две части системы

### 1. SaaS-приложение — `app.aio.tech`

Веб-приложение, в котором живут все пользователи AIO (баеры, тех-команды, админы). Здесь:

- UI всех разделов системы (`Tracker`, `Content`, `Tech`, `Settings`, `Marketing`, `Analytics`).
- Конфигурация тенантов: флоу, кампании, дистрибуции, права, метрики.
- Метаданные визитов, лидов, постбэков.
- Аналитическое хранилище. **Trash-визиты** (визиты с пометкой `is_trash` — они исключены из основной аналитики, причина отсева пишется в поле визита `Trash Reason`) хранятся в этом же хранилище.
- Внутренний и публичный API: всё, что можно нажать кнопкой в UI, можно сделать через API. Есть `API 2.0` для интеграции с третьими системами.

Важно: **визит не попадает в SaaS**. Клик по трекерной ссылке не ведёт на `app.aio.tech` — он ведёт на домен клиента, который смотрит на сервер клиента, где работает AIO-агент.

### 2. AIO-агент

Серверный компонент, который ставится на серверы клиента через `Deploy`-скрипт. Это конечный автомат (FSM), работающий **по командам AIO**: агент принимает запрос визитёра, на каждом шаге обращается к AIO и исполняет полученную команду — что отдать визитёру, куда вести визит дальше. Решения флоу — переходы, фильтрацию, выбор сплит-варианта, пуш в Destination — вычисляет AIO; агент исполняет их на краю и сообщает AIO о событиях флоу (submit формы, переход по ссылке-шагу). Полная модель агента и протокол команд — [models/server.md](../models/server.md).

Что делает агент:

- Принимает входящий запрос на доменах, которые смотрят на этот сервер.
- Распознаёт визит по `cuuid` (UUID кампании) и `suuid` (UUID Source) в URL; сам визит идентифицируется отдельным `visit_uuid`.
- Снимает с визита трекинговые параметры (IP, user-agent, гео, browser_language_code, fingerprint и т.п.).
- Исполняет команды AIO: отдаёт визиту HTML лэнда, который пришёл ему в команде от AIO, запускает Backfix, принимает submit формы — а решение, куда вести визит дальше (фильтр пропустил/срезал, какой сплит-вариант, какой переход), приходит от AIO. Страницу агент не рендерит и не собирает: подресурсы лэнда (картинки, css, js, видео) браузер визитёра тянет с CDN через CDN-путь агента, а единственная правка HTML на агенте — правка вида этого пути, если у типа лэнда включён флаг `Temp CDN used`: файлы отдаются те же ([models/landing.md](../models/landing.md)).
- Сообщает AIO о событиях флоу (submit формы, переход по ссылке-шагу) — на их основе AIO ведёт визит дальше и считает аналитику. Поведение посетителя на странице (клики, скроллы для heatmap'ов и записи сессий) снимает отдельно клиентский SDK на самом лэнде, не агент.
- Поднимает Squid Proxy на том же сервере, если так настроен `Deploy`.

## Почему серверы клиента — агностичны

Это ключевое архитектурное решение, от которого зависят масштабирование, репойнт и работа с лэндами:

- Файлы лэндов (HTML, JS, CSS, картинки, видео) **не лежат** на серверах клиента. Они лежат на **CDN**.
- На сервере живёт только AIO-агент + Squid Proxy по дефолту.
- Все сервера внутри идентичны: один и тот же агент, один и тот же `Deploy`.

Отсюда вытекает практическая суть:

- **Сервер можно мгновенно заменить.** Не нужно переносить файлы, как в классических трекерах, где лэнды лежат на самих серверах. На серверах клиента файлов лэндов нет — они на CDN.
- **Репойнт работает быстро.** Достаточно перекинуть DNS-рекорды — все лэнды уже доступны на CDN отовсюду.
- **Сервера взаимозаменяемы.** Можно строить пул серверов разных гео и распределять трафик по регионам (`Repoint Group` держит регионы раздельно). На скорость открытия гео сервера при этом влияет слабо — динамические шаги упираются в контрол-плейн, статику кэширует Cloudflare ([models/server.md](../models/server.md)).

## Tenant как единица

### Что такое tenant

`Tenant` — это **тенант** (workspace по терминологии других SaaS) в AIO. У каждого тенанта есть:

- `Name`, `Description`, `Billing email`, `Country code` (для фильтрации/визуализации активностей по странам).
- Свой набор серверов, доменов, флоу, кампаний, лэндов, дистрибуций, юзеров, ролей.
- Свои метрики, конверсии и аналитика.

Понятие `Workspace` **не используется** — используется только `Tenant`. Если кто-то говорит «воркспейс», имеется в виду тенант.

### Шаблон тенанта

Новый тенант поднимается **из шаблона**. Шаблон содержит:

- Преднастроенные флоу (Two-Step with Filter, One-Step with Filter и т.п.).
- Дефолтные кампании-примеры.
- Готовый источник `Facebook CAPI`.
- Преднастроенные роли (`Owner / Admin / Employee`).
- Преднастроенный антифрод (`Traffic Filters`).
- Шаблоны сообщений рассылки (`Message templates`) и правила уведомлений (`Notification Rules`) — если они заведены в самом шаблоне. Поэтому в свежем тенанте уже могут лежать готовый текст рассылки и настроенный алерт, которых никто в этом тенанте не создавал.

Тенанты собираются из шаблонов, но все команды запускаются по-разному, поэтому шаблон подстраивается под специфику команды.

### Что из шаблона в новый тенант НЕ приезжает — архив, домены и сервера

**Архивные сущности шаблоном не переносятся: в новый тенант едет только живое.** Правило действует почти на всё, что копируется: теги, поля визита, формы, метрики, типы конверсий, пресеты, источники, дестинейшны, трекеры, макросы, креативы, трафик-фильтры, дистрибуции, команды, флоу с их шагами, кампании, адвертайзеры, группы плейсхолдеров, ленды и позиции. Производные сущности подрезаются по живым родителям: языки форм берутся только у неархивных форм, ноды — только у неархивных дистрибуций, переходы флоу — только между неархивными шагами.

**Домены и сервера шаблоном не копируются вообще.** Вместо них новому тенанту заводится тестовая пара «сервер + домен» для экспериментов — [how-to/domains.md](../how-to/domains.md). Из-за этого в кампаниях-примерах домен не выбран: перед запуском домен в кампании выбирается вручную.

### Multi-tenancy

- Один **User** может иметь доступ к **нескольким** тенантам — через дроп-даун в правом верхнем углу переключается между ними.
- Один **Tenant** может быть пошарен между **несколькими** юзерами.
- Тенанты изолированы: метрики, поля визита, конверсии, команды одного тенанта не пересекаются с другим.
- Под разные вертикали обычно заводят **отдельные тенанты** (доптенант — см. [models/tenant.md](../models/tenant.md)).

## Сервера и домены — связка

### Как добавляется сервер

Два пути (`Buy a server` / `Add manually`) и полная таблица атрибутов — [models/server.md](../models/server.md). Deploy-скрипт ставит Docker, Squid, AIO-агент + сервис обновления (самообновление); кастомный Deploy — например, чтобы сервер стал прокси. При `Buy a server` скрипт выполняет провайдер при первом запуске машины, при `Add manually` — владелец сервера по SSH; AIO в обоих случаях лишь ждёт ответа агента на `/ping` (~30 минут) — что делать, если сервер завис в `Processing` или упал в `Danger`,.

### Как добавляется домен

Через `Tech → Domains → +Domain`. Два пути (Buy / Add Manually) и атрибуты домена (`Description`, `Tags`, `Monitoring User`, `Allow indexing by search engines`, `Default Query Code`) — [how-to/domains.md](../how-to/domains.md).

### Связка домен → сервер

Домен указывает на IP сервера через A-record в DNS-провайдере. Один домен обычно смотрит на **один сервер** в моменте, но связку можно поменять — это и есть механика репойнта.

## Repoint — что это и зачем

### Сценарий

Сервер падает, провайдер блокирует аккаунт, или не прошла оплата — сервер становится недоступен. Мониторинг подтверждает это по кворуму через 5–10 минут (секция «Мониторинг и нотификации» в этом документе). Что происходит дальше — **один раз, в момент открытия инцидента**:

1. AIO автоматически берёт **все домены**, которые смотрели на этот сервер.
2. Для каждого домена выбирает **случайный живой сервер** (`Running`) в той же `Repoint Group` (выбор случайный — гео/latency при выборе не учитываются; географию задаёт сама группа), поэтому домены одного упавшего сервера могут разъехаться по разным серверам группы.
3. Через DNS-провайдера меняет A-record каждого домена на IP нового сервера — по отдельной задаче на каждый домен, без пауз между ними.
4. Трафик продолжает идти, как только DNS-пропагация дойдёт до юзеров.

Это работает **именно** потому что сервера агностичны: на новом сервере уже стоит тот же агент, готовый принимать визиты, а лэнды лежат на CDN — их переносить не надо.

**Автоповтора нет.** Если задача репойнта домена упала (DNS-провайдер ответил ошибкой, например rate limit Cloudflare при переезде большой пачки), домен остаётся в `Danger` со строкой `Repoint failed: <причина>` и AIO повторно его не трогает — переезд запускают руками (`right click → Repoint to a new server`). Отдельного алерта об ошибке репойнта нет: причина видна в строке статуса домена (в `Domain logs` записи репойнта идут уровнем `Debug` и без переключения `Severity` не показываются). Домен без DNS-провайдера при падении сервера не репойнтится вовсе — он уходит в `Danger` с текстом инцидента (в Telegram — `Domain is not under AIO Control`). Разбор строк → «Домен ушёл в репойнт».

### Repoint Group

Атрибут сервера = строка (например, `eu`, `us`, `tier1`). Репойнт работает **только внутри группы**.

- Если в группе есть живой сервер — репойнтит на него.
- Если в группе **нет живого** сервера — переезжать некуда: репойнт НЕ выходит за пределы группы, трафик с этих доменов останавливается.

Поэтому правило: **в одной репойнт-группе нужно держать минимум 2 сервера**. Если в группе всего один — репойнт фактически нечем отрабатывать, и единственная защита — держать в группе минимум 2 живых сервера.

Также используется для разделения трафика по гео / вертикалям / командам — чтобы в момент репойнта Сан-Франциско не оказался в Амстердаме.

### Рекомендация на практике

- Держать аккаунты у **нескольких** Server Providers. Если падает один провайдер целиком — трафик уйдёт на другой.
- Серверы в одной репойнт-группе — желательно от **разных** провайдеров.
- Минимум 2 сервера в группе.

## Мониторинг и нотификации

### Pinging серверов — кворум раз в 5 минут, подтверждение ~150 секунд

Мониторинг — **отдельная выделенная подсистема** (вся логика пингов и алертов живёт внутри неё), и у серверов и доменов **разные контуры**. Сервер пингуется по `http://<ip>/ping` раз в **5 минут** с **нескольких географически распределённых точек мониторинга** (состав точек настраивается, не фиксирован). Решение «упал / жив» — **по кворуму** точек, и недоступность должна продержаться не меньше **~150 секунд** по подряд идущим пингам, то есть подтвердиться минимум двумя раундами. Отсюда штатная задержка: сервер получает `Danger` и алерт **через 5–10 минут после реального падения**, не мгновенно. Восстановление подтверждается первым же успешным раундом кворума — инцидент закрывается сам.

Разбор подтверждённых инцидентов идёт каждые 30 секунд: именно он ставит `Danger`, шлёт алерт и запускает авто-репойнт доменов (секция «Repoint — что это и зачем»). Сервер в статусе `Processing` (установка или удаление идёт) мониторинг не проверяет; сервер с инцидентом старше 7 дней из проверок выпадает. Мониторинг фиксирует **факт** недоступности — причину он не определяет.

### Pinging доменов — отдельный контур раз в минуту

Домены проверяются **не** серверным кворумом: у них свой контур — раз в **минуту** AIO отдаёт список доменов с включённым мониторингом внешнему координатору, тот дёргает `https://<домен>/ping` и возвращает изменения статуса. Домен, который перестал отвечать, получает `Danger` со строкой причины от мониторинга; когда снова отвечает — `Running` со строкой `Fine`. Кворум из нескольких точек и подтверждение ~150 секунд — это про серверы; у доменов решение приходит от координатора готовым.

Пока по домену открыт инцидент (`Danger`, мониторинг включён), сводка `AIO Monitoring` в Telegram уходит **каждую минуту** — она сама об этом предупреждает: `To mute Ongoing alerts, archive the domain or remove it from monitoring`. Как выглядит сводка и как отобрать такие домены фильтром `Alerting Now` — [how-to/domains.md](../how-to/domains.md) → «Как работает мониторинг доменов».

### Статусы в интерфейсе — что означает иконка у сервера и домена

Статусов три, и они **одни и те же у сервера и домена**: `Running`, `Processing`, `Danger`. Иконка в строке — это статус записи, а не «здоровье прямо сейчас»: `Danger` держится, пока инцидент не закрыт или операция не повторена.

- **Иконки нет** — `Running`: всё ок.
- **Синий вращающийся значок** — `Processing`: идёт операция (создание, установка, выпуск SSL, репойнт, удаление).
- **Красный крестик** — `Danger`: открытый инцидент недоступности **или** провалившаяся операция. Причина — в подсказке у иконки (`status_text`): у сервера `Current Incident: <причина>` / `All install checks failed: …`, у домена `Repoint failed: …`, `All checks failed: …`, `<имя чекера> Incident: <вердикт>` и другие строки.

Вердикт домен-чекера (`Google Threat` / VirusTotal) **тоже кладёт домен в `Danger`** — со строкой `<имя чекера> Incident: <вердикт>` (например, `1 Suspicious & 2 Malicious`), отдельного «жёлтого» статуса под чекеры нет. Жёлтый значок-предупреждение в строке домена означает включённый `Under Attack`; значок глаза / перечёркнутого глаза — включён или выключен мониторинг домена.

### Что отслеживается

- Доступность сервера (отвечает ли агент на `/ping` по IP).
- Доступность домена (открывается ли `https://<домен>/ping`).
- CPU сервера (по агенту — AIO ведёт мониторинг агентов). Можно завести отдельный чат с уведомлениями и добавить туда бота, который шлёт алерт при CPU выше ~85%.
- Срок регистрации домена и срок SSL по расписанию **не** отслеживаются (*Что AIO проставляет и делает сам — фоновые задачи и их расписание*).

### Monitoring User

`Monitoring User` — это юзер в AIO, которому `AIO-tech-bot` шлёт нотификации в Telegram, если статус сервера/домена меняется. Назначается отдельно для сервера и для домена в момент добавления (`Tech → Servers / Domains → Edit`).

Можно использовать не отдельного юзера, а **групповой чат** — тогда создаётся «технический юзер-чат» (бот добавляется в чат, в системе заводится юзер, привязанный к этому чату), и все алерты падают в общий чат, где их видит вся команда.

### AIO-tech-bot и 2FA: что это и что гейтит

`AIO-tech-bot` — это Telegram-бот, который шлёт нотификации и может использоваться для включения 2FA. 2FA настраивается **через Telegram (`AIO-tech-bot`) или через Google Authenticator** — привязка к Telegram для 2FA больше не обязательна (её сделали необязательной, когда добавили 2FA через Google Authenticator). Нотификации доставляются только в Telegram.

Когда 2FA включена, она гейтит **сам вход**: при каждом логине (после логаута) AIO требует код подтверждения (verification-код от `AIO-tech-bot` в Telegram либо TOTP-код из Google Authenticator). То есть 2FA защищает и сам шаг входа в `app.aio.tech`, и доступ к чувствительным колонкам (телефон, email, логи) — если 2FA выключена, эти колонки скрыты. Доставка же нотификаций зависит не от 2FA, а от привязки аккаунта к Telegram.

### Почему не приходят алерты: нет привязки к Telegram

**Алерты уходят через `AIO-tech-bot` в Telegram, поэтому без привязки аккаунта к Telegram доставить их некуда.** AIO не может связать аккаунт с TG — и нотификация не уходит. Проверять надо именно наличие TG-привязки у Monitoring User'а.

2FA через Google Authenticator привязку к TG **не даёт** — с ним 2FA есть, а алерты всё равно не идут, пока нет привязки к Telegram. Раньше привязка к TG была обязательной частью 2FA, поэтому симптом совпадал с «2FA не включена»; теперь эти две вещи разошлись.

### На каком языке приходит алерт

**Алерт рендерится на языке получателя: язык хранится на его аккаунте и следует за переключателем языка интерфейса, в самом правиле он не задаётся.** Что переводится, а что остаётся английским, и почему интерфейс уже на русском, а уведомления продолжают приходить английскими — [mechanics/notification-center.md](../mechanics/notification-center.md).

### Как включить 2FA

Включить 2FA (Telegram):
1. Открыть `Profile Settings` (правый верхний угол).
2. Через QR или поиск `@aio_tech_bot` открыть бота в Telegram.
3. Послать `/setup2fa`, нажать `Enable 2FA`, ввести 4-значный код из бота.

Альтернатива — Google Authenticator: в `Profile Settings` выбрать настройку 2FA через authenticator-приложение (привязка по QR/секрету, вход по TOTP-коду).

## CDN — куда едут лэнды

Когда лэнд загружается ZIP-архивом через `Content → Landings → +Landing`, AIO процессит архив (нормализует структуру, переписывает пути на CDN, инжектит `{{aio:head}}`/`{{aio}}`) и выкладывает все файлы на CDN. Детали пайплайна — [models/landing.md](../models/landing.md).

Практические последствия:

- **Лэнд доступен мгновенно отовсюду** — CDN решает географию.
- **Замена сервера не требует переноса лэндов** — они уже на CDN, не на серверах клиента.
- **Через вкладку `CDN files`** можно править отдельные файлы (CSS / HTML / JS) без перезаливки всего архива. Это полезно для мелких правок.

## Защита и устойчивость доменов

### Устойчивость к массовым жалобам на домен

Домен может стать недоступен по внешним причинам, и от этого не должна встать вся связка. Основной инструмент — **Domain-Change Step во флоу**: он разделяет трекинговый и публичный домен ([models/domain.md](../models/domain.md)), поэтому публичный домен меняется массовым `Replace Domain` без переподключения рекламных кампаний. Вторая сторона — настройки шага `Filter` во флоу, они разобраны отдельно.

### Toggle Under Attack (Cloudflare)

`Toggle Under Attack` — экшен на доменах с подключённым Cloudflare. Включает Under Attack mode в CF — каждому визиту показывается captcha «Verify you are human».

- Single-action на одном домене или массовый на множестве.
- Это **первая ступень** защиты от DDoS, рубильник.
- Использовать с осторожностью: captcha рубит обычным юзерам конверсию.

### AS-Net Block-листы

Списки IP-диапазонов прямо в AIO (не в Cloudflare). Поддерживают CIDR (`x.x.x.x/24`) и через тире (`x.x.x.0-x.x.x.255`). Жёсткое отсечение DDoS-источников.

### Direct без Cloudflare

Эксперимент: добавить домен в AIO **без** DNS-провайдера. SSL-сертификат можно выпустить кнопкой прямо из AIO либо загрузить вручную. Запросы идут напрямую на сервер.

Когда применяется: в вертикалях с низким бан-рейтом — где жалобы на домены летят редко. В вертикалях с высоким бан-рейтом — почти никогда: без CF сервер уязвим к DDoS, а при бан-атаке может упасть весь.

## Domains: trackingDomain vs publicDomain

Если во флоу есть `Domain-Change Step`, визит начинается на трекинговом домене, а дальше по флоу переходит на публичный. Это разделяет роли: трекинговый домен зашит в рекламную ссылку, публичный домен открывает лэнд. Публичный домен можно сменить массовым `Replace Domain`, не переподключая рекламные кампании. Смена трекингового домена требует перезапуска рекламной кампании (ссылка на стороне площадки поменяется). Один визит может пройти через несколько доменов — это by design. Полная механика — [models/domain.md](../models/domain.md).

## Чекеры доменов

Отдельные интеграции для мониторинга бана доменов (`Tech → Domain checkers`): **`Google Threat`** (API-проверка и браузерная дают разные результаты — дополнительный сигнал, не главный) и **VirusTotal** (лимит по IP запроса, не по ключу; ~100-150 доменов на аккаунт). Подробнее — [how-to/domains.md](../how-to/domains.md).

Рекомендация: **добавить сразу** — обе интеграции бесплатные, мониторинг бана включается из коробки.

## Что из этого следует на практике

### Серверы агностичны и лэнды на CDN — что это значит при замене сервера

- **Сервера агностичны → можно безопасно пересобирать инфру.** Замена/добавление сервера ничего не ломает в работе уже загруженных лэндов.
- **Repoint Group обязательна → если в группе 1 сервер, защиты нет.** При вопросе «почему репойнт не сработал» — первое, что смотрим: сколько серверов в группе.
- **Файлы лэндов — на CDN (доступны отовсюду), поэтому при смене сервера их не переносят.** Контент визитёру отдаёт агент на сервере (по командам AIO), но гео сервера на скорость открытия влияет слабо: динамические шаги упираются в контрол-плейн AIO, статику кэширует Cloudflare. Разбор и что реально ускоряет открытие — [models/server.md](../models/server.md).

### Алерты не приходят или публичный домен забанили — что делать

- **Нет привязки к Telegram → алерты некуда доставить.** Если «не приходят алерты» — проверяем, привязан ли аккаунт Monitoring User'а к Telegram (алерты идут только в TG). 2FA через Google Authenticator привязку к TG не даёт — с ним алерты не пойдут. Механика — § «AIO-tech-bot и 2FA».
- **Публичный домен меняется массовым Replace Domain.** Рекламную кампанию перезапускать не надо.

### Интеграции, API и аналитика — практические выводы

- **Все интеграции (Server / Domain / DNS Providers) добавляются по запросу.** Если нужно что-то, чего нет в дефолтном списке — это запрос в саппорт, обычно делается в день обращения.
- **API = всё, что есть в UI.** Автоматизировать можно что угодно. Документации по API мало (используется тот же endpoint, что и фронт), но в проде это уже работает именно так.
- **Аналитика на больших объёмах.** Тормоза при разбивке по `fb_ad_id` за месяц — это природа аналитического хранилища на больших объёмах. После миграции 2026 стало быстрее, но ограничения БД остаются.

## Дополнительные факты архитектуры

### Multi-tenancy ограничения и tab-sessions

- **Домен может быть только в одном тенанте одновременно** — единственное мультитенантное ограничение AIO. Все остальные сущности кросс-тенантно изолированы стенами, но один и тот же домен в двух тенантах одновременно жить не может.
- Для одновременной работы в нескольких тенантах в браузере — механизм **локальных tab-session** (+ local storage).

### Серверы — нагрузка и uptime

- AIO **видит** нагрузку сервера (есть алерт CPU > 85%), но **не следит** за ней — мониторинг и реакция остаются зоной клиента.
- Страница кампаний постранична — 1000-3000 кампаний не «убивают» AIO. Домен и привязку к дистрибуции можно добавить за одно действие; одной дистрибуции достаточно на все домены.

### Безопасность входа

- **Self-whitelist по IP есть** — тенант сам ведёт список доверенных IP (`Manage tenant` → многострочное поле `IP address`, по одному IP на строку; правит роль `Admin`/`Owner`). Это не ограничение входа в аккаунт: вайтлист нужен, когда перед AIO стоит собственный прокси-сервер клиента — без него в поле визита `ip_address` попадает IP прокси, а не визитёра. Механика, что при этом ломается и как настроить — [models/server.md](../models/server.md) §«У всех визитов один и тот же IP».
- Вход в UI `app.aio.tech` — логин/пароль + 2FA (Telegram или Google Authenticator).
- AIO **не отдаёт** клиенту токены / API-ключи подключённой Meta Application — скрыты. Альтернатива — тянуть FB-данные из AIO через AIO-API.

### Своя инфраструктура и CDN

- Подключение **своего CDN** сейчас недоступно.
- Свой проксирующий сервер перед AIO-агентом — возможен, такая схема встречается в бою. Но **официального гайда нет** — собирается самостоятельно.

### Лэнды на агенте: pseudo-paths и re-upload

- Лэнд на сервере отдаётся **одним HTTP-response'ом**; пути внутри лэнда — pseudo-path, локальные для этого лэнда. `style.css` разных лэндов на одном домене **не конфликтуют**.
- Каждая загрузка лэнда — **полный re-upload** на CDN + переписывание ссылок (не инкрементально).
- Все формы на лэндах подставляются **из SDK**, не из HTML самого лэнда (рендерится HTML-форма, но из SDK). Благодаря этому форму можно сплитовать на уровне кампании.

### Антибот-защита агента

Не каждый входящий запрос доходит до флоу: часть агент отбрасывает на входе, ещё **до шага `Filter`**. Настраиваемая фильтрация во флоу — отдельный слой.

### Режимы обработки запроса на агенте — не только отдача лэнда

- Отдать лэнд с CDN — не единственный режим обработки входящего запроса на агенте: какой режим применить на шаге, решает AIO и присылает агенту командой.

### AIO записывает любой клик

- AIO записывает **любой дошедший клик** — визит будет записан, даже «без всего». Гипотеза «AIO не принял клик» при дебаге почти всегда неверна.
- AIO **не whitelist-ит** свои IP в брокерских интеграциях — пул IP большой и динамичный. Альтернатива — `Proxy String` в настройках Destination (статический прокси-IP).

### Косты и профит по FB — через метрику `Meta Spend`, уровень матчинга переключаемый

**Косты и профит по FB — основной способ через метрику `Meta Spend`.** Она считается на лету в момент отчёта, матчит трафик с расходом Meta по идентификаторам кампании / адсета / объявления, ничего не теряет, а рядом стоит revenue — профит и ROI по FB читаются прямо в отчёте по любому разрезу. Уровень матчинга выбирается кнопкой `Meta Engine attribution level` в тулбаре таблицы (`Campaign` / `Adset` / `Ad`), дефолт — `campaign`, выбор хранится в браузере — поэтому у двух людей одна таблица может показывать разный `Meta Spend`. Полная механика — [mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md).

Старый перелив костов **на визиты** (`Cost Update Strategy` = `AIO Meta`; уровень у него свой и на `Meta Spend` не влияет, разбор — [how-to/campaigns.md](../how-to/campaigns.md)) — устаревший путь: он наполняет метрику `Costs` на визитах для классического ROI в трекере и теряет часть расхода, если по ключу нет визита; ещё работает, но по костам/профиту FB ориентируйся на `Meta Spend`.

### Косты на уровне визита для других источников

Косты для источников, кроме Meta, проставляют вручную через `Update costs` (за период / по полю / Costs или CPC) либо они приходят прямо с кликом, если источник передаёт цену клика в URL-параметрах. ROI по таким костам считается на визитах. Как работает ручной `Update costs` и как введённая сумма разливается по визитам — [how-to/campaigns.md](../how-to/campaigns.md).

### Собственная защита IP серверов

На уровне самих машин IP сервера ничем не прикрыт: с доменом за Cloudflare реальный IP сервера снаружи не виден, без Cloudflare сервер доступен по IP напрямую.

### Постбэки и очередь

Постбэки попадают в **общую очередь** AIO — отсюда возможные задержки при пиковой нагрузке.

### Параметр уровня кампании — паттерн tenant-default → campaign-override

- Общий паттерн настроек — **tenant-default → campaign-override**: поле уровня кампании (`yes`/`no`/пусто, пусто = дефолт тенанта) переопределяет дефолт для конкретной кампании. Пример: `fbPixel` — поле-переключатель «использовать пиксель или нет».

### AIO принципиально не блокирует автоматически

- AIO **принципиально не блокирует автоматически** по данным сторонних сервисов. Накопленных датасетов у AIO нет — каждый тенант копит свои.

### Геобалансировка

- Геобалансировка трафика через Cloudflare (multi-A-record) возможна.
- Схема «tracking-домен под рекламу + второй домен под лэнды» повышает устойчивость: два домена с разными ролями изнашиваются независимо, и замена публичного не трогает рекламную ссылку.

### Monitoring User через групповой чат

Алерты можно слать не отдельному юзеру, а в общий TG-чат («технический юзер-чат»). Полная пошаговая процедура — [how-to/domains.md](../how-to/domains.md) → «Monitoring User через групповой чат TG».
