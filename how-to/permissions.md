# Permissions / Users / Sharing (How-to)

Практические процедуры по правам и юзерам в тенанте: добавить и деактивировать юзера, привязать к Position, пошарить связку, скрыть чужие флоу. Концепт-модель (роли / Positions / Teams / Imperatives / Sharing) — в [models/permissions-model.md](../models/permissions-model.md).

---

## TL;DR

- Добавление юзеров — через инвайт (`Settings → Users → +User`, кнопка `Generate Invite`). Это единственный путь.
- Удаление **vs** деактивация: **деактивировать** через `Manage Tenant`, не удалять (иначе автор прошлых заливок становится «empty»).
- Привязка Position юзеру: `Settings → Positions → выбрать → assign`.
- Share на сущности (Campaign / Landing): ПКМ → `Share`.
- Пошарить можно и **папку**: доступ получает всё её содержимое, включая сущности, добавленные в неё позже.
- Скрыть флоу от байеров — `Change ownership` (массовый пункт — `Mass change ownership`) + access type «по пошарке» (`By Share`). Работает и на `Tracker → Flows`, и на флоу рассылок в `Marketing → Flows`.

---

## Как добавить нового юзера

Единственный путь — **инвайт-линк** (`Settings → Users → зелёная кнопка +User`). Поля инвайта (Name / Code / Usages / Role / Position / Team) и кнопка `Generate Invite` — в [models/permissions-model.md](../models/permissions-model.md) → Invite User.

**Шаги:**

1. `Settings → Users → +User` → заполнить поля инвайта (Name / Code / Usages / Till Date / Role / Position / Team).
2. `Role` — это **роль тенанта**, не Position. При инвайте доступны только `Admin` (полный доступ) или `Employee` (ограниченный — видит только пошаренное ему и его команде); роль `Owner` через инвайт не выдаётся. Тонкая настройка доступа Employee — через Positions (см. [models/permissions-model.md](../models/permissions-model.md)).
3. `Generate Invite` → отдать инвайт-код и ссылку новому юзеру.
4. Новый юзер регистрируется по ссылке (Name / Email / Telegram / Password), включает 2FA (через `@aio_tech_bot` в Telegram или Google Authenticator).

Если у человека **уже есть аккаунт AIO**, по инвайту он входит в тенант **тем же аккаунтом** — новый юзер не заводится. Запрос «дайте доступ к другому тенанту» = добавить существующий аккаунт в нужный тенант, а не создавать нового юзера. Один аккаунт-`User` живёт в нескольких тенантах, права в каждом свои ([models/user.md](../models/user.md)).

### Как самостоятельно проверить дефолтные доступы байера

Полезно зарегать **тестового юзера** на стандартной позиции (`Buyer`), открыть в инкогнито и глазами байера увидеть, что он реально видит — может оказаться, что часть нужного не видна, часть лишнего видна. Лучше проверить до реального использования.

См. [models/permissions-model.md](../models/permissions-model.md) → эвристика «Обрезать всё, потом раздавать».

## Как удалить или деактивировать юзера

**Путь:** `Manage Tenant → юзер → Deactivate / Delete`.

**Разница:**

| Действие | Что происходит | Когда использовать |
|---|---|---|
| **Deactivate** | Юзер не может войти, но остаётся в истории как автор прошлых сущностей | По умолчанию — когда юзер уходит из команды |
| **Delete** | Юзер удаляется. Автор прошлых заливок становится `empty` | Никогда не делать, если важна история |

**Рекомендация:** всегда **Deactivate**, не **Delete**.

## Как привязать юзера к Position

**Путь:** `Settings → Positions → выбрать Position → assign` (или через `Manage Tenant → Edit User → Positions`).

**Шаги:**

1. Открыть нужную Position.
2. Добавить юзера в список assignees.
3. Если у юзера несколько Positions — задать **Priority** (слайдер в модалке Position, шаг 10; больше = выше приоритет при конфликте Allow/Deny между Positions).
4. `Save`.

Также см. [models/permissions-model.md](../models/permissions-model.md) → Positions.

### Как посмотреть дефолтные доступы позиции Buyer

Когда: проверить, что входит в стандартную позицию `Buyer` до раздачи юзерам.

**Путь:** `Settings → Positions → Buyer` (или зарегать тестового юзера на `Buyer` и зайти в инкогнито).

## Как пошарить сущность (Campaign / Landing / Domain) конкретному юзеру

Когда: хочешь дать одному юзеру / команде доступ к **одной конкретной** сущности (Campaign / Landing / Domain), без раздачи прав в Position.

**Путь:** на сущности (Campaign / Landing / Domain) → ПКМ → `Share` → выбрать юзера или команду.

### Какие права выдать каждому грантополучателю

Внутри модалки Share, у каждого добавленного юзера/команды:

- **Зелёный карандаш** — право редактирования сущности.
- **Иконка стрелок** — право шарить / перешаривать сущность дальше (отдельно от редактирования).
- Bulk-шорткаты: `+Add all` — пошарить со всем тенантом сразу; `All can edit` — выдать право редактирования всем, с кем уже пошарено.

Сама модалка Share (вкладки `All / Users / Teams`, `Add all`, `Remove all`) описана в [reference/ui-common.md](../reference/ui-common.md) → Share. При шаринге Campaign на шаге `Next` показывается окно с тем, что **уезжает вместе с кампанией** (используемые в ней Landings и Destinations) — их отдельно шарить не нужно. Кто получил доступ — видно в колонке `Shares` на сущности.

### Как пошарить сразу несколько сущностей (mass-select)

При выделении нескольких сущностей доступны действия:

- **`Share Also`** — добавить к уже шаренным (старые шаринги остаются).
- **`Unshare`** — снять шаринг с указанных.
- **`Force Share`** — снять все предыдущие, оставить только новые.

Также см. [models/permissions-model.md](../models/permissions-model.md) → Sharing.

Если массовое действие падает ошибкой (`Some UUIDs were not found in this model`, `Missing or invalid uuids`, `Action type is not correct`, при Copy — `Model wasn't found`) — разбор симптом→причина→проверка.

### Сотруднику нужно править чужие лэнды — не шарить каждый по одному

Если человеку постоянно нужно править не свои лэнды, шарить их по одному не надо: в его Position включается ветка `Editor Scopes` (императив `Editor Scopes: content landings`) — она снимает проверку владения на правке и шаринге лэндов. Видимости она при этом не даёт: чтобы чужие лэнды вообще появились у него в списке, нужно ещё право `Scopes: content landings`. Механика обеих веток — [models/permissions-model.md](../models/permissions-model.md).

Не путать с шарингом папки: папка **раздаёт доступ** к конкретным сущностям, которые в ней лежат, а `Editor Scopes` **снимает проверку владения** на правке лэндов вообще, без раздачи доступа. Инструменты разные и решают разные задачи.

## Как не шарить каждую сущность по одной — шаринг папки

Пошарить можно не только сущность, но и **папку**: доступ ко всему содержимому раздаётся одним действием, и сущности, которые положат в эту папку позже, тоже получат доступ. Это ответ на «замучился шарить каждый лэнд после создания» — папка становится общим контейнером доступа.

**Путь:** блок папок над таблицей раздела (`Content → Landings`, `Tracker → Campaigns` и т.п.) → ПКМ по чипу папки → `Share` → выбрать юзеров/команды и уровень доступа → `Next` → `Save`.

Пункт `Share` в контекстном меню папки появляется только у того, кто может **редактировать папки** этого раздела (право вида `content.landings.folders.edit`, `tracker.campaigns.folders.edit`); с одним правом просмотра папок ПКМ-меню по чипу не открывается. Шарить папку можно и на юзера, и на команду — как обычную сущность. Массового шаринга папок нет: папки шарятся по одной.

### Что уезжает вместе с папкой при шаринге

Доступ получают все сущности, лежащие в папке, **и их зависимости**: пошарив папку кампаний, ассайни получает и сами кампании, и используемые в них Landings и Destinations — отдельно их шарить не нужно.

Перед сохранением состав видно: в модалке Share вкладка `Details` показывает список того, что уедет вместе с папкой (вкладка появляется, только если зависимости есть). Уровень доступа выбирается на каждого ассайни теми же тремя иконками, что и при шаринге сущности: глаз (`Allowed to view`), карандаш (`Allowed to edit`), стрелки (`Allowed also to share`).

### Какой уровень доступа получает содержимое папки

Сущности, лежащие в папке, получают **уровень самой папки**, причём принудительно: если у этого же юзера уже был доступ к такой сущности с другим уровнем, уровень переписывается уровнем папки.

Подтянувшиеся следом зависимости (лэнды и дестинейшны кампаний) ведут себя иначе: если у ассайни на них **уже был** шаринг — прежний уровень сохраняется, уровень папки на них не переписывается. Уровень папки достаётся зависимости, только если доступа к ней не было вовсе.

Практический вывод: уровень предсказуем для того, что физически лежит в папке, и не предсказуем для подтянутых зависимостей. Если важен конкретный уровень на конкретном лэнде — проверять и выставлять его на самой сущности, а не через папку.

### Положил сущность в уже пошаренную папку — доступ выдастся сразу

Доступ выдаётся в момент назначения папки, а не когда-нибудь потом. Путь: ПКМ на сущности → `Assign to folder` → поле `Folder` (`Choose folder to assign`) → сохранить. Сущность попадает в папку и тут же раздаётся всем, кому папка пошарена, с тем же уровнем доступа; вместе с ней доступ получают её зависимости.

Папка у сущности одна: в диалоге назначения выбирается **одна** папка, и назначение **заменяет** прежнюю, а не добавляется к ней. Вложенных папок в AIO нет — уровень вложенности один.

### Убрал сущность из папки — что снимется с доступа, а что останется

Снимается доступ **к самой сущности** — и только если ассайни не сохраняет её через другую пошаренную ему папку. Путь: ПКМ на сущности → `Unassign from folder` → подтвердить (`Are you sure you want to unassign?`).

Два следствия, о которые бьются чаще всего:

- **Зависимости остаются пошаренными.** При добавлении в папку доступ выдавался и сущности, и её зависимостям (лэндам и дестинейшнам кампании), а при изъятии снимается только с самой сущности. Лэнды когда-то пошаренной кампании останутся доступны — снимать их нужно отдельно, экшеном `Unshare` на самих лэндах.
- **Прямой личный шаринг снимается тоже.** Если сущность была пошарена этому же юзеру ещё и напрямую, помимо папки, вынос из папки удалит и этот доступ: происхождение гранта не различается. После выноса такой шаринг придётся выдать заново.

### Расшарил папку — что снимется с доступа

`Unshare` на папке снимает доступ к самой папке и к сущностям, которые в ней лежат, — кроме тех, доступ к которым ассайни сохраняет из другого источника (например, та же сущность лежит ещё в одной пошаренной ему папке).

Зависимости, уехавшие вместе с папкой (лэнды и дестинейшны её кампаний), **не отзываются**: они остаются пошаренными. То есть «расшарил папку» ≠ «отозвал всё, что через неё уехало» — остаточные доступы снимаются вручную, `Unshare` на самих сущностях.

### Для каких сущностей есть папки, а что шарится только поштучно

Папки есть не у всех сущностей. Они существуют для: Campaigns, Landings, Destinations, Sources, Trackers, Creatives, Content Library (`Lander Placeholder Groups`), Meta Social Profiles, Google Accounts. Исключение по раздаче доступа — папки Google Accounts: на их содержимое шаринг папки не распространяется, Google-аккаунты шарятся поштучно.

Папок **нет** у Domains, Servers, Flows, Distributions, Proxies, Presets, Fields, Metrics — эти сущности шарятся по одной (ПКМ → `Share`) или массовыми действиями `Share Also` / `Force Share`. Положить их в папку негде, поэтому «пошарить папку доменов или серверов» в AIO не работает.

## Скрыть флоу от байеров (Change Ownership)

Когда: байеры видят все флоу в кампании — хочется оставить им только нужные.

**Путь:** список флоу → ПКМ → `Change ownership` / `Mass change ownership`.

**Шаги:**

1. Выделить флоу (один или несколько).
2. ПКМ → `Change ownership` (на одном флоу) или `Mass change ownership` (на выделении из нескольких).
3. Выбрать **access type**:
   - `доступен всем` (Everyone) — флоу виден всем юзерам тенанта.
   - `по пошарке` (By Share) — флоу виден только тем, кому пошарен.
4. Подтвердить.

После переключения на `по пошарке` — флоу пропадает у тех байеров, кому не пошарен.

Также см. [models/permissions-model.md](../models/permissions-model.md) (модель Sharing / Ownership).

### Флоу рассылок (`Marketing → Flows`) прячутся так же

Список `Marketing → Flows` показывает не все флоу тенанта: юзер видит свои, пошаренные ему, флоу с access type `Everyone` и флоу подчинённых; роль полного доступа (Owner / Admin) видит все. Новый флоу рассылок создаётся с access type `By Share` — по умолчанию его видит только владелец, остальным его нужно пошарить.

В списке есть колонки `Owner` и `Access type`; у `Access type` тултип `Using for visibility only, everyone shared cannot edit anyway.` — access type управляет **только видимостью**, права на правку он не выдаёт. Колонка `Shares` (кому флоу пошарен) по умолчанию скрыта и включается в настройках таблицы.

Экшены те же, что на трафиковых сущностях: `Change ownership` / `Mass change ownership` и шаринг `Share also` / `Force share` / `Unshare`. Закрыты они собственной веткой прав — доступ к трафиковым флоу и кампаниям её не даёт (ветки перечислены в [models/permissions-model.md](../models/permissions-model.md)). Сама сущность — [models/marketing-flow.md](../models/marketing-flow.md).

### Видеть все флоу, ничего не шаря — ветка `Scopes`

Обратный ход к `By Share`: чтобы сотрудник видел все флоу тенанта и не пришлось шарить каждый по одному, в его Position включается право `Scopes: tracker flows` (`scopes.tracker.flows`) — с ним ограничение видимости по владению, шарингу и access type на флоу снимается.

Право снимает ограничение **только на просмотр**. Править чужой флоу оно не разрешает: правку без владения снимает ветка `Editor Scopes`, а она существует только для лэндов ([models/permissions-model.md](../models/permissions-model.md)). «Видит все флоу» и «может их менять» — разные вещи.

### Change Ownership на кампании

Аналогично — ПКМ на кампании → `Change ownership` (на выделении из нескольких — `Mass change ownership`) → выбрать целевого юзера + access type.

Также см. [how-to/campaigns.md](campaigns.md) → Change Owner.

## Типичные ошибки при работе с правами и юзерами

- **Удалил юзера через Delete — автор прошлых заливок стал empty.** Откатить нельзя. На будущее — **Deactivate**.
- **Дал юзеру Position, но он всё равно не видит.** Несколько Positions, конфликт Allow/Deny — выигрывает Position с **большим Priority** (слайдер в модалке Position). Проверить значение Priority у обеих. Внутри одной Position императивы применяются **сверху вниз** (`Deny` убирает, `Allow` добавляет) — нижний может перекрыть верхний; механика — [models/permissions-model.md](../models/permissions-model.md).
- **Без 2FA — часть полей скрыта.** Это by design. Включить 2FA через `@aio_tech_bot` (Telegram) или Google Authenticator.
- **Сделал Change Owner на кампании, но не стал Tenant Owner.** `Owner сущности` ≠ `Tenant Owner` — разные вещи; механика — [models/permissions-model.md](../models/permissions-model.md).
- **«Скройте этого юзера от других байеров».** Глобального скрытия нет by design.
- **Действие отклонено — `Read access denied` / `Edit access denied`.** У юзера роль не Owner/Admin и в Position нет нужного view/Action-императива; видеть ≠ редактировать — разбор.
