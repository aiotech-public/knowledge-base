# Permissions / Users / Sharing (How-to)

Практические процедуры по правам и юзерам в тенанте: добавить и деактивировать юзера, привязать к Position, пошарить сущность или папку, сменить владельца, скрыть чужие флоу. Модель доступа (уровни `Use` / `View` / `Edit` / `Own`, роли, Positions, команды, `Access type`, `Scopes`, тексты отказов) — в [models/permissions-model.md](../models/permissions-model.md).

---

## TL;DR

- Юзеры добавляются только инвайтом: `Settings → Users → +User` → `Generate Invite`; приглашают Owner и Admin. Уходящего юзера — деактивировать: `Settings → Users` → ПКМ → `Switch activity`.
- Position юзеру: `Settings → Positions` → вкладка `Assigned users`. Увидеть интерфейс глазами сотрудника — `Log in as user` (ERP, Owner / Admin).
- Шаринг: ПКМ по строке → `Share` → роль `Use` / `Viewer` / `Editor`, по желанию `Can share further` и срок. Шарит тот, у кого на объект уровень `Own`, или кому пошарили с `Can share further`.
- В ERP можно пошарить и папку — содержимое получает роль папки, включая то, что положат позже. В MTK списка папок в таблицах нет — там папки не создаются и не шарятся.
- Владелец и `Access type` меняются одним диалогом `Change ownership`; прежнему владельцу по умолчанию остаётся `Editor`.
- `Access type`: `Private` — только по доступу; `Use` (в API — `Everyone`) — все видят в списках и селектах, карточка закрыта; `View` — все читают. Правку `Access type` не открывает.
- Весь раздел без шаринга: `Scopes` — `View` на все объекты раздела, `Editor Scopes` — `Own`; ветки есть у 27 разделов, включая ассайны автоправил.
- Отказ `Action access denied (<ключ> required)` — не хватает права в Position; `No access to this object (<уровень> level required)` — уровня на объект. Уровень строки — внизу ПКМ-меню: `Your access: <уровень>`.

## Как добавить нового юзера

Единственный путь — **инвайт-линк**: `Settings → Users → зелёная кнопка +User`. Кнопка есть у Owner и Admin — приглашать может только полный доступ. Поля инвайта (Name / Code / Usages / Role / Position / Team) и кнопка `Generate Invite` — в [models/permissions-model.md](../models/permissions-model.md) → Invite User.

**Шаги:**

1. `Settings → Users → +User` → заполнить поля инвайта (Name / Code / Usages / Till Date / Role / Position / Team). Position в инвайте выбирается одна — остальные назначаются потом во вкладке `Assigned users` у позиции.
2. `Role` — это **роль тенанта**, не Position. При инвайте доступны `Admin` (полный доступ: уровень `Own` на все объекты тенанта) или `Employee` (доступ по уровням: своё, объекты нижестоящих по команде, пошаренное ему и его командам, объекты с `Access type` `Use` / `View`); роль `Owner` через инвайт не выдаётся. Тонкая настройка доступа Employee — через Positions (см. [models/permissions-model.md](../models/permissions-model.md)).
3. `Team` — команда, в которую человек попадёт; по инвайту он встаёт в неё на уровень 0 (самый нижний). Поднять уровень — в диалоге команды.
4. `Generate Invite` → отдать инвайт-код и ссылку новому юзеру.
5. Новый юзер регистрируется по ссылке (Name / Email / Telegram / Password), включает 2FA (через `@aio_tech_bot` в Telegram или Google Authenticator).

Если у человека **уже есть аккаунт AIO**, по инвайту он входит в тенант **тем же аккаунтом** — новый юзер не заводится. Запрос «дайте доступ к другому тенанту» = добавить существующий аккаунт в нужный тенант, а не создавать нового юзера. Один аккаунт-`User` живёт в нескольких тенантах, права в каждом свои ([models/user.md](../models/user.md)).

### Как самостоятельно проверить дефолтные доступы байера

**Быстрее всего — зайти под сотрудника с позицией `Buyer` через `Log in as user`** (ERP, для Owner и Admin): интерфейс откроется его глазами, и сразу видно, что из нужного ему не видно, а что лишнее видно. Как войти и выйти — секция «Как увидеть интерфейс глазами сотрудника — `Log in as user`».

Если сотрудника на этой позиции ещё нет или тенант в MTK — зарегистрировать **тестового юзера** на позицию `Buyer` из шаблона тенанта (её описание — «Launches and runs traffic. Sees only their own campaigns, no team data.») и открыть его в инкогнито. Проверять лучше до реального использования.

См. [models/permissions-model.md](../models/permissions-model.md) → эвристика «Обрезать всё, потом раздавать».

## Как удалить или деактивировать юзера

**Путь:** `Settings → Users` → ПКМ по юзеру → `Switch activity` или `Remove from tenant`. Пункты есть только у Owner и Admin; на строке Owner-а тенанта, своей строке и строке сотрудника AIO их нет. `Manage tenant` в меню профиля юзерами не управляет — там только название тенанта, `Billing Email` и IP-вайтлист.

**Разница:**

| Действие | Что происходит | Когда использовать |
|---|---|---|
| **`Switch activity`** | Юзер теряет доступ к этому тенанту, но остаётся в списке юзеров; включается обратно тем же пунктом | По умолчанию — когда юзер уходит из команды |
| **`Remove from tenant`** | Юзер убирается из тенанта: снимаются его роль в тенанте и членство в командах тенанта | Когда возвращать не планируется; вернуть — только новым инвайтом |

**Рекомендация:** по умолчанию — **`Switch activity`**: он откатывается тем же пунктом.

## Как привязать юзера к Position

**Путь:** `Settings → Positions → выбрать Position` → вкладка `Assigned users`. Одну Position можно выбрать и при инвайте; `Manage tenant` позиции не назначает.

**Шаги:**

1. Открыть нужную Position.
2. На вкладке `Assigned users` добавить юзера.
3. Если у юзера несколько Positions — задать **`Priority`** (слайдер 10–500, шаг 10). Позиции применяются по возрастанию `Priority`, поэтому при конфликте Allow/Deny выигрывает позиция с большим значением.
4. `Save`.

Также см. [models/permissions-model.md](../models/permissions-model.md) → Positions.

### Как посмотреть дефолтные доступы позиции Buyer

Когда: проверить, что входит в позицию `Buyer` из шаблона тенанта, до раздачи юзерам.

**Путь:** `Settings → Positions → Buyer` → вкладка `Imperatives`. Слева — императивы по порядку (`Allow` / `Deny`), справа — панель `Granted permissions`: итоговый список ключей этой позиции с поиском. Панель считает только эту позицию — другие позиции юзера в ней не учтены, поэтому итог для конкретного человека надёжнее проверить через `Log in as user`.

Рядом лежат остальные позиции шаблона — `Full Access`, `Team Lead`, `Tech`, `Analyst`, а в ERP ещё `Creative` и `Finance`; что в них собрано — [models/permissions-model.md](../models/permissions-model.md).

### Как увидеть интерфейс глазами сотрудника — `Log in as user`

**Owner и Admin тенанта могут войти под активного сотрудника своего тенанта и проверить, что ему доступно: `Settings → Users` → ПКМ по юзеру → `Log in as user` → подтвердить.** Интерфейс откроется с его правами — его позициями, командами и шарами: сразу видно, какие разделы, пункты меню и объекты ему открыты, а каких не хватает. Выход — `Exit` на плашке вверху страницы или `Exit impersonation` в меню профиля.

Сколько длится такая сессия, что под ней нельзя делать и как она отражается в логах — [models/permissions-model.md](../models/permissions-model.md) → «Как посмотреть интерфейс глазами сотрудника — `Log in as user`».

### Какие императивы включить, чтобы сотрудник работал с автоправилами

Раздел `Automations` (автоправила над сущностями Meta) открывается только своей веткой прав `automation.*` — доступ к рекламным кабинетам и страницам Meta его не даёт. Полный список императивов и что каким правом закрыто — [models/permissions-model.md](../models/permissions-model.md).

Два типовых набора для Position:

- **Собирает правила сам:** `automation.templates.view` и `automation.templates.edit` (шаблоны правил), `automation.assignments.view` и `automation.assignments.edit` (ассайны), `automation.assignments.edit.test-run` (прогон `Backtest Rules`), `automation.status.view` (страница статуса и проверка `Live check`).
- **Только подтверждает вердикты:** `automation.actions.view`, `automation.actions.edit.approve`, `automation.actions.edit.decline`. Права на шаблоны и ассайны такому человеку не нужны, но в `History` он увидит вердикты только тех ассайнов, которые ему видны по уровню доступа (свои, нижестоящих по команде, открытые через `Access type` и т.д. — секция «Выдал все права `automation.*`, а сотрудник не видит чужие ассайны»); все — при `scopes.automation.assignments`.

Наборы складываются: тому, кто и строит правила, и сам подтверждает их вердикты, нужны оба.

Если из всего перечисленного выдан только `automation.status.view`, пункт меню `Automations` не появится — меню открывают `automation.templates.view`, `automation.assignments.view` или `automation.actions.view`.

Помимо прав на сам раздел стоит проверить права **владельца ассайна** на сущностях Meta: действие уходит в рекламный кабинет с его правами, а не с правами того, кто его подтвердил. Как устроены сами правила — [how-to/auto-rules.md](auto-rules.md).

### Выдал все права `automation.*`, а сотрудник не видит чужие ассайны — это уровень доступа, не права

**Императивы `automation.assignments.*` открывают страницу ассайнов, а не чужие записи на ней: чужой ассайн виден, только если на него есть уровень доступа.** Ассайн видят владелец; участники с более высоким уровнем в команде владельца; равные по уровню, если у уровня настроено `Peers:`; позиции со `Scopes` / `Editor Scopes` на ассайны; Owner / Admin; прежний владелец, если при `Change ownership` осталась галка `Keep Editor access for the previous owner`; все в тенанте — если у ассайна `Access type` = `Use` (виден в списке) или `View` (открывается на чтение). Новый ассайн создаётся с `Access type = Private`. Кто что видит на каждой странице раздела — [how-to/auto-rules.md](auto-rules.md).

Пункта `Share` на странице ассайнов нет — пошарить ассайн нельзя. Рычаги:

- **Видеть все ассайны тенанта** — в Position `scopes.automation.assignments` (`View` на все); **владеть всеми** — `edit-scopes.automation.assignments` (`Own`: правка, смена владельца, архив). В матрице позиций эти ряды без подписи — искать по ключу.
- **Открыть один ассайн всем** — ПКМ → `Change ownership` → `Access type` = `View` (все читают) или `Use` (все видят в списке).
- **Отдать ассайн** — `Change ownership` на нужного юзера.

Править чужой ассайн через `Access type` нельзя: правку дают владение, более высокий уровень в команде, `Peers:` с `Edit` и выше, `Editor Scopes`, роль Owner / Admin или шара `Editor`, которая остаётся прежнему владельцу после `Change ownership`.

## Как пошарить сущность (Campaign / Landing / Domain) конкретному юзеру

**Шаринг выдаёт одному юзеру или команде доступ к одной сущности без правки Position: ПКМ по строке → `Share` (группа `Teams & permissions`) → слева выбрать юзеров или команды → справа задать роль → `Save`.** Шара на команду действует на всех её участников, уровень в команде не важен. Кто получил доступ — видно в колонке `Shares` на сущности (в части таблиц она скрыта по умолчанию и включается в настройках таблицы).

Шарятся кампании, лэнды, дестинейшны, источники, флоу, дистрибуции (включая `Rule Templates`), домены, серверы, провайдеры серверов / доменов / DNS, прокси, пресеты, поля, метрики, Money Streams, External Reports, шаблоны сообщений, Meta-профили и Meta-шаблоны, Google-аккаунты (только по одному), Content Library, макросы, формы, адвертайзеры, а в ERP — ещё и папки. Ассайны автоправил не шарятся.

### Кто может шарить — и почему у строки нет пункта `Share`

**Пункт `Share` есть у строки, если у вас на эту сущность уровень `Own` или её пошарили вам с `Can share further` — и в Position есть право `<раздел>.share` (например `tracker.campaigns.share`).** Уровень `Own` дают владение, более высокий уровень в команде владельца, `Peers: Own` у равных по уровню, `Editor Scopes` на раздел и роль Owner / Admin. С уровнем `Use`, `View` или `Edit` без `Can share further` пункта нет.

Свой уровень видно внизу ПКМ-меню строки: `Your access: <уровень>`, наведение показывает источник (`owner`, `shared with you`, `subordinate’s object`, `position`, `full access` и т.п.). Если сервер всё же отказал — `No access to share this object (own level or "can share" is required)`. Модель уровней — [models/permissions-model.md](../models/permissions-model.md).

### Что выбрать в диалоге `Share`: роль `Use` / `Viewer` / `Editor`, `Can share further`, срок

**У каждого получателя в правой колонке `With access` задаются роль, право раздавать дальше и срок.** Слева — `Users in tenant` с фильтром `All` / `Users` / `Teams`, поиском и кнопкой `Add all`; справа — таблица `Who` / `Role & share` / `Granted by` / `Expires` и кнопка `Remove all`. Сверху — ваш уровень: `Your access: <уровень> (<источник>)`.

- **Роль** — лесенка из трёх кнопок. `Use` — видит в списках и может выбрать в своих формах, настройки закрыты; `Viewer` — плюс открывает карточку на чтение; `Editor` — меняет настройки, теги, цвет, папку и запускает операционные действия. Новому получателю по умолчанию ставится `Viewer` (если ваш уровень ниже — `Use`). Роли выше вашего уровня не показываются.
- **`Can share further`** (иконка стрелок) — получатель сможет раздавать дальше с ролью не выше своей. Включить может только уровень `Own`; у остальных вместо переключателя — ненажимаемый значок, который только показывает, стоит ли флаг.
- **`Expires`** — по умолчанию `No expiry`, дата выбирается только в будущем. Просроченная шара остаётся в списке красной (`Expired: access is no longer active`) и доступа не даёт.

`Owner` шарингом не выдаётся: владение (а с ним архив и смена `Access type`) передаётся только через `Change ownership`. Старые шары с ролью `Share` или `Owner` показываются как `Editor` + `Can share further`. Убрать получателя — крестик в его строке (или перетащить влево) и `Save`.

### Чужая выдача в диалоге `Share` под замком — `Granted by`

**Без уровня `Own` менять и снимать можно только свои выдачи и выдачи тех, кто ниже вас по команде; чужие строки в `With access` закрыты замком.** Колонка `Granted by` показывает, кто выдал доступ: имя; `owner` — у старых шар и шар без автора (их трогает только уровень `Own`); `new` — у только что добавленных.

Наведение на замок объясняет причину: `Granted by someone else: you can only change or revoke shares granted by you or your subordinates`. Если такой запрос всё же дойдёт до сервера, ответ — `You can only change or revoke shares granted by you or your team members below you (this one was granted by the owner or another user)`. Снять чужую выдачу может владелец или любой, у кого на объект уровень `Own`.

### Шаринг кампании: Landings и Destinations получают роль `Use`

**Вместе с кампанией получатель получает её Landings и Destinations с ролью `Use`: они видны в списках и в карточке кампании, но их карточки не открываются и не правятся.** Список того, что уедет, — на вкладке `Details` после кнопки `Next` (вкладка есть, только если зависимости есть; подпись `Linked landers and destinations get the Use role, no choice here`). Срок шары кампании переносится на зависимости, `Can share further` — нет. Если у получателя на лэнд уже была шара выше `Use`, она не понижается.

Нужен просмотр или правка лэнда — пошарить его отдельно с `Viewer` / `Editor`.

Сам владелец кампании при её сохранении тоже получает `Use` на лэнды, дестинейшны, источник и домен из её настроек — если они чужие, не открыты всем через `Access type` и своей шары на них у владельца нет. Так в карточке кампании не остаётся неизвестных объектов; открыть или править их это не даёт.

### Как пошарить сразу несколько сущностей — `Share also`, `Force share`, `Unshare`

**Выделите строки — в ПКМ-меню появятся три массовых пункта шаринга, они действуют на все выделенные сущности сразу.**

- **`Share also`** — добавить доступ. Слева нет тех, у кого доступ уже есть ко всем выделенным. Существующая шара не понижается: роль только повышается, `Can share further` только добавляется, срок не меняется.
- **`Force share`** — перезаписать доступ (пункт помечен как опасный, в диалоге предупреждение `Access for selected users will overwrite previous access settings.`). Справа заранее стоят все, у кого есть доступ хотя бы к одной выделенной. Всем, кто остался справа, роль, `Can share further` и срок перезаписываются на **всех** выделенных сущностях, где хватает вашего уровня (остальные пропускаются — секция ниже). По умолчанию у них `Viewer` без раздачи и без срока: у кого был `Editor` — понизится, у кого был доступ к части сущностей — получит ко всем. Убранные влево теряют доступ.
- **`Unshare`** — снять доступ. Справа все, у кого есть доступ хотя бы к одной выделенной; уберите (крестик или `Remove all`) тех, у кого снять, и `Save`.

В массовом диалоге предлагаются все три роли и `Can share further` — хватает ли вашего уровня, сервер проверяет по каждой сущности отдельно. Модель — [models/permissions-model.md](../models/permissions-model.md).

### Массовое действие применилось не ко всем — `Applied` и `Skipped`

**Массовые действия применяются к сущностям, где вашего уровня хватает, остальные пропускаются с причиной; ошибка на всю пачку бывает, только когда ни одна выделенная сущность вам недоступна.** Итог — уведомление `Applied: N` · `Skipped: M` и строка на каждую причину с именами:

- `no access` — на сущность не хватает уровня: для шаринга нужен `Own` или шара с `Can share further`, для `Mass change ownership` — `Own`. Действие делает владелец.
- `role above your level` — выбранная роль выше вашего уровня на эту сущность; выберите роль ниже.
- `sharing rights require owner level` — `Can share further` выдаёт только уровень `Own`; выключите его или попросите владельца.
- `not granted by you` — без `Own` действие затронуло бы чужую выдачу; её меняет владелец.
- `not found` — сущность не найдена.

Если ни одна выделенная сущность не открыта вам даже на уровне, с которым действие её загружает (для шаринга — `Use`, для `Mass change ownership` и архива — `Own`), — `No access to the selected objects (<уровень> level required): '<имена>'` (403); если не найдена ни одна из выделенных — `Some UUIDs were not found in this model. No access to: '<…>'.` (404). Если `Use` на сущности есть, но раздавать их вы не можете, массовый шаринг не падает — приходит `Applied: 0` и список пропущенных.

### Скопировать чужую кампанию или лэнд — нужен хотя бы `View`

**Копия создаётся, только если исходник открыт вам хотя бы на `View` и в Position есть право копирования раздела: для кампаний — `tracker.campaigns.edit.copy`, для лэндов — `content.landings.edit` (отдельного ключа копирования у лэндов нет).** С одним `Use` (объект виден только в списках) копирование отклоняется: `No access to this object (view level required)`. Копия принадлежит тому, кто копировал, получает `Access type = Private` и имя `<имя> Copy`; шары оригинала на неё не переносятся, теги переносятся.

## Доступ ко всему разделу без шаринга — `Scopes` и `Editor Scopes`

**Чтобы сотрудник работал со всеми объектами раздела, а не с пошаренными по одному, в его Position включается ветка `Scopes` или `Editor Scopes` на этот раздел: `scopes.<раздел>` даёт уровень `View` на все объекты раздела, `edit-scopes.<раздел>` — уровень `Own`.**

Ветки есть у 27 разделов — от кампаний, флоу и лэндов до доменов, серверов и ассайнов автоправил; часть — только в ERP. Полный список по билдам — [models/permissions-model.md](../models/permissions-model.md).

В матрице позиций подписаны не все ряды: большинство `edit-scopes.*` и часть `scopes.*` (например `scopes.automation.assignments`) видны сырым ключом — искать их по ключу. Источник такого доступа в меню строки — `position`.

### Видеть все флоу (кампании, лэнды, ассайны) тенанта, ничего не шаря — `Scopes`

**`Scopes: <раздел>` открывает сотруднику все объекты раздела на просмотр: они видны в списках и селектах, карточки открываются только на чтение, аналитика по ним не режется.** Для флоу это `Scopes: tracker flows` (`scopes.tracker.flows`): ограничение по владению, шарингу и `Access type` снимается для всех флоу тенанта, включая флоу рассылок в `Marketing → Flows`. Так же `scopes.tracker.campaigns` открывает и ремаркетинг-кампании; кнопки действий в разделе ремаркетинга при этом всё равно требуют прав `marketing.*`. Для ассайнов автоправил — `scopes.automation.assignments` (ERP).

`Scopes` засчитывается и за права вида `<раздел>.view…` (например `content.landings.view.download`). Править объекты `Scopes` не разрешает — для этого `Editor Scopes`.

### Сотруднику нужно править чужие лэнды — `Editor Scopes`, а не шаринг по одному

**`Editor Scopes` на раздел даёт сотруднику уровень `Own` на все объекты раздела: видеть, открывать, править, шарить, менять владельца и `Access type`, архивировать.** Для лэндов это `Editor Scopes: content landings` (`edit-scopes.content.landings`), для кампаний — `edit-scopes.tracker.campaigns`, для доменов — `edit-scopes.tech.domains`, и так по каждому разделу из списка выше. Добавлять к нему `Scopes` не нужно: `Editor Scopes` уже даёт видимость и засчитывается за права `<раздел>.view…`, `<раздел>.edit…` и `<раздел>.share…`.

Не путать с шарингом папки (ERP): папка раздаёт доступ к конкретным сущностям, которые в ней лежат, а `Editor Scopes` даёт `Own` на весь раздел — включая объекты, которые кто угодно создаст позже.

## Как не шарить каждую сущность по одной — шаринг папки

**В ERP можно пошарить папку: доступ получает всё её содержимое одним действием, включая сущности, которые положат в неё позже.** В MTK кнопки списка папок в таблицах нет — там папки не создаются и не шарятся, сущности шарятся по одной или массово (`Share also` / `Force share`).

Шаринг папки — ответ на «замучился шарить каждый лэнд после создания»: папка становится общим контейнером доступа.

**Путь:** кнопка с иконкой папки в верхней панели таблицы раздела (`Content → Landings`, `Tracker → Campaigns` и т.п.; тултип `Folders: filter rows by folder, right-click a folder to edit, archive or share it`) → в выпадающем списке папок правый клик по нужной → `Share` → выбрать юзеров или команды и роль → `Next` → `Save`.

ПКМ-меню папки (`Edit folder`, архив, `Share`) открывается у тех, у кого есть право редактировать папки раздела (`content.landings.folders.edit`, `tracker.campaigns.folders.edit` и т.п.). Сохранить шаринг папки может Owner / Admin тенанта — или тот, кому папку пошарили с `Can share further`; остальным сервер отвечает `No access to share this object (own level or "can share" is required)`. Массового шаринга папок нет — папки шарятся по одной.

### Что уезжает вместе с папкой и какую роль получает содержимое

**Всё, что лежит в папке, получает роль папки принудительно, но без `Can share further`; зависимости содержимого получают роль `Use`.**

- **Сущности в папке** — роль и срок как у шары папки. Если у получателя на такую сущность уже была шара с другой ролью, она переписывается ролью папки — и вверх, и вниз. `Can share further` на содержимое не переносится, даже если он выдан на саму папку, а прежний на такой сущности сбрасывается.
- **Зависимости** (Landings и Destinations кампаний из папки) — роль `Use`, без понижения: если у получателя на лэнд уже была шара выше, она остаётся. Роль папки зависимостям не достаётся никогда.

Состав виден до сохранения — на вкладке `Details` после `Next` (подпись `Folder contents get the folder role`). Нужен конкретный уровень на конкретном лэнде — выставлять его шарингом самого лэнда, а не через папку.

### Положил сущность в уже пошаренную папку — доступ выдастся сразу

**Сущность, положенная в пошаренную папку, сразу раздаётся всем, кому пошарена папка.** Путь: ПКМ на сущности → группа `Folders` → `Assign to folder` → поле `Folder` (`Choose folder to assign`) → сохранить.

Каждый получатель папки получает на сущность ту же роль, `Can share further` и срок, что у его шары на папку, — прежняя его шара на эту сущность переписывается. Зависимости сущности (лэнды и дестинейшны кампании) получают `Use`.

Папка у сущности одна: в диалоге назначения выбирается **одна** папка, и назначение **заменяет** прежнюю. При переносе в другую папку получатели прежней папки, которым новая не пошарена, теряют доступ к сущности — вместе с их прямой шарой на неё; получатели новой папки получают её роль, `Can share further` и срок. Вложенных папок в AIO нет — уровень вложенности один.

### Убрал сущность из папки — что снимется с доступа, а что останется

**`Unassign from folder` снимает доступ к самой сущности у всех получателей папки.** Путь: ПКМ на сущности → группа `Folders` → `Unassign from folder` → подтвердить (`Are you sure you want to unassign?`).

- **Прямой личный шаринг снимается тоже.** У пары «сущность + получатель» одна запись доступа, происхождение не различается: если сущность была пошарена этому же получателю (юзеру или команде) ещё и напрямую, после выноса такую шару придётся выдать заново.
- **Зависимости, выданные при `Assign to folder`, снимаются вместе с сущностью**, если у получателя нет к ним другого пути (другой пошаренной ему кампании или папки, где они есть). Зависимости, выданные при шаринге самой папки (сущность к тому моменту уже лежала в ней), держатся до снятия шаринга папки. Шара на зависимость, которая была у получателя ещё до этого, остаётся.

### Расшарил папку — что снимется с доступа

**Снятие шаринга папки забирает у получателя доступ к папке, к сущностям в ней и к зависимостям, которые приехали с шарингом папки.** Путь: ПКМ по папке в списке папок → `Share` → убрать получателя из `With access` → `Save`.

Остаётся то, до чего получатель дотягивается другим путём — через другую пошаренную ему кампанию или папку (например, лэнд из папки используется в кампании, пошаренной ему отдельно). Прямая шара на сущность из папки другим путём не считается и снимается тоже — у пары «сущность + получатель» одна запись доступа. Не снимаются шара на зависимость, которая была у получателя ещё до шаринга папки, и зависимости, выданные при `Assign to folder` сущностям, положенным в уже пошаренную папку.

### Для каких сущностей есть папки, а что шарится только поштучно

**Папки (кнопка папок в верхней панели таблицы) есть в ERP у Campaigns, Sources, Destinations, Landings, Creatives, Content Library (`Lander Placeholder Groups`), Meta Social Profiles и Google Accounts.** Шаринг папки Google-аккаунтов раздаёт содержимое так же, как у остальных папок. У Creatives объектного доступа (владельца и шар) нет — их видят все, у кого есть право раздела, поэтому шаринг папки креативов на видимость не влияет.

Папок **нет** у Domains, Servers, Flows, Distributions, Proxies, Presets, Fields, Metrics и остальных сущностей — они шарятся по одной (ПКМ → `Share`) или массово (`Share also` / `Force share`). Положить их в папку негде, поэтому «пошарить папку доменов или серверов» не работает. Google-аккаунты без папки шарятся только по одному — массовых пунктов шаринга у них нет.

## Сменить владельца и `Access type` — `Change ownership`

**Владелец и `Access type` любой сущности меняются одним диалогом: ПКМ по строке → `Change ownership` (на выделении из нескольких — `Mass change ownership`).** Диалог один на всех сущностях с владельцем — от кампаний, лэндов и флоу до доменов и ассайнов автоправил; отдельного пункта `Change owner` нет.

Поля диалога (`Transfer ownership and update the access level.`):

- `Access type` — `Private` / `Use` / `View`: только по доступу / все видят в списках и селектах / все читают.
- `Tenant users` — новый владелец. В диалоге на одной строке по умолчанию стоит текущий владелец: чтобы поменять только `Access type`, его не трогайте.
- `Keep Editor access for the previous owner` — включена по умолчанию: при смене владельца прежний получает шару `Editor` (без `Can share further`, без владения и архива). Снимите галку — прежний владелец увидит объект только по общим правилам.

**Кто может:** тот, у кого на объект уровень `Own`, — владелец, участник с более высоким уровнем в команде владельца, равный с `Peers: Own`, позиция с `Editor Scopes` на раздел, Owner / Admin; плюс право `<раздел>.share.ownership` в Position (например `tracker.campaigns.share.ownership`). Отказ — `No access to this object (own level required)` или `Action access denied (<раздел>.share.ownership required)`. Владелец сущности — не `Tenant Owner`: смена владельца роль в тенанте не меняет.

### Что значит `Access type`: `Private`, `Use`, `View`

**`Access type` задаёт, что получают на объект все в тенанте; максимум — просмотр, правку он не открывает никогда.** В русском интерфейсе — `Приватный` / `Использование` / `Просмотр`.

- **`Private`** (в API — `By Share`) — все остальные не получают ничего: объект видят только те, у кого есть доступ по владению, команде, шаре, `Scopes` или роли.
- **`Use`** (в API — `Everyone`) — объект виден в списках и селектах, его можно выбрать в своей кампании или форме; карточка закрыта.
- **`View`** — плюс карточка открывается только на чтение.

У каких сущностей есть `Access type` и с каким значением они создаются — [models/permissions-model.md](../models/permissions-model.md). У кампаний, лэндов, прокси, Meta-профилей и Google-аккаунтов колонка `Access type` в таблице скрыта по умолчанию — включается в настройках таблицы.

### «Все видят, никто не правит» — `Access type = View`, а `Everyone` правку не открывает

**Чтобы объект все читали, но никто не менял, ставьте `Access type = View`; `Use` (в API — `Everyone`) не даёт даже открыть карточку.** Раньше `Everyone` открывал объект на правку любому с правом раздела — теперь это только `Use`, как и обещает тултип колонки (`Using for visibility only, everyone shared cannot edit anyway.`).

Правку дают только: владение, шара `Editor` (в том числе шара нижестоящего, поднятая к вам через `Below:`), более высокий уровень в команде владельца, `Peers:` с `Edit` или `Own` у равных по уровню, `Editor Scopes` на раздел и роль Owner / Admin.

Типовые настройки:

- все выбирают флоу в селекте кампании, но настройки закрыты — `Use`;
- все читают настройки, правит только владелец — `View`;
- одна команда правит, остальные только читают — `View` + шара `Editor` на команду.

## Скрыть флоу от байеров (Change ownership)

Когда: байеры видят в селекте кампании все флоу тенанта — хочется оставить им только нужные.

**Путь:** `Tracker → Flows` → ПКМ по флоу → `Change ownership` (на выделении из нескольких — `Mass change ownership`).

**Шаги:**

1. Выделить флоу (один или несколько).
2. ПКМ → `Change ownership` или `Mass change ownership`.
3. Выбрать **`Access type`**:
   - `Private` — флоу видят только те, у кого к нему есть доступ: владелец, кто выше него по команде, кому пошарили, позиции со `Scopes`;
   - `Use` — флоу видят все в списке и в селекте кампании, но не открывают;
   - `View` — плюс все открывают его на чтение.
4. `Tenant users` — оставить текущего владельца или выбрать нового; `Keep Editor access for the previous owner` — по необходимости.
5. Сохранить.

После переключения на `Private` флоу пропадает у байеров без доступа к нему. Байеру, которому флоу нужен, — пошарить его с `Use` (чтобы выбрать в кампании) или `Viewer` / `Editor`. Модель — [models/permissions-model.md](../models/permissions-model.md).

### Флоу рассылок (`Marketing → Flows`) прячутся так же

**Список `Marketing → Flows` показывает флоу по тем же уровням доступа, что и трафиковые: свои, флоу нижестоящих по команде, пошаренные вам и вашим командам, флоу с `Access type` `Use` / `View`; все — при `Scopes: tracker flows` и у Owner / Admin.** Новый флоу рассылок создаётся с `Access type = Private` — по умолчанию его видят владелец и те, у кого доступ по команде или позиции.

В списке есть колонки `Owner` и `Access type`; колонка `Shares` (кому флоу пошарен) по умолчанию скрыта и включается в настройках таблицы.

Экшены те же, что на трафиковых сущностях: `Change ownership` / `Mass change ownership` и шаринг `Share` / `Share also` / `Force share` / `Unshare`. Права на них — ветка `marketing.flows.*` (`marketing.flows.share`, `marketing.flows.share.ownership`); права на трафиковые флоу и кампании её не дают (ветки перечислены в [models/permissions-model.md](../models/permissions-model.md)). Сама сущность — [models/marketing-flow.md](../models/marketing-flow.md).

## Типичные ошибки при работе с правами и юзерами

### Типичные ошибки с юзерами и позициями

- **У юзера в `Settings → Users` нет пунктов `Switch activity` / `Remove from tenant`.** Их видят только Owner и Admin, и не на строке Owner-а тенанта, своей строке и строке сотрудника AIO. В `Manage tenant` управления юзерами нет.

- **Дал юзеру Position, но он всё равно не видит раздел.** При конфликте Allow/Deny между Positions выигрывает позиция с **большим `Priority`**; внутри одной Position императивы применяются **сверху вниз**. Итог проверить через `Log in as user`; механика — [models/permissions-model.md](../models/permissions-model.md).

- **Действие отклонено — `Action access denied (<ключ> required)`.** В Position не хватает права на это действие; нужный ключ назван в тексте — добавить его (или раздел-префикс) в `Allow`. Owner / Admin эту проверку проходят всегда.

- **`Read access denied` / `Edit access denied`.** Открыт или сохраняется чужой профиль юзера — свой профиль правит только сам юзер. К правам Position эти тексты отношения не имеют.

- **Без 2FA — часть полей скрыта.** Это by design. Включить 2FA через `@aio_tech_bot` (Telegram) или Google Authenticator.

- **«Скройте этого юзера от других байеров».** Глобального скрытия нет by design.

### Типичные ошибки с доступом к объектам и шарингом

- **Раньше флоу с `Access type = Everyone` открывался и правился, теперь не открывается.** `Everyone` теперь — уровень `Use`: объект виден в списках и селектах, карточка закрыта. Все должны читать — `Access type = View`; править — шара `Editor`, уровни команды или `Editor Scopes`.

- **Объект не открывается: тост `Sorry, you do not have access`, иконка строки `No access to open` или 403 `No access to this object (<уровень> level required)`.** Не хватает уровня на объект — смотрите `Your access: <уровень>` внизу ПКМ-меню строки. С `Use` карточка закрыта, с `View` — только чтение (`Read-only` вместо сохранения), правка — `Edit`, шаринг — `Own` или `Can share further`, смена владельца и архив — `Own`.

- **Копия не создаётся — `No access to this object (view level required)`.** На исходник только `Use`; для копии нужен хотя бы `View`.

- **Тимлид не видит объект своего баера.** Объекты баера видит только участник с **более высоким** уровнем в той же команде; равные по уровню по умолчанию друг друга не видят (это меняет `Peers:`). Пошаренное баеру поднимается к тимлиду только в режиме `Below: Owned and direct shares` или `Below: Owned and all shares`; по умолчанию (`Owned only`) — только объекты во владении баера. Настройка — в диалоге команды.

- **`Change ownership` на кампании не сделал меня Tenant Owner.** Владелец сущности ≠ `Tenant Owner` — разные вещи; механика — [models/permissions-model.md](../models/permissions-model.md).

### Из подменю ремаркетинга пропала страница `Other`, хотя `Campaigns` открывается

**Страница аналитики рассылок `Other` закрыта правом `marketing.campaigns.view.analytics` (в матрице Positions — `Remarketing: analytics pages`); оно вложено в `marketing.campaigns.view` по префиксу, поэтому `Allow marketing.campaigns.view` (как и `marketing.campaigns`, `marketing`) открывает и `Campaigns`, и `Other`.** Если `Campaigns` открывается, а `Other` нет, в позициях юзера стоит `Deny marketing.campaigns.view.analytics` — ниже `Allow` в той же позиции или в позиции с большим `Priority`; убрать этот `Deny`. Отдельным `Allow` страницу `Other` можно выдать и без `Campaigns`.

Роли полного доступа (Owner / Admin) проходят без этого права. То же в обоих билдах — в MTK страница `Other` живёт во вкладке `PWA` платного модуля. Подробнее — [how-to/remarketing-campaigns.md](remarketing-campaigns.md).
