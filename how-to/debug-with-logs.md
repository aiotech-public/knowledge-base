# Debug с логами AIO

«Лид ушёл, а рекламодатель не подтверждает», «фильтр не работает», «AIO Meta не пуллит», «AIO вообще принял мой клик?», «кто поменял настройку» — почти любой такой разбор начинается с логов. Этот документ — как читать логи AIO: где какой namespace в `Settings → Logs`, как поймать конкретный визит фильтром `Loggable UUID`, что показывают логи сущности и почему без привязки к Telegram нотификации из логов не приходят.

---

## Какой лог для чего — быстрая справка

- **В ERP ПКМ по визиту → `Visit logs`** — быстрый путь к логам одного визита (уже отфильтровано по нему). Для детальной отладки добавьте уровень `Debug` в `Severity` — детали ниже. В MTK используйте `Settings → Logs` и `Loggable UUID`. Рядом `Visit timeline` — те же события хронологией ([how-to/visit-timeline.md](visit-timeline.md)).
- **`Settings → Logs`** — центральное окно логов: дропдаун `Namespace` задаёт тип логов (`Destination Handler`, `Tracker`, `Traffic Filter`, `Conversions`, `Remarketing` и другие — разбор ниже), фильтр `Loggable UUID` ловит визит, конверсию или сообщение рассылки.
- **Логи сущности** (`Domain logs`, `Source logs`, `Tracker logs` и другие) — JSON-записи действий и сообщения соответствующей подсистемы. Запись действия содержит переданные аргументы и результат; это не гарантированный полный снимок всех настроек. Для домена `Domain logs` показывает и репойнт сервер→сервер.
- **Debug JSON визита** — одно из двух мест с сырым JSON визита (другое — отчёт визита через `Show Visit`).

- **`Destination Handler`** — namespace логов для **диагностики пуша** в Destination. На лэнде виден только бинарный исход (`success: true/false`); причина реджекта дублируется в поле визита `last_rejection_reason` (+ `Rejected Destination` / `Rejected Advertiser`).
- **Без привязки к Telegram сообщения `AIO-tech-bot` не приходят.** Прямые сообщения бота (алерты мониторинга и т. п.) доставляются только в Telegram — нужна привязка аккаунта к TG (`Profile settings`); 2FA через Google Authenticator её не заменяет. Уведомления центра нотификаций идут в колокольчик и могут уходить в Slack без Telegram — [mechanics/notification-center.md](../mechanics/notification-center.md).

## Самый быстрый путь к логам одного визита — ПКМ → Visit logs (ERP)

Когда нужны логи по **одному конкретному визиту** (что с ним происходило, почему зарубило, что ответил Destination), не обязательно копировать `Visit UUID` и идти в `Settings → Logs`. В ERP быстрее — **правый клик по строке визита в `Tracker → Visits` → `Visit logs`**: откроются логи, уже отфильтрованные по этому визиту. В MTK используйте `Settings → Logs` с UUID визита в `Loggable UUID`.

**Если таблица пустая, проверьте `Severity`: по умолчанию `Debug` исключён.** Детальная отладка фильтра и пуша пишется на этом уровне. Выбор только `Debug` покажет только Debug-записи; для всех уровней выберите `Debug`, `Info`, `Success`, `Warning` и `Error`. Период и остальные фильтры продолжают действовать.

Что внутри: **записи, привязанные к визиту** — проверки шага `Filter` и подключённого фильтра, пуши в Destination. Состав запроса и ответа в записи зависит от интеграции; при ошибке ищите текст ошибки и причину реджекта. Это более простой путь, чем копировать `Visit UUID` и вручную собирать фильтр в `Settings → Logs`; ручной путь ниже нужен, когда фильтруешь сразу по нескольким визитам или заходишь в логи не от строки визита.

Рядом в контекстном меню — **`Visit timeline`**: та же диагностика визита, но как хронология событий (какие поля когда и на что менялись, какие конверсии заспавнились, в какие Destination визит попал). Разбор — [how-to/visit-timeline.md](visit-timeline.md).

## Как открыть логи компонента — кнопка Settings → Table settings → Namespace

Когда нужно посмотреть логи конкретного компонента (Destination Handler / Traffic Filter / Tracker): **`Settings → Logs` → справа над таблицей кнопка `Settings` (если выбран пресет — на ней стоит его имя) → пункт `Table settings` → выбрать `Namespace` (например, `Destination Handler`) → `Apply`.** Как устроены настройки таблицы и пресеты — [reference/ui-common.md](../reference/ui-common.md).

**Дропдаун `Namespace` перечисляет все неймспейсы системы — их больше двух десятков, закрытым списком из четырёх он не ограничен.** Ходовые в разборах:

- **`Destination Handler`** — обмен при пуше визита в Destination.
- **`Tracker`** — исходящие отбивки конверсий в рекламные платформы.
- **`Traffic Filter`** — проверки трафика: что решили трафик-фильтры и антифрод по визиту (антифрод логирует под этим же namespace, отдельного `Antifraud` в дропдауне нет).
- **`Conversions`** — жизнь конверсий: как создана, что пришло постбэком.
- **`Remarketing`** — отправка сообщений рассылок: скипы по лимитам, отсутствие push-подписки у визита (сами рассылки — [how-to/remarketing-campaigns.md](remarketing-campaigns.md)).
- **`Monitoring`** — серверы и домены: смены статуса от мониторинга, репойнт и его повторы, проверки после выпуска домена и установки сервера, заказ сервера у провайдера, зависшие операции, кому ушёл Telegram-отчёт.

Нужного типа логов в этом списке нет — открой дропдаун целиком: у подсистем есть собственные неймспейсы помимо перечисленных.

**Фильтрация по сущности (`Table settings`):** ввести UUID сущности (Visit, Conversion, а для логов рассылки — сообщения) в поле `Loggable UUID` + выбрать `Namespace` — останутся только логи этой сущности. Под задачу: `Destination Handler` — ошибка пуша в Destination; `Conversions` — логи по конверсиям.

### Где кнопка Severity (Debug / Info / Success / Warning / Error)

**`Severity` — отдельная кнопка рядом с фильтром, а не пункт внутри `Table settings`.** Уровни: Debug / Info / Success / Warning / Error. Для детальной отладки добавьте `Debug` к выбранным уровням: на нём пишутся ответы интеграций и диагностические записи. Если выбрать только `Debug`, записи других уровней не попадут в результат. Уровень работает вместе с остальными фильтрами — например, с `Loggable UUID`, когда разбираете один конкретный визит.

### Поле Message пустое или скрыто — нужен 2FA-код

**Если включена защита данных 2FA, вместо текста `Message` показывается `Protected` до ввода кода.** Это относится и к `Settings → Logs`, и к `Tracker logs`. Пустой текст сам по себе не доказывает блокировку 2FA: проверяйте именно значение `Protected`.

## Loggable UUID — отслеживание конкретного визита

Чтобы посмотреть всё, что произошло с конкретным визитом:

1. Получаете `Visit UUID` (из отчёта визита / `Show Visit`).
2. `Settings → Logs` → фильтр `Loggable UUID = <VISIT_UUID>`.
3. Видите записи, привязанные к UUID визита, например проверки шага `Filter` и пуши `Destination Handler`. Их набор зависит от пройденных шагов и выбранных уровней `Severity`.

**Namespace `Conversions`** показывает логи по конверсиям и как именно конверсия создана — шагом флоу `Spawn Conversion` или из постбэка. Loggable UUID при этом — **Conversion UUID** (не Visit UUID).

**Ручной запуск конверсии тоже попадает в логи — но на визит, а не на конверсию.** Когда конверсию триггерят руками из интерфейса, в namespace `Conversions` пишется запись уровня `Info` с текстом `Manual conversion trigger requested` и указанием типа конверсии, а Loggable UUID у неё — **Visit UUID**. Поэтому «кто и когда дёрнул конверсию вручную» ищется по UUID визита, а не по UUID конверсии — по конверсии этой записи не видно.

### Сообщение рассылки срезал лимит — искать по UUID сообщения, не визита

**Когда лимит срезает уже созданное сообщение рассылки, запись в логах есть — но `Loggable UUID` у неё — UUID сообщения из `Marketing → Messages` (ERP), а не UUID визита и не идентификатор пуш-события.** По UUID визита такая запись не найдётся — отсюда и ощущение «в логах ничего нет».

Что искать: namespace `Remarketing`, уровень `Error`, текст `Remarketing send skipped by limit: <причина> (campaign <uuid>)`. Причины пишутся дословно — `daily_limit`, `hourly_limit`, `min_interval`.

**Лог пишется к сообщению рассылки, поэтому он есть только тогда, когда лимит сработал уже на отправке.** Если лимит срезал визит ещё на этапе посева, сообщения не создаётся вовсе — искать в логах нечего, результат виден только в аналитике (`Send Result` / `RMK Send Results`).

Второй след того же события — remarketing-событие `Failed` с той же причиной. Сам визитёр при этом ничего не замечает: сообщение просто не уходит. Какие лимиты действуют и как они считаются — [how-to/remarketing-campaigns.md](remarketing-campaigns.md).

### «AIO принял мой клик?» — полный путь от UUID до логов визита

Когда: «AIO принял мой клик?» / «Что произошло с этим конкретным визитом?».

> Быстрее всего — **в ERP ПКМ по визиту → `Visit logs`** (уже отфильтровано по нему; для детальной отладки добавьте `Debug` в `Severity`, см. раздел выше). Ручной путь ниже нужен, когда UUID уже на руках или заходишь в логи не от строки визита.

Ручной путь — UUID визита и восемь шагов:

1. Перейти `Tracker → Visits`.
2. Найти нужный визит (через фильтр по дате / гео / Source).
3. Добавить колонку `UUID` через кнопку `Settings` → `Table settings` (если её нет) → копировать значение.
4. Перейти `Settings → Logs`.
5. Проверить остальные фильтры и убрать мешающие; для полного сброса настроек используйте пункт `Reset settings` в меню кнопки `Settings`: он снимает фильтры, пресет, сортировку и порядок колонок разом (период дат не трогает).
6. Добавить фильтр **`Loggable UUID = <UUID визита>`**.
7. Добавить **`Debug` в `Severity`**.
8. Если `Message` показывает `Protected`, ввести код **2FA** для просмотра текста.

После — видны подходящие под период и фильтры записи по UUID визита: например проверки шага `Filter` и пуши `Destination Handler`.

## Логи сущности (Show logs) — кто и когда менял настройки

Пункт логов сущности открывает окно записей по её UUID: например, `Domain logs`, `Source logs` или `Tracker logs`. **JSON-запись действия содержит его аргументы и результат; это не полный снимок всех настроек после любого изменения.**

- Отдельного диффа настроек в окне нет: сопоставьте аргументы соседних записей действий вручную.
- Доступ: правый клик по сущности → пункт её логов; пункт открывается правом Position `settings.logs.view` (`Settings: logs page`) — тем же, что и страница `Settings → Logs`.

Применение: «кто и когда поменял настройку X» — ищите запись действия и сравнивайте переданные значения с предыдущими записями. Чувствительные ключи могут быть заменены на `*****`.

### Нет пункта Show logs / Visit logs или раздела Settings → Logs — какое право нужно

**Для ролей с ограниченным доступом логи открываются правом Position — `settings.logs.view` (в списке императивов — `Settings: logs page`): и страница `Settings → Logs`, и пункт логов на сущности, и `Visit logs` на визите, и логи трекера.** Отдельных прав на логи по разделам (вида `Show Logs: <раздел>`) больше нет — выдавать их не нужно, старые такие императивы ничего не открывают.

Окно логов сущности показывает те же записи, что и `Settings → Logs`. Роли с ограниченным доступом для него нужен Allow на `settings.logs.view`; роли с полным доступом видят логи без отдельных Allow в Position. Нет пункта логов сущности в меню правого клика или раздела `Logs` в `Settings` — добавьте в Position юзера Allow на `settings.logs.view` (или на весь раздел `settings`). Пункт `User logs` в `Settings → Users` показывается по праву на просмотр юзеров (`settings.users.view`), но логи юзера и там открываются только с `settings.logs.view`. Как устроены Positions и Allow/Deny — [models/permissions-model.md](../models/permissions-model.md).

### Логируется ли репойнт домена сервер→сервер

Да. Репойнт домена пишется в **логи домена (`Domain logs`)** — окно, которое открывает `Domain logs` на домене ([how-to/domains.md](domains.md) → Action Menu), — и в `Settings → Logs` под namespace `Monitoring`. Записи: `Repoint requested: server <IP> down → <IP>` (авто-репойнт), `Repoint attempt <n> of 6 failed, retry in <N> s: <ошибка>` (`Warning`), `Repoint done: domain points to <IP>` (`Success`), `Repoint failed: <ошибка>` (`Error`), `Repoint impossible — left in Danger: <причина>`. Там же — смены статуса от мониторинга (`Monitoring: Running → Danger: <причина>`) и итог проверки домена (`Provision check OK: …` / `Provision check: all 24 attempts failed: …`). Логи сервера (`Server logs`) несут то же для сервера: падение и восстановление, решение о переносе его доменов при падении сервера, итог проверки установки.

## Debug JSON визита — сырые поля визита

Одно из двух мест с сырым JSON визита (другое место — отчёт визита, через `Show Visit`).

Применение: посмотреть точные значения всех полей визита, включая системные (fingerprint, headers, agent_version) — когда нужно проверить, что именно записалось в поле, а не как значение отрисовано в таблице.

### В значении параметра знак `�`, в логе визита `Invalid UTF-8 in query params` — битый байт в ссылке

**Если в параметре ссылки пришёл байт, который не складывается в UTF-8 (например, `campaign_name=…%8D`), AIO заменяет его знаком `�` (U+FFFD) и сохраняет визит со всеми остальными параметрами.** Для визита, не опознанного ботом, AIO пишет в лог (namespace `Traffic`, уровень `Warning`) `Invalid UTF-8 in query params, replaced with U+FFFD: <параметры>` — список параметров, где была замена.

Причину ищут там, где ссылку собирают или переписывают до перехода на домен AIO: например, промежуточная страница, перекодирующая параметры, или макрос площадки, обрезанный посреди многобайтного символа. Так же AIO чистит битые байты в заголовках запроса и в `User-Agent`.

## Destination Handler — диагностика пуша

**`Destination Handler` — namespace для диагностики пуша в Destination.** При успехе интеграция может вернуть `Push Log` с данными обмена; состав запроса и ответа в нём зависит от типа интеграции. При отказе AIO пишет текст ошибки. Отказ может возникнуть ещё до запроса рекламодателю — например, из-за заполненной капы.

Текст отказа сохраняется и в поле визита `last_rejection_reason`.

### «Лид ушёл, рекламодатель не подтверждает» — где причина реджекта

На лэнде у визита виден только бинарный исход: `success: true/false`. **Ответ или ошибку пуша ищут в логах** `Destination Handler`; полного ответа рекламодателя в каждой записи может не быть. Но причина реджекта при этом пишется **прямо в поле визита `last_rejection_reason`** (плюс `Rejected Destination` / `Rejected Advertiser` — какой Destination и адвертайзер отклонили лид), так что для быстрой диагностики логи открывать не обязательно — поля видны в `Tracker → Visits`.

Симптомы «лид зарубило», «лид ушёл, а рекламодатель (в обиходе — брокер) не подтверждает» разбираются так: взять `Visit UUID` → `Settings → Logs` → namespace `Destination Handler` → `Loggable UUID = <VISIT_UUID>` → проверить текст ошибки пуша и доступные данные обмена.

## Логи Traffic Filter — почему поле визита пустое

**Если Traffic Filter оставил поле визита пустым, начните с Debug-логов визита.** Там могут быть записи, которые вернула интеграция, и текст её ошибки; пустое поле не гарантирует наличие дословного ответа.

- Путь: `Visit UUID` → `Settings → Logs` → `Loggable UUID = <VISIT_UUID>` → Severity `Debug`.
- Проверить записи `Log: …, Filter …` и `Filtered Error: …, Filter …`. Набор данных зависит от интеграции: при ошибке соединения в записи бывает только текст ошибки.

### Сторонний фильтр возвращает 403 Forbidden — что делать

Запись `Filtered Error: <ошибка>, Filter <имя> - <uuid>` в Debug-логах по `Visit UUID` означает ошибку выбранного фильтра. Сверьте имя и UUID из сообщения, затем тип и настройки фильтра. Если `403 Forbidden` вернул API стороннего поставщика, проверьте доступ к нему и обратитесь в его поддержку с этим ответом.

## Логи трекера — что AIO реально отправил наружу

**`Tracker logs` доступен у трекеров разных типов, включая постбэк-трекеры и FB CAPI.** Записи показывают результат выполнения интеграции, время и ответ либо ошибку. Состав данных зависит от типа: например, TikTok записывает ответ платформы, без outgoing payload.

- Путь: `Tracker → Trackers` (в MTK — `Settings → Trackers`) → ПКМ на нужном tracker или постбэк-трекере → `Tracker logs`.
- Поиск по конкретной конверсии — ввести Conversion UUID в строку поиска.
- Текст лога — в поле `Message`; при включённой защите данных 2FA до ввода кода показывается `Protected`.

Применение: «AIO отправляет ли Lead в рекламную платформу / в постбэк-трекер?» → `Tracker logs` на нужном трекере → результат отправки и доступные данные запроса или ответа. Полная механика логов трекера — [models/tracker.md](../models/tracker.md).

### Facebook Pixel events не логируются

AIO **не хранит логи событий Facebook Pixel**. В логи попадают только конверсии, отправленные через **CAPI**; кастомные Pixel-события (когда Pixel-код добавлен на лэнд или как макрос, см. [how-to/landings.md](landings.md)) в логах AIO **не трекаются**.

Применение: если вы гоняете события через Pixel (а не CAPI) и не видите их в логах — их там и не будет: логируется только CAPI-отбивка.

### Conversion Postback логируется только при успешном создании конверсии

`Conversion Postback` **логируется только при успешном создании конверсии**. Если постбэк пришёл, но конверсия не создалась (нет такого `Conversion Type`, нет визита с таким `visit_uuid`) — в логах постбэков **этого не будет**. Поэтому пустой лог ещё не значит «постбэк не приходил».

## Нотификации из логов не приходят — проверьте привязку к Telegram

Без привязки аккаунта к Telegram сообщения `AIO-tech-bot` (например, алерты мониторинга) **не приходят** — прямые сообщения бота доставляются только в TG; уведомления Notification Center при этом идут в колокольчик и в Slack / Telegram по Preferences ([mechanics/notification-center.md](../mechanics/notification-center.md)). 2FA через Google Authenticator привязку к TG не даёт, так что «2FA включена» ещё не значит, что нотификации пойдут. Типичная картина: нотификации выглядят «сломанными», а на деле просто не подключён Telegram.

Если алерты по серверам и доменам ждёт команда, привязка нужна у назначенного `Monitoring User` — как он задаётся, см. [context/architecture.md](../context/architecture.md) (`AIO-tech-bot`, 2FA, Monitoring User).

### Как подключить Telegram для нотификаций

1. `Profile settings` (правый верх).
2. Указать в профиле свой Telegram username — тот же аккаунт, с которого будете писать боту.
3. Для настройки Telegram-2FA выбрать метод `Telegram`. Если уже включён другой метод 2FA, сначала выключить его кодом этого метода.
4. Через QR / поиск `@aio_tech_bot` открыть бота в Telegram и послать `/setup2fa`.
5. Нажать `Enable 2FA` и ввести 4-значный код (эта же привязка используется для 2FA через Telegram).

Без этого `AIO-tech-bot` молчит — легко подумать, что нотификации сломаны, хотя просто не подключён TG.
