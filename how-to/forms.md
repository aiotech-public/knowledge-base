# Forms (How-to)

Форма на лэнде решает две задачи разом: собирает введённые визитом данные в поля визита и на сабмите толкает визит дальше по флоу — на пуш лида в Destination. Этот файл — про то, как поставить форму, связать её поля с полями визита, настроить гео-зависимую валидацию телефона (`intl-tel-input`) и что проверять, когда «форма не сабмитится» или лид не пишется. SDK-форма vs Non-SDK Form Handler, обязательные slug-маппинги, override per-tenant.

---

## TL;DR

- **SDK-форма (`{{form}}`)** — основной путь. Настраивается в `Settings → Forms`. Controls + Layouts + Steps + Languages + Behavior. Рекомендуется.
- **Non-SDK Form Handler** — фолбэк, если своя HTML-форма. Цепляется к тегу `<form>`. **Активно не развивается.**
- **Slug инпутов** при Non-SDK Form Handler обязаны совпадать с AIO-слагами: `first_name`, `last_name`, `email`, `phone`. Без этого данные не маппятся.
- **Layouts отвечают только за визуальное расположение**, не за маппинг. Если у получателя данные перепутаны (в поле телефона — имя) — смотреть Controls.
- **Форма мультиязычная:** `Base language` + добавленные языки, авто-переключение по языку браузера визитёра. Авто-перевод заполняет только четыре стандартных контрола и кнопку Submit — **непереведённая строка уезжает на лэнд пустой** (у поля не будет ни подписи, ни плейсхолдера).
- **Валидация телефонов** — сторонняя либа `intl-tel-input.com`. По странам ведёт себя по-разному (DE — `strictMode: false`; BR — 10 и 11 цифр валидны).
- **`Required` на Form Control** (в Form Builder, `Settings → Forms → Controls → инпут`) — **есть**, ставится в правилах инпута. **`required` на поле визита** (`Settings → Fields`) — **нельзя** напрямую; для полей визита обязательность задаётся через `Link Generator`. Это **два разных контекста**.

## SDK-форма vs Non-SDK Form Handler — что выбрать

| | SDK-форма | Non-SDK Form Handler |
|---|---|---|
| Куда вставляется | `{{form}}` на лэнде | На обычную `<form>` лэнда |
| Setup | `Settings → Forms → +Form` | `Content → Macros` → подключить `AIO Non-SDK Form Handler` |
| Slug-маппинг | Авто | **Обязан совпадать** буквально: `first_name`, `last_name`, `email`, `phone` |
| Customisable submit/before | Да (Submit Promises, Before Submit Promises) | Ограниченно |
| Pushing modal / autologin | Да | Нет |
| Form Builder UI | Полная конфигурация Controls / Steps / Layouts / Languages | — |
| Активная разработка | Да | **Нет** (фолбэк) |

Рекомендация: **SDK-форма для всех новых лэндов**. Non-SDK — только если редизайн SDK-формы под существующий лэнд слишком сложен.

> **Отдельные push-скрипты на лэнде не нужны** (ни для SDK-формы, ни для Non-SDK Form Handler). Push-попытка (доставка лида) срабатывает сама, когда визитёр заполнил форму и нажал submit. Если на лэнде уже есть свои push-скрипты — **удалить**, иначе конфликт.

## Form Builder — 6 вкладок и что в каждой

`Settings → Forms → +Form / Edit Form` — 6 вкладок конструктора: `Info` (Name, Description, Tags, Base language, **Color**, **Icon**), `Controls` (инпуты и правила валидации), `Steps` (шаги), `Layouts` (раскладка), `Languages` (переводы), `Preview` (превью). Полное описание концепта — [models/form.md](../models/form.md).

В упрощённом виде системы конструктора форм нет — контролы задаются макросами, блоком `config.form` в макросе `AIO SDK Macros Collection` (`Settings → Macros`). Дефолтный набор полей тот же. Плейсхолдер `{{form}}` и сам SDK-компонент в обоих видах одинаковы.

> Действия над формой (правый клик по строке): `Edit form`, `Form builder`, `Copy form`.

### Каждый Control (`Control settings`) и маппинг контрол↔поле визита

Открывается по шестерёнке у контрола в Form Builder. Именно привязка `Field` определяет, куда уйдёт введённое значение. Поля:
- **Type** — тип контрола, показывается человеческим названием: `String text`, `Phone`, `Email`, `Checkbox`, `Drop list`, `Number`, `Date`, `Text area`. У нового контрола подпись по умолчанию равна названию его типа.
- **Label** / **Placeholder** / **Value** — подпись, плейсхолдер и значение по умолчанию.
- **Field** — на какое **поле визита** пишется значение (напр. `Visit → First Name`). Это и есть slug-маппинг: контрол ↔ поле визита. У контрола есть `key` (slug).
- **Attributes** — правила валидации: `required` (Boolean), `minlength`, `maxlength` (можно добавлять ещё через `+ Attribute`). Дефолт для First Name: `required` + `minlength 1` + `maxlength 64`.

Дефолтная форма (`Default Leads Form`) = 4 контрола — First Name, Last Name, Email, Phone, каждый смаплен на одноимённое поле визита (совпадает с дефолтом SDK-формы, см. [reference/sdk.md](../reference/sdk.md)).

### Поля визита, которые SDK заполняет без контрола — Screen Dimensions

Поле визита `Screen Dimensions` (одно поле) собирается автоматически как часть SDK из `browser_window_width` / `browser_window_height` (см. [reference/sdk.md](../reference/sdk.md) → `windowDimensions`; фиксируется изначальное). Как заводятся и читаются сами поля визита (slug, чтение плейсхолдером, `Is Macro Visible`) — [how-to/custom-fields.md](custom-fields.md).

### Кнопка сабмита настраивается — Submit control и его строки

Кнопка «Отправить» в SDK-форме — это отдельный контрол `Submit`, у которого настраиваются попереводные строки (задаются на каждый язык во вкладке Languages). Строки: `label` (текст кнопки, дефолт `Join Now`), `loading` (пока идёт отправка, дефолт `Applying...`), `success` (после успешного сабмита, дефолт `Success! (%counter%)`), `step` (текст перехода на промежуточном шаге, дефолт `Next step`).

Строка `success` умеет обратный отсчёт: подстановка `%counter%` показывает секунды до следующего действия и отсчитывается вниз по `successTimeoutSeconds`. Так после сабмита можно показать «Success! (5)», «(4)», … и увести визит дальше по таймауту.

### Прогрессивный сбор — поля пишутся в визит до сабмита

Данные из формы собираются **прогрессивно**: каждое поле уходит в визит ещё до сабмита — SDK ловит ввод по `blur`. Поэтому «поля визита имя и почта заполнились, хотя визит форму не отправлял» — это **норма, а не баг**: значение записалось при потере фокуса инпута, финальный сабмит только толкает визит по флоу.

Исключение — поле **`phone`**: телефон **не** собирается по `blur`, а уходит в визит только на самом сабмите (в международном формате через `getNumber()`). Отсюда частая картина «имя и почта заполнились в визите до отправки, а телефона нет» — так и задумано.

### Layouts отвечают только за визуальное расположение

Если push успешен, а у получателя данные перепутаны — чинить в Controls, Layouts тут не при чём (механика — [models/form.md](../models/form.md)). Раскладка (`Layouts`) отвечает только за то, как поля стоят на экране; куда уходит значение, определяет привязка контрола к полю визита.

### Несколько форм на одном лэнде — `{{form:N}}` и handle-ветки

Несколько форм на одном лэнде подключаются через нумерованные плейсхолдеры `{{form:1}}`, `{{form:2}}` и т.д. — **до 5 форм**. Каждая форма даёт **отдельную ветку перехода во флоу**: `Handle form 1`, `Handle form 2`, 3, 4, 5, плюс общая `Handle all forms` (поведение зеркалит `{{link:N}}`, см. [reference/placeholders.md](../reference/placeholders.md)).

Альтернатива — один и тот же `{{form}}` вставить в нескольких местах лэнда: это одна и та же форма, не разные. Какая именно форма дала лид, видно в поле визита `form_uuid`. Выбор конкретной формы через ноду `Fill form` или Content-шаг работает так же, как маршрутизация по ссылкам.

## Мультиязычная форма — Base language, добавленные языки и переводы

Форма рендерится на **одном** языке: SDK вычисляет его при загрузке из браузера визитёра и подставляет строки этого языка. Набор языков формы задаётся во вкладке `Languages` конструктора: `Base language` (выбирается во вкладке `Info`) плюс добавленные языки. Со стороны лэнда для мультиязычности делать не нужно ничего — словарь переводов уезжает на лэнд вместе с `{{aio}}`.

`Base language` — понятие конструктора, а не рантайма: на нём открывается превью, и удалить его из языков формы нельзя. На отрендеренной форме фолбэк всегда English — `Base language` в него не подставляется. Новая форма стартует с `English` в качестве базового.

### Как добавить язык в форму — кнопка `Languages` и два сегмента

Языки добавляются кнопкой `Languages` во вкладке `Languages`. Диалог выбора разделён на два сегмента:

- **`Auto-translated`** — 53 языка, для которых в конструкторе есть готовый авто-перевод. Язык, взятый отсюда, приезжает **частично заполненным**.
- **`All languages`** — весь справочник языков (185), включая те же авто-переводимые. Один и тот же язык, взятый из `All languages`, приходит **полностью пустым**: будет ли префил, определяет сегмент, из которого язык выбран.

В диалоге есть поиск по названию и коду языка и `Select all` по видимому списку. Тултип у кнопки сохранения перечисляет языки, которые будут удалены (`No languages will be removed`, если удалять нечего). Базовый язык из выбора убрать нельзя — тултип `Base language cannot be deleted`.

Переключатель `Pre-fill controls` в том же диалоге (работает только при добавлении языков) дописывает в форму недостающие контролы First Name, Last Name, Email, Mobile Phone на базовом языке.

### Что заполняет авто-перевод, а что остаётся пустым

Авто-перевод заполняет подпись и плейсхолдер (одной и той же строкой) только у контролов с ключом `first_name`, `last_name`, `email`, `phone` — и только если контрол смаплен на поле визита, — плюс четыре строки кнопки Submit. **Кастомные контролы и варианты `Drop list` остаются пустыми** и переводятся вручную.

Рядом с языком идёт счётчик «переведено / всего», где «всего» = число контролов формы + 1 на кнопку Submit. Бейдж языка: `Auto-translated`, `Translated` или красный `Not Translated` — красный ставится, когда какой-то элемент переведён не целиком.

### Непереведённая строка уезжает на лэнд пустой

Если язык к форме добавлен, а конкретная строка на нём не переведена — на лэнде она рендерится **пустой**: у поля не будет ни подписи, ни плейсхолдера. Фолбэка на английский тут не происходит, и причина в том, как SDK читает словарь: пустая строка для него — это значение, а не отсутствие перевода, поэтому он выводит её как есть. Английский подставляется только когда строки нет вовсе — то есть для языков, которых в форме нет. Поэтому: добавили свой язык — переведите на нём **все** строки формы.

Вкладка `Preview` это маскирует: если среди языков формы есть `English`, превью подставит вместо пустой строки английскую, и в конструкторе форма выглядит нормальной. Отсюда диагностический признак — **«в превью подписи есть, а на живом лэнде поля без подписей» = язык формы переведён частично**.

### Визитёр с языком, которого в форме нет — фолбэк на `en`, потом ключ строки

Для визитёра, чьего языка в форме нет, строка ищется по цепочке: нужный язык → `en` → сам ключ строки. Только для этого случая цепочка и работает.

Словарь, приехавший из ERP, замещает встроенный пак самого SDK целиком: в SDK 33 языка, но после подключения формы из ERP они остаются лишь последним фолбэком для четырёх строк `SUBMIT*`. Поэтому если из языков формы убрать `English` (новая форма стартует с него, и убрать его можно только сделав базовым другой язык), визитёр с языком вне списка увидит вместо подписей и плейсхолдеров служебные токены вида `first_name_label` / `first_name_placeholder`. Держите `English` в языках формы как страховочный фолбэк.

### Как править переводы — `Open translations`, импорта JSON нет

Действия по языку (`Language actions` в строке языка):

- **`Open translations`** — пословный редактор с колонками `Original` и `Translate`, строки кнопки вынесены в отдельный блок `Submit button`.
- **`Reset auto-translations`** — возвращает контролы с доступным авто-переводом в исходное состояние.
- **`Delete language`** — базовый и последний оставшийся язык удалить нельзя.

**Импорта или экспорта JSON с переводами в Form Builder нет** — только пословный редактор по каждому языку. Массово подменить словарь можно лишь со стороны лэнда — сообщением `form-translations` в `window.aioBus` (протокол — [reference/sdk.md](../reference/sdk.md)).

### Контрол, добавленный после языков, приезжает непереведённым

Контрол, добавленный в форму **после** того, как языки уже заведены, приходит непереведённым во все небазовые языки: авто-перевод на этом пути не применяется даже к четырём стандартным слагам.

- `first_name` / `last_name` / `email` / `phone` — чинится `Reset auto-translations` по языку.
- Кастомный контрол — ни `Reset auto-translations`, ни пересоздание языка не помогут: его придётся перевести вручную в `Open translations`.

### Может ли визитёр сам переключить язык формы — нет

Переключателя языка для визитёра нет: форма рендерится на одном языке, вычисленном при загрузке, и сменить язык уже отрисованной формы нельзя. Язык берётся из браузера визитёра, а не из лэнда: визит с браузером на другом языке увидит форму не на том языке, на котором написан лэнд. Зафиксировать язык заранее может лэнд — этим и занимается макрос `Static Language Country` (см. ниже), он же фиксирует страну телефона.

Дропдаун языков есть только во вкладке `Preview` конструктора: он перечисляет языки самой формы и открывается на `Base language` — это инструмент оператора, а не визитёра.

## Non-SDK Form Handler — как подключить и подводные камни

### Подключение

1. На лэнде — твоя `<form>` с HTML-инпутами.
2. Slug'и инпутов **должны совпадать** буквально: `first_name`, `last_name`, `email`, `phone`. Иначе лид «уходит», но поля визита пустые.
3. На лэнде после `{{aio}}` добавляешь: `{{aio:macros:nonsdk_form_handler}}` (slug может отличаться — проверь в `Content → Macros`).

### Подводные камни

- **Цепляется только к тегу `<form>`.** Если форма свёрстана как `<div>` — сабмит не перехватывается.
- **Грузит intl-tel-input со своими CSS.** Форма может «съезжаться» после подключения. Лечится точечной адаптацией стилей или переходом на SDK.
- **`required` не выставлен** на кастомных формах по умолчанию → лиды с пустым `last_name`, email не валидируется. Проверь правила на инпутах.

## Валидация телефона — intl-tel-input: параметры и гео-специфика

Номер в SDK-форме проходит валидацию **сторонней библиотекой** `intl-tel-input.com` — в браузере, ещё до отправки; это не AIO-антифрод.

### Параметры (через `AIO SDK Macros Collection`)

```javascript
intlParameters: {
  separateDialCode: true,
  strictMode: false,
  showFlags: true,
  nationalMode: true,
  autoPlaceholder: "aggressive"
}
```

### Гео-специфика

- **Германия (DE):** `separateDialCode: true` + `strictMode: false`. Немецкие номера длиннее стандартных; `strictMode: true` режет `+49`. Настраивается per-тенант в `AIO SDK Macros Collection`.
- **Бразилия:** телефоны и 10, и 11 цифр валидны (зависит от кода оператора); стандартная либа `intl-tel-input` может считать 10-значный невалидным. Бразильский «по виду стационарный» может быть мобильным.

### Что делать, если получатель реджектит номер

- Усиливать валидацию **на форме** (`minlength` / `maxlength` / `pattern`, гео-зависимые правила). На визите виден только итог `pushed` / `rejected` без причины; полный ответ получателя — в логе `Settings → Logs` → `Destination Handler` (разбор — [how-to/destinations.md](destinations.md)). Быстрее — ПКМ по визиту в `Tracker → Visits` → `Visit logs` (переключи `Severity` на `Debug`, иначе таблица выглядит пустой; [how-to/debug-with-logs.md](debug-with-logs.md)).
- Готовый паттерн `pattern:no-local-emails` отсекает локальные email-адреса прямо на форме — ставь на инпут email, если получатель их не принимает.

### Двойные дропдауны страны / intl-tel-input глючит

«Два дропдауна страны у телефона» или выбор кода ведёт себя странно → на лэнде остались свои скрипты `<script src="…intl-tel-input…">`. SDK подгружает свою копию, вторая конфликтует. Удалить с лэнда — SDK подгрузит нужное сам.

## SDK-конфиг per-тенант — Static Language Country

`Static Language Country` (`aio_static_language__country_for_form`) — фиксирует язык формы и страну телефона по метаданным лэнда (`Countries` / `Languages`), без него под VPN подставляется страна VPN-сервера (гео визита) и язык браузера. Симптом «под VPN в форме не тот код страны / не тот язык» → макрос не включён. Как это называют: «форма на неправильном языке / не на том коде страны», «в форме `+44` вместо нужного», «fallback на GB / `+44`», «нет флагов в форме». Макрос шаблонный, часто уже включён; при фиксированном таргетинге по стране держать глобально. Полная механика — [reference/sdk.md](../reference/sdk.md).

## fbPixel + fbCapi — дедупликация и причины дублей

- **`event_id` ставится только на серверное CAPI-событие** (формат `conversion.<visit_uuid>.<conversion_type_uuid>`), браузерное событие пикселя уходит без него. То есть автоматической дедупликации «пиксель ↔ CAPI» по общему идентификатору нет — если один и тот же лид отбивается и пикселем, и через CAPI, Meta может засчитать его дважды.
- `fbPixel` выключается **одной строкой** в `AIO SDK Macros Collection` (`features.fbPixel: false`).
- Дубликаты FB-лидов — когда:
  1. Третья сторона (получатель) дополнительно отбивает Pixel.
  2. На лэнде остался **свой Pixel-скрипт**, который шлёт то же событие параллельно SDK.
  3. Внутренний баг FB.

Диагностика — `FB Events Manager`.

## Required — два контекста: Form Control vs Visit Field

| Контекст | Где | Поддерживается? |
|---|---|---|
| **Form Control `Required`** | `Settings → Forms → Controls → <инпут>` (Form Builder) | **Да** — ставится как правило валидации инпута SDK-формы. Инпут не отдаст форму без значения. |
| **Visit Field `required`** | `Settings → Fields → <поле>` | **Нет** напрямую. UI не позволяет. Помечать обязательным — через **`Link Generator`** при генерации ссылки кампании. Это обязательность **параметра в URL**, не поля как такового. |

Это **два разных уровня обязательности** — на форме (валидация SDK) vs на ссылке кампании (Link Generator).

## Что происходит на сабмите — переход Handle-form двигает визит

Когда визит заполняет форму и жмёт «Отправить», сабмит запускает во флоу переход `Handle-form` — и по нему визит идёт на следующий шаг (обычно пуш лида в Destination). Технически сабмит — это запрос на сам лэнд, в который SDK всегда добавляет метку `_aio_handle=form`; по ней запрос распознаётся как форма — визит идёт по `Handle-form`.

Это отличается от клика по переходной ссылке `{{link}}` на лэнде — тот ведёт визит по переходу `Handle-link`. На одном лэнде можно развести два пути: форма уходит по `Handle-form` на пуш лида, а отдельная кнопка-ссылка — по `Handle-link` на другой шаг. Исходы пуша (`Pushed` / `Rejected` / `Destination Full`) — см. [mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md).

## Антифрод-чек на сабмите — fraud_score

После валидации в браузере и перед пушем в `Destination` лид проходит встроенный `AIO Antifraud`; итог проверки пишется в поля визита `fraud_score` и `triggered_rules`.

Отладка: лид не доходит до получателя, а форма и сабмит исправны → разбирать не форму, а антифрод-проверку лида.

### Дубли лидов от повторного нажатия «Отправить» — макрос Form Loader

Если человек нетерпеливо жмёт «Отправить» несколько раз подряд, каждое нажатие может уйти отдельной заявкой — с одного заполнения получатель увидит несколько одинаковых лидов. Лечится макросом `Form Loader` (`aio_form_loader`): после первого сабмита он блокирует повторные нажатия кнопки и показывает лоадер, пока идёт отправка. Так с одного заполнения уходит ровно один лид, а не три. Включается в макросах.

## Submit Promise / Before-Submit Promise — кастомизация

- Кастомизируются под кейс. Rejected Message тоже кастомизируется.
- Свой пре-сабмит хук `beforeSubmitPromise` (подтверждение, модалка, свой запрос), который висит без ответа или отклоняет сабмит, — частая причина «кнопка „Отправить“ мёртвая» на лэндах со своим JS. Механика хуков — [reference/sdk.md](../reference/sdk.md).
- Переводы формы кастомизацией не покрываются: авто-перевод заполняет только четыре стандартных контрола и кнопку Submit, остальные строки на каждом языке заполняются вручную (см. «Мультиязычная форма» выше).

## Типовые вопросы по формам — диагностика и ответ

- «Данные у получателя перепутаны» → ключи Controls не совпадают. Layouts тут не помогут.
- «Форма не отправляется, AIO её не видит» → `<form>` вместо `{{form}}` без Non-SDK Form Handler.
- «Форма вообще не отрисовалась (пусто вместо формы)» → нет `{{form}}` в HTML лэнда, или нет `{{aio}}` перед `</body>`, или `features.form: false`, или форма не выбрана во флоу.
- «Кнопка „Отправить“ не отправляет, в Network нет запроса» → CSS перекрыл кнопку (`pointer-events: none` / `disabled`), или завис хук `beforeSubmitPromise`, или осталась старая HTML-форма / свои intl-скрипты.
- «Двойные дропдауны страны / `intl-tel-input` глючит» → на лэнде остались свои `<script src=".../intl-tel-input...">`. Удалить — SDK подгрузит сам.
- «Хочу свою HTML-форму» → Non-SDK Form Handler, slug'и `first_name/last_name/email/phone`. Но рекомендуется SDK.
- «Получатель реджектит DE-номер» → `strictMode: false` + `separateDialCode: true` в `intlParameters`.

Полная диагностика «форма не сабмитится» (быстрый водораздел через Dummy Destination, чтение сетевого ответа сабмита).

### Типовые вопросы по языкам формы

- «В превью подписи есть, а на живом лэнде поля без подписей» → язык формы переведён частично: непереведённая строка уходит на лэнд пустой, а превью подставляет вместо неё английскую.
- «Добавил язык, а он пустой» → язык взят из сегмента `All languages`; префил даёт только сегмент `Auto-translated`, и то лишь для четырёх стандартных контролов и кнопки Submit.
- «Вместо подписей на форме видны `first_name_label` и подобное» → в языках формы не осталось `English`, а язык визитёра в списке отсутствует — показывается сам ключ строки.
- «Можно ли дать визитёру переключать язык формы» → нельзя, переключателя нет; язык вычисляется один раз при загрузке.
- «Где выгрузить переводы в JSON» → в Form Builder такого нет, переводы правятся пословно в `Open translations`.

## Пошаговые инструкции — создание, подключение и дублирование формы

### Создать SDK-форму

Когда: с нуля собрать новую SDK-форму с нужными контролами / шагами / переводами.

**Путь:** `Settings → Forms → +Form`.

**Шаги:**

1. Задать **Name** + Description + Tags (вкладка Info).
2. **Controls** — добавить инпуты (`String text`, `Email`, `Phone`, `Text area`, `Checkbox`, `Drop list`, `Number`, `Date`) с правилами валидации, плюс отдельный контрол `Submit`.
3. **Steps** — 1 или несколько шагов (например, шаг 1: email, шаг 2: phone). Сабмит на промежуточном шаге — **не** пуш лида: он отправляет поля текущего шага в визит и переводит на следующий шаг; лид уходит только на финальном сабмите.
4. **Languages** — кнопкой `Languages` добавить языки (сегмент `Auto-translated` даёт частичный префил), затем дописать оставшиеся строки в `Open translations` по каждому языку.
5. **Preview** — посмотреть результат.
6. `Save`.

После — форма доступна для подключения в кампании через шаг `Fill Form` во флоу.

### Добавить шаг Fill Form во флоу

Когда: SDK-форма создана, нужно подключить её к флоу.

**Путь:** `Edit Flow → +Step → Fill Form → выбрать форму → включить Campaign Template`.

**Шаги:**

1. В Flow Editor добавить шаг `Fill Form`.
2. В настройках шага выбрать конкретную форму из списка.
3. Включить `Campaign Template` (или Flow Only — см. [how-to/flow-editor.md](flow-editor.md) → Settings Availability).
4. Сохранить.

После — все кампании на этом флоу используют форму через `{{form}}` на лэнде.

### Дублировать SDK-форму — Copy form

Когда: новая форма мало отличается от существующей (например, другие переводы под другую гео).

**Путь:** `Settings → Forms → форма → `Copy form` → сохранить с другими переводами`.

**Что копируется:** Controls вместе с маппингами контрол↔поле визита, Steps, Layout, Languages (с возможностью отредактировать).

**Что не копируется:** Tags / Description (заполняются заново).
