# Forms (How-to)

Форма на лэнде собирает введённые данные в поля визита и при сабмите запускает переход во флоу. Доставка лида выполняется следующим шагом Destination, если к нему ведёт настроенный флоу. Этот файл — про то, как поставить форму, связать её поля с полями визита, настроить гео-зависимую валидацию телефона (`intl-tel-input`) и что проверять, когда «форма не сабмитится» или лид не пишется. SDK-форма vs Non-SDK Form Handler, обязательные slug-маппинги, override per-tenant.

---

## TL;DR

- **SDK-форма (`{{form}}`)** — основной путь. В ERP настраивается в `Settings → Forms`; в MTK выбирается готовая форма кампании. Controls + Layouts + Steps + Languages. Рекомендуется.
- **Non-SDK Form Handler** — фолбэк, если своя HTML-форма. Цепляется к тегу `<form>`. **Активно не развивается.**
- **Slug инпутов** при Non-SDK Form Handler обязаны совпадать с AIO-слагами: `first_name`, `last_name`, `email`, `phone`. Без этого данные не маппятся.
- **Layouts отвечают только за визуальное расположение**, не за маппинг. Если у получателя данные перепутаны (в поле телефона — имя) — смотреть Controls.
- **Форма мультиязычная:** `Base language` + добавленные языки, авто-переключение по языку браузера визитёра. Авто-перевод заполняет только четыре стандартных контрола и кнопку Submit — **непереведённая строка уезжает на лэнд пустой** (у поля не будет ни подписи, ни плейсхолдера).
- **Валидация телефонов** — сторонняя либа `intl-tel-input.com`. По странам ведёт себя по-разному (DE — `strictMode: false`; BR — 10 и 11 цифр валидны).
- **`Required` на Form Control** (в ERP Form Builder, `Settings → Forms → Controls → инпут`) — **есть**, ставится в правилах инпута. **`required` на поле визита** (ERP `Settings → Fields`) — **нельзя** напрямую; для полей визита обязательность задаётся через `Link Generator`. Это **два разных контекста**.

## SDK-форма vs Non-SDK Form Handler — что выбрать

| | SDK-форма | Non-SDK Form Handler |
|---|---|---|
| Куда вставляется | `{{form}}` на лэнде | На обычную `<form>` лэнда |
| Setup | ERP: `Settings → Forms → +Form`; MTK: `Choose Form` в кампании | Макрос `AIO Non-SDK Form Handler` из ERP `Content → Macros` / MTK `Settings → Macros` (в шаблонах Finance, Nutra и Sweeps уже активен) + строка `{{aio:macros:aio_nonsdk_form_handler}}` на лэнде |
| Slug-маппинг | Авто | **`name` инпута = слаг поля визита**, буквально: `first_name`, `last_name`, `email`, `phone` (и любое другое поле тенанта) |
| Customisable submit/before | Да (Submit Promises, Before Submit Promises) | Ограниченно — правкой обработчиков в теле макроса |
| Pushing modal / autologin | Да | Модалки нет; после успешного пуша — редирект по URL из ответа интеграции |
| Form Builder UI | Полная конфигурация Controls / Steps / Layouts / Languages | — |
| Активная разработка | Да | **Нет** (фолбэк) |

Рекомендация: **SDK-форма для всех новых лэндов**. Non-SDK — только если редизайн SDK-формы под существующий лэнд слишком сложен.

> **Отдельные push-скрипты на лэнде не нужны** (ни для SDK-формы, ни для Non-SDK Form Handler). Сабмит запускает переход во флоу; отдельный push-скрипт не нужен, если доставка настроена через Destination. Если на лэнде уже есть свои push-скрипты — **удалить**, иначе конфликт.

## Как устроен Form Builder — Settings, Preview и четыре режима

В ERP: `Settings → Forms → +Form / Form builder` — две вкладки: `Settings` и `Preview`. В `Settings` слева расположен блок `Info` (Name, Description, Tags, Base language, **Color**, **Icon**), справа — режимы `Controls` (инпуты и правила валидации), `Steps` (шаги), `Layouts` (раскладка), `Languages` (переводы). Полное описание концепта — [models/form.md](../models/form.md).

> Действия над формой (правый клик по строке): `Edit form`, `Form builder`, `Copy form`.

В MTK конструктора форм нет: формы приезжают готовыми из шаблона тенанта (набор по вертикали — [models/form.md](../models/form.md)) и выбираются в карточке кампании шагом `Choose Form`. Свои контролы задаются макросом — блоком `config.form` в `AIO SDK Macros Collection` (`Settings → Macros`). Плейсхолдер `{{form}}` и сам SDK-компонент в обоих видах одинаковы.

### Каждый Control (`Control settings`) и маппинг контрол↔поле визита

Открывается по шестерёнке у контрола в Form Builder. Именно привязка `Field` определяет, куда уйдёт введённое значение. Поля:
- **Type** — тип контрола, показывается человеческим названием: `String text`, `Phone`, `Email`, `Checkbox`, `Drop list`, `Number`, `Date`, `Text area`. У нового контрола подпись по умолчанию равна названию его типа.
- **Label** / **Placeholder** / **Value** — подпись, плейсхолдер и значение по умолчанию.
- **Field** — на какое **поле визита** пишется значение (напр. `Visit → First Name`). Это и есть slug-маппинг: контрол ↔ поле визита. У контрола есть `key` (slug).
- **Attributes** — правила валидации: `required` (Boolean), `minlength`, `maxlength` (можно добавлять ещё через `+ Attribute`). У встроенного контрола SDK `first_name`: `required` + `minlength 1` + `maxlength 64`. У нового контрола в конструкторе правила задаются отдельно.

Пример из шаблона тенанта — `Default Leads Form` (Finance) и `Default SOI Form` (Sweeps): 4 контрола First Name, Last Name, Email, Phone, каждый смаплен на одноимённое поле визита (совпадает со встроенным дефолтом SDK-формы — [reference/sdk.md](../reference/sdk.md)). Правила у стандартных контролов шаблонных форм: `first_name` / `last_name` — `required` + `minlength 1` + `maxlength 64`; `email` — `required` + `minlength 3` + `maxlength 64` + `pattern:no-local-emails`; `phone` — `required` + `minlength 5` + `maxlength 20`. Какие формы засеяны в каждой вертикали — [models/form.md](../models/form.md).

### Поля визита, которые SDK заполняет без контрола — Screen Dimensions

Колонка визита `Screen Dimensions` отображает пару `browser_window_width` / `browser_window_height`, которую автоматически собирает SDK (см. [reference/sdk.md](../reference/sdk.md) → `windowDimensions`; фиксируется изначальное). Как заводятся и читаются сами поля визита (slug, чтение плейсхолдером, `Is Macro Visible`) — [how-to/custom-fields.md](custom-fields.md).

### Кнопка сабмита настраивается — Submit control и его строки

Кнопка «Отправить» в SDK-форме — это отдельный контрол `Submit`, у которого настраиваются попереводные строки (в ERP задаются на каждый язык в режиме `Languages` конструктора). Строки: `label` (текст кнопки, дефолт `Join Now`), `loading` (пока идёт отправка, дефолт `Applying...`), `success` (после успешного сабмита, дефолт `Success! (%counter%)`), `step` (текст перехода на промежуточном шаге, дефолт `Next step`).

Строка `success` умеет обратный отсчёт: подстановка `%counter%` показывает секунды до следующего действия и отсчитывается вниз по `successTimeoutSeconds`. Так после сабмита можно показать «Success! (5)», «(4)», … и увести визит дальше по таймауту.

### Прогрессивный сбор — поля пишутся в визит до сабмита

При стандартном `collectDataEvent: 'blur'` SDK ставит непустые значения обычных контролов в обмен после потери фокуса; одинаковое или укороченное значение повторно не отправляет. Поэтому имя и почта могут попасть в визит до сабмита. Сброс обмена по умолчанию идёт раз в 10 секунд ([reference/sdk.md](../reference/sdk.md)); его интервал можно изменить. Финальный сабмит передаёт данные формы и запускает переход во флоу.

Контрол типа **`phone`** не собирается по `blur`. Телефон передаётся при сабмите в формате `getNumber()` по умолчанию; если он принадлежит промежуточному шагу формы, значение может уйти уже при переходе к следующему шагу. Поэтому отсутствие телефона до сабмита само по себе не означает ошибку.

### Layouts отвечают только за визуальное расположение

Если push успешен, а у получателя данные перепутаны — чинить в Controls, Layouts тут не при чём (механика — [models/form.md](../models/form.md)). Раскладка (`Layouts`) отвечает только за то, как поля стоят на экране; куда уходит значение, определяет привязка контрола к полю визита.

### Несколько форм на одном лэнде — `{{form:N}}` и handle-ветки

Нумерованные плейсхолдеры `{{form:1}}`…`{{form:5}}` различают места отправки: SDK передаёт `_aio_handle=form-1`…`form-5`, а во флоу можно настроить переходы `Handle form 1`…`Handle form 5` и общий `Handle all forms`. Номер не выбирает другую конфигурацию Form — все формы страницы получают текущие Controls, Layouts и Steps.

Обычный `{{form}}` можно повторить в нескольких местах. Поле визита `form_uuid` хранит UUID выбранной конфигурации, а не номер отправившей формы. Конфигурацию задаёт `Fill form`; если она ещё не выбрана, Content-шаг может использовать `Form fallback`.

## Мультиязычная форма — Base language, добавленные языки и переводы

Форма рендерится на **одном** языке: SDK вычисляет его при загрузке из браузера визитёра и подставляет строки этого языка. В ERP набор языков формы задаётся в режиме `Languages` конструктора: `Base language` (выбирается в блоке `Info` вкладки `Settings`) плюс добавленные языки. Со стороны лэнда для мультиязычности делать не нужно ничего — словарь переводов уезжает на лэнд вместе с `{{aio}}`.

`Base language` — понятие конструктора, а не рантайма: на нём открывается превью, и удалить его из языков формы нельзя. На отрендеренной форме фолбэк всегда English — `Base language` в него не подставляется. Новая форма стартует с `English` в качестве базового.

### Как добавить язык в форму — кнопка `Languages` и два сегмента

Языки добавляются кнопкой `Languages` во вкладке `Languages`. Диалог выбора разделён на два сегмента:

- **`Auto-translated`** — 53 языка, для которых в конструкторе есть готовый авто-перевод. Язык, взятый отсюда, приезжает **частично заполненным**.
- **`All languages`** — весь справочник языков (185), включая те же авто-переводимые. Один и тот же язык, взятый из `All languages`, приходит **полностью пустым**: будет ли префил, определяет сегмент, из которого язык выбран.

В диалоге есть поиск по названию и коду языка и `Select all` по видимому списку. Тултип у кнопки сохранения перечисляет языки, которые будут удалены (`No languages will be removed`, если удалять нечего). Базовый язык из выбора убрать нельзя — тултип `Base language cannot be deleted`.

Переключатель `Pre-fill controls` в том же диалоге (работает только при добавлении языков) дописывает в форму недостающие контролы First Name, Last Name, Email, Mobile Phone на базовом языке.

### Что заполняет авто-перевод, а что остаётся пустым

Авто-перевод заполняет непустые исходные подпись и плейсхолдер у контролов с ключом `first_name`, `last_name`, `email`, `phone`, смапленных на поле визита. Для обеих строк используется один перевод, но пустая исходная строка остаётся пустой. Четыре строки Submit тоже переводятся только при непустой исходной строке. **Кастомные контролы и варианты `Drop list` остаются пустыми** и переводятся вручную.

При неполном переводе рядом с языком виден счётчик «переведено / всего»: «всего» = число контролов в переводе + 1 на Submit. Бейдж — `Auto-translated`, `Translated` или красный `Not Translated`. Красный означает отсутствие требуемых исходных строк или полностью пустой элемент; частично заполненный необязательный элемент сам по себе не всегда делает бейдж красным.

### Непереведённая строка уезжает на лэнд пустой

Если язык к форме добавлен, а конкретная строка на нём не переведена — на лэнде она рендерится **пустой**: у поля не будет ни подписи, ни плейсхолдера. Фолбэка на английский тут не происходит, и причина в том, как SDK читает словарь: пустая строка для него — это значение, а не отсутствие перевода, поэтому он выводит её как есть. Английский подставляется, когда ключа строки нет вовсе: это возможно и у языка, уже добавленного в форму. Поэтому: добавили свой язык — переведите на нём **все** строки формы.

Вкладка `Preview` это маскирует: если среди языков формы есть `English`, превью подставит вместо пустой строки английскую, и в конструкторе форма выглядит нормальной. Отсюда диагностический признак — **«в превью подписи есть, а на живом лэнде поля без подписей» = язык формы переведён частично**.

### Визитёр с языком, которого в форме нет — фолбэк на `en`, потом ключ строки

Для визитёра, чьего языка в форме нет, строка ищется по цепочке: нужный язык → `en` → сам ключ строки. Та же цепочка работает, если язык присутствует, но конкретный ключ в его словаре отсутствует. Пустая строка не запускает фолбэк.

Словарь, приехавший из ERP, замещает встроенный пак самого SDK целиком: в SDK 33 языка, но после подключения формы из ERP они остаются лишь последним фолбэком для четырёх строк `SUBMIT*`. Поэтому если из языков формы убрать `English` (новая форма стартует с него, и убрать его можно только сделав базовым другой язык), визитёр с языком вне списка увидит вместо подписей и плейсхолдеров служебные токены вида `first_name_label` / `first_name_placeholder`. Держите `English` в языках формы как страховочный фолбэк.

### Как править переводы — `Open translations`, импорта JSON нет

Действия по языку (`Language actions` в строке языка):

- **`Open translations`** — пословный редактор с колонками `Original` и `Translate`, строки кнопки вынесены в отдельный блок `Submit button`.
- **`Reset auto-translations`** — возвращает контролы с доступным авто-переводом в исходное состояние.
- **`Delete language`** — базовый и последний оставшийся язык удалить нельзя.

**Импорта или экспорта JSON с переводами в Form Builder нет** — только пословный редактор по каждому языку. Массово подменить словарь можно лишь со стороны лэнда — сообщением `form-translations` в `window.aioBus` (протокол — [reference/sdk.md](../reference/sdk.md)).

### Контрол, добавленный после языков, приезжает непереведённым

Контрол, добавленный в форму **после** того, как языки уже заведены, приходит непереведённым во все небазовые языки: авто-перевод на этом пути не применяется даже к четырём стандартным слагам.

- `first_name` / `last_name` / `email` / `phone` — чинится `Reset auto-translations` по языку.
- Кастомный контрол — ни `Reset auto-translations`, ни пересоздание языка не помогут: его придётся перевести вручную в `Open translations`.

Это касается и форм из шаблона тенанта: языки в них уже добавлены (несколько десятков; у Nutra набор короче), поэтому любой контрол, дописанный в шаблонную форму, придёт непереведённым во все её языки.

### Может ли визитёр сам переключить язык формы — нет

Переключателя языка для визитёра нет: форма рендерится на одном языке, вычисленном при загрузке, и сменить язык уже отрисованной формы нельзя. Язык берётся из браузера визитёра, а не из лэнда: визит с браузером на другом языке увидит форму не на том языке, на котором написан лэнд. Зафиксировать язык заранее может лэнд — этим и занимается макрос `Static Language Country` (см. ниже), он же фиксирует страну телефона.

Дропдаун языков есть только во вкладке `Preview` конструктора: он перечисляет языки самой формы и открывается на `Base language` — это инструмент оператора, а не визитёра.

## Non-SDK Form Handler — как подключить и подводные камни

### Подключение

1. На лэнде — своя `<form>` с HTML-инпутами.
2. `name` каждого инпута **должен совпадать со слагом поля визита** буквально: `first_name`, `last_name`, `email`, `phone` — и любые другие поля тенанта (например, `city`, `zip_code` в Nutra- и Sweeps-шаблонах). Инпут с другим именем молча отбрасывается: лид «уходит», а поля визита пустые.
3. На лэнде после `{{aio}}` добавляешь строку `{{aio:macros:aio_nonsdk_form_handler}}` — так называется макрос во всех шаблонах тенанта, где он есть (Finance, Nutra, Sweeps; в iGaming его нет). В тенанте, собранном давно, слаг сверь в ERP `Content → Macros` / MTK `Settings → Macros`.

Готовый образец в шаблоне — лэнд-пример с меткой `AIO EXAMPLE`: `Example Offer Page — Custom HTML Form` (Finance), `Offer Example #3 - Custom HTML Form` (Nutra), `Offer Example #2 - Custom HTML Form` (Sweeps) — своя HTML-форма с инпутами по слагам полей и одной строкой макроса.

### Подводные камни

- **Цепляется только к тегу `<form>`.** Если форма свёрстана как `<div>` — сабмит не перехватывается. SDK-формы (`.aio-form`, `.aio-sdk-form`) макрос пропускает, но держать на одном лэнде `{{form}}` и свою форму всё равно не стоит.
- **Вешает на инпут `[type=tel]` SDK-шный `intl-tel-input`** (флаг, код страны, проверка номера; телефон уходит в международном формате). Инпут получает его стили — форма может «съезжаться» после подключения. Лечится точечной адаптацией стилей или переходом на SDK.
- **Ответ показывается браузерным `alert`**: невалидный номер, ошибка отправки, реджект получателя с его сообщением. Успешный пуш — редирект по URL из ответа интеграции (автологин, если интеграция вернула именно такую ссылку); модалок и хуков SDK-формы здесь нет.
- **`required` не выставлен** на кастомных формах по умолчанию → лиды с пустым `last_name`, email не валидируется. Проверь правила на инпутах.

### Своя сложная форма без ответа сервера — `AIO Pre-Fill form Handler` (Sweeps)

В Sweeps-шаблоне есть третий путь для своей вёрстки — макрос `AIO Pre-Fill form Handler` (`aio_prefill_form_handler`, вставляется той же строкой `{{aio:macros:aio_prefill_form_handler}}`; в шаблоне подключён к прилэнду-примеру `Preland Example #2 - Gift Boxes w/ Quiz Form`). Он для формы, которую не пересобрать SDK-контролами — квиз, колесо, выбор подарка: на сабмите сопоставляет имена инпутов со слагами полей тенанта (понимает и ходовые варианты вроде `firstname`, `tel`, `zip`), проверяет телефон тем же `intl-tel-input` и уводит визит по `{{link}}` с этими значениями в query — AIO записывает их в поля визита тем же запросом. Ответа получателя этот путь не ждёт и не показывает: визит идёт дальше по флоу как по клику `{{link}}` (переход `Handle-link`). В кампании-примере `Quiz Boxes -> Custom Form - Campaign Example` так устроена связка: прилэнд-квиз с этим макросом собирает приз, возраст и контакты, а оффер `Offer Example #2 - Custom HTML Form` открывается уже с заполненными полями и отправляет лид через `AIO Non-SDK Form Handler`.

## Валидация телефона — intl-tel-input: параметры и гео-специфика

Номер в SDK-форме проходит валидацию **сторонней библиотекой** `intl-tel-input.com` — в браузере, ещё до отправки; это не AIO-антифрод.

### Параметры (через `AIO SDK Macros Collection`)

```javascript
intlParameters: {
  separateDialCode: true,
  strictMode: false,
  showFlags: true,
  nationalMode: true,
  autoPlaceholder: "aggressive"
}
```

### Гео-специфика

- **Германия (DE):** если ввод номера обрезается, проверь `strictMode`; в таком случае его отключают. `separateDialCode: true` показывает код отдельно. Эти настройки не отменяют проверку `isValidNumber()` и требования получателя; задаются per-тенант в `AIO SDK Macros Collection`.
- **Бразилия:** телефоны и 10, и 11 цифр валидны (зависит от кода оператора); стандартная либа `intl-tel-input` может считать 10-значный невалидным. Бразильский «по виду стационарный» может быть мобильным.

### Что делать, если получатель реджектит номер

- Усиливать валидацию **на форме** (`minlength` / `maxlength` / `pattern`, гео-зависимые правила). На визите виден только итог пуша — колонка `Pushed` (да / нет) без причины; полный ответ получателя — в логе `Settings → Logs` → `Destination Handler` (разбор — [how-to/destinations.md](destinations.md)). Быстрее — ПКМ по визиту в `Tracker → Visits` → `Visit logs` (переключи `Severity` на `Debug`, иначе таблица выглядит пустой; [how-to/debug-with-logs.md](debug-with-logs.md)).
- Готовый паттерн `pattern:no-local-emails` отсекает локальные email-адреса прямо на форме — ставь на инпут email, если получатель их не принимает (на контроле `email` всех форм из шаблона тенанта он уже стоит).

### Двойные дропдауны страны / intl-tel-input глючит

«Два дропдауна страны у телефона» или выбор кода ведёт себя странно → на лэнде остались свои скрипты `<script src="…intl-tel-input…">`. SDK подгружает свою копию, вторая конфликтует. Удалить с лэнда — SDK подгрузит нужное сам.

## SDK-конфиг per-тенант — Static Language Country

`Static Language Country` — макрос `AIO Static Language Country for Form` из шаблона тенанта (слаг `aio_static_language__country_for_form` в Finance, `aio_static_language_country_for_form` в Nutra и Sweeps; в iGaming-шаблоне его нет) — фиксирует язык формы и страну телефона по метаданным лэнда (`Countries` / `Languages`), каждое независимо: страна берётся у лэнда, если у него задана ровно одна страна, язык — если ровно один язык. Если значений несколько либо они не заданы, это значение берётся у визита — гео и язык браузера, то есть под VPN подставляется страна VPN-сервера. Выбор страны в телефоне при этом всегда сужен до одной — той, что выбрана. Симптом «под VPN в форме не тот код страны / не тот язык» → макрос не подключён к лэнду, или у лэнда задана не одна страна (ни одной либо несколько). Как это называют: «форма на неправильном языке / не на том коде страны», «в форме `+44` вместо нужного», «fallback на GB / `+44`», «нет флагов в форме».

Макрос не глобальный: в шаблоне он активен и подключён к лэндам-примерам с формой, на свой лэнд его вставляют строкой `{{aio:macros:<slug>}}` после `{{aio}}`; при фиксированном таргетинге по стране можно сделать его глобальным (`Global` в карточке макроса). Полная механика — [reference/sdk.md](../reference/sdk.md).

## fbPixel + fbCapi — дедупликация и причины дублей

- **`event_id` ставится только на серверное CAPI-событие** (формат `conversion.<visit_uuid>.<conversion_type_uuid>`), браузерное событие пикселя уходит без него. То есть автоматической дедупликации «пиксель ↔ CAPI» по общему идентификатору нет — если один и тот же лид отбивается и пикселем, и через CAPI, Meta может засчитать его дважды.
- `fbPixel` выключается **одной строкой** в `AIO SDK Macros Collection` (`features.fbPixel: false`).
- Дубликаты FB-лидов — когда:
  1. Третья сторона (получатель) дополнительно отбивает Pixel.
  2. На лэнде остался **свой Pixel-скрипт**, который шлёт то же событие параллельно SDK.
  3. Внутренний баг FB.

Диагностика — `FB Events Manager`.

## Required — два контекста: Form Control vs Visit Field

| Контекст | Где | Поддерживается? |
|---|---|---|
| **Form Control `Required`** | ERP: `Settings → Forms → Controls → <инпут>` (Form Builder) | **Да** — ставится как правило валидации инпута SDK-формы. Инпут не отдаст форму без значения. |
| **Visit Field `required`** | ERP: `Settings → Fields → <поле>` | **Нет** напрямую. UI не позволяет. Помечать обязательным — через **`Link Generator`** при генерации ссылки кампании. Это обязательность **параметра в URL**, не поля как такового. |

Это **два разных уровня обязательности** — на форме (валидация SDK) vs на ссылке кампании (Link Generator).

## Что происходит на сабмите — переход Handle-form двигает визит

Когда визит заполняет форму и жмёт «Отправить», сабмит запускает во флоу переход `Handle-form` — и по нему визит идёт на следующий шаг (обычно пуш лида в Destination). Технически сабмит — это запрос на сам лэнд, в который стандартная SDK-форма добавляет `_aio_handle=form` (нумерованная — `form-N`). При настроенном переходе обычная форма идёт по `Handle-form`; иначе используется общий `Handle`.

Это отличается от клика по переходной ссылке `{{link}}` на лэнде — тот ведёт визит по переходу `Handle-link`. На одном лэнде можно развести два пути: форма уходит по `Handle-form` на пуш лида, а отдельная кнопка-ссылка — по `Handle-link` на другой шаг. Исходы пуша (`Pushed` / `Rejected` / `Destination Full`) — см. [mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md).

### Пробелы по краям полей SDK-форма обрезает до проверки

**Перед отправкой SDK-форма убирает пробелы в начале и в конце текстовых полей, email, телефона и многострочного поля, а затем проверяет правила формы браузером.** Поэтому в данных отправки значения идут без пробелов по краям, а поле из одних пробелов с `required` считается пустым: форма не отправляется, браузер подсвечивает поле своей подсказкой. Чекбоксы и выпадающие списки не трогаются. Прогрессивный сбор (`collectDataEvent: 'blur'`, секция «Прогрессивный сбор — поля пишутся в визит до сабмита») мог ещё до сабмита отправить в визит вариант с пробелом: укороченное значение он повторно не шлёт. Как ещё спрашивают: «лид с пробелом в имени», «форма отправилась с пустым именем из пробелов».

## Антифрод-чек на сабмите — fraud_score

`AIO Antifraud` проверяет лид, если соответствующий шаг настроен во флоу перед `Destination`. Поля для результата задаются в настройках фильтра; в шаблонном сценарии это `fraud_score` и `triggered_rules`.

Отладка: если форма и сабмит исправны, но лид не доходит до получателя, проверь переход следующего шага, результат настроенной антифрод-проверки и лог Destination.

### Дубли лидов от повторного нажатия «Отправить» — макрос Form Loader

Стандартная SDK-форма отключает Submit на время отправки. Если повторные нажатия всё же создают заявки, проверь собственные обработчики формы. Макрос `AIO Form Loader` (`aio_form_loader`) из шаблона тенанта дополнительно показывает состояние отправки: после первого сабмита он накрывает форму оверлеем с лоадером и локализованным сообщением, пока идёт отправка, — оверлей препятствует повторным нажатиям, но не гарантирует дедупликацию любых запросов к получателю. Текст оверлея свой в каждой вертикали (Finance — про создание аккаунта, Nutra — про оформление заказа, Sweeps — про проверку приза); в iGaming-шаблоне макроса нет. Макрос не глобальный: в шаблоне он активен и уже подключён к лэндам-примерам с SDK-формой, на свой лэнд вставляется строкой `{{aio:macros:aio_form_loader}}` после `{{aio}}`.

## Submit Promise / Before-Submit Promise — кастомизация

- Кастомизируются под кейс. Rejected Message тоже кастомизируется.
- Свой пре-сабмит хук `beforeSubmitPromise` (подтверждение, модалка, свой запрос), который висит без ответа или отклоняет сабмит, — частая причина «кнопка „Отправить“ мёртвая» на лэндах со своим JS. Механика хуков — [reference/sdk.md](../reference/sdk.md).
- Переводы формы кастомизацией не покрываются: авто-перевод заполняет только четыре стандартных контрола и кнопку Submit, остальные строки на каждом языке заполняются вручную (см. «Мультиязычная форма» выше).

## Типовые вопросы по формам — диагностика и ответ

- «Данные у получателя перепутаны» → ключи Controls не совпадают. Layouts тут не помогут.
- «Форма не отправляется, AIO её не видит» → `<form>` вместо `{{form}}` без Non-SDK Form Handler.
- «Форма вообще не отрисовалась (пусто вместо формы)» → нет `{{form}}` в HTML лэнда, или нет `{{aio}}` перед `</body>`, или `features.form: false`, Выбор Form во флоу сам по себе не обязателен: без выбранной конфигурации и Content `Form fallback` SDK сохраняет встроенные контролы. Проверь также, что SDK подключён и его инициализация не упала.
- «Кнопка „Отправить“ не отправляет, в Network нет запроса» → CSS перекрыл кнопку (`pointer-events: none` / `disabled`), или завис хук `beforeSubmitPromise`, или осталась старая HTML-форма / свои intl-скрипты.
- «Двойные дропдауны страны / `intl-tel-input` глючит» → на лэнде остались свои `<script src=".../intl-tel-input...">`. Удалить — SDK подгрузит сам.
- «Хочу свою HTML-форму» → Non-SDK Form Handler (`{{aio:macros:aio_nonsdk_form_handler}}`), `name` инпутов = слаги полей `first_name/last_name/email/phone`. Но рекомендуется SDK.
- «Номер DE обрезается при вводе» → проверить `strictMode` в `intlParameters`; отказ получателя разбирать по его ответу, а не только по виду поля.

Полная диагностика «форма не сабмитится» (быстрый водораздел через Dummy Destination, чтение сетевого ответа сабмита).

### Типовые вопросы по языкам формы

- «В превью подписи есть, а на живом лэнде поля без подписей» → язык формы переведён частично: непереведённая строка уходит на лэнд пустой, а превью подставляет вместо неё английскую.
- «Добавил язык, а он пустой» → в ERP проверь сегмент выбора и `Prefill`: авто-перевод работает для новых языков из `Auto-translated`, если префил включён, и только для четырёх стандартных контролов и кнопки Submit.
- «Вместо подписей на форме видны `first_name_label` и подобное» → нужного ключа нет ни в языке визитёра, ни в `English` — SDK показывает сам ключ строки.
- «Можно ли дать визитёру переключать язык формы» → нельзя, переключателя нет; язык вычисляется один раз при загрузке.
- «Где выгрузить переводы в JSON» → в Form Builder такого нет, переводы правятся пословно в `Open translations`.

## Пошаговые инструкции — создание, подключение и дублирование формы

### Создать SDK-форму

Когда: с нуля собрать новую SDK-форму с нужными контролами / шагами / переводами.

**Путь:** `Settings → Forms → +Form`.

**Шаги:**

1. Задать **Name** + Description + Tags (вкладка Info).
2. **Controls** — добавить инпуты (`String text`, `Email`, `Phone`, `Text area`, `Checkbox`, `Drop list`, `Number`, `Date`) с правилами валидации. Кнопку Submit добавляет SDK; её строки правятся в `Languages`.
3. **Steps** — 1 или несколько шагов (например, шаг 1: email, шаг 2: phone). Сабмит на промежуточном шаге — **не** пуш лида: он отправляет поля текущего шага в визит и переводит на следующий шаг; лид уходит только на финальном сабмите.
4. **Languages** — кнопкой `Languages` добавить языки (сегмент `Auto-translated` даёт частичный префил), затем дописать оставшиеся строки в `Open translations` по каждому языку.
5. **Preview** — посмотреть результат.
6. `Save`.

После — форма доступна для подключения в кампании через шаг `Fill form` во флоу.

### Добавить шаг Fill form во флоу

Когда: SDK-форма создана, нужно подключить её к флоу.

**Путь:** `Edit Flow → +Step → Fill form → выбрать форму → включить Campaign template`.

**Шаги:**

1. В Flow Editor добавить шаг `Fill form`.
2. В настройках шага выбрать конкретную форму из списка.
3. Включить `Campaign template` (или Flow only — см. [how-to/flow-editor.md](flow-editor.md) → Settings Availability).
4. Сохранить.

После — выбранный payload задаёт `form_uuid` визита. В режиме `Campaign template` форму можно выбрать в карточке конкретной кампании; `{{form}}` использует текущую конфигурацию.

В шаблонных флоу с формой этот шаг уже стоит под именем `Choose Form` в режиме `Campaign template`: форма выбирается в карточке кампании, флоу для этого править не нужно. В кампаниях-примерах она уже выбрана (например, `Form Landing - Campaign Example` в Finance идёт с `Default Leads Form`).

### Дублировать SDK-форму — Copy form

Когда: новая форма мало отличается от существующей (например, другие переводы под другую гео).

**Путь:** `Settings → Forms → форма → `Copy form` → сохранить с другими переводами`.

**Что копируется:** Controls вместе с маппингами контрол↔поле визита, Steps, Layout, Languages (с возможностью отредактировать).

**Description и Tags тоже копируются:** при открытии `Copy form` они подставляются из исходника; перед сохранением их можно изменить.
