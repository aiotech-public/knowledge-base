# Domains (How-to)

Как работать с доменами в AIO: оба пути добавления (Buy / Add manually), атрибуты домена, мониторинг, чекеры на бан и красный экран, репойнт при падении сервера, замена домена при бане и первая линия защиты от DDoS.

## Что нужно подключить до добавления домена

- **Tenant** с правами `Admin` или Position с доступом на раздел `Domains` (см. [models/permissions-model.md](../models/permissions-model.md)).
- Интеграции:
  - Для пути **Buy** — два провайдера + сервер: `Domain Provider` (Namecheap / NameSilo, откуда покупаются домены) и `DNS Provider` (Cloudflare, куда пишем записи), плюс уже добавленный в AIO **`Server`** (инстанс), на который домен сразу указывает. Провайдеры подключаются в `Tech → Domain providers`, `Tech → DNS providers` (раздел **Tech**, не Settings — полные списки провайдеров в разделе «Раздел Tech — карта подсекций и провайдеры»). В модалке Buy выбирается именно готовый **`Server`**, а не `Server Provider` — интеграция `Server Provider` нужна раньше, чтобы этот сервер создать ([models/server.md](../models/server.md)).
  - Для пути **Manual** — только `DNS Provider` + `Server`. `Domain Provider` не нужен, домен уже куплен снаружи.
- **AIO-tech-bot** подключён в Telegram у того, кто будет `Monitoring User`-ом — **аккаунт привязан к Telegram**. Алерты идут только в TG, поэтому без привязки к Telegram нотификации доставить некуда (2FA через Google Authenticator такую привязку не даёт).
- Хотя бы один **сервер** добавлен и доступен — домену нужна точка приземления.

> В тенанте из коробки есть **преднастроенный тестовый сервер и тестовый домен** для экспериментов. Для реального трафика их использовать **не рекомендуется** — заводи свои.

### Domain Provider `Proxy String` — как подключить Namecheap с вайтлистом IP

`Tech → Domain providers → +` открывает `Create domain provider`: `Name` + `Description` + `Tags` + **`Integration Type`** (напр. `Namecheap`) + ключи учётки. У **части интеграций** (например, **Namecheap**) в этой модалке есть **обязательное** поле **`Proxy String`** (формат `user:pass@ip:port`). Через этот прокси AIO шлёт **API-запросы к самому регистратору** — исходящий IP запросов AIO к провайдеру будет IP этого прокси. Поле показывается в зависимости от выбранного `Integration Type`.

**Зачем это Namecheap:** Namecheap принимает API-запросы **только с IP из своего вайтлиста**. Поэтому «белый IP» — это IP прокси: пропиши в `Proxy String` прокси, а **его IP добавь в вайтлист Namecheap** — `Profile → Tools → Business & Dev Tools → Namecheap API Access → Whitelisted IPs`. Тогда запросы AIO идут через прокси, с IP, который Namecheap ожидает. Namecheap-специфика чек-боксов/ключа — `Namecheap API Key` + `Namecheap User` (username аккаунта-регистратора).

**Не путать с прокси в `Destination`.** Похожая настройка с другой целью: здесь прокси нужен, чтобы AIO **достучался до регистратора** по его вайтлисту; в `Destination` поле `Proxy to communicate` (в части интеграций — `Proxy`) показывает **рекламодателю** один статический исходящий IP ([context/architecture.md](../context/architecture.md)). К настройке Domain Provider тот механизм отношения не имеет.

### Cloudflare для доменов — несколько аккаунтов и какой ключ нужен

> **Несколько Cloudflare-аккаунтов.** В `Tech → DNS providers` можно подключить **несколько** CF-аккаунтов — каждый отдельным `DNS Provider`. При добавлении домена выбираешь, на каком CF-аккаунте его держать. Когда доменов много, их разводят по разным CF-аккаунтам — **один домен, один CF-аккаунт** (изоляция blast-radius) — см. [heuristics/domain-launch.md](../heuristics/domain-launch.md).

> **Ключ Cloudflare — либо Global API Key, либо API Token; тип определяется по самому ключу, а не по заполненности полей.** Рабочие оба, на полном объёме операций с доменом. Ключ `cfk_…` и «голый» hex-ключ AIO отправляет как **Global API Key** — парой email + ключ, поэтому при них поле `Cloudflare Email` обязано быть **заполнено**: без него провайдер отвечает `Global API Key requires an account email; fill the email field or use an API Token`. Ключ `cfut_…` и обычный API Token уходят **Bearer-заголовком**, email им не нужен; самому токену нужны права `Zone → Read`, `Zone → DNS → Edit` и `Zone → Zone Settings → Edit`. Что делать, если ключ не принимается, — разбор ошибок ниже.

### Что вписывать в поле `Cloudflare Account ID ( Optional )`

`Cloudflare Account ID ( Optional )` ждёт **32-символьный hex Account ID**, а не email. Взять его: дашборд Cloudflare → любой домен → `Overview` → `Account ID`. Подсказка у поля говорит то же самое: `32-hex Account ID (Cloudflare dashboard → any domain → Overview → Account ID). Not an email. Leave empty to use the API key default account.`

Поле опциональное: оставили пустым — зона создастся в аккаунте, который у этого ключа дефолтный. Указывать Account ID имеет смысл, когда у ключа несколько аккаунтов и зона должна лечь в конкретный.

Значение, не похожее на 32-hex (email, UUID с дефисами, обрывок строки), AIO в Cloudflare **не отправляет** — такое поле просто игнорируется, и зона уходит в дефолтный аккаунт ключа. Плейсхолдер поля — `Ex: 1a2b3c4d5e6f7a8b9c0d1e2f3a4b5c6d`.

### Cloudflare не подключается — что означают ошибки провайдера

Ошибки Cloudflare AIO показывает разобранными: `Cloudflare: <что поправить> (code N: <оригинальный текст>)`. Диагноз читается по коду:

| Код | Что произошло | Что делать |
|---|---|---|
| `1000` | Ключ ушёл Bearer-заголовком как API Token, и Cloudflare его не принял | Проверить, что токен скопирован целиком и не отозван |
| `6003`, `6103` | Ключ ушёл как Global API Key (`cfk_…` или hex), и Cloudflare такие заголовки не принял | Проверить, что это действительно Global API Key и что `Cloudflare Email` — email того же аккаунта |
| `9109`, `10000` | Токену не хватает прав на этот ресурс | Добавить токену права `Zone → Zone Settings → Edit` и `Zone → DNS → Edit` — либо перейти на Global API Key |
| `1061` | Зона для этого домена в Cloudflare уже существует | Удалить/переиспользовать существующую зону |
| `1097`, `1099` | Некорректный или незаданный `Account ID` | Поправить `Account ID` в настройках провайдера |
| `7003` | Запрошенный объект не найден | Проверить домен и `Account ID` |
| `1015` | Упёрлись в rate limit Cloudflare | Повторить позже |

Подсказки в ошибках `1000`, `6003`, `6103` предлагают заполнить или очистить `Cloudflare Email` — на способ авторизации это поле не влияет: тип ключа AIO определяет по самому ключу. Email нужен только Global API Key, лишний email рядом с токеном ничего не ломает.

Проверять ключ лучше кнопкой теста на самом `DNS Provider` — ошибка придёт с этим же разбором, не дожидаясь провала на покупке домена.

## Как добавить домен в AIO — Buy или Add manually

`Domains → +Domain` открывает окно `Add Domain to AIO`. Внутри — два пути (у каждого есть и bulk-вариант для пачки доменов):

- **Buy** — AIO покупает домен через подключённый `Domain Provider` (по апишке).
- **Add manually** — домен уже куплен снаружи, добавляем его в AIO вручную.

Основной путь — добавление через апишку (покупка): меньше кликов, автоматическое проставление настроек, удобнее и быстрее.

### Buy — AIO покупает

1. Открой `Domains → +Domain → Buy`.
2. Выбери:
   - **Domain Provider** — через какого регистратора покупаем (например, Namecheap).
   - **DNS Provider** — куда автоматически записать NS / A-record (Cloudflare).
   - **Server** — на какой сервер сразу указать домен (чтобы A-record был прописан).
   - **Deploy** — какой деплой-скрипт использовать (см. [context/architecture.md](../context/architecture.md) про агент / Squid).
   - **Domain name** — либо вписать вручную с доменной зоной, либо нажать рандомизатор.
   - Description, Tags — опционально.
3. Жми Confirm.
4. Домен зарегистрируется у провайдера, после успеха появится в списке `Domains`. Параллельно автоматически прописываются DNS-рекорды на выбранный сервер.

> Несмотря на API-интеграции с регистраторами (Namesilo / Namecheap / GoDaddy / Dynadot), доступность и цену конкретного имени стоит проверить **на сайте самого регистратора** до покупки.

### Домен не покупается / не регистрируется — что проверять

Домен через `Buy` не появляется в списке `Domains`, ругается на регистрацию или «висит». Разбор по частым причинам (симптом → проверка):

- **Не хватает баланса на аккаунте регистратора.** Покупка идёт по апишке с реального счёта у `Domain Provider` (Namecheap / NameSilo / Dynadot). Пустой или недостаточный баланс — регистрация не проходит. **Проверка:** ПКМ на провайдере в `Tech → Domain providers → Check balance` (баланс на аккаунте регистратора). Пополнить на стороне регистратора. У `GoDaddy` и `Spaceship` эта проверка всегда показывает `Balance: 0` — баланс по API они не отдают, смотреть надо в кабинете регистратора (секция «`Check balance` показывает `Balance: 0` — у части регистраторов баланс не отдаётся по API»).

- **Провайдер не настроен / нет доступа (ключ, прокси).** Апишка AIO не достучалась до регистратора — неверный/протухший API-ключ либо запрос идёт через недоступный прокси. **Проверка:** ПКМ на провайдере → `Test ...` (проверка коннекта, см. «Проверка провайдера»). Откуда брать ключи и как их выставлять — секция «Откуда брать API-ключи провайдеров». **Для Namecheap частая причина — `Proxy String`:** у него это поле **обязательно** и его IP должен быть в вайтлисте Namecheap — см. «Domain Provider `Proxy String` — как подключить Namecheap с вайтлистом IP».

- **Свежий домен — NS ещё не пропагировались.** Только что зарегистрированный домен не открывается / чекер молчит не потому, что покупка сломалась, а потому что DNS-записи ещё расходятся. Это `DNS-пропагация` — часть DNS-протокола, не баг AIO (та же механика, что даёт даунтайм при репойнте, см. «Repoint при бане сервера»). **Проверка:** подождать и перепроверить через минуту-две (шаг «Через минуту-две зайди на домен в браузере» в разделе «Как проверить, что получилось»).

- **Массовая закупка + SSL идут по очереди.** При `Buy domains in bulk` регистрация пачки и выпуск SSL-сертификатов обрабатываются **не мгновенно и не разом** — по очереди. Часть доменов появится и получит SSL позже остальных. **Проверка:** это ожидаемо — дать очереди доработать, затем перепроверить список; выпуск SSL вручную — `Issue SSL certificate` (см. одноимённую секцию). Это не зависшая покупка.

Если после этих проверок домен так и не регистрируется — глянь аудит операции: `right click → Show Logs` (окно `Domain logs`, полный трейл действий над доменом).

### Manual — домен уже куплен

1. На стороне регистратора **переведи NS домена на тот DNS-провайдер, что подключён в AIO** (обычно Cloudflare). Проверить список можно в `Tech → DNS providers`.
2. В AIO открой `Domains → +Domain → Add manually`.
3. Заполни:
   - **Name** — имя домена.
   - **Server** — на какой сервер он будет смотреть.
   - **DNS Provider** — тот, на который перевёл NS на шаге 1.
   - **Monitoring User** — кому в TG слать алерты при падении (см. «Как работает мониторинг доменов»).
4. Жми Confirm.

> Шаг 1 обязателен. Если NS на стороне регистратора не переведены на тот же провайдер, что выбран в AIO, AIO не сможет управлять DNS-рекордами этого домена.

## Какие настройки есть у домена (атрибуты)

`Right click → Edit Domain` открывает окно с настройками:

- **Description / Tags** — для поиска и фильтрации в списке.
- **Monitoring User** — юзер (или групповой чат через бота-юзера), которому AIO-tech-bot шлёт алерты. Подробнее — раздел «Как работает мониторинг доменов».
- **`Allow indexing by search engines`** — тоггл внутри модалки `Edit Domain` (не отдельный экшен и не свойство самого домена). Разрешает поисковикам индексировать домен. Для SEO-доменов включай, для всех остальных оставляй выключенным.
- **Default Query Code** — параметры, автоматически прикрепляющиеся к визиту при прямом заходе на голый домен без UTM. Используется для Direct Traffic (альтернатива — централизованный `Direct Traffic Distribution`, см. глоссарий).
- **Repoint Group** — формально это атрибут **сервера**, не домена. Но напрямую влияет на то, куда переедет домен при падении сервера (см. раздел Repoint).

## Как проверять домены на бан и красный экран (чекеры)

`Tech → Domain checkers`. Рекомендация — добавить **оба сходу**, оба бесплатные. В UI типы чекеров называются `Google Threat` и `Virus Total Public API`.

### Добавление чекера

`+Domain Checker` открывает окно создания: `Domain Checker Name`, `Description`, `Integration Type`. Набор остальных полей зависит от выбранного типа интеграции — API-ключи, client ID или прочие токены аутентификации. После заполнения — Confirm. Предусловие: активный аккаунт сервиса-чекера с готовым API-ключом.

### Google Threat

API-проверка домена на статус в блок-листе Google Safe Browsing («красный экран»). В UI тип интеграции чекера называется `Google Threat`.

- Бесплатная, лимитов по запросам нет.
- Настройка — через гугловский playground.
- **Нюанс:** браузерная проверка и API-проверка дают разные результаты. Браузер может уже показывать «красный экран», а API — отвечать `все ок`. Это лаг между обновлениями на стороне Google.
- Поэтому `Google Threat` — **дополнительный сигнал, а не главный показатель**. Если на домене уже виден красный экран, а чекер молчит — это нормально.

### VirusTotal

Публичный API с лимитом запросов.

- Один аккаунт ≈ 100–150 доменов — этого хватает на своевременные проверки.

### Тест чекера выдаёт `not implemented` — это не значит, что чекер не работает

`not implemented` при тесте домен-чекера значит, что не имплементирован **сам путь тестирования** (проверка «работает чекер или нет» через кнопку), а не что чекер не работает. Обычно чекер при этом **работает нормально**. Это не баг чекера.

Подтвердить работу чекера можно только по факту: увидеть, что он реально помечает какие-то домены (домен уходит в `Danger` со строкой `<имя чекера> Incident: <вердикт>`). Если пометки появляются — чекер работает, несмотря на `not implemented` при тесте.

### Почему статус бана появляется с задержкой

Чекеры перепроверяют домен **не на каждом прогоне**, а со своим минимальным интервалом на каждый тип чекера — поэтому между реальным баном домена и жёлтой пометкой в списке `Domains` есть лаг. Это ожидаемо: свежий бан может ещё не отобразиться, а держаться после снятия. Когда именно AIO гоняет домен-чекеры — *Что AIO проставляет и делает сам — фоновые задачи и их расписание*.

## Как работает мониторинг доменов

### Pinging — как работает

Домены пингует отдельный контур мониторинга **раз в минуту** (`https://<домен>/ping`); серверный кворум с пингом раз в 5 минут и подтверждением ~150 секунд — про серверы, не про домены. Канон механики — [context/architecture.md](../context/architecture.md) → «Мониторинг и нотификации». Мониторинг фиксирует **сам факт недоступности** и шлёт алерт — **детальную причину он не определяет**. Почему именно домен лёг — выясняет владелец домена.

В интерфейсе `Domains` иконка у домена — его статус (`Running` / `Processing` / `Danger`), а не «здоровье прямо сейчас»:

- **Иконки нет** — `Running`, всё ок.
- **Синий вращающийся значок** — `Processing`: идёт операция (покупка, выпуск SSL, репойнт, provision-check).
- **Красный крестик** — `Danger`: домен недоступен по мониторингу **или** упала операция (`Repoint failed: …`, `All checks failed: …`) **или** сработал чекер (`<имя чекера> Incident: <вердикт>`); подсказка у иконки показывает строку причины (`status_text`).
- **Жёлтый значок-предупреждение** — включённый `Under Attack`, не сигнал чекеров. Глаз / перечёркнутый глаз — мониторинг домена включён / выключен.

Сигнал чекеров (`Google Threat` / VirusTotal) приходит **тем же красным `Danger`** со строкой `<имя чекера> Incident: <вердикт>` (например, `1 Suspicious & 2 Malicious`); отдельного жёлтого статуса у чекеров нет. Как читать статус домена дальше — «Как проверять домены на бан и красный экран (чекеры)».

### Как отобрать домены, по которым мониторинг алертит прямо сейчас (`Alerting Now`)

В тулбаре списка `Domains` есть быстрый фильтр **`Alerting Now`** — он оставляет только домены, по которым мониторинг шлёт нотификации уровня `Danger` в данный момент. Подсказка у фильтра говорит то же: `Domains currently firing Danger monitoring notifications`.

Под фильтр домен попадает, только если совпало всё сразу: у домена **включён мониторинг**, по нему **открыт незакрытый инцидент недоступности** и **статус домена — `Danger`**. Домен с выключенным мониторингом или с уже закрытым инцидентом в выборку не войдёт, даже если он лежит.

### Сводка `AIO Monitoring` в Telegram приходит каждую минуту, пока домен в `Danger`

Алерт по доменам приходит не отдельным сообщением на домен, а сводкой `🛰 AIO Monitoring` со счётчиками `Ongoing` / `Resolved` и списком доменов по тенантам (до 5 на тенант, остальные — `⋯ and N more` со ссылкой на `Domains`). Пока по домену открыт инцидент, сводка уходит **каждую минуту** — она сама об этом предупреждает: `To mute Ongoing alerts, archive the domain or remove it from monitoring. Otherwise this report will be sent every few minutes.`

Заглушить поток, не чиня домен, можно двумя способами: снять мониторинг (`right click → Delete monitoring`) или заархивировать домен. Сообщение о восстановлении (`Recovered`) приходит один раз.

### Monitoring User

Юзер, которому AIO-tech-bot шлёт нотификации в Telegram при падении домена.

- Можно назначить **отдельного юзера**.
- Можно назначить **группового бота-юзера на чат** — тогда алерты падают в общий чат, и несколько человек могут на них реагировать. Полная процедура заведения такого юзера — раздел «Monitoring User через групповой чат TG».
- **Нужна привязка аккаунта к Telegram** (механика — [context/architecture.md](../context/architecture.md)). Алерты идут только в TG — без привязки AIO не может связать аккаунт с Telegram, и алерты не доходят (2FA через Google Authenticator привязку к TG не даёт).

### Алерты по нагрузке (опционально)

Помимо доступности AIO мониторит **нагрузку агента** на сервере. Если CPU держится выше 85% несколько минут — приходит алерт. Это отдельный канал: создаётся отдельный чат, в него добавляется второй бот AIO с Grafana, и алерты падают туда.

> Полезно при DDoS: рост RPS / CPU замечается раньше, чем падает кворум-пинг.

## Repoint при бане сервера

### Что происходит автоматически

При падении сервера все его домены авторепойнтятся на живой сервер **в пределах той же `Repoint Group`** — один раз, в момент, когда мониторинг подтвердил инцидент (через 5–10 минут после падения). Домен получает статус `Repoint requested - Current Incident: <причина>`, затем `Repoint done` и provision-check по `/ping`. Полная механика — [context/architecture.md](../context/architecture.md) → «Repoint — что это и зачем».

### Что должно быть готово, чтобы это работало

- **Минимум 2 живых сервера в одной `Repoint Group`** — иначе переезжать некуда: домены уходят в `Danger` с текстом инцидента (в Telegram — `No server to repoint`). Лучше у разных провайдеров / аккаунтов.
- **У домена подключён DNS-провайдер** — без него AIO не управляет записями и репойнтить нечем: домен уходит в `Danger` (в Telegram — `Domain is not under AIO Control`).

### Что не лечится автоматически

**DNS-пропагация — штатный даунтайм.** A-запись у DNS-провайдера меняется задачей на каждый домен, но пока DNS у визита обновится — пройдёт время. Это часть протокола, AIO с этим ничего не делает.

**Провал репойнта не повторяется.** Если DNS-провайдер ответил ошибкой (например, `Cloudflare: Cloudflare rate limit reached — try again later (code 1015…)` при переезде большой пачки — задачи идут подряд без пауз), домен остаётся в `Danger` с `Repoint failed: <причина>` и AIO повторно его не трогает; отдельного алерта об этом нет. Такие домены переезжают руками: отфильтровать по `Status` = `Danger`, выделить, `Repoint to a new server`. Разбор строк → «Домен ушёл в репойнт».

### Полу-ручной репойнт

Если хочется переехать конкретным доменом не дожидаясь падения — `right click домена → Repoint to a new server → выбрать сервер(ы)`. Экшен многосерверный: поле `Servers` — мультиселект (`server_uuids`). Есть и массовый вариант (выбрать пачку доменов → `Repoint to a new server`).

Многосерверный вариант у DNS-провайдера Cloudflare сначала удаляет A-записи, которых нет в новом списке серверов, и только потом добавляет новые — поэтому если добавление упало (`Repoint failed: …`), домен может остаться без A-записи и перестать резолвиться. Проверять статус домена сразу после массового репойнта и повторять экшен на доменах в `Danger`.

## Replace domain — массовая замена

Когда применять: **домен (а не сервер) забанили или попал в красный экран.** Репойнт не поможет, потому что упал не сервер — упал сам домен.

`Replace domain` — массовый action **над кампаниями** (не над самим доменом): в модалке выбираешь `From domain` → `To domain`, и старый домен заменяется на новый во всех domain-change-хендлерах связанных кампаний. Удобно в схеме с `Domain-Change Step`, где трекинговый и публичный домены разделены: меняем публичный домен, трекинговый (тот, что зашит в рекламную кампанию) не трогаем. Разница трекинговый↔публичный и что становится недоступно первым — [models/domain.md](../models/domain.md).

Если недоступен **трекинговый** домен — `Replace domain` не поможет, AIO в саму рекламную кампанию не вмешивается. Кампанию на площадке надо перезапускать с новой ссылкой.

## Create Subdomain

`right click домена → Create Subdomain`. Экшен доступен **только на домене с подключённым DNS-провайдером** — зону сабдомена AIO заводит через него; у домена без DNS-провайдера пункта в меню нет.

Открывается окно, в нём:

- **Subdomain name** — имя сабдомена.
- **Servers** — мультиселект (`server_uuids`): на какие серверы сабдомен будет смотреть (могут отличаться от родительских). Поле обязательное.
- **Monitoring User** — кому слать алерты по сабдомену. Поле обязательное: без него сервер запрос не примет.

Зачем: расширить охват одного купленного домена (например, `news.example.com`, `offer.example.com`), не покупая новые.

Сабдомен — отдельная строка в списке `Domains` со своим SSL: сертификат родительского домена его не покрывает, выпускать надо на строке самого сабдомена (секция «На какое имя выпускается сертификат — родительский домен субдомен не покрывает» в этом документе).

### Получился `b.example.com` вместо `b.a.example.com` — третий уровень так не создать

Имя сабдомена приклеивается к **registrable-домену** родительской записи, а не к её полному имени. Если вызвать `Create Subdomain` на записи, которая сама является сабдоменом (`a.example.com`), и ввести `b`, получится `b.example.com`, а не `b.a.example.com` — третий уровень этим экшеном не создаётся.

Полное имя сабдомена должно быть **уникальным среди доменов**: если такая запись в `Domains` уже есть, создание не пройдёт валидацию.

## Clear Domain

`right click → Clear Domain` — **полностью сбрасывает все связи домена** (с кампаниями, флоу, дистрибуциями). Сам домен из системы не удаляется, но обнуляется.

Используй осторожно — обратно вернуть связи нельзя, придётся перевешивать руками.

## Direct без Cloudflare

Штатная фича, не эксперимент. При **ручном** добавлении домена `DNS Provider` можно оставить пустым — домен будет смотреть прямо на сервер без Cloudflare. SSL-сертификат можно выпустить кнопкой прямо из AIO (через интерфейс на самом домене) либо добавить вручную.

**Когда применять:** это просто ещё один способ подключить домен — доступен всем и не привязан к конкретной вертикали. Уместен там, где Cloudflare-прослойка не нужна (например, при **низком бан-рейте серверов**).

**Что учитывать (риски):**

- Без Cloudflare сервер уязвимее к DDoS — нет первой ступени защиты.
- При бан-атаке может лечь весь сервер целиком, а не отдельные домены.

## Как защититься от DDoS: Under Attack и AS-Net Block-листы

Первая и вторая линии защиты от DDoS.

### Assign under attack status (Cloudflare)

`right click домена → Assign under attack status`. В UI экшен называется именно так (для пачки доменов — `Assign under attack`); подтверждение в модалке — `Are you sure you want to assign the under attack status?`. Cloudflare после этого показывает всем визитам `Verify you are human` captcha. Доступен только для доменов с подключённым Cloudflare (без DNS-провайдера экшена нет).

- Можно single-action (на один домен).
- Можно массово (выбрать пачку доменов, потом `Assign under attack`).
- По механике это **toggle** — включает/выключает under-attack-режим на домене (повторный вызов снимает статус).

### AS-Net Block-листы (AIO)

Списки IP-диапазонов для блокировки **на уровне AIO** (не Cloudflare). Используется, когда определили IP-источник DDoS и хочется его жёстко отсечь, чтобы запросы вообще не доходили до агента.

- Поддерживают **CIDR** (`x.x.x.x/24`).
- Поддерживают **диапазон через тире**.
- Блок-листы AIO **не дублируются в Cloudflare** — это отсечение именно на стороне AIO.

### Что AIO не делает автоматически

- Авто-включения Under Attack по триггеру роста RPS — **нет**. Решение и нажатие — руками владельца домена.
- Манипуляции настройками Cloudflare изнутри AIO (WAF, country block) — **нет**. WAF настраивается на своей стороне Cloudflare.

## Domain-Change Step (упоминание)

Дополнительный шаг во флоу, который разделяет два домена: **трекинговый** (тот, что зашит в рекламную кампанию) и **публичный** (тот, под которым лэнд реально открывается).

Зачем для доменов:

- Устойчивость публичного домена — публичный домен можно поменять через `Replace domain` без перезапуска рекламной кампании (трекинговый в объявлении остаётся прежним).
- Разнесение ролей — трекинговый и публичный домены меняются независимо друг от друга.

Детально про устройство и настройку — см. [models/flow-model.md](../models/flow-model.md).

## Частые грабли при настройке доменов

- **Один сервер в `Repoint Group`.** Самая частая. Репойнту некуда переезжать, защита не работает. Минимум — 2 сервера на группу, лучше — у разных провайдеров.
- **Нет привязки к Telegram у Monitoring User-а.** Алерты AIO-tech-bot идут только в TG — без привязки их доставлять некуда (2FA через Google Authenticator привязку не даёт). Чек: подключён ли юзер к боту.
- **Перепутаны `Domain Provider` и `DNS Provider` при настройке.** `Domain Provider` — где домен куплен (Namecheap, NameSilo). `DNS Provider` — где живут DNS-рекорды (Cloudflare). Эти роли разные, апишки разные, ключи разные.

- **Global API Key без `Cloudflare Email`.** Поддержаны оба типа ключа, но Global API Key (`cfk_…` или hex) уходит только парой email + ключ: с пустым полем придёт `Global API Key requires an account email; fill the email field or use an API Token`. API Token email не требует.
- **Manual-добавление без перевода NS.** Добавили домен через `Add manually`, выбрали Cloudflare, а на регистраторе NS остались старые. AIO не сможет управлять DNS-рекордами этого домена, домен будет глух.
- **Direct без Cloudflare под DDoS.** Фича штатная, но без CF нет первой ступени защиты — при атаке рискует лечь весь сервер. Под жёсткую нагрузку лучше оставлять CF.

- **`Buy` не проходит: пустой баланс или сломанный провайдер.** Покупка идёт с реального счёта у регистратора через апишку — нет баланса или неверный ключ/прокси, и регистрация фейлится. Чек: `Check balance` + `Test` на `Domain Provider`. Разбор причин — секция «Домен не покупается / не регистрируется».

- **Свежий домен «не работает» сразу после покупки.** Обычно это `DNS-пропагация` (NS ещё расходятся), а при `Buy in bulk` — ещё и очередь регистрации/SSL, которая обрабатывается не мгновенно. Не баг покупки — подождать и перепроверить.

## Как проверить, что получилось

После добавления домена (любым путём) проверь:

1. В списке `Domains` у домена нет иконки статуса (`Running`) — не синий вращающийся значок (`Processing`) и не красный крестик (`Danger`).
2. `right click → Show Logs` — нет ошибок последней операции.
3. Если домен через `Buy` — на стороне `Domain Provider` и `Cloudflare` появились соответствующие записи (опционально).
4. Через минуту-две зайди на домен в браузере — должен открыться placeholder либо лэнд (если уже привязан к кампании).
5. Если есть `Monitoring User` — убедись, что AIO-tech-bot пишет ему в TG (можно искусственно протриггерить — `right click → Place monitoring` / `Delete monitoring`).

## Нюансы и edge-кейсы доменов

### SSL и Repoint

- При `Repoint` SSL-сертификаты переносятся **автоматически** — отдельных шагов не требуется.

### Proxied / unproxied при добавлении

- При добавлении домена через DNS-провайдер есть опция `Proxied yes / no` (Cloudflare orange/grey cloud).

### Sitemap.xml и индексация

- `sitemap.xml` сейчас **не обновляется** — статичный. Серверных date-плейсхолдеров нет; клиентский JS-рендер дат бот не видит. Индексация — через `robots.txt` (тоггл `Allow indexing by search engines` в `Edit Domain`).

### DPI-блокировки и чекеры

- В странах с DPI-блокировками внешние чекеры доменов ненадёжны — достоверная проверка статуса возможна только **из самой страны** (свой бот-чекер из нужного гео).

### Бан публичного домена

- В схеме с разделением доменов публичный домен меняют через `Replace domain` **без перезапуска** рекламной кампании — трекинговый домен в объявлении остаётся прежним.

### Ротация домена через API

- Смена UUID домена в настройках `Domain-Change`-шага (PATCH). Флоу не пересобирается, новый трафик сразу идёт по новому домену.

### Уровни устойчивости домена — три инструмента

1. `Domain-Change Step` — разделение трекингового и публичного домена.
2. `Lock campaign to this domain` — кампания открывается только под своим доменом.
3. `AIO Filter Service` — фильтрация входящего трафика.

### Lock campaign to this domain — только один домен

- `Lock campaign to this domain` — **только один** домен, не несколько (выбора нескольких в UI нет).

### RU-домены — трафик с русских IP не открывает лэнд (`ECH` в Cloudflare)

- Если на домен, добавленный в AIO (смотрит на AIO-агент, под ним открываются лэнды), заходят с **русских IP** — из-за текущих блокировок возможны проблемы с открытием лэнда. Помогает включённый параметр `ECH` (Encrypted Client Hello) в Cloudflare: если его **отключить**, лэнды на таком домене начинают «падать».
- Это **не настройка AIO** — `ECH` включается в панели Cloudflare, не через `app.aio.tech`. Отдельная рекомендация, ни к чему в AIO не привязанная.

### IPv6 — точка выхода провайдера

- IPv6 определяется провайдером связи (точкой выхода), не AIO. На мобильной связи в EU доля IPv6 высокая.

### Локальные хостеры блокируют CDN

- Локальные хостеры могут блокировать запросы к CDN или к Cloudflare IP — лэнд не грузится **из-за хостера**, не AIO.

### Default Query — поля source, не кампании

- Поля внизу страницы домена под `Default Query Code` — это поля **source**, не кампании (частая путаница).

## Пошаговые инструкции по действиям с доменом

### Domain-Change шаг во флоу

**Путь:** `Flow → +Step → Domain-Change Step → выбрать домен → переименовать` (например, `Offer Domain-Change`, `Thankyou Domain-Change`).

После — визит на этом шаге переезжает с трекингового домена на публичный (см. [context/architecture.md](../context/architecture.md) → `Domain-Change Step`).

Также см. [models/flow-model.md](../models/flow-model.md) → Domain Change State.

### Default Query Code — JSON формат

Когда: голый домен (без UTM) должен попадать в конкретную кампанию через серверный Default Query.

Как ещё называют: заход на домен «без хвоста» (без query-хвоста); сам query-хвост в обиходе зовут «хвост».

**Путь:** `Tech → Domains → <D> → Edit Domain → Default Query → JSON`.

**Формат — массив объектов** `mode` / `path` / `query`:

```json
[
  {
    "mode": "path",
    "path": "/",
    "query": {
      "cuuid": "<UUID кампании>",
      "suuid": "<UUID source>",
      "launcher": "<UUID юзера>"
    }
  }
]
```

- `mode` — поведение query; пока единственное значение `path`.
- `path` — путь, для которого дописывается query (дефолт `/`). Несколько объектов с разными `path` разводят один домен по разным кампаниям: `/fr` → Campaign A, `/de` → Campaign B.
- `query` — UTM-параметры, дописываемые к URL после `?` (ключей сколько угодно). Реальные имена: `cuuid` — UUID кампании (`Tracker → Campaigns → UUID`), `suuid` — UUID source (`Tracker → Sources → UUID`), `launcher` — UUID юзера (`Settings → Users → UUID`).

Альтернатива — `Direct Traffic Distribution` (мощнее; сравнение двух путей маршрутизации голого домена — [models/distributions-model.md](../models/distributions-model.md)). Не миксовать оба на одном домене — конфликт.

### Tags на домене

**Путь:** `Edit Domain → Tags → +тег` (например, `Domain-Change`, `EN`, `Finance`).

Теги используются для фильтрации в списке доменов и для группировки в массовых action-ах.

### Replace domain — замена во всех кампаниях

Когда: домен забанили или попал в красный экран — нужно заменить во всех связанных кампаниях.

`Replace domain` — это action **над кампаниями** (не над самим доменом): в модалке два поля — `From domain` и `To domain`. Старый домен заменяется на новый во всех domain-change-хендлерах кампаний.

После — старый домен везде заменяется на новый. См. также секцию «Replace domain — массовая замена» выше.

### Archive vs Clear

**Путь:** ПКМ на домене → `Archive` или `Clear`.

| Действие | Что делает | Когда |
|---|---|---|
| **Archive** | Архивация только в AIO (домен пропадает из списка) | Когда домен больше не нужен, но прав на удаление в провайдере нет |
| **Clear** | Полная очистка: в AIO + сброс Cloudflare-настроек | Полный отказ от домена |

Прямого «удалить домен» в AIO **нет** — только Archive / Clear. Чтобы освободить имя для повторного добавления — Clear.

### Balance domains на сервере

Когда: на одном сервере слишком много доменов, хочешь распределить нагрузку на пул серверов.

**Путь:** `Servers → сервер → ПКМ → Balance domains` (это server-action `Server\ReBalanceDomains`, не domain-action).

AIO раскидывает домены этого сервера по `Running`-серверам той же `Repoint Group`: каждому домену случайно выбирается сервер из группы, домен получает статус `Repoint requested - Manual ReBalance`, затем обычный репойнт (`Repoint done` → provision-check). В выборку попадает и сам исходный сервер, поэтому часть доменов может остаться на месте; домены без DNS-провайдера экшен пропускает молча. Провал переезда отдельного домена (`Repoint failed: …`) не повторяется — такой домен репойнтят руками.

Также см. [context/architecture.md](../context/architecture.md) → Repoint Group.

### Issue SSL Certificate

Когда: для домена нужен SSL-сертификат (Let's Encrypt) — например, для Direct без Cloudflare или для домена в режиме `DNS only` (серое облако Cloudflare — запросы идут на сервер напрямую, не через прокси).

**Путь:** `<Domain> → Issue SSL certificate` (в UI action называется `Issue SSL certificate`).

AIO дёрнет Let's Encrypt и выпустит сертификат автоматически.

Выпуск повторяется сам: до **3 попыток с паузой 3 минуты**. Пока попытки не исчерпаны, домен держится в `Processing`; в `Danger` уходит только после третьей.

**Альтернатива (ручной сертификат):** `<Domain> → Edit → загрузить вручную`.

При ручной загрузке возможны две ошибки: `invalid certificate: <детали>` — файл сертификата невалиден/не читается; `not for this domain: <домены сертификата>` — сертификат валиден, но выписан **на другой домен** (имя домена не совпадает с CN/SAN сертификата; хвост строки перечисляет домены, на которые сертификат реально выписан).

### На какое имя выпускается сертификат — родительский домен субдомен не покрывает

Сертификат выпускается **ровно на одно имя** — то, которое записано в самой строке домена в списке `Domains`. У субдомена это только сам субдомен (`sub.example.com`); родительский домен в сертификат не входит. Подтверждение владения (ACME-challenge) идёт по этому же имени.

Сертификат **не wildcard**: выпущенный на родительском домене субдомен не покрывает. Если субдомену нужен сертификат от AIO (сценарий без внешнего прокси перед доменом — «Direct без Cloudflare»), запускай `Issue SSL certificate` **на строке самого субдомена**, а не на родителе.

Что показывает `status_text`, если выпуск упал (причина приходит хвостом строки после `:`).

### Cloudflare Under Attack Mode — массово

**Путь:** ПКМ на домене → `Assign under attack status` (single); для пачки — mass-select → `Assign under attack`.

Включает Cloudflare Under Attack — каждому визиту показывается captcha «Verify you are human». Первая ступень защиты от DDoS.

Captcha рубит конверсию у обычных юзеров — использовать только при реальной атаке.

Также см. секцию «Assign under attack status» выше.

### Monitoring User через групповой чат TG (полная процедура)

Когда: алерты должны падать в общий чат команды, не отдельному юзеру.

**Шаги:**

1. Создать TG-группу.
2. Добавить **AIO-tech-bot** в группу.
3. Получить **ID группы** (через `/getgroupid` команду боту).
4. Завести в AIO **юзера-пустышку** с этим chat ID.
5. В настройках домена / сервера выбрать этого юзера как `Monitoring User`.

## Прямой трафик в MTK: `Default Query` на домене (не дистрибуция)

В MTK прямой заход без UTM настраивается через `Default Query` на каждом домене — в MTK это ведётся вручную на каждом домене. Централизованный `Direct Traffic Distribution` в MTK **не используется**: это операционная настройка, которую надо постоянно дорабатывать (добавлять домены и кампании), а такую централизацию MTK не ведёт. Поле `Direct traffic distribution` в модалке домена есть, но в MTK-практике не задействуется.

`Default Query` задаётся на домене (`Domains → <домен> → Edit → Default Query`); формат JSON стандартный — секция `Default Query Code — JSON формат` в этом документе. Раздел `Domains` в MTK — отдельная плоская вкладка топ-навигации (`/app/mtk/tech/domains`), а не внутри группы `Tech`.

В MTK-виде домены доступны как отдельная вкладка топ-навигации, а серверы и провайдеры лежат в `Settings`; сам набор действий над доменом тот же. Разбор билда целиком — *Как устроен MTK-вид AIO: навигация, пресеты из шаблона и методы под типовые задачи*.

## Раздел Tech — карта подсекций и провайдеры

### Где находится в ERP

Серверы, домены, прокси, провайдеры и чекеры живут в разделе **`Tech`** (`/app/tech`), **НЕ в `Settings`**.

Раздел `Tech` — 9 подсекций: **Servers · Domains · Proxies · DNS providers · Domain providers · Domain checkers · Proxy providers · Server providers · Deployments**.

В MTK эти настройки расположены иначе: серверы, прокси и провайдеры — в `Settings`; домены — отдельная плоская вкладка `Domains` в топ-навигации (`/app/mtk/tech/domains`). См. *Как устроен MTK-вид AIO: навигация, пресеты из шаблона и методы под типовые задачи*.

### Provider / Checker — `Integration type` (примеры)

Каждый провайдер/чекер создаётся как `Name` + `Description` (+ `Tags`) + **`Integration type`** (дропдаун). Список поддержанных интеграций **постоянно обновляется** — не держим его здесь как эталон; всегда актуальный полный перечень виден **в самом дропдауне `Integration type` в UI**. Ниже — примеры того, что поддержано, для ориентира:

| Подсекция | `Integration type` (примеры) |
|---|---|
| **Server providers** | напр. Digitalocean · Hetzner · Vultr · Gcore |
| **Domain providers** (регистраторы) | напр. Namecheap · Namesilo · GoDaddy · Dynadot · Porkbun |
| **DNS providers** | напр. Cloudflare · GCore |
| **Domain checkers** | Google Threat · Virus Total Public API |

> Поле прокси в модалке есть у нескольких типов провайдеров:
> - **DNS providers** и **Domain checkers** — `Proxy` (**опциональный**): API-запросы провайдера/чекера идут через него; полезно для разведения VirusTotal по IP (см. секцию VirusTotal выше).
> - **Часть Domain providers** (напр. `Namecheap`) — `Proxy String` (**обязательный**): регистратор принимает API только с вайтлист-IP, поэтому запросы AIO идут через прокси, чей IP добавлен в вайтлист регистратора. Детали — «Domain Provider `Proxy String` — как подключить Namecheap с вайтлистом IP» выше.

### Откуда брать API-ключи провайдеров

- **NameSilo** (`Domain Provider`): ключ генерируется в `API Manager`. При создании ключа отметить **только** чекбокс Agreement; Read-only access и прочие опции оставить **снятыми** — иначе AIO не сможет управлять доменом.
- **Cloudflare** (`DNS Provider`): для доступа к API нужен **подтверждённый email** на аккаунте. Global API Key берётся в `My Profile → API Tokens → Global API Key` (в том числе новый формат `cfk_`); он ходит парой email + key, поэтому поле `Cloudflare Email` при нём заполняется обязательно. API Token (`cfut_…` или обычный токен) поддержан наравне — он уходит Bearer-заголовком, `Cloudflare Email` ему не нужен, а самому токену нужны права `Zone → Read`, `Zone → DNS → Edit` и `Zone → Zone Settings → Edit` (разбор ошибок — «Cloudflare не подключается» выше). Поля модалки `Create DNS Provider`: `Cloudflare API Key`, `Cloudflare Email`, `Cloudflare Account ID ( Optional )` и `Proxied` — что вписывать в Account ID, см. секцию «Что вписывать в поле `Cloudflare Account ID ( Optional )`».

### Проверка провайдера (Test)

ПКМ на созданном провайдере → `Test ...` проверяет, что ключ рабочий:

- **Server Provider** (DigitalOcean): успех — `Auth as <email>, with N droplets limit`. Плохой ответ (`Unidentified`) = нет связи с DO / неверные креды. Если аккаунт заблокирован, ответ прямо это говорит: `account is inactive - Your team has been locked due to lack of payment or improper use of the platform. Please open a ticket...`.
- **DNS Provider** (Cloudflare): успех — `Cloudflare OK — <тип ключа> (<аккаунт>), zone <зона>, all required permissions present` (на аккаунте без зон вместо зоны будет `no zones yet`). Тест не просто дёргает ключ: он прогоняет права, нужные для работы с зоной, поэтому их нехватка всплывает здесь, а не позже на создании домена — тогда вместо успеха придёт `Cloudflare: missing permissions — ...` с перечнем недостающих.
- **Domain Provider**: помимо `Test` есть `Check balance` — посмотреть баланс на аккаунте регистратора.

### `Check balance` показывает `Balance: 0` — у части регистраторов баланс не отдаётся по API

`Balance: 0` не всегда означает пустой счёт: часть регистраторов баланс через API не отдаёт, и AIO показывает по ним ноль. Так работают **GoDaddy** и **Spaceship** — у них `Check balance` вернёт `Balance: 0`, и колонка баланса в списке `Tech → Domain providers` тоже будет 0 независимо от реальных денег на аккаунте.

Смотреть баланс таких аккаунтов надо в личном кабинете самого регистратора. У остальных подключаемых регистраторов (`Namecheap`, `Namesilo`, `Dynadot`, `Porkbun`, `Timeweb`, `NiceNic`) `Check balance` показывает реальную сумму со счёта.

### Proxies (`Tech → Proxies`)

`+ Proxy` → **`Name`** + **`Proxy string`** (формат `http://login:password@host:port`). Прокси переиспользуются в DNS-провайдерах, чекерах и в сценариях с внешними лэндами.

Это **не то же самое**, что `Proxy providers` (следующая секция): `Proxies` — конкретный статический прокси (`Name` + `Proxy string`), `Proxy provider` — интеграция с провайдером прокси, у которой свои поля учётки.

### Proxy providers (`Tech → Proxy providers`)

`Tech → Proxy providers` (`/app/tech/proxy-providers`, ERP-only) — **отдельная сущность** от `Proxies`. `Proxies` — это готовая прокси-строка (`Name` + `Proxy string`), а `Proxy provider` — провайдер прокси, подключённый как интеграция: форма `Name` + **`Integration type`** (дропдаун) + поля учётки, зависящие от выбранного типа.

Типы `Integration type`:

- **`Static`** — ручной статический прокси. Поля: `proxy_login`, `proxy_password`, `proxy_address`, `proxy_port` (все опциональные).
- Прокси-провайдер, подключаемый **по API-ключу вендора** — поля учётки приходят по выбранному типу интеграции. Актуальный полный список типов — в самом дропдауне `Integration type` в UI.

### Deployments (`Tech → Deployments`)

`+ Deployment` → **`Name`** (имя скрипта) + **`Script`** (код-редактор; shell-скрипт сетапа сервера). Выбирается при добавлении сервера (поле `Deployment` в `Buy a server`, `Deployment script` в `Add manually`) и при `Buy`-домене (`Deploy`).

### Add server (`Tech → Servers → + Server`)

Два пути: **`Buy a server`** (через Server Provider API; скрипт установки выполняет провайдер при первом запуске машины) и **`Add manually`** (публичный IP + атрибуты; скрипт из `Script content` выполняется на машине самостоятельно). В обоих случаях AIO ждёт ответа агента на `GET http://<ip>/ping` до ~30 минут, потом `Danger` с `All install checks failed`. Полный список атрибутов — [models/server.md](../models/server.md); если сервер не устанавливается.

> **`Monitoring user` можно назначить только юзеру с включённой 2FA** — без 2FA юзер в дропдауне на эту роль не выбирается.

### Add domain (`Tech → Domains → + Domain`)

Четыре пути: **`Buy domain`** / **`Buy domains in bulk`** (купить через `Domain Provider`) · **`Add manually`** / **`Add manually in bulk`** (свои домены). Модалка `Add manually`: **`Domain`** + **`Servers`** (куда указывает) + **`DNS provider`** + **`Monitoring user`** + тоггл **`Allow indexing by search engines`** (off по умолчанию). Тулбар списка доменов: фильтры `Server` / `Provider` / `Status`, быстрый фильтр `Alerting Now` (см. «Как отобрать домены, по которым мониторинг алертит прямо сейчас»), плюс сортировка по **серверам** или **владельцам** (Owner) и фильтр `With Archived?`.

> **`Servers` обязателен.** Если поле `Servers` пустое, создание падает с ошибкой `no servers provided` — домену нужна точка приземления. Укажи хотя бы один добавленный и доступный сервер.

### Action Menu — мониторинг и логи домена

- **`Place monitoring` / `Delete monitoring`** — отдельный экшен в ПКМ-меню, который **назначает или снимает мониторинг** с домена (подтверждение в окне `Place monitoring` / `Delete monitoring`). Это не только способ протриггерить тестовый алерт (см. «Как проверить»), но и штатное действие включить/выключить пинг-мониторинг.
- **`Show Logs`** открывает окно `Domain logs` — это **полный аудит-трейл всех действий** над доменом, а не только проверка последней операции.
