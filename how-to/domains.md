# Domains (How-to)

Как работать с доменами в AIO: оба пути добавления (Buy / Add manually), атрибуты домена, мониторинг, чекеры на бан и красный экран, репойнт при падении сервера, замена публичного домена и первая линия защиты от DDoS.

## Что нужно подключить до добавления домена

- **Tenant** с правами на нужное действие над доменом: `tech.domains.edit.buy-domain` для Buy или `tech.domains.edit.add-manually` для ручного добавления; одного просмотра `Domains` недостаточно (см. [models/permissions-model.md](../models/permissions-model.md)).
- Интеграции:
  - Для пути **Buy** — два провайдера + сервер: `Domain Provider` (Namecheap / NameSilo, откуда покупаются домены) и `DNS Provider` (Cloudflare, куда пишем записи), плюс уже добавленный в AIO **`Server`** (инстанс), на который домен сразу указывает. В ERP провайдеры подключаются в `Tech → Domain providers` и `Tech → DNS providers`, в MTK — в `Settings → Domain providers` и `Settings → DNS providers`. Полные списки — в разделе «Раздел Tech — карта подсекций и провайдеры». В модалке Buy выбирается добавленный **`Server`** с IP, а не `Server Provider` — интеграция `Server Provider` нужна раньше, чтобы этот сервер создать ([models/server.md](../models/server.md)).
  - Для пути **Manual** нужен `Server`. `DNS Provider` выбирают для управления DNS через AIO; для Direct его можно оставить пустым. `Domain Provider` не нужен, домен уже куплен снаружи.

- Для доставки алертов **AIO-tech-bot** подключён в Telegram у `Monitoring User` — **аккаунт привязан к Telegram**. Алерты идут только в TG, поэтому без привязки к Telegram нотификации доставить некуда (2FA через Google Authenticator такую привязку не даёт).
- Хотя бы один **сервер** добавлен и доступен — домену нужна точка приземления.

> **Рабочие серверы и домены шаблон тенанта не копирует: для трафика свои сервер и домен заводятся здесь и в `Tech → Servers` (ERP) или `Settings → Servers` (MTK) руками.** Что именно приезжает из шаблона — [context/architecture.md](../context/architecture.md). В кампаниях-примерах из шаблона домен не выбран — его выбирают перед запуском.

### Domain Provider `Proxy String` — как подключить Namecheap с вайтлистом IP

В ERP `Tech → Domain providers → +`, в MTK `Settings → Domain providers → +` открывает `Create domain provider`: `Name` + `Description` + `Tags` + **`Integration Type`** (напр. `Namecheap`) + ключи учётки. У **части интеграций** (например, **Namecheap**) в этой модалке есть **обязательное** поле **`Proxy String`** (формат `user:pass@ip:port`). Через этот прокси AIO шлёт **API-запросы к самому регистратору** — исходящий IP запросов AIO к провайдеру будет IP этого прокси. Поле показывается в зависимости от выбранного `Integration Type`.

**Зачем это Namecheap:** Namecheap принимает API-запросы **только с IP из своего вайтлиста**. Поэтому «белый IP» — это IP прокси: пропиши в `Proxy String` прокси, а **его IP добавь в вайтлист Namecheap** — `Profile → Tools → Business & Dev Tools → Namecheap API Access → Whitelisted IPs`. Тогда запросы AIO идут через прокси, с IP, который Namecheap ожидает. Namecheap-специфика чек-боксов/ключа — `Namecheap API Key` + `Namecheap User` (username аккаунта-регистратора).

### Формат `Proxy String` у Namecheap — HTTP-прокси или SOCKS5 (`socks5://`)

`Proxy String` принимает прокси в двух видах, и от вида строки зависит, каким протоколом AIO подключается к прокси:

- `user:pass@ip:port` — без префикса: AIO подключается к нему как к **HTTP-прокси**;
- `socks5://user:pass@ip:port` — с префиксом: как к **SOCKS5**-прокси.

Префикс `socks5://` — не ошибка формата: для SOCKS5-прокси он нужен, а HTTP-прокси можно записать без префикса или с `http://`. Вид строки должен совпадать с протоколом, который отдаёт поставщик прокси; если не совпал или прокси не пускает к API Namecheap, тест провайдера вернёт `Proxy CONNECT aborted` или `Can't complete SOCKS5 connection to api.namecheap.com. (N)` — разбор в секции «Namecheap: `Proxy CONNECT aborted` или `Can't complete SOCKS5 connection…`» в этом документе.

Namecheap сверяет с вайтлистом адрес, с которого запрос к нему пришёл, — обычно это IP из строки. Если прокси выходит в интернет с другого адреса, Namecheap назовёт реальный в ошибке `Invalid request IP` — секция «Namecheap: `Invalid request IP` (ошибка `1011150`)» в этом документе.

### `Proxy String` у Domain Provider — не то же, что прокси в `Destination`

Похожая настройка с другой целью: в Domain Provider прокси нужен, чтобы AIO **достучался до регистратора** по его вайтлисту; в `Destination` поле `Proxy to communicate` (в части интеграций — `Proxy`) задаёт прокси для API-запросов **к рекламодателю**; постоянство исходящего IP зависит от выбранного прокси ([context/architecture.md](../context/architecture.md)). К настройке Domain Provider тот механизм отношения не имеет.

### Cloudflare для доменов — несколько аккаунтов и какой ключ нужен

> **Несколько Cloudflare-аккаунтов.** В ERP `Tech → DNS providers`, в MTK `Settings → DNS providers` можно подключить **несколько** CF-аккаунтов — каждый отдельным `DNS Provider`. При добавлении домена выбираешь, на каком CF-аккаунте его держать. Когда доменов много, их разводят по разным CF-аккаунтам — **один домен, один CF-аккаунт** (изоляция blast-radius) — см. [heuristics/domain-launch.md](../heuristics/domain-launch.md).

> **Ключ Cloudflare — либо Global API Key, либо API Token; тип определяется по самому ключу, а не по заполненности полей.** Интеграция поддерживает оба типа; доступность операций зависит от прав ключа и выбранного ресурса. Ключ `cfk_…` и «голый» hex-ключ AIO отправляет как **Global API Key** — парой email + ключ, поэтому при них поле `Cloudflare Email` обязано быть **заполнено**: без него провайдер отвечает `Global API Key requires an account email; fill the email field or use an API Token`. Ключ `cfut_…` и обычный API Token уходят **Bearer-заголовком**, email им не нужен; самому токену нужны права `Zone → Read`, `Zone → DNS → Edit` и `Zone → Zone Settings → Edit`. Что делать, если ключ не принимается, — разбор ошибок ниже.

### Что вписывать в поле `Cloudflare Account ID ( Optional )`

`Cloudflare Account ID ( Optional )` ждёт **32-символьный hex Account ID**, а не email. Взять его: дашборд Cloudflare → любой домен → `Overview` → `Account ID`. Подсказка у поля говорит то же самое: `32-hex Account ID (Cloudflare dashboard → any domain → Overview → Account ID). Not an email. Leave empty to use the API key default account.`

Поле опциональное: оставили пустым — зона создастся в аккаунте, который у этого ключа дефолтный. Указывать Account ID имеет смысл, когда у ключа несколько аккаунтов и зона должна лечь в конкретный.

Значение, не похожее на 32-hex (email, UUID с дефисами, обрывок строки), AIO в Cloudflare **не отправляет** — такое поле просто игнорируется, и зона уходит в дефолтный аккаунт ключа. Плейсхолдер поля — `Ex: 1a2b3c4d5e6f7a8b9c0d1e2f3a4b5c6d`.

### Cloudflare не подключается — что означают ошибки провайдера

Ошибки Cloudflare с известным кодом AIO показывает разобранными: `Cloudflare: <что поправить> (code N: <оригинальный текст>)`. Диагноз читается по коду:

| Код | Что произошло | Что делать |
|---|---|---|
| `1000` | Ключ ушёл Bearer-заголовком как API Token, и Cloudflare его не принял | Проверить, что токен скопирован целиком и не отозван |
| `6003`, `6103` | Ключ ушёл как Global API Key (`cfk_…` или hex), и Cloudflare такие заголовки не принял | Проверить, что это действительно Global API Key и что `Cloudflare Email` — email того же аккаунта |
| `9109`, `10000` | Не хватает прав (`9109`) или Cloudflare отказал в авторизации на ресурс (`10000`) | Проверить доступ токена к ресурсу и права `Zone → Zone Settings → Edit`, `Zone → DNS → Edit`; альтернатива — Global API Key |
| `1061` | Зона для этого домена в Cloudflare уже существует | Удалить/переиспользовать существующую зону |
| `1097`, `1099` | Некорректный или незаданный `Account ID` | Поправить `Account ID` в настройках провайдера |
| `7003` | Запрошенный объект не найден | Проверить домен и `Account ID` |
| `1015` | Упёрлись в rate limit Cloudflare | Повторить позже |

Подсказки в ошибках `1000`, `6003`, `6103` предлагают заполнить или очистить `Cloudflare Email` — на способ авторизации это поле не влияет: тип ключа AIO определяет по самому ключу. Email нужен только Global API Key, лишний email рядом с токеном ничего не ломает.

Проверять ключ лучше кнопкой теста на самом `DNS Provider` — ошибка придёт с этим же разбором, не дожидаясь провала на покупке домена.

### `Invalid request headers` или `Authentication error` от Cloudflare — те же коды, только без разбора

`Invalid request headers` — оригинальный текст Cloudflare для кода `6003`, `Authentication error` — для кода `10000`. Сейчас AIO показывает их внутри разобранной строки, например `Cloudflare: … (code 6003: Invalid request headers)`. В прежних версиях они приходили как есть: `Please note! Invalid request headers` в окне `Test DNS provider` или `Domain creation failed: Authentication error` в статусе домена. Читаются они по таблице из секции «Cloudflare не подключается — что означают ошибки провайдера»:

- `6003` — ключ ушёл как Global API Key (`cfk_…` или hex), и Cloudflare не принял заголовки авторизации. Проверьте, что в `Cloudflare API Key` ключ скопирован целиком, а в `Cloudflare Email` — email того же аккаунта Cloudflare без лишних символов. API Token (`cfut_…` и остальные токены) уходит Bearer-заголовком и email не использует.
- `10000` — Cloudflare отказал в авторизации на ресурс: обычно у API Token не хватает прав `Zone → Zone Settings → Edit` / `Zone → DNS → Edit`. Расширьте права токена или перейдите на Global API Key.

`Test DNS provider` перечисляет ресурсы, которые не удалось прочитать, строкой `Cloudflare: missing permissions — …`. Права на запись тест не проверяет; если доступных зон ещё нет, проверки DNS и настроек зоны пропускаются. Разбор — секция «Проверка провайдера (Test)».

## Тест провайдера показывает `Please note! …` — как читать ответ

`Please note!` — заголовок окна, в котором AIO показывает результат проверки провайдера; сам ответ — текст после него. Проверка запускается, как только открыто окно `Test` из меню доменного провайдера (у DNS-провайдера — `Test DNS provider`), и берёт **сохранённые** настройки: после правки ключей сохраните провайдера и откройте проверку заново. Провайдеры — в `Tech → Domain providers` и `Tech → DNS providers`, в MTK — в `Settings`. Так же выглядит окно `Check balance`: `Please note! Balance: <сумма>`.

### Какой ответ `Test` значит «всё работает»

- `Success` — доменный провайдер (регистратор) принял ключи.
- `Cloudflare OK — <тип ключа> (<аккаунт>), zone <зона>, all required permissions present` — Cloudflare принял ключ и выполнил проверки чтения. Запись этот тест не проверяет; без доступных зон проверки DNS и настроек зоны пропускаются.
- `{"zones_total":N,"zones":[…]}` — `GCore` или `Bunny` вернули список зон аккаунта.
- `Auth as <email>, with N droplets limit` — провайдер серверов DigitalOcean.

Формат результата зависит от интеграции. При отказе тест показывает сообщение провайдера, ошибку соединения или короткое `Failed`. Разбор частых ответов — в секциях этого раздела.

### Spaceship: `Test` показывает `Please note! Failed`

`Please note! Failed` при подключении Spaceship как `Domain Provider` значит, что Spaceship не отдал список доменов по ключам из настроек провайдера. AIO запрашивает `GET <API Url>/api/v1/domains` с заголовками из `API Key` и `API Secret`; любой ответ, кроме `200`, или обрыв соединения дают `Failed`, а причину этот тест не показывает. Так же отвечают тесты `GoDaddy`, `Dynadot`, `Namesilo` и `Timeweb`; у `NiceNic` и `Porkbun` причина идёт после `Failed:`.

Что проверить:

1. `API Url` — базовый адрес `https://spaceship.dev`, как в подсказке поля: путь `/api/v1/…` AIO дописывает сам.
2. `API Key` и `API Secret` — пара от одного ключа Spaceship, скопированная целиком.
3. У ключа в Spaceship есть доступ ко всем операциям, которые делает AIO: список доменов (его и проверяет `Test`), проверка доступности имени, контакты, регистрация, статус домена и смена NS.
4. После правки — сохранить провайдера и открыть `Test` заново.

Контактные поля (`Contact First Name` … `Contact Postal Code`) тест не проверяет: ошибка в них всплывёт только при покупке, в статусе домена. Телефон заполняйте в формате из подсказки поля — `+1.123456789`, иначе Spaceship отвечает `The phone field must follow the allowed format.`

### Namecheap: `Proxy CONNECT aborted` или `Can't complete SOCKS5 connection…` — нет соединения через прокси

Обе строки значат, что запрос AIO не дошёл до Namecheap: его не пропустил прокси из `Proxy String`. До проверки вайтлиста Namecheap дело не дошло.

- `Proxy CONNECT aborted` — AIO подключался к прокси как к HTTP-прокси (строка без префикса или с `http://`), и прокси оборвал соединение, не открыв канал до API Namecheap.
- `Can't complete SOCKS5 connection to api.namecheap.com. (N)` — AIO подключался по SOCKS5 (строка с `socks5://`), и прокси отказался соединять с Namecheap; число в скобках — код отказа самого прокси.

Что проверить: прокси жив, логин и пароль в строке верные; протокол прокси совпадает с видом строки (SOCKS5 — только с `socks5://`, HTTP — без префикса или с `http://`, секция «Формат `Proxy String` у Namecheap» в этом документе); поставщик прокси пускает соединения к `api.namecheap.com`. Если прокси исправен, а ошибка та же, — нужен другой прокси. Те же тексты приходят и при покупке — в статусе домена после `Domain creation failed:`.

### Namecheap: `Invalid request IP` (ошибка `1011150`) — адрес запроса не в вайтлисте

`Cannot fetch address info: {"Error":{"__text":"Invalid request IP: <IP>","_Number":"1011150"}}` — ответ самого Namecheap: запрос пришёл с адреса, которого нет в вайтлисте API-доступа аккаунта. Префикс `Cannot fetch address info:` добавляет AIO: на этом шаге тест запрашивает у Namecheap адрес аккаунта, а дальше идёт ответ Namecheap как есть. Другие отказы Namecheap на этом шаге приходят с тем же префиксом, текст — внутри `__text`.

Что делать:

1. Добавить адрес из ошибки в Namecheap: `Profile → Tools → Business & Dev Tools → Namecheap API Access → Whitelisted IPs`.
2. Если адрес в ошибке не совпадает с IP в `Proxy String` — прокси выходит в интернет с другого адреса. В вайтлист нужен именно адрес из ошибки; IP из `Proxy String` там тоже оставьте.
3. Если адрес в ошибке меняется от проверки к проверке — выходной IP у прокси плавающий, и вайтлист Namecheap с ним работать не будет: нужен прокси с постоянным выходным IP.

### Namecheap: `Missing address info: …` — в аккаунте Namecheap не заполнен адрес

Тест Namecheap проверяет не только ключ, но и адрес в аккаунте Namecheap: при покупке AIO подставляет его в контакты домена. `Missing address info: <поля>` перечисляет, чего не хватает, из набора `FirstName`, `LastName`, `Address1`, `City`, `StateProvince`, `Zip`, `Country`, `Phone`, `EmailAddress`. Заполните эти поля в профиле аккаунта Namecheap и откройте `Test` заново — при полном адресе тест отвечает `Success`.

Ещё одна настройка влияет на ответы: при `Enable Sandbox API for tests` = `Enable` AIO обращается к песочнице Namecheap (Sandbox API), а не к боевому API.

### `There is no Api credentials at settings` — у провайдера не заполнены ключи

Тест не отправлялся: в сохранённых настройках провайдера пусты обязательные поля ключей. У регистраторов это `There is no Api credentials at settings`, у Namecheap — `There are no Api credentials or proxy at settings` (ему нужен ещё и `Proxy String`), у Cloudflare — `There is no CL Key at settings`. Заполните поля в `Edit domain provider` или `Edit DNS provider`, сохраните и откройте `Test` снова.

## Как добавить домен в AIO — Buy или Add manually

`Domains → +Domain` открывает окно `Add domain to AIO`. Внутри — два пути (у каждого есть и bulk-вариант для пачки доменов):

- **Buy** — AIO покупает домен через подключённый `Domain Provider` (по апишке).
- **Add manually** — домен уже куплен снаружи, добавляем его в AIO вручную.

Основной путь — добавление через апишку (покупка): меньше кликов, автоматическое проставление настроек, удобнее и быстрее.

### Buy — AIO покупает

1. Открой `Domains → +Domain → Buy`.
2. Выбери:
   - **Domain Provider** — через какого регистратора покупаем (например, Namecheap).
   - **DNS Provider** — куда автоматически записать NS / A-record (Cloudflare).
   - **Servers** — серверы, на которые сразу указать домен (чтобы A-record был прописан).
   - **Domain to buy** — либо вписать вручную с доменной зоной, либо нажать рандомизатор.
3. Жми Confirm.
4. Запись появится в `Domains` до завершения регистрации. Дальше AIO сначала настраивает DNS, затем покупает домен у регистратора и проверяет его доступность.

> Несмотря на API-интеграции с регистраторами (Namesilo / Namecheap / GoDaddy / Dynadot), доступность и цену конкретного имени стоит проверить **на сайте самого регистратора** до покупки.

### Домен не покупается / не регистрируется — что проверять

Домен через `Buy` не появляется в списке `Domains`, ругается на регистрацию или «висит». Разбор по частым причинам (симптом → проверка):

- **Не хватает баланса на аккаунте регистратора.** Покупка идёт по апишке с реального счёта у `Domain Provider` (Namecheap / NameSilo / Dynadot). Пустой или недостаточный баланс — регистрация не проходит. **Проверка:** ПКМ на провайдере → `Check balance`; в ERP список в `Tech → Domain providers`, в MTK — `Settings → Domain providers` (баланс на аккаунте регистратора). Пополнить на стороне регистратора. У `GoDaddy` и `Spaceship` эта проверка всегда показывает `Balance: 0` — у этих регистраторов AIO баланс не запрашивает, смотреть надо в кабинете регистратора (секция «`Check balance` показывает `Balance: 0` — у части регистраторов баланс не отдаётся по API»).

- **Провайдер не настроен / нет доступа (ключ, прокси).** Апишка AIO не достучалась до регистратора — неверный/протухший API-ключ либо запрос идёт через недоступный прокси. **Проверка:** ПКМ на провайдере → `Test ...` (проверка коннекта, см. «Проверка провайдера»). Откуда брать ключи и как их выставлять — секция «Откуда брать API-ключи провайдеров». **Для Namecheap частая причина — `Proxy String`:** у него это поле **обязательно** и его IP должен быть в вайтлисте Namecheap — см. «Domain Provider `Proxy String` — как подключить Namecheap с вайтлистом IP».

- **Свежий домен — NS ещё не пропагировались.** Если регистрация завершилась, а домен ещё не открывается, проверьте делегирование NS и DNS-пропагацию. Молчание чекера само по себе не подтверждает успешную покупку. Это `DNS-пропагация` — часть DNS-протокола, не баг AIO (та же механика, что даёт даунтайм при репойнте, см. «Repoint при падении сервера»). **Проверка:** подождать и перепроверить через минуту-две (шаг «Через минуту-две зайди на домен в браузере» в разделе «Как проверить, что получилось»).

- **Массовая закупка обрабатывается не мгновенно.** При `Buy domains in bulk` AIO регистрирует и проверяет доступность каждого домена отдельно. SSL автоматически эта цепочка не выпускает: после покупки запустите `Issue SSL certificate` (см. одноимённую секцию).

Если после этих проверок домен так и не регистрируется — глянь аудит операции: `right click → Domain logs` (доступные записи журнала домена).

### Manual — домен уже куплен

1. Если используете DNS Provider, на стороне регистратора **переведите NS домена на этот DNS-провайдер** (обычно Cloudflare). Список в ERP — `Tech → DNS providers`, в MTK — `Settings → DNS providers`. Для Direct без DNS Provider настройте A-record самостоятельно.
2. В AIO открой `Domains → +Domain → Add manually`.
3. Заполни:
   - **Domain** — имя домена.
   - **Servers** — серверы, на которые он будет смотреть.
   - **DNS Provider** — тот, на который перевели NS на шаге 1; для Direct оставьте пустым.
   - **Monitoring User** — кому в TG слать алерты при падении (см. «Как работает мониторинг доменов»).
4. Жми Confirm.

> При использовании DNS Provider шаг 1 нужен, чтобы его записи обслуживали домен. Само изменение зоны через API не переводит NS у регистратора. Для Direct без DNS Provider этот шаг не нужен.

## Какие настройки есть у домена (атрибуты)

`Right click → Edit domain` открывает окно с настройками:

- **Description / Tags** — для поиска и фильтрации в списке.
- **Monitoring User** — юзер (или групповой чат через бота-юзера), которому AIO-tech-bot шлёт алерты. Подробнее — раздел «Как работает мониторинг доменов».
- **`Allow indexing by search engines`** — тоггл внутри модалки `Edit domain` (настройка домена, не отдельный экшен). Управляет запретом индексации в `robots.txt`; включение само по себе не гарантирует индексацию. Для SEO-доменов включай, для всех остальных оставляй выключенным.
- **Default Query Code** — параметры, которыми AIO дополняет пустые значения query при совпадении пути с настройкой домена; существующие непустые значения сохраняются. Используется для Direct Traffic (альтернатива — централизованный `Direct Traffic Distribution`, см. глоссарий).
- **Repoint Group** — формально это атрибут **сервера**, не домена. Но напрямую влияет на то, куда переедет домен при падении сервера (см. раздел Repoint).

## Как проверять домены на бан и красный экран (чекеры)

В ERP — `Tech → Domain checkers`, в MTK — `Settings → Domain checkers`. Рекомендация — добавить **оба сходу**, оба бесплатные. В UI типы чекеров называются `Google Threat` и `Virus Total Public API`.

Чекеры проверяют только домены в `Running`, и не непрерывно, а периодически; `Virus Total Public API` проверяет домен заметно реже, чем `Google Threat`. Поэтому между реальным баном и алертом в AIO бывает лаг — это не пропущенный алерт (*Что AIO проставляет и делает сам — автоматические обновления и их лаг*).

### Добавление чекера

`+Domain Checker` открывает окно создания: `Name`, `Description`, `Integration Type`. Набор остальных полей зависит от выбранного типа интеграции — API-ключи, client ID или прочие токены аутентификации. После заполнения — Confirm. Предусловие: активный аккаунт сервиса-чекера с готовым API-ключом.

### Google Threat

API-проверка домена на статус в блок-листе Google Safe Browsing («красный экран»). В UI тип интеграции чекера называется `Google Threat`.

- Бесплатная, лимитов по запросам нет.
- Настройка — через гугловский playground.
- **Нюанс:** браузерная проверка и API-проверка дают разные результаты. Браузер может уже показывать «красный экран», а API — отвечать `все ок`. Причину расхождения эти два результата не устанавливают.
- Поэтому `Google Threat` — **дополнительный сигнал, а не главный показатель**. Если на домене уже виден красный экран, а чекер молчит — это нормально.

### VirusTotal

Публичный API с лимитом запросов.

- Один аккаунт ≈ 100–150 доменов — этого хватает на своевременные проверки.

### Тест чекера выдаёт `not implemented` — это не значит, что чекер не работает

`not implemented` при тесте домен-чекера значит, что не имплементирован **сам путь тестирования** (проверка «работает чекер или нет» через кнопку), а не что чекер не работает. Обычно чекер при этом **работает нормально**. Это не баг чекера.

Подтвердить работу чекера можно только по факту: увидеть, что он реально помечает какие-то домены (домен уходит в `Danger` со строкой `<имя чекера> Incident: <вердикт>`). Если пометки появляются — чекер работает, несмотря на `not implemented` при тесте.

### Почему статус бана появляется с задержкой

Чекеры перепроверяют домен **не на каждом прогоне**, а со своим минимальным интервалом на каждый тип чекера — поэтому между реальным баном домена и красным `Danger` в списке `Domains` есть лаг. Это ожидаемо: свежий бан может ещё не отобразиться, а держаться после снятия. Когда именно AIO гоняет домен-чекеры — *Что AIO проставляет и делает сам — автоматические обновления и их лаг*.

## Как работает мониторинг доменов

### Pinging — как работает

AIO сам следит за доступностью доменов с включённым мониторингом (как и серверов): упавший домен получает `Danger` со строкой причины, восстановившийся — `Running` со строкой `Fine`. Механика — [context/architecture.md](../context/architecture.md) → «Мониторинг и нотификации». Мониторинг фиксирует **факт недоступности** и текст ошибки проверки и шлёт алерт — **почему именно домен лёг, он не определяет**. Это выясняет владелец домена.

В интерфейсе `Domains` иконка у домена — его статус (`Running` / `Processing` / `Danger`), а не «здоровье прямо сейчас»:

- **Иконки нет** — статус `Running`; это не отдельная проверка доступности прямо сейчас.
- **Синий вращающийся значок** — `Processing`: идёт операция (покупка, выпуск SSL, репойнт, проверка домена после выпуска или репойнта).
- **Красный крестик** — `Danger`: домен недоступен по мониторингу **или** упала операция (`Repoint failed: …`, `All checks failed: …`) **или** сработал чекер (`<имя чекера> Incident: <вердикт>`); подсказка у иконки показывает строку причины (`status_text`).
- **Жёлтый значок-предупреждение** — включённый `Under Attack`, не сигнал чекеров. Глаз / перечёркнутый глаз — мониторинг домена включён / выключен. Такой же глаз стоит у каждого сервера в колонке `Servers` — включён ли мониторинг самого сервера; рядом IP сервера с иконкой копирования.

Сигнал чекеров (`Google Threat` / VirusTotal) приходит **тем же красным `Danger`** со строкой `<имя чекера> Incident: <вердикт>` (например, `1 Suspicious & 2 Malicious`); отдельного жёлтого статуса у чекеров нет. Как читать статус домена дальше — «Как проверять домены на бан и красный экран (чекеры)».

### `Wrong server: …`, `Unreachable: …`, `Domain not found: …` в статусе домена — это мониторинг доступности

Эти строки в подсказке у красного крестика пишет мониторинг доступности, когда домен не ответил так, как отвечает агент AIO. `Wrong server: Probe did not answer 200 "ok"` — ответ пришёл, но не такой, как у агента AIO: отвечает чужой сервер или прокси перед сервером. `Unreachable: Check timed out` — ответа не дождались. `Domain not found: Domain does not exist` — имя домена не находится в DNS. `TLS invalid: …` — проблема с сертификатом домена. `Domain expiring: <дата> (N days left)` / `Domain expired: …` — подходит или прошёл срок регистрации домена. Когда домен снова отвечает как надо, мониторинг сам возвращает `Running` со строкой `Fine`.

### Значок `M` или `S` у домена — `Multiple servers linked: N` и `Single server linked`

Чип `S` / `M` рядом с номером домена показывает счётчик привязок к серверам в карточке AIO: `S` (подсказка `Single server linked`) — одна, `M` (подсказка `Multiple servers linked: N`) — несколько, где `N` — значение счётчика. Красный цвет у `M` — не ошибка. Фактические A-записи проверяют у DNS-провайдера.

Серверов у домена несколько, когда в мультиселекте `Servers` выбрано больше одного — при `Buy domain`, `Add manually`, `Create subdomain` или `Repoint to a new server`. Какие именно серверы — колонка `Servers` в списке `Domains`.

Колонки `Servers`, `Server` и `Server Provider` и фильтр `Server` видны только с правом `tech.servers.view`, колонка `Domain Provider` и фильтр `Provider` — с `tech.domain-providers.view`, колонка `DNS Provider` — с `tech.dns-providers.view`; без права их нет ни в таблице, ни в `Table settings`.

Счётчик и колонка могут расходиться: после покупки через `Buy domain` и после `Create subdomain` AIO учитывает основной сервер дважды, поэтому при одном выбранном сервере чип покажет `M` и `Multiple servers linked: 2`. Ориентируйтесь на колонку `Servers`; `Repoint to a new server` пересчитывает счётчик по фактическому списку серверов.

### Как отобрать домены, по которым мониторинг алертит прямо сейчас (`Alerting Now`)

В тулбаре списка `Domains` есть быстрый фильтр **`Alerting Now`** — он отбирает домены по трём условиям ниже. Доставку нотификаций конкретному пользователю фильтр не проверяет. Подсказка у фильтра говорит то же: `Domains currently firing Danger monitoring notifications`.

Под фильтр домен попадает, только если совпало всё сразу: у домена **включён мониторинг**, по нему **висит незакрытый инцидент** и **статус домена — `Danger`**. Инцидентом считается не только недоступность, но и провал репойнта или проверки после выпуска (`All 6 repoint attempts failed: …`, `All checks failed: …`), предупреждение о сроке домена и зависание в `Processing` дольше 3 часов — всё, что попадает в Telegram-отчёт. Домен с выключенным мониторингом или с уже закрытым инцидентом в выборку не войдёт, даже если он лежит.

### Отчёт `AIO Monitoring · Domains` в Telegram — при изменении, напоминание раз в час

Алерт по доменам приходит не отдельным сообщением на домен, а отчётом `🛰 AIO Monitoring · Domains` со счётчиками `Ongoing` / `Resolved` и списком доменов по тенантам: под каждым доменом — IP сервера и причина (`└ <IP> · Unreachable: …`), до 5 доменов на тенант, свежие изменения первыми, остальные — `⋯ and N more` со ссылкой на `Domains`. После падения или восстановления отчёт уходит при ближайшем цикле рассылки. Пока инцидент висит, а нового нет, приходит напоминание раз в час: `To mute Ongoing alerts, archive the domain or remove it from monitoring. Otherwise a reminder is sent every hour.` Серверы приходят отдельным отчётом `🛰 AIO Monitoring · Servers` ([context/architecture.md](../context/architecture.md)).

Домен, который пролежал в `Danger` больше 30 дней, AIO снимает с мониторинга сам — строка `Monitoring paused: down for 30+ days — re-enable monitoring to check again`, напоминания по нему прекращаются; вернуть проверки — `Place monitoring` ([context/architecture.md](../context/architecture.md) → «Объект в `Danger` дольше 30 дней — мониторинг выключается сам»).

В отчёт попадают и провалы операций: домен, у которого кончились попытки репойнта (`All 6 repoint attempts failed: …`) или проверки домена после выпуска и репойнта (`All checks failed: …`), и домен, зависший в `Processing` дольше 3 часов.

Заглушить отчёты, не чиня домен, можно двумя способами: снять мониторинг (`right click → Delete monitoring`) или заархивировать домен. Архив при этом останавливает и трафик на домене — секция «`Archive` у домена — прячет из списков и останавливает трафик» в этом документе. О восстановлении (`Recovered`) отчёт сообщает один раз.

### Monitoring User

Юзер, которому AIO-tech-bot шлёт нотификации в Telegram при падении домена.

- Можно назначить **отдельного юзера**.
- Можно назначить **группового бота-юзера на чат** — тогда алерты падают в общий чат, и несколько человек могут на них реагировать. Полная процедура заведения такого юзера — раздел «Monitoring User через групповой чат TG».
- **Нужна привязка аккаунта к Telegram** (механика — [context/architecture.md](../context/architecture.md)). Алерты идут только в TG — без привязки AIO не может связать аккаунт с Telegram, и алерты не доходят (2FA через Google Authenticator привязку к TG не даёт).

### Алерты по нагрузке (опционально)

Помимо доступности AIO мониторит **нагрузку агента** на сервере. Если CPU держится выше 85% несколько минут — приходит алерт. Это отдельный канал: создаётся отдельный чат, в него добавляется второй бот AIO с Grafana, и алерты падают туда.

> Полезно при DDoS: рост RPS / CPU замечается раньше, чем мониторинг увидит, что сервер перестал отвечать.

## Repoint при падении сервера

### Что происходит автоматически

При падении сервера AIO один раз запускает авто-репойнт его неархивных доменов, у которых он указан основным сервером, — когда мониторинг перевёл сервер в `Danger`. Для переезда нужны DNS-провайдер и другой `Running`-сервер **в пределах той же `Repoint Group`**. Домен получает статус `Repoint requested - Current Incident: <причина>`, затем `Repoint done` и проверка домена на новом сервере. Итог виден в отчёте `AIO Monitoring · Servers` под упавшим сервером: `Repointing N domains → group <группа>`. Полная механика — [context/architecture.md](../context/architecture.md) → «Repoint — что это и зачем».

### Что должно быть готово, чтобы это работало

- **Рекомендуется заранее держать минимум 2 сервера в одной `Repoint Group`**, лучше у разных провайдеров / аккаунтов. При падении одного для переезда достаточно одного другого неархивного сервера со статусом `Running`. Если такого нет, домены уходят в `Danger` с текстом инцидента (в отчёте по серверу — `N left in Danger: no running server to repoint in group <группа>`).
- **У домена подключён DNS-провайдер** — без него AIO не управляет записями и репойнтить нечем: домен уходит в `Danger` (в отчёте по серверу — `N left in Danger: no DNS provider (not under AIO control)`).

### Что не лечится автоматически

**DNS-пропагация — штатный даунтайм.** A-запись у DNS-провайдера меняется задачей на каждый домен, но пока DNS у визита обновится — пройдёт время. Это часть протокола, AIO с этим ничего не делает.

**Временную ошибку DNS-провайдера репойнт переживает сам, исчерпанные попытки — уже нет.** На ошибке (например, `Cloudflare: Cloudflare rate limit reached — try again later (code 1015…)` при переезде большой пачки) задача домена повторяется до 6 раз с паузой, домен всё это время в `Processing` со строкой `Repoint attempt <n> of 6 failed: …`. Если попытки кончились, домен остаётся в `Danger` с `All 6 repoint attempts failed: <причина>` и, если у домена включён мониторинг, попадает в Telegram-отчёт. Такие домены переезжают руками: отфильтровать по `Status` = `Danger`, выделить, `Repoint to a new server`. Разбор строк → «Домен ушёл в репойнт».

### Полу-ручной репойнт

Если хочется переехать конкретным доменом не дожидаясь падения — `right click домена → Repoint to a new server → выбрать сервер(ы)`. Экшен многосерверный: поле `Servers` — мультиселект (`server_uuids`). Есть и массовый вариант (выбрать пачку доменов → `Repoint to a new server`).

**Переставит ли ручной репойнт DNS, решает `DNS provider` у домена.** У домена с `DNS provider` (купленного через `Buy` или добавленного через `Add manually` с выбранным провайдером) экшен переписывает A-записи у провайдера на новые серверы: статус `Repoint requested` → `Repoint done` → проверка домена на новом сервере. У домена без `DNS provider` (Direct) AIO только перепривязывает домен к выбранным серверам в своей карточке: статус не меняется, A-запись у своего DNS переставляете сами; число доменов у серверов пересчитывается не сразу. Одиночный и массовый варианты меняют привязки одинаково. В ERP массовый пункт появляется, только если у **всех** выделенных доменов есть `DNS provider`: Direct-домены перепривязывают по одному. В MTK такого ограничения массового пункта нет.

Многосерверный вариант у DNS-провайдера Cloudflare сначала удаляет A-записи, которых нет в новом списке серверов, и только потом добавляет новые — поэтому если добавление упало (`Repoint failed: …`), домен может остаться без A-записи и перестать резолвиться. Проверять статус домена сразу после массового репойнта и повторять экшен на доменах в `Danger`.

## Replace domain — массовая замена

Когда применять: **сменить нужно сам домен, а не сервер** — например, домен попал в «красный экран» браузера. Репойнт тут не поможет: сервер работает, менять нужно домен.

`Replace domain` — массовый action **над кампаниями** (не над самим доменом): в модалке выбираешь `From domain` → `To domain`, и старый домен заменяется на новый в domain-change-хендлерах выделенных кампаний. Удобно в схеме с `Domain-Change Step`, где трекинговый и публичный домены разделены: меняем публичный домен, трекинговый (тот, что зашит в рекламную кампанию) не трогаем. Разница трекинговый↔публичный и что становится недоступно первым — [models/domain.md](../models/domain.md).

Если недоступен **трекинговый** домен — `Replace domain` не поможет, AIO в саму рекламную кампанию не вмешивается. Кампанию на площадке надо перезапускать с новой ссылкой.

## Create subdomain

`right click домена → Create subdomain`. Для создания нужен **подключённый DNS-провайдер** — AIO настраивает записи сабдомена через него. В ERP пункт скрыт без DNS-провайдера; в MTK пункт может отображаться и без него, но такая задача завершится ошибкой.

Открывается окно, в нём:

- **Domain** — имя сабдомена.
- **Servers** — мультиселект (`server_uuids`): на какие серверы сабдомен будет смотреть (могут отличаться от родительских). Поле обязательное.
- **Monitoring User** — кому слать алерты по сабдомену. Поле обязательное: без него сервер запрос не примет.

Зачем: расширить охват одного купленного домена (например, `news.example.com`, `offer.example.com`), не покупая новые.

Сабдомен — отдельная строка в списке `Domains`. SSL автоматически при создании не выпускается: сертификат только на имя родительского домена сабдомен не покрывает, выпуск запускают на строке сабдомена (секция «На какое имя выпускается сертификат — родительский домен субдомен не покрывает» в этом документе).

### Получился `b.example.com` вместо `b.a.example.com` — имя добавляется к registrable-домену

Имя сабдомена приклеивается к **registrable-домену** родительской записи, а не к её полному имени. Если вызвать `Create subdomain` на записи, которая сама является сабдоменом (`a.example.com`), и ввести `b`, получится `b.example.com`, а не `b.a.example.com` — для `b.a.example.com` в поле имени нужно ввести `b.a`.

Полное имя сабдомена должно быть **уникальным среди доменов**: если такая запись в `Domains` уже есть, создание не пройдёт валидацию.

## Clear Domain и Archive — как убрать домен и можно ли его вернуть

Действия «удалить домен» в AIO нет: домен убирают из работы через `Archive` или `Clear domain` (ПКМ по домену, у обоих есть массовый вариант). Оба прячут домен из списка `Domains`, но делают разное: `Archive` обратим и держит имя занятым, `Clear domain` стирает имя у записи и освобождает его для повторного добавления.

### `Clear domain` — имя стирается, запись уходит в архив

`Clear domain` стирает у записи имя домена, выключает мониторинг, ставит статус `Danger` со строкой `Domain cleared` и архивирует запись; прежнее имя остаётся только в описании — `Cleared: <домен>`. Сама запись не удаляется: там, где домен был выбран (кампании, `Link Generator`, шаги `Domain-Change`), ссылка остаётся на запись без имени — в таблицах она видна как `cleared domain`, и домен там нужно выбрать заново.

Изменение доходит до трафика не мгновенно; после этого AIO больше не находит это имя, и новый запрос инициализации через агент получает `502` ([mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md)). Имя освобождается — домен можно снова добавить в AIO.

### `Clear strategy`: `Full Clear` удаляет зону у DNS-провайдера, `Just AIO` — нет

В окне `Clear domain` есть поле `Clear strategy`, по умолчанию `Full Clear`:

- `Full Clear` — вдобавок к очистке в AIO запрашивает удаление домена у DNS-провайдера: у домена — всю зону со всеми её записями, у сабдомена — его A-запись. Если DNS-провайдера у записи нет, этот шаг пропускается.
- `Just AIO` — чистит только запись в AIO, DNS у провайдера остаётся как был.

Подпись окна `Domain will be cleared, but DNS records will remain.` верна только для `Just AIO`: при `Full Clear`, который стоит по умолчанию, AIO запрашивает удаление у провайдера. После очистки проверьте результат у провайдера: успешная очистка записи AIO сама по себе не подтверждает удаление DNS. Регистрацию домена у регистратора `Clear domain` не трогает ни в одном варианте.

### Можно ли восстановить домен после `Clear domain`

Вернуть имя очищенной записи нельзя: ни `Edit domain`, ни `Unarchive` его не возвращают — из архива запись вернётся без имени. Домен у регистратора при этом не удалён, и его можно завести в AIO заново, как новую запись, — через `Add manually` (секция «Manual — домен уже куплен» в этом документе).

Что учесть при повторном добавлении:

- если `Full Clear` удалил зону у DNS-провайдера — при `Add manually` с `DNS provider` AIO создаст её заново, а NS у регистратора должны указывать на эту зону (их видно в колонке `Nameservers` списка `Domains`, по умолчанию скрыта);
- новая запись — это новый домен: в кампаниях, `Link Generator` и шагах `Domain-Change` его выбирают заново, а кампания с `Lock campaign to this domain` не откроется на новой записи, пока домен в ней не выбран заново;
- `Default Query`, `Direct traffic distribution` и теги задаются на новой записи с нуля.

Прежнее имя очищенной записи видно в её описании `Cleared: <домен>` — в списке `Domains` с фильтром `Archived` (`Show archived items`).

### `Archive` у домена — прячет из списков и останавливает трафик

`Archive` убирает домен из списка `Domains` и из выпадающих списков, снимает с него `Monitoring user`, мониторинг архивный домен не проверяет; когда изменение доходит до трафика (не мгновенно), AIO отклоняет новые запросы инициализации на нём — агент отдаёт `502` ([mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md)). Имя остаётся занятым: пока запись в архиве, добавить тот же домен заново нельзя — для этого нужен `Clear domain`.

Вернуть домен в работу — `Unarchive` (запись видна в списке с фильтром `Archived`); `Monitoring user` после этого назначьте заново. Архивировать домен может только тот, у кого на него уровень доступа `Own` ([models/permissions-model.md](../models/permissions-model.md)).

### Что будет с доменами, если заархивировать DNS-провайдер

С доменами ничего не происходит: архив DNS-провайдера прячет его из списка DNS-провайдеров (ERP — `Tech → DNS providers`, MTK — `Settings → DNS providers`) и из выпадающих списков, а домены, которые уже на нём, продолжают работать через него. Их записи у провайдера не меняются; авто-репойнт, `Create subdomain`, `Assign under attack status` и `Full Clear` у этих доменов идут через того же провайдера. Для нового домена архивного провайдера в списке нет — чтобы выбрать его снова, верните провайдера из архива (`Unarchive`). Так же ведёт себя архив доменного провайдера (регистратора): на уже добавленные домены он не влияет.

### `No query results for model [App\Models\Domain]` при архивации или другом действии с доменом

Текст значит, что действие не нашло запись домена: записи с таким uuid нет в тенанте, из которого отправлен запрос (после `[App\Models\Domain]` может стоять uuid записи). Обновите страницу `Domains` и повторите действие. Если домен в списке есть, а ошибка повторяется, напишите в чат поддержки и приложите uuid домена (колонка `UUID`, по умолчанию скрыта).

В прежних версиях этот же текст приходил, когда на домен не хватало уровня доступа. Сейчас такой отказ выглядит иначе: `No access to this object (own level required)` для `Archive`/`Unarchive` и `No access to this object (edit level required)` для действий, требующих Edit. У других действий свои требования ([models/permissions-model.md](../models/permissions-model.md)).

## Direct без Cloudflare

Штатная фича, не эксперимент. При **ручном** добавлении домена `DNS Provider` можно оставить пустым — домен будет смотреть прямо на сервер без Cloudflare. SSL-сертификат можно выпустить кнопкой прямо из AIO (через интерфейс на самом домене) либо добавить вручную.

**Когда применять:** это просто ещё один способ подключить домен — доступен всем и не привязан к конкретной вертикали. Уместен там, где Cloudflare-прослойка не нужна (например, при **низком бан-рейте серверов**).

**Что учитывать (риски):**

- Без Cloudflare сервер уязвимее к DDoS — нет первой ступени защиты.
- При бан-атаке может лечь весь сервер целиком, а не отдельные домены.

### Как подключить DNS-провайдера (Cloudflare) к уже добавленному Direct-домену

У домена, который уже заведён в AIO, `DNS provider` не меняется: в `Edit domain` такого поля нет, провайдер выбирается только при создании записи. Поэтому Direct-домен (добавленный без DNS-провайдера) переводят под Cloudflare пересозданием записи: освобождают имя через `Clear domain` и добавляют домен заново через `Add manually` — уже с `DNS provider`.

Заархивировать старую запись недостаточно: архив имя не освобождает, и `Add manually` с тем же именем не пройдёт проверку уникальности. Между очисткой старой записи и созданием новой возможны `502`; новая запись тоже доходит до трафика не мгновенно. Делайте оба шага подряд и после добавления проверяйте домен.

Что даёт DNS-провайдер: авто-репойнт при падении сервера, `Create subdomain` и `Assign under attack status` работают только у домена с DNS-провайдером.

### Шаги: перевести Direct-домен под Cloudflare

1. Подключите Cloudflare в `Tech → DNS providers` (в MTK — в `Settings`) и проверьте его окном `Test DNS provider` (секция «Cloudflare для доменов — несколько аккаунтов и какой ключ нужен» в этом документе).
2. Запишите, где выбран домен: домен кампании в `Edit Campaign` (и `Lock campaign to this domain`), `Link Generator`, шаги `Domain-Change`, а в `Edit domain` — `Default Query`, `Direct traffic distribution`, теги. У новой записи этих привязок и настроек не будет.
3. ПКМ по домену → `Clear domain`. У Direct-домена `Clear strategy` ни на что не влияет: DNS-провайдера у записи нет, у провайдера трогать нечего.
4. `Domains → + Domain → Add manually`: то же имя, `Servers`, `DNS provider` = ваш Cloudflare, `Monitoring user`. AIO заведёт зону в этом аккаунте Cloudflare, если её там нет, и пропишет A-запись на выбранный сервер; если зона уже есть — возьмёт её и оставит у имени домена только A-записи на выбранные серверы.
5. У регистратора поставьте NS этой зоны Cloudflare: их видно в Cloudflare и в колонке `Nameservers` списка `Domains` (по умолчанию скрыта).
6. Дождитесь статуса `Running` (после проверки домена — строка `Everything is fine`) и выберите домен заново везде, где он стоял (шаг 2).

## Как защититься от DDoS: Under Attack и AS-Net Block-листы

Первая и вторая линии защиты от DDoS.

### Assign under attack status (Cloudflare)

`right click домена → Assign under attack status`. В UI экшен называется именно так (для пачки доменов — `Assign under attack`); подтверждение в модалке — `Are you sure you want to assign the under attack status?`. Действие переключает Security Level зоны Cloudflare в `under_attack` или обратно в `medium`. В ERP пункт показывается при наличии DNS-провайдера; поддержан он интеграцией Cloudflare. В меню MTK этого пункта нет.

- Можно single-action (на один домен).
- Можно массово (выбрать пачку доменов, потом `Assign under attack`).
- По механике это **toggle** — включает/выключает under-attack-режим на домене (повторный вызов снимает статус).

### AS-Net Block-листы (AIO)

Списки IP-диапазонов для блокировки **на уровне AIO** (не Cloudflare). Используется, когда определили IP-источник DDoS и хочется его жёстко отсечь, для дополнительного отсечения трафика в фильтре AIO; это не обещание остановки сетевых запросов до агента.

- Поддерживают **CIDR** (`x.x.x.x/24`).
- Поддерживают **диапазон через тире**.
- Блок-листы AIO **не дублируются в Cloudflare** — это отсечение именно на стороне AIO.

### Что AIO не делает автоматически

- Авто-включения Under Attack по триггеру роста RPS — **нет**. Решение и нажатие — руками владельца домена.
- Управления WAF и country block из интерфейса AIO — **нет**. WAF настраивается на своей стороне Cloudflare.

## Domain-Change Step (упоминание)

Дополнительный шаг во флоу, который разделяет два домена: **трекинговый** (тот, что зашит в рекламную кампанию) и **публичный** (тот, под которым лэнд реально открывается).

Зачем для доменов:

- Устойчивость публичного домена — публичный домен можно поменять через `Replace domain` без перезапуска рекламной кампании (трекинговый в объявлении остаётся прежним).
- Разнесение ролей — трекинговый и публичный домены меняются независимо друг от друга.

Детально про устройство и настройку — см. [models/flow-model.md](../models/flow-model.md).

## Частые грабли при настройке доменов

- **Один сервер в `Repoint Group`.** Самая частая. Репойнту некуда переезжать, защита не работает. Минимум — 2 сервера на группу, лучше — у разных провайдеров.
- **Нет привязки к Telegram у Monitoring User-а.** Алерты AIO-tech-bot идут только в TG — без привязки их доставлять некуда (2FA через Google Authenticator привязку не даёт). Чек: подключён ли юзер к боту.
- **Перепутаны `Domain Provider` и `DNS Provider` при настройке.** `Domain Provider` — где домен куплен (Namecheap, NameSilo). `DNS Provider` — где живут DNS-рекорды (Cloudflare). Эти роли разные, апишки разные, ключи разные.

- **Global API Key без `Cloudflare Email`.** Поддержаны оба типа ключа, но Global API Key (`cfk_…` или hex) уходит только парой email + ключ: с пустым полем придёт `Global API Key requires an account email; fill the email field or use an API Token`. API Token email не требует.
- **Manual-добавление без перевода NS.** Добавили домен через `Add manually`, выбрали Cloudflare, а на регистраторе NS остались старые. AIO изменит зону у выбранного DNS-провайдера, но эти записи не обслуживают домен, пока NS у регистратора указывают на другого провайдера.
- **Direct без Cloudflare под DDoS.** Фича штатная, но без CF нет первой ступени защиты — при атаке рискует лечь весь сервер. Под жёсткую нагрузку лучше оставлять CF.

- **`Buy` не проходит: пустой баланс или сломанный провайдер.** Покупка идёт с реального счёта у регистратора через апишку — нет баланса или неверный ключ/прокси, и регистрация фейлится. Чек: `Check balance` + `Test` на `Domain Provider`. Разбор причин — секция «Домен не покупается / не регистрируется».

- **Свежий домен «не работает» сразу после покупки.** Обычно это `DNS-пропагация` (NS ещё расходятся), а при `Buy domains in bulk` — домены пачки ещё регистрируются. SSL выпускается отдельным действием. Проверьте статус покупки и DNS; ожидание само по себе не исключает ошибку.

## Как проверить, что получилось

После добавления домена (любым путём) проверь:

1. В списке `Domains` у домена нет иконки статуса (`Running`) — не синий вращающийся значок (`Processing`) и не красный крестик (`Danger`).
2. `right click → Domain logs` — проверьте доступные записи последней операции и `status_text` домена; не все события попадают в этот журнал.
3. Если домен через `Buy` — на стороне `Domain Provider` и `Cloudflare` появились соответствующие записи (опционально).
4. Откройте на домене ссылку кампании из `Link Generator` и проверьте загрузку лэнда. Для захода на голый домен отдельно нужен `Default Query` или `Direct traffic distribution`; сама покупка домена не создаёт страницу.
5. Если есть `Monitoring User` — убедись, что AIO-tech-bot пишет ему в TG `Place monitoring` / `Delete monitoring` включают и выключают проверку доступности, но сами не отправляют тестовый алерт.

## Нюансы и edge-кейсы доменов

### SSL и Repoint

- При `Repoint` сертификат остаётся в общей записи домена AIO. Агент на новом сервере запрашивает его по имени домена; отдельного действия переноса не требуется.

### Proxied / unproxied при добавлении

- Режим `Proxied` (`Yes` / `No`) задаётся в настройках Cloudflare DNS Provider и используется при создании DNS-записей домена.

### Sitemap.xml и индексация

- AIO не обновляет `sitemap.xml` автоматически. Для дат в HTML лэнда есть серверные плейсхолдеры — [reference/placeholders.md](../reference/placeholders.md); они подставляются до выдачи страницы. Индексация — через `robots.txt` (тоггл `Allow indexing by search engines` в `Edit domain`).

### DPI-блокировки и чекеры

- В странах с DPI-блокировками внешние чекеры доменов ненадёжны — достоверная проверка статуса возможна только **из самой страны** (свой бот-чекер из нужного гео).

### Смена публичного домена без перезапуска рекламы

- В схеме с разделением доменов публичный домен меняют через `Replace domain` **без перезапуска** рекламной кампании — трекинговый домен в объявлении остаётся прежним.

### Замена домена шага Domain-Change через API

- Замена UUID домена в Campaign settings для `Domain-Change` через Actions API (`POST /api/v1/actions/process`, `Campaign\ReplaceAtChangeDomainHandler`). Флоу не пересобирается, новый трафик идёт по новому домену через несколько минут (*Что AIO проставляет и делает сам — автоматические обновления и их лаг*).

### Уровни устойчивости домена — три инструмента

1. `Domain-Change Step` — разделение трекингового и публичного домена.
2. `Lock campaign to this domain` — кампания открывается только под своим доменом.
3. `AIO Filter Service` — фильтрация входящего трафика.

### Lock campaign to this domain — только один домен

- `Lock campaign to this domain` — **только один** домен, не несколько (выбора нескольких в UI нет).

### RU-домены — трафик с русских IP не открывает лэнд (`ECH` в Cloudflare)

- Если на домен, добавленный в AIO (смотрит на AIO-агент, под ним открываются лэнды), заходят с **русских IP** — из-за текущих блокировок возможны проблемы с открытием лэнда. Помогает включённый параметр `ECH` (Encrypted Client Hello) в Cloudflare: если его **отключить**, лэнды на таком домене начинают «падать».
- Отдельного поля `ECH` в интерфейсе `app.aio.tech` нет; его меняют в панели Cloudflare. При настройке зоны AIO отправляет `ECH = off`, поэтому после такой операции проверяйте значение ECH у Cloudflare.

### IPv6 — точка выхода провайдера

- IPv6 определяется провайдером связи (точкой выхода), не AIO. Доля IPv6 зависит от оператора связи.

### Локальные хостеры блокируют CDN

- Локальные хостеры могут блокировать запросы к CDN или к Cloudflare IP — лэнд не грузится **из-за хостера**, не AIO.

### Default Query — поля source, не кампании

- В `Default Query` параметр `suuid` выбирает source, а `cuuid` — кампанию. Это JSON-настройка параметров визита; её формат — в разделе «Default Query Code — JSON формат».

## Пошаговые инструкции по действиям с доменом

### Domain-Change шаг во флоу

**Путь:** открыть Flow, добавить шаг `Domain change` из палитры, выбрать домен в настройках шага и задать имя (например, `Offer Domain-Change`, `Thankyou Domain-Change`).

После — визит на этом шаге переезжает с трекингового домена на публичный (см. [context/architecture.md](../context/architecture.md) → `Domain-Change Step`).

Также см. [models/flow-model.md](../models/flow-model.md) → Domain Change State.

### Default Query Code — JSON формат

Когда: голый домен (без UTM) должен попадать в конкретную кампанию через серверный Default Query.

Как ещё называют: заход на домен «без хвоста» (без query-хвоста); сам query-хвост в обиходе зовут «хвост».

**Путь:** в ERP `Tech → Domains`, в MTK отдельная вкладка `Domains`; затем `<D> → Edit domain → Default Query` (JSON).

**Формат — массив объектов** `mode` / `path` / `query`:

```json
[
  {
    "mode": "path",
    "path": "/",
    "query": {
      "cuuid": "<UUID кампании>",
      "suuid": "<UUID source>",
      "launcher": "<UUID юзера>"
    }
  }
]
```

- `mode` — поведение query; пока единственное значение `path`.
- `path` — путь, для которого применяются параметры `query`; для корня укажи `/`. Несколько объектов с разными `path` разводят один домен по разным кампаниям: `/fr` → Campaign A, `/de` → Campaign B.
- `query` — параметры визита, которые AIO подставляет на сервере, если соответствующее значение пустое; адрес браузера переписывать не требуется. `cuuid` — UUID кампании, `suuid` — UUID source (в ERP `Tracker → Campaigns` / `Tracker → Sources`, в MTK отдельные вкладки `Campaigns` / `Sources`), `launcher` — UUID юзера (`Settings → Users`).

Альтернатива — `Direct Traffic Distribution` (мощнее; сравнение двух путей маршрутизации голого домена — [models/distributions-model.md](../models/distributions-model.md)). Для понятной маршрутизации выбирай один основной способ. Если настроены оба, сначала применяются параметры Distribution, затем Default Query заполняет оставшиеся пустые значения.

### Tags на домене

**Путь:** `Edit domain → Tags → +тег` (например, `Domain-Change`, `EN`, `Finance`).

Теги помогают отфильтровать домены в списке, затем выделить их для массового действия.

### Replace domain — замена в выбранных кампаниях

Когда: публичный домен нужно сменить во всех связанных кампаниях — например, он попал в «красный экран» браузера.

`Replace domain` — это action **над кампаниями** (не над самим доменом): в модалке два поля — `From domain` и `To domain`. В выбранных кампаниях заменяются совпадающие домены в сохранённых Campaign settings для domain-change-шагов. Значение, унаследованное из Flow без настройки в кампании, этот action не меняет.

Чтобы заменить домен во всех нужных кампаниях, выбери их для action-а и проверь результат в Campaign settings. См. также секцию «Replace domain — массовая замена» выше.

### Balance domains на сервере

Когда: на одном сервере слишком много доменов, хочешь распределить нагрузку на пул серверов.

**Путь:** `Servers → сервер → ПКМ → Balance domains` (это server-action `Server\ReBalanceDomains`, не domain-action).

AIO раскидывает домены этого сервера по `Running`-серверам той же `Repoint Group`: каждому домену случайно выбирается сервер из группы, домен получает статус `Repoint requested - Manual ReBalance`, затем обычный репойнт (`Repoint done` → проверка домена). В выборку попадает и сам исходный сервер, поэтому часть доменов может остаться на месте; домены без DNS-провайдера экшен пропускает молча. Переезд отдельного домена при ошибке DNS-провайдера повторяется до 6 раз; если попытки кончились (`All 6 repoint attempts failed: …`), такой домен репойнтят руками.

Также см. [context/architecture.md](../context/architecture.md) → Repoint Group.

### Issue SSL Certificate

Когда: для домена нужен SSL-сертификат (Let's Encrypt) — например, для Direct без Cloudflare или для домена в режиме `DNS only` (серое облако Cloudflare — запросы идут на сервер напрямую, не через прокси).

**Путь:** `<Domain> → Issue SSL certificate` (в UI action называется `Issue SSL certificate`).

AIO запустит автоматический выпуск сертификата через Let's Encrypt.

Выпуск повторяется сам: до **3 попыток с паузой 3 минуты**. Пока попытки не исчерпаны, домен держится в `Processing`; в `Danger` уходит только после третьей.

**Альтернатива (ручной сертификат):** `<Domain> → Edit SSL certificate` → вставить PEM-сертификат в `ssl_cert` и приватный ключ в `ssl_key`.

При ручной загрузке возможны две ошибки: `invalid certificate: <детали>` — сертификат не читается или не проходит проверку, например истёк его срок; `not for this domain: <домены сертификата>` — сертификат валиден, но выписан **на другой домен** (имя домена не совпадает с CN/SAN сертификата; хвост строки перечисляет домены, на которые сертификат реально выписан).

### На какое имя выпускается сертификат — родительский домен субдомен не покрывает

При `Issue SSL certificate` сертификат выпускается **ровно на одно имя** — то, которое записано в самой строке домена в списке `Domains`. У субдомена это только сам субдомен (`sub.example.com`); родительский домен в сертификат не входит. Подтверждение владения (ACME-challenge) идёт по этому же имени.

Сертификат **не wildcard**: выпущенный на родительском домене субдомен не покрывает. Если субдомену нужен сертификат от AIO (сценарий без внешнего прокси перед доменом — «Direct без Cloudflare»), запускай `Issue SSL certificate` **на строке самого субдомена**, а не на родителе.

Что показывает `status_text`, если выпуск упал (причина приходит хвостом строки после `:`).

### Cloudflare Under Attack Mode — массово

**Путь в ERP:** ПКМ на домене → `Assign under attack status` (single); для пачки — mass-select → `Assign under attack`.

Переключает уровень безопасности Cloudflare между `under_attack` и `medium`. Первая ступень защиты от DDoS.

Captcha рубит конверсию у обычных юзеров — использовать только при реальной атаке.

Также см. секцию «Assign under attack status» выше.

### Monitoring User через групповой чат TG (полная процедура)

Когда: алерты должны падать в общий чат команды, не отдельному юзеру.

**Шаги:**

1. Создать TG-группу.
2. Добавить **AIO-tech-bot** в группу.
3. Получить **ID группы** (через `/getgroupid` команду боту).
4. Написать в чат команде AIO: групповой chat ID привязывают к отдельному `Monitoring User` с её стороны.
5. В настройках домена / сервера выбрать этого юзера как `Monitoring User`.

## Прямой трафик в MTK: `Default Query` на домене (не дистрибуция)

В MTK прямой заход без UTM настраивается через `Default Query` на каждом домене — в MTK это ведётся вручную на каждом домене. Централизованный `Direct Traffic Distribution` в MTK **не используется**: это операционная настройка, которую надо постоянно дорабатывать (добавлять домены и кампании), а такую централизацию MTK не ведёт. Поле `Direct traffic distribution` в модалке домена есть, но в MTK-практике не задействуется.

`Default Query` задаётся на домене (`Domains → <домен> → Edit domain → Default Query`); формат JSON стандартный — секция `Default Query Code — JSON формат` в этом документе. Раздел `Domains` в MTK — отдельная плоская вкладка топ-навигации (`/app/mtk/tech/domains`), а не внутри группы `Tech`.

В MTK-виде домены доступны как отдельная вкладка топ-навигации, а серверы и провайдеры лежат в `Settings`; набор действий отличается от ERP: например, `Assign under attack status` в меню MTK отсутствует. Разбор билда целиком — *Как устроен MTK-вид AIO: навигация, пресеты из шаблона и методы под типовые задачи*.

## Раздел Tech — карта подсекций и провайдеры

### Где находится в ERP

Серверы, домены, прокси, провайдеры и чекеры живут в разделе **`Tech`** (`/app/tech`), **НЕ в `Settings`**.

В навигации `Tech` предусмотрено 8 пунктов: **Servers · Domains · Proxies · DNS providers · Domain providers · Domain checkers · Server providers · Deployments**.

В MTK эти настройки расположены иначе: серверы, прокси и провайдеры — в `Settings`; домены — отдельная плоская вкладка `Domains` в топ-навигации (`/app/mtk/tech/domains`). См. *Как устроен MTK-вид AIO: навигация, пресеты из шаблона и методы под типовые задачи*.

### Provider / Checker — `Integration type` (примеры)

Каждый провайдер/чекер создаётся как `Name` + `Description` (+ `Tags`) + **`Integration type`** (дропдаун). Список поддержанных интеграций **постоянно обновляется** — не держим его здесь как эталон; всегда актуальный полный перечень виден **в самом дропдауне `Integration type` в UI**. Ниже — примеры того, что поддержано, для ориентира:

| Подсекция | `Integration type` (примеры) |
|---|---|
| **Server providers** | напр. Digitalocean · Hetzner · Vultr · Gcore |
| **Domain providers** (регистраторы) | напр. Namecheap · Namesilo · GoDaddy · Dynadot · Porkbun |
| **DNS providers** | напр. Cloudflare · GCore · Bunny (поле `Bunny API Access Key`) |
| **Domain checkers** | Google Threat · Virus Total Public API |

> Поле прокси в модалке есть у нескольких типов провайдеров:
> - **DNS providers** и **Domain checkers** — `Proxy` (**опциональный**). DNS-интеграции и `Virus Total Public API` используют его для API-запросов; полезно для разведения VirusTotal по IP (см. секцию VirusTotal выше). `Google Threat` это поле при проверке доменов не использует.
> - **Часть Domain providers** (напр. `Namecheap`) — `Proxy String` (**обязательный**): регистратор принимает API только с вайтлист-IP, поэтому запросы AIO идут через прокси, чей IP добавлен в вайтлист регистратора. Детали — «Domain Provider `Proxy String` — как подключить Namecheap с вайтлистом IP» выше.

### Откуда брать API-ключи провайдеров

- **NameSilo** (`Domain Provider`): ключ генерируется в `API Manager`. При создании ключа отметить **только** чекбокс Agreement; Read-only access и прочие опции оставить **снятыми** — иначе AIO не сможет управлять доменом.
- **Cloudflare** (`DNS Provider`): для доступа к API нужен **подтверждённый email** на аккаунте. Global API Key берётся в `My Profile → API Tokens → Global API Key` (в том числе новый формат `cfk_`); он ходит парой email + key, поэтому поле `Cloudflare Email` при нём заполняется обязательно. API Token (`cfut_…` или обычный токен) поддержан наравне — он уходит Bearer-заголовком, `Cloudflare Email` ему не нужен, а самому токену нужны права `Zone → Read`, `Zone → DNS → Edit` и `Zone → Zone Settings → Edit` (разбор ошибок — «Cloudflare не подключается» выше). Поля модалки `Create DNS Provider`: `Cloudflare API Key`, `Cloudflare Email`, `Cloudflare Account ID ( Optional )` и `Proxied` — что вписывать в Account ID, см. секцию «Что вписывать в поле `Cloudflare Account ID ( Optional )`».

### Проверка провайдера (Test)

ПКМ на созданном провайдере → `Test` (у DNS-провайдера — `Test DNS provider`) проверяет, что ключ рабочий. Ответ приходит в окне с заголовком `Please note!`; частые ответы (`Failed` у Spaceship, ошибки прокси и вайтлиста у Namecheap) разобраны в разделе «Тест провайдера показывает `Please note! …` — как читать ответ» этого документа. Что отвечает тест по типам провайдеров:

- **Server Provider** (DigitalOcean): успех — `Auth as <email>, with N droplets limit`. Плохой ответ (`Unidentified`) = нет связи с DO / неверные креды. Если аккаунт заблокирован, ответ прямо это говорит: `account is inactive - Your team has been locked due to lack of payment or improper use of the platform. Please open a ticket...`.
- **DNS Provider** (Cloudflare): успех — `Cloudflare OK — <тип ключа> (<аккаунт>), zone <зона>, all required permissions present` (на аккаунте без зон вместо зоны будет `no zones yet`). Тест проверяет чтение доступных ресурсов и возвращает `Cloudflare: missing permissions — ...`, если прочитать их не удалось. Запись он не проверяет; без доступных зон проверки DNS и настроек зоны пропускаются. Успешный тест не гарантирует создание домена.
- **Domain Provider**: помимо `Test` есть `Check balance` — посмотреть баланс на аккаунте регистратора.

### Почему `Check balance` показывает `Balance: 0` у GoDaddy и Spaceship

`Balance: 0` не всегда означает пустой счёт. У **GoDaddy** и **Spaceship** AIO баланс не запрашивает: `Check balance` и колонка баланса показывают 0 независимо от реальных денег. Список провайдеров: в ERP `Tech → Domain providers`, в MTK `Settings → Domain providers`.

Смотреть баланс таких аккаунтов надо в личном кабинете самого регистратора. У `Namecheap`, `Namesilo`, `Dynadot`, `Porkbun`, `Timeweb` и `NiceNic` интеграция запрашивает баланс по API. При успешном ответе показывается полученная сумма; при ошибке запроса эти интеграции тоже могут вернуть 0.

### Proxies — прокси-строки

В ERP: `Tech → Proxies`; в MTK: `Settings → Proxies`.

`+ Proxy` → **`Name`** + **`Proxy string`** (формат `http://login:password@host:port`). Прокси переиспользуются в DNS-провайдерах, чекерах и в сценариях с внешними лэндами.

`Proxies` хранит конкретную прокси-строку (`Name` + `Proxy string`). Постоянство исходящего IP зависит от выбранного прокси.

### Deployments (`Tech → Deployments`)

`+ Deployment` → **`Name`** (имя скрипта) + **`Script`** (код-редактор; shell-скрипт сетапа сервера). Выбирается при добавлении сервера (поле `Deployment` в `Buy a server`, `Deployment script` в `Add manually`).

### Add server — подключение сервера

В ERP: `Tech → Servers → + Server`; в MTK: `Settings → Servers → + Server`.

Два пути: **`Buy a server`** (через Server Provider API; скрипт установки выполняет провайдер при первом запуске машины) и **`Add manually`** (публичный IP + атрибуты; скрипт из `Script content` выполняется на машине самостоятельно). В обоих случаях AIO ждёт ответа установленного агента до ~30 минут, потом `Danger` с `All install checks failed`. Полный список атрибутов — [models/server.md](../models/server.md); если сервер не устанавливается.

### Add domain — покупка или ручное добавление

В ERP: `Tech → Domains → + Domain`; в MTK: `Domains → + Domain`.

Четыре пути: **`Buy domain`** / **`Buy domains in bulk`** (купить через `Domain Provider`) · **`Add manually`** / **`Add manually in bulk`** (свои домены). Модалка `Add manually`: **`Domain`** + **`Servers`** (куда указывает) + **`DNS provider`** + **`Monitoring user`** + тоггл **`Allow indexing by search engines`** (off по умолчанию). В тулбаре списка доменов — фильтры `Server` / `Provider` / `Status`, быстрый фильтр `Alerting Now` (см. «Как отобрать домены, по которым мониторинг алертит прямо сейчас») и фильтры архива: `Archived` (подсказка `Show archived items` — показать архивные вместе с рабочими) и `Only archived`. По владельцу можно сортировать через колонку `Owner`; сортировки по серверу нет.

> **`Servers` обязателен.** Если поле `Servers` пустое, создание падает с ошибкой `no servers provided` — домену нужна точка приземления. Укажи хотя бы один добавленный и доступный сервер.

### Action Menu — мониторинг и логи домена

- **`Place monitoring` / `Delete monitoring`** — отдельный экшен в ПКМ-меню, который **назначает или снимает мониторинг** с домена (подтверждение в окне `Place monitoring` / `Delete monitoring`). Действие включает или выключает мониторинг доступности домена; немедленного тестового алерта оно не отправляет.
- **`Domain logs`** открывает окно `Domain logs` — показывает сохранённые сообщения о домене. Сообщения уровня `Debug` в этом окне не выводятся.
