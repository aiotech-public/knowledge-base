# API / External Integrations (How-to)

Всё, что есть в UI AIO, доступно и через API — интерфейс сам общается с бэкендом через этот же API, поэтому теми же запросами можно и читать данные, и выполнять действия: загрузить лендинг, поправить кампанию, залить косты. Своя документация прямо в продукте есть у **Data API** (справочники сущностей — меню профиля → `Data API`) и у **MCP-сервера** для внешних AI-агентов (кнопка `MCP` в окне `AIO Chat`, разбор — [how-to/mcp-server.md](mcp-server.md)). Для всего остального публичной документации нет, и основной путь — снять запрос в UI через F12 и переиспользовать. Концепт-уровень (Compact API, broad API, лимиты, Heavy query limit) — в [reference/glossary.md](../reference/glossary.md) и [context/architecture.md](../context/architecture.md).

## TL;DR

### Какие API использовать для данных и действий?

- **API = всё, что есть в UI.** Документации мало, путь — F12 → Network → скопировать запрос → подменить параметры.
- **Data API** (`/api/v1/data/*`) — плоские справочники сущностей (кампании, домены, лендинги, юзеры…) со спекой прямо в интерфейсе (профиль → `Data API`). Не аналитика — метрик там нет.
- **MCP-сервер** (`POST /api/v1/mcp`) — подключить внешнего AI-агента (Claude Code и другие MCP-клиенты) к данным трекера на чтение; ссылка и инструкция собираются кнопкой `MCP` в окне `AIO Chat` ([how-to/mcp-server.md](mcp-server.md)).
- **Tables Data / Pivot Report** — метрики и отчёты: `Tables Data` — единый endpoint для большинства таблиц (Visits / Campaigns / Meta / Adsets), передаются имя `table` (`Namespace\Entity`) и параметры выбранной таблицы. По токену статистика отдаётся за период не длиннее 31 дня.
- **Actions API** (`/actions/process`) — запись: загрузить лендинг, поправить кампанию и её вайт, сменить режим фильтра, купить домен, залить косты.

### Какие лимиты и доступы учитывать в API?

- **Стандартные лимиты обычных запросов по токену** — 60 в минуту, 3 одновременно и бюджет 20 секунд обработки завершённых запросов за скользящее окно 60 секунд; значения задаются для юзера, для некоторых эндпоинтов есть исключения ([reference/limits.md](../reference/limits.md)).
- **`X-Tenant-Id`** — Data API, Tables Data, Pivot Report и Actions API без него используют тенант, выбранный юзером в интерфейсе. В MCP тенант передаётся обязательно.
- **External Report → CSV (ERP)** — два типа: `Visits CSV` и `Google Conversions CSV` (загрузка офлайн-конверсий в Google Ads).
- **Токены AIO API — бесконечные**, доступы = доступам юзера.

## Выгрузить данные AIO в таблицу / Google Sheets

Отдельной кнопки «экспорт в Google Sheets» нет — данные тянут из AIO **через API или CSV-ссылку** и импортируют в таблицу (Google Sheets / Excel):

- **Метрики и отчёты** (визиты, кампании, Meta-косты, конверсии) — через `Tables Data` (`POST /api/v1/tables/data`) или `Pivot Report API` (оба ниже). В Google Sheets их подтягивают своим скриптом (Apps Script → UrlFetchApp) на этот endpoint со своим токеном.
- **Готовый CSV-отчёт (ERP)** — `External Report → Visits CSV`: синхронная ссылка `external-reports/data`, её можно скормить прямо в Google Sheets через `=IMPORTDATA("<ссылка>")`. (`Google Conversions CSV` — про другое: загрузка офлайн-конверсий в Google Ads, а не выгрузка в таблицу.)

Если задача — тянуть **FB-косты/статистику в свою таблицу**, тяни их **из AIO** (через API), а не из FB напрямую: AIO уже собирает Meta-данные подключённой соцки ([how-to/meta-ads.md](meta-ads.md)), так не нужен отдельный FB-токен и мульти-аккаунтная возня.

Полная механика обоих путей — ниже (`Tables Data` / `Pivot Report API` и `External Report → CSV`).

## Токен API — где взять и как передавать

### Где взять токен

Токен AIO API выдаёт команда AIO: сгенерировать его себе в интерфейсе нельзя — за токеном и за включением API-доступа напишите в чат команде AIO. Токены **бесконечные** (нет TTL). Доступы токена = доступы юзера, под которым он создан. Для API-автоматизации обычно заводят **отдельного юзера** с минимально нужным набором прав (см. [models/permissions-model.md](../models/permissions-model.md) → «Что НЕ делает Permissions Model»). Токен подставляется query-параметром `?token=xxx` — не заголовком `Authorization`.

### Ссылку с токеном пересылать нельзя — это пароль

Токен в URL — это полный доступ к API от вашего имени, поэтому передать ссылку с ним всё равно что передать пароль. Ссылка уезжает в историю терминала, конфиги скриптов и репозитории, так что не пересылайте её и не коммитьте. Особенно это касается ссылки MCP-сервера, где токен зашит в адрес по конструкции ([how-to/mcp-server.md](mcp-server.md)). Перевыпустить утёкший токен самостоятельно нельзя — новый выдаёт команда AIO.

### «Дайте read-only токен» — отдельного read-only флага нет

Отдельного «read-only токена» как флага в AIO нет. Токен всегда **наследует права своего юзера** ([models/permissions-model.md](../models/permissions-model.md) → «Что НЕ делает Permissions Model»), поэтому read-only API-доступ делается через права: завести отдельного юзера с ролью `Employee` (у Owner / Admin права позиции не проверяются — у них полный доступ), в его позиции (`Settings → Positions`) разрешить только ключи просмотра нужных разделов (`tracker.campaigns.view`, `content.landings.view` и т. п.) без `.edit`-ключей, и использовать его токен. Например, `Campaign\UpdateCosts` проверяет право `tracker.campaigns.edit.update-costs`: без него такой юзер получит `403` `Action access denied (<ключ> required)`. Настройка прав юзера — [how-to/permissions.md](permissions.md).

### Можно ли вместо API-токена взять куку `token` из браузера

Кука `token` из браузера (DevTools → `Application` → `Cookies`) — это сессия входа в интерфейс, а не ключ API, и для скриптов она не годится. Сессия живёт, пока жив вход в этом браузере: выход из аккаунта гасит её сразу, смена или сброс пароля — тоже (сброс пароля разлогинивает все устройства — [how-to/registration.md](registration.md)), для нового входа нужен пароль и, если включена 2FA, её код. Скрипт на такой куке в какой-то момент начнёт получать `401` `Auth Middleware: Unauthorized`. API-токен от этого не зависит: он бессрочный, смена пароля его не гасит, и он передаётся явно — `?token=<api_token>`. Токен выдаёт команда AIO вместе с включением API-доступа юзеру.

## Какой тенант читает запрос — заголовок `X-Tenant-Id`

### Без `X-Tenant-Id` запрос идёт в тенант, выбранный в интерфейсе

Заголовок `X-Tenant-Id` с uuid тенанта задаёт, в каком тенанте выполняется запрос; без него API берёт тенант, который этот юзер последним выбрал в переключателе тенантов интерфейса.

- **Один тенант** — заголовок можно не слать: другого выбора нет.
- **Несколько тенантов** — без заголовка запрос уйдёт в тот, куда юзер последний раз переключился в интерфейсе, с любого браузера и устройства. Переключились — скрипт молча начинает читать другой тенант: пустые ответы, «чужие» цифры. Для автоматизации заголовок стоит слать всегда.
- **Чужой или несуществующий uuid** — `401` `Auth Middleware: Unauthorized`: значение сверяется со списком тенантов юзера, а не подставляется как есть.

Так работают Data API, `Tables Data`, `Pivot Report` и Actions API. MCP-сервер — исключение: у него тенант обязателен, заголовком или `?tenant=` ([how-to/mcp-server.md](mcp-server.md)).

### Как узнать uuid тенанта для токена — `GET /api/v1/auth/user` или диалог `Data API`

Uuid тенантов, доступных токену, отдаёт `GET /api/v1/auth/user?token=<api_token>`: в списке `available_tenants` у каждого тенанта есть `tenant.uuid`, `tenant.name`, `tenant.build` и `is_selected`, а `request.tenant` показывает uuid тенанта, в который попал сам этот запрос. Если вызвать его без `X-Tenant-Id`, `request.tenant` и тенант с `is_selected: true` — ровно тот, куда уходят все запросы без заголовка.

В интерфейсе uuid текущего тенанта подставлен прямо в примеры диалога `Data API` (меню профиля → `Data API`, вкладка `Overview`, строка `X-Tenant-Id` в блоке про заголовки) — его можно скопировать оттуда.

## Data API — документированные справочники сущностей (`/api/v1/data/*`)

Справочники сущностей — часть API с **собственной документацией прямо в интерфейсе**: меню профиля → **`Data API`** (`Data API docs`). Отдельно ходить за спекой и снимать запросы через F12 для этих данных не нужно — в диалоге пять вкладок: `Overview`, `Parameters`, `Endpoints`, `Access`, `Errors`.

Что отдаёт: **плоские списки сущностей тенанта** — кампании, домены, источники, дестинейшены, лендинги, юзеры, метрики, рекламодатели, типы лендингов. Это **не аналитика**: метрик, футеров и группировок здесь нет, только атрибуты объектов. За цифрами — `Tables Data` / `Pivot Report` ниже.

База — `https://<host>/api/v1/data`. Тенант задаёт заголовок `X-Tenant-Id`: без него берётся тенант, выбранный у юзера в интерфейсе, чужой uuid даёт **401** `Auth Middleware: Unauthorized` (разбор — секция «Какой тенант читает запрос — заголовок `X-Tenant-Id`»). Токен — тем же query-параметром `?token=`, что и у остальных эндпоинтов.

### Data API — параметры запроса и постраничность

Общие параметры всех списочных эндпоинтов:

| Параметр | Тип | Дефолт | Что делает |
|---|---|---|---|
| `page` | int | `1` | Номер страницы |
| `limit` | int | `100` | Размер страницы, зажимается в **1…1000** |
| `uuids[]` | string[] | — | Вернуть только эти записи (фильтр по `uuid`) |
| `human_ids[]` | string[] | — | Вернуть только эти записи (фильтр по `human_id`); работает у `/campaigns`, `/domains`, `/destinations`, `/landings` |

**В распознанном фильтре — не больше 100 значений.** Для `uuids` превышение даёт `500` с текстом `Table filter UUID values amount exceeded: 101 > 100`. В `human_ids` сначала отбрасываются нечисловые значения и дубли; лимит применяется к оставшимся уникальным ID. Бить запросы на пачки до 100 ID. Сортировка фиксированная, `created_at DESC`, снаружи не меняется.

У `/sources` фильтр `uuids[]` не поддерживается: запрос с ним отвечает `500` с текстом вида `Argument #1 ($query) must be of type …`. Нужные источники отбирают по `uuid` на своей стороне из постраничного списка `/sources`.

Ответ одинаковый у всех эндпоинтов, кроме `/shared`: `rows` + `next` + `previous`. **`next` — эвристика**, а не признак наличия данных: `true`, когда вернулось ровно `limit` строк. Если размер последней страницы случайно совпал с `limit`, придёт `next: true`, а следующая страница окажется пустой — это нормальный конец списка, а не сбой. Общего количества строк API не отдаёт, поэтому листать надо по `next`, а не по счётчику. `previous` — просто `page > 1`.

### `uuids=` без `[]` — ошибка `sizeof(): Argument #1 ($value) must be of type Countable|array, string given`

Списки в query Data API передаются с квадратными скобками — `uuids[]=<uuid>`, отдельной парой на каждое значение: `?uuids[]=<uuid1>&uuids[]=<uuid2>`. Запрос `uuids=<uuid>` без скобок сервер получает строкой, а не списком, и отвечает `500` с телом `{"error":"sizeof(): Argument #1 ($value) must be of type Countable|array, string given"}` — скобки нужны и для одного uuid. `human_ids` одиночное значение без скобок принимает (`human_ids=1043`), но несколько значений и там передаются только как `human_ids[]=`.

В curl скобки надёжнее всего передавать через `-G --data-urlencode 'uuids[]=<uuid>'` — так их не съест оболочка; готовые примеры — во вкладке `Parameters` диалога `Data API`. Закодированная форма `uuids%5B%5D=<uuid>` — то же самое.

### Data API — что лежит в ответе

`created_at` всегда объект из двух полей — `timestamp` (unix) и `string` (ISO); парсить строку не надо, для сортировки на клиенте берут `timestamp`. Набор полей **не унифицирован** между эндпоинтами: `human_id` есть у кампаний, доменов, дестинейшенов и лендингов, но нет у источников; `owner` есть не везде и может быть `null`.

Отдельные детали по эндпоинтам:

- `/campaigns` — `languages` и `countries` приходят массивами (в базе лежат json-строкой, наружу уже распарсены);
- `/sources` — `settings` распарсенный объект, набор ключей зависит от источника;
- `/landings` — `landing_type` может быть `null`, `folders` и `shares` — пустыми массивами;
- `/users` — `is_active` означает общую активность учётной записи юзера; отдельная активность в текущем тенанте здесь не отдаётся. Email тут нет. Поле `telegram` (ник из профиля) приходит только владельцу токена с полным доступом (`Owner` / `Admin`) или с правом `api.users.telegram` (ветка прав `api` → `api.users`); без права этого поля в ответе нет.

**Архивные записи приходят вместе с активными** — параметра «только активные» нет, фильтровать по `is_archived` на своей стороне.

### В каких командах юзер — поле `teams` в `GET /data/users`

Команды юзера отдаёт Data API: у каждой строки `GET /api/v1/data/users` есть `teams` — список `{uuid, name, access_type}` — и `positions` (`{uuid, name}`). Так по API проверяют, в какой команде баер, и переводят uuid владельца кампании из аналитики (`campaign_owner_uuid`) в имя.

`access_type` в `teams` — огрублённый уровень участника в команде: `Team Member` (уровень 0), `Team Leader` (1), `Team Head` (2 и выше). Точного числового уровня Data API не отдаёт — он виден в `Settings → Teams`, а как уровни дают доступ к объектам — [models/permissions-model.md](../models/permissions-model.md). Список не скоуплен (все юзеры тенанта), email в нём нет; нужен просмотр таблицы юзеров (`settings.users.view`), иначе `500` `Table access denied`.

### Data API — кто что видит (скоупы)

**Owner / Admin видят всё в тенанте — скоуп к ним не применяется; остальным Data API режет список по тому же правилу, что списки в интерфейсе: в ответ идёт всё, до чего у юзера есть хотя бы уровень доступа `Use`.** В ответ попадают:

- свои записи и записи участников с более низким уровнем в его командах;
- записи равных по уровню — если так настроена команда (`Peers`);
- записи с `Access type` `Use` или `View` (в API — `Everyone` / `View`);
- пошаренное лично ему или любой его команде, пока шара не истекла; пошаренное его нижестоящим — если так настроен режим команды `Below`;
- весь раздел, если у его позиции есть `Scopes` или `Editor Scopes` на этот раздел.

Правило одно для всех скоупленных эндпоинтов, включая кампании и лэнды. Лестница уровней и откуда берётся доступ — [models/permissions-model.md](../models/permissions-model.md).

| Эндпоинт | Скоуп |
|---|---|
| `/campaigns`, `/landings`, `/sources`, `/destinations`, `/domains`, `/metrics`, `/advertisers` | по уровню доступа — не ниже `Use` |
| `/landing-types`, `/users`, `/advertiser-types` | без скоупа — весь тенант |

Поверх скоупа работают права на таблицу. Права нет → **500** с телом `{"error": "Table access denied"}` (да, именно 500, а не 403). Отдельный `403` отдаётся только на нехватку read-доступа к колонкам.

### `GET /data/shared` — что видит конкретный юзер

Особый эндпоинт: не список сущностей, а **срез доступов другого юзера** — им построен экран настроек шеринга, чтобы показать, до чего человек дотягивается. Обязательный параметр `user_uuid` — uuid юзера этого же тенанта.

Доступен **только Owner / Admin**. Сервер на время этого одного запроса считает скоупы от имени указанного юзера — по тем же уровням доступа, что и списки Data API (не ниже `Use`), поэтому в срез попадают и записи, которые юзер видит в списках и селектах, но открыть не может. Это не вход под юзером: посмотреть интерфейс глазами сотрудника позволяет отдельная функция `Log in as user` ([how-to/permissions.md](permissions.md)).

Сущности в ответе — плоские списки uuid без имён и атрибутов (`campaign_uuids`, `source_uuids`, `destination_uuids`, `landing_uuids`, `field_uuids`, `metric_uuids`, `domain_uuids`, `server_uuids`), **без постраничности**. Кроме них приходят `user` (`uuid`, `name`, `email`) и `tenant_uuid`. Это полный набор доступных сущностей, список может быть длинным. Если у юзера роль без скоупинга (Owner / Admin), вернутся все uuid тенанта; если у его позиции есть `Scopes` / `Editor Scopes` на раздел — все uuid этого раздела.

Ошибки: не Owner / Admin, не передан `user_uuid`, нет такого юзера в тенанте.

## MCP-сервер — подключить к данным внешнего AI-агента

`POST /api/v1/mcp` — MCP-сервер AIO: внешний AI-агент (`Claude Code`, `Claude Desktop`, любой другой MCP-клиент) подключается по ссылке и сам читает данные трекера — трафик, метрики, прогнозы, логи кампаний. Ссылку с готовой командой и конфигом собирает диалог `MCP Server` (кнопка `MCP` в окне `AIO Chat`). Авторизация та же, что у остальных эндпоинтов: `?token=<api_token>` прямо в ссылке.

Два отличия от Data API, на которых спотыкаются:

- **Тенант обязателен и явен** — заголовок `x-tenant-id` или `?tenant=<uuid>`. Фоллбэка на тенант, выбранный у юзера, здесь нет: без тенанта придёт `400` `Tenant is required: pass x-tenant-id header or ?tenant=<uuid>`.
- **Свой поминутный счётчик** — серии вызовов от агента не съедают 60 запросов в минуту обычного API и наоборот. Настроенные для юзера лимиты параллельности и тяжёлых запросов у MCP общие с остальными запросами по токену, кроме `actions/file`, и потолок периода статистики в 31 день действует так же.

Что именно отдаётся наружу, почему через MCP нельзя ничего изменить и как подключить конкретного агента — [how-to/mcp-server.md](mcp-server.md).

## Параллельные запросы к `pivot-report/data` и `tables/data` — сколько можно

Параллельно слать можно; при стандартном лимите **3 запроса** четвёртый получает `429` с телом `{"message":"Too many concurrent requests ( 3 of 3 ). Try later."}`. Стандартные значения двух других лимитов — **60 запросов в минуту** и бюджет «тяжёлых» запросов: после **20 секунд** обработки завершённых запросов, начатых за последние **60 секунд**, новые запросы отклоняются. Значения настраиваются отдельно для юзера (дальше `429` `Heavy-usage limit reached ( 20s last 60s ). Try later.`).

Счётчики считаются на юзера, а не на эндпоинт: Data API, `Tables Data`, `Pivot Report`, Actions API и MCP-сервер делят настроенные слоты и бюджет тяжёлых запросов, кроме загрузки через `actions/file`; поминутный счётчик у MCP свой. Безопасная схема для выгрузки — очередь на 2–3 параллельных запроса, пауза, чтобы не выйти за 60 в минуту, и повтор на любой из этих отказов через столько секунд, сколько указано в заголовке `Retry-After` ответа `429`; тяжёлые отчёты — длинный период, много группировок — лучше слать по одному. Остаток видно в заголовках ответа `X-Concurrency-Limit-Used` / `X-Heavy-Limit-Used`. Числа, что именно считается и какие значения ставит команда AIO — [reference/limits.md](../reference/limits.md).

## Найти payload для пуллинга через F12

Когда: нужно автоматизировать получение данных (визиты, кампании, отчёты) через API, но публичной документации нет — берём payload из UI.

**Шаги:**

1. Открыть в UI нужную таблицу (например, `Analytics → Visits` / `Tracker → Campaigns`).
2. Открыть **DevTools (`F12`) → Network**.
3. Найти запрос с именем `Tables Data` (это единый endpoint для большинства таблиц).
4. Скопировать **payload** (Request body).
5. Использовать как шаблон в скрипте:
   - Поле `table` — определяет, какую таблицу запрашиваем. Меняй значение для других таблиц (например, `Tracker\Visits` → `Facebook\AdSets` / `Facebook\Ads` для Meta-таблиц).
   - Фильтры, groupers — копируются как часть payload.
   - Ключ `metrics` из скопированного тела **убрать**, если нужны все метрики: интерфейс может сузить расчёт видимыми метриками и их зависимостями (разбор — «`metrics` — считать только перечисленные метрики» ниже).
6. Запрос делать на тот же endpoint от своего токена.

Запросы инспектируются в `DevTools → Network → Data` и переиспользуются добавлением своего токена через query-параметр `?token=xxx`. Это **не публичный API** и может меняться без предупреждения — на стабильность полагаться нельзя.

### Tables Data — как устроен payload и что менять для разных таблиц

Endpoint: `POST /api/v1/tables/data?token=xxx`. Тело — объект `request`, в котором под произвольными ключами лежат запросы таблиц: `{"request": {"campaigns": {"table": "Tracker\\Campaigns", …}}}`; ответ приходит под теми же ключами, поэтому в одном `POST` можно забрать несколько таблиц. Идентификатор таблицы задаётся ключом `table` в формате `Namespace\Entity`. Базовая структура запроса общая; меняется ключ `table`, а набор полей (`sort_key`, флаги `hide_*` и т.п.) подстраивается под конкретную таблицу. Примеры идентификаторов:

| `table` | Что |
|---|---|
| `Tech\Domains` | домены |
| `Tech\Servers` | серверы |
| `Tech\DnsProviders` | DNS-провайдеры |
| `Funnel\Landers` | лендинги |
| `Settings\Users` | юзеры |
| `Settings\Tags` | теги |
| `Tracker\Visits` | визиты |
| `Tracker\Conversions` | конверсии (в MTK — `MTK\Conversions`) |

Поля payload: `page`, `limit`, `search`, `sort_key`, `sort_direction`, `analytics_position`, `filters`, `dates` (`from` / `to`, опц. таймзона третьим элементом массива), `hide_empty_metrics`, `hide_bots`, `unwrap_tree`, `hide_trash`, `event_time_attribution`, `back_fix_attribution`, `metric_filters`, `metric_definition(s)`, и два необязательных ключа — `metrics` и `meta_spend_attribution_engine_level` (разобраны в двух секциях ниже). Без `dates` таблица считает текущие сутки в таймзоне запроса или профиля, а не всю историю тенанта. `limit` — не больше 100 строк на страницу (по умолчанию 25; у части справочников настроек — до 1000), дальше листают `page`.

`analytics_position` — номер позиции в воронке, за которую списки `Funnel\Landers` и `Tracker\Destinations` считают метрики: строка лэнда или Destination получает цифры только по визитам, где эта сущность стояла на позиции `#N`. Интерфейс шлёт `1` по умолчанию и переключает между `1` и `2` кнопкой `#1` / `#2` в тулбаре этих списков; лэнд, живущий на второй позиции, при `1` покажет нули. Разбор позиционной аналитики — [how-to/landings.md](landings.md).

### `metrics` — считать только перечисленные метрики (почему скопированный запрос возвращает не все колонки)

`metrics` — необязательный массив uuid метрик, которые нужно посчитать. Ключа в теле **нет** → считаются все неархивные метрики каталога тенанта. Ключ содержит хотя бы один UUID неархивной метрики каталога → считаются найденные метрики плюс зависимости формул. Пустой массив или массив без подходящих UUID не сужает каталог — операнды формульной метрики AIO доразворачивает сам, перечислять их не нужно. Скрытие пустых строк (`hide_empty_metrics`) и сортировка по умолчанию тоже работают по этому суженному набору: пустота строки проверяется по метрикам этого набора, а сортировка по умолчанию выбирается только среди посчитанных. Uuid метрики — тот же, что в `Settings → Metrics` и в ключах ответа `metric_<uuid>`, без префикса `metric_`.

Интерфейс формирует `metrics` из видимых колонок и зависимостей виртуальных метрик; при неизвестной видимости он может не передать ключ. Поэтому скопированный запрос может сузить расчёт. Нужны все неархивные метрики — удалить ключ `metrics` из тела целиком.

Отдельное значение `_chart` в этом же массиве — не метрика, а сентинел для интерфейса: «считать мини-графики колонок». Для запросов по API-токену мини-графики не считаются в любом случае, так что в скрипте `_chart` можно не передавать.

### `meta_spend_attribution_engine_level` — уровень матчинга Meta Spend в запросе

`meta_spend_attribution_engine_level` — необязательный ключ со значением `ad` | `adset` | `campaign`: на каком Meta-объекте спенд сшивается с трафиком для метрик семейства `Meta Spend`. Ключа нет → уровень `campaign`. Интерфейс кладёт сюда выбор кнопки уровня в тулбаре таблицы (дефолт `campaign`, выбор хранится в браузере), поэтому скопированный из DevTools запрос уносит и его. Meta-группер или Meta-фильтр в том же запросе перебивает ключ своим уровнем. `POST /api/v1/tables/data` — единственный внешний запрос, который принимает уровень; `Pivot Report API` такого поля не имеет и всегда считает на `campaign`. Что такое уровень матчинга, чем `campaign` отличается от `ad` и где ещё он не переключается — [mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md).

### Pivot Report — какой payload слать

Endpoint: `POST /api/v1/pivot-report/data?token=xxx`. Обязательны пять булевых флагов. Также передают `dates`, `conditions`, `definitions`: без дат используются дата создания тенанта, текущее время и таймзона юзера, а для условий и группировок дефолт — пустой массив. Но из пяти флагов в Pivot фактически влияют только два — `event_time_attribution` и `hide_empty_metrics`; остальные три (`back_fix_attribution`, `hide_bots`, `hide_trash`) в Pivot-пути **no-op** (тело их требует, но отчёт их не читает; см. ниже «полярность»). Постраничности у Pivot нет: ответ — всё дерево комбинаций за период сразу.

- `dates` — `[from, to, timezone]`. Формат datetime — `YYYY-MM-DD HH:mm:ss`, начало диапазона включается, конец исключается: `[from, to)` (для полного дня конец — `00:00:00` следующего дня). Третий элемент — **IANA-таймзона** (напр. `Asia/Bangkok`, `Europe/Berlin`); всегда указывай, чтобы избежать неоднозначности. По токену между `from` и `to` — не больше 31 суток (разбор отказа — «Pivot Report отвечает `422` `Wrong query`» ниже).
- `conditions` — массив фильтров; каждый элемент `{ "key": "...", "values": ["<uuid>", ...] }`, где `values` зависят от ключа: UUID для сущностей, коды стран для `location_country_code`, значения поля для `string_fields[<uuid поля>]`. Несколько `conditions` объединяются по **AND**. Нераспознанный ключ в `conditions` не даёт ошибку — фильтр молча не применяется.
- `definitions` — массив `{"key":"..."}` для группировки (напр. `campaign_owner_uuid`, `location_country_code`). **Порядок задаёт вложенность** (`group_0`, `group_1`, …); движок возвращает все комбинации, присутствующие в данных (разреженные комбо могут отсутствовать).
- Часть измерений мультизначные — индекс в скобках выбирает конкретный слот: `landing_uuids[1]` — первый лендинг (позиционные и роль-ключи — в следующей секции).

### Pivot Report — ключи `landing_uuids[N]` / `landing_of_type[<uuid>]` и уровень Meta Spend

Позиционный ключ `landing_uuids[N]` в `definitions` группирует по лэнду на позиции `N` воронки (`landing_uuids[1]` — первый лендинг). Роль-ключ `landing_of_type[<uuid типа лэнда>]` группирует по лэнду, сыгравшему роль этого типа на **любой** позиции воронки — аналог роль-группера `LP: <Тип>` в каталоге групперов ([how-to/analytics.md](analytics.md)); uuid типа лэнда отдаёт `Data API` эндпоинтом `/landing-types` (см. выше).

Поля уровня матчинга Meta Spend в Pivot Report **нет**: метрики семейства `Meta Spend` здесь всегда считаются на уровне `campaign` (Meta-кампания × день). Нужен уровень `adset` / `ad` — только через `Tables Data` ключом `meta_spend_attribution_engine_level` (см. выше); что такое уровень матчинга — [mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md).

### Статистика по креативам с разбивкой по баерам — ключи `campaign_owner_uuid` и `string_fields[<uuid поля>]`

Разбивка «баер × креатив» в Pivot Report собирается двумя ключами в `definitions`: баер — `campaign_owner_uuid` (владелец кампании AIO), креатив — поле визита, в которое приходит идентификатор или имя объявления, ключом `string_fields[<uuid поля>]`. Uuid поля — в `Settings → Fields`, колонка `UUID` (например, у поля, куда источник пишет FB Ad ID или название объявления). Порядок задаёт вложенность: `[{"key":"campaign_owner_uuid"},{"key":"string_fields[<uuid поля>]"}]` — баер, под ним его креативы. Тем же ключом `string_fields[<uuid поля>]` работает и `conditions` — например, отчёт только по нескольким креативам.

В ответе баер — uuid юзера; имя и команды юзера отдаёт `GET /api/v1/data/users` (секция «В каких командах юзер — поле `teams` в `GET /data/users`»).

### Фильтр по баеру в Pivot Report и старые ключи `field_*`

Отчёт по одному или нескольким баерам фильтруют ключом `string_fields[780102b12-322c-4131-bf84-c292a8793f51]` — это uuid системного поля `Campaign Owner`, одинаковый во всех тенантах, и им же фильтрует по владельцу интерфейс; в `values` — uuid юзеров. Ключ `campaign_owner_uuid` в `conditions` не распознаётся и молча пропускается: отчёт вернётся по всем баерам, без ошибки. В `definitions` `campaign_owner_uuid` работает как обычно.

Ключи из старого каталога вида `field_*` — `field_fb_ad_id`, `field_fb_ad_name`, `field_fb_campaign_name`, `field_launcher` и остальные — аналитика сейчас не принимает: в `definitions` запрос с ними отвечает `422` `Wrong query`, в `conditions` они молча не применяются. Вместо них — `string_fields[<uuid поля>]` нужного поля визита.

### Tables Data — атрибуция времени и скрытие пустых строк

Для расчёта метрик `event_time_attribution: true` выбирает время события конверсии, `false` — время визита. `hide_empty_metrics: true` убирает строки, где все счётные метрики нулевые; формулы и Meta-метрики не учитываются в проверке пустоты. В списках сущностей `false` позволяет показать пустые строки; у таблиц группировок пустые строки скрываются принудительно.

### Pivot Report — какие флаги реально влияют

В Pivot Report из пяти обязательных флагов влияют только `event_time_attribution` (время события или визита) и `hide_empty_metrics` (скрытие строк с нулевыми счётными метриками).

### Pivot Report — что в ответе: дерево группировок и UUID метрик

Ответ — дерево значений группировок. В его листьях значения метрик лежат под их UUID, без префикса `metric_` и без обёртки `placeholders`. Название метрики смотри в `Settings → Metrics`; запрашивай значение по UUID, поскольку название можно переименовать.

Тенант, по которому строится отчёт, задаёт заголовок `x-tenant-id`; без него — тенант, который юзер токена последним выбрал в интерфейсе (секция «Какой тенант читает запрос — заголовок `X-Tenant-Id`»).

### Pivot Report отвечает `200` и пустым `[]` — в видимом срезе нет данных

`200` с пустым массивом `[]` значит, что запрос выполнился, но не вернул строк отчёта. Это не отказ: нехватка доступа к тенанту даёт `401`, ошибка в запросе — `422`. Причины по частоте:

1. **Юзер токена не видит кампаний.** Owner / Admin и позиции со `Scopes` на раздел кампаний получают статистику всего тенанта; остальным Pivot считает только кампании и источники, к которым у юзера есть хотя бы уровень доступа `Use` — как в списках интерфейса ([models/permissions-model.md](../models/permissions-model.md)). Если доступных кампаний нет, обычный запрос без дополнительных фильтров по кампании не вернёт их статистику. Отдельного права «на Pivot» нет — достаточно видеть нужные кампании.
2. **Запрос ушёл в другой тенант** — не передан `X-Tenant-Id`, а юзер переключился в интерфейсе. Проверка — `request.tenant` в ответе `GET /api/v1/auth/user?token=…`.
3. **Условия ничего не нашли**: в фильтре по сущности имена или `human_id` вместо UUID, период не тот или таймзона сдвинула окно.
4. **`hide_empty_metrics: true`** убрал строки, где все счётные метрики нулевые.

### Pivot Report отвечает `422` `Wrong query` — период длиннее 31 дня или ошибка в запросе

`422` с телом `{"error":"Wrong query","trace":[]}` Pivot отдаёт на **любую** ошибку внутри запроса — причину текст не называет. Частые причины:

1. **Период длиннее 31 дня.** По API-токену статистика считается за период, где между `from` и `to` не больше 31 суток: полный календарный месяц проходит, 67 дней — нет. Длинный период запрашивают кусками до 31 дня и складывают у себя — счётные метрики суммируются, а отношения (CR, ROI) пересчитывают из сумм. В интерфейсе такого ограничения нет.
2. **Нерабочий ключ в `definitions`** — опечатка или ключ из старого каталога `field_*` (секция «Фильтр по баеру в Pivot Report и старые ключи `field_*`»).
3. **Неразбираемые `dates`** — не тот формат даты или неизвестная таймзона.
4. **Запрос не уложился в ограничение времени выполнения аналитики** — много детальных группировок (`visit_uuid`, `user_agent`) на длинном периоде; помогает укоротить период или убрать лишние ключи.

Сводка потолка периода и как он выглядит на других эндпоинтах — [reference/limits.md](../reference/limits.md).

## Actions API — как выполнять действия через API (не только читать)

Помимо чтения данных, через API доступны **действия (Actions)**: `POST /api/v1/actions/process?token=xxx`. Тело:

- `action` — имя действия (напр. `Domain\Create`, `Domain\CreateManually`, `Campaign\UpdateCosts`).
- `repository` — репозиторий (напр. `Eloquent\DomainRepository`, `MassiveEloquent\CampaignRepository`).
- `uuids` (опц.) — массив UUID для массовых действий.
- `arguments` — параметры конкретного действия.

### Как узнать аргументы экшена — `POST /api/v1/actions/data`

Поля формы экшена и вспомогательные данные отдаёт `POST /api/v1/actions/data?token=…` с тем же телом, что у `actions/process` (`action`, `repository`, `uuids`): в ответе `fields` — имена полей и их текущие значения у объекта из `uuids` (для нового объекта — пустые значения или дефолты), `data` — вспомогательные данные формы, например допустимые варианты селектов.

Самый короткий путь к точному телу — один раз выполнить действие в интерфейсе с открытым DevTools (`F12` → `Network`), найти запрос `process` и скопировать его: имена `action` / `repository` и формат `arguments` будут ровно такими, как ждёт сервер. Экшены проверяют права позиции юзера токена так же, как кнопки интерфейса ([models/permissions-model.md](../models/permissions-model.md)).

### Купить домен в AIO

`action: Domain\Create`, `repository: Eloquent\DomainRepository`. В `arguments`:

- `domain_provider_uuid` — провайдер доменов.
- `domain_url` — URL домена.
- `server_uuid` — сервер, на который указывает A-запись.
- `dns_provider_uuid` — DNS-провайдер.
- `monitoring_user_uuid` — юзер, который получает нотификации.
- `settings` — JSON-строкой, напр. `{"robots":{"allow":false}}`.

Домен, купленный **вне** AIO, добавляется через `action: Domain\CreateManually` (тот же `repository: Eloquent\DomainRepository`). Основные поля похожи, но у `CreateManually` **нет** `domain_provider_uuid`, а `dns_provider_uuid` необязателен. Оба экшена объединяют `server_uuid` и `server_uuids`; `Create` дополнительно убирает повторы.

### Загрузить лендинг через API — `Lander\Upload` из ZIP-архива

Отдельного эндпоинта «залить лендинг» нет, а Data API только читает; лендинг создаётся через Actions API тем же экшеном, что и загрузка ZIP в интерфейсе. Два запроса:

1. **Загрузить архив:** `POST /api/v1/actions/file?token=…`, `multipart/form-data`, поле `file` — в ответе `url` и `uuid` файла.
2. **Создать лендинг:** `POST /api/v1/actions/process` — `action: Lander\Upload`, `repository: Eloquent\LanderRepository`, в `arguments` — `name`, `lander_type_uuid` (uuid типа — `GET /api/v1/data/landing-types`), `lander_template_uuid` (выбранная обёртка-шаблон; её UUID проще всего взять из снятого в F12 запроса загрузки), `zip_url` — `url` из первого шага; по желанию `countries`, `languages`, `tags`.

В ответе `uuid` — uuid нового лендинга. Архив обрабатывается в фоне: статус идёт `Preparing` → `Fine` или `Issues` — в `Content → Landings`, а по API в строке таблицы `Funnel\Landers` (`tables/data`, поле `_identity`: `status` и `status_text`). Разбор `Issues` и лимиты размера, [reference/limits.md](../reference/limits.md). Нужно право позиции `content.landings.edit.upload`.

### Создать лендинг из HTML или заменить архив через API — `Lander\Create` и `uuids`

Лендинг из готового HTML без архива создаёт `action: Lander\Create` (`repository: Eloquent\LanderRepository`): вместо `zip_url` в `arguments` передаётся `html`, плюс те же `name`, `lander_type_uuid`, `lander_template_uuid`; нужно право `content.landings.edit`. С `uuids: [<uuid лендинга>]` оба экшена правят существующий лендинг: `Lander\Upload` заменяет архив (прежние архивы остаются в истории загрузок), `Lander\Create` — HTML и атрибуты. При правке `tags`, `countries` и `languages` перезаписываются тем, что пришло в запросе, — отсутствующие обнуляются, поэтому текущие значения берут из `POST /api/v1/actions/data` и отправляют вместе с изменением. Что происходит с HTML при загрузке и как устроен лендинг — [how-to/landings.md](landings.md).

### Поставить вайт или другой лендинг в кампанию через API — `Campaign\Create` с uuid кампании

Лендинги шагов, вайт, Traffic Filter на шаге `Filter` и остальные настройки шагов кампании меняются через API одним способом — сохранением кампании: `action: Campaign\Create`, `repository: Eloquent\CampaignRepository`, `uuids: [<uuid кампании>]`. Отдельного экшена «привязать вайт» нет.

Настройки шагов лежат в аргументе `settings` — JSON-строке, где ключи — uuid шагов флоу, а значения — выбранные варианты (лендинги, вайт, фильтр и его режим). Правильный `settings` проще всего получить, поменяв вайт в `Edit Campaign` с открытым `F12`: тело запроса `process` и есть образец.

Шаг, у которого во флоу `Settings Availability` = `Flow Only`, в кампании не настраивается вовсе: такие настройки из `settings` отбрасываются, и вайт на этом шаге меняется правкой флоу — сразу для всех его кампаний ([models/flow-model.md](../models/flow-model.md)).

### Правка кампании через API сняла теги или упала — `Campaign\Create` сохраняет кампанию целиком

`Campaign\Create` с `uuids` требует полный набор параметров формы: многие пропущенные аргументы сбрасываются или вызывают ошибку. Без `tags` у кампании снимаются все теги, без `countries` / `languages` — гео и языки, а без `description` или `settings` запрос падает с `500` `{"message":"Undefined array key \"description\""}` (или `"settings"`).

Поэтому правка идёт в три шага: `POST /api/v1/actions/data` с тем же `action` / `repository` / `uuids` → взять из `fields` все значения → поменять в `settings` нужный шаг и отправить весь набор в `actions/process`. Нужно право `tracker.campaigns.edit` (для remarketing-кампаний — `marketing.campaigns.edit`).

### Обновить косты кампании

`action: Campaign\UpdateCosts`, `repository: MassiveEloquent\CampaignRepository`, `uuids` — массив UUID кампаний. В `arguments`:

- `from` / `to` — диапазон дат.
- `timezone` — таймзона.
- `value` — сумма (USD).
- `is_cpc` — bool.
- `field_uuid` + `field_value` — фильтр по значению поля визита в режиме суммы Costs (`is_cpc: false`), если оба значения непустые. В ручном режиме CPC (`is_cpc: true`) эти аргументы игнорируются.

Окно — от `from` включительно до `to` не включительно, в таймзоне `timezone`. Как кост ложится на визиты и почему цифра в отчёте может отличаться от введённой — [how-to/campaigns.md](campaigns.md) (раздел `Update Costs`).

### Несколько кампаний в `uuids` с одним `value` — сумма делится пропорционально визитам

При `is_cpc: false` `value` — общая сумма на весь набор кампаний: AIO делит её на визиты всех перечисленных кампаний за окно (с учётом фильтра по полю) и пишет получившийся кост каждому визиту. Каждая кампания получает долю, пропорциональную своим визитам, а не полное `value`. При `is_cpc: true` `value` — кост одного визита, и он пишется каждому визиту каждой кампании как есть.

Нужна своя сумма на каждую кампанию — отдельный запрос с одной кампанией в `uuids`. По токену сумма (`is_cpc: false`) считается только для окна не длиннее 31 дня; длиннее — `500` `{"message":"Fetching events amount is failed"}`.

### Ответы Actions API — `uuid` объекта, `400 validation_errors`, `403`

Успешный `actions/process` отвечает `200` с `messages` (тексты уведомлений), `uuid` и `primary` — uuid созданного или изменённого объекта; у массовых экшенов есть ещё `result` с UUID, допущенными к обработке, и пропусками (`skipped`). Фактическое число изменений конкретного экшена проверяют и по `messages`: массовый экшен может пропустить часть объектов. Ошибки:

- `400` `{"validation_errors": {"<аргумент>": ["<текст>"]}}` — не прошла проверка аргументов (нет обязательного, не тот формат);
- `403` `{"message": "Action access denied (<ключ> required)"}` — у позиции нет права на экшен; `No access to this object (<уровень> level required)` — не хватает уровня доступа к объекту;
- `404` — одиночного объекта нет в тенанте либо в массовом запросе не найден ни один объект; при частичном совпадении ненайденные UUID попадают в `result.skipped`;
- `500` `{"message": "<текст>"}` — остальные ошибки внутри обработки, текст — причина; устаревший контракт может дать `426`.

## Как выгрузить список конверсий (click id, user id, тип, сумма, время) — CSV или API

Список конверсий выгружается и файлом, и по API: в интерфейсе — кнопкой `Export as CSV` на странице `Conversions`, большими объёмами за период — через Events Exporter, а постранично из скрипта — через `POST /api/v1/tables/data`. Конверсия приходит с типом, суммой (`revenue`, при праве `features.conversions-revenue`), временем конверсии и визита, uuid конверсии и визита. Идентификаторы клика и пользователя (click id, user id, sub id) — это поля визита или конверсии, как они названы в `Settings → Fields`; они идут колонками полей.

### Список конверсий по API — `tables/data`, таблица `Tracker\Conversions` (в MTK — `MTK\Conversions`)

`POST /api/v1/tables/data?token=…`, в запросе таблицы — `table: Tracker\Conversions` (так её открывает страница `Conversions` в ERP; в MTK — `MTK\Conversions`) и `dates: [from, to, timezone]` в формате `YYYY-MM-DD HH:mm:ss` — окно по времени создания конверсии; дальше `page` / `limit` (до 100 строк на страницу). Колонки строки: `type` (тип конверсии), `revenue` при праве `features.conversions-revenue`, `conversion_date`, `visit_date`, `uuid` конверсии, `visit_uuid`, кампания, источник и колонки полей визита и конверсии. `search` находит конверсию по её uuid или по uuid визита.

Это список, а не статистика, поэтому потолок периода в 31 день по токену на него не действует. Нужен просмотр конверсий (`tracker.conversions.view`); юзер без полного доступа видит конверсии только своих видимых кампаний и источников. Точное тело проще всего снять на странице `Conversions` через `F12`. Колонки таблицы в интерфейсе — [models/conversion-model.md](../models/conversion-model.md).

### Список конверсий в CSV — кнопка `Export as CSV` или Events Exporter

`Export as CSV` на странице `Conversions` — и в ERP, и в MTK — выгружает видимые колонки, доступные для CSV, в их порядке, до 10000 строк за раз ([reference/limits.md](../reference/limits.md)); колонки полей с click id включаются в настройках таблицы, а саму кнопку открывает право `features.table-export` ([how-to/analytics.md](analytics.md)).

Для больших объёмов — Events Exporter: датасет `Conversions` со стандартным пределом периода 31 день, файл `csv.gz` или `parquet`, с uuid конверсии и её типа, `revenue`, `payout`, временем и полями визита; запускается и из интерфейса, и запросом `POST /api/v1/events-exporter/export` ([how-to/events-exporter.md](events-exporter.md)).

## External Report → CSV-экспорт

`External Reports` — раздел **только ERP-вида; в MTK его НЕТ**. В MTK конверсии выгружаются кнопкой `Export as CSV` на странице `Conversions` (до 10000 строк за раз) и по API — таблица `MTK\Conversions` в `POST /api/v1/tables/data`, постранично; оба пути разобраны в секции «Как выгрузить список конверсий».

CSV-экспорт доступен только для **двух** Integration Type: `Visits CSV` (экспорт визитов) и `Google Conversions CSV` (загрузка офлайн-конверсий в Google Ads).

Создание отчёта: `Settings → External reports` → `+ External reports` → пресет `Conversions list`. У готового отчёта в списке есть колонки `UUID` и `Secret` — их значения подставляются в экспорт-ссылку. Если колонок не видно — включить их через кнопку `Settings` в тулбаре таблицы → `Table settings` (устройство настроек таблицы и пресетов — [reference/ui-common.md](../reference/ui-common.md)).

Поле `Secret` чувствительное; видимость колонки зависит от настроек таблицы. Если поле отображается как `Protected`, чтобы открыть его значение, нужен включённый 2FA (`Profile settings` → вкладка `Profile` → блок `Select a 2FA authentication method`, [reference/profile-settings.md](../reference/profile-settings.md)); затем клик по полю `Secret` + ввод 2FA-кода.

### Visits CSV

Поля при создании (`Integration Type = Visits CSV`):

- `Name`, `Description` — произвольные.
- `Lookup Hours` — за сколько часов отчёт.
- `Time Attribute` — `Created` (визиты по времени создания) или `Updated` (по времени обновления визита).
- `Timezone` — напр. `Europe/Berlin`.

Базовая ссылка экспорта:

```
https://app.aio.tech/api/v1/external-reports/data?uuid=REPORT_UUID&secret=REPORT_SECRET
```

Ссылка вводится в адресную строку браузера; файл скачивается как `export.csv`.

### Google Conversions CSV

Когда: нужно загрузить офлайн-конверсии (`Lead` / `Purchase`) в Google Ads.

Поля при создании (`Integration Type = Google Conversions CSV`):

- `Name`, `Description`.
- `Conversion Types` — какие типы конверсий включить в отчёт.

Полная ссылка собирается из UUID + Secret отчёта, UUID gclid-поля и (опц.) фильтра. UUID полей (фильтр-поле, gclid-поле) — в `Settings → Fields`, колонка `UUID`:

```
https://app.aio.tech/api/v1/external-reports/data?uuid=REPORT_UUID&secret=REPORT_SECRET&rename[Lead]=...&rename[Purchase]=...&filters[FIELD_UUID]=VALUE&gclid=GCLID_FIELD_UUID&ngsw-bypass&deep=30&timezone=Europe/Rome
```

Параметры:

- `rename[Lead]=...` / `rename[Purchase]=...` — (опц.) переименовать тип конверсии в выгруженном CSV.
- `filters[FIELD_UUID]=VALUE` — (опц.) выгрузить только конверсии, где поле `FIELD_UUID` равно `VALUE` (напр. Ad ID = 123).
- `gclid=GCLID_FIELD_UUID` — UUID поля gclid в тенанте.
- `ngsw-bypass` — служебный параметр: запрос идёт мимо service worker приложения (важно, когда ссылку открывают в браузере на домене приложения); оставить как есть.
- `deep=30` — сколько прошедших дней включить.
- `timezone=Europe/Rome` — таймзона отчёта; если опущена — используется таймзона из настроек отчёта, а без неё — **GMT+3 (`Europe/Moscow`)**.

Ссылка вводится в адресную строку, файл скачивается как `export.csv`.

После генерации `app.aio.tech` в ссылке можно заменить на домен из `Tech → Domains`, направленный на работающий AIO Agent (обычно — домен, с которого льётся трафик), и уже эту ссылку вставлять в Google Pixel как URL для загрузки офлайн-конверсий.

Google подтягивает CSV по этой ссылке сам и делает это нечасто — оперативных конверсий этим путём не получить. Поэтому Google Conversions CSV — лишь один из двух параллельных путей передачи конверсий в Google Ads (второй — gtag, для оперативности); полный разбор, что каким путём закрывается и почему нет дублей — [models/conversion-model.md](../models/conversion-model.md) → «Google: два пути конверсий — gtag и Google Conversions CSV».

При генерации Google-ссылки в `Link Generator` нужно указывать **отдельно `Google Account ID`** — это **основной** путь, ID вписывается в URL при генерации и сохраняется в поле визита; для CSV по одному аккаунту добавляют `filters[<UUID поля Google Account ID>]=<Account ID>`. Отдельной колонки Account ID в Google CSV нет. Альтернатива через `Fill Field` ноды во флоу — см. [how-to/campaigns.md](campaigns.md) → секция «Google Ads — Account ID и Conversion ID для атрибуции».

## Pull Data (FB-аккаунт) — ручной запуск подтяжки из интерфейса и через Actions API

`Pull data` запускает в фоне полное обновление данных Meta — кампаний, адсетов, объявлений и статистики — не дожидаясь фонового расписания. В интерфейсе: `Meta → Social profiles` → ПКМ на соцке → **`Pull data`** (весь профиль) или то же на кабинете в `Meta → Ad Accounts`. В диалоге два поля глубины в днях: `Backward for data` (кампании / адсеты / объявления, менявшиеся за период) и `Backward for insights` (статистика).

Через Actions API это те же экшены: `action: FacebookSocialProfile\PullData` (`repository: Eloquent\FacebookSocialProfileRepository`) и `action: FacebookAdAccount\PullData` (`repository: Eloquent\FacebookAdAccountRepository`), в `arguments` — `backward_data` (дней, не больше 120) и `backward_insights` (дней, не больше 31). Права — `meta.social-profiles.edit.pull-data` / `meta.ad-accounts.edit.pull-data`.

Повторный запуск отбивается `Should be at least 30 minutes between pull tries`, если с последнего обновления структуры кабинета (на профиле — списка его кабинетов) прошло меньше 30 минут, считая фоновые обновления; идущая подтяжка — `Already pulling`. Для активного кабинета на профиле с `Pulling interval` = `Auto` AIO сам регулярно обновляет фоном и структуру, и спенд за сегодня. Ручной полный pull не пройдёт раньше 30 минут после последнего обновления структуры; если её отметки ещё нет, учитывается последнее успешное обновление кабинета. Повторять `PullData` по расписанию из скрипта обычно не требуется. Разбор ограничений — [how-to/meta-ads.md](meta-ads.md), расписание — [how-to/meta-data-health.md](meta-data-health.md).

При `Pulling interval` = `Manually` отключены регулярная подтяжка списка кабинетов, их структуры и статистики. Их обновляют через `Pull data` или перепривязку профиля; это не отключает все фоновые процессы Meta, например синхронизацию Pages.

## Частые проблемы с API

### «Зачем мне F12, дайте Swagger» — публичного Swagger нет

Публичного Swagger нет. Но если вопрос про **справочники сущностей** (список кампаний, доменов, лендингов, юзеров), спека есть прямо в интерфейсе: меню профиля → **`Data API`** — параметры, эндпоинты, скоупы и коды ошибок (см. «Data API» выше). А если задача — «пусть AI-агент сам смотрит мои цифры», код писать не нужно вовсе: инструкция на каждого агента лежит в диалоге `MCP Server` ([how-to/mcp-server.md](mcp-server.md)). Для аналитики (`Tables Data`, `Pivot Report`) и всего остального документации нет — путь через F12.

### Поминутный лимит бьёт на batch-задаче — ответ `429` `Too Many Attempts.`

Превышение поминутного лимита приходит как `429` с телом `{"type":"Illuminate\\Http\\Exceptions\\ThrottleRequestsException","message":"Too Many Attempts."}` и заголовком `Retry-After` — через сколько секунд счётчик пропустит запрос снова. Для обычных API-запросов счётчик общий на юзера и его вкладки интерфейса; стандартный лимит — 60 в минуту, индивидуальный может отличаться. MCP, селекты и комментарии имеют отдельные поминутные счётчики. При превышении выждать `Retry-After` секунд (не дольше минуты) и продолжить.

Для batch-задач: очередь с паузами между запросами, несколько таблиц одним `POST /api/v1/tables/data` (разными ключами внутри `request`), период статистики — кусками до 31 дня. Параллельность и бюджет тяжёлых запросов — отдельные счётчики (секция «Параллельные запросы к `pivot-report/data` и `tables/data`»). Альтернатива для очень больших объёмов — выделенная инфраструктура под тенант (за отдельную плату, детали через саппорт); полный разбор варианта — [context/architecture.md](../context/architecture.md).

### Токен API не работает

Симптом — `401` `Auth Middleware: Unauthorized` вместо данных. Причины: (1) **у юзера выключен API-доступ** — это отдельный флаг, колонка `API` в `Settings → Users`; по умолчанию он выключен, включает его команда AIO по запросу; (2) юзер деактивирован; (3) неверный сам токен; (4) в `X-Tenant-Id` uuid тенанта, которого у юзера нет (секция «Какой тенант читает запрос — заголовок `X-Tenant-Id`»). Если авторизация проходит, а отказ приходит на конкретном запросе — причина другая: (5) у юзера токена не хватает прав: на таблицу — `500` (в Data API с телом `Table access denied`), на действие — `403` `Action access denied (<ключ> required)` (ключ права позиции назван прямо в тексте) или `403` `No access to this object (<уровень> level required)` (не хватает уровня доступа к конкретной записи — [models/permissions-model.md](../models/permissions-model.md)); (6) неверный HTTP-метод / endpoint.

### Формат ошибки API — как парсить неуспешный ответ

Любая необработанная ошибка API возвращается единым JSON-конвертом:

```json
{"type": "<ExceptionClass>", "message": "<текст ошибки>"}
```

- `type` — класс исключения (техническое имя, для диагностики).
- `message` — человекочитаемый текст ошибки (то же, что показывает UI).
- HTTP-код ответа = код ошибки; если у исключения нет валидного HTTP-статуса, отдаётся **500**.

Часть эндпоинтов заворачивает ошибки в свой формат: Data API — `500` `{"error": "<текст>"}` или отказ доступа к записи `403` `{"message": "<текст>"}`, `Tables Data` — `500` `{"error": "Error while processing request"}` (а на неверное имя таблицы — `422` `{"message": "Invalid table name"}`, секция ниже), `Pivot Report` — `422` `{"error": "Wrong query"}`, Actions API — `{"message": …}` или `400` `{"validation_errors": …}`, лимиты параллельности и тяжёлых запросов — `429` `{"message": …}`; поминутный лимит отвечает `429` в общем конверте с `message` `Too Many Attempts.`. В скрипте ориентируйся на HTTP-код и поле `message` или `error` (не на `type` — оно может меняться).

### `422` `Invalid table name` — в имени таблицы двойной обратный слэш

**`422` с телом `{"message": "Invalid table name"}` значит, что значение `table` не похоже на имя таблицы: сегменты имени разделяются ровно одним обратным слэшем — `Tracker\Visits`, `Facebook\AdSets`.** Так отвечают `POST /api/v1/tables/data`, `/api/v1/tables/settings` и `/api/v1/tables/csv`. Если в одном `POST` несколько таблиц, одно неверное имя отклоняет весь запрос.

Частая причина — двойное экранирование. В тексте JSON обратный слэш экранируется один раз: `"table": "Tracker\\Visits"` даёт в значении один слэш. Если скрипт экранирует его ещё раз, в запрос уходит `"Tracker\\\\Visits"` — в значении два слэша подряд, то есть пустой сегмент, и сервер отвечает `422`. Так же отбиваются имя со слэшем в начале или в конце, прямой слэш `/` вместо обратного и пустое `table` (у `/tables/csv` на пустое `table` текст другой — `table is required`).

### `Statistics request interval exceeded` — период статистики по токену длиннее 31 дня

Текст `Statistics request interval exceeded, current: …` — не про частоту запросов, а про длину периода: по API-токену статистика считается за период не длиннее 31 суток, и после `current:` стоит сам этот потолок, а не время ожидания. Дословно текст приходит от эндпоинтов, которые не заворачивают ошибку в свой формат, — например `GET /api/v1/dashboard/data`: `500` с этим текстом в `message`. `Pivot Report` на то же отвечает `422` `Wrong query`, `Tables Data` — `500` `Error while processing request`. Помогает только укоротить период: запросы кусками до 31 дня. Сводка — [reference/limits.md](../reference/limits.md).

### Heavy query исчерпал бюджет — `429` `Heavy-usage limit reached ( 20s last 60s )`

При стандартных настройках `429` с телом `{"message":"Heavy-usage limit reached ( 20s last 60s ). Try later."}` значит, что обработка завершённых запросов по токену, начатых за последние 60 секунд, заняла 20 секунд и больше. Новые запросы отклоняются, пока записи не выйдут из окна; заголовок `Retry-After` в ответе `429` говорит, через сколько секунд бюджета хватит на новый запрос. Бюджет и длина окна задаются для юзера. Считается время обработки, а не число запросов, поэтому бюджет съедают тяжёлые отчёты: длинный период, много группировок, детальные ключи вроде `visit_uuid`.

Что помогает: не слать тяжёлые отчёты параллельно, дробить период, убирать лишние группировки; сколько бюджета уже потрачено, показывает заголовок ответа `X-Heavy-Limit-Used` ([reference/limits.md](../reference/limits.md)).
