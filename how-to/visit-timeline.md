# Visit timeline — хронология событий визита

**Visit timeline — одна лента всех событий одного визита в хронологическом порядке: когда он создался, по каким нодам флоу прошёл, какие поля менялись, когда пришёл на Destination и создал конверсию, плюс системные логи.** Это диагностика «что вообще происходило с этим визитом и в каком порядке» — вместо того чтобы собирать картину из разных вкладок, вы видите весь путь визита сверху вниз с таймингом между событиями.

Открывается по правому клику на строке визита в `Tracker → Visits` → `Visit timeline`.

## Что показывает лента

Лента собирается из нескольких источников событий и рисует их одним потоком, отсортированным по времени. Каждая строка — время, дельта от предыдущего события (`+300ms`, `+5s`, `+2m 10s`, `+1d 4h`) и карточка события. Типы событий:

### Visit created — создание визита

Первая строка ленты — момент создания визита (`Visit created — initial state`). Несёт стартовый контекст: `country` (гео по IP), `source` и `campaign` (короткие UUID, полный копируется по клику), `cost` (списанная стоимость клика). Это точка отсчёта, от неё считается тайминг остальных событий.

### Переход по флоу — нода Flow State

Каждый вход визита в ноду флоу — отдельная строка, подписанная **именем ноды** (например `Filter`, `Content`, `Destination`), с чипом `node` (короткий UUID ноды). Так видно фактический маршрут визита по графу флоу: в каком порядке он прошёл шаги и на каком остановился. Что такое Flow State и чем он отличается от Visit Status — [models/visit.md](../models/visit.md).

### Field changes — изменения полей визита

Изменения полей визита сворачиваются в одну карточку `Field changes` с числом изменений. Внутри — по строке на поле: slug поля и `previous → value` (было → стало; если поле новое, показывается только новое значение). Поля конверсии помечены тегом `conv` — так отличается изменение поля визита от поля конверсии. Про сами поля визита как субстрат данных — [models/visit-field.md](../models/visit-field.md).

### Destination arrived — приход на Destination

Строка `Destination arrived` — визит дошёл до Destination. Несёт чипы `destination` и `advertiser` (короткие UUID). Это событие прихода на назначение; технический обмен самого пуша (запрос/ответ рекламодателя) в ленте не показывается — он в отдельных логах (см. ниже про `Destination Handler`). Реджект от рекламодателя виден косвенно: как изменение полей `last_rejection_reason` / `rejected_destination_uuid` в карточке `Field changes` и красной строкой системного лога — а полный ответ рекламодателя лежит в `Visit logs` / `Destination Handler` ([how-to/debug-with-logs.md](debug-with-logs.md)).

### Conversion created — конверсия

Конверсия рисуется строкой `Conversion created` (или `Conversion created — revenue`, если у конверсии есть доход) с денежным бейджем (`$0` или сумма). Чипы: `conv` (UUID конверсии), `type` (UUID типа конверсии), `revenue`, `payout`. У визита может быть несколько конверсий — каждая своей строкой. Модель конверсии — [models/conversion-model.md](../models/conversion-model.md).

### Системный лог

Обычные системные логи визита выводятся компактной строкой: текст сообщения + бейдж namespace. Ошибочные логи подсвечены красным, успешные — зелёным. Это сырые события агента по визиту, встроенные в общую хронологию.

## Как читать ленту

- **Тайминг между событиями.** Дельта слева от каждой строки показывает, сколько прошло с предыдущего события. Суб-секундные разрывы показаны в миллисекундах (`+300ms`) — видно порядок событий даже внутри одной секунды. Это помогает поймать, где визит «завис» или где события шли слишком быстро.
- **Копирование значений.** Клик по чипу или по строке поля копирует полное значение (короткие UUID в ленте обрезаны для читаемости, но копируется полный). Клик по заголовку строки разворачивает его без обрезки.
- **Пустая лента.** Если по визиту нет событий, показывается `No events for this visit` — обычно это очень свежий визит. Прежде чем списывать на свежесть, проверь колонку `Trash?`: у визита, помеченного `Trash` ещё на регистрации, лента пустая целиком.

### Лента обрывается на середине маршрута — визит помечен `Trash`

**Как только визиту проставлен флаг `is_trash`, его дальнейшие переходы по нодам флоу в ленту не пишутся** — маршрут в ленте обрывается на той ноде, где визит пометили. Строка входа в саму эту ноду ещё видна (она пишется до того, как нода отработала), а переход по ветке `Rejected` — уже нет.

Как это выглядит:

- **Лента обрывается на `Filter`** — визит не прошёл фильтрацию, и на этом шаге ему проставили `is_trash`.
- **Лента обрывается на `Condition`** — на шаге включён тоггл `Trash when Rejected`, и визит не прошёл условие.
- **Лента пустая целиком** (`No events for this visit`) — визиту проставили `is_trash` ещё на регистрации, до первого шага флоу.

Проверка — колонка `Trash?` у визита в `Tracker → Visits`. Поэтому короткая или обрывающаяся лента — **не всегда «визит только что пришёл»**: сначала смотри флаг `Trash`. Конкретную причину показывает поле визита `Trash Reason` ([mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md)).

## Как открыть Visit timeline

1. Открой `Tracker → Visits`.
2. Правый клик по строке нужного визита.
3. В контекстном меню выбери `Visit timeline`.

Экшен доступен на билде `erp`. Виден он не всем ролям тенанта: пункт `Visit timeline` в контекстном меню показывается только топ-ролям тенанта (`Owner`, `Admin`); рядовым ролям вроде `Employee` его в меню нет.

## Не путать: Visit timeline vs Show sessions vs логи Destination Handler

Три разные вещи, которые легко перепутать:

- **Visit timeline** (этот док) — хронология **событий** визита: путь по флоу, изменения полей, конверсии. Отвечает на «что и когда происходило с визитом».
- **`Show sessions`** — **запись поведения** посетителя (скроллы, клики) для воспроизведения, отдельный экшен с записями сессий. Это Session Replay, а не лента событий. Разница Visit vs Session — [models/visit.md](../models/visit.md).
- **Логи `Destination Handler`** — сырой **запрос/ответ пуша** визита в Destination (причина реджекта от рекламодателя), namespace в `Settings → Logs`, фильтр по `Loggable UUID` = `visit_uuid`. Timeline показывает только сам факт прихода на Destination; технический обмен — в этих логах. Как их читать — [how-to/debug-with-logs.md](debug-with-logs.md).
