# Visit timeline — хронология событий визита

**Visit timeline — хронология записанных событий одного визита: создание, переходы по нодам флоу, события Destination, конверсии и логи.** Лента помогает проследить порядок событий и сравнить время между строками. Она может быть неполной: например, число загружаемых логов ограничено, а отдельные события могут не записываться.

Открывается по правому клику на строке визита в `Tracker → Visits` → `Visit timeline`.

## Что показывает лента

Лента собирается из нескольких источников событий и рисует их одним потоком, отсортированным по времени. Каждая строка — время, дельта от предыдущей отображаемой строки (`+300ms`, `+5s`, `+2m 10s`, `+1d 4h`) и карточка события. У группы `Field changes` время берётся из первой записи группы. Типы событий:

### Visit created — создание визита

Строка `Visit created — initial state` показывает время создания и сохранённый контекст визита: `country` (гео по IP), `source` и `campaign` (короткие UUID, полный копируется по клику). Чип `cost` показывает сохранённую стоимость визита и скрыт при нуле. Это не снимок всех значений на момент регистрации. Если запись визита ещё отсутствует в основном хранилище, строки создания может не быть; дельты считаются между соседними отображаемыми строками.

### Переход по флоу — нода Flow State

Записанный переход визита на другую ноду флоу — отдельная строка с **именем ноды** и чипом `node` (короткий UUID ноды). Если имя недоступно, вместо него показывается UUID. По строкам видна записанная часть маршрута; последняя строка не доказывает, что обработка остановилась именно там. Что такое Flow State и чем он отличается от Visit Status — [models/visit.md](../models/visit.md).

### Field changes — изменения полей визита

Карточка `Field changes` отображает сохранённые журнальные записи изменений полей. Соседние записи сворачиваются в одну карточку с числом изменений. Внутри — slug поля (или UUID, если slug недоступен) и `previous → value`; при отсутствии предыдущего значения показывается только новое. Записи полей конверсии помечены тегом `conv`. Новые изменения полей не добавляются в этот журнал при обычном обновлении полей, поэтому отсутствие карточки не доказывает, что поля не менялись. Про сами поля визита как субстрат данных — [models/visit-field.md](../models/visit-field.md).

### Destination arrived — приход на Destination

Подпись `Destination arrived` используется и для события прихода, и для записанного отказа Destination; она сама по себе не доказывает успешный пуш. Чипы `destination` и `advertiser` показывают последние UUID из сохранённых списков визита. При отказе эти списки могут относиться к предыдущему успешному пушу — Destination отказа проверяй по логу.

В ленту попадают и сохранённые логи `Destination Handler`: причина отказа и, если интеграция передала его, `Push Log`. Поля `last_rejection_reason` и `rejected_destination_uuid` проверяй в данных визита; их появление в `Field changes` не гарантируется. Отдельный просмотр логов — `Visit logs` / `Settings → Logs`, namespace `Destination Handler` ([how-to/debug-with-logs.md](debug-with-logs.md)).

### Conversion created — конверсия

Конверсия рисуется строкой `Conversion created` (или `Conversion created — revenue`, если у конверсии есть доход) с денежным бейджем (`$0` или сумма). Чипы: `conv` (UUID конверсии), `type` (UUID типа конверсии); `revenue` появляется при положительном доходе, `payout` — при ненулевой выплате. У визита может быть несколько конверсий — каждая своей строкой. Модель конверсии — [models/conversion-model.md](../models/conversion-model.md).

### Системный лог

Обычные системные логи визита выводятся компактной строкой: текст сообщения + бейдж namespace. Ошибочные логи подсвечены красным, успешные — зелёным. Это сохранённые системные логи, привязанные к визиту и встроенные в общую хронологию.

## Как читать ленту

- **Тайминг между событиями.** Дельта слева показывает разницу со временем предыдущей отображаемой строки; у группы `Field changes` используется время её первой записи. Суб-секундные разрывы показаны в миллисекундах (`+300ms`) — видно порядок событий даже внутри одной секунды. Это помогает поймать, где визит «завис» или где события шли слишком быстро.
- **Копирование значений.** Клик по чипу или по строке поля копирует полное значение (короткие UUID в ленте обрезаны для читаемости, но копируется полный). Клик по заголовку строки разворачивает его без обрезки.
- **Пустая лента.** Если по визиту нет событий, показывается `No events for this visit` — обычно это очень свежий визит. Прежде чем списывать на свежесть, проверь колонку `Trash`: если флаг установлен ещё на регистрации, записей переходов по флоу может не быть. Пустая лента сама по себе не доказывает Trash — так же выглядит ошибка загрузки данных.

### Лента обрывается на середине маршрута — визит помечен `Trash`

**Пока у визита установлен `is_trash`, новые переходы по нодам флоу в Timeline не записываются.** Если переход в ноду, пометившую визит, был записан до её выполнения, эта строка остаётся; переход по ветке `Rejected` после установки флага уже не записывается. Другие системные логи могут появиться и после последней строки перехода.

Например:

- **`Filter`** помечает визит как Trash при отклонении фильтром.
- **`Condition`** помечает отклонённый визит, если включён `Trash when Rejected`.
- **Нет записей переходов по флоу** — проверь, не установлен ли `is_trash` ещё на регистрации, до первого шага флоу. Системные логи при этом могут присутствовать.

Проверка — колонка `Trash` у визита в `Tracker → Visits`. Поэтому короткая или обрывающаяся лента — **не всегда «визит только что пришёл»**: сначала смотри флаг `Trash`. Конкретную причину показывает поле визита `Trash Reason` ([mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md)).

## Как открыть Visit timeline

1. Открой `Tracker → Visits`.
2. Правый клик по строке нужного визита.
3. В контекстном меню выбери `Visit timeline`.

Экшен доступен на билде `erp`. Пункт `Visit timeline` доступен ролям `Owner` и `Admin`; для `Employee` он скрыт.

## Не путать: Visit timeline vs Show sessions vs логи Destination Handler

Три разные вещи, которые легко перепутать:

- **Visit timeline** (этот док) — хронология **событий** визита: путь по флоу, изменения полей, конверсии. Отвечает на «что и когда происходило с визитом».
- **`Show sessions`** — **запись поведения** посетителя (скроллы, клики) для воспроизведения, отдельный экшен с записями сессий. Это Session Replay, а не лента событий. Разница Visit vs Session — [models/visit.md](../models/visit.md).
- **Логи `Destination Handler`** — логи обработки пуша визита в Destination, включая причину отказа и сохранённый `Push Log`, если интеграция его передала. Их можно смотреть отдельно в `Settings → Logs`: namespace `Destination Handler`, `Loggable UUID` = `visit_uuid`. Эти же сохранённые логи могут попасть в Timeline; отдельная таблица удобна для подробного просмотра и фильтрации. Как их читать — [how-to/debug-with-logs.md](debug-with-logs.md).
