# Analytics / Reports (How-to)

Частые операции в аналитике: подсветка строк, переключатель атрибуции `Attribute by events time`, цветовая разметка по диапазонам, древовидные отчёты через Groupers, Cohorts и Tracker data-секции (ERP), Roll Up по полям антифрода. Концептуальные понятия (Cohorts, Compare, Visit Loss, Qualified Visits) — в [reference/glossary.md](../reference/glossary.md).

---

## TL;DR

- **Highlight Row** = подсветить выбранные строки (фильтр по объектам). ПКМ → `Highlight Row`.
- **`Attribute by events time`** = тоггл: считать конверсии по дате события, а не дате визита.
- **Colorize → Static** (ERP) = окрасить строки по диапазонам метрики (Roll-Up).
- **Древовидный отчёт (Groupers)** = `+` рядом с чипами групперов → каталог: вертикальный список категорий (Funnel/Tracker/Location/Landings/Destinations/Variants/Client/Device/OS/Time/Browser/Other + категории полей тенанта) с поиском и блоком избранного сверху; синие `►` на строках раскрывают drill-down; до 7 групперов; работает в `Campaigns` и `Roll Up report`.
- **Роль-групперы `LP: <Тип>`** = разбивка по ленду, сыгравшему роль типа (`Offer`, `Preland`…) на любой позиции воронки; в каталоге — в пикере строки `Landing` под позициями `First` / `Second` / `Third`.
- **`Unwrap tree view`** = кнопка, которая разворачивает древовидную группировку в плоский список всех комбинаций.
- **`Export as CSV`** = выгрузка таблицы в фон, файл приходит в колокольчик: колонки выбираются по правилам CSV ниже, до 10000 строк, ссылка живёт 7 дней; в `Roll Up report` — иконка, в остальных таблицах — пункт `Table tools`; нужно право `features.table-export`.
- **Таймзона** = для пресетов периодов и Roll Up — часы в шапке; произвольный период сохраняет свою таймзону. Подробности и BI — ниже.

## Highlight Row

Когда: выделить пачку строк в таблице, чтобы дальнейшие отчёты строились **только по ним**.

**Путь:** ПКМ на строке (или нескольких выделенных) → `Highlight Row`.

После применения — в таблицу добавляется фильтр по выбранным объектам. Снять — через панель фильтров.

**Где доступен:** не только в отчётах аналитики — тот же экшен есть в таблицах Meta-модуля (на каких именно вкладках и в ERP, и в MTK-виде — [how-to/meta-ads.md](meta-ads.md)). Механика везде одна: фильтр по выделенным строкам добавляется в таблицу, снимается через панель фильтров, работает и на нескольких выделенных строках сразу.

## Атрибуция по времени события — тоггл `Attribute by events time`

Когда: смотришь конверсии за период и хочешь разделить «лиды, пришедшие в этот день» vs «лиды по визитам, состоявшимся в этот день».

Частые формулировки: «тоггл атрибуции по времени события», «Attribution by Event Time», «переключатель атрибуции», «атрибуция по конверсии».

**Путь:** `Roll Up report` / `Campaigns` / другие таблицы с аналитическими фильтрами → тоггл **`Attribute by events time`** в верхней панели таблицы (подсказка тоггла: `Attribute by event time (Also known as conversion time attribution)`).

**Что делает:**

- **Дефолт** (тоггл выключен) — конверсия атрибутируется к **дате визита**. Лид, пришедший сегодня по визиту вчерашнего дня — попадёт во вчерашний день.
- **`Attribute by events time` включён** — конверсия атрибутируется к **дате события** (когда пришёл постбэк). Лид сегодня — в сегодняшний день.

**Когда что:**

- ROI по дню запуска кампании → тоггл выключен (дефолт).
- Дневная статистика поступления конверсий → включить `Attribute by events time`.

Также см. [reference/glossary.md](../reference/glossary.md) → Attribute by events time.

Если у команды разные toggle-настройки между байерами и тимлидом — числа не сойдутся. Договариваться единообразно: держать `Attribute by events time` в одном положении на всю команду.

## В какой таймзоне считаются даты и часы в отчётах

### Таймзона отчётов — выбранная в часах в шапке, а не UTC и не таймзона тенанта

**Таблицы с периодом-пресетом и `Roll Up report` считают в таймзоне, выбранной в часах в шапке интерфейса (справа вверху: дата, время и смещение вроде `+03:00`).** В ней режутся границы периода (`Today`, `Yesterday`, `Last week`) и строки групперов `Day`, `Hour`, `Day Part`, `Week`, `Month`, `Year`; «сегодня» начинается в полночь этой таймзоны. Произвольные даты обычной таблицы сохраняют таймзону, в которой их выбрали; `BI Builder` берёт таймзону профиля (подробнее ниже). AIO хранит данные в UTC и пересчитывает даты и часы под таймзону запроса. Своей таймзоны у тенанта нет — она у каждого пользователя своя. Частые формулировки: «в каком часовом поясе статистика», «UTC или таймзона аккаунта», «в какой таймзоне `created_at_day` / `created_at_hour` / `day_part`», «где поменять таймзону отчётов».

Неделя в группере `Week` начинается с дня из поля `Weekdays start` профиля (`Monday` / `Sunday`).

### Где поменять таймзону — часы в шапке и поле `Location` в профиле

- **Часы в шапке** — клик по смещению (например `+03:00`) открывает список таймзон с поиском. Выбранная сразу применяется к отчётам и сохраняется на аккаунте: в другом браузере будет та же.
- **`Set default timezone`** («Сбросить таймзону») в начале того же списка возвращает таймзону профиля; пункт виден, только когда выбранная от неё отличается.
- **`Location`** («Местоположение») в `Profile settings → Appearance → Locale settings` — таймзона профиля ([reference/profile-settings.md](../reference/profile-settings.md)). По ней считаются запросы без явной таймзоны: API без третьего элемента `dates` ([how-to/api.md](api.md)) и конструктор дашбордов `BI Builder` (ERP) — он берёт таймзону профиля, даже если в шапке выбрана другая.
- **По умолчанию** в обоих местах стоит `Europe/London`, а не таймзона компьютера.

### `Day Part` («Время суток») — час суток за весь период, `Hour` — час конкретного дня

`Day Part` раскладывает статистику по 24 часовым интервалам суток в таймзоне отчёта — строки вида `09:00 - 10:00` — и суммирует каждый интервал за все дни периода. Частей суток вроде «утро / вечер» у этого группера нет. `Hour` — час конкретной даты (строка на каждый час каждого дня), `Day` — календарный день.

При включённом `Attribute by events time` конверсии и деньги по ним ложатся в день и час **события**, а визиты — всегда в день и час визита (секция «Атрибуция по времени события — тоггл `Attribute by events time`» выше).

### Цифры «за сегодня» у коллег разные или поменялись после смены таймзоны

Симптом: у двух человек в одном отчёте разные цифры за один день, или после смены таймзоны часть таблиц показывает другие суммы. Что проверить:

- **Таймзона в шапке у каждого своя** — «сегодня» у пользователя с `+03:00` и с `Europe/London` начинается в разное время. Сверять цифры в одной таймзоне.
- **Произвольный период запоминает таймзону, в которой его задали.** На обычной таблице даты, выбранные вручную в календаре, после смены таймзоны в шапке остаются в прежней — перевыберите период. Пресеты (`Today`, `Last week`…) и `Roll Up report` пересчитываются в новой таймзоне сами.
- **`BI Builder` (ERP) считает в таймзоне профиля** (`Location`), а не в выбранной в шапке — держите их одинаковыми, если сверяете дашборд с таблицами.
- **`Attribute by events time`** в разном положении — секция о тоггле выше.

### `Meta Spend` за день не совпадает с кабинетом Meta — сутки режутся по таймзоне отчёта

**`Meta Spend` AIO берёт у Meta по часам и раскладывает по дням таймзоны, выбранной в шапке, а не таймзоны рекламного аккаунта.** Поэтому дневной спенд совпадёт с кабинетом, только если в шапке стоит таймзона рекламного аккаунта; у кабинетов в разных таймзонах одна настройка подойдёт лишь части из них. Частые формулировки: «какой часовой пояс ставить, чтобы видеть реальный Meta Spend», «спенд за день не бьётся с кабинетом».

От таймзоны зависит и сходимость разбивки с итогом. Спенд сшивается с визитами по паре «объект Meta × день» в таймзоне отчёта; спенд пары, у которой нет (дошедших) визитов, в строки не попадает и уходит в `Out of scope`. Сдвинули таймзону — сдвинулись границы суток и размер `Out of scope`, поэтому на тех же данных сумма строк может сходиться с итогом в одной таймзоне и расходиться в другой. Отдельной логики под конкретную таймзону, в том числе UTC+0, у AIO нет. Причины расхождения строк с итогом — [mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md).

## Colorize → Static в Roll-Up

Когда: визуально подсветить строки по диапазону метрики (например, `Engagement Rate %`: ниже 25, от 25 до 60, выше 60).

**Путь:** `Roll Up report → Colorize rows → выбрать метрику → Static → задать From / To → Apply`.

**Шаги:**

1. Открыть Roll-Up Report.
2. В панели сверху открыть `Colorize rows`.
3. Выбрать метрику (`Engagement Rate %`, `CR %`, `ROI %` или свою).
4. Выбрать режим `Static` (второй режим — `Gradient`).
5. Задать две границы диапазона в `From` / `To` или ползунком. Цвета шкалы заданы автоматически с учётом того, лучше большее или меньшее значение метрики.
6. Нажать `Apply`.

После применения строки окрашиваются по значению выбранной метрики.

## Древовидный отчёт через Groupers

Когда: разбивка таблицы по нескольким полям (drill-down), напр. `Campaigns → Source → Country` или `Landing 1 → Landing 2 → Destination #1`. Работает **одинаково и в `Tracker → Campaigns` (и других Tracker-таблицах), и в `Analytics → Roll Up report`**.

**Как добавить:** рядом с чипами групперов (напр. чип `Campaigns`) — кнопка **`+`** → открывается **каталог групперов**: вертикальный список категорий с поиском сверху (как он устроен — в секции «Как искать группер в каталоге» ниже). Выбираешь группер — он встаёт чипом в цепочку (`Campaigns → Source → …`), `×` на чипе убирает. До **7 групперов** стеком. Большие разбивки могут долго строиться — сужайте период и фильтры. Лимиты программного доступа через Pivot API описаны отдельно в [reference/glossary.md](../reference/glossary.md).

**Как раскрыть:** после добавления у каждой строки появляются **синие стрелки `►`** — клик раскрывает строку на следующий уровень группера (drill-down по дереву). Частые формулировки: «лид не в дрилдауне», «конверсия не раскрывается в дереве», «не проваливается на следующий уровень» — обычно лид есть, но не под тем группером/уровнем, на который смотрят.

### Чипы групперов над таблицей — префикс `Group:`, тултип `Pivot Group #N`, кнопка `+`

Цепочка групперов над таблицей — синие чипы: у первого стоит серый префикс `Group:` (`Группа:`), у каждого чипа тултип `Pivot Group #N` — номер уровня в цепочке; `×` убирает группер там, где он доступен. У первого группера Tracker-таблицы кнопки `×` нет. Тултип кнопки `+` — `Add grouper and then expand rows in the table via the caret button` («Добавьте группер, затем раскрывайте строки в таблице кнопкой-кареткой»). Потолок цепочки — 7 групперов. Частые формулировки: «pivot group», «группа над таблицей», «чип группировки», «как убрать группировку».

### Раскрыл дерево, поменял даты — подгруппы свернулись; `Refresh table` их сохраняет

Симптом: раскрытые синими стрелками `►` подгруппы схлопнулись после смены периода, фильтра или сортировки. Это штатно: полная перезагрузка корневой таблицы сворачивает раскрытые уровни — их данные к новому запросу уже не относятся. Не сворачивают: кнопка `Refresh table` в тулбаре (перечитывает только корень, раскрытые ветки остаются) и подгрузка следующей страницы скроллом. У каждой раскрытой подгруппы рядом с кареткой есть своя кнопка обновления (тултип `Refresh group` / «Обновить группу») — перечитывает только её, соседние уровни не трогает. Смена группера на уровне глубже первого тоже не перезагружает всю таблицу: корень зависит только от первого группера. Контролы тулбара целиком — [reference/ui-common.md](../reference/ui-common.md).

### Косты и профит по FB в разрезах — колонка Meta Spend

Когда: смотришь косты, спенд или профит по FB в разбивке (по Source, Destination, гео, офферу) прямо в древовидном отчёте. Частые формулировки: «где мои косты по FB в отчёте», «спенд по разрезу», «профит по Destination», «ROI по FB в Roll-Up».

**Основной способ — колонка `Meta Spend`** в Roll Up report. Она считается на лету в момент отчёта и разносит расход из Meta по визитам под выбранный группер, а рядом стоит revenue → профит и ROI по FB читаются прямо в отчёте. Предупреждающий значок рядом с `Meta Spend` появляется при статусе `noisy` / `partial` либо ненулевых `Orphans` / `Out of scope`; при `fine` без этих сумм стоит значок-галочка. Наведение показывает разбор `Matched` / `Orphans` / `Out of scope` / `Total`; `Orphans`, `Out of scope` и `Total + out of scope` видны, когда соответствующие суммы ненулевые. Полная механика раскладки, статусы, out-of-scope и сходимость сумм между разрезами — [mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md).

### Уровень атрибуции Meta Engine — кнопка `Campaign` / `Adset` / `Ad` в тулбаре

На таблице с Meta-колонкой (`Meta Spend`, `Meta Impressions`, `Meta Inline Link Clicks`, `Meta Commission`) можно выбрать текущий уровень — `Campaign`, `Adset` или `Ad` (в меню у пунктов подсказки `campaign × day attribution` и т.д.). В `Roll Up report` это кнопка с иконкой Meta в верхней панели; в остальных таблицах — пункт `Meta attribution level` в меню `Table tools`. Уровень задаёт, как спенд Meta матчится к трафику: дефолт — `Campaign`; чем ниже уровень, тем точнее привязка, но больше спенда выпадает. Исключение — разрез или фильтр по Meta-сущности: там уровень задаёт сама разбивка, кнопка на него не влияет. Выбор глобальный на все таблицы и хранится в браузере — не в пресете и не в профиле, другой браузер или устройство стартует с `Campaign`; смена уровня перечитывает страницу. Отсюда вопрос «у коллеги в том же отчёте другой `Meta Spend`»: сверить выбранный уровень. Как матчинг устроен на каждом уровне и что именно выпадает — [mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md).

### Каталог групперов

Каталог (категория → групперы) — типовые системные групперы (динамический per-tenant состав, роль-групперы `LP: <Тип>` по типам лендов тенанта и категории `RMK ...` по рассылкам — в подсекциях ниже). Порядок в таблице — порядок секций в списке: путь визита собран сверху, в категории `Funnel`.

| Категория | Групперы |
|---|---|
| **Funnel** | Campaigns, Source, Landing 1…3, `LP: <Тип>` (роль-групперы — по одному на тип лендов тенанта), Destination #1…#3, `Funnels contains LP` / `Funnels contains LP type` (визит — в строке каждого своего ленда / типа; без итоговой строки) |
| **Tracker** | Flow, Split Group |
| **Location** | Country, City, Continent, Time Zone |
| **Landings** | LP Type #1…#3 |
| **Destinations** | Advertiser #1…#3 |
| **Variants** | Variant #1…#10 |
| **Client** | Client Engine, Client Engine Version, Client Family, Client Name, Client Type, Client Version |
| **Device** | Brand Name, Device Name, Model (`Device Name` бьёт метрики по device-type: `smartphone` / `tablet` / `desktop` и др.) |
| **OS** | OS Combined, OS Name, OS Platform, OS Version |
| **Time** | Day, Hour, Month, Week, Year, Day Part, Week Part |
| **Browser** | Browser Language, Initial Domain, Initial Path, Browser Window Height, Browser Window Width |
| **Other** | Screen Dimensions, Agent Version, Trash Reason, ASN Organization, Visit UUID, Ip Address, User Agent |

Ниже категорий трекера идут категории полей тенанта, затем `RMK ...` по рассылкам. Замыкает список `Other`. Категории полей могут называться `Facebook` / `Google`; системные групперы рекламных объектов и **отдельная секция `Time` со временем инсайта** (`Day` / `Hour` / `Month` / `Year`) относятся к каталогам разделов `Meta` / `Google`, а не к каталогу Tracker / Roll Up.

### Как искать группер в каталоге — поиск и подсказки строк

Курсор при открытии каталога сразу стоит в поле поиска — можно печатать, не целясь мышью. Поиск включается со **второго символа**.

Ищет он не только по подписи группера: матчатся ещё английское имя категории (`Funnel`, `Other`), имя серии и алиасы, в том числе русские разговорные — `гео`, `камп`, `сплит`, `оффер`, `браузер`, `крео`, `лп`, `рмк`. То есть «гео» находит `Country`, а «крео» в каталоге раздела `Meta` — системный группер `Ads` категории `Facebook`. В блоке `Favorites` поиск проверяет только подпись избранного группера.

Наведение на строку даёт тултип с описанием группера, примером значения (`Example: NL` / `Пример: NL`) и — у тяжёлых разбивок — предупреждением о кардинальности. Описания системных групперов приходят по-английски и не переводятся. У группера по полю тенанта тултип — это `Description` самого поля из `Settings → Fields`, в том виде и на том языке, как его заполнили при создании поля; пустое описание оставляет стандартную подсказку ([how-to/user-fields.md](user-fields.md)).

### Избранные групперы — блок `Favorites` и режим управления

Избранные групперы собираются в блок **`Favorites`** (`Избранное`) первым в списке каталога, над категориями. Помеченный группер уезжает туда из своей категории — в двух местах одновременно он не показывается.

Звезда у строки видна не всегда: сначала надо включить режим управления кнопкой-звездой слева от поля поиска (тултип `Click to manage favorite groupers` / `Управлять избранными группировками`; когда режим включён — `Click to disable managing mode` / `Отключить режим управления`). В этом режиме звезда у каждой строки добавляет группер в избранное и убирает обратно.

В блок попадают только групперы текущего каталога: звёзды, поставленные в другом разделе, сюда не подмешиваются.

### Позиционные групперы — одна строка с выбором позиции

Позиционные серии занимают в каталоге **одну строку** с пикером позиции справа: `First` / `Second` / `Third` (`Первый` / `Второй` / `Третий`), у `Variant` — до `Tenth` (`Десятый`); по умолчанию выбрана первая позиция, у позиций в пикере стоит значок-решётка `#`. Так свёрнуты `Landing`, `LP Type`, `Destination`, `Advertiser`, `Variant` и все семь серий `RMK ...`. У серии `Landing` пикер длиннее: под позициями, за разделителем, идут бейджи типов лендов — это роль-групперы `LP: <Тип>` (секция «Роль-групперы `LP: <Тип>`» ниже).

Подпись серии в строке каталога не переводится — она всегда по-английски (`Landing`, `Destination`). На чипе и в шапке колонки встаёт полная подпись выбранного группера — `Landing 1`, `Landing 2`.

Позиционные групперы лендов подписаны `Landing 1` / `Landing 2` / `Landing 3`. Частые формулировки — «первый ленд», «прилэнд отдельно», «второй ленд», «лп1», «лп2»: в каталоге это строка `Landing` и выбор позиции.

### Что значит позиция `#N` у `Landing` и `Destination` — порядок в пути визита, не нода флоу

Позиция — порядковый номер в **пути конкретного визита**, а не номер шага во флоу. `Landing N` — N-й **уникальный** ленд, который визит открыл: ленд записывается в путь при первом показе, повторный показ того же ленда новой позиции не даёт. `Destination #N` — N-й уникальный Destination, куда визит **успешно запушен** (`Destination-pushed`): позиции считаются по успешным пушам, отклонённые и неуспешные попытки позиции не занимают, повторный пуш в тот же Destination новой позиции не создаёт. Поэтому оффер, стоящий на двух нодах флоу, в разбивке `Destination #1` / `Destination #2` виден только на той позиции, на которой визит дошёл до него впервые — обычно `#1`. Частые формулировки: «оффер на двух позициях», «группер видит только первую позицию», «второй дестинейшн пустой». Разбивки «Destination на любой позиции» в каталоге нет; для лендов эту задачу закрывают роль-групперы `LP: <Тип>`. Как собирается путь визита — [mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md).

### Тяжёлые групперы — значок и предупреждение о кардинальности

Четыре группера помечены как тяжёлые: `Client Version`, `Visit UUID`, `Ip Address`, `User Agent`. В строке каталога у них стоит значок-восклицание, а в тултипе — строка `High cardinality — grouping may be heavy` (`Высокая кардинальность — группировка может быть тяжёлой`).

Смысл пометки: у такой разбивки очень много уникальных значений — вплоть до строки на каждый визит, — поэтому отчёт строится долго и легче упирается в лимиты Pivot API. Частые формулировки: «отчёт не грузится», «аналитика висит», «отвалился по таймауту». Лечится сужением периода, фильтрами или более крупной разбивкой — у `Visit UUID` это написано прямо в подсказке: `One group per visit — use with filters`. Помогает и скрытие лишних метрик-колонок: таблица считает видимые метрики и необходимые для них зависимости, шапка и фильтры при этом рисуются сразу, а строки доезжают следом ([reference/ui-common.md](../reference/ui-common.md)). Без явной сортировки временные групперы упорядочены по времени, свежее сверху; у остальных разрезов используется первая посчитанная аналитическая колонка, поэтому скрытие колонки может поменять порядок строк.

### Стрелка в строке группера — `Opens another page`

Стрелка справа в строке каталога означает, что выбор этого группера уведёт на другую страницу; её тултип — `Opens another page` (`Откроет другую страницу`). Появляется она только в пикере **первого** группера цепочки: там смена группера переключает саму секцию (напр. группер `Country` перебрасывает в `Countries`). В каталоге по кнопке `+`, где группер добавляется вторым и дальше, стрелки нет — добавление уровня страницу не меняет.

### Роль-групперы `LP: <Тип>` — ленд в роли типа на любой позиции воронки

Роль-группер отвечает на вопрос «какой ленд играл роль типа T (`Offer`, `Preland`, …) в визите, на какой бы позиции воронки он ни стоял». Строка группы — **ленд**, а не тип: тип здесь только отбор. Частые формулировки: «перформанс ленда в любой позиции», «где ленд участвовал», «ленд в роли оффера», «группировка по типу ленда», «разбивка по офферам без позиции». Групперов по одному на каждый тип лендов тенанта с включённым тоглом `Generate events` (у типа `White` из шаблона тенанта он выключен во всех семи шаблонах — строки `LP: White` в каталоге нет; у остальных засеянных типов — `Offer`, `Preland` везде, `Preland w/ Form` в Finance / Nutra, `Thank-You Page` в Finance / Nutra / Sweeps, `PWA` в iGaming — включён); подпись — `LP: <имя типа>`, категория `Funnel`. Если визит прошёл несколько лендов одного типа, в строку попадает **первый** из них — один визит даёт максимум одну строку на роль, строки не пересекаются. При выключенном `Show empty fields` визиты без ленда этой роли не входят ни строкой, ни в футер. Разбивка по типу как по значению остаётся позиционной — `LP Type #1…#3`; роль-групперов по типам рекламодателей (`Advertiser`) нет. Как тип задаёт роль ленда — [how-to/landings.md](landings.md).

### Где роль-группер в каталоге — пикер серии `Landing`, чип `Landing: <тип>`

В каталоге роль-групперы не занимают отдельной строки: они сидят в пикере строки `Landing` — сверху позиции `First` / `Second` / `Third` со значком `#`, под разделителем — типы лендов с иконкой и цветом типа. Выбранный тип встаёт на чип как `Landing: <иконка> <имя типа>`, а не сырое `LP: Offer`; дословная подпись `LP: <Тип>` видна в списке фильтров таблицы. Поиск каталога находит их по имени типа и по словам `роль` / `role`. Работают в таблицах трекера и в `Roll Up report` — каталог у них общий. На странице `Content → Landings` тот же роль-группер включается переключателем типа слева в тулбаре (`All` / имя типа) вместе с фильтром списка по типу; без него метрики страницы считаются по выбранной позиции `#N` (по умолчанию первой), и у ленда, стоящего на другой позиции, выходят нули — [how-to/landings.md](landings.md).

### В пикере `Landing` нет моего типа — у типа выключен `Generate events`

Симптом: в пикере строки `Landing` есть не все типы лендов тенанта, нужного бейджа нет. Частые формулировки: «нет группера по моему типу», «в списке нет типа», «`LP: <тип>` не появился». Причина: роль-группер создаётся только для типов с включённым `Generate events` — у типа с выключенным флагом его нет. Проверка в ERP при праве `content.landing-types.view`: `Content → Landings → + Landing ▾ → Manage landing types`, колонка `Generate events` у типа ([how-to/landings.md](landings.md)). После включения флага группер появляется в каталоге после перезагрузки страницы.

### Фильтр по ленду в роли типа — `LP: <Тип>` в панели фильтров таблицы

Каждый группер каталога автоматически доступен и как фильтр таблицы (`Table settings → Filters`) под своей подписью — у роль-группера это дословное `LP: <Тип>`. Такой фильтр оставляет визиты, у которых этот ленд играл роль типа на любой позиции; позиционные `Landing 1…3` фильтруют по ленду на конкретной позиции. Значение вводится вручную полным uuid лендинга (плейсхолдер `Enter full value`) — выпадающего списка лендов у этих фильтров нет.

### Строка `Empty` на разбивке по лендам / `Destination` — визиты, не дошедшие до этой точки

**На funnel-разрезах — позиционные `Landing` / `LP Type` / `Destination` / `Advertiser`, роль-групперы `LP: <Тип>`, позиционные `RMK ...` — визиты без ленда или Destination на этой позиции собраны в строку `Empty`; так же ведут себя групперы по полям тенанта (например `Offer State`, `PWA State`) для визитов без значения поля.** Строка `Empty` всегда стоит последней — при любой сортировке она уезжает на последнюю страницу, — показана приглушённо, у иконки подсказка `No value for this grouping`. Попадает она и в CSV-выгрузку таблицы.

Визиты строки `Empty` входят в футер трафика (`Visits`, конверсии), поэтому у суммируемых счётчиков сумма всех строк совпадает с футером; средние значения и формулы так суммировать нельзя. `Meta Spend` раскладывается только по дошедшим визитам: у строки `Empty` своей доли нет, а расход Meta-объектов, у которых до этой точки не дошёл никто, показывается в `Out of scope` строки `Empty` ([mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md)).

Тумблер **`Show empty fields`** в аналитическом фильтре таблицы (тултип «Show the Empty row and count visits without the field in totals and Meta spend share») на эту выдачу не влияет: строка `Empty` показывается и при выключенном тумблере. На обычных разрезах (кампания, источник, страна) пустое значение тоже стоит строкой `Empty` и входит в итог.

Страница `Tracker → Destinations` строки `Empty` не показывает и считает футер только по визитам, дошедшим до Destination на выбранной позиции, — поэтому `Visits` там меньше, чем на `Campaigns`. Частые формулировки: «итог меньше, чем на кампаниях», «в разбивке по дестинейшнам появилась строка Empty», «откуда пустая строка внизу таблицы». Сходимость сумм между разрезами и внутри раскрытых уровней — [mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md).

### Цифры в `Destinations` не совпадают с разбивкой кампаний по `Destination #N` — позиция и архивные кампании

**Скрытие метрики на групперах (`Hidden at groupers`, например `LP1 Visits` / `LP2 Visits` на `Destination #1…#3` и `Advertiser #1…#3`) на цифры не влияет — прячется только колонка** ([models/metric.md](../models/metric.md)). Расхождение страницы `Tracker → Destinations` с разбивкой кампаний по Destination дают сами разрезы. Частые формулировки: «`LP#1 Visits` в Destinations и в Campaigns разные», «скрыл метрику на уровне Advertiser — поменялись цифры?».

- **Позиция.** Страница `Destinations` считает Destination на позиции, выбранной кнопкой `#1` / `#2` в тулбаре, а группер `Destination #N` — на своей позиции `N`. Сравнивайте одинаковые позиции.
- **Архивные кампании.** `Tracker → Campaigns` архивные кампании не показывает и в итоги не берёт, а `Destinations` считает визиты всех кампаний, включая архивные.
- **Только дошедшие визиты.** В строке Destination — визиты, дошедшие до Destination на этой позиции, поэтому метрики воронки у Destination меньше, чем у кампании: `LP1 Visits` (визиты хотя бы с одним лендингом) у Destination — это только те из них, кто дошёл до этого Destination (секция «Строка `Empty` на разбивке по лендам / `Destination` — визиты, не дошедшие до этой точки» выше).

### Бледная строка с красным крестиком — `Currently disabled at top level grouper`

`Currently disabled at top level grouper` («Сейчас отключён группером верхнего уровня») — подсказка на красном значке-крестике у лендинга или Destination в разбивке: кампания (или флоу), под которой стоит строка, **сейчас не отправляет трафик** на этот лендинг / Destination, хотя за выбранный период трафик на нём был. Сама строка при этом бледная, серая. Частые формулировки: «серый дестинейшн в разбивке», «бледная строка», «красный крестик у оффера», «что значит currently disabled at top level grouper».

Пометка бывает только у строк `Landing` / `Destination`, отфильтрованных по кампании или флоу: раскрыли кампанию в дереве (первый группер `Campaigns`, ниже — `Destination #N` или `Landing N`) или открыли таблицу с фильтром по кампании. AIO сверяет строку с **текущими** настройками кампании (флоу) и помечает её, если этого лендинга / Destination нет среди активных:

- вариант выключен в сплите кампании;
- лендинг / Destination из кампании убран;
- он стоит в дереве дистрибуции, где выключена его нода или любая родительская (`Strategy`, `Folder`).

Цифры в такой строке — настоящий трафик периода: пометка говорит о текущем состоянии кампании, а не о том, что данные неверные. Вернуть вариант в работу — в настройках кампании ([how-to/campaigns.md](campaigns.md)).

### Групперы по рассылкам — категории `RMK ...` в каталоге

В каталоге есть **семь системных `RMK`-категорий (21 группер)** — разбивки по рассылкам. Они приезжают каждому тенанту безусловно, отдельной настройки или права под них нет. В каждой категории по три позиции `#1`…`#3`, и в списке категория занимает одну строку с пикером позиции (`First` / `Second` / `Third`). Дословные подписи групперов — то, что встаёт на чип и в шапку колонки:

`RMK Audience #1`…`#3`, `RMK Campaign #1`…`#3`, `RMK Flow #1`…`#3`, `RMK Templates #1`…`#3`, `RMK Channel #1`…`#3`, `RMK Template Node #1`…`#3`, `RMK Send Result #1`…`#3`.

Подписи в интерфейсе английские (перевода у этих групперов нет) — искать и цитировать их надо дословно, как выше.

**Убрать `RMK`-категории из каталога нельзя** — это частый запрос от тех, кто рассылками не пользуется и хочет разгрузить список. Настройки видимости у них нет: каталог отдаётся тенанту целиком, и вкладок, за которые эти категории можно было бы убрать, в каталоге нет — семь `RMK`-секций идут в общем вертикальном списке наравне с остальными. Разгружает поиск: он понимает алиас `рмк`, так что листать список не обязательно. Скрыть можно не группер, а **колонку** — у метрики есть настройка `Hidden at groupers`, она убирает колонку при разбивке по выбранным групперам ([models/metric.md](../models/metric.md)).

### `RMK Audience` или `RMK Campaigns` — какая разбивка про что

Две соседние категории каталога отвечают на разные вопросы. **`RMK Audience`** (групперы `RMK Audience #1`…`#3`) — в какие аудитории рассылки визит **собирался**; список только пополняется, выбывший визит из него не исчезает, поэтому это история попадания, а не текущий состав аудитории. **`RMK Campaigns`** (групперы `RMK Campaign #1`…`#3`) — из каких кампаний визиту **пытались отправить сообщение**: учитываются как успешные, так и неудачные отправки.

Разбирать по ним «кому уйдёт следующий пуш» нельзя: попадание в аудиторию не равно отправке. Что показывают колонки визита — [models/visit.md](../models/visit.md); почему список аудиторий не уменьшается — [models/marketing-flow.md](../models/marketing-flow.md).

### Разбивки раздела `Marketing` — отдельный набор группировок, не трекерный

**Группировок по рассылкам два набора, и они не пересекаются.** В каталоге трекера (Roll Up, Tracker-таблицы) — позиционные категории `RMK ...` с позициями `#1`…`#3`, как у лендов. На страницах раздела `Marketing` (`/app/remarketing` — рассылки) каталог другой: свой набор группировок в категориях `Remarketing` (кампания, флоу, дистрибуция шаблонов, канал, результат отправки) и `Time` (время отправки), и в Roll Up он недоступен — это отдельный namespace аналитики, устроенный так же, как у Meta-группировок.

Разница не косметическая. У одного визита за жизнь набирается много кампаний, флоу, дистрибуций и каналов, поэтому позиционная разбивка отвечает на вопрос про путь конкретного визита («первая отправка, вторая, третья»), а группировки раздела `Marketing` считают отправки **в сумме** — по кампании, флоу, дистрибуции шаблонов, каналу, результату отправки и времени.

**Разбивка по дистрибуции шаблонов есть** — группировка называется `Templates`. Полный список девяти группировок раздела — [how-to/remarketing-campaigns.md](remarketing-campaigns.md).

### На каких страницах раздела `Marketing` есть колонки метрик

Колонки метрик подмешиваются к **четырём** страницам раздела `Marketing` (`/app/remarketing`): `Campaigns`, `Flows`, `Template distributions` и `Other` (страница-свалка для группировок без своей страницы-сущности — канал, результат отправки и время). На остальных страницах раздела — `Messages`, `Message templates`, `Sender providers` — аналитики нет вовсе: это списки сущностей.

Показываются на этих страницах только метрики типа `Remarketing count` и формулы целиком над ними — почему так и как собрать процент, см. [models/metric.md](../models/metric.md).

### Почему суммы по дням в разделе `Marketing` выходят за границы периода

Симптом: в разделе `Marketing` (рассылки) отправки разложены по `Day`, а в таблице видны даты за пределами выбранного периода. Частые формулировки: «даты рассылки не совпадают с периодом», «в отчёте чужие дни».

Причина — связка с тогглом `Attribute by events time`. Колонка времени (`Day` / `Hour` / `Month` / `Year`) в этом разделе показывает время события рассылки — отправки, ошибки, доставки или открытия — в таймзоне отчёта. А период выбирается по-разному: с включённым тогглом — по времени этого события (даты сойдутся), с выключенным (дефолт) — по времени **визита**. То есть по умолчанию в отчёт попадают события рассылок по визитам выбранного периода, а сами события могли произойти позже и лечь в колонке `Day` на свою дату.

Проверка: включить `Attribute by events time`, если нужен ровно период отправок.

### Есть ли аналитика по конкретному тексту пуша

**Нет: до текста конкретного сообщения аналитика не доходит.** Отправленный текст (после раскрытия спинтакса) в аналитике не хранится — он собирается заново на каждую отправку.

Самое мелкое, до чего разложимы отправки, — **узел-шаблон дерева дистрибуции**: под него в каталоге трекера заведена категория `RMK Template Node #1`…`#3`. В разделе `Marketing` среза по узлу шаблона нет, как нет и среза по шагу серии `Drip schedule`: разложить серию по шагам через группировки нельзя.

### Почему каталог групперов у меня другой (динамический per-tenant)

Каталог групперов **динамический и per-tenant**. Таблица выше — **системные** групперы; плюс туда попадают **кастомные поля визита** из `Settings → Fields` с доступностью группера `Tables` в `Edit Field → Availability as grouper`. Этот каталог используется и в Tracker-таблицах, и в Roll Up. Поле встаёт группером под категорией из своего атрибута `Group` (пустой `Group` → категория `Fields`), подписью группера служит имя поля. Категории полей `Facebook` / `Google` не требуют подключения рекламной интеграции; системные рекламные групперы находятся в отдельных каталогах Meta / Google. Поэтому у разных тенантов список разный: стартовый набор категорий полей приезжает из шаблона тенанта (следующая секция), а дальше добавляются свои поля под конкретный источник или интеграцию. Категории полей тенанта идут в списке следом за `Fields` и с её же иконкой; ничего не сворачивается и не прячется за счётчиком — весь список листается целиком, а быстрее найти поле через поиск по имени.

*(Не путать: экшен `Make analytic` по полю — это **отдельная колонка для скорости** разбивок, а не вкл/выкл группера.)* См. [how-to/custom-fields.md](custom-fields.md).

### Какие категории полей-групперов приходят из шаблона тенанта

Категории полей в каталоге у нового тенанта — из полей шаблона тенанта, и состав зависит от вертикали ([context/architecture.md](../context/architecture.md)). Во всех семи шаблонах с доступностью `Analytics` и `Tables` засеяны `LP Split Content` (`LP Header`…) и `Google` (`Google Keyword`…); `Tracking` (`Buyer UTM`, `Creative`) и почти все поля `Facebook` (`FB Ad Name`…) — только `Tables`, что позволяет выбирать их и в Tracker-таблицах, и в Roll Up; `Filter` (`Fraud Score`, `Triggered Rules`) есть только в шаблонах Finance / Nutra / Sweeps — в iGaming этих полей нет. По вертикалям добавляются свои группы: `Form` (Nutra, Sweeps), `PWA` (iGaming), `Leads`. Категории `Facebook` / `Google` собираются из полей и без подключённой интеграции; системные разрезы рекламных объектов находятся в каталогах соответствующих разделов.

### Статистика по командам и байерам — группер `Campaign Owner` и фильтр `Team`

**Группера «Команда» нет: залив по байерам разбивают группером `Campaign Owner` («Владелец кампании», категория `Fields`), а по командам — фильтром `Team` («Команда»).** Частые формулировки: «статистика заливов по командам», «разбивка по байерам», «стата команды», «по владельцам кампаний».

- **`Campaign Owner`** — владелец кампании на момент визита: он записывается в визит, поэтому смена владельца кампании прошлую статистику не переносит. Во всех шаблонах тенанта есть пресет `Roll Up report` `By Buyer [Owner → Campaign]` — байеры, под ними их кампании.
- **Фильтр `Team`** в панели `Filters` `Roll Up report` оставляет визиты, чей записанный при регистрации `Campaign Owner` **сейчас** состоит в выбранной команде; смена владельца самой кампании этот срез не переносит. Выберите одну команду — итоговая строка покажет её залив. В списке — команды, где вы состоите (с полным доступом — все).
- **`Tracker → Campaigns`** — быстрые фильтры `Owner` и `Team` в тулбаре: кампании выбранных владельцев или владельцев из команды; сужают и строки, и итоги.

Чьи кампании вообще попадают в вашу статистику, решает доступ к ним ([models/permissions-model.md](../models/permissions-model.md)).

### Архивные кампании в `Roll Up report` — переключателя нет, их трафик считается

**В `Roll Up report` фильтра или переключателя «без архивных» нет: визиты архивных кампаний входят в отчёт наравне с остальными.** Прячет архивные только `Tracker → Campaigns`: там они скрыты по умолчанию — и из строк, и из итогов — и возвращаются тумблером `Archived` в выпадающем `N of M` тулбара ([reference/ui-common.md](../reference/ui-common.md)). Частые формулировки: «скрыть архивные кампании из статистики», «архив попадает в отчёт», «аналитика без архивных».

Нужна статистика без архивных — стройте разбивку в `Tracker → Campaigns`: раскрывайте кампании групперами (синие `►`), итоговая строка там считается только по видимым кампаниям. В `Roll Up report` отчёт можно ограничить нужными кампаниями фильтром группера `Campaigns` в панели `Filters`.

### Поиск в Roll Up — ищет по значению первого группера, сущности — по имени

**Строка поиска в `Roll Up report` ищет в значении первого группера цепочки — и только на верхнем уровне дерева** (Enter / кнопка-лупа; без группера поиск недоступен). Обычно это подстрока без учёта регистра; что сравнивается, зависит от группера:

- лендинг, кампания, Destination — подстрока имени или `Human ID`, либо полный UUID;
- флоу и источник — подстрока имени либо полный UUID;
- рекламодатель — только UUID (или его часть): по имени такой поиск не находит;
- поле визита (`Creative`, `Sub 1`, `FB Ad Name` и другие) — само значение поля; так ищут креативы по части имени (секция ниже).

Символ `_` в строке поиска значит «любой один символ», `%` — «любые символы»: `BM_lee` найдёт и `BM-lee`.

По имени находятся только сущности, которые вам видны по правам. Как ещё спрашивают: «найти кампанию по названию в Roll Up», «поиск по имени источника в отчёте».

### Как найти креативы по части имени (`T-`) — поиск по первому групперу и режим `Contains`

**Отдельного фильтра «содержит» по имени креатива нет, но подстроку в `Roll Up report` ищут два инструмента — оба без учёта регистра.** Частые формулировки: «фильтр по подстроке», «все креативы, в имени которых есть T-», «содержит в названии», «агрегация по тегу в имени креатива».

- **Строка поиска.** Поставьте первым группером поле, в котором приходит имя креатива (`Creative`, `FB Ad Name`, свой `Sub N`), и введите `T-`: останутся только строки со значением, содержащим `T-`.
- **Фильтр поля в панели `Filters`** (в `Roll Up report` — слева от таблицы). У полей категории `Fields` (без своей группы) рядом со значением есть переключатель `Equal` / `Contains` («Равно» / «Содержит»). В режиме `Contains` отчёт считается только по визитам, где поле содержит подстроку, — поэтому сузятся и строки, и итоги при любой разбивке. Берётся одно значение за раз. У полей со своей группой (`Tracking`, `Facebook`…) и у остальных фильтров сравнение только по полному значению (подсказка `Enter full value`).

### Table Settings в Roll Up — кнопка `Settings` → `Table settings`

Настройки таблицы открываются кнопкой **`Settings`** в тулбаре (пока пресет не выбран; при выбранном — на ней имя пресета) → пункт `Table settings`; в том же меню — `Reset settings`, полный сброс настроек таблицы ([reference/ui-common.md](../reference/ui-common.md)). В окне: фильтры, пометка строк как **Favorites**, скрытие / переупорядочивание колонок, сохранение пресетов, число строк на странице (`10 / 25 / 50 / 100`). Есть страницы, которые грузят весь список **одним запросом, до 1000 строк**: `Settings → Fields`, `Settings → Metrics` и общая страница `Distributions` (без выбранного типа дистрибуции — страница конкретного типа работает обычной таблицей с пагинацией). Там переключателя числа строк в окне нет и в верхней панели нет пагинации — листать нечего.

### Номер строки в таблице — считается на фронте, не идентификатор

В таблице есть колонка с порядковым номером строки. Подсказка в шапке: `Row number. Calculated on the front end — handy for naming a row while sharing your screen`. Номер считается **на фронте по текущей выдаче** — это позиция в том, что сейчас на экране, а не идентификатор записи: при смене сортировки, фильтров или страницы он у той же строки поменяется. Ссылаться на объект по нему нельзя, для этого есть `Human ID` / UUID ([reference/glossary.md](../reference/glossary.md)).

### Отчёт не строится: нужно выбрать группер

Симптом: отчёт (Roll Up / DrillDown) не строится, приходит ошибка про группировку. Причина — не выбран ни один группер. Точные сообщения:

- `Groups must be selected.` — DrillDown-отчёт запущен без единого группера.
- `Please specify group` — Tracker-таблица `Other` открыта без выбранного группера (без заданного группера таблица пустая). Панель фильтров и пресеты при этом уже доступны — их можно выставить до выбора группера; фильтр `Geo` действует и на раскрытые подгруппы.

Проверка: добавить хотя бы один группер (кнопка `+` рядом с чипами) и повторить.

### Фильтр по колонке не применяется: слишком много значений

Симптом: фильтр таблицы отбивается ошибкой про количество значений. Частые формулировки: «фильтр не применился», «слишком много значений в фильтре», «`values amount exceeded`».

Причина: в обычный фильтр колонки со списком значений можно передать не больше **100** значений. При превышении приходит ошибка `Table filter <label> values amount exceeded: <n> > 100` (где `<label>` — имя колонки, `<n>` — сколько значений пришло). Число — в [reference/limits.md](../reference/limits.md).

Проверка: сузить выбор значений в фильтре до 100 или отфильтровать другим способом (по метрике, по поиску).

## Как выгрузить таблицу в CSV и что попадает в файл

Выгрузка запускается кнопкой **`Export as CSV`** (`Экспорт в CSV`) в верхней панели таблицы: открывается панель со списком условий → `Start export` (`Начать экспорт`) → тост `Экспорт запущен — появится в уведомлениях, когда будет готов`. Файл собирается в фоне и приходит уведомлением в колокольчик.

Панель дословно перечисляет, что попадёт в файл:

- `Uses the current filters and sorting.` — берётся текущее состояние таблицы: период, фильтры, поиск, сортировка.
- `Exports a selected subset of columns (not all).` — в файл идут **видимые колонки, поддерживающие CSV, в порядке экрана**. Колонки без поддержки CSV пропускаются; колонка группировки заменяется парой UUID / Name. Если выбранные колонки вовсе не совпали с поддерживаемыми, выгружается полный CSV-набор таблицы.
- `Only the first level of the table is exported.` — подсказка панели; фактически древовидный отчёт выгружается **по всей цепочке групперов сразу**: строка на комбинацию значений всех уровней, у каждого уровня своя пара колонок `Group #N UUID` / `Group #N Name`. Раскрывать дерево на экране для этого не нужно.
- `Up to 10000 rows are exported.` — потолок строк на одну выгрузку ([reference/limits.md](../reference/limits.md)).
- `The download link is valid for 7 days.` — срок жизни ссылки на готовый файл.

Файл пишется с BOM, поэтому Excel открывает кириллицу без «кракозябр».

Считается файл по полному набору неархивных метрик тенанта, а не только по видимым колонкам — скрытые колонки экспорт не ускоряют (в отличие от экрана, где запрашиваются видимые метрики и их зависимости). Набор колонок файла выбирается отдельно по описанным выше правилам.

### Где кнопка экспорта в CSV — иконка в `Roll Up report`, пункт `Table tools` в остальных таблицах

**В `Roll Up report` (Drill Down; в MTK — вкладка `Reports`) экспорт — отдельная иконка-документ со стрелкой вниз в ряду инструментов справа от кнопки `Settings`; подпись появляется при наведении — `Export as CSV` («Экспорт в CSV»).** На остальных таблицах с выгрузкой (`Tracker → Campaigns`, `Tracker → Other`, `Conversions`, `Marketing → Campaigns`) инструменты свёрнуты в кнопку `Table tools` («Инструменты таблицы»), и экспорт — пункт `Export as CSV` в её меню с подсказкой `Download the current view as CSV with the current filters and sorting; the file arrives in the notifications bell`. Частые формулировки: «где кнопка экспорта в CSV», «как скачать отчёт», «нет выгрузки в Drill Down».

Кнопки нет совсем — у роли нет права `features.table-export` или таблица выгрузку не поддерживает (секции «На каких таблицах есть кнопка `Export as CSV`» и «Кнопки `Export as CSV` нет или выгрузка отвечает `403`» ниже).

### Колонки группировок в файле — пары `Group #N UUID` и `Group #N Name`

В CSV древовидного отчёта каждый уровень группировки выгружается **парой колонок**: `Group #1 UUID` + `Group #1 Name`, `Group #2 UUID` + `Group #2 Name` и так далее по всей цепочке групперов. Экранная колонка `Group #N` в файл не идёт — её и заменяет эта пара, чтобы в таблице были и идентификатор объекта, и его читаемое имя.

Пары идут в файл по всем уровням цепочки, даже если на экране дерево не раскрыто: строки файла — это комбинации значений всех групперов, а не только верхний уровень, который виден до клика по синей стрелке `►`. Из-за этого строк в файле обычно больше, чем на экране, и потолок `10000` достигается быстрее.

### В CSV вместо названия кампании — UUID: какие колонки выгружаются идентификаторами

**Часть колонок пишется в файл UUID-ами по устройству выгрузки — имя в таких случаях лежит в другой колонке или не выгружается вовсе.** Частые формулировки: «в экспорте UUID вместо названия кампании», «identity в CSV заменяется на uuid», «в файле нет имён».

- **`Conversions`** — колонки кампании, источника и типа конверсии в файле содержат UUID. В ERP так же выгружаются `Last Destination` и `Last Advertiser`; в MTK — `Destination`, колонки рекламодателя там нет. На экране показаны имена, но CSV-колонок с именами для этих объектов нет. Сопоставить UUID кампании с именем в ERP можно выгрузкой `Tracker → Campaigns`: там колонка `Campaign` уходит именем, а `UUID` — идентификатором.
- **`Roll Up report`** — имя уровня лежит в `Group #N Name`, в `Group #N UUID` всегда идентификатор. UUID стоит и в `Group #N Name`, если имя не нашлось: объекта нет в справочнике или имя пустое, а у Destination, рекламодателя и лендинга — ещё и когда у вас к нему нет доступа.
- **`Tracker → Other`** — колонка группировки в файл не идёт вовсе; выгружается только колонка `UUID`, если она видна (по умолчанию скрыта).
- **Включён `Unwrap tree view`** — колонок группировок в файле нет (секция «В CSV нет колонок группировок — дерево было развёрнуто»).

### В CSV нет колонок группировок — дерево было развёрнуто

Симптом: в файле одни метрики, колонок `Group #1 UUID` / `Group #1 Name` нет вовсе. Частые формулировки: «в экспорте пропали группировки», «CSV без названий строк», «непонятно, к чему цифры».

Причина: выгрузка запущена при включённой кнопке `Unwrap tree view`. В развёрнутом виде колонки группировок на экране называются иначе, чем колонки группировок в файле, и в набор колонок выгрузки не попадают — остаются одни метрики. Строки при этом те же самые: теряются именно колонки с названиями группировок.

Проверка: выключить `Unwrap tree view`, дождаться перерисовки таблицы и запустить `Export as CSV` заново — в свёрнутом дереве пары `Group #N UUID` / `Group #N Name` выгружаются по всей цепочке групперов.

### На каких таблицах есть кнопка `Export as CSV`

Выгрузка в CSV поддерживается не каждой таблицей. Кнопка есть в древовидных отчётах — `Roll Up report` (в MTK-билде тот же отчёт открывается табом `Reports`) и Tracker-секция `Other` (только ERP) — а также в `Tracker → Campaigns` (только ERP), в `Marketing → Campaigns` (список remarketing-кампаний; в MTK та же таблица — страница `Campaigns` вкладки `PWA` платного модуля `PWA + Push` — [how-to/remarketing-campaigns.md](remarketing-campaigns.md)) и в `Conversions`, причём конверсии выгружаются и в ERP, и в MTK.

На таблице визитов (`Tracker → Visits`) выгрузки в CSV нет вовсе — это частый вопрос. Нет её и на остальных Tracker-секциях (`Countries`, `Days`, `Devices`, `OS`, `Browsers`, `Day part`), на остальных страницах раздела `Marketing` (`Flows`, `Template distributions`, `Messages`, `Message templates`, `Sender providers`, `Other`) и на таблицах настроек. Запрос на экспорт такой таблицы отбивается кодом `422` и текстом `CSV export is not available for this table`. Массовая выгрузка сырых визитов и конверсий делается другим инструментом — [how-to/events-exporter.md](events-exporter.md).

Если кнопки нет на таблице, которая выгрузку поддерживает, — дело не в таблице, а в отсутствующем праве `features.table-export` ([models/permissions-model.md](../models/permissions-model.md)).

### Файл из уведомления не скачивается — ссылка устарела

Скачивание из колокольчика идёт кусками, поэтому на кнопке `Download CSV` во время загрузки показывается прогресс (`Download CSV · 42%`, а если размер файла заранее неизвестен — сколько мегабайт уже скачано), а сама кнопка на это время заблокирована — это штатная работа, а не зависание.

Ссылке больше 7 дней → скачивание падает с сообщением `The download link has expired — run the export again`. Лечится повторным запуском экспорта: старая нотификация не оживёт, ссылку не продлить. Любой другой сбой скачивания даёт `Download failed` — повторить попытку, при устойчивом повторе написать в чат поддержки. Срок жизни ссылки — [reference/limits.md](../reference/limits.md).

## CSV-экспорт таблицы обрезался / выгрузка неполная

Симптом: таблица аналитики выгружена в CSV, а в файле меньше строк, чем в отчёте. Частые формулировки: «CSV из таблицы обрезался», «выгрузка неполная», «не все строки в экспорте», «пропали строки в CSV».

Причина: in-table CSV-экспорт таблицы аналитики ограничен **10000 строками**. При достижении этого числа в готовой нотификации приходят `truncated:true`, `rows_total` (число строк в файле) и предупреждение `Row limit reached — some rows were not included`. Предупреждение появляется и при ровно 10000 строках в отчёте; общего числа строк сверх лимита нотификация не сообщает. Это потолок именно табличного экспорта, не отчёта. Число — в [reference/limits.md](../reference/limits.md).

Не путать с двумя другими выгрузками:

- **Events Exporter** — массовый экспорт сырых событий (сотни млн строк, окно по умолчанию до 31 дня). Большие выгрузки делаются им → [how-to/events-exporter.md](events-exporter.md).
- **Pivot Report API** — программный доступ к сгруппированным данным без постраничной выдачи (см. [reference/glossary.md](../reference/glossary.md)).

### Статус CSV-экспорта: running / ready / failed

Экспорт таблицы асинхронный: жмёшь выгрузку — job уходит в фон, а прогресс приходит нотификацией. Три статуса в заголовке нотификации: `CSV export running` (стартовал, идёт), `CSV export ready` (готов, в payload — `file_url` со ссылкой на файл, `rows_total`, `truncated`), `CSV export failed` (упал).

При падении в нотификацию попадает абстрактный `Something went wrong during export` — реальная причина туда не пишется (уходит во внутренний трейс). Если в нотификации `CSV export failed` без деталей — это ожидаемо, конкретику разбирает команда AIO.

Ссылка на готовый файл живёт **7 дней**, после чего экспорт нужно запустить заново — [reference/limits.md](../reference/limits.md).

### Кнопки `Export as CSV` нет или выгрузка отвечает `403` — нет права на экспорт

Выгрузка гейтится **отдельным правом** `features.table-export`, и без него кнопки `Export as CSV` в таблице просто не видно: интерфейс её скрывает, а не показывает и отбивает отказом. Данные на экране при этом видны — право читать таблицу и право забрать её файлом разные.

Если запрос всё же уходит (например, из давно открытой вкладки), ответ — `403` с текстом `Table export is not allowed for your role`. Как право подписано в матрице `Settings → Positions`, кто проходит без него и как его выдать — [models/permissions-model.md](../models/permissions-model.md).

### Meta-метрики в CSV — одно число с выбранным уровнем атрибуции, без out-of-scope

Meta-метрики (`Meta Spend`, Impressions и т.п.) внутри несут не одно значение, а разбор: привязанное значение, orphans (нераспределённый спенд) и out-of-scope. В CSV такая колонка выгружается **одним числом — `Total` (привязанное + orphans)**; out-of-scope в файл не попадает, даже если на экране в футере включён показ `Total + out of scope`. Выбранный уровень атрибуции передаётся в выгрузку: при `Adset` / `Ad` файл использует тот же уровень, что таблица; разрез или фильтр по Meta-сущности задаёт свой уровень в обоих случаях. Значок статуса аллокации и сам разбор суммы в файл не идут. Что такое orphans и out-of-scope и почему спенд не привязался к строке — [mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md).

## Значения пользовательских полей видно колонками в таблицах визитов и конверсий

В таблицах визитов и конверсий каждое пользовательское поле показывается своей колонкой. В `Visits` (ERP и MTK) выводятся поля типов `Visit`, `Source`, `Campaign`, `Landing`, `Destination`; в `Conversions` (ERP и MTK) — те же плюс `Conversion`. Поля типа `Conversion` берут значение с самой конверсии, все остальные типы — с визита, к которому относится строка: поэтому значение, дописанное на лендинге или на `Destination`, видно и в строке конверсии.

В CSV-выгрузку таблицы конверсий колонка поля попадает, если она видна на экране; таблица визитов CSV не поддерживает. Общие правила выбора колонок — в секции про CSV выше. Архивные поля колонок не дают вовсе. Как поле заводится и какая сущность в него пишет — [how-to/user-fields.md](user-fields.md) и [models/visit-field.md](../models/visit-field.md).

## Roll Up по полям антифрода

Поля антифрода — обычные поля визита: `fraud_score` и `triggered_rules` встают в отчёт групперами `Fraud Score` и `Triggered Rules` (категория `Filter`), как любое поле с включённым `Availability as grouper` в `Settings → Fields` ([how-to/custom-fields.md](custom-fields.md)). В шаблонах Finance / Nutra / Sweeps (ERP и MTK) оба поля засеяны с доступностью `Analytics` и `Tables`, включать их отдельно не нужно; в шаблонах iGaming этих полей нет, как и записи `AIO Antifraud`. Дерево раскрывается синими стрелками `►` или разворачивается целиком кнопкой `Unwrap tree view`.

## Как считаются `CPM $`, `[Meta] CTR %`, `CPL $` и почему они расходятся с кабинетом Meta

**`CPM $`, `[Meta] CTR %` и `CPL $` в Tracker / Roll Up — формулы тенанта: у Meta AIO забирает расход, показы, клики и счётчики событий кабинета (лиды, покупки, регистрации), а CPM, CTR, CPC и CPL считает сам.** Ниже — формулы из шаблонов тенанта; в тенанте их могли переименовать или поменять (в ERP точное определение — колонка `Definition` в `Settings → Metrics`, [models/metric.md](../models/metric.md)). Во всех шаблонах расход — `Total Costs $` = `Meta Spend + Costs $`: спенд Meta плюс косты, записанные в визиты ([how-to/campaigns.md](campaigns.md)).

### `CPM $` — стоимость 1000 визитов, а не 1000 показов, поэтому выше, чем в Facebook

**В шаблонах `CPM $` = `Total Costs $ / Visits * 1000` — расход на 1000 визитов AIO.** CPM в Facebook — расход на 1000 показов, а показов обычно в разы больше, чем визитов, поэтому `CPM $` в AIO выше. Частые формулировки: «как считается CPM», «CPM в трекере намного выше, чем в ФБ».

CPM по показам дают скрытая по умолчанию метрика ERP-шаблонов `[Meta] CPM $` = `Meta Spend / [Meta] Impressions * 1000` и родная колонка `CPM $` на вкладках раздела `Meta` (подсказка `Cost per 1000 impressions`). Обе берут расход с комиссией поставщика, если соцпрофиль к нему привязан, иначе с комиссией самого соцпрофиля ([mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md)); положительная комиссия увеличивает расход и CPM. Соседние формулы шаблонов тоже считают на визит: `RPM $` = `Revenue $ / Visits * 1000`, а в Finance / Sweeps — `CPC $` = `Total Costs $ / Visits`.

### `[Meta] CTR %` и «Meta CTR» — считает AIO по формуле

**В ERP-шаблонах `[Meta] CTR %` = `[Meta] Clicks / [Meta] Impressions` — формула над выгруженными кликами и показами.** `[Meta] Clicks` построена на источнике `Meta Inline Link Clicks`, в который AIO пишет исходящие клики Meta (`outbound_clicks`); `[Meta] Impressions` — показы. Так же считаются родная колонка `CTR %` на вкладках `Meta` (подсказка `Clicks / impressions %`) и условие `Meta CTR` в автоправилах ([mechanics/auto-rules-engine.md](../mechanics/auto-rules-engine.md)). Частые формулировки: «Meta CTR тянется из API или считается формулой», «CTR не как в кабинете».

В MTK-шаблонах `[Meta]`-метрик нет. Метрику с именем `Meta CTR` или `[Meta] Meta CTR` шаблоны не создают — если она у вас есть, её завели в тенанте, и из чего она собрана, видно в её `Definition`.

### `CPL $` показывает `$0.00`, хотя лиды и расходы есть

**В шаблонах `CPL $` = `Total Costs $ / Leads`, а деление на ноль формула превращает в 0 — `$0.00` значит, что в этой строке ноль в числителе или в знаменателе.** `N/A` вместо суммы — значения нет вовсе. Частые формулировки: «CPL не считается», «CPL пустой», «CPL 0 при лидах и расходах».

- **`Leads` считает только тип конверсии `Lead`.** Лиды приходят другим типом — `Leads` = 0. В шаблонах iGaming `CPL $` нет: стоимость там считают по регистрациям и установкам (`CPR $`, `CPI $`).
- **Расход в `Out of scope`.** Эта часть `Meta Spend` в формулы не попадает; `orphans` в расчёт входят ([mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md), «Meta Spend пустой / не матчится»).
- **Вы на вкладке `Meta`.** Там трекерные формулы, зависящие от Meta-метрик (`Total Costs $`, `CPL $`, `Profit $`, `ROI %`), не считаются — в строках 0. Родная колонка `CPL $` там — расход кабинета на лиды по событию Meta `lead`, а не по конверсиям AIO.
- **Своя формула.** CPL, который делит только `Costs $`, при расходе через `Meta Spend` получает ноль в числителе.
- **Слагаемое заархивировано** — архивная метрика в расчёт не берётся и считается нулём ([models/metric.md](../models/metric.md)).

### `Profit $` и `ROI %` — от `Total Costs $`; метрика «считает от Costs, а не от Meta Spend»

**В шаблонах `Profit $` = `Revenue $ − Total Costs $`, `ROI %` = `Profit $ / Total Costs $`, а `Total Costs $` = `Meta Spend + Costs $` — спенд Meta в них уже входит.** Если метрика считается только от `Costs $` (своя стоимостная метрика вроде `LP Visits $` или `ROI %` в старом виде), при расходе через `Meta Spend` она покажет ноль расхода или завышенный профит — это её формула, а не расчёт AIO. Частые формулировки: «почему ROI без спенда Meta», «метрика берёт Costs, а не Meta Spend».

Из чего собрана метрика, видно в её `Definition`; в ERP — колонка `Definition` в `Settings → Metrics`, там же формулу правят: `Costs $` заменяют на `Total Costs $` ([models/metric.md](../models/metric.md)).

## Где Roll Up report в MTK-интерфейсе

В MTK-билде Roll Up report открывается через топ-таб **`Reports`** (`/app/mtk/analytics/dd`), а не через группу `Analytics → Roll Up`. Это единственный аналитический отчёт MTK: остальные отчёты вкладки Analytics (Cohorts, Comparative analytics) в MTK отсутствуют.

## Что есть в разделе Analytics — подсекции-билдеры (`/app/analytics`)

### Roll Up report — древовидный drill-down отчёт (`/analytics/dd`)

Групперы (`+` → каталог) + панель `Filters` слева + синие `►`. Каталог — тот же, что в Tracker-таблицах (см. «Каталог групперов» выше): системные категории Funnel / Tracker / Location / Landings / Destinations / Variants / Client / Device / OS / Time / Browser / Other плюс семь `RMK`-категорий по рассылкам (см. «Групперы по рассылкам» выше).

> В каталоге есть и динамические per-tenant категории — **`Fields`** и категории из атрибута `Group` кастомных полей с `Availability as grouper: Tables`, включая **`Facebook`** / **`Google`**. Подключение интеграции для категорий полей не требуется (см. блок про динамический per-tenant каталог выше + [how-to/custom-fields.md](custom-fields.md)).

### Cohorts report — когортный анализ (`/analytics/cohorts-report`)

Отчёт-«лесенка»: строки — когорты по датам, столбцы — прожитые периоды. Задаётся тремя селекторами когорты в тулбаре + режимами отображения справа + сайдбаром фильтров слева. Концепт (что такое когорта, зачем) — [reference/glossary.md](../reference/glossary.md) → Cohorts Report.

#### Три селектора когорты (слева в тулбаре)

- **`Size`** — размерная метрика когорты, отдельная колонка базы строки. Список исключает trash-метрики и формулы с trash-зависимостями, циклом или неизвестной зависимостью; дефолт подбирается по имени — `Visits`, иначе `LP Visits`, иначе первая в списке (`Visits` есть во всех семи шаблонах тенанта).
- **`Target`** — целевая (событийная) метрика, чью динамику по периодам смотрим. Список сужен до событийных метрик и формул над ними. Денежная метрика шаблона называется `Revenue $`, а не `Revenue`, поэтому с засеянным набором дефолт — счётчик целевого действия (Finance, iGaming) или `Leads` (Nutra, Sweeps).

- **`Unit`** — шаг периода: `day` / `week` / `month`.

В выпадающих списках есть поиск; короткий список может отображаться кнопками. Смена любого селектора перезапрашивает данные.

#### Cohort не строится: ошибка про Size / Target метрику

Симптом: когортный отчёт не открывается, приходит ошибка 500 про выбранную метрику. Проверка пригодности метрик выдаёт следующие сообщения:

- `Size metric is not available (trash metric, or a formula depending on one)` — в селектор `Size` попала trash-метрика (или формула, зависящая от trash-метрики). Выбрать в `Size` обычную метрику (`Visits` / `LP Visits`).
- `Target metric must be an event-based metric (conversions / payout / revenue / passed) or a formula over them` — в `Target` попала не-событийная метрика. `Target` принимает только событийные метрики (conversions / payout / revenue / passed) или формулу над ними.

Проверка: сменить проблемный селектор на подходящую метрику из подсказки в тексте ошибки.

#### Режимы отображения (справа, кнопки-группы)

- **Режим значения** — `Rate` (доля Target от суммы Target в строке при `By row` или во всей сетке при `Total`) / `Value` (абсолютное значение в ячейке).
- **Цветовая схема** — тепловая карта: `Single` (моно-градиент), `Gradient` (negative→warning→positive), `Positive` (один positive-тон по насыщенности).
- **База нормализации** — `By row` (внутри строки-когорты) / `Total` (по всей сетке).
- **`Skip +0`** — тогл-кнопка: исключить период +0 из нормализации цвета. В ячейке +0 — значение `Target` за период создания визита; `Size` стоит отдельной колонкой. Rate при этом не меняется, только раскраска.

Плюс date-range пресеты (`Last month` / `Last week` / `This week` / `This month`), выбор дат и refresh.

#### Сайдбар фильтров (слева, свёрнут по умолчанию)

Фильтры по значениям групперов и полей (та же панель `Table settings → Filters`, что в таблицах) — сужают выборку визитов и событий, например по кампании или лендингу.

### Почему нет Comparative analytics в меню Analytics

**`Comparative analytics` отсутствует в меню Analytics.** Для группировки данных за выбранный период используйте `Roll Up report`, для динамики событий по когортам — `Cohorts report`.

### Live Pulse — живой поток событий трафика (`/analytics/live-pulse`)

`Live Pulse` (`/app/analytics/live-pulse`, право `analytics.live-pulse`, только ERP) — экран живого потока событий трафика: `init` (визит зарегистрирован), `handle` (дискретное событие флоу — submit формы или клик по handle-ссылке), `conversion` (создана конверсия). Счётчики копятся только пока страница открыта и обнуляются при перезагрузке, поэтому **сверять цифры Live Pulse с отчётами и таблицами нельзя** — это не отчёт. Полностью — [how-to/live-pulse.md](live-pulse.md).

### Session Analytics — записи сессий и сравнение карт лэндов (`/analytics/session-analytics`)

`Session Analytics` (`/app/analytics/session-analytics`, право `analytics.session-analytics`, только ERP) — записи сессий с плеером плюс сравнение scroll- и click-карт до трёх лэндов рядом. Частые формулировки: «где посмотреть запись сессии», «тепловая карта лэнда», «куда кликают», «докуда доскроллили», «сравнить два лэнда по карте». Полностью — [how-to/session-analytics.md](session-analytics.md).

### Settings → Metrics — кастомные метрики (что можно считать в отчётах)

Метрики (числовые показатели в колонках Roll Up / Cohorts) — **настраиваемые** в `Settings → Metrics → + Metric`. Четыре типа: `Conversions count` (число конверсий), `Remarketing count` (события рассылок — `Sent` / `Failed` / `Delivered` / `Opened` по выбранным каналам), `Computable metric` (формула), `Data feed metric` (фид событий; денежные суммы = источник `Conversions By Type Revenue`/`Payout`) — концепт, поля форм и `Flag`-enum в [models/metric.md](../models/metric.md). Колонки списка метрик: `Metric`, `Definition` (из чего метрика собрана — формула или источник с аргументами), `Access Type`, `Owner`, `Visible`, `Created`; остальные включаются в настройке колонок. Что показывает `Definition` и чем отличаются два вида списка (`Groups` / `Order`) — [models/metric.md](../models/metric.md). Набор доступных метрик в аналитике **per-tenant**: готового системного набора метрик-колонок у AIO нет — стартовые метрики приезжают из шаблона тенанта: общие для всех вертикалей (`Visits`, `Trash Visits`, `Revenue $`, `Costs $`, `Profit $`, `ROI %`, `CPM $`, `RPM $`, `Meta Spend`…) плюс воронка своей вертикали (`Leads` и `CR %` у Finance, Nutra и Sweeps; `Registrations` у Sweeps и iGaming; `Installs` у iGaming), а дальше добавляются заведённые вручную ([models/metric.md](../models/metric.md), [context/architecture.md](../context/architecture.md)).

## Tracker data-секции (Countries / Day part / Devices / Days / OS / Browsers / Other)

В ERP Tracker-табе есть **7 data-секций** для просмотра деталей Visits в табличном виде, независимо друг от друга: **Countries, Day part, Devices, Days, OS, Browsers, Other**. Каждая сегментирует Visits/Conversions по заданному критерию.

Интерфейс — как у прочих Tracker-таблиц: кнопка-иконка hide-empty без подписи (тултип начинается с `Hide empty columns`; прячет строки без трафика) и тоггл `Attribute by events time` (атрибуция по времени события), настройки таблицы через кнопку `Settings` → `Table settings` (колонки, порядок, пресеты, 10/25/50/100 строк — [reference/ui-common.md](../reference/ui-common.md)), date-range. Поиск работает в `Countries`, `Devices`, `OS`, `Browsers` и `Other`; его условия зависят от группера. В `Days` и `Day part` строка поиска выборку не фильтрует.

### Дефолтный grouper и переключение секции

Каждая секция (кроме `Other`) применяет свой group-критерий по умолчанию: `Country` для Countries, `Day` для Days и т.д. Групперы — в левом верхнем углу, меню раскрывается кликом по имени группера. Смена первого группера в этих data-секциях **не переключает страницу**: выбранный разрез применяется к текущей таблице. `Other` без заданного группера показывает пустую таблицу; группер можно выбрать вручную или получить из пресета либо параметра перехода.

### Не вижу групперы Facebook в каталоге

Категория полей `Facebook` появляется в Tracker-каталоге, если у тенанта есть поля этой группы с `Availability as grouper: Tables`, например `FB Ad Name`. Она не требует подключённой интеграции с Meta и находится в общем вертикальном списке — можно долистать или найти поле по имени. Системный группер `Ads` с алиасом `крео` находится в каталоге раздела `Meta`, а не Tracker / Roll Up ([how-to/meta-ads.md](meta-ads.md)).

Частые формулировки: «FB-групперы скрыты по дефолту», «не вижу групперы Facebook», «где разбивка по FB», «по названию креатива», «крео», «creo», «fb ad name».

Каталог в Tracker data-секциях тот же, что в Roll Up report, вместе с блоком избранного — как он устроен, в секции «Избранные групперы — блок `Favorites` и режим управления».

### Action Menu Tracker data-секции

**Action Menu** (ПКМ по строке): `Freeze top` / `Freeze bottom` закрепляют строку вверху/внизу; обратно — `UnFreeze top` / `UnFreeze bottom`. В `Countries`, `Day part`, `Devices`, `Days`, `OS`, `Browsers` при праве `analytics.roll-up-report` также есть `Build Roll Up report` — открывает Roll Up с фильтром по выбранной строке. В `Other` этого пункта нет.

> Каталог групперов здесь — тот же динамический per-tenant каталог, что и в Roll Up report (см. «Древовидный отчёт через Groupers» выше).
