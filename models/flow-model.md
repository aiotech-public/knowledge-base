# Flow Model AIO

Flow в AIO — это визуальный конструктор пути визита от Source до Destination. Состоит из States (шагов) и Transitions (переходов между ними). Типов флоу три: `Campaigns` (он же `Campaign Flow` — полный путь Source → Destination), `SubFlow` (вставной переиспользуемый кусок) и `Notifications` (флоу рассылок). Конкретные процедуры построения — в [how-to/flow-editor.md](../how-to/flow-editor.md).

## Что такое Flow в AIO

Flow — это набор связанных State'ов, описывающий путь визита от клика на ссылку источника (Source) до конечной интеграции (Destination).

Один **Tenant** содержит **несколько Flow** (обычно из шаблона). Каждый Flow может быть переиспользован в **нескольких Campaign** — подробнее о сущности Campaign и наследовании настроек: [models/campaign.md](campaign.md).

## Какие бывают Flow States (типы нод/шагов)

Transitions — стрелки между States. Палитра Flow Editor («Nodes to create») содержит 14 типов нод (+ `Start` авто, итого 15 нод).

### Start — точка начала Flow

Автоматически добавляется при создании Flow. Точка начала.

### Source — точка входа визита

Точка входа визита в Flow. **Обязателен для Campaign Flow.** Один `Source` на Flow.

### Content — показ контента визиту

Шаг, который показывает визиту контент: лэнд (Preland/Offer/White), редирект, reflect, 404.

Атрибуты Content:
- **Lander Type** — `Preland` / `Offer` / `White`. Можно выбрать несколько (например, шаг может принять и Preland, и Offer — на разные ситуации).
- **Payload Type** — что именно делает шаг:
  - `Landing` — показ ZIP-лэнда или PWA.
  - `HTML` — inline-HTML, пишется прямо в Code Editor на уровне кампании в настройках шага (не требует заливки лэнда). Удобно для простых вайтов / 404-замен / временных страниц.
  - `Redirect` — переход на стороннюю ссылку. Как thank-you шаг **после API-push** redirect не работает: после пуша визит остаётся на месте и не редиректится. Если нужен переход после пуша — ставь `Destination`, а не `Redirect`.
  - `Reflect` / `Proxy-reflector` — показ внешнего сайта как контента шага; как это устроено.
  - `Skip` — пропуск шага (например, чтобы из 2-step сделать 1-step).
  - `404` — дефолт, если шаг не выбран.

В Content-шаге можно добавить **дополнительный вариант** для вайта с `Payload Type: Campaign Content Distribution` — тогда для новых кампаний вайт берётся из дистрибуции, но байер может выбрать статичный вручную (компромисс).

Как ещё называют `White`-лэнд: «вайты», «сплит вайтов» (тест нескольких вайт-вариантов).

### Destination — конечная интеграция

Конечная интеграция, куда пушится лид (рекламодатель, партнёрка, CRM). **Обязателен для Campaign Flow.**

Атрибуты: выбор Destination из таблицы доступных, `Info message`, тумблер `Collapsed by default` в `Visual settings` (сохраняется, но на вид карточки в `Edit Campaign` не влияет — секция «Другие настройки State»).

### Domain Change — смена домена внутри флоу

Смена домена внутри Campaign Flow с **трекингового** на **публичный** (и обратно при необходимости). Механика: до шага `Filter` визит идёт на трекинговом домене (тот, что стоит в рекламной ссылке), после фильтра прошедший трафик уходит на публичный домен, под которым открывается лэнд. Разбор трекингового и публичного доменов и `Replace Domain` — [models/domain.md](domain.md).

**Settings Availability:** у `Domain Change`, как у других шагов, есть `Settings Availability` — домен настраивается per-campaign либо во Flow (`Flow Only`). При `Flow Only` домен один для всех кампаний этого флоу — это общее поведение `Flow Only`, не особенность Domain Change.

### Fill Fields — заполнение полей визита (серверный шаг)

Заполнение полей визита по правилам или из Content Library. **Невидим визиту** — это серверный шаг.

Атрибуты:
- **Fields** — какие поля визита заполнять.
- **Placeholder Group** — группа плейсхолдеров (если нужна).
- **Payload Type** — `Fill Text` (статичный текст) или `Fill Content` (из Content Library).
- **Compact/Control toggle** — режим настройки правил.

Источник правил: либо вручную (`add condition`), либо из `Fields by Distribution` (см. [models/distributions-model.md](distributions-model.md)).

### Filter — Traffic Filter

Шаг фильтрации трафика: для каждого визита даёт `Passed` или `Rejected` и по этим веткам ведёт его дальше по флоу. Какой фильтр стоит на шаге и по каким правилам он отбирает трафик — сущность Filter и её параметры разобраны, каталог подключаемых фильтров —.

### SubFlow-нода — вставка переиспользуемого блока

Вставка ранее созданного `SubFlow` в Campaign Flow. SubFlow **не работает самостоятельно** — только как вставка.

Типичный use case: централизованное `Fill Fields` для нескольких Campaign Flow (например, `buyer_utm` назначается через один SubFlow, переиспользуемый везде через `Buyer UTM Distribution`).

### Finish — конец SubFlow

Конец SubFlow. Маркер «вернись в основной Campaign Flow». Транзишены **только входят** в Finish, никаких исходящих.

### Дополнительные ноды редактора

Палитра Flow Editor («Nodes to create») содержит, помимо разобранных выше, ещё несколько типов нод (серверные шаги, видны при `Edit flow`):

- **Fill form** — подключает SDK-форму на шаге (на канвасе — нода «Choose Form / Select form»); связан с `Settings → Forms` и `{{form}}`. См. [how-to/forms.md](../how-to/forms.md), [models/form.md](form.md).
- **Fields by distribution** — заполняет поля визита из **дерева Distribution** (вариант Fill Fields, где значения берёт Distribution). На канвасе — «Fill Buyer UTM», «Offer Name Distribution» (подпись «Use trees to fill fields»). См. [models/distributions-model.md](distributions-model.md).
- **Condition** — ветвление по условию на поля визита (без показа контента); тогглом `Trash when Rejected` (по умолчанию выключен) умеет ещё и помечать отклонённый визит как trash.
- **Spawn conversion** — порождает конверсию на шаге флоу. См. [models/conversion-model.md](conversion-model.md).
- **Field Verification** — шаг проверки/валидации поля визита (в handler-типах UI подписан `Phone Verification`; ветки `passed` / `rejected`).
- **Notifications flow** — сеет визит во флоу рассылки (тип `Notifications`) прямо из кампанийного флоу. Это кастомный путь: штатно рассылку запускает ремаркетинг-кампания ([how-to/remarketing-campaigns.md](../how-to/remarketing-campaigns.md)). См. [mechanics/notifications-flow.md](../mechanics/notifications-flow.md), [models/marketing-flow.md](marketing-flow.md).

`Edit Offer Name` — не отдельная нода палитры, а вариант шага `Fill fields` с конкретным полем (Offer Name), группой плейсхолдеров (`Offer Names`) и payload type `Fill Content`. Про варианты `Fill fields` из дистрибуций — [models/distributions-model.md](distributions-model.md).

### Сам редактор флоу — панели и действия над флоу

`Edit flow` из контекст-меню флоу открывает редактор: слева панель **Flow details** (Name, Description, Tags, тумблер «Show archived states»), секция `User fields` и палитра **Nodes to create**; справа — канвас на точечной сетке, схема раскладывается **сверху вниз** (`Start` наверху), транзишены подписаны (на ветках `Filter` — `passed` / `rejected`). Нижний тулбар канваса: зум `+` / `−` / **fit** / lock / **`Re-sort`** (авто-раскладка). Плитки палитры окрашены по смысловой группе шага — структура, контент, работа с полями и конверсиями, ветвление, отправка сообщений, тайминг рассылок; описание шага показывается в тултипе плитки. Действия над флоу (правый клик по строке): `Edit flow`, `View flow`, `Copy flow`, `Change ownership`, `Share`, `Archive`.

В редакторе граф показывается целиком, без сворачивания цепочек — сворачивание и легенда есть только в просмотре (`View flow`, секция «`View flow` — просмотр схемы: полный экран, свёрнутые цепочки, легенда»). Как открыть настройки ноды и как её двигать — секция «Нода на канвасе: клик открывает настройки, двигать — за drag-хендл».

### Нода на канвасе: клик открывает настройки, двигать — за drag-хендл

**Нода в `Edit flow` — одна строка «цветная левая граница + иконка типа + имя» (если имени нет — подпись типа), под ней описание серым; клик по любому месту ноды открывает модалку её настроек, а перетаскивание работает только за drag-хендл** — крестик из четырёх стрелок слева в строке ноды. Иконка-шестерёнка справа в строке — просто значок: клик по ней открывает ту же модалку, что и клик по имени. Модалку не открывают только клики по портам транзишенов и по самому drag-хендлу; `Enter` на выделенной ноде открывает её так же, как клик.

Симптом «нода не двигается, вместо этого открывается окно настроек» — это норма: тянуть надо за крестик, а не за тело ноды. Хендл рисуется только когда флоу редактируемый; в `View flow` ноды не двигаются и модалка не открывается.

Что внутри модалки и почему кнопка `Apply settings` не сохраняет флоу — секция «Модалка настроек ноды — `Apply settings` закрывает окно, флоу сохраняет `Save`».

### `View flow` — просмотр схемы: полный экран, свёрнутые цепочки, легенда

**`View flow` (контекст-меню флоу; та же схема открывается кнопкой `Flow preview` — иконка глаза рядом с выбранным флоу в карточке кампании) показывает флоу на весь экран, сверху вниз, без редактирования.** Линейные участки графа — цепочки шагов, у каждого из которых один вход и один выход, — свёрнуты в одну ноду со списком шагов: клик по ней разворачивает цепочку, повторный клик сворачивает обратно. Правила сворачивания: сворачивание включается, когда во флоу 10 и больше нод (короткие флоу показываются целиком); пара `Start` → `Source` сворачивается всегда; шаг `Filter` не сворачивается никогда и рвёт цепочку с обеих сторон; переходы `handle` / `start` / `arrived` внутри свёрнутой ноды не подписываются.

Внизу — легенда «иконка + цвет → тип шага», собранная по фактическому составу схемы; служебные `Start`, `Source` и `Sub flow` в неё не попадают. Ту же свёрнутую схему показывает превью в окне выбора флоу при создании кампании.

### Как флоу раздаёт поля своим кампаниям — секция `User fields` в редакторе

Поля визита, которые `Flow` передаёт своим кампаниям, выбираются в левой панели редактора — группа `User fields` между `Flow details` и палитрой `Nodes to create`. Кнопка `Add field` добавляет поле в список, у каждой строки переключается режим.

Режимов три: `Flow only` — значение задаётся только во флоу; `Campaign template` — флоу даёт заготовку, а кампания её правит; `Campaign only` — поле объявляется во флоу, а значение вводится уже в кампании. Пул полей здесь тот же, что у карточки кампании, — поля с `Type = Campaign`. Полная механика режимов, наследования строк и подстановки заготовки — [how-to/user-fields.md](../how-to/user-fields.md).

Лейблы режимов совпадают с `Settings availability` шага дословно (`Flow only` / `Campaign template` / `Campaign only`), но это разные настройки: `Settings availability` решает, где настраивается сам шаг флоу (секция «State Settings (на уровне Flow vs Campaign)»), а режим в `User fields` — где задаётся значение поля визита.

## Какие бывают Flow Transitions (переходы между States)

Transitions — стрелки между States. Каждая стрелка имеет тип, который определяет, **когда визит идёт по этому переходу**.

### Arrived — начало пути визита

Единственный transition из `Source`. Начало пути визита.

### Handle — базовый переход по умолчанию

Базовый transition между States. Используется по умолчанию, если других условий нет.

### Handle-form — переход при submit формы

Срабатывает только при **submit формы** на текущем шаге. Используется когда лэнд имеет несколько путей (форма vs ссылка).

### Handle form N — нумерованные переходы при нескольких формах

Когда на одном лэнде несколько форм через `{{form:1}}`, `{{form:2}}` … (до 5), каждая триггерит свой нумерованный transition: `Handle form 1`, `Handle form 2`, 3, 4, 5 — по номеру засабмиченной формы (машинные слаги переходов — `handle-form-1` … `handle-form-5`). Базовый `handle-form` (UI-лейбл `Handle All Forms`) — общий переход на submit любой формы шага: это не отдельная сущность, а тот же `handle-form`, что описан выше как `Handle-form`. Паттерн зеркалит нумерованные `{{link:N}}` → `Handle-link`-переходы (`handle-link-1` … `handle-link-5`, базовый — `handle-link`). Выбор формы (нода `Fill form` vs Content-шаг) работает так же, как с ссылками. Про сами плейсхолдеры форм — [reference/placeholders.md](../reference/placeholders.md), [models/form.md](form.md).

### Handle-link — переход при клике на `{{link}}`

Срабатывает при клике на `{{link}}` (или другую переходную ссылку) на текущем шаге.

**Пример use case:** на Preland есть и форма (для тех, кто готов оставить контакты) и кнопка «Узнать больше» (для тех, кто хочет на оффер). `Handle-form` ведёт на Destination, `Handle-link` — на Offer.

### Destination-rejected — возврат при отклонении лида

**Обратный** transition (машинный слаг — `destination-rejected`): если Destination отклонил визит — визит возвращается на предыдущий State (обычно — Offer). Улучшает аналитику (видно, сколько лидов отклонено) и позволяет показать визиту fallback-страницу.

Возврат на предыдущий Content-шаг происходит и без нарисованного `Destination-rejected`. Flow держит внутренний **history-стек только из Content-шагов**: при заходе на каждый Content-шаг его позиция кладётся в стек. Когда Destination отклонил визит или переполнил капу и на шаге НЕ нарисован ни `destination-rejected`, ни `destination-interacted`, ни `destination-full`, — визит всё равно откатывается на вершину этого стека (предыдущий Content) через внутренний переход `state-back-content` (history-pop). Поэтому визит после reject почти всегда оказывается на прошлом лэнде, даже если байер не рисовал явную ветку. `Destination-rejected` — это явная, видимая в аналитике версия того же возврата. Это **не** SDK-`Backfix` (браузерная кнопка «Назад» на преленде) — механизм чисто серверный.

### Destination-pushed — переход после успешного пуша

Прямой transition после успешного пуша (машинный слаг — `destination-pushed`). Позволяет визиту пройти через несколько Destination'ов подряд (например, `PWA → Destination`). Используется для трекинга полного пути визита.

### Destination-interacted — переход при любом исходе пуша

Любой исход — `Pushed` или `Rejected` (машинный слаг — `destination-interacted`). Используется, когда логика после пуша одинаковая независимо от результата.

### Passed — визит прошёл Filter

После `Filter`: визит прошёл шаг и идёт дальше по основной ветке.

### Rejected — визит не прошёл Filter

После `Filter`: визит не прошёл шаг и уходит по второй ветке — куда именно, решает схема флоу.

### No payload — fallback при отсутствии подходящего варианта

Fallback (машинный слаг перехода — `no-payload`). Если у State не осталось подходящих вариантов после применения `State Rules` — визит уходит по `No payload`.

**Пример:** Content step с несколькими вариантами лэндов по правилам гео. Все правила не совпали (гео визита — например, Mongolia, лэндов под Mongolia нет) → визит идёт по `No payload` на `White`-лэнд.

### Destination Full — переход при переполнении капы

Transition шага `Destination` (машинный слаг — `destination-full`): срабатывает, когда у Destination переполнена капа (`Daily` / `Infinity` лимит). Визиты, не поместившиеся в капу, уходят в fallback — другой `Destination` или дистрибуцию. Капа считается **в момент открытия Destination**, не в момент захода визита. Как настроить fallback — [how-to/flow-editor.md](../how-to/flow-editor.md) (раздел «Fallback при переполнении капы»).

## Типы флоу: Campaign Flow, SubFlow и Notifications

Тип флоу определяет, как оно может использоваться в системе. Общий список флоу тенанта — `Tracker → Flows`: в нём лежат все три типа, а флоу рассылок (`Notifications`) вдобавок выведены отдельным списком в разделе рассылок.

### Campaign Flow — полный путь визита

Полный путь визита. **Содержит** `Source` и `Destination`. Привязывается к Campaign при создании. Один Flow → несколько Campaign.

При создании кампании Flow выбирается из дропдауна `Select Flow` — там лежат и преднастроенные шаблоны Tenant'а, например `One Step` и `Instant Destination`.

Менять существующий `Flow`, на котором уже работают кампании, **не следует** — лучше создать новый и с какого-то момента создавать кампании на нём. Старые кампании можно перепривязать вручную, но новые шаги/лэнды для уже созданных не подтянутся.

### SubFlow — переиспользуемый вставной блок

Вставной кусок. **НЕТ** `Source` и `Destination`, есть `Start` и `Finish`. Используется как переиспользуемый блок (обычно — для `Fill Fields` логики).

SubFlow **не работает самостоятельно** — только через State `SubFlow` в Campaign Flow.

### Notifications — флоу рассылок

Третий тип флоу — `Notifications`: флоу рассылки, которое **исполняется по триггеру ремаркетинг-кампании**, а не заходом визита в кампанию. Ремаркетинг-кампания обязана ссылаться на флоу именно этого типа — без него форма не сохраняется и отдаёт `Remarketing campaign requires a Notifications flow`. Свой список таких флоу — `Marketing → Flows`: там лежат только они, и оттуда же они создаются. В общем списке `Tracker → Flows` они тоже видны.

Чем запускается рассылка (триггеры `Schedule` / `Conversion` / `Manual`, аудитория, расписание) — [how-to/remarketing-campaigns.md](../how-to/remarketing-campaigns.md); концепт модуля целиком — [models/marketing-flow.md](marketing-flow.md); ноды внутри самого флоу рассылки — [mechanics/notifications-flow.md](../mechanics/notifications-flow.md).

Есть и кастомный способ запустить такое флоу — нода `Notifications flow` внутри кампанийного флоу: она сеет в выбранный `Notifications`-подфлоу любой дошедший до неё не-трэшевый визит. Дефолтом рассылки это не является и ремаркетинг-кампанию не заменяет: у визита, посеянного нодой, нет ни аудитории кампании, ни её лимитов и метрик отправки.

### Advanced Flow и APK-шаблоны

`Advanced Flow` — готовый шаблон для PWA с разделением по платформам: после фильтра → Domain-Change → проверка Android → iOS → Desktop (отдельная ветка). Во флоу с PWA можно ставить лэнды **до** пвашки (разогреть, потом сбросить) и/или **после** (открыл пвашку → лэнд с колесом фортуны → оффер).

Для APK-запусков (Android-приложения, не PWA) — **отдельный** flow-шаблон: простой, фиксирует «открыл APK → ушёл в оффер». Внутренние `AIO Push Notifications` работают **только** для AIO-PWA, не для 3rd-party.

## State Settings (на уровне Flow vs Campaign)

Каждый State имеет настройку **Settings Availability** — где доступны его настройки:

| Значение | Доступно в Edit Flow | Доступно в Edit Campaign | Use case |
|---|---|---|---|
| `Campaign Template` | да | да | Дефолт. Flow задаёт начальные значения, Campaign может переопределить. |
| `Flow Only` | да | **нет** (опция скрыта) | Хочешь жёстко зафиксировать настройку на уровне Flow для всех Campaign. Например, всегда определённый Destination, который никому нельзя поменять. |
| `Campaign Only` | **нет** (опция скрыта) | да | Хочешь, чтобы настройка задавалась только в каждой Campaign отдельно. На уровне Flow вообще не появляется. |

**Practical:** обычно `Campaign Template` подходит. `Flow Only` — для жёсткой стандартизации. `Campaign Only` — для редко используемых, специфичных шагов.

Три значения **сосуществуют на разных шагах одного флоу** — это by design, для гибкой настройки: у одного шага `Flow Only` (одинаков для всех кампаний этого флоу), у другого `Campaign Template` (переопределяется из кампании). Приводить все шаги к одному значению не нужно — на сохранение флоу это не влияет. Единственное место, где `Settings Availability` вообще нельзя задать, — MTK: там нет редактора Flow, поэтому и настроить нечего; с тарифом или ролью юзера механика не связана.

### Другие настройки State

- **`Info message`** — синий или красный текст с подсказкой, отображается при настройке Campaign.
- **`State color`** — для визуальной организации: цвет левой границы и иконки ноды на канвасе, кружок в заголовке модалки настроек.
- **Archived** (тумблер `Archive state`) — State в архиве, не используется (требует сначала удалить все transitions к нему и от него).
- **Collapsed by default** — тумблер в `Visual settings`, который ни на что не влияет (секция «`Collapsed by default` не сворачивает карточку шага в `Edit Campaign`»).

### `Collapsed by default` не сворачивает карточку шага в `Edit Campaign`

**Тумблер `Collapsed by default` (ключ настройки стейта `is_collapsed`, блок `Visual settings`) сохраняется во флоу, но ни один экран его не читает: карточка шага в `Edit Campaign` от него свёрнутой не открывается, и на канвасе `Edit flow` он тоже ничего не меняет.** Свёрнутость карточек шагов в `Edit Campaign` задаётся только вручную — кликом по шапке карточки; выбор запоминается в браузере, а не во флоу, поэтому в другом браузере карточки снова развёрнуты. Как устроены карточки шагов в форме кампании — [how-to/campaigns.md](../how-to/campaigns.md).

Симптом «включил `Collapsed by default`, а шаг в кампании всё равно развёрнут» — это наблюдаемое поведение, а не ошибка настройки: сворачивайте карточку кликом.

## State Rules — динамика на уровне State

Часть States (`Content`, `Destination`, `Filter` с custom allowance) поддерживают **Rules** — динамические правила выбора варианта.

**Где открыть редактор правил.** В настройках шага (модалка ноды во Flow Editor или карточка шага в `Edit Campaign`) у правила без условий стоит зелёная кнопка-чип, клик по ней открывает окно **`Manage rule`**. Подпись чипа зависит от шага: у вариантов `Content` / `Destination` — **`All`**; в блоке `Custom allowance rules` шагов `Filter` и `Condition` — **`Accept everything`** (RU `Принимать всё`). У правила без условий окно начинается с экрана плиток-пресетов (секция «Пресеты правила»); полный конструктор условий `field + operator + value` — это пресет `Custom`.

**Структура правила:** Поле визита + Оператор + Значение.

**Пример (Content step с несколькими вариантами лэндов):**
- Вариант A: `Visit Country Code == "IT"` → итальянский лэнд.
- Вариант B: `Visit Country Code == "DE"` → немецкий лэнд.
- Вариант C (без правил, fallback) → английский лэнд.

Если хотя бы одно правило сработало → визит идёт по выбранному варианту. Если ни одно — `No payload`.

В `Fill Fields` State через Rules задаются условия заполнения поля.

### Пресеты правила: экран плиток вместо пустого конструктора

**Пока у правила нет ни одного условия, `Manage rule` открывается экраном плиток-пресетов** — и при создании нового правила, и при открытии сохранённого пустого («( Accept everything )»). Плитка сама подставляет плейсхолдер(ы) и жёстко фиксирует оператор `in`: в упрощённой форме остаются только значения, селекта оператора там нет вовсе.

Простые пресеты (бейдж `Simple`): `Visit Country` (`aio.visit.country_code`), `Visit Language` (`aio.visit.language_code`), `Visit Domain` (`aio.visit.domain_uuid`), `Device Name` (`aio.visit.device_name`), `OS Name` (`aio.visit.os_name`), `OS Version` (`aio.visit.os_version`), `Campaign Owner` (`aio.campaign.owner_uuid`). С бейджем `Advanced`: `Visit Country + Language`, `Visit Domain + Country` и `Custom` — прежний полный конструктор `field + operator + value`.

Плитка видна, только если все её плейсхолдеры доступны в этом контексте; `Custom` доступен всегда. Диалог общий: он же открывается из настроек кампании, из правил шага флоу, из дерева дистрибуции и из content-сплитов.

### Сохранённое правило открылось в `Custom` — почему

**В форму пресета сохранённое правило попадает, только если его условия в точности повторяют набор полей пресета И все используют оператор `in`** — иначе открывается `Custom`. Переключение пресета отбрасывает условия вне его набора, кнопка `Back` возвращает к плиткам.

Отдельной сущности на сервере у пресетов нет: на выходе получается обычное условие с оператором `in`.

### Совпало несколько вариантов — какой выберется (тай-брейк)

**Тай-брейк ВАРИАНТОВ и тай-брейк ПРАВИЛ — это два разных механизма, не путать.**

**Выбор варианта Content / Destination (стратегия `First`) — выигрывает первое совпадение сверху вниз.** Если под визит подошло несколько вариантов, берётся тот, что выше в списке; остальные не рассматриваются. Отсюда практика: более общее правило держат ниже (как fallback), более узкое — выше, иначе общее «съест» трафик до того, как дойдёт до узкого. Стратегия `First` — это ровно этот же проход сверху вниз до первого подходящего варианта.

**Несколько `Allowance Rules` на одном шаге (`Condition`, а также `Filter`) — это AND «все должны пройти», а не «первое подошедшее выигрывает».** Шаг прогоняет ВСЕ активные правила и обрывает проход на ПЕРВОМ правиле, вернувшем `false` (событие `Rejected`); совпавшее (true) правило НЕ шорткатит визит в pass. Визит проходит, только удовлетворив каждое правило. То есть больше правил — строже отбор, а не «сработает первое из списка».

Внутри одного `Allowance Rule` условия комбинируются слева-направо без группировки и без скобок, поверх стартового `true`: коннектор (`or` / `and`) самого первого условия игнорируется — оно всегда AND-ится к `true`, а дальше применяется в порядке следования. Смешанные `and` / `or` не расставляют приоритет: `A AND B OR C` считается как `((true AND A) AND B) OR C`, а не `A AND (B OR C)`. Поэтому порядок условий в правиле влияет на результат.

## Split Groups — маршрутизация цветами

Цветные метки на вариантах шагов. Когда визит на первом шаге с выбором получает «цвет» — на всех последующих шагах он попадает только в варианты с тем же цветом.

Как ещё называют: «цветовой сплит», «color split», «синий оффер», «красный оффер» (вариант шага, помеченный цветом).

### На каких шагах визит получает цвет (Split Group)

Цвет записывается визиту любой **нодой-выборщиком** — `Content`, `Fill fields`, `Fill form`, `Fields by distribution` (все шаги из «Паттерна нод-выборщиков», которые выбирают вариант). Записывается ровно один раз: первый НЕ-`Rainbow` цветной вариант, выбранный визитом БЕЗ цвета, локает цвет визита на весь остаток флоу. `Rainbow`-победитель и уже выставленный цвет не перезаписываются — визит, у которого цвет уже стоит, повторным заходом на нод-выборщик его не меняет. На остальных шагах цвет уже считывается, но не выставляется. Из этого следует:

- По дефолту визит идёт без цвета — он появляется только когда дошёл до первого нод-выборщика с цветным (не-`Rainbow`) вариантом.
- Если перед `Fill Offer Name` (или другим шагом, читающим цвет) не было ни одного нод-выборщика с цветными вариантами — на этом шаге Split Groups не сработают: визит без цвета не сматчится ни с одним цветным вариантом.
- Если в воронке вообще не дошли до нод-выборщика с цветным вариантом, а нужный шаг уже требует цвета, и нет варианта **Rainbow** — визиту покажется ошибка («нет подходящего варианта»).

### Как цвет связывает шаги воронки (пример)

- Content (Preland) — 2 варианта: «зелёный» и «синий».
- Content (Offer) — 2 варианта: «зелёный» и «синий».
- Destination — 2 варианта: «зелёный», «синий».

Если визит на Preland попал на «зелёный» — на Offer пойдёт на «зелёный», на Destination — тоже на «зелёный». Это позволяет тестировать **связку** preland-offer-destination целиком, не путая трафик.

Специальный цвет **Rainbow** принимает любые цвета (используется на Destination или там, где нужен «общий» вариант для всех групп) — а также для подстраховки, если в воронке цвет ещё не выставлен. Новым вариантам по дефолту присваивается именно `Rainbow`.

### Значения цвета (Color Group) у варианта

Варианты:

- `Rainbow` — принимает любой цвет, включая `Empty`.
- `Empty` (выставляется через `Clear Select`) — матчится **только** с другими `Empty` (в отличие от `Rainbow`, который принимает всё).
- Цветные значения (Green, Black, Blue…) — матчатся только внутри своего цвета (Green ↔ Green).

### Быстро проставить одинаковый Split Group + условие нескольким вариантам

На исходном варианте — шорткат `Copy condition & group`, затем `Paste condition & group` на остальных вариантах (только в режиме `Control`). Сброс группы и условия — иконкой корзины.

### Согласование стратегий выбора при настройке Split Groups

Цвет с первого шага не сматчится на втором, если стратегии выбора не согласованы. Первой группе ставят `Weights` или AI (рандомизированный выбор варианта для входящего визита), а второй (связанной по цвету) — `First`, чтобы алгоритм сканировал варианты сверху вниз и брал совпадающий по цвету. Про стратегии `First` / `Weights` — см. «Настройки нод — поштучно».

## Что учитывать на практике при работе с Flow

### Какой Transition сработал — главное при разборе пути визита

Понимать, какой Transition сработал, — главное при разборе, куда уехал визит. В аналитике AIO видно, по какому Transition визит ушёл: смотреть надо не на порядковый номер шага, а на сработавший переход.

### Domain Change не применяется к кампании — проверь Settings Availability

**Симптом: `Domain Change` настроили во Flow, а к кампании он не применяется.** Причина: `Domain Change` подчиняется `Settings Availability` (как другие шаги) — домен задаётся per-campaign или во Flow (`Flow Only`). Проверка: если режим шага per-campaign, домен берётся из кампании, а не из Flow — тогда правка во Flow ни на что не влияет.

### Fill Fields пуст — поле не заполнено шагом

`Fill Fields` невидим визиту, опциональный шаг: по правилам пишет в кастомные поля визита кастомные значения (вручную или через Distribution) — например, проставить `team_name` по правилу «визит из кампании определённого пользователя». Если поле, которое ДОЛЖЕН был заполнить `Fill Fields`, пусто — проверь этот шаг.

### No payload — частая причина «не туда уехал визит»

Если правила Content'а слишком узкие → визит уходит по `No payload` → fallback (White или 404). Проверять в первую очередь при «лэнд не открывается».

### Destination-rejected не настроен — отклонения теряются

`Destination-rejected` улучшает аналитику. Если он не настроен, отклонения дестинейшна теряются — стоит настроить.

### SubFlow — когда вынести логику Fill Fields из кампаний

SubFlow подходит для общей логики `Fill Fields`. Если несколько кампаний с одинаковым набором filled-полей (`buyer_utm`, AffID и т.п.) — логику стоит вынести в SubFlow.

### Лэнд под конкретный Destination — через Fill Fields до Landing

Чтобы лэнд показывал контент под конкретный Destination — Destination выбирают шагом `Fill Fields` **до** Landing, пишут в поле визита. На лэнде через `{{aio.visit.fields.<destination_uuid>}}`. Данные оффера держат в JS-мапе в макросе или в Content Library. `Content Splits` для этого **не рекомендуется**.

### UUID стейта флоу — как получить

UUID стейта флоу напрямую в UI не виден. Получить его — открыть стейт через `Edit`, нажать `Save` (даже без правок); тогда UUID появится в payload-аргументах макроса.

## Настройки нод — поштучно (`Edit flow` → клик по ноде открывает модалку)

Палитра `Nodes to create` — **14 типов** (+ `Start` авто, итого 15 нод): Finish · Source · Content · Destination · Domain change · Fill fields · Fields by distribution · Spawn conversion · Field Verification · Fill form · Filter · Condition · Sub flow · Notifications flow. Настройки каждой ноды открываются отдельной модалкой по клику на ноду (секция «Модалка настроек ноды — `Apply settings` закрывает окно, флоу сохраняет `Save`»).

**Общий каркас всех нод:** `Name` + `Description` + **`Visual settings`** (`State color` / `Collapsed by default` / `Archive state`; `Collapsed by default` ни на что не влияет — секция «`Collapsed by default` не сворачивает карточку шага в `Edit Campaign`»). У большинства «контент-производящих» нод сверху — **`Settings availability`** (`Campaign template` / `Flow only` / `Campaign only`, см. «State Settings») и блок выбора варианта со стратегией **`First` / `Weights`** + переключатель режима просмотра `Compact` / `Control`; в строке варианта — цвет (= Split Group, см. «Split Groups — маршрутизация цветами»), сама ценность, вес и тоггл **Fill First** (приоритет варианта поверх весов — [models/distributions-model.md](distributions-model.md)), кнопка `+ Add another variant`; в футере блока — счётчик `{count} variants` (RU «Вариантов: {count}») по вариантам, видимым в текущем режиме. (`Balance` — не отдельная стратегия ноды флоу, а кнопка режима `Weights` для распределения весов на Distribution / сплитах.)

### Модалка настроек ноды — `Apply settings` закрывает окно, флоу сохраняет `Save`

**Клик по ноде во Flow Editor открывает модалку настроек шага: в заголовке — имя шага (или подпись его типа, если имени нет) и кружок цвета стейта, под ним описание, внизу кнопка `Apply settings` (RU `Применить настройки`).** Форма пишет в стейт живьём — нода на канвасе обновляется по ходу правки, — поэтому `Apply settings` ничего не «применяет», а просто закрывает окно. Сам флоу при этом не сохранён: изменения уезжают на сервер только кнопкой `Save` редактора флоу. Закрыл модалку и вышел из редактора без `Save` — настройки шага потеряны.

Как открыть модалку и почему нода не тянется за тело — секция «Нода на канвасе: клик открывает настройки, двигать — за drag-хендл». В `View flow` модалка не открывается.

### Веса в режиме `Compact` показываются долей трафика в процентах

**У сплита со стратегией `Weights` режим просмотра `Compact` показывает не сам вес варианта, а его долю трафика в процентах: вес, делённый на сумму весов только активных вариантов, с округлением до целых.** Выключенный вариант всегда показан как `0%` — трафика он не получает и в сумму не входит. У варианта с включённым `Fill First` вместо процента стоит флажок. Сырое число веса (поле `0-100`) вводится и видно только в режиме `Control`; при других стратегиях (`First`, `Conversions AI`) колонки веса нет вовсе.

Отсюда практический вывод: веса относительные, в сумме давать 100 не обязаны — два варианта с весами `100` и `100` дадут `50%` / `50%`, а `30` и `10` — `75%` / `25%`. Тултип у процентного чипа описывает вес (`Relative share (0–100), not a percent…`), а число рядом с ним — уже процент. Как работает распределение по весам и `Fill First` — [models/distributions-model.md](distributions-model.md).

### Блок `Custom allowance rules` — сплит без переключателя режимов

**Блок `Custom allowance rules` на шагах `Filter` и `Condition` — это сплит, состоящий из одних правил, поэтому он рисуется упрощённо: топ-бара с переключателем `Compact` / `Control` нет, режим всегда `Control`, копирования условий между вариантами (`Copy condition & group` / `Paste condition & group`) нет, пустой список правил не показывает заглушку `No variants yet`.** Пустое правило подписано `Accept everything` (RU `Принимать всё`); клик по нему открывает `Manage rule` (секция «State Rules — динамика на уровне State»). Счётчик `{count} variants` в футере у этого блока тоже есть. ветвление на `Condition` — секция «Condition (Check rules) — настройки».

### `Redirect strategy` — чем визитёра отправляют дальше (301 / 302 / Meta Refresh)

**`Redirect strategy` (в payload узла — ключ `redirect_strategy`) задаёт, каким способом шаг отправляет визитёра на следующий URL.** В форме шага поле рисуется тремя кнопками `301 Permanent` / `302 Temporary` / `Meta Refresh No Referer` (если кнопки не влезают по ширине — обычным дропдауном с плейсхолдером `Default`); повторный клик по выбранной кнопке снимает выбор. Пустое значение (`Default`) = редирект `301`. Тултип поля: `How the visitor is sent further: 301 is cached by the browser, 302 is not, Meta Refresh hides the referer`.

- **`301 Permanent`** — постоянный редирект, браузер его кэширует.
- **`302 Temporary`** — временный редирект, не кэшируется.
- **`Meta Refresh No Referer`** — вместо 30x визитёру отдаётся HTML-прослойка, которая сама уводит на целевой URL; реферер режется гарантированно во всех браузерах, включая Safari/WebKit.

Заголовок `Referrer-Policy: no-referrer` AIO ставит при любой стратегии — и на `301`, и на `302`, и на любом своём HTML-ответе; выключить это нельзя. На 30x-ответах Safari/WebKit этот заголовок игнорирует, поэтому там, где срез реферера нужен во всех браузерах, ставится `Meta Refresh No Referer`. Если рекламодателю нужен реферер — он передаётся параметром через `{{aio.visit.fields.referer}}`; полный разбор того, что уезжает рекламодателю, — [how-to/destinations.md](../how-to/destinations.md).

### На каких узлах есть `Redirect strategy` и где она не действует

Поле есть у трёх нод: `Content`, `Destination` и `Domain change`.

На шаге `Destination` стратегия действует на переходы по ссылкам (handle `link`, `link-1` … `link-5`) и на редирект в уже зарегистрированный URL дестинейшена. На сабмит формы (handle `form`) она не применяется — там ответ уходит визиту JSON'ом, а не редиректом.

В целевом URL разрешены только `http(s)`-адреса, протокол-относительные (`//…`) и абсолютные-путевые (`/…`): всё остальное подменяется на `/`, управляющие символы вычищаются.

### Start (Initial state) — настройки

Только общий каркас — точка входа, добавляется авто.

### Source (Initial state) — настройки

Только общий каркас. Исходящий транзишн — `arrived`.

### Filter (Traffic filtering) — настройки

Модалка настроек шага задаёт, каким фильтром и по каким правилам отбирается трафик; ветки транзишенов — `passed` / `rejected`. Блок `Custom allowance rules` здесь рисуется без переключателя `Compact` / `Control`, пустое правило подписано `Accept everything` (секция «Блок `Custom allowance rules` — сплит без переключателя режимов»).

### Condition (Check rules) — настройки

**`Allowance rules`** (`+ Allowance rule`) — чистое логическое ветвление по полям визита, **без** показа контента и **без** фильтрации. Ветки `passed` / `rejected`. Шаг прогоняет все активные `Allowance Rules`: прошли все → событие `Passed`; первое правило, вернувшее false, обрывает проход → событие `Rejected` (rejected-ветка обычно ведёт на Thank-You без пуша).

Вторая настройка шага — тоггл **`Trash when Rejected`** (ключ `is_trash_when_rejected`), **по умолчанию выключен**: пока он выключен, отклонённый на `Condition` визит в trash не попадает. Что даёт включение — секция «`Trash when Rejected` — Condition тоже помечает визит trash».

### `Trash when Rejected` — Condition тоже помечает визит trash

Тоггл **`Trash when Rejected`** на шаге `Condition` (ключ настройки стейта `is_trash_when_rejected`, подсказка в UI — `Mark trash when condition was rejected`) заставляет шаг класть отклонённый визит в trash. **По умолчанию выключен** — без него реджект на `Condition` визит не помечает.

При включённом тоггле на первом непрошедшем активном `Allowance Rule` визиту проставляется `is_trash`, а причина пишется в поле `Trash Reason` (дословные литералы причин); только после этого пушится обычное событие `Rejected` — визит идёт по rejected-ветке уже помеченным. Прошли все правила → `Passed`, тоггл ни на что не влияет.

Тоггл настраивается **только на уровне Flow** — per-campaign переопределения нет (на кампанию из настроек стейта уезжает только payload, то есть сами `Allowance Rules`). Поэтому включение действует сразу на все кампании этого флоу. Кому он нужен, а кому навредит — секция «Когда включать `Trash when Rejected`, а когда не стоит».

### Когда включать `Trash when Rejected`, а когда не стоит

Включать, если `Condition` у вас фактически работает **отсекающим правилом**: визит не проходит условие по значению поля, и считать его дальше не нужно. Такой визит уводят в тупиковую ветку — дальше по воронке он не пойдёт и конверсий не принесёт, но без пометки останется в основной таблице визитов и в общей аналитике, то есть будет портить знаменатель. Тоггл убирает его из общей аналитики на вкладку `Trash`.

Не включать, если `Condition` — обычное **ветвление**, и обе ветки везут нормальный трафик (развести Android / iOS, выбрать разный путь по полю визита). Здесь `Rejected` значит «пошёл по второй ветке», а не «мусор», и пометка выкинет из аналитики живые визиты. Именно поэтому шаг не помечает trash сам: `Condition` изначально держит оба сценария — и реджект, и ветвление, — авто-пометка была бы неверна для второго. Отсюда отдельный переключатель, по умолчанию выключенный.

**Симптом, по которому узнают кейс** (из него тоггл и вырос): часть команд строила `Condition` как отсекающее правило и получала «визиты зарезаны на `Condition` и уведены в тупиковую ветку, но лежат в основной таблице визитов и портят статистику». Это ровно то, что чинит тоггл.

### Визит помечен trash — что перестаёт работать ниже по флоу

Пометка `is_trash` — не ярлык, а переключатель поведения: визит выпадает из общей аналитики и уходит на вкладку `Trash` ([mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md)), а часть веток флоу у него глохнет.

- **Нода `Notifications flow` визит не сеет** — в подфлоу рассылки он через неё не попадёт (единственное условие ноды — визит не помечен trash).
- **На `Destination` лид пушится как обычно, но авто-конверсия ноды не создаётся** — разбор в секции «Destination (External target) — настройки».
- **Переходы визита по нодам перестают попадать в Visit timeline** — лента обрывается на ноде, где визит помечен ([how-to/visit-timeline.md](../how-to/visit-timeline.md)).

### Content (Show to browser) — настройки

Вариант = **`Select landing page`**; **`Linked field`**; **`Payload type`** (Landing / HTML / Redirect / Reflect / Skip / 404); **`Lander type`** (Preland / Offer / White, мульти-выбор); **`Advertiser type`**; **`Form fallback`**; **`Redirect strategy`** — как отправлять визитёра на сторонний URL варианта `Redirect` (секция «`Redirect strategy` — чем визитёра отправляют дальше»).

Что делают три «неочевидных» атрибута:

- **`Linked field`** — линкует поле формата `Variant`: в это поле визита при выборе пишется content-object выбранного в этой Content-ноде варианта (source записи — `Variant`, только на запись). Пример: на шагах PWA и Offer выбранный вариант пишется в `PWA State` / `Offer State`.
- **`Advertiser type`** — фильтр, схлопывающий варианты payload (ограничивает выбор Destination на шаге, так же как на шаге `Destination`).
- **`Form fallback`** — очень старый способ выбрать форму: если шага `Choose form` нет, но на шаге Flow нужна конкретная форма из `Settings → Forms`. Если нет ни `Choose form`, ни `Form fallback` — грузится дефолтная форма из SDK.

#### Два слоя Content-ноды: стратегия выбирает вариант, процессор его рендерит

Content-нода (и любая нода-выборщик) работает в два независимых слоя, поэтому «стратегия» и `Payload type` — это ортогональные настройки одного варианта, а не одна ось.

- **Слой 1 — стратегия выбора** (`First` / `Weights` / AI). Она выбирает РОВНО ОДИН вариант из строк ноды (по порядку, по весам или по обучению). Что именно за контент в варианте — на этом слое не важно.
- **Слой 2 — процессор по `Payload type`** выбранного варианта. По типу варианта (`Landing` / `HTML` / `Redirect` / `Reflect` / `Skip` / `404` / `Destination` / …) отдельный процессор рендерит страницу или эмитит команду перехода. Один и тот же вариант с одной стратегией может нести любой из типов.

Поэтому вопрос «какой лэнд показался» решается на слое 1 (стратегия + правила + цвет), а «что физически произошло с визитом» — на слое 2 (тип варианта).

#### Sticky-повтор варианта: `visit.variants` и повторный заход на шаг

При первом выборе варианта нода-выборщик записывает выбор в реестр `visit.variants` — ключ на шаг (по кампании и стейту) → выбранный вариант. При повторном заходе визита на тот же шаг стратегия НЕ выбирает заново: возвращается ТОТ ЖЕ вариант из реестра (sticky). Повторный заход поэтому не перезаписывает цвет Split Group, не перезаписывает `Linked field` и не двоит статистику выбора — весь блок записи выполняется только при первом (не-sticky) выборе. Практический вывод: визит, вернувшийся на шаг, увидит тот же вариант, что и в первый раз.

### Destination (External target) — настройки

Вариант = **`Select destination`**; `Linked field`; `Advertiser type`; **`Reject conversion spawn`** (спаун конверсии при reject); **`Pushed conversion spawn`** (спаун при успешном push); **`Redirect strategy`** — чем отправлять визитёра дальше по ссылке дестинейшена (секция «`Redirect strategy` — чем визитёра отправляют дальше»).

`Reject conversion spawn` / `Pushed conversion spawn` — это опции **для удобства** на шаге Destination, а не единственный способ спавна. `Spawn conversion` — отдельная нода, её можно поставить в **любое место** флоу (перед, после или рядом с Destination). Эти опции просто позволяют спавнить конверсию прямо в момент reject / push, не заводя отдельный шаг — удобно, но не обязательно.

**У визита с флагом `is_trash` обе опции молчат: авто-конверсия на ноде не создаётся**, хотя сам лид в Destination уходит как обычно (аналитические события прихода и реджекта на Destination у такого визита тоже не публикуются). Асимметрия, которую стоит помнить при разборе: отдельная нода `Spawn conversion` такого гейта не имеет и конверсию создаст, входящий постбэк у trash-визита конверсию тоже создаёт — см. [models/conversion-model.md](conversion-model.md). Откуда у визита берётся `is_trash` — секция «Визит помечен trash — что перестаёт работать ниже по флоу».

### Fill fields (Operate with fields) — настройки

Вариант = **`Enter text`** (статичное значение); **`Fields`** (целевое поле визита); **`Placeholder group`**; **`Payload type`** (`Fill Text` / `Fill Content`).

### Fields by distribution (Use trees to fill fields) — настройки

Вариант = **`Select distribution`** + **`Fill Field`** — значение поля берётся из **дерева Distribution** (а не вручную).

### Fill form (Select form) — настройки

Вариант = **`Select form`** (форма из `Settings → Forms`). Можно сплитовать **разные формы** по весам. *(`Payload type` зарезервирован на будущее; сейчас всегда используется Form как фильтр.)*

### Domain change (Flip domains) — настройки

Вариант = **`Select domain`** — на какой домен флипнуть (трекинговый ↔ публичный). Конкретный домен обычно задаётся per-campaign (Settings availability). Есть и **`Redirect strategy`** — каким способом визитёра переносят на выбранный домен (секция «`Redirect strategy` — чем визитёра отправляют дальше»).

### Spawn conversion (Initiate conversion) — настройки

**`Conversion type`** — тип конверсии, который порождается на этом шаге.

### Field Verification (Verify field via sender provider) — настройки

**`Contact`** (поле для проверки — phone / email) + **`Sender provider`** (через какого провайдера верифицировать — те же Sender Providers, что в Marketing: Twilio / Telegram / …). По сути OTP/верификация контакта внутри флоу. Ветки транзишенов — `passed` / `rejected`. Тип ноды — `Field Verification`; в списке handler-типов UI эта нода подписана `Phone Verification`.

**Статусы верификации (Field Verification Statuses).** Семь статусов (RAW enum-значения). Из них экран ввода кода визит видит **только на двух**: `Sent` (код отправлен) и `Invalid Code` (код не совпал) — на них рендерится HTML-страница верификации, где статус показан текстом (текст локализуется под язык визита средствами страницы). Остальные пять — **терминальные**: визит на них уходит по ветке `passed`/`rejected`, экран не показывается, статус лишь пишется в поле `visit.verifications` (трейс в данных визита).

- `Sent` — код отправлен на контакт, ждём ввода. **Визит видит экран.**
- `Invalid Code` — введённый код не совпал; счётчик неверных попыток растёт, визит остаётся на экране и вводит код заново. **Визит видит экран.**
- `Verified` — код совпал, визит уходит по ветке `passed`. Трейс-статус (экрана нет).
- `Tries Exceed` — исчерпан лимит неверных вводов → ветка `rejected`. Трейс-статус.
- `Expired` — истёк срок жизни кода → ветка `rejected`. Трейс-статус.
- `Not Found` — для шага нет отправленного кода (визит попал на `handle` без отправки) → ветка `rejected`. Трейс-статус.
- `Failed To Send` — код не удалось отправить (сбой Sender Provider / пустой контакт после подстановки плейсхолдера); шаг пропускает визит дальше по ветке `passed`, но верификация не состоялась. Трейс-статус.

Display-лейблы на экране (`Sent` / `Invalid Code`) отличаются от RAW-значений: экран показывает `Verified ✓` / `Tries Exceeded` / `Failed to Send` (регистр/окончание не совпадают с enum). Лимиты верификации (число попыток ввода, число отправок на визит, срок жизни кода) — [reference/limits.md](../reference/limits.md).

#### Как устроена проверка кода (OTP-механика шага)

Шаг `Field Verification` — это мини-FSM проверки одноразового кода. Первый заход отправляет код и рендерит экран ввода; последующие заходы проверяют введённое.

- **Отправка кода — одна за заход.** На первом входе шаг зовёт Sender Provider, ставит статус `Sent`, кладёт код и срок его жизни в `visit.verifications` (по uuid стейта) и планирует отложенную ре-проверку к моменту истечения кода. Повторно отправить код в рамках одного захода нельзя (`SEND_LIMIT` = 1 отправка).
- **Неверный код НЕ реджектит — визит остаётся на шаге.** При несовпадении счётчик неверных вводов растёт, статус становится `Invalid Code`, экран ввода рендерится заново, визит по-прежнему на этом шаге (без события перехода). Реджект наступает только когда исчерпан лимит попыток.
- **Три попытки — потом `Tries Exceed`.** Лимит неверных вводов — 3 (`TRIES_LIMIT`). На четвёртом визит уходит по ветке `rejected` со статусом `Tries Exceed` (именно `Tries Exceed`, не «Exceeded»).
- **Срок жизни кода — 5 минут.** По истечении (`EXPIRY_MINUTES` = 5) код становится `Expired` и визит уходит по `rejected`; отложенный джоб к этому моменту делает плановую ре-проверку, если визит сам не вернулся.

Состояние каждой верификации хранится в поле `visit.verifications` по uuid стейта — один визит может нести несколько независимых верификаций (несколько шагов `Field Verification` во флоу).

### Sub flow (Extend your flow) — настройки

**`Sub-flow`** — выбор готового SubFlow для вставки.

### Notifications flow (Send notifications) — настройки

**`Notification flows`** — единственное поле ноды, обязательное: выбор `Notifications`-подфлоу (плейсхолдер `Select notification sub-flow`, ключ в payload узла — `flow_uuid`). Нода сеет в выбранный подфлоу любой не-трэшевый визит, дошедший до неё.

Это кастомный способ запустить рассылку прямо из кампанийного флоу; штатный — ремаркетинг-кампания ([how-to/remarketing-campaigns.md](../how-to/remarketing-campaigns.md)). Ноды внутри самого флоу рассылки — [mechanics/notifications-flow.md](../mechanics/notifications-flow.md).

### Finish (Ending state) — настройки

Только общий каркас — маркер конца SubFlow, входящие транзишены без исходящих.

### Паттерн нод-«выборщиков» — одна механика вариантов у шести нод

Все ноды-«выборщики» (`Content` / `Destination` / `Fill fields` / `Fields by distribution` / `Fill form` / `Domain change`) используют единый паттерн: стратегия `First` / `Weights` + строки вариантов с цветом (Split Group), весом и `+ Add another variant`. Разница только в том, **что** выбирается (лэнд / дестинейшн / текст поля / дистрибуция / форма / домен). В режиме `Compact` вес показан долей трафика в процентах (секция «Веса в режиме `Compact` показываются долей трафика в процентах»).

Панели редактора, тулбар канваса и то, как двигать ноду и открывать её настройки, — секции «Сам редактор флоу — панели и действия над флоу» и «Нода на канвасе: клик открывает настройки, двигать — за drag-хендл»; подписи транзишенов (`start` / `arrived` / `handle` / `passed` / `rejected` / …) — «Какие бывают Flow Transitions».
