# User — концепт (модель)

> Модель сущности **User**: что это и как связано. То, что у юзера **ЕСТЬ** в тенанте (роль, позиции, команда, шаринг) — это отдельная **модель доступа**: [models/permissions-model.md](permissions-model.md). Процедуры (инвайт, деактивация, Position, Share) — [how-to/permissions.md](../how-to/permissions.md).

## Что такое User в AIO и чем он отличается от его прав

**User — это ОДИН аккаунт человека в AIO, который может состоять сразу в нескольких тенантах.** Юзер — это *кто* (actor): он создаёт, владеет и оперирует сущностями. Что именно он видит и может — определяется его **доступом** (роль, позиции, членство в команде), причём **доступ свой в каждом тенанте**; но это отдельная модель (*permissions*), а не сам юзер. Аккаунт идентифицируется почтой/телеграмом + 2FA; в сущностях, которые он создал, он становится **Owner**.

## Как устроен User: мульти-тенантность, ownership, жизненный цикл

### Один аккаунт User — сразу несколько тенантов

- **User — глобальный аккаунт, не привязан к одному тенанту.** Один и тот же человек **состоит сразу в нескольких тенантах** (membership многие-ко-многим), переключается между ними через **смену тенанта** в меню профиля (см. `reference/ui-map.md`).
- **Доступ — свой в каждом тенанте.** В одном тенанте юзер может быть Admin, в другом — Employee с узкой позицией. Права не «перетекают» между тенантами (изоляция тенанта — `models/tenant.md`).
- **Аккаунт:** name + email + telegram + password; **2FA через Telegram-бота или Google Authenticator** ([context/architecture.md](../context/architecture.md) → 2FA). Без активной 2FA (`Unsecured Mode`) часть полей юзера в UI скрыта (`telegram`, `email`, `name`) — это by design.
- **Как юзер попадает в тенант:** инвайт (`Settings → Users → + User` → инвайт-линк, роль Admin/Employee) — если у человека уже есть аккаунт, он входит в тенант этим же аккаунтом; либо саморегистрация по коду/триалу создаёт аккаунт + тенант (`how-to/registration.md`). **Tenant Owner** — тот, кто создал тенант.

### Что у User есть в тенанте (Role / Position / Team) — это отдельная модель доступа

Доступ в **конкретном тенанте** определяют **атрибуты** юзера, а не он сам:
- **Role** — Owner / Admin / Employee;
- одна или несколько **Positions** — наборы прав через *Imperatives* (Allow/Deny по секциям), с `Priority` при конфликте;
- членство в **Team** с уровнем Member / Leader / Head.

Как из этого вычисляется «что видно / что можно» — **целиком** в `models/permissions-model.md` (это **отдельная модель** — модель доступа, со своими сущностями Role/Position/Team/Imperative/Sharing). Концептуально: **User — сущность-actor, Permissions — модель того, что у этой сущности есть в тенанте.** Поэтому это разные модели.

### Кто такой Owner сущности и чем отличается от Tenant Owner

- Создал сущность (кампанию / лэнд / домен / дистрибуцию…) → стал её **Owner**. `Change Owner` передаёт владение (прежний owner остаётся как shared с теми же правами).
- **Owner сущности ≠ Tenant Owner** — разные понятия; полное объяснение и механика Change Owner: [models/permissions-model.md](permissions-model.md).
- Юзер фигурирует в данных как **Campaign Owner** и **Launcher** (кто сгенерил конкретную ссылку) — эти «роли в контексте» влияют, например, на маршрутизацию `Fill Field Distribution` (см. `models/distributions-model.md`).

### Как логируются действия User

- **Каждое действие логируется** (IP / User-Agent / timestamp / что сделал) — инструмент разбора «кто это сделал». Логирование работает для любого юзера тенанта.

### Жизненный цикл User: почему деактивировать, а не удалять

- **Деактивируй, не удаляй** — механика и процедура: [how-to/permissions.md](../how-to/permissions.md). При удалении авторство прошлых заливок становится `empty` (откатить нельзя); деактивация оставляет юзера в истории как автора и просто закрывает вход.
- Юзеры **намеренно не скрыты** друг от друга — by design скрыть одного юзера от команды нельзя (модель как в Slack/Discord: все участники видят друг друга; отдельные поля юзера тоже не спрятать).
- Спец-случай — **Monitoring User**: «юзер-пустышка» на chat ID группового чата, чтобы алерты мониторинга доменов/серверов падали в общий чат, а не в личку (заводится через саппорт). Алерты идут только в Telegram → у Monitoring User нужна привязка к Telegram (Google Authenticator её не даёт). См. `context/architecture.md`, `how-to/domains.md`.

## Как User связан с Tenant, Permissions и сущностями AIO

- **состоит в одном или нескольких Tenant** (membership многие-ко-многим); права — свои в каждом.
- **HAS Role / Positions / Team** (в данном тенанте) → модель доступа `models/permissions-model.md`.
- **OWNS сущности** (Owner); `Change Owner` передаёт владение.
- фигурирует как **Campaign Owner / Launcher** — контекстные роли, влияющие на Distribution-маршрутизацию.

## Частые путаницы: User vs Permissions, Owner сущности vs Tenant Owner, Launcher

| Не путать | Разница |
|---|---|
| **User vs Permissions** | User — *сущность*-actor (аккаунт). Permissions (Role/Position/Team/Sharing) — *модель доступа*: что у юзера есть **в тенанте** (`models/permissions-model.md`). User ≠ его права. |
| **User (аккаунт) vs membership в тенанте** | Аккаунт **один**; он состоит в нескольких тенантах. «Юзер в тенанте» — это аккаунт + его роль/позиции **в этом** тенанте. Удаление из одного тенанта не удаляет аккаунт. |
| **Owner сущности vs Tenant Owner** | Tenant Owner — владелец **тенанта** (full access ко всему в нём). Owner сущности — кто **её** создал. Разные «owner». |
| **User vs Launcher** | Launcher — юзер, **сгенерировавший конкретную ссылку** (роль-в-контексте, фиксируется в момент генерации). У Direct-визитов `Launcher = Unknown`. |

## Частые ошибки с User: не тот тенант, удаление, нет 2FA, Monitoring User

- **Юзер — один аккаунт, в нескольких тенантах.** «Дайте доступ к другому тенанту» = **добавить этот же аккаунт** в нужный тенант (инвайт/назначение роли там), а не заводить нового юзера. Права в каждом тенанте — свои.
- **Деактивируй, не удаляй** — иначе авторство прошлых заливок становится `empty`.
- **Нет 2FA → поля скрыты** — «не вижу telegram/email юзера» часто значит «не включена 2FA» (`Unsecured Mode`).
- **Monitoring User** для алертов — отдельная «юзер-пустышка» на chat ID, заводится через саппорт.
