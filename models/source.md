# Source — концепт

> Концепт: что такое Source и как он определяет, *что* AIO знает о входящем визите. Процедуры (создать source, rewrites, постбэк-трекеры) — в [how-to/source-trackers.md](../how-to/source-trackers.md). UI — [reference/ui-map.md](../reference/ui-map.md) → Tracker → Sources.

## Что такое Source и какую роль он играет для входящего трафика

**Source — это пресет «откуда и с каким описанием» приходит трафик.** Он отвечает на три вопроса для каждого входящего визита: (1) **через какой источник** визит вошёл (`suuid`), (2) **какие параметры из URL** записать в какие поля визита (Source Mapping / rewrites), (3) **какие события** отправлять обратно — на рекламную платформу или рекламодателю (постбэк-трекеры, прикреплённые к Source). По сути Source — это «адаптер» между внешней рекламной системой (FB, Google, Taboola, нативка) и внутренней моделью данных AIO.

## Как Source обрабатывает входящий визит: suuid, маппинг, трекеры

### Что такое `suuid` и как он определяет источник входа

В tracking-ссылке вместе с `cuuid` (кампания) едет **`suuid` = UUID этого Source**. Пара `cuuid`+`suuid` — это «координаты входа»: агент на домене снимает их из URL и передаёт AIO, а AIO по ним определяет, в какую кампанию и через какой источник класть визит и какие правила парсинга URL применять (агент работает по командам AIO — [models/server.md](server.md)). Один Source переиспользуется во многих кампаниях (например, единый «Facebook» source на все FB-запуски).

У самого Source есть свойство **`Integration Type`** — набор параметров под конкретную рекламную платформу (Google, Facebook и т.д.). Именно оно задаёт, под какой канал заточен пресет (это поле Source, не путать с одноимённым `Integration type` у Destinations / Sender providers / Domain checkers / Traffic filters — там оно про свои интеграции). Расходы Source тянет иначе: он умеет принять параметр из URL рекламной платформы (например, CPC или трекинг-плейсхолдер), а правила маппинга (rewrites в JSON) проставляют его в поле `Cost` визита — детали в `how-to/source-trackers.md`.

### Как Source Mapping раскладывает URL-параметры по полям визита

Главная работа Source — **разложить query-параметры входящей ссылки по полям визита**. Реклама приносит параметры в своём формате (`ad_name`, `adset_id`, `fb_pixel`, `gclid`, `utm_*`…), а AIO хранит их в полях визита со своими slug-ами (`field_fb_ad_name`, `field_fb_ad_set_id`…). Source описывает это соответствие.

- Если имя URL-параметра **совпадает** со slug поля — пишется автоматически.
- Если **не совпадает** (`pixel` в URL vs поле `fb_pixel`) — нужен **rewrite**: правило соответствия «ключ URL → slug поля». В конструкторе Source rewrites задаётся двумя способами: рядами `from → to` во вкладке **«Переписывания»** либо ключом `rewrites` в сыром JSON-конфиге (вкладка **Raw**, вместе с `settings`/`placeholders`) — это одно и то же, вкладка «Переписывания» персистится в тот же JSON-ключ. См. `how-to/source-trackers.md`.

Поле визита, в которое маппится параметр, **должно существовать заранее** — иначе значение из URL потеряется. Это самая частая ошибка первичной настройки источника. Причём поле должно быть **прописано и в самом коде Source** (в JSON-конфиге): если поля нет в конфиге источника, параметры из tracking-ссылки не захватываются.

### Нет нужного поля под маппинг — где его завести

Сначала заведи поле (`Settings → Fields`, см. `how-to/custom-fields.md` → «добавить новое поле»), потом добавь его в код Source.

### Нет нужного поля под маппинг — где его завести (MTK)

Конструктор полей (`Settings → Fields`) в MTK-виде скрыт — создать поле самому нельзя. Нужное поле приходит из шаблона либо заводится разово командой AIO (через `Switch Build` → ERP-вид того же тенанта). См. *Как устроен MTK-вид AIO: навигация, пресеты из шаблона и методы под типовые задачи*.

### Задать значение поля прямо в карточке Source, без параметра в ссылке

Не всякое поле обязано приезжать из URL. В форме source (`Tracker → Sources`) есть секция `User fields`: кнопкой `Add field` в неё добавляются поля визита с `Type = Source`, и вписанное там значение попадает в каждый визит, вошедший через этот source, — без параметра в tracking-ссылке и без rewrite.

Родителя у Source нет, поэтому режимов раздачи полей (они есть у `Flow`, `Lander Type` и `Advertiser`) в его форме не бывает — значение задаётся только здесь. Пул полей, кнопка `Add field` и что делать, если нужного поля в списке нет, — [how-to/user-fields.md](../how-to/user-fields.md).

### Зачем к Source привязывают Trackers — постбэки «наружу»

К Source прикрепляются **Trackers** — конфиги отправки событий из AIO во внешние системы при наступлении событий по визиту/конверсии. Два типа:
- **Conversion type** трекера — на какое событие он реагирует (Lead / Purchase …);
- **Tracker type** — куда и как шлёт (полный список типов и описание каждого — [models/tracker.md](tracker.md)); если у Source нет conversion API (как Facebook CAPI / TikTok Events API) — выбирают HTTP GET.

То есть Source — это не только «вход» (парсинг URL), но и точка, откуда уходят **обратные сигналы** в рекламную платформу (например, FB CAPI «случился лид» для оптимизации). Поэтому Source концептуально двунаправлен: ловит на входе, рапортует на выходе. Детали — `how-to/source-trackers.md`.

### Визит без `suuid` — как назначается source (Direct Traffic)

Голый заход на домен без `cuuid`/`suuid` → визиту неоткуда взять кампанию/source. Если на домене **не** настроена привязка — ссылка не откроется и корректно отдаёт `502`. Если привязка есть, источник назначается механизмами Direct Traffic: `Default Query` на домене (per-item путь, работает в обоих билдах). См. `mechanics/visit-lifecycle.md`.

### Direct Traffic Distribution — централизованный путь (ERP)

Альтернатива `Default Query` — централизованный `Direct Traffic Distribution` (`Settings → Distributions`). В MTK конструктор Distributions скрыт, а сама эта централизованная дистрибуция **не используется** — для прямого трафика остаётся только `Default Query` на каждом домене (см. *Как устроен MTK-вид AIO: навигация, пресеты из шаблона и методы под типовые задачи*).

## Как Source связан с остальными сущностями

- **Campaign использует Source** — через Link Generator (`Campaign + Domain + Source` → ссылка с `cuuid`+`suuid`).
- **Source → поля визита.** На входе пишет первичные поля визита (FB-параметры, UTM, гео из IP) по своему маппингу. Эти поля потом читают групперы, дистрибуции, лэнды.
- **Source → Trackers → внешние системы.** Постбэки наружу при конверсиях.
- **Visit входит через `cuuid`+`suuid`** — Source это «s» в этой паре.

## Чем Source отличается от смежных понятий

| Не путать | Разница |
|---|---|
| **Source vs Tracker** | Source — **пресет входа** (suuid + маппинг URL). Tracker — его **ребёнок**, конфиг отправки события **наружу** (постбэк в FB CAPI / рекламодателю). У одного Source — много Trackers. |
| **Source vs Campaign** | Source — *откуда* и *с какими данными* трафик. Campaign — *по какому пути* он пойдёт. Ссылка = Campaign × Source. |
| **Source vs Detected source** | `Detected source` — аналитическая колонка («что мы распознали по визиту»), не сама сущность Source. Её значение на кампании AIO **проставляет сам** по преобладающему трафику за последний час (фоновой пересчёт — *Что AIO проставляет и делает сам — фоновые задачи и их расписание*), а не вводит вручную. |
| **Source vs Channel** | Канал (FB/Google/нативка) — это вертикаль рекламы; Source — конкретный настроенный пресет под него в AIO (их может быть несколько на один канал). |

## Подводные камни Source — частые ошибки настройки

- **Поля под маппинг заводи заранее** (`Settings → Fields`) — иначе данные из URL теряются.
- **rewrites задаётся и вкладкой «Переписывания» (ряды `from → to`), и ключом `rewrites` в сыром JSON** (вкладка Raw) — это один и тот же конфиг.
- Новый поток/оффер с другой таксономией событий → обычно **отдельный Source + отдельные Trackers**, не переиспользуй старый (эвристика, см. `conversion-model.md`).
- Source сидит в `Tracker → Sources` (не в Settings — частая галлюцинация).
