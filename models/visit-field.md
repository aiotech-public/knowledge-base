# Visit Field — концепт

> Концепт: что такое поле визита и почему это субстрат, на котором держится вся система. Процедуры (создать поле, пачка полей под интеграцию, Available Values, Item Lists) — [how-to/custom-fields.md](../how-to/custom-fields.md). Плейсхолдеры — [reference/placeholders.md](../reference/placeholders.md). UI — `Settings → Fields`.

## Суть в одном абзаце

**Visit Field — это именованный слот данных, который висит на визите.** Звучит скромно, но поля визита — это **субстрат всей системы AIO**: почти каждая сущность либо *пишет* в поля визита, либо *читает* из них. Source раскладывает в них URL-параметры, карточки `Campaign`, лендинга и `Destination` отдают вписанные в них значения, SDK пишет рантайм-данные, Fill-шаги флоу заполняют их по правилам, постбэки от брокера дописывают результат, а групперы, дистрибуции и лэнды — читают. Значение поля **накапливается вдоль пути визита**. Поэтому понять поля = понять, как данные текут через AIO.

## Как это работает на самом деле

### 1. Поле = slug + тип + атрибуты

Поле заводится в `Settings → Fields`. Ключевое в нём — **slug** (генерится из имени): это **буквальный ключ**, под которым значение живёт и адресуется везде:
- в плейсхолдерах лэнда: `{{aio.visit.fields.<slug>}}`;
- в маппинге Source (URL-параметр → slug);
- в постбэк-трекерах и Non-SDK Form Handler.

Поэтому **slug менять нельзя** на существующем поле — иначе порвутся все ссылки (процедура — [how-to/custom-fields.md](../how-to/custom-fields.md)).

#### `Type` — сущность-владелец поля (6 значений), она же роутит адресацию

`Type` — это **сущность, которой принадлежит поле**, а не бинарь «Visit или Campaign». Значений шесть: `Conversion` / `Visit` / `Campaign` / `Source` / `Landing` / `Destination`. Тип грузонесущий — он решает, **в каком неймспейсе поле адресуется плейсхолдером**:
- `Conversion`-поля читаются через отдельный неймспейс — `{{aio.conversion.fields.<slug>}}` (данные конверсии, не визита);
- остальные пять типов (`Visit` / `Campaign` / `Source` / `Landing` / `Destination`) читаются как поля визита — `{{aio.visit.fields.<slug>}}` — и предлагаются в пикере плейсхолдеров в группе `Visit Fields`.

По источнику дефолта значения: `Visit` — дефолт из ссылки/URL; `Campaign` — дефолт из карточки кампании (напр. FB Pixel/CAPI Token, чтобы не светить в URL); `Source` — дефолт из source-маппинга; `Landing` — из карточки лендинга или его `Lander Type`; `Destination` — из карточки дестинейшена или его `Advertiser`.

Значение при любом типе живёт **на визите**, тип отвечает только за то, где задаётся дефолт и каким неймспейсом поле читается. Как значение вписывается в карточку сущности — [how-to/user-fields.md](../how-to/user-fields.md). `Campaign`-поле — тоже поле визита: значение может быть перезаписано по конкретному визиту (разбор — таблица «Visit field vs Campaign field» в этом документе). Плейсхолдеры — [reference/placeholders.md](../reference/placeholders.md).

#### `Format` — как хранить + дефолт + formatter + тип плейсхолдера

`Format` — не только про отображение: он выбирает дефолт значения, formatter и тип плейсхолдера поля. Это select из ~20 значений; список **не исчерпывающий**. Грузонесущие: `String`, `Number`, `Boolean`, `Placeholder`, `Variant` (часто для `LP_*` сплитов), `Money`, `Phone`, `Ip`, `Country`, `Language`, `Destination`, `Lander`, `Percentage`, `Time Seconds`, `Progress Number` и др. Числовые форматы (`Money`/`Number`/`Time Seconds`/`Progress Number`/`Percentage`) дают дефолт `0`, остальные — пустую строку; `Destination`/`Lander` подставляют связанную сущность, а не голый uuid; `Phone`/`Ip` типизируют плейсхолдер (валидация формата). Полный набор форматов — [how-to/custom-fields.md](../how-to/custom-fields.md). `Format` выбирается только при создании поля: в `Edit Field` этого select нет.

### 2. Кто наполняет поле

**Кто реально пишет в поле, определяют пишущие сущности вдоль пути визита — не какая-то настройка поля.** В карточке поля есть select **`Data source`**, но он **устаревший и ни на что не влияет**: значение выбрать можно, эффекта нет ([how-to/custom-fields.md](../how-to/custom-fields.md)). Реальный источник записи штампует **сама пишущая сущность** (`Agent Init` при заходе, `HTTP Trigger`, `ERP Defined` для Fill-шагов и значений из карточек сущностей, `Form`, `Variant`, `System`), а не выбор в этом селекте. Реальная картина «кто за поле отвечает» — это цикл накопления значения (Source из URL, карточки сущностей, SDK-макросы, Fill-шаги, постбэки от брокера).

### 3. Цикл накопления: кто пишет, кто читает

Главная концептуальная картина — **значение поля аккретит по мере движения визита**:

```
ПИШУТ (по ходу пути):
  Source          → раскладывает URL-параметры (FB ad_name, utm, гео из IP)
  Карточки        → значения, вписанные в Source / Campaign / Flow / лендинг /
  сущностей         Lander Type / Destination / Advertiser  [ERP]
  SDK / Macros    → рантайм-данные на лэнде (поведение, технические сигналы визитора, форма)
  Fill fields /
  Fields by distr → значения по правилам/из дерева на шагах флоу  [ERP; в MTK — JS-макрос, см. ниже]
  Postback/Tracker→ результат конверсии от брокера
ЧИТАЮТ:
  Лэнд            → {{aio.visit.fields.<slug>}} (динамический контент/оффернейм)
  Групперы        → разбивки в аналитике
  Distributions   → ветвление/контент/деньги по значению поля
  Filter          → значения полей визита
```

Отсюда вытекает самый частый дебаг-вопрос: «**поле пустое — почему?**» = найти, **кто должен был его записать** (Source-маппинг? Fill-шаг? постбэк?) и на каком этапе цепочка порвалась.

#### Как значение реально хранится на визите

Все значения полей визита лежат одним массивом записей, ключ каждой записи — внутренний `field_uuid` поля (не slug; slug транслируется в uuid при записи). Логика записи:
- **обычное поле (не `Is Registry`)** — новое значение **перезаписывает** value первой записи с этим `field_uuid` (одно актуальное значение на поле);
- **registry-поле (`Is Registry`)** — новое значение **добавляется** новой записью (копится история `1,2,3…`);
- **точный повтор** (та же пара `field_uuid` + value) — **no-op**, не пишется второй раз;
- **пустое значение пропускается** — не затирает уже записанное.

Это механизм за вопросом «поле пустое / со старым значением — почему?» и за поведением `Is Registry` (перезапись vs накопление).

### Какое значение победит, если в поле пишут несколько источников

Побеждает тот, кто записал позже: у обычного поля новая запись заменяет прежнее значение, поэтому в поле визита лежит последнее записанное по ходу пути. Исключения — в самой логике записи: пустое значение и точный повтор не пишутся, а `Is Registry`-поле не заменяет ничего, а копит историю (раздел «Как значение реально хранится на визите» в этом документе).

Отдельно от этой очереди стоят поля родительской сущности в режиме «только родитель» (`Flow only`, `Lander type only`, `Advertiser only`): значение берётся из родительской карточки, а то, что осталось в дочерней, отбрасывается ещё до записи в визит — [how-to/user-fields.md](../how-to/user-fields.md).

### В каком порядке значения ложатся на визит — от захода до пуша

Речь о **пользовательских полях**, заведённых в `Settings → Fields`: системные значения визита в этой очереди не участвуют и перезаписи не подлежат.

Порядок фиксирован ходом визита. **При заходе** значения собираются одним пакетом, и внутри пакета каждый следующий шаг перетирает предыдущий:

1. значения из карточки `Campaign`;
2. значения из карточки `Source`;
3. поля `Flow` в режиме `Flow only` — поверх кампанейских, прежнее значение кампании при этом сбрасывается;
4. параметры ссылки, чьи имена совпали со слагами полей — **поверх всего перечисленного**.

**Дальше по пути** пишут остальные:

- **шаг `Content`, когда флоу отдаёт визиту лэнд** — поля карточки лендинга плюс `Lander type only`-поля его `Lander Type`; один раз на лэнд, повторный проход того же лэнда значения не переписывает;
- **SDK на лэнде и шаг `Fill Fields`** — в тот момент, когда визит проходит лэнд и соответствующий шаг флоу;
- **шаг `Destination`** — поля карточки дестинейшена плюс `Advertiser only`-поля его `Advertiser`; записываются до сборки push-payload, поэтому уезжают и в сам пуш рекламодателю (в том числе когда пуш потом отбивается по капе);
- **постбэк от брокера** — результат конверсии, последним.

Trash-визиту значения карточек лендинга и дестинейшена не пишутся вовсе. Пометка `is_trash` ставится не в одной точке пути и не обязательно на входе — причина каждого визита лежит в его поле `Trash Reason` ([mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md)).

### Как URL-параметр попадает в поле визита — по совпадению слага

**Параметр запроса, имя которого буквально совпадает со слагом поля визита, записывается в это поле.** Работает на двух этапах пути визита:

- **на заходе** — параметры ссылки, по которой визит пришёл (источник записи `Agent Init`);
- **на каждом переходе по флоу** — параметры запроса, которым визит дёрнул хэндл: клик по `{{link}}` или сабмит формы (источник записи `Form`). Именно так лэнд передаёт собранные на нём данные в визит — дописывая их к `{{link}}` ([reference/placeholders.md](../reference/placeholders.md)).

Условия жёсткие:

- **имя параметра = слаг поля, буквально**, включая разделители (`sub_1` ≠ `sub1`);
- поле должно существовать в этом тенанте;
- **поля с таким слагом нет — значение молча отбрасывается**, никакой ошибки не будет.

Отсюда типовой дебаг «лэнд передаёт значение, а поле пустое»: сверить слаг поля с именем параметра, а не искать проблему в SDK. Если разом пропали все параметры — скорее всего с них слетела handle-пара `{{link}}` (*Command not found / визит не переходит на оффер, остаётся на White*).

### 4. Атрибуты поля (поведение)

Тоглы в `Edit Field` управляют поведением поля (полные определения — [how-to/custom-fields.md](../how-to/custom-fields.md)):
- **`Is Registry`** — хранить **последовательность** значений (история `1,2,3…`) vs перезаписывать каждым новым;
- **`Is Macro Visible`** — JS-доступ через объект `aio` на лэнде;
- **`2FA Protected`** (он же Unsecured Mode) — значение скрыто в UI без 2FA;
- **`Is Visible`** — показывать в UI визита;
- **`Available Values`** — превратить строковое поле в select из фикс-списка.

Особняком — **`Is Used For Cost`**: атрибут включает поле в ручной `Update Costs By <Field>` (агрегация костов по визитам с одинаковым значением поля). Механика работает, но **выставить флаг из интерфейса нельзя** — контрола у него в карточке поля больше нет ([how-to/custom-fields.md](../how-to/custom-fields.md)).

### Как шаг Fill Fields пишет значение в поле (и почему source = ERP Defined)

Шаг `Fill Fields` во флоу таргетит **одно** поле визита (выбранное в настройках шага). Записанное этим шагом значение получает data source `ERP Defined` — поэтому при дебаге поле, заполненное `Fill Fields`, показывает источник `ERP Defined` (а не `Agent Init`/`Form`). Как значение попадает в поле, зависит от типа контента варианта:
- **`Fill Text`** — плейсхолдеры в значении **резолвятся** (напр. `{{aio.visit.fields.<slug>}}` подставляется реальным значением) перед записью;
- **`Fill Content` (Content Library) и `Fill Destination`** — контент пишется **сырьём**, без резолва плейсхолдеров.

Процедура настройки шага и разбор `Fill Fields` во флоу — [models/flow-model.md](flow-model.md); how-to по полям — [how-to/custom-fields.md](../how-to/custom-fields.md).

### 5. Поле → группер: Availability as grouper (не путать с Make analytic)

Чтобы поле стало **разбивкой в аналитике (группером)** — `Edit Field → Availability as grouper`. **Каталог групперов per-tenant** = системные поля + кастомные с включённым `Availability as grouper`. Детали и процедуры — [how-to/custom-fields.md](../how-to/custom-fields.md).

**Не путать с `Make analytic`** (правый клик): экшен **оптимизирует поле для быстрых разбивок/аналитики**, но **группер не включает**. Группер — это `Availability as grouper`. (Частая путаница, см. [how-to/analytics.md](../how-to/analytics.md).)

## Как Visit Field связан с остальными сущностями

- **Пишут в поля:** Source (URL→поле), карточки настроечных сущностей через секцию `User fields` ([how-to/user-fields.md](../how-to/user-fields.md)), SDK/Macros (рантайм), Fill fields / Fields by distribution (шаги флоу, ERP), постбэки/Trackers (конверсии).
- **Читают поля:** лэнды (плейсхолдеры), групперы (аналитика), дистрибуции (ветвление/деньги), Filter (по значениям полей визита).
- **slug — универсальный ключ**, связывающий URL ↔ поле ↔ плейсхолдер ↔ постбэк.
- Поле — **горизонтальный слой**: пронизывает почти все сущности, поэтому в спайне это «субстрат», а не отдельная ветка пути.

## Чем Visit Field отличается от смежных понятий

| Не путать | Разница |
|---|---|
| **Поле vs его значение** | Поле — *слот* (slug+тип, заведён один раз). Значение — то, что в него записали для конкретного визита (у каждого визита своё). |
| **Visit field vs Campaign field** | Оба — поля **на визите** (значение хранится по каждому визиту отдельно). Разница только в источнике дефолта: `Visit`-поле заполняется из ссылки/URL, а `Campaign`-поле берёт дефолт из карточки кампании (FB Pixel/CAPI Token и т.п. — один дефолт на весь трафик кампании, не светится в URL; при заходе копируется на визит). Значение `Campaign`-поля можно перезаписать для отдельного визита (в том числе целью шага `Fill Fields`) — это **не** общее неизменяемое значение на всю кампанию. |
| **Availability as grouper vs Make analytic** | Первое (внутри поля) — *включает группер*. Второе (экшен) — *оптимизирует поле для быстрых разбивок*, но группер не включает. |
| **Поле vs плейсхолдер** | Плейсхолдер (`{{aio.visit.fields.<slug>}}`) — *способ прочитать* значение поля на лэнде. Само поле — хранилище. |

### Колонки визита, которые путают с полями — Language и Cost

Отдельно стоят две **колонки самого визита** (не атрибуты поля-концепта), которые часто путают со смежными настройками:

| Не путать | Разница |
|---|---|
| **`Language`-колонка визита vs Form i18n** | Колонка `Language` в `Tracker → Visits` — это **язык устройства визитора** (записан на визите при заходе). Не путать с языком SDK-формы / `Static Language Country` / тегом-категорией лэнда — это про переводы контента, а не про записанный на визите атрибут. |
| **`Cost`-колонка визита vs cost-атрибуция** | Колонка `Cost` в визите — это **расход на привлечение визитора на конкретную страницу** (метрика для оценки прибыли/убытка Campaign). Не путать с механикой атрибуции расходов (`Is Used For Cost` / `Update Costs By <Field>`): первое — *показанное на визите значение*, второе — *как поле участвует в ручном проставлении costs*. |

## Подводные камни Visit Field — частые ошибки настройки

- **Поле под маппинг/интеграцию заводи ЗАРАНЕЕ** — без заранее созданного поля ответ интеграции теряется (самая частая ошибка первичной настройки); подробнее — *уточните у поддержки*.
- **slug не меняется** на существующем поле ([how-to/custom-fields.md](../how-to/custom-fields.md)); если уже в плейсхолдерах — придётся править лэнды.
- **`required` на Visit Field напрямую нельзя** — только через `Link Generator` (обязательность параметра в ссылке). Не путать с `Required` на Form Control в Form Builder.
- **`Make analytic` ≠ группер** — если ждёшь разбивку, включай `Availability as grouper`.

## Как записать значение в поле визита по правилу в MTK

В MTK шага `Fill Fields` во флоу нет — **правилом флоу поле в MTK не заполнить, для динамической записи остаётся JS на лэнде через `window.aioBus`.** Статичные значения при этом задаются как обычно: секция `User fields` есть и в MTK-формах `Advertiser`, `Destination` и лендинга — формы там те же самые ([how-to/user-fields.md](../how-to/user-fields.md)).

Механика (та же, что в [reference/sdk.md](../reference/sdk.md)): после тега `{{aio}}` на лэнде пушишь команду `trigger` — `window.aioBus.push({ type: "trigger", key: "<slug_поля>", value: "..." })`. `key` — slug уже существующего поля визита; `Trigger Field` может обновить любое поле. Значение уходит в визит на ближайшем flush (≤10 c), не мгновенно.

**Создать новое поле из MTK нельзя** — раздела управления полями в MTK-виде нет: заведённые поля видны на визитах, в форме и в колонках, но добавить новое нельзя. Новое поле — статичная настройка: приходит из шаблона либо команда AIO заводит разово.

Про SDK и `window.aioBus` — [reference/sdk.md](../reference/sdk.md); общая карта MTK — *Как устроен MTK-вид AIO: навигация, пресеты из шаблона и методы под типовые задачи*.
