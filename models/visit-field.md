# Visit Field — концепт

> Концепт: что такое поле визита и почему это субстрат, на котором держится вся система. Процедуры (создать поле, пачка полей под интеграцию, Available Values, Item Lists) — [how-to/custom-fields.md](../how-to/custom-fields.md). Плейсхолдеры — [reference/placeholders.md](../reference/placeholders.md). UI создания и редактирования поля — `Settings → Fields` в ERP.

## Суть в одном абзаце

**Visit Field — это именованный слот данных, который висит на визите.** Звучит скромно, но поля визита — это **субстрат всей системы AIO**: почти каждая сущность либо *пишет* в поля визита, либо *читает* из них. Source раскладывает в них URL-параметры, карточки `Campaign`, лендинга и `Destination` отдают вписанные в них значения, SDK пишет рантайм-данные, Fill-шаги флоу заполняют их по правилам, постбэки от брокера дописывают результат, а групперы, дистрибуции и лэнды — читают. Значение поля **накапливается вдоль пути визита**. Поэтому понять поля = понять, как данные текут через AIO.

## Как это работает на самом деле

### 1. Поле = slug + тип + атрибуты

Поле заводится в `Settings → Fields` в ERP. Ключевое в нём — **slug** (генерится из имени): это **буквальный ключ**, под которым значение живёт и адресуется везде:
- в плейсхолдерах лэнда: `{{aio.visit.fields.<slug>}}`;
- в маппинге Source (URL-параметр → slug);
- в постбэк-трекерах и Non-SDK Form Handler.

В окне `Edit field` **slug не меняется** на существующем поле — иначе порвутся все ссылки (процедура — [how-to/custom-fields.md](../how-to/custom-fields.md)).

#### `Type` — сущность-владелец поля (6 значений), она же роутит адресацию

`Type` — это **сущность, которой принадлежит поле**, а не бинарь «Visit или Campaign». Значений шесть: `Conversion` / `Visit` / `Campaign` / `Source` / `Landing` / `Destination`. Тип грузонесущий — он решает, **в каком неймспейсе поле адресуется плейсхолдером**:
- `Conversion`-поля читаются через отдельный неймспейс — `{{aio.conversion.fields.<slug>}}` (данные конверсии, не визита);
- остальные пять типов (`Visit` / `Campaign` / `Source` / `Landing` / `Destination`) читаются как поля визита — `{{aio.visit.fields.<slug>}}` — и предлагаются в пикере плейсхолдеров в группе `Visit Fields`.

По источнику дефолта значения: `Visit` — дефолт из ссылки/URL; `Campaign` — дефолт из карточки кампании (напр. FB Pixel/CAPI Token, чтобы не светить в URL); `Source` — из карточки конкретного `Source` (секция `User fields`): у самого поля дефолта нет, поэтому новый source стартует с пустым значением, и настройка с других source на него не переносится — вписывается в каждом (копия source экшеном `Copy` значения переносит), разбор — [how-to/user-fields.md](../how-to/user-fields.md); `Landing` — из карточки лендинга или его `Lander Type`; `Destination` — из карточки дестинейшена или его `Advertiser`.

Значение пяти типов живёт **на визите**, а `Conversion`-поля — на конверсии. Тип также определяет, где задаётся дефолт и каким неймспейсом поле читается. Как значение вписывается в карточку сущности — [how-to/user-fields.md](../how-to/user-fields.md). `Campaign`-поле — тоже поле визита: значение может быть перезаписано по конкретному визиту (разбор — таблица «Visit field vs Campaign field» в этом документе). Плейсхолдеры — [reference/placeholders.md](../reference/placeholders.md).

#### `Format` — как хранить + дефолт + formatter + тип плейсхолдера

`Format` — не только про отображение: он выбирает дефолт значения, formatter и тип плейсхолдера поля. Это select из ~20 значений; список **не исчерпывающий**. Грузонесущие: `String`, `Number`, `Boolean`, `Placeholder`, `Variant` (часто для `LP_*` сплитов), `Money`, `Phone`, `Ip`, `Country`, `Language`, `Destination`, `Lander`, `Percentage`, `Time Seconds`, `Progress Number` и др. При чтении плейсхолдера отсутствие значения числовых форматов (`Money`/`Number`/`Time Seconds`/`Progress Number`/`Percentage`) даёт `0`, остальных — пустую строку. Для `Destination`/`Lander` используется relation-formatter в интерфейсе; обычный плейсхолдер возвращает записанный UUID. `Phone`/`Ip` задают тип плейсхолдера, но не валидируют каждую запись поля автоматически. Полный набор форматов — [how-to/custom-fields.md](../how-to/custom-fields.md). `Format` задаётся при создании поля и меняется в `Edit field`.

### 2. Кто наполняет поле

**Кто реально пишет в поле, определяют пишущие сущности вдоль пути визита — не какая-то настройка поля.** В карточке поля есть select **`Data source`**, но он **не определяет, кто запишет значение на визит** ([how-to/custom-fields.md](../how-to/custom-fields.md)). Источник передаёт **сама пишущая сущность**: например, `Agent Init` при заходе, `HTTP Trigger`, `ERP Defined` для Fill-шагов и карточек Landing/Destination или `Form`. Source/Campaign/Flow при инициализации входят в пакет `Agent Init`. Не каждая запись хранит `source`: новый scalar entry его не содержит, а перезапись value обычного поля сохраняет прежние метаданные. Реальная картина «кто за поле отвечает» — это цикл накопления значения (Source из URL, карточки сущностей, SDK-макросы, Fill-шаги, постбэки от брокера). Пример макроса-писателя из шаблона тенанта: в Finance глобальный `AIO Save Landing Params to Visit` на лэнде с формой пишет в визит `landing_country`, `landing_language` и `landing_name` из метаданных лэнда командой `trigger`.

### 3. Цикл накопления: кто пишет, кто читает

Главная концептуальная картина — **значение поля аккретит по мере движения визита**:

```
ПИШУТ (по ходу пути):
  Source          → раскладывает URL-параметры (FB ad_name, utm)
  Карточки        → значения, вписанные в Source / Campaign / Flow / лендинг /
  сущностей         Lander Type / Destination / Advertiser
  SDK / Macros    → рантайм-данные на лэнде (поведение, технические сигналы визитора, форма)
  Fill fields /
  Fields by distr → значения по правилам/из дерева на шагах флоу  [ERP; в MTK — JS-макрос, см. ниже]
  Postback        → результат конверсии от брокера
  Стрим Visit     → данные партнёрской платформы, фоном, в том числе
  Fields            по давним визитам
ЧИТАЮТ:
  Лэнд            → {{aio.visit.fields.<slug>}} (динамический контент/оффернейм)
  Групперы        → разбивки в аналитике
  Distributions   → ветвление/контент/деньги по значению поля
  Filter          → значения полей визита
```

Отсюда вытекает самый частый дебаг-вопрос: «**поле пустое — почему?**» = найти, **кто должен был его записать** (Source-маппинг? Fill-шаг? постбэк?) и на каком этапе цепочка порвалась.

#### Как значение реально хранится на визите

Все значения полей визита лежат одним массивом записей, ключ каждой записи — внутренний `field_uuid` поля (не slug; slug транслируется в uuid при записи). Логика записи:
- **обычное поле (не `Is Registry`)** — новое значение **перезаписывает** value первой записи с этим `field_uuid` ;
- **registry-поле (`Is Registry`)** — новое значение **добавляется** новой записью (копится история `1,2,3…`);
- **точный повтор** (та же пара `field_uuid` + value) — **no-op**, не пишется второй раз;
- **пустое значение пропускается** — не затирает уже записанное.

Это механизм за вопросом «поле пустое / со старым значением — почему?» и за поведением `Is Registry` (перезапись vs накопление).

### Какое значение победит, если в поле пишут несколько источников

У обычного поля с одной записью новое значение заменяет прежнее. Если у поля сохранилось несколько записей после использования `Is Registry`, чтение одиночного плейсхолдера выбирает запись с наиболее поздним временем создания — простая перезапись value первой записи не меняет это время. Исключения — в самой логике записи: пустое значение и точный повтор не пишутся, а `Is Registry`-поле не заменяет ничего, а копит историю (раздел «Как значение реально хранится на визите» в этом документе).

Отдельно от этой очереди стоят поля родительской сущности в режиме «только родитель» (`Flow only`, `Lander type only`, `Advertiser only`): значение берётся из родительской карточки, а то, что осталось в дочерней, отбрасывается ещё до записи в визит — [how-to/user-fields.md](../how-to/user-fields.md).

### В каком порядке значения ложатся на визит — от захода до пуша

Речь о **пользовательских полях**, заведённых в `Settings → Fields`: отдельные системные атрибуты визита обновляются своими обработчиками.

Порядок фиксирован ходом визита. **При заходе** значения собираются одним пакетом, и внутри пакета каждый следующий шаг перетирает предыдущий:

1. значения из карточки `Source` — как значения по умолчанию;
2. значения из карточки `Campaign` — поверх Source: если одно поле задано и в Source, и в кампании, на визит ляжет значение кампании;
3. поля `Flow` в режиме `Flow only` — поверх кампанейских, прежнее значение кампании при этом сбрасывается;
4. параметры ссылки, чьи имена совпали со слагами полей — **поверх всего перечисленного**.

**Дальше по пути** пишут остальные:

- **обычный шаг `Content`, когда флоу отдаёт визиту лэнд** — поля карточки лендинга плюс `Lander type only`-поля его `Lander Type` (для White-лэнда в `Combined Landing` этот перенос пропускается); один раз на лэнд, повторный проход того же лэнда значения не переписывает;
- **SDK на лэнде и шаг `Fill Fields`** — в тот момент, когда визит проходит лэнд и соответствующий шаг флоу;
- **шаг `Destination`** — поля карточки дестинейшена плюс `Advertiser only`-поля его `Advertiser`; записываются до подстановки плейсхолдеров в URL и параметры дестинейшена и до сборки push-payload, поэтому `{{aio.visit.fields.<slug>}}` в URL дестинейшена видит значения его собственной карточки, а сами поля уезжают и в пуш рекламодателю (в том числе когда пуш потом отбивается по капе);
- **постбэк от брокера** — результат конверсии; позже могут прийти новые обновления с лэнда;

Trash-визиту значения карточек лендинга и дестинейшена не пишутся вовсе; значения, которые SDK шлёт с лэнда, trash-визиту тоже не пишутся — приёмник отбрасывает их с момента пометки ([reference/sdk.md](../reference/sdk.md)). Пометка `is_trash` ставится не в одной точке пути и не обязательно на входе — причина каждого визита лежит в его поле `Trash Reason` ([mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md)).

### Как URL-параметр попадает в поле визита — по совпадению слага

**Параметр запроса, имя которого буквально совпадает со слагом поля визита, записывается в это поле.** Работает на двух этапах пути визита:

- **на заходе** — параметры ссылки, по которой визит пришёл (источник записи `Agent Init`);
- **при обработке handle лэнда или Destination** — параметры запроса, которым визит дёрнул хэндл: клик по `{{link}}` или сабмит формы (источник записи `Form`). Именно так лэнд передаёт собранные на нём данные в визит — дописывая их к `{{link}}` ([reference/placeholders.md](../reference/placeholders.md)).

Условия жёсткие:

- **имя параметра = слаг поля, буквально**, включая разделители (`sub_1` ≠ `sub1`);
- поле должно существовать в этом тенанте;
- **поля с таким слагом нет — значение молча отбрасывается**, никакой ошибки не будет.

Отсюда типовой дебаг «лэнд передаёт значение, а поле пустое»: сверить слаг поля с именем параметра, а не искать проблему в SDK. Если разом пропали все параметры — скорее всего с них слетела handle-пара `{{link}}`.

### Почему параметр в URL попал не в одноимённое поле — служебные пометки

**По совпадению слага пишутся пользовательские поля, но не всякий параметр в URL работает так: часть параметров — служебные пометки, по которым поле визита проставляет сам сервер.**

Так `backfix=true` даёт поле `Backfix` ([reference/sdk.md](../reference/sdk.md)), а параметр `_hess_reason`, который PWA-макрос дописывает к ссылке продолжения флоу, — поле визита `PWA Hess Reason` (slug `pwa_hess_reason`): им размечено, каким путём визит ушёл с PWA-лэнда на оффер. Значения этого поля и как их читать — [how-to/pwa.md](../how-to/pwa.md).

### 4. Атрибуты поля (поведение)

Тоглы в `Edit field` управляют поведением поля (полные определения — [how-to/custom-fields.md](../how-to/custom-fields.md)):
- **`Is registry?`** — хранить **последовательность** значений (история `1,2,3…`) vs перезаписывать каждым новым;
- **`Is macros visible?`** — JS-доступ через объект `aio` на лэнде;
- **`Is 2FA protected?`** — значение скрывается в таблице, когда включена защита данных аккаунта и не активен `Unsecured Mode`;
- **`Is visible?`** — показывать колонку поля по умолчанию (тултип тоггла — `Visibility by default at columns etc`). На таблицах настроечных сущностей (кампании, источники, дестинейшены, лендинги) флаг колонку не включает — там она добавляется настройкой колонок ([how-to/custom-fields.md](../how-to/custom-fields.md));
- **`Available values`** — превратить строковое поле в select из фикс-списка.

Особняком — **`Is used for costs?`**: атрибут включает поле в ручной `Update Costs by <Field>` (агрегация костов по визитам с одинаковым значением поля). Механика работает, но **выставить флаг из интерфейса нельзя** — контрола у него в карточке поля больше нет ([how-to/custom-fields.md](../how-to/custom-fields.md)).

### Как шаг Fill Fields пишет значение в поле

Шаг `Fill Fields` во флоу таргетит **одно** поле визита (выбранное в настройках шага). Шаг передаёт в запись источник `ERP Defined`. Он не обязательно появится в метаданных значения: новый scalar entry не хранит source, а перезапись value обычного поля сохраняет прежние метаданные. Как значение попадает в поле, зависит от типа контента варианта:
- **`Fill Text`** — плейсхолдеры в значении **резолвятся** (напр. `{{aio.visit.fields.<slug>}}` подставляется реальным значением) перед записью;
- **`Fill Content` (Content Library) и `Fill Destination`** — контент пишется **сырьём**, без резолва плейсхолдеров.

Процедура настройки шага и разбор `Fill Fields` во флоу — [models/flow-model.md](flow-model.md); how-to по полям — [how-to/custom-fields.md](../how-to/custom-fields.md).

### 5. Поле → группер: Availability as grouper (не путать с Make analytic)

Для выбора поля **разбивкой в аналитической таблице (группером)** задайте `Edit field → Availability as grouper → Tables` в ERP. В каталоге доступны неархивные поля, к которым у пользователя есть доступ; защищённые поля туда не включаются. Детали и процедуры — [how-to/custom-fields.md](../how-to/custom-fields.md).

**Не путать с `Make analytic`** (правый клик): экшен **помечает поле аналитическим**, но **группер не включает**. Группер — это `Availability as grouper`. (Частая путаница, см. [how-to/analytics.md](../how-to/analytics.md).)

### Registry-поле в разбивке: визит попадает в одну строку, а не во все свои значения

**В отчётах у визита по каждому полю одно значение, поэтому при разбивке по registry-полю визит учитывается в одной строке, даже если у него накопилось несколько значений.** Историю значений (`Is Registry`) видно на самом визите; читать её можно через `{{aio.visit.fields.comma.<slug>}}`. Для поддерживаемых форматов также есть `{{aio.visit.fields.array.<slug>}}`, но полный набор сохранённых значений он возвращает не во всех случаях ([reference/placeholders.md](../reference/placeholders.md)), а развернуть визит по всем значениям отчёт не умеет. Частые формулировки: «в визит идут оба значения, а в статистику одно», «как учесть визит в обеих строках разбивки».

Когда нужно посчитать каждое значение отдельно (например, какую из трёх кнопок нажали), считают не поле, а события: на каждое значение — свой тип конверсии и метрика `Conversions count` на нём, общая сумма — формулой ([models/metric.md](metric.md)).

## Как Visit Field связан с остальными сущностями

- **Пишут в поля:** Source (URL→поле), карточки настроечных сущностей через секцию `User fields` ([how-to/user-fields.md](../how-to/user-fields.md)), SDK/Macros (рантайм), Fill fields / Fields by distribution (шаги флоу, ERP), постбэки (конверсии), стримы `Visit Fields` (данные партнёрки, *уточните у поддержки*).
- **Читают поля:** лэнды (плейсхолдеры), групперы (аналитика), дистрибуции (ветвление/деньги), Filter (по значениям полей визита).
- **slug — универсальный ключ**, связывающий URL ↔ поле ↔ плейсхолдер ↔ постбэк.
- Поле — **горизонтальный слой данных**, который используют разные сущности AIO.

## Чем Visit Field отличается от смежных понятий

| Не путать | Разница |
|---|---|
| **Поле vs его значение** | Поле — *слот* (slug+тип, заведён один раз). Значение — то, что в него записали для конкретного визита (у каждого визита своё). |
| **Visit field vs Campaign field** | Оба — поля **на визите** (значение хранится по каждому визиту отдельно). Разница только в источнике дефолта: `Visit`-поле заполняется из ссылки/URL, а `Campaign`-поле берёт дефолт из карточки кампании (FB Pixel/CAPI Token и т.п. — один дефолт на весь трафик кампании, его не нужно передавать в URL; при заходе копируется на визит). Значение `Campaign`-поля можно перезаписать для отдельного визита (в том числе целью шага `Fill Fields`) — это **не** общее неизменяемое значение на всю кампанию. |
| **Availability as grouper vs Make analytic** | Первое (внутри поля) — *задаёт доступность группировки*: для аналитической таблицы нужен `Tables`. Второе (экшен) — *помечает поле аналитическим*, но группер не включает. |
| **Поле vs плейсхолдер** | Плейсхолдер (`{{aio.visit.fields.<slug>}}`) — *способ прочитать* значение поля на лэнде. Само поле — хранилище. |

### Колонки визита, которые путают с полями — Language и Cost

Отдельно стоят две **колонки самого визита** (не атрибуты поля-концепта), которые часто путают со смежными настройками:

| Не путать | Разница |
|---|---|
| **`Language`-колонка визита vs Form i18n** | Колонка `Language` в `Tracker → Visits` — это **язык браузера визитора** (записан на визите при его создании; откуда именно берётся — раздел «Откуда берётся `Language` визита» в этом документе). Не путать с языком SDK-формы / `Static Language Country` / тегом-категорией лэнда — это про переводы контента, а не про записанный на визите атрибут. |
| **`Cost`-колонка визита vs cost-атрибуция** | Колонка `Cost` в визите — это **расход, отнесённый к этому визиту** (метрика для оценки прибыли/убытка Campaign). Не путать с механикой атрибуции расходов (`Is used for costs?` / `Update Costs by <Field>`): первое — *показанное на визите значение*, второе — *как поле участвует в ручном проставлении costs*. |

### Откуда берётся `Language` визита — из заголовка браузера

**Колонка `Language` в `Tracker → Visits` — это язык браузера визитора: первый короткий код после разбора заголовка `Accept-Language` того запроса, которым визит создался. При разборе учитывается приоритет кодов; региональная часть отбрасывается.** Это не язык устройства или ОС и не производная от гео: гео определяется отдельно, по IP, и с языком не связано.

Значение пишется один раз, при создании визита, и дальше не меняется. Визитор переключил язык браузера посреди сессии — в визите останется тот код, который пришёл на заходе.

`Accept-Language` настраивается на стороне визитора и подделывается, поэтому таргетинг и разбивки по языку на этом поле — мягкий сигнал, а не гарантия реального языка человека.

## Подводные камни Visit Field — частые ошибки настройки

- **Поле под маппинг/интеграцию заводи ЗАРАНЕЕ** — значения ответа не запишутся в неизвестные поля (самая частая ошибка первичной настройки); подробнее.
- **slug не меняется в `Edit field`** на существующем поле ([how-to/custom-fields.md](../how-to/custom-fields.md)); если уже в плейсхолдерах — придётся править лэнды.
- **`required` на Visit Field напрямую нельзя** — только через `Link Generator` (обязательность параметра в ссылке). Не путать с `Required` на Form Control в Form Builder.
- **`Make analytic` ≠ группер** — если ждёшь разбивку в аналитической таблице, выбери `Tables` в `Availability as grouper`.

## Как записать значение в поле визита по правилу в MTK

В MTK-виде нет редактора флоу, где можно настроить шаг `Fill Fields`. Для динамической записи поля можно использовать JS на лэнде через `window.aioBus`. Статичные значения при этом задаются как обычно: секция `User fields` есть и в MTK-формах `Advertiser`, `Destination` и лендинга — формы там те же самые ([how-to/user-fields.md](../how-to/user-fields.md)).

Механика (та же, что в [reference/sdk.md](../reference/sdk.md)): после тега `{{aio}}` на лэнде пушишь команду `trigger` — `window.aioBus.push({ type: "trigger", key: "<slug_поля>", value: "..." })`. `key` — slug уже существующего поля визита; `Trigger Field` обновляет распознанное по slug неархивное поле, доступное этому визиту; неизвестные поля и обновления Trash-визита пропускаются. По умолчанию SDK отправляет накопленные значения каждые 10 секунд и при `pagehide`. Запись в визит происходит после обработки на сервере; это не гарантия записи за 10 секунд.

**В MTK-виде нет интерфейса создания нового поля** — раздела управления полями там нет: заведённые поля используются на визитах, в форме и в колонках. Новое поле — статичная настройка: приходит из шаблона тенанта при его создании либо команда AIO заводит разово. Под произвольные параметры ссылки в MTK-шаблонах уже заведены свободные поля `sub1`…`sub15`: параметр с таким именем в ссылке кампании ложится в одноимённое поле визита.

Про SDK и `window.aioBus` — [reference/sdk.md](../reference/sdk.md); общая карта MTK — *Как устроен MTK-вид AIO: навигация, пресеты из шаблона и методы под типовые задачи*.
