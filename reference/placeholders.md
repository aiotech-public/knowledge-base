# Placeholders в AIO

Плейсхолдеры — это то, чем вы связываете статический лэнд с рантаймом AIO: переходы по флоу, SDK-форму, пути к файлам на CDN, значения полей визита. Вы пишете их прямо в HTML/JS/CSS, а AIO подставляет реальные значения. Различаются они **моментом подстановки** — это важно понимать, чтобы не искать значение не там: часть при процессинге ZIP, часть AIO подставляет при отдаче лэнда визиту, часть исполняется в runtime на стороне визита.

Плейсхолдеры делятся на четыре семейства: лэнд-плейсхолдеры (`{{link}}`, `{{form}}`, `{{aio}}`, `{{cdn}}`), локальные макросы (`{{aio:macros:<slug>}}`), поля визита (`{{aio.visit.*}}`) и Source-link плейсхолдеры в JSON-коде Source. Плюс `vue.`-форма для реактивных Vue.js-шаблонов на лэнде. К любому плейсхолдеру данных `{{aio.*}}` можно дописать **модификатор** через двоеточие — `{{aio.visit.uuid:urlencode}}`, `{{aio.visit.landing_human_ids:json_array_first}}` (раздел «Модификаторы плейсхолдеров» этого документа). Отдельным разделом в конце — **спинтакс** в текстах рассылок (`{вариант 1|вариант 2}`): это не плейсхолдер, а синтаксис случайного выбора варианта, и живёт он только в сообщениях.

## Как работают лэнд-плейсхолдеры `{{link}}`, `{{form}}`, `{{aio}}`

Лэнд-плейсхолдеры подставляются при отдаче лэнда визиту (значения подставляет AIO) или при процессинге ZIP.

| Плейсхолдер | Где используется | Кто и когда обрабатывает |
|---|---|---|
| `{{link}}` | в HTML лэнда (`href` ссылок) | AIO при отдаче лэнда — подставляет query-строку с handle-парой (переход по флоу) |
| `{{form}}` | в HTML лэнда | AIO — спавнит SDK-форму |
| `{{aio:head}}` | в `<head>` лэнда | автоматически вставляется при процессинге ZIP |
| `{{aio}}` | перед `</body>` лэнда | автоматически вставляется при процессинге ZIP |
| `{{cdn}}` | в JS/CSS файлах внутри ZIP | процессинг ZIP — заменяет на полный путь к CDN |
| `{{cdn-lp-folder}}` | в inline-скриптах в `index.html` | runtime (на стороне визита) |
| `{{aio:macros:<slug>}}` | в HTML лэнда | AIO — подгружает конкретный макрос локально |
| `{{settings.<key>}}` | в HTML лэнда | AIO — значение из Content Settings лэнда (схема Lander Type) |

### Кто раскрывает плейсхолдеры — AIO, а не агент

**Плейсхолдеры раскрывает AIO: на агент контент и редиректы приезжают уже собранными, и агент отдаёт визиту готовый HTML как есть** ([models/server.md](../models/server.md)). Единственная правка HTML на стороне агента — правка вида CDN-путей лэнда, если у типа лэнда включён флаг `Temp CDN used`: файлы отдаются те же, на раскрытие плейсхолдеров это не влияет (флаг как часть типа — [models/landing.md](../models/landing.md)).

Практический вывод для диагностики: если плейсхолдер приехал визиту нераскрытым (в `View Source` видно `{{...}}`), разбирайся на стороне AIO — со схемой `Lander Type`, полем визита или настройкой шага, а не с сервером и не с агентом.

### Плейсхолдеры данных визита и генерации ссылки — сводка

Отдельные семейства: поля визита `{{aio.visit.*}}`, Source-link плейсхолдеры в JSON-коде Source и Vue.js-форма. Разбор каждого — в разделах ниже.

| Плейсхолдер | Где используется | Кто и когда обрабатывает |
|---|---|---|
| `{{aio.visit.uuid}}` | в Destination URL / Simple Redirect | AIO — подставляет UUID визита |
| `{{aio.visit.fields.<field>}}` | в Destination URL / templates | AIO — значение поля визита |
| `{{aio.visit.query}}` | в Destination URL / templates | AIO — все захваченные параметры визита одним JSON-объектом (не строкой `a=1&b=2`) |
| `{{aio.visit.query.<key>}}` | в Destination URL / templates | AIO — сырой URL-параметр (напр. `{{aio.visit.query.lp}}`) |
| `{{aio.visit.fields.<field>.<key>}}` | то же + Content Library | AIO — значение из Content Library item |
| `{{aio.campaign.uuid}}` / `{{aio.source.uuid}}` / `{{aio.user.uuid}}` / `{{aio.replace}}` | в JSON-коде Source (`links[].parameters`) | Link Generator — при генерации ссылки |
| `{{vue.aio.visit.<...>}}` | в HTML лэнда с `id="vue"` | Vue.js на стороне визита |

## Лэнд-плейсхолдеры — справочник по каждому

### Как вести переходы по флоу через `{{link}}`

Место, где визиту нужно уйти на следующий шаг флоу. `{{link}}` ставится **значением атрибута `href`** (`<a href="{{link}}">`) вместо захардкоженного статичного URL из исходного лэнда — это не альтернатива тегу `<a href>`, а то, что подставляется внутрь него.

**Пример использования:**
```html
<a href="{{link}}" class="cta">Get Started</a>
```

**Как работает:** AIO подставляет вместо `{{link}}` **query-строку, а не готовый URL** (агенту лэнд приезжает уже с подставленным значением). Раскрывается в `?<ключ>=<значение>&<ключ>=<значение>` — две пары: первая говорит AIO, какой это визит и на каком шаге флоу он сейчас, вторая — какой хэндл дёрнут (`Handle-link`). Обе пары — хэши, у каждого визита свои.

Поэтому `<a href="{{link}}">` даёт ссылку на **тот же адрес** с этой query: визит никуда не «уезжает по ссылке» — он повторно стучится на свой же URL, а агент по параметрам двигает его по флоу и отвечает командой (редирект на оффер, контент следующего шага). Механика агента — [models/server.md](../models/server.md).

**Если на лэнде несколько кнопок с переходом** — есть два пути:

- **Все через `{{link}}`** — все кнопки ведут в одно и то же место (следующий шаг по флоу). Дефолтный путь.
- **Через пронумерованные `{{link:N}}`** — `{{link:1}}`, `{{link:2}}`, ... до 5 разных линков. Каждый номер — отдельный transition во флоу (`Link 1`, `Link 2`, ...), может вести в разные наборы офферов. На шаге с `{{link:N}}` обязателен базовый `Handle` — fallback, если ни один пронумерованный `Handle-link N` не подошёл. Глоссарий — [reference/glossary.md](glossary.md) → `{{link:N}} + Link N`.

### Почему нельзя пересобирать ссылку из `{{link}}` — теряется handle

**Всё, что несёт `{{link}}`, лежит в его query-строке: сотрёшь её — переход не сработает.** Симптом: визит не уходит со шага, а параметры, которые лэнд хотел передать, не попадают в поля визита.

Самая частая ловушка — **HTML-форма с `method="GET"` и `action="{{link}}"`**: при GET-сабмите браузер **выбрасывает query у `action`** и подставляет на её место поля формы, так что handle-пара исчезает. По той же причине нельзя «чистить» ссылку, обрезать её или собирать заново из кусков.

Как правильно:

- **дописать свои параметры** — через `&`, потому что `{{link}}` уже начинается с `?`: `{{link}}&first_name=Ivan`;
- **кастомная `<form>`** — не вешать на `action="{{link}}"`, а подложить handle скрытыми полями (`{{link_key}}` / `{{link_value}}`, ниже);
- **сабмит из JS** — `{{link-form}}` (ниже).

### Как подложить handle в кастомную форму — `{{link_key}}` и `{{link_value}}`

**`{{link_key}}` и `{{link_value}}` отдают ту же handle-пару по частям — чтобы положить её скрытым полем в свою `<form>`.** SDK-форма проставляет это себе сама (`handle.key` / `handle.value` + `_aio_handle` — [reference/sdk.md](sdk.md)); кастомной форме их нужно поставить руками, иначе GET-сабмит потеряет handle и сабмит не станет переходом `Handle-form`:

Дальше в форме идут обычные поля (имя, телефон и т.д.):

```html
<form method="GET">
  <input type="hidden" name="{{link_key}}" value="{{link_value}}">
  <input type="hidden" name="_aio_handle" value="form">
  <input type="text" name="first_name">
  <input type="text" name="phone">
</form>
```

Слаги полей формы должны совпадать со слагами полей визита — иначе значения не запишутся ([models/visit-field.md](../models/visit-field.md)).

### Как вызвать сабмит формы из JS без SDK-формы — `{{link-form}}`

**`{{link-form}}` — готовая query-строка с form-хэндлом: для случаев, когда сабмит формы нужно выполнить кодом, а самой SDK-формы на лэнде нет.** Отличается от `{{link}}` только тем, какой переход дёргает: `Handle-form` вместо `Handle-link`.

```js
fetch('{{link-form}}&first_name=Ivan&phone=' + encodeURIComponent(phone));
```

### Как вернуть визит, когда страница уже закрыта — `{{link:s:permanent}}` и `{{link:h:permanent}}`

**В этих ссылках визит опознаётся по сессии (`sess` / `hess`), а не по паре «визит + текущий шаг».** Отсюда AIO берёт ссылки, которые SDK использует в PWA (`pwa.session.sess` / `pwa.session.hess` — [how-to/pwa.md](../how-to/pwa.md)): установленное приложение открывают уже после того, как исходная страница закрыта.

- `{{link:s:permanent}}` (`sess`) — **вход в стейт** (state-enter): визит заново входит в свой текущий шаг флоу. Это стартовый URL самой PWA.
- `{{link:h:permanent}}` (`hess`) — **вызов хэндла**: визит идёт дальше по флоу (на оффер).
- Нумерованные варианты — `{{link:s:permanent:N}}` и `{{link:h:permanent:N}}`, `N` = 1…5, по аналогии с `{{link:N}}`.

### Как подключить SDK-форму через `{{form}}`

Место AIO SDK-формы на лэнде. Заменяет статичную HTML-форму.

**Пример:**
```html
<div class="form-wrapper">
  {{form}}
</div>
```

**Как работает:** SDK подгружает форму, выбранную для текущей кампании. Конкретная форма привязывается к флоу через шаг `Fill Form` либо через выбор формы в `Content` шаге (`Edit Flow → Content → Settings → Forms`).

**Несколько разных форм на лэнде — пронумерованные `{{form:N}}`.** Для лэнда с несколькими формами используются `{{form:1}}`, `{{form:2}}`, ... до 5. Каждый номер даёт отдельный `Handle` в переходах флоу (`Handle form 1`, `Handle form 2`, `Handle form 3`, `Handle form 4`, `Handle form 5`), плюс есть `Handle all forms` — по аналогии с `{{link:N}}` ([reference/glossary.md](glossary.md) → `{{link:N}} + Link N`). Так одна форма может вести в один шаг флоу, другая — в другой.

**Одна и та же форма в нескольких местах лэнда — повторяй `{{form}}`.** Несколько инстансов одного плейсхолдера `{{form}}` (без номера) выводят одну и ту же форму в разных местах на одном лэнде — отдельные `Handle` для этого не нужны.

**Без `{{form}}` форма не отрисуется**, даже если в флоу настроена.

**Альтернатива — HTML-форма с `Non-SDK Form Handler`** (`{{aio:macros:nonsdk_form_handler}}`): цепляется только к тегу `<form>`, не к `<div>`; активно не развивается. Полная механика — [how-to/forms.md](../how-to/forms.md).

### Что делают `{{aio:head}}` и `{{aio}}` — служебные плейсхолдеры

**Если `{{aio}}` нет — SDK не подгрузится, формы не работают, Backfix не работает, аналитика поломана.** Это критичный плейсхолдер.

Два плейсхолдера, **которые автоматически вставляются** при процессинге ZIP. Руками их добавлять не нужно — если ты пишешь лэнд с нуля и хочешь явно проконтролировать места, можешь вставить.

- `{{aio:head}}` — в `<head>` лэнда. Сюда рендерятся макросы с `Preferred Placement: head` (задаётся в `Content → Macros → Preferred Placement`).
- `{{aio}}` — перед `</body>` (footer placement). Сюда рендерятся макросы без явного preferred placement (по дефолту — footer), включая весь **AIO SDK Macros Collection**.

### Когда нужен `{{cdn}}` — замена путей в JS/CSS при загрузке ZIP

Подставляется на этапе **процессинга ZIP** при загрузке. Заменяется на полный путь к CDN.

**Когда нужен:** внутри JS / CSS файлов, когда из скрипта или стиля нужна ссылка на файл, лежащий рядом в архиве.

**Пример** (внутри `script.js` в архиве):
```javascript
const img = '{{cdn}}/assets/hero.png';
```

**Когда НЕ нужен:** в обычных HTML / CSS пути обрабатываются автоматически. AIO сам заменяет относительные пути на CDN-ссылки.

### Когда нужен `{{cdn-lp-folder}}` — замена путей в inline-скриптах в runtime

Подставляется в **runtime** (на стороне визита), не при процессинге.

**Когда нужен:** в inline-скриптах прямо в `index.html`, которые сами обращаются к файлам и не должны вшивать конкретный путь.

**Пример:**
```html
<script>
  fetch('{{cdn-lp-folder}}/data.json').then(...);
</script>
```

**Чем отличается от `{{cdn}}`:**
- `{{cdn}}` — внутри файлов JS/CSS, **процессится при загрузке ZIP** (вшивается полный путь сразу).
- `{{cdn-lp-folder}}` — внутри `index.html` inline-скриптов, **процессится на стороне визита** (подставляется на лету, а не вшивается при загрузке).

### Как подставить Content Settings лэнда — `{{settings.<key>}}`

**`{{settings.<key>}}` подставляет значение из Content Settings конкретного лэнда — тех полей, которые задаёт схема его `Lander Type` ([models/landing.md](../models/landing.md)).** Типичное применение — название и картинка товара, вынесенные из вёрстки в настройки, чтобы один лэнд переиспользовать под разные офферы.

```html
<img src="{{settings.productImage}}" alt="{{settings.productName}}">
```

Ключ совпадает со схемой **буквально**: `{{settings.productName}}` возьмёт `productName` и не возьмёт `product_name`. Подстановка серверная, при отдаче лэнда; внутрь самого значения можно класть плейсхолдеры визита (`{{aio.visit.*}}`) — они тоже раскроются.

**Если ключа в схеме типа нет или он не заполнен у этого лэнда, плейсхолдер остаётся в HTML литеральной строкой** — `{{settings.productName}}`, а не пустым значением. Дальше эта строка молча уезжает в ссылки и в поля визита как мусор. Поэтому проверяй результат в отданном лэнде (`View Source`), а не в редакторе, и не подставляй значение в URL или в поле визита, не убедившись, что оно раскрылось.

## Как подключить локальный макрос через `{{aio:macros:<slug>}}`

Локальный вызов конкретного макроса из `Content → Macros`. Используется для макросов, у которых `Global: false` — они не подгружаются автоматически на все лэнды, а вызываются вручную где нужно.

**Пример:**
```html
{{aio:macros:my_custom_pixel}}
```

**Slug макроса** — задаётся при создании макроса в `Content → Macros` (в MTK макросы под `Settings → Macros`). Через него макрос и вызывается.

**Когда использовать:** кастомный JS-код, который нужен только на части лэндов (особый пиксель партнёрки, специальный tracking, и т.п.). Если макрос нужен везде — проще сделать его глобальным, тогда вызов не нужен.

## Как подставить поля визита через плейсхолдеры `{{aio.visit.*}}`

Используются для подстановки данных визита в:
- URL дестинейшна (Simple Redirect режим)
- Шаблоны интеграций с третьими системами
- Постбэки

**Корректный способ хранить произвольный новый URL-параметр** — завести **отдельное поле визита** (`Settings → Fields`). Полей визита **лимита нет** (в отличие от sub-ов в трекерах). Если параметр пришёл без одноимённого поля — **не теряется**, остаётся в `aio.visit.query`.

### Основные поля визита в `{{aio.visit.*}}`

| Плейсхолдер | Что подставляет |
|---|---|
| `{{aio.visit.uuid}}` | UUID самого визита (по нему AIO потом мэтчит конверсии); это же — **Click ID** в терминах AIO |
| `{{aio.visit.fields.phone}}` | поле телефона |
| `{{aio.visit.fields.email}}` | поле email |
| `{{aio.visit.fields.first_name}}` | поле имени |
| `{{aio.visit.fields.last_name}}` | поле фамилии |
| `{{aio.visit.fields.<любое_поле>}}` | любое поле визита, заведённое в Settings → Fields |

`phone` / `email` / `first_name` / `last_name` — это **поля** (через `fields.`), а не системные плейсхолдеры: они приходят из дефолтной формы, но технически это те же кастомные поля визита.

Через `fields.` читаются поля **пяти** типов — `Visit`, `Campaign`, `Source`, `Landing`, `Destination`: все они живут в неймспейсе визита, поэтому у поля типа `Landing` плейсхолдер такой же, `{{aio.visit.fields.<slug>}}`, и в пикере-гексагоне оно лежит в группе `Visit Fields` (глобальные — `Visit Global Fields`). Отдельный неймспейс только у типа `Conversion` — `{{aio.conversion.fields.<slug>}}`. Что означает `Type` поля и откуда берётся его значение — [models/visit-field.md](../models/visit-field.md).

**Click ID = Visit UUID.** Когда внешняя платформа / брокер / API-шаблон (например, при создании Destination `By Integration` в `Tracker → Destinations`) просит передать «Click ID» — в AIO под этим именем выступает именно Visit UUID, то есть `{{aio.visit.uuid}}`. Список доступных AIO-плейсхолдеров в форме создания дестинейшна открывается по иконке-гексагону.

**Пример в Simple Redirect дестинейшне:**
```
https://broker.example.com/api/leads?
  visit_id={{aio.visit.uuid}}&
  phone={{aio.visit.fields.phone}}&
  email={{aio.visit.fields.email}}
```

### Плейсхолдеры самого дестинейшена — `{{destination_domain}}`, `{{destination_human_id}}`, `{{destination_name}}`

**В поле `URL Parameters` адвертайзера с `Integration type` = `Simple Redirect` кроме обычных `{{aio.visit.*}}` работают три плейсхолдера уровня дестинейшена: `{{destination_domain}}` (хост из его `Redirect URL`), `{{destination_human_id}}` и `{{destination_name}}`.** Тултип поля перечисляет их дословно: `Extra placeholders: {{destination_domain}}, {{destination_human_id}}, {{destination_name}}`.

Больше нигде эти три не разворачиваются: в полях других интеграций дестинейшена такая запись уедет получателю строкой как есть. Правила склейки `URL Parameters` со ссылкой дестинейшена — [how-to/destinations.md](../how-to/destinations.md).

### Прямые системные плейсхолдеры (не через `fields.`)

Кроме полей визита есть **системные** плейсхолдеры — данные, которые AIO пишет сам. Обращение к ним **прямое**, без `fields.`. Актуальный полный список всегда виден в UI-пикере (иконка-гексагон) — он подтягивается динамически; ниже — самые ходовые.

- **Гео / устройство:** `{{aio.visit.country_code}}`, `{{aio.visit.location_city}}`, `{{aio.visit.location_postal_code}}`, `{{aio.visit.language_code}}`, `{{aio.visit.ip_address}}`, `{{aio.visit.useragent}}`, `{{aio.visit.os_name}}`, `{{aio.visit.os_version}}`, `{{aio.visit.device_name}}`, `{{aio.visit.brand_name}}`, `{{aio.visit.model}}`, `{{aio.visit.client_name}}`.
- **Путь / инфраструктура визита:** `{{aio.visit.path}}`, `{{aio.visit.initial_path}}`, `{{aio.visit.domain}}`, `{{aio.visit.campaign_human_id}}`, `{{aio.visit.created_at}}`, `{{aio.visit.is_backfix}}`, `{{aio.visit.is_push_subscribed}}`, `{{aio.visit.pwa_app_name}}`, `{{aio.visit.pwa_icon_url}}`, `{{aio.visit.form_uuid}}`, `{{aio.visit.flow_uuid}}`.
- **Пуш в Destination / деньги:** `{{aio.visit.destination_url}}`, `{{aio.visit.destination_external_id}}`, `{{aio.visit.destination_uuid}}`, `{{aio.visit.revenue}}`, `{{aio.visit.payout}}`.

### Плейсхолдеры кампании, конверсии, Source и текущего времени — `{{aio.campaign.*}}`, `{{aio.conversion.*}}`, `{{aio.source.*}}`, `{{aio.common.*}}`

Кроме данных визита системные плейсхолдеры есть у кампании, конверсии и Source, плюс группа `Common` с текущим временем; обращение тоже прямое, без `fields.`, ключи — как в UI-пикере.

- **Кампания:** `{{aio.campaign.uuid}}`, `{{aio.campaign.name}}`, `{{aio.campaign.country_code}}`, `{{aio.campaign.language_code}}`.
- **Конверсия:** `{{aio.conversion.uuid}}`, `{{aio.conversion.conversion_type_uuid}}`, `{{aio.conversion.revenue}}`, `{{aio.conversion.payout}}`, `{{aio.conversion.created_at}}`.
- **Source / время:** `{{aio.source.uuid}}`, `{{aio.source.name}}`, `{{aio.common.current_timestamp}}`, `{{aio.common.current_date}}`, `{{aio.common.current_day_hour}}`, `{{aio.common.current_week_day}}`.

### В URL уехало `%5B309889%5D` вместо ID лэнда — массивные плейсхолдеры `landing_human_ids`, `landing_uuids`, `landing_type_uuids`, `flow_uuids`

**Четыре системных плейсхолдера визита несут не одно значение, а JSON-массив, поэтому без модификатора подставляются со скобками — `[309889]`, — а после URL-кодирования в `URL Parameters` уезжают рекламодателю как `%5B309889%5D`.** Один элемент берётся модификатором позиции: `{{aio.visit.landing_human_ids:json_array_first}}` → `309889` (раздел «Модификаторы плейсхолдеров» этого документа).

- `{{aio.visit.landing_human_ids}}` (в пикере `Landing Human IDs`) — human ID лэндов, которые визит прошёл, в порядке прохода; повторный заход на уже пройденный лэнд в массив не добавляется.
- `{{aio.visit.landing_uuids}}` (`Landing UUIDs`) и `{{aio.visit.landing_type_uuids}}` (`Landing Type UUIDs`) — те же лэнды и их `Lander Type` в виде UUID.
- `{{aio.visit.flow_uuids}}` (`Flow UUIDs`) — флоу визита по уровням вложенности: первый элемент — флоу кампании, дальше — по одному `Sub flow` на уровень (вход в другой `Sub flow` того же уровня замещает запись, а не добавляет). Флоу кампании одним значением — `{{aio.visit.flow_uuid}}`.

UUID внутри массива без модификатора теряют кавычки (`[abc,def]`): чистка `default` снимает кавычки, а скобки оставляет.

### Как отдать рекламодателю реферер — `{{aio.visit.fields.referer}}`

**Реферер визита хранится в системном поле `Referer` (slug `referer`; в пикере — группа `Visit Global Fields`), поэтому плейсхолдер — `{{aio.visit.fields.referer}}`; отдельного `{{aio.visit.referer}}` нет.** В поле лежит заголовок `Referer` первого запроса визита на домен кампании — адрес, с которого пришёл клик, если браузер его передал, — а не адрес лэнда.

Сам переход от AIO реферер рекламодателю не передаёт: страницы и редиректы AIO уходят с политикой `no-referrer`, и отключить её нельзя. Если партнёр ждёт реферер, его передают параметром — `ref={{aio.visit.fields.referer}}` в `URL Parameters`. Что именно доезжает до рекламодателя и как это устроено — [how-to/destinations.md](../how-to/destinations.md); два поля `Referer` у визита (колонка и системное поле) — [models/visit.md](../models/visit.md).

### Как разделить трафик по версии ОС, бренду и модели устройства — `os_version`, `brand_name`, `model`

**Кроме `{{aio.visit.os_name}}` и `{{aio.visit.device_name}}` у визита есть три более точных признака устройства: `{{aio.visit.os_version}}` (в пикере — `Os Version`), `{{aio.visit.brand_name}}` (`Brand Name`) и `{{aio.visit.model}}` (`Model`), все три в группе `Visit`.** Значения AIO записывает в визит при его регистрации, распознавая устройство визитора, — поэтому они заполнены и на уже накопленном трафике, а не только на новом.

В конструкторе правил значение `Brand Name` выбирается из готового списка брендов устройств, а не вводится строкой, — так же, как у `Os Name` и `Device Name`.

Доступны эти три ключа в контекстах `Macros`, `Landing`, `Destination`, `Tracker` и `Campaign Split` — то есть на лэнде, в шаблонах дестинейшена и трекера и в условиях сплитов. **В деревьях дистрибуций (`Distribution Revenue`, `Distribution Payout`, `Distribution Fill Field`, `Distribution Campaign Content`, `Distribution Direct Traffic`) их нет** — как нет там и давних `{{aio.visit.os_name}}` и `{{aio.visit.device_name}}`. Развести дистрибуцию по устройству не получится — из признаков визитора в её дереве доступно, например, гео `{{aio.visit.country_code}}`.

### Иконка PWA-приложения визита — `{{aio.visit.pwa_icon_url}}`

**`{{aio.visit.pwa_icon_url}}` (в пикере — `PWA App Icon`, группа `Visit`) подставляет иконку PWA-приложения, которое прошёл визит** — пара к `{{aio.visit.pwa_app_name}}`. Значение AIO пишет визиту один раз, в момент прохода PWA-лендинга: берётся иконка `icon512x512` из manifest-блока контента лендера (побеждает последний такой блок) — тот же источник, что и у самого манифеста ([how-to/pwa.md](../how-to/pwa.md)). У визита, который PWA-лендинг не проходил, и у PWA без manifest-блока с `icon512x512`, значение пустое.

Контексты — те же, что у `{{aio.visit.pwa_app_name}}`: `Macros`, `Landing`, `Destination`, `Tracker`, `Campaign Split`. Типичное применение — подставить плейсхолдер в поле `Push Icon` шаблона сообщения, чтобы уведомление пришло с иконкой того самого приложения ([mechanics/notifications-flow.md](../mechanics/notifications-flow.md)).

**Колонка `PWA App Icon` (категория `PWA`) в таблицах визитов и `Marketing → Messages` показывает исходный адрес картинки, и со значением плейсхолдера он не совпадает:** в само уведомление адрес отдаётся через домен визита. Сверять два значения «в лоб» не нужно.

### В селектах правил доступен не весь список полей

Плейсхолдеры выше — для **шаблонов** (Destination URL, постбэки, лэнды). Поле-пикеры **правил и условий** (Allowance Rules, условия шага Filter/Condition, условия дистрибуций, Fill Fields) показывают **контекстно-отфильтрованный субсет**: скалярные поля визита/кампании/сорса (системные + кастомные не-registry). **Не** доступны как ключ правила: registry/мультизначные поля (лендинги, типы лендингов, варианты, список флоу) и их `.array`/`.comma`-варианты, а также поля конверсии. Конкретный набор зависит от контекста (условие фильтра ≠ дистрибуция ревенью ≠ Fill Field).

**`Backfix` теперь можно использовать как ключ правила.** Плейсхолдер `{{aio.visit.is_backfix}}` (поле визита `Backfix`, *уточните у поддержки*) раньше был доступен только в шаблонах лэндов, Destination и трекера — теперь он есть и в пикерах **сплитов кампании** и **дистрибуций**: выбор контента, `Fill Fields` и правила прямого трафика. То есть визиты, прошедшие через Backfix, можно разводить отдельной веткой, а не только помечать.

Не-registry поля типов `Landing` и `Destination` в этот субсет тоже входят — но не везде, а в сплите кампании и в дистрибуциях `Campaign Content`, `Revenue`, `Payout`, `Fill Field`. Так значение, заданное в карточке лендинга или дестинейшена, становится ключом правила наравне с обычным полем визита.

### Почему в конструкторе условий `Manage rule` разный набор плиток готовых правил

**Конструктор условий (диалог `Manage rule`) открывается экраном плиток готовых правил, и набор плиток зависит от контекста: плитка есть в списке, только если в этом контексте доступны ВСЕ её плейсхолдеры** — поэтому в сплите кампании плитки все, а в дереве дистрибуции их меньше. Состав плиток, их ключи, оператор упрощённой формы и всегда доступная плитка `Custom` (полный конструктор из любых плейсхолдеров и операторов) — в [models/flow-model.md](../models/flow-model.md).

В контексте `Campaign Split` — условия кампании, правила вариантов и `Allowance Rules` шага флоу, Content Splits — доступны все плитки.

В дереве дистрибуции набор у́же и зависит от типа дерева:
- плиток по устройству (`Device Name`, `OS Name`, `OS Version`) нет ни в одном контексте дистрибуции;
- `Visit Country` — во всех пяти (`Distribution Revenue`, `Distribution Payout`, `Distribution Campaign Content`, `Distribution Fill Field`, `Distribution Direct Traffic`);
- `Visit Language` и `Campaign Owner` — во всех, кроме `Distribution Direct Traffic`;
- `Visit Domain` (плитка собрана над ключом `{{aio.visit.domain_uuid}}`) — только в `Distribution Campaign Content`, `Distribution Fill Field` и `Distribution Direct Traffic`;
- составная плитка доступна там, где доступны обе её части.

Дистрибуция типа `Auto Rules` этот конструктор не открывает вовсе: условия её правил собираются отдельным редактором со своим набором операндов ([how-to/auto-rules.md](../how-to/auto-rules.md)).

### Как прочитать накопленную историю registry-поля — `.comma.` и `.array.`

`{{aio.visit.fields.<slug>}}` отдаёт **одно** (последнее) значение поля. Если у поля включён `Is Registry` ([models/visit-field.md](../models/visit-field.md)), оно копит историю значений (`1,2,3…`) — и на неё есть отдельные плейсхолдеры:
- `{{aio.visit.fields.comma.<slug>}}` — вся история **через запятую** (`1,2,3`);
- `{{aio.visit.fields.array.<slug>}}` — история **массивом** (для Destination / Placeholder / скалярных registry-полей).

Для `Conversion`-полей (`Type = Conversion`) те же формы живут в неймспейсе конверсии: `{{aio.conversion.fields.comma.<slug>}}` и `{{aio.conversion.fields.array.<slug>}}`. Эти доп-плейсхолдеры появляются только у registry-полей; у обычного поля их нет.

### Click ID (Visit UUID) ≠ FB Click ID (FBC)

Не путать AIO Click ID (`{{aio.visit.uuid}}`) с `FB Click ID` (FBC) — это отдельный параметр для FB CAPI. Механика FBC/CAPI — [reference/sdk.md](sdk.md).

### Как достать сырой URL-параметр визита через `{{aio.visit.query.<key>}}`

`aio.visit.query` — в первую очередь **шаблонный плейсхолдер**. Форма с ключом `{{aio.visit.query.<key>}}` подставляет значение одного параметра; бэйр-форма `{{aio.visit.query}}` — все захваченные параметры **одним JSON-объектом** (`{"lp":"1","sub1":"abc"}`), а не строкой `lp=1&sub1=abc`; без модификатора кавычки из него срезаются (`{lp:1,sub1:abc}`), валидный JSON даёт `{{aio.visit.query:raw}}` (раздел «Модификаторы плейсхолдеров» этого документа). Обе формы резолвит **AIO на стороне сервера** по query, захваченному при создании визита, поэтому значение отдаётся даже если параметр скрыт из адресной строки (например при `enableStrangeUrlParameters=true`).

На JS-стороне (`window.aio`) `aio.visit.query` — это **строка** (сериализованный захваченный query), а **не** keyed-объект: обращение `aio.visit.query.<key>` напрямую в JS лэнда вернёт `undefined`. Нужен параметр в JS — бери его через плейсхолдер `{{aio.visit.query.<key>}}` (сервер подставит значение в код лэнда) или распарси строку сам.

`{{aio.visit.query.<key>}}` подставляет значение произвольного URL-параметра, с которым визит пришёл — прямо из query-строки, без заведённого одноимённого поля.

`<key>` — имя параметра как в URL. Например, параметр `lp` в ссылке визита достаётся через `{{aio.visit.query.lp}}`.

**Зачем нужен:** когда параметр пришёл в URL, но одноимённого поля визита в `Settings → Fields` нет, значение **не теряется** — оно остаётся в `aio.visit.query` и доступно через этот плейсхолдер (в Destination URL, шаблонах интеграций, постбэках). Заводить отдельное поле для этого не обязательно.

**Отличие от `{{aio.visit.fields.<field>}}`:**
- `{{aio.visit.fields.<field>}}` — значение из **заведённого поля визита** (`Settings → Fields`); поле могло заполниться формой, `Fill Fields` step'ом или из query при совпадении имени.
- `{{aio.visit.query.<key>}}` — **сырой** параметр прямо из query-строки визита, поле заводить не нужно.

Постоянный параметр, который нужен как самостоятельная сущность (аналитика, разбивки), лучше всё же завести отдельным полем визита — `{{aio.visit.query.<key>}}` покрывает разовые/произвольные параметры.

### Как подставить данные Content Library через ключ `{{aio.visit.fields.<field>.<key>}}`

Когда поле визита привязано к Content Type из Content Library, у него есть **ключи** (slug'и), определённые в `Edit Structure`. Через них можно подставлять разные значения одного объекта.

**Типичный пример — оффер-нейм:**
- На лэнде показываем визиту: `{{aio.visit.fields.offer_name.for_visitor}}`
- В пуш в интеграцию шлём: `{{aio.visit.fields.offer_name.for_advertiser}}`

Содержимое подставляется из соответствующего Content Item — выбранного по правилам дистрибуции/флоу.

Ключ подставляет не только текст, но и картинку: если Content Item держит изображение, `{{aio.visit.fields.<field>.image}}` в атрибуте `src` заменяется на нужную картинку варианта.
```html
<img src="{{aio.visit.fields.content_storage.image}}" alt="">
```

### LP Variants Field — специальные поля типа `variant` (`LP_HEADER`, `LP_SUBHEADER`)

Поля визита с префиксом `LP_*` и типом `variant` — `LP_HEADER`, `LP_SUBHEADER`, `LP_HEADER_IMAGE`. Если `slug` content split'а совпадает с именем такого поля — выбранный сплитом вариант записывается в это поле, и можно сводить аналитику разбивкой по нему.

Подставляются на лэнде так же: `{{aio.visit.fields.LP_HEADER}}`.

### Динамика на лэнде в MTK — своими JS-макросами

В MTK-виде хранилища `Content Library` нет, поэтому плейсхолдеры `{{aio.visit.fields.<field>.<key>}}` и LP Variants недоступны. Динамическую подстановку и ротацию контента на лэнде делают **своими JS-макросами** прямо в коде лэнда.

Значения читаются из объекта визита `aio.visit` (например `aio.visit.country_code`, `aio.visit.fields.<slug>`) и подставляются в разметку своим кодом. Записать значение в поле визита можно через шину SDK после плейсхолдера `{{aio}}`:
```javascript
window.aioBus.push({ type: "trigger", key: "<slug>", value: "..." });
```
Выделенного инструмента ротации контента в MTK-виде нет — логика выбора и подстановки живёт в собственном скрипте на лэнде.

## Модификаторы плейсхолдеров — `{{ключ:modifier}}`: `raw`, `urlencode`, `json_array_first`, `timestamp`, `encrypt`

**К любому плейсхолдеру данных `{{aio.*}}` можно дописать модификатор через двоеточие — `{{aio.visit.uuid:urlencode}}`, `{{aio.visit.landing_human_ids:json_array_first}}` — и AIO подставит уже преобразованное значение.** Список: `raw`, `urlencode`, `json_array_first` … `json_array_ninth` и `json_array_last`, `timestamp`, `encrypt`, `encrypt_url`; без модификатора применяется неявный `default`. В пикере-гексагоне модификаторы не показываются — их дописывают руками к ключу, взятому из пикера.

Правила:

- Работают везде, где раскрываются `{{aio.*}}`: `Redirect URL` и `URL Parameters` дестинейшена, шаблоны интеграций и трекеров, HTML лэнда и макросы, значения `Fill Fields`, тексты сообщений, Source-link плейсхолдеры при генерации ссылки (исключение — `encrypt`/`encrypt_url`: при генерации ссылки они не работают, у Link Generator нет ключа тенанта).
- Один модификатор на плейсхолдер: запись с двумя (`{{ключ:a:b}}`) AIO не раскрывает — она остаётся в тексте как есть.
- Неизвестный модификатор ошибки не даёт — значение подставляется как без модификатора.
- Двоеточие в `{{link:1}}`, `{{form:2}}`, `{{link:s:permanent}}` — не модификатор: это нумерация лэнд-плейсхолдеров, другой механизм (секция «Как вести переходы по флоу через `{{link}}`» этого документа).

### Что происходит со значением без модификатора — неявный `default`

**Без модификатора AIO обрезает пробелы по краям и удаляет из значения двойные и одинарные кавычки, табуляцию, перевод строки и обратный слэш (включая литеральные `\t` и `\n`).** Так значение не рвёт кавычки атрибута HTML, JS-строки или JSON-шаблона, в который подставляется. Следствия:

- кавычки из значения пропадают: `O'Brien` уедет как `OBrien`; нужны как есть — `:raw`;
- JSON-значение перестаёт быть JSON: `{{aio.visit.query}}` без модификатора даёт `{lp:1,sub1:abc}`, с `:raw` — `{"lp":"1","sub1":"abc"}`;

### `raw` — подставить значение как есть

**`{{ключ:raw}}` отключает чистку `default`: кавычки, переводы строк и слэши остаются в значении.** Нужен, когда значение — JSON или текст с кавычками, который дальше разбирает получатель: `{{aio.visit.query:raw}}`, `{{aio.visit.fields.array.<slug>:raw}}`. В HTML-атрибуте или JS-строке лэнда `:raw` без своего экранирования опасен — кавычка из значения закроет строку раньше времени.

### `urlencode` — закодировать значение для URL

**`{{ключ:urlencode}}` кодирует значение по правилам URL-формы: пробел → `+`, `&` → `%26`, `=` → `%3D`, скобки → `%5B`/`%5D`.** Нужен там, где AIO значение не кодирует сам — в HTML лэнда, в значениях `Fill Fields`. В `URL Parameters` дестинейшена `Simple Redirect` двойного кодирования не будет: склейка URL сначала раскодирует значение параметра, потом кодирует заново ([how-to/destinations.md](../how-to/destinations.md)), так что `%5B` уедет как `%5B`, а пробел из `+` станет `%20`.

### `json_array_first` … `json_array_ninth` — взять один элемент массива

**Модификаторы `json_array_first`, `json_array_second`, `json_array_third`, `json_array_fourth`, `json_array_fifth`, `json_array_sixth`, `json_array_seventh`, `json_array_eighth`, `json_array_ninth` достают из плейсхолдера-массива элемент по позиции — без скобок и кавычек.** Работают на всём, чьё значение — JSON-массив: системные `landing_human_ids`, `landing_uuids`, `landing_type_uuids`, `flow_uuids` (секция «В URL уехало `%5B309889%5D` вместо ID лэнда» этого документа) и `.array.`-формы registry-полей. Позиция за концом массива даёт пустое значение. `json_array_last` в списке есть, но последний элемент не отдаёт — значение приходит как без модификатора; нужен последний — берите его по номеру позиции.

### `timestamp` — дата как unix-время

**`{{ключ:timestamp}}` превращает плейсхолдер-дату в unix-timestamp в секундах: `{{aio.visit.created_at:timestamp}}`, `{{aio.conversion.created_at:timestamp}}`.** Работает только на плейсхолдерах, которые несут дату; на строковом значении (например `{{aio.common.current_date}}`) даёт пустое. Текущее время в секундах есть готовым плейсхолдером — `{{aio.common.current_timestamp}}`.

### `encrypt` и `encrypt_url` — зашифровать значение ключом тенанта

**`{{ключ:encrypt}}` шифрует значение AES-CBC ключом тенанта и отдаёт base64 от «IV (16 байт) + шифротекст» без хвостовых `=`; `{{ключ:encrypt_url}}` — то же в URL-safe base64 (`-` и `_` вместо `+` и `/`).** Каждая подстановка даёт новый шифротекст (случайный IV); получатель расшифровывает тем же ключом. Ключ на тенант заводит команда AIO по запросу, в интерфейсе его нет. **Пока ключа нет, модификатор не шифрует: значение уходит открытым текстом, без ошибки** — проверяйте результат в `destination_url` или в логах, а не по факту написанного модификатора.

## Как работают Source-link плейсхолдеры в JSON-коде Source

Отдельное семейство плейсхолдеров — внутри JSON-кода Source (`Tracker → Sources`), в блоке `links[].parameters`. Они подставляются **при генерации ссылки** (Link Generator), не на стороне визита, и собирают итоговый URL для рекламной площадки.

| Плейсхолдер | Куда подставляется (ключ параметра) | Что подставляет |
|---|---|---|
| `{{aio.campaign.uuid}}` | `cuuid` | UUID кампании |
| `{{aio.source.uuid}}` | `suuid` | UUID самого Source |
| `{{aio.user.uuid}}` | `launcher` | UUID юзера-лаунчера (кто сгенерил ссылку) |
| `{{aio.replace}}` | поля с `"type": "replace"` | значение, которое лаунчер вводит в форме при генерации ссылки (replace-поле Source) |

`{{aio.replace}}` — это не конкретное значение, а маркер «сюда подставить то, что введёт лаунчер в одноимённое replace-поле». Само поле определяется в массиве `replace` Source-кода (ключ `key`), а в `links[].parameters` оно ссылается типом `"type": "replace"`.

Типичные replace-поля Source в рекламных заливах — `fb_account_id`, `creative`, `fb_pixel`, `fb_capi_token` (FB CAPI): их значения лаунчер вводит в форме при генерации ссылки.

**Source Mapping** — это не отдельный UI-блок, а настройка **rewrites на уровне Source**: маппинг входящего URL-параметра в поле визита, заданный ключом `rewrites` в JSON-коде Source. Полная механика — [models/source.md](../models/source.md) и [how-to/source-trackers.md](../how-to/source-trackers.md).

## Как использовать Vue.js плейсхолдеры `{{vue.aio.visit.<...>}}`

`vue.`-форма любого `{{aio.*}}` плейсхолдера подставляет данные визита реактивно, для Vue-шаблонов на лэнде.

### Как включить Vue.js на лэнде и взять `vue.`-плейсхолдеры

Если на элементе лэнда стоит `id="vue"` — включается Vue.js. Работает на `<body id="vue">` или на любом `<div id="vue">` (на том элементе, где он нужен). Тогда доступны:

| Плейсхолдер | Что |
|---|---|
| `{{vue.aio.visit.<...>}}` | то же, что `{{aio.visit.*}}`, но реактивно, для Vue-шаблонов |

**`vue.`-форма есть у любого `{{aio.*}}` плейсхолдера** — просто добавь префикс `vue.` (`{{aio.visit.country_code}}` → `{{vue.aio.visit.country_code}}`). Обе формы можно использовать на одной странице одновременно: обычная подставится статично при отдаче, `vue.`-форма — реактивно.

**Поддерживаемые директивы:** `v-if`, `v-else-if`, `v-else`, `v-for`, `@click`.

**Объекты для шаблонов** — объявляются через `window.aioBus.push({type:"vue-data-object", data:{...}})`.

### Что можно собрать на Vue-плейсхолдерах — use cases и мульти-условие

Vue-плейсхолдеры нужны, когда содержимое лэнда зависит от данных визита прямо в браузере — переводы, условный рендер, списки.

**Use cases:**
- Динамические переводы по `language_code` визита.
- Условный рендер блоков (`v-if` по полю визита).
- Списки (например, рейтинговый блок с разными карточками офферов).

**Мульти-условие в `v-if`** — несколько проверок через `&&`, включая поля визита по слагу `vue.aio.visit.fields.<slug>`:
```html
<div v-if="vue.aio.visit.country_code === 'DE' && vue.aio.visit.fields.creative === 'image'">
  ...
</div>
```

## Спинтакс в текстах рассылок — `{вариант 1|вариант 2}` и `{Random=(100,1500)}`

**Спинтакс — это не плейсхолдер, и работает он только в текстах сообщений рассылки: `{вариант 1|вариант 2}` подставляет один случайный вариант на отправку, `{Random=(100,1500)}` — случайное число из диапазона.** Вне рассылок — на лэнде, в Destination URL, в постбэках — этот синтаксис не действует: там подставляются только плейсхолдеры `{{aio.*}}` из этого справочника.

Одно другому не мешает: спинтакс разворачивается **после** подстановки плейсхолдеров `{{aio.*}}`, поэтому в тексте сообщения можно писать и то, и другое. Полная семантика обоих макросов, каналы и подсказка в форме шаблона — [mechanics/notifications-flow.md](../mechanics/notifications-flow.md).

## Типичные ошибки с плейсхолдерами

### Лэнд не открывается или форма не работает — проверь `{{aio}}` и `{{form}}`

- **Забыли `{{aio}}` перед `</body>`** — SDK не подгружается. Хотя процессинг ZIP должен вставить автоматически, проверь в `Manage landing → Code`.
- **`{{form}}` нет в HTML** — форма не отрисуется, даже если в флоу выбрана.

### Шаринг ссылки даёт пустой лэнд — скопировали URL из адресной строки

Скопировали URL из адресной строки, отправили коллеге, а у него открывается пустой лэнд — так и задумано при включённом Backfix. Если в `AIO SDK Macros Collection → backFix → enableStrangeUrlParameters: true` — реальные CUUID/SUUID в URL переписываются на fake-UTM, и по такому URL визит не повторить. Механика — [reference/sdk.md](sdk.md).

Для теста отправляйте правильную (Encrypted) ссылку из Link Generator, а не URL из адресной строки.

### Подстановка в URL дестинейшна не работает — поле не заполнено

- Проверь, что поле визита заведено в `Settings → Fields` и заполнено (либо через форму, либо через `Fill Fields` step во флоу).

### Использовал `{{aio.visit.fields.offer_name}}` без ключа — значение не подставляется

- Если у Content Type есть несколько ключей (`for_visitor`, `for_advertiser`) — нужно **обязательно** указать ключ. Без ключа AIO не знает, какое значение подставить.

### Картинка из Content Library осталась абсолютной ссылкой на исходный домен

Относительные пути к файлам внутри ZIP-архива AIO переписывает на CDN при загрузке лэнда автоматически. Но **абсолютную ссылку** на картинку, которая приходит из Content Library, AIO не переписывает — она остаётся как задана, и лэнд грузит изображение с исходного домена. Указывай картинки в Content Item **относительным путём**, а не абсолютной ссылкой — тогда изображение отдаётся с CDN вместе с остальным лэндом.

### Slug-параметр в ссылке не совпадает с именем поля — значение не подхватывается

**AIO пишет параметр ссылки в поле визита, когда имя параметра совпадает со слагом поля буквально — включая разделители.** Кейс: передавали `sub1`, поле называлось `sub_1` → значение не подхватывалось. Поля с таким слагом нет вообще — параметр просто отбрасывается, никакой ошибки при этом не будет. Полная механика записи (кто и на каком этапе пишет) — [models/visit-field.md](../models/visit-field.md).

### На вайте плейсхолдеры `aio.*` не подставляются

- На вайте SDK-плейсхолдеры **не подставляются** — данных визита нет, плейсхолдеры `aio.*` не работают, вытащить нечего.
