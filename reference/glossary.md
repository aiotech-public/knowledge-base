# AIO Glossary

Базовый справочник по терминам AIO: при ссылке на термин AIO имена пишутся **как здесь**.

**Условные обозначения:** `[AIO]` — внутренний термин системы AIO; `[общий]` — общая терминология аффилиейт-маркетинга.

---

## Воркфлоу запуска и базовые понятия AIO

- **Прилэнд** `[общий]` — прогревочный лэнд без формы, только ссылки на следующий шаг. (разг.: «прокла», «прокладка»)
- **Оффер** `[общий]` — лэнд с формой, push в интеграцию лида. (разг.: «money page», «мани пейдж», «блэк», «блэк-страница»)
- **Прилэнд с формой** `[AIO, тип лэнда]` — гибрид: прилэнд, но с формой прямо на нём. В шаге прилэнда можно выбирать оба типа.
- **Оффер-нейм / афернейм** `[общий]` — название оффера. В AIO может быть динамическим: один — для отображения на лэнде, другой — для пуша в интеграцию.
- **Бренд** `[общий]` — то же, что оффер-нейм, синоним в речи команд.
- **For Visitor / For Advertiser** `[AIO, атрибуты оффер-нейма]` — два дефолтных атрибута каждого оффер-нейма в библиотеке: что показываем визиту на лэнде vs что шлём в интеграцию рекламодателю. Структуру хранилища можно расширять — например, добавлять изображение/лого, которое тоже подставляется динамически.
- **Two-step / One-step воронка** `[общий]` — двухступенчатая (прилэнд + оффер) и одношаговая (через `Скип` шага прилэнда — сразу на оффер) воронки. В AIO можно опционально превратить дефолтный two-step в one-step без перенастройки флоу. Соответствуют pre-configured Flow-ам тенанта.
- **Спасибка** `[общий]` — лэнд после успешной отправки формы.
- **Backfix / Back-link** `[AIO]` — встроенная фишка: если юзер на прилэнде нажал «Назад», его принудительно перекидывает вперёд (на оффер). Работает через SDK-конфиг в `AIO SDK Macros Collection` (см. ниже `Backfix (конфиг)`). [reference/sdk.md](sdk.md).
- **Витрина** `[общий]` — воронка с множеством разных прилэндов (баннеров/креативов), которые сходятся к одному и тому же офферу. Куда юзер ни кликнул, попадает в один оффер.
- **Vertical / Вертикаль** `[общий]` — направление трафика клиента (финансы, нутра, iGaming, свипстейкс и т.п.). Выбирается при регистрации в профиле компании (не в Form Builder); полный список вертикалей — *Вертикали в арбитраже трафика*. В тенанте обычно несколько `Teams` — по одной на вертикаль.
- **Медиабаер / баер** `[общий]` — специалист, который запускает и ведёт рекламные кампании в трекере (закуп трафика, креативы, оптимизация связок). Подробнее о роли и моделях работы — *Медиабаинг и место AIO в нём*.
- **Связка** `[общий]` — комбинация элементов рекламной кампании (источник + крео + прилэнд + оффер + гео), которая в сумме даёт положительную конверсию и прибыль. Ключевой рабочий термин медиабаинга — *Медиабаинг и место AIO в нём*.
- **Human ID** `[AIO, системное поле]` — человекочитаемый (короткий числовой) идентификатор объекта, по которому объект удобно искать и называть вместо длинного UUID. Виден в окнах создания/редактирования кампаний и лэндов (`Campaign details`, Settings лэнда). **Создаётся и ассайнится автоматически при создании объекта** — руками задавать/менять его не нужно. **Глобальный, сквозной по всей системе AIO** (не по тенанту): нумерация единая для всех визитов/кампаний, а не отдельная в каждом тенанте. Это уже существующее системное поле — вопрос «как добавить Human ID в тенант» некорректен: добавлять нечего, оно есть у объекта по умолчанию.

## Инфраструктура и серверы AIO

- **Tenant / Тенант** `[AIO]` — клиентский воркспейс в системе. Имеет name, description, billing email, country code. Один user может иметь несколько тенантов; один тенант может быть пошарен между юзерами. Базовая единица изоляции — «Tenant» (понятия «Workspace» нет).
- **Шаблон тенанта** `[AIO]` — преднастроенный набор флоу/кампаний/ролей, поднимаемый при создании тенанта. Конкретные шаблоны (напр. `Finance Template`, готовый ERP-шаблон) поднимаются командой AIO.
- **Manage Tenant** `[AIO, интерфейс / экшен]` — действие в правом верхнем углу для управления тенантом: удаление / деактивация юзеров, смена ролей и т.п. Доступно только Admin / Owner. При полном удалении юзера теряется авторство старых действий — деактивируй, не удаляй; откатить нельзя. [how-to/permissions.md](../how-to/permissions.md).
- **Сервер** `[AIO]` — серверная единица в `Tech → Servers`, на которую AIO ставит свой агент через Deploy-скрипт. Сервера агностичны — на них нет файлов лэндов, всё лежит на CDN; сервер только исполняет команды AIO по визитам. Можно добавить вручную (`Add Manually` — указать IP, deploy-скрипт ставится руками через SSH) или купить через `Server Provider` (DigitalOcean и т.п.). Атрибуты: Name, Description, Tags, Server Provider, Region, Droplets Size & Image, Deployment Script, `Monitoring User` (только юзер с включённой 2FA), `Repoint Group`.
- **Destroy Server** `[AIO, экшен]` — необратимое удаление сервера, после которого он не операционален.
- **Агент** `[AIO]` — серверный компонент AIO на сервере клиента. Рендерит контент (лэнды с CDN), исполняет команды AIO по визиту и сообщает AIO о событиях флоу (submit формы, переход по ссылке-шагу). Поведение пользователя (heatmaps, записи сессий) снимает не агент, а клиентский SDK на лэнде ([reference/sdk.md](sdk.md)).
- **Домен** `[общий]` — домен, ведущий на сервер. Можно репойнтить между серверами автоматически (downtime-protection при бане).
- **Edit Domain (атрибуты)** `[AIO]` — у домена настраиваются: Description, Tags, Monitoring User, тоггл `Allow indexing by search engines` (разрешить поисковикам индексировать домен), `Default Query Code` (дефолтные параметры запроса при прямом заходе на домен — используется в Direct Traffic).
- **Subdomain / Create Subdomain** `[AIO, экшен]` — экшен в Action Menu домена. Позволяет создать саб-домен от существующего: указать имя, сервер, Monitoring User.
- **Clear Domain** `[AIO, экшен]` — экшен очистки домена. Полностью сбрасывает связи домена.
- **Default Query** `[AIO, опция домена]` — настройка домена, автоматически прикрепляющая Campaign + Source к визитам, которые пришли на голый домен без UTM-параметров. Используется при прямом трафике. Альтернатива — `Direct Traffic Distribution` (более централизованный).
- **Трекинговый домен** `[AIO]` — домен, который указан в рекламной кампании, до фильтра. Если в флоу есть `Domain-Change Step`, трекинговый домен отличается от публичного, под которым у визита фактически открывается лэнд.
- **Публичный домен** `[AIO]` — домен, под которым у визита фактически открывается лэнд после `Domain-Change Step`. При бане его можно заменить без переподключения рекламной кампании (через `Replace Domain`).
- **Lock Domain** `[AIO, действие]` — экшен на самом домене, запрещающий изменения и перенос. Защита от случайных правок на инфраструктурном уровне (не путать с `Lock campaign to this domain` — это другой механизм на уровне кампании).
- **Lock campaign to this domain** `[AIO, toggle]` — переключатель в `Edit Campaign` / `Link Generator`, привязывающий кампанию к конкретному домену: ссылки с других доменов не открывают её. По дефолту любой добавленный домен может открывать любую кампанию.
- **Абузы доменов** `[общий]` — целенаправленные жалобы на домены, чтобы их забанило. Трекинговый и публичный домены разносит `Domain-Change Step` — [models/domain.md](../models/domain.md).
- **Repoint Group / Репойнт-группа** `[AIO]` — атрибут сервера: строка-группа. При падении сервера автоматический репойнт идёт **только в пределах этой группы**. Если живых серверов в группе нет — репойнт не сработает, и трафик с тех доменов остановится. Поэтому в одной группе важно держать минимум два сервера. Пример: связать в одну группу серверы по гео или по аккаунтам провайдеров.
- **Monitoring User / Мониторинг-юзер** `[AIO]` — юзер, которому AIO-tech-bot шлёт нотификации в Telegram, если сервер/домен падает или становится недоступен. Назначается отдельно для серверов и доменов при добавлении. Можно использовать не отдельного юзера, а групповой чат (через бота-юзера на чат). Алерты идут только в Telegram — нужна привязка аккаунта к TG, иначе доставлять некуда.
- **AIO-tech-bot** `[AIO]` — Telegram-бот AIO для уведомлений и для включения 2FA. 2FA можно настроить через этот бот (Telegram) или через **Google Authenticator** (привязка к Telegram для 2FA необязательна с тех пор, как добавили Google Authenticator). Нотификации доставляются только в Telegram: без привязки аккаунта к Telegram они не приходят — 2FA через Google Authenticator такую привязку не даёт.
- **Pinging / 5-минутный мониторинг** `[AIO]` — отдельная выделенная подсистема: каждые 5 минут с географически распределённых агентов в нескольких регионах (напр. Европа / Азия / Америка / …) проверяется доступность каждого сервера и домена; решение «упало / не упало» — по кворуму. [context/architecture.md](../context/architecture.md).
- **Repoint** `[AIO, действие]` — автоматическое перенаправление всех доменов с упавшего сервера на случайный живой сервер в той же `Repoint Group` (гео/близость не учитываются).
- **Assign under attack status (Under Attack mode)** `[AIO, действие на доменах с Cloudflare]` — включает Cloudflare Under Attack mode для домена(ов). UI-подпись действия: `Assign under attack status` (одиночное) / `Assign under attack` (массовое). Cloudflare показывает «Verify you are human» captcha всем визитам. Первая ступень защиты от DDoS.
- **AS-Net Sites / Block-листы** `[AIO]` — списки IP-диапазонов для блокировки прямо на уровне AIO (не Cloudflare). Поддерживают CIDR (`x.x.x.x/24`) и через тире. Используется для жёсткого отсечения DDoS-источников.
- **Deploy / Deploys** `[AIO]` — скрипт, который раскатывается на серверу при добавлении (ставит Docker, Squid, AIO-агент). Можно создавать кастомные Deploys — например, чтобы любой добавляемый сервер становился ещё и Squid-прокси (юзер/пароль/порт задаются в Deploy).
- **Squid Proxy** `[общий]` — прокси-сервер, ставится по дефолту в Deploy-скрипте AIO. Позволяет любой добавленный сервер использовать как прокси.
- **Provider (общий зонтик)** `[AIO]` — внешний партнёр, через которого AIO покупает/использует ресурсы. Три типа: **Server Provider** (DigitalOcean и др.), **Domain Provider** (Namesilo, Namecheap и др.), **DNS Provider** (Cloudflare и др.). Каждый добавляется в свой раздел `Tech → ...` (`Tech → Server providers` / `Domain providers` / `DNS providers`), требует API-ключ + email/username, имеет actions `Test` (проверка коннекта) и `Check balance`.
- **Test Provider** `[AIO, экшен]` — экшен в Action Menu провайдера, отправляет API-запрос для проверки коннекта. Для DNS Provider — прогоняет права, нужные для работы с зоной (для Cloudflare успешный ответ выглядит как `Cloudflare OK — <тип ключа> (<аккаунт>), zone <зона>, all required permissions present`, разбор — [how-to/domains.md](../how-to/domains.md)); для Server Provider — `Auth as ..., with N droplets limit`; для Domain Provider — может также показать баланс. Плохой ответ Server Provider (`Unidentified` / нет коннекта к DigitalOcean) означает проблему с кредами или неактивный аккаунт — текст вида `account is inactive - Your team has been locked due to lack of payment or improper use of the platform. Please open a ticket...`.
- **Proxy Provider** `[AIO, Tech]` — провайдер прокси как интеграция, раздел `Tech → Proxy providers` (ERP-only). Запись-интеграция провайдера, откуда AIO берёт прокси. Тип интеграции `Static` — ручной прокси: хост:порт + login/password (значения задаются руками, не тянутся из внешнего API). **Не путать с `Proxies`** — отдельный справочник самих прокси-записей (атрибуты `Name` + прокси-строка), тогда как `Proxy Provider` — это интеграция-источник.
- **Server-провайдер** `[AIO]` — внешний провайдер серверов (DigitalOcean и другие).
- **Domain-провайдер** `[AIO]` — внешний регистратор доменов (Namesilo, Namecheap и другие).
- **DNS-провайдер** `[AIO]` — внешний DNS-провайдер (Cloudflare и другие).
- **Чекеры доменов** `[AIO]` — интеграции для отслеживания бана доменов:
  - **Google Threat** — публичная (бесплатная) проверка на красный экран (в UI тип чекера так и называется — `Google Threat`).
  - **VirusTotal** — публичная апишка с лимитом запросов; AIO распределяет домены между несколькими VirusTotal-аккаунтами для увеличения общего лимита.
- **Replace Domain** `[AIO, действие]` — массовый экшен для замены одного домена на другой (например, при бане).
- **Direct без Cloudflare** `[AIO]` — штатный способ добавить домен с пустым DNS-провайдером (без Cloudflare). SSL-сертификат можно выпустить кнопкой прямо из AIO. Запросы идут напрямую на сервер. Не привязан к вертикали — просто ещё одна фича; учитывать только, что без Cloudflare сервак уязвимее к DDoS (при бан-атаке может упасть весь). Полностью — [how-to/domains.md](../how-to/domains.md).
- **DNS-пропагация** `[общий]` — время, за которое DNS-записи распространяются после смены — единственный реальный даунтайм при репойнте сервера в AIO.
- **Multi A-record** `[AIO, DNS]` — несколько A-записей на одном домене для балансировки нагрузки между серверами на уровне DNS.
- **Agent Cluster / кластер агентов** `[AIO]` — горизонтальная масштабируемость AIO-агента: домен балансится через несколько CF-рекордов на несколько серверов с агентами.
- **Rebalance Domains** `[AIO, экшен на сервере]` — правый клик на сервере → равномерно распределяет привязанные домены между серверами. **Не путать с `Repoint`** (тот — при падении сервера).
- **Domain-Change Handler** `[AIO]` — агентский механизм обработки шага Domain-Change: «возьми текущий payload и продли сессию на другом домене, проставив куки/сессию».
- **String (payload type в Domain-Change)** `[AIO]` — тип payload для Domain-Change Step: вместо UUID домена-объекта передаётся **строка** (`test.com`), ротатор меняет строку. См. также `Parent-Tenant Domain Pool`.
- **Parent-Tenant Domain Pool** `[AIO]` — общий пул доменов между тенантами одного клиента через parent-тенант. В шаге Domain Change можно выбрать payload типа `Domain String` — туда вписывается название домена строкой. Если домен есть в Parent-тенанте (но нет в текущем) — он всё равно корректно применится и будет обрабатывать трафик, несмотря на защиты (сервера/домены одного тенанта работают только с кампаниями этого же тенанта).
- **Tech-Donor / технический тенант-донор** `[AIO]` — отдельный тенант под пул общих доменов и агентов, без трафика на нём. Центральный «провайдер» доменов для child-тенантов.
- **Domain Checkers** `[AIO, интеграции]` — бесплатные интеграции для доп-проверки доменов: ловят флаги **VirusTotal** и **Google Safe Browsing «Red Screen»**.
- **Архитектура мониторинга доменов** `[AIO]` — проверки доменов распределяются координатором между несколькими чекерами, а не идут одним инстансом: так они не упираются в таймауты на больших пулах доменов и не дают ложных «домен упал» из-за неотвеченного DNS. Механика проверки — [context/architecture.md](../context/architecture.md) §Pinging.
- **Last Check Info** `[AIO, поле UI домена]` — результат последнего чека VirusTotal: количество `malicious` / `suspicious` + timestamp. Хоть один найден → домен проблемный, уведомление в TG.
- **Tag на домене (для Domain-Change-ротации)** `[AIO, рабочий приём]` — вешать тег на домены, используемые в Domain-Change, чтобы API-ротация по таблице доменов фильтровала только их.
- **Сервер-мониторинг чат** `[AIO]` — выделенный TG-чат, куда AIO может слать уведомления о перегрузке сервера (CPU > 85% несколько минут).
- **Self-update агента** `[AIO]` — агенты на серверах самообновляются — ручного обновления серверной части не требуется.
- **AIO Agent + Squid (deployment-скрипт)** `[AIO]` — стандартный bash-скрипт deployment, раскатывается при добавлении сервера: ставит **Squid** + **агент** + **сервис обновления**. По образу можно создавать кастомные. **Deployments вкладка** нужна для хранения bash-скриптов. [models/server.md](../models/server.md).
- **AIO-агент = конечный автомат** `[AIO]` — формальное определение: агент на сервере — это finite state machine, работающий по командам AIO: принимает запрос визитёра, на каждом шаге получает от AIO команду (что отдать визитёру, куда вести визит дальше), исполняет её и сообщает AIO о событиях флоу (submit формы, переход по ссылке-шагу). Решения флоу (переходы, фильтрация, сплит-выбор) вычисляет AIO. [models/server.md](../models/server.md).
- **CDN-streaming видео** `[AIO]` — видео с CDN стримится, а не загружается в память агента.

## Трекинг и флоу

- **SEO-трафик** `[общий]` — органический трафик из поисковиков по брендовым запросам. В AIO заводится отдельным `Source`.
- **Direct Traffic** `[AIO]` — трафик, пришедший на голый домен без UTM/source-параметров. Привязывается либо через `Default Query` на самом домене, либо централизованно через `Direct Traffic Distribution`. Внутри одного домена можно разделять между кампаниями по `initial_path`.
- **Source / Источник** `[AIO]` — источник трафика (Facebook, Google, Taboola, нативка). Pop-under платформы не поддерживаются.
- **Destination / Дестинейшн** `[AIO]` — конечная интеграция, куда пушится лид (рекламодатель, партнёрка, CRM).
- **Flow / Флоу** `[AIO]` — визуальный конструктор пути визита от Source до Destination. Стандартные шаги: Sources → Filters (AIO Filter, Antifraud) → Lands (Pre-land + Offer) → Destination.

### Flow States (полный набор)

- **Flow States** `[AIO]` — типы шагов внутри флоу:
  - **Start** — автоматическое начало флоу.
  - **Source** — точка входа визита (для Campaign Flow обязательна).
  - **Content** — шаг с контентом (Landing / HTML / Redirect / 404 и т.п.). Имеет атрибуты `Lander Type` (Preland/Offer/White), `Payload Type` (Landing / HTML / Redirect / Reflect / Proxy reflect / Skip / 404), Settings Availability, `Collapsed by default` (тумблер есть, `Edit Campaign` его не читает), Info message.
  - **Destination** — финальная интеграция (для Campaign Flow обязательна). Атрибуты: Settings Availability, `Collapsed by default`, Info message.
  - **Domain Change** — смена домена между трекинговым и публичным (см. отдельный термин `Domain-Change Step` ниже).
  - **Fill Fields** — заполнение полей визита по правилам или из Content Library. Атрибуты: Fields, Placeholder Group, Payload Type (Fill Text / Fill Content), Compact/Control toggle. Невидим визиту.
  - **Filter** — шаг фильтрации трафика: в нём выбирается используемый `Traffic Filter`.
  - **SubFlow** — вставка ранее созданного SubFlow. SubFlow не работает самостоятельно; используется для централизованного Fill Fields.
  - **Finish** — конец SubFlow, возврат в основной флоу.

  [models/flow-model.md](../models/flow-model.md).

### Flow Transitions (полный набор)

- **Flow Transitions** `[AIO]` — переходы между шагами флоу:
  - **Arrived** — единственный transition из Source. Начало пути визита.
  - **Handle** — общий transition между шагами, выстраивающий путь визита.
  - **Handle-form** — срабатывает только при submit формы.
  - **Handle-link** — срабатывает при клике на `{{link}}`.
  - **Destination-rejected** — обратный transition от Destination к предыдущему шагу, если Destination отклонил лид. Улучшает аналитику и разделение успешных/отклонённых.
  - **Destination-pushed** — позволяет визиту проходить через несколько Destinations подряд (например, PWA → Destination), для трекинга полного пути.
  - **Destination-interacted** — любой исход (Pushed или Rejected). Используется, когда логика после пуша одинаковая независимо от результата.
  - **Passed** — после Filter, если визит прошёл фильтр.
  - **Rejected** — после Filter, если визит отклонён фильтром.
  - **No payload** — fallback. Если у шага не осталось вариантов после фильтрации правилами, визит уходит сюда (например, на вайт).

  [models/flow-model.md](../models/flow-model.md).

### Атрибуты Content step

- **Lander Type** `[AIO, атрибут лэнда]` — тип лэнда; **набор типов настраивается** (`Content → Landings ▾ → Manage landing types`), дефолтные — **Preland** (прогрев без формы), **Offer** (с формой), **White** (вайт-фолбэк), `Preland w/ Form`, `Thank-You Page`. Это не просто метка, а **набор флагов поведения** (макросы/события/CDN) — см. [models/landing.md](../models/landing.md). Указывается при загрузке лэнда. Используется в Backfix-конфиге (где UUID типа лэнда определяет, должен ли срабатывать Backfix), в Content State флоу (можно ограничить шаг конкретными типами лэндов).
- **Payload Type** `[AIO, атрибут Content state]` — что именно делает Content step с визитом:
  - **Landing** — показ загруженного лэнда: ZIP с `index.html` из `Content → Landings` либо PWA-шка из `Content → PWA` (на шаге выбирается как обычный лэнд).
  - **HTML** — показ HTML-куска, который **пишется прямо в Code Editor на уровне кампании в настройках шага**. Не требует заливки лэнда. Удобно для простых вайтов / 404-замен / временных страниц — HTML пишется inline, без лишних файлов в `Content → Landings`.
  - **Redirect** — переход на стороннюю ссылку.
  - **Reflect / Proxy reflect** — показ стороннего сайта под текущим доменом кампании.
  - **Skip** — пропуск шага (например, чтобы из 2-step сделать 1-step).
  - **404** — дефолт, если шаг не выбран.
  - **Fill Text / Fill Content** — для Fill Fields step.
- **Settings → Availability** `[AIO, настройка шага флоу]` — уровень видимости/редактируемости настроек шага при создании кампании. Три варианта:
  - **Campaign Template** — настройки берутся из флоу как дефолт, но баер может их менять в кампании.
  - **Campaign Only** — настраивается только в кампании (на уровне флоу пропадает).
  - **Flow Only** — настраивается только во флоу, в кампании опция скрыта; одна и та же штука применяется ко всем кампаниям этого флоу.

  [models/flow-model.md](../models/flow-model.md).

- **`Collapsed by default` (тумблер в `Visual settings` ноды флоу)** `[AIO, настройка шага флоу]` — переключатель в блоке `Visual settings` формы ноды (есть у шагов, которые показываются в `Edit Campaign`), сохраняется в настройках ноды как `is_collapsed`. Интерфейс его не читает: карточки шагов в `Edit Campaign` сворачиваются только кликом по шапке карточки, и это состояние хранится в браузере, а не во флоу; на канвасе редактора флоу флаг тоже не используется. Симптом «поставил `Collapsed by default`, а шаг в кампании открыт развёрнутым» — штатное поведение. [models/flow-model.md](../models/flow-model.md).

### Шаги, транзишны, маршрутизация

- **Transition / Транзишн** `[AIO]` — общий термин: переход между шагами флоу (по клику на ссылку / по сабмиту формы / по результату пуша). Полный список — см. блок Flow Transitions выше.
- **Domain-Change Step** `[AIO]` — дополнительный шаг во флоу для смены домена между трекинговым (тот, что в рекламной кампании) и публичным (тот, под которым открывается лэнд). [models/flow-model.md](../models/flow-model.md).
- **Condition / Кондишен** `[AIO, шаг во флоу]` — условный шаг: проверяет любое поле визита через билдер правил и ветвит флоу на `Passed` / `Rejected`. [models/flow-model.md](../models/flow-model.md); типовое применение после `AIO Antifraud`.
- **Fields by Distribution / Fill Fields by Distribution** `[AIO, шаг во флоу]` — шаг, на котором значения полей визита заполняются из централизованной дистрибуции по правилам (а не вручную в каждой кампании). Самый частый кейс — `Buyer UTM Distribution`: поле визита `buyer_utm` заполняется UTM-меткой баера по правилу `Campaign Owner`. Ставится в начале флоу до фильтра. Встречаются оба имени — `Fields by Distribution` (короткое) и `Fill Fields by Distribution` (полное); это **один и тот же шаг**. Не путать с типом дистрибуции `Fill Field Distribution` (см. раздел «Источники, трекеры и дистрибуции AIO» этого глоссария).
- **Allowance Rules** `[AIO]` — кастомные правила на шаге `Filter` **ИЛИ** на payload шагов с множеством вариантов (`Content` с несколькими лэндами, `Destination` с несколькими вариантами, `Condition`-шаг), определяющие, какие визиты проходят. Структура правила: поле визита + оператор + значение, комбинируются через AND. **Отклонение зависит от шага:** на `Condition` — не прошло → событие `Rejected`, а в Trash визит кладётся, только если на шаге включён тоггл `Trash when Rejected` (по умолчанию выключен, настраивается на уровне Flow — [models/flow-model.md](../models/flow-model.md)); на `Content` / `Destination` — не прошло правило → визит просто не попадает в этот payload и в Trash **НЕ** уходит.
- **Split Groups / Сплит-группы** `[AIO, маршрутизация во флоу]` — цветные метки на вариантах шагов. Визит получает цвет на первом шаге с выбором — на следующих шагах он попадает только в варианты с тем же цветом. **Цвет визиту записывается на любой ноде-выборщике — `Content`, `Fill fields`, `Fill form`, `Fields by distribution`** (первый не-`Rainbow` цветной вариант локает цвет на весь остаток флоу); на остальных шагах цвет только считывается. Если до требующего цвет шага не было ни одной такой ноды с цветами — визит идёт без цвета и не сматчится ни с одним цветным вариантом. Специальный цвет **Rainbow** принимает в себя любые цвета (используется на дестинейшне или там, где нужен «общий» вариант для всех групп). [models/flow-model.md](../models/flow-model.md).
- **Дефолтный флоу** `[AIO]` — преднастроенный флоу из шаблона: прилэнд + оффер с динамическим оффер-неймом. Альтернативный — с domain-change.

## Фильтр и антифрод в AIO

- **Фильтр** `[AIO]` — серверная фильтрация трафика на шаге `Filter`: для каждого визита решается `Passed` / `Rejected`.
- **Allowed Country** `[AIO, поле фильтра]` — поле шага `Filter`: ограничение по гео визита. *уточните у поддержки*.
- **Traffic Filters** `[AIO]` — раздел `Settings → Traffic Filters`, где подключаются интеграции фильтрации и обогащения трафика; иконка-шестерёнка. Полная запись — см. ниже `Settings → Traffic Filters`.
- **Кастомные правила** `[AIO, в фильтре]` — правила, заданные пользователем: любое поле визита + оператор + значение. *уточните у поддержки*.
- **FB-click-id** `[общий]` — параметр клика из рекламной площадки; приезжает в поле визита и доступен в кастомных правилах.
- **AIO Antifraud** `[AIO]` — встроенный антифрод-чекер AIO. Срабатывает во флоу перед пушем в `Destination`: пишет в визит `fraud_score` и `triggered_rules`, сам визит не отсекает.

  **Внешние** интеграции (`IPInfo`, `Emailable`, `WhatsAppCheck` и т.д.) — **не часть AIO Antifraud**, а отдельные `Traffic Filter`-шаги во флоу. **Отдельного сервиса `IPQuality` / `IPQuality Score` в AIO НЕТ** — подключить его как интеграцию нельзя; единственный отдельный IP-сервис — `IPInfo`.
- **Фрод-скор / fraud_score** `[AIO, поле визита]` — числовое поле визита, которое проставляет модуль `AIO Antifraud`; используется в правилах и `Condition`-шагах флоу.
- **Триггер-рулс / triggered_rules** `[AIO, поле визита]` — поле визита со списком сработавших чеков `AIO Antifraud`. *уточните у поддержки*.
- **Fingerprint** `[AIO, поле визита]` — уникальный отпечаток устройства визита.
- **Visit Status: Wait / Live / Left** `[AIO]` — три статуса визита, связанные **только с записью сессии** (AIO SDK). `Wait` — визит ждёт первые ивенты, которые сбросит SDK (запись сессии ещё не началась); `Live` — идёт запись (пополняется duration); `Left` — сессия началась и завершилась. `Wait` может быть единственным статусом, если ивентов от SDK так и не было — визит не дождался прогрузки JS, либо флоу используется без лендингов. Механика — [mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md).
- **Session flush interval = 10 секунд** `[AIO, SDK]` — интервал сброса SDK-ивентов (`aioExchange.flushInterval` + persist-session-record); меньше ~10 сек активности → первый флаш не успел уйти, визит остаётся в `Wait`. Механика — [mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md).
- **Sessions Recorder (AIO SDK)** `[AIO, SDK]` — JS-макрос AIO SDK, который пишет события на лэнде — heatmaps, video sessions, переходы, развитие визита. [mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md).
- **Сроки хранения записей сессий** `[AIO]` — записи сессий (основа scroll/click-карт и сводок) хранятся **7 суток**; запрос глубже по картам молча подтягивается к границе. Список сессий в интерфейсе отсекается более широким порогом — **14 суток**, но это порог интерфейса, а не срок хранения: глубже 7 суток список пуст. [mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md), [how-to/session-analytics.md](../how-to/session-analytics.md).
- **Replayer not enough events** `[AIO, ошибка]` — ошибка Session Replay-ера: AIO получил недостаточно ивентов от визита для воспроизведения сессии (ивенты сбрасываются каждые 10 секунд). [mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md).
- **options=new-session** `[AIO, дебаг-параметр]` — дебаг-параметр в ссылке — инициирует новую сессию визита при каждом клике. После теста убирать; **не для прод-трафика**. [mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md).
- **Сессия: init / Index Pages / Allowed paths** `[AIO]` — `init` — первое попадание визита/браузера в AIO на домене; AIO выбирает кампанию (UTM / Default Query / Direct Traffic Distribution) и подставляет index при отсутствии подпути. `Allowed paths` — набор разрешённых под-путей лэнда; вне набора → `404`. `Index Pages`-логика — при отсутствии подпути возвращает `404` (не редирект), чтобы боты-краулеры не уходили в бесконечный луп. [mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md).
- **Initial Domain (поле визита)** `[AIO]` — с какого домена визит зашёл изначально (до Domain-Change). По нему разбивается нагрузка в метриках/логах.
- **Launcher (поле визита)** `[AIO]` — UUID юзера, который сгенерировал ссылку и запускал трафик. Отличается от `Owner` (владелец кампании). В Pivot Report — `field_launcher`.
- **Поля визита на стадии голого захода (initial_path и др.)** `[AIO]` — на моменте, когда визит приходит на голый домен без всего, доступны поля: `IP`, `city`, `country code`, `initial_path`. На них строятся правила Direct Traffic Distribution.
- **Внешние фильтры** `[AIO]` — сторонние сервисы, подключаемые как `Traffic Filter`. *уточните у поддержки*.
- **AIO Filter Service** `[AIO]` — собственный сервис фильтрации AIO, отдельный механизм от старого `AIO Filter`. Подключается на уровне флоу как `Traffic Filter`.
- **White / Вайт** `[AIO]` — нейтральная страница-заглушка: один из дефолтных типов лэнда (`Lander Type`) и шаг флоу с этим типом. Чаще всего там нейтральный лэнд / 404 / редирект. Не путать с `Wait` (один из статусов визита — `Visit Status: Wait / Live / Left`).
- **Сторонние фильтры** `[AIO]` — внешние сервисы фильтрации, которые подключаются в шаге `Filter` флоу через API-интеграцию (по запросу). Какие именно доступны в тенанте, видно в дропдауне `Integration type` при создании `Traffic Filter`. *уточните у поддержки*.
- **Filter Mode** `[AIO]` — режим работы шага `Filter`. Одна и та же настройка, доступная в трёх местах: (1) на шаге `Filter` в Edit Campaign; (2) в блоке `AIO Filter` кампании (MTK); (3) массово через `Force filter mode` (правый клик по таблице кампаний).
- **Force filter mode (массовый экшен)** `[AIO, экшен]` — single + массовый экшен на кампании (правая кнопка) — смена режима фильтра без захода в Edit. *уточните у поддержки*.
- **Antifraud Points (Condition-шаг)** `[AIO]` — дефолтный `Condition`-шаг во флоу после `AIO Antifraud`.
- **Rainbow Split Group** `[AIO]` — спец-значение Split Group, **принимающее любой цвет**; фолбэк для визитов без подходящего по цвету варианта на следующем шаге.
- **Trash Reason** `[AIO, поле визита]` — поле визита с причиной, по которой ему проставлен `is_trash`. Поле живёт в отдельной таблице Trash (см. ниже `Trash / Trash Visits` в разделе «Аналитика»).
- **AIO Filter (старый) vs AIO Filter Service (новый)** `[AIO]` — два **разных** механизма, не путать: `AIO Filter` — старый, простой, дефолтный шаг `Filter` базовых тенантов; `AIO Filter Service` — новый, продвинутый.
- **Emailable** `[AIO, интеграция]` — внешний email-чекер, подключается как `Traffic Filter`.
- **WhatsAppCheck / WaCheck (IsOnWhatsApp)** `[AIO, интеграция]` — внешний чекер номера телефона, подключается как `Traffic Filter`; ответ пишется в поле визита `IsOnWhatsApp`. *уточните у поддержки*.
- **Traffic Filter** `[AIO]` — **единая сущность** в продукте для всех интеграций фильтрации/обогащения трафика. Подключается в `Settings → Traffic Filters` и используется как шаг во флоу. Примеры: `IPInfo`, `Emailable`, `WhatsAppCheck`, `AIO Filter`, `AIO Filter Service`, а также сторонние сервисы фильтрации и генерации вайтов (набор доступных — в дропдауне `Integration type`).
- **`Traffic Enrichment` (условный ярлык, не отдельная сущность)** `[AIO]` — **не отдельный тип в продукте**, а условное название use-case'а, когда `Traffic Filter` дозаполняет поля визита. Технически — обычный `Traffic Filter`. *уточните у поддержки*.
- **Settings → Traffic Filters** `[AIO, раздел UI]` — раздел, где подключаются все интеграции `Traffic Filter`. *уточните у поддержки*.
- **landing fingerprint** `[AIO, SDK]` — данные о визите, которые SDK скидывает батчем при первом заходе на лэнд: `timezone`, `landed`, скроллинги, разрешение экрана, landing fingerprint.
- **landing JS check** `[AIO]` — флаг, отправляемый в AIO при успешной прогрузке лэнда и работе JS. Индикатор для `Qualified Visits` / `Visit Loss`.

## Контент и лэндинги AIO

### Структура раздела Content

- **Content section (вкладки)** `[AIO]` — раздел Content имеет 7 вкладок: **Landings**, **PWA**, **Creatives**, **Content Library**, **Macros**, **Uploaded Files**, **CDN files**.
  - **Landings** — лэнды с метаданными (UUID, Tags, Type, Templates); только лэнды режима `Editor`.
  - **PWA** — PWA-шки, лэнды режима `PWA` (только ERP); отдельная страница рядом с `Landings`. [how-to/pwa.md](../how-to/pwa.md).
  - **Creatives** — креативный контент (баннеры, файлы) сгруппированный в папки.
  - **Content Library** — типизированные объекты с custom structure (см. ниже).
  - **Macros** — макросы тенанта (см. ниже).
  - **Uploaded Files** — личные файлы юзера (видит только свои).
  - **CDN files** — файлы на CDN (CSS, HTML, JS — редактируемы; остальное только просмотр).
- **Creatives** `[AIO, вкладка в Content]` — вкладка для хранения креативного контента (баннеры, картинки и т.п.) в папках. Каждая папка имеет экшен `Show Creative Items` для просмотра содержимого.
- **Uploaded Files** `[AIO, вкладка в Content]` — личные файлы пользователя. Каждый юзер видит только свои загрузки.

### Лэнды и редактор

- **Manage landing** `[AIO]` — визуальный редактор лэндов. Без верстальщика правишь текст/визуал/структуру. 4 режима редактора:
  - **Code** — HTML-код.
  - **Visual** — WYSIWYG, правка текста / изображений.
  - **Split** — два пана: код + визуал side-by-side.
  - **Full Preview** — превью без редактирования.

### Content Splits / LP-сплиты на лэнде

- **Content Settings (внутри Manage landing)** `[AIO]` — кнопка справа в Manage landing для управления Content Splits (LP-сплитами). Внутри: `+Create Split`, `Control` (выбор стратегии: Conversions AI / Weights / First), `Conversion` field (на какую конверсию оптимизироваться или `Any Conversion by business value`).
- **A/B тестирование (Split) / LP-сплиты** `[AIO]` — функция сплитирования контента на лэнде. Пишешь Split Key (например `cta`), добавляешь варианты, выставляешь вес и правила показа по любой переменной из клика. Варианты конкретного элемента лэнда (заголовок, изображение, любой HTML), управляемые на уровне кампании. Создаются на лэнде через выпадающее меню справа, типы: text / image / HTML. Дают байеру возможность тестировать варианты, не имея доступа к самому лэнду.
- **Color Groups (в Content Splits)** `[AIO]` — связывают сплиты между разными элементами лэнда. Если один сплит выбрал «зелёный» вариант, другой сплит с той же color group тоже покажет «зелёный». Аналог Split Groups на уровне Flow, но для контента лэнда.
- **MVT (Multivariate Testing)** `[AIO]` — мультивариативное тестирование. Алгоритм оптимизации Томпсона. Не отключает остальные варианты — ретестирует на новой аудитории. Метрики на элементе:
  1. Показ
  2. Reward (целевая конверсия)
  3. Эффективность (% из показа в конверсию)

### Аналитика и инструменты лэнда

- **Heatmaps** `[AIO]` — тепловые карты. Красная зона = наибольший интерес, синяя = где интерес пропадает. Облачное решение, без редиректа — работают всегда.
- **Video Sessions** `[AIO]` — видеозаписи сессий. Каждое действие на лэндинге. Notes можно фиксировать прямо в интерфейсе.
- **Глобальные макросы** `[AIO]` — пиксели и кастомные куски кода, применяемые ко всем лэндингам системы сразу (см. также `Macros`).
- **Загрузка лэнда** `[AIO]` — поддерживается ZIP-файл. **index.html должен быть в корне архива** (типичная ошибка — папка-в-папке; с вероятностью 95% сломанные стили именно из-за этого). Альтернатива — создать PWA прямо в системе. При загрузке указывается `Lander template` (по дефолту `Simple`), Lander Type, опциональные Country и Language. [how-to/landings.md](../how-to/landings.md).
- **Lander Template** `[AIO]` — обёртка над лэндом, в которую можно вынести общие элементы (например, header / footer для серии новостных лэндов). По дефолту все лэнды используют шаблон `Simple` — пустую обёртку.
- **Sub-pages / Подстраницы** `[AIO]` — дополнительные `.html` файлы в архиве лэнда (кроме `index.html`). Доступны в редакторе через выпадающее меню Pages. Можно использовать для разных языковых версий или встроенной спасибки. **Возврат на главную страницу** — через корневой путь `href="/"` (возврат на index = пустой путь `""`). [how-to/landings.md](../how-to/landings.md).
- **Категоризация лэндов** `[AIO, рабочий приём]` — лэндам можно задавать страну/гео и язык, после чего фильтровать по тегам/гео в интерфейсе. Альтернатива папкам под разные истории/гео. Сразу важно: эта категоризация **не влияет на доступ трафика** к лэнду — это просто метаданные для скриптов и поиска.
- **Процессинг лэнда** `[AIO]` — обработка ZIP-архива при загрузке: AIO заменяет href-ы на CDN-пути, добавляет `{{aio:head}}` в `<head>` и `{{aio}}` перед `</body>`. Лэнд доступен мгновенно отовсюду — CDN решает географию. [models/landing.md](../models/landing.md).
- **Download Landing** `[AIO, действие]` — экшен по правой кнопке мыши на лэнде: собирает архив асинхронно, готовые ссылки приходят уведомлением в колокольчик — `Original` (изначально загруженный, без правок) и `Merged` (с правками из редактора AIO). Ссылка живёт 7 дней. Механика уведомления — [mechanics/notification-center.md](../mechanics/notification-center.md), процедура — [how-to/landings.md](../how-to/landings.md).
- **CDN files** `[AIO]` — отдельная вкладка лэнда со всеми файлами, загруженными на CDN из архива. CSS/HTML/JS редактируемы; остальные форматы только на просмотр. Файл `index.html` здесь показан как **`<uuid>.index.html`** — это **оригинальный** index из архива, AIO его не трогает. **Визит этот файл НЕ открывает** — визиту отдаётся обработанный (processed) `index.html` из редактора `Manage landing → Code`. JS/CSS при этом не дублируются и не модифицируются — процессятся только HTML-файлы (index и подстраницы). *уточните у поддержки*.
- **Landing Quick Preview / Embed Preview** `[AIO, экшен]` — быстрый preview лэнда без открытия новой вкладки. Доступен:
  - В `Content → Landings` через иконку «глаз» или action `Embed Preview`;
  - В `Tracker → Campaigns` при наведении на лэнд внутри Content step;
  - В `Analytics → Roll Up Report / Campaigns` через групёры с лэндами.

  Ссылка превью открывается только под активной сессией AIO: в инкогнито или у человека без доступа к рабочему пространству она отдаёт `404` вместо страницы лэнда. Показать лэнд снаружи через неё не выйдет — [how-to/landings.md](../how-to/landings.md).
- **Dummy Destination** `[AIO, мок]` — встроенный «дестинейшн» для тестов. Существует **два варианта**: `DummyApi` — фейк-API (в режиме `Push` отдаёт `success` + фейковый id лида + автологин на `google.com`); `DummyRedirect` — то же для redirect-интеграции. Режим задаёт настройка `Mode`: `Push` (все пуши успешны) / `Reject` (все пуши реджектятся). Удобно при настройке нового лэнда — прогнать форму, убедиться что она пушится, без отправки тестов в реальную партнёрку.

### Плейсхолдеры и макросы

- **Плейсхолдер `{{link}}`** `[AIO, плейсхолдер]` — placeholder для ссылки, ведущей на следующий шаг во флоу. На прилэнде — обычно на оффер, на оффере — в дестинейшн (или на любой другой шаг, если так настроено в Flow). Ставится значением атрибута `href` (`<a href="{{link}}">`) вместо статичного URL исходного лэнда — не заменяет сам тег `<a href>`, а подставляется внутрь него. Доп. параметров не нужно — AIO сам разруливает, куда вести по текущему флоу.
- **Плейсхолдер `{{form}}`** `[AIO, плейсхолдер]` — placeholder, в который подгружается AIO SDK-форма. Заменяет статичную HTML-форму. Привязка конкретной формы к кампании — через шаг флоу `Fill Form` либо через выбор формы в `Content` шаге флоу (`Settings → Forms` создаёт форму, `Tracker → Flows → Content` или `Fill Form` её выбирает). Пронумерованные формы `{{form:1}}`, `{{form:2}}` (до 5) поднимают отдельные транзишны флоу: `Handle form 1`, `Handle form 2`, 3, 4, 5, плюс `Handle all forms` — тот же паттерн, что у `{{link:N}}`. Как альтернатива, несколько плейсхолдеров `{{form}}` рендерят одну и ту же форму в разных местах лэнда (одна форма, несколько точек отображения).
- **AIO Head / AIO Body** `[AIO, плейсхолдеры]` — два служебных плейсхолдера, которые AIO автоматически добавляет в каждый загруженный лэнд при процессинге:
  - `{{aio:head}}` — ставится в `<head>` лэнда, в него рендерятся макросы с `Preferred Placement: head` (задаётся в `Content → Macros → Preferred Placement`).
  - `{{aio}}` — ставится перед `</body>` (footer placement), в него рендерятся макросы без явного preferred placement (по дефолту — footer), включая `AIO SDK Macros Collection`.
- **Плейсхолдеры `{{cdn}}` / `{{cdn-lp-folder}}`** `[AIO, плейсхолдеры]` — два плейсхолдера для путей к файлам лэнда:
  - `{{cdn}}` — обрабатывается на этапе процессинга при загрузке ZIP, заменяется на полный путь к CDN. Используется внутри JS / CSS файлов, когда из скрипта или стиля нужна ссылка на файл на CDN (например, `{{cdn}}/assets/image.png`).
  - `{{cdn-lp-folder}}` — подставляется в runtime (на стороне визита). Используется внутри inline-скриптов прямо в `index.html`, которые сами обращаются к файлам и не должны вшивать конкретный путь.
  - Нужны только тогда, когда вызовы изображений / скриптов идут изнутри JS / CSS / inline-script'ов (в обычном HTML/CSS пути обрабатываются автоматически).
- **Macros** `[AIO, вкладка в Content]` — вкладка `Content → Macros`, в которой лежат все макросы тенанта: и шаблонные (`AIO SDK Macros Collection` — конфиг SDK, `AIO Non-SDK Form Handler` и др.), и кастомные. У каждого макроса:
  - **Active** — включён/выключен.
  - **Global** — глобальный (применяется ко всем лэндам автоматически) или локальный (вызывается на лэнде через `{{aio:macros:<slug>}}`).
  - **Prefer Placement** — `Header` (макрос подгружается в `{{aio:head}}`) или `Footer` (в `{{aio}}`).
  - **Slug** — используется в локальном вызове.
- **AIO SDK Macros Collection** `[AIO, шаблонный макрос]` — главный шаблонный макрос из коробки, лежит в `Content → Macros`. Содержит JS-конфиг SDK: блок `features` (флаги фич) + блоки настроек для каждой включённой фичи (`backFix`, `form` и т.п.). Технически — обычный макрос в блоке `Macros`, просто с дефолтным содержимым. Дефолтный набор `features`: `backFix`, `fbCapi`, `fbPixel`, `form`, `browserTimezone`, `landed`, `scrolling`, `sessionRecords`, `timeOnLandings`, `windowDimensions`, `hueChanger`. При тонкой настройке (расширить Backfix, привязать `Push Subscribe Toggle`, добавить `beforeSubmitPromise` и т.п.) правки идут именно в этом макросе.
- **Backfix (конфиг)** `[AIO, SDK]` — внутри `AIO SDK Macros Collection`, блок `backFix: {...}`. Под-настройки:
  - `enabledBackFix: () => [...].includes(aio.landing.lander_type_uuid)` — функция-условие. Обычно проверяет, что текущий лэнд — preland (по UUID типа лэнда).
  - `enableStrangeUrlParameters: true` — переписывает реальные CUUID/SUUID в URL на fake UTM-параметры, чтобы юзер не мог расшарить ссылку.
  - `pathName`, `localStorageKey` — служебные.
  - `link: '{{link}}&backfix=true'` — куда уходит визит при срабатывании Backfix, с пометкой `backfix=true`.
  - В аналитике у визитов, пришедших через Backfix, есть отдельное поле `Backfix=Yes` в трекере.

  [reference/sdk.md](sdk.md).
- **EnableStrangeURLParameters** `[AIO, фича SDK]` — под-настройка `backFix`. Если включена — в URL визита реальные CUUID/SUUID/etc. переписываются в fake UTM-параметры (рандомный набор). Защита от шаринга ссылки: если кто-то скопирует URL и пошлёт другому, по нему нельзя будет повторить визит.
- **landed** `[AIO, фича SDK]` — boolean-фича, фиксирует, что визит реально загрузил лэнд (используется в метрике `Qualified Visits`).
- **windowDimensions** `[AIO, фича SDK]` — записывает размеры окна визита (ширина/высота).
- **Static Language Country (макрос)** `[AIO]` — глобальный макрос, который фиксирует язык и страну SDK-формы по **лэнду**, а не по визиту (без него — берёт из браузера/гео визита; ломается под VPN). Рекомендуется включать как глобальный. [reference/sdk.md](sdk.md).

### Формы — конфигурация и макросы

- **Form Behavior settings (`config.form`)** `[AIO, SDK]` — дефолтная конфигурация формы (можно переопределить через `window.aioBus.push({type:"config", config:{form:{...}}})`):
  - `url`, `selector`, `defaultCss`
  - `successTimeoutSeconds` (по дефолту 5)
  - `language` (по дефолту `navigator.language.slice(0,2)`)
  - `defaultCountryCode` (по дефолту `GB`)
  - `stepsShowing`, `collectDataEvent` (`blur`)
  - `rejectedMessage` (по дефолту «We cant register you at this time.»)
  - `beforeSubmitPromise`, `submitPromises` (хуки SDK-формы)
  - `intlParameters` (для intl-tel-input — `nationalMode`, `autoPlaceholder`)
  - `templates` (HTML-шаблоны для каждого типа поля)
- **Non-SDK Form Handler / AIO Non-SDK Form Handler** `[AIO, макрос-фолбэк]` — макрос в `Content → Macros` для лэндов, где нужно оставить родную HTML-форму вместо SDK-формы. Подкручивает обработку сабмита, чтобы лид всё равно ушёл по флоу AIO. Вызывается на лэнде через `{{aio:macros:nonsdk_form_handler}}`, ставится после закрывающего `{{aio}}`. Требует, чтобы slug-и инпутов кастомной формы совпадали с AIO-слагами: `first_name`, `last_name`, `email`, `phone`. Активно НЕ развивается, новые фичи не приезжают — использовать только в крайнем случае.
- **BeforeSubmit Promise** `[AIO, хук SDK-формы]` — асинхронный JS-хук: «форму проверили валидацией, но ещё не запушили в дестинейшн». Позволяет вставить дополнительную логику до пуша (например, проверку, показ модалки).
- **Submit Promise** `[AIO, хук SDK-формы]` — асинхронный JS-хук вокруг самого пуша в дестинейшн: можно отслеживать момент отправки и обработки ответа, переключать модалки по результату.
- **Pushing modal / Countdown** `[AIO, UX SDK-формы]` — модалка «идёт отправка» с обратным отсчётом; собирается хуком `submitPromises`, длительность задаётся в самом хуке. Если ответ не пришёл — модалка переключается на «обнови страничку / попробуй ещё». При успешном пуше — на success-модалку с редиректом на автологин-ссылку (её countdown — `form.successTimeoutSeconds`, дефолт 5 c).
- **Advanced Form Sample** `[AIO, пример макроса]` — готовый пример макроса со связкой Promise + модалок (Pushing → Success → Reject); берётся как референс для форм со сложным UX вокруг пуша. Разбор хуков — [reference/sdk.md](sdk.md).

### Формы — Form Builder и SDK-форма

- **SDK-форма** `[AIO]` — форма на оффере, подгружаемая из AIO-SDK (а не вшитый HTML на стороне клиента). Управляется через `Form Builder`. Отображение формы и пуш данных в интеграцию — на бэке AIO, на лэнде форма не «светится».
- **HTML-форма** `[общий]` — обычная HTML/JS-форма, прописанная прямо в коде лэнда. В дефолтном AIO-флоу не используется — заменяется на `SDK-форму`.
- **Form Builder / Билдер форм** `[AIO]` — UI настройки SDK-форм в `Settings → Forms`. 6 вкладок:
  - **Info** — имя, описание.
  - **Controls** — типы полей: text, email, phone, textarea, checkbox, select, submit, date, number; правила: required, minlength, maxlength, pattern.
  - **Steps** — массив массивов, порядок и группировка полей на шагах.
  - **Layouts** — визуальное расположение, поля на одной строке или разных.
  - **Languages** — мульти-язычные переводы: `Label` / `Placeholder`, варианты `Drop list` и строки кнопки Submit; один `Base language` + N дополнительных. Языки добавляются из диалога с двумя сегментами — `Auto-translated` (53 языка, приезжают с префилом) и `All languages` (справочник 185 языков, приезжает пустым).
  - **Preview** — превью формы на разных устройствах.

  [models/form.md](../models/form.md).
- **Controls** `[AIO, форма]` — input-элементы формы. Атрибуты: `key`, `placeholder`, `label`, `value`, `type` (text/email/phone/select/textarea/checkbox/submit/date/number), `rules` (required, minlength:X, maxlength:Y, pattern, type:url, type:number, pattern:no-local-emails).
- **Steps (форма)** `[AIO, форма]` — массив массивов: каждый внутренний массив — один шаг формы.
- **Layouts (форма)** `[AIO, форма]` — массив массивов: внутри одного массива поля идут side-by-side, между массивами — на новой строке.
- **Languages (форма)** `[AIO, форма]` — мульти-язычные переводы `Label` / `Placeholder`, вариантов поля `Drop list` и строк кнопки Submit; у `Tooltip` перевода нет. Один `Base language` + N дополнительных; форма авто-переключается по языку браузера визита. Языки добавляются из диалога с двумя сегментами: `Auto-translated` (53 языка) и `All languages` (справочник 185 языков) — префил определяет выбранный сегмент: из `Auto-translated` язык приходит частично заполненным, из `All languages` — пустым. Авто-перевод заполняет подпись и плейсхолдер только у контролов с ключом `first_name` / `last_name` / `email` / `phone`, смапленных на поле визита, плюс четыре строки кнопки Submit; кастомные контролы и варианты `Drop list` остаются пустыми. Непереведённая строка уже добавленного языка рендерится на лэнде **пустой** — фолбэка на английский нет. [how-to/forms.md](../how-to/forms.md).
- **CSS-переменные `--aio-sdk-form-*`** `[AIO, SDK-форма]` — кастомизация стилей формы через CSS-переменные, оверрайдятся в `<style>` блоке на лэнде или глобально через `AIO SDK Macros Collection`. Полный список: `--aio-sdk-form-padding`, `--aio-sdk-input-bg/border/color/...`, `--aio-sdk-submit-bg/color/...`, `--aio-sdk-form-step-*`.

### SDK и aioBus

- **window.aioBus** `[AIO, SDK]` — глобальный массив-очередь команд для SDK. Через `window.aioBus.push({type, ...})` SDK получает команды:
  - `type: "config"` — конфигурация фич и формы (`features: {...}`, `form: {...}`, `backFix: {...}`).
  - `type: "trigger"` — заполнить визит-поле значением (`{type:"trigger", key:"...", value:"..."}`).
  - `type: "conversion"` — отправить конверсию (`{type:"conversion", type_uuid:"...", query:{revenue: 10}}`).
  - `type: "form-controls"` — заполнить controls формы.
  - `type: "vue-data-object"` — объявить data для Vue.js.
  - Используется как глобально (в `AIO SDK Macros Collection`), так и локально на лэнде (после `{{aio}}`).
- **Vue.js (на лэндах AIO)** `[AIO]` — кастомизация лэндов через Vue.js: `id="vue"` на корневом элементе включает Vue, плейсхолдеры доступны как `{{vue.aio.visit.<...>}}`. Поддерживаемые директивы: `v-if`, `v-else-if`, `v-else`, `v-for`, `@click`. Объекты для шаблонов объявляются через `window.aioBus.push({type:"vue-data-object", data:{...}})`. Используется для динамических переводов / условного рендера / списков.

### Content Library и поля визита

- **Content Library** `[AIO, вкладка в Content]` — хранилище объектов с настраиваемой структурой и атрибутами. Используется для оффер-неймов (с `For Visitor` / `For Advertiser`), для контент-персон (FirstName / LastName / FullName / image / GIF / Title / Description), для пикселей+токенов и т.п. Также **сюда кладётся `Showcase Site`** (массив `Showcase Item`-ов; *уточните у поддержки*); из управления самим объектом задаются только сторона/язык/название, остальное — атрибуты ноды. Объекты можно группировать по папкам.
- **Content Library → Edit Structure** `[AIO, экшен]` — изменение структуры Content Type (атрибуты, поля, ключи).
- **Content Library → Manage Data → +Placeholder Data** `[AIO, экшен]` — добавление конкретных Content Items внутри Content Type. Создаются с именем, заполняются поля из Edit Structure, выбираются Countries/Languages, Lander Placeholder Group, опционально — изображение.
- **Placeholder Group / Lander Placeholder Group** `[AIO]` — группировка Content Item-ов в Content Library, по которой шаг `Fill Fields` во флоу выбирает, из какого набора брать значения. Указывается в атрибуте шага и в атрибутах самого Content Item.
- **Key (в Content Type)** `[AIO]` — slug, используемый для формирования плейсхолдера на лэнде. Если у Content Type, привязанного к полю `offer_name`, создан key `for_visitor`, на лэнде доступен плейсхолдер `{{aio.visit.fields.offer_name.for_visitor}}` — он динамически вставляет значение из соответствующего Content Item. Частный случай для оффер-нейма: на лэнде используется `{{aio.visit.fields.offer_name.for_visitor}}` (For Visitor), при пуше в интеграцию — `for_advertiser` (For Advertiser).
- **LP_HEADER / LP_SUBHEADER / LP_HEADER_IMAGE** `[AIO, специальные поля визита]` — три дефолтных поля типа `variant` из шаблона тенанта. Если `slug` сплита совпадает с одним из этих ключей, выбранный вариант записывается в это поле визита — и можно сводить аналитику разбивкой по нему. При нехватке полей добавляются через Settings → Fields.
- **LP Variants Field** `[AIO]` — специальные поля визита с префиксом `LP_*` и типом `variant`. Если slug сплита совпадает с slug-ом такого поля (`LP_Header`, например) — выбранный вариант записывается в поле визита, и аналитику можно сводить разбивкой по этому полю.
- **Slug (в сплитах лэнда)** `[AIO]` — ключ сплита, должен совпадать с именем `LP Variants Field` (например, `LP_Header`). Тогда выбранный сплитом вариант записывается в поле визита, и аналитику можно сводить разбивкой по этому полю.
- **Showcase — паттерн, не отдельная фича** `[AIO]` — витрина-showcase собирается из существующих механик, отдельной фичи «Showcase» в продукте нет. `Showcase Site`, `Showcase Item`, `Link to Campaign`, `Vue Showcase Site`, `Type Block ID` — **НЕ отдельные термины/фичи AIO**, а произвольные имена объектов и атрибутов.
- **Showcase Send / Showcase Catch + Sessions per Domain** `[AIO]` — имена кампаний в двух-кампанийной схеме витрины. **Sessions per Domain** — в рамках одного домена визит может иметь только одну активную сессию (один State).
- **aio.visit.query** `[AIO, поле визита + плейсхолдер]` — поле визита, в которое AIO при init записывает полный исходный query-string ссылки. Это **и JS-объект, и шаблонный плейсхолдер**: на JS доступно как `aio.visit.query` (весь query) и по ключам через точку (`aio.visit.query.tva`), а в шаблонах — как `{{aio.visit.query}}` (весь query) и `{{aio.visit.query.<key>}}` (один параметр). **Не зависит от** `enableStrangeUrlParameters` — содержит исходный набор даже при скрытых параметрах. Плейсхолдер-форма — [reference/placeholders.md](placeholders.md).
- **Lander Templates** `[AIO]` — механизм смены «шкурки» лэнда (HTML-обёртки) налету через темплейт, без создания отдельных лэндов. Дефолт — `Simple`.
- **Subpage Path (множественные пути)** `[AIO]` — поле `Path` в карточке подстраницы лэнда может содержать **несколько путей через запятую**. Подстраница отдаётся по любому из них.
- **Original / Merged HTML — деталь** `[AIO]` — в `Merged`-версии обработаны **все HTML-файлы** лэнда (`index.html` и каждая подстраница): локальные пути заменены на CDN, вставлены `{{aio}}`-плейсхолдеры. JS/CSS при этом не дублируются и не модифицируются. `Original` — исходный архив без правок.
- **Full CDN used / Temp CDN used** `[AIO, опции Landing Type]` — два флага типа лэнда, относящиеся к раздаче файлов лэнда. `Full CDN used` — неиспользуемая заготовка: читателей в рантайме у неё нет, на отдачу лэнда она не влияет. `Temp CDN used` влияет на то, как раздаются файлы лэнда.

- **Reflect vs Proxy Reflect** `[AIO, payload-типы Content / White шага]` — два payload-типа для показа стороннего сайта под текущим доменом кампании: `Reflect` (облегчённый) и `Proxy Reflect` (полное проксирование через агент).
- **Отдельный домен под лэнды (при Domain Change)** `[AIO]` — отдельный публичный домен, под которым после прохода фильтра открывается лэнд — в противовес tracking-домену залива. Появляется только если в флоу есть шаг Domain Change.
- **Спасибка как Flow Only-шаг** `[AIO, паттерн]` — Content step с `Payload Type: Landing` и режимом `Flow Only` как «динамическая спасибка», видная только во флоу, не торчит в кампаниях.
- **GenAI (кнопка в Content Splits)** `[AIO]` — кнопка, генерирующая через AI **три варианта** похожих заголовков для тестирования.
- **LP Splits (campaign-level кнопка)** `[AIO]` — кнопка в Edit Campaign, появляется **только если на лэнде в payload настроены сплиты**. Позволяет переопределить варианты сплитов локально для кампании, не меняя лэнд глобально. Опции: варианты лэнда **или** `use campaign splits`.
- **Split Group field (split groups MT)** `[AIO, поле визита]` — поле визита, в котором хранится сплит-группа (цвет). По дефолту визит приходит без сплит-группы. Цвет пишет любая нода-выборщик — **Content**, **Fill fields**, **Fill form**, **Fields by distribution** — первым не-`Rainbow` вариантом (см. также [models/flow-model.md](../models/flow-model.md), раздел «Split Groups — маршрутизация цветами»).
- **Fill Text (payload type шага Fill Fields)** `[AIO]` — режим payload для шага `Fill Fields`, ограничивающий контент только текстом (запись текста в поля визита).
- **Handle-link N / Handle all links / Handle (fallback)** `[AIO, transitions]` — `Handle-link <N>` — пронумерованный transition на клик, привязан к кнопке через `{{link:N}}`. `Handle all links` — отдельный тип transition, обрабатывающий клик на **любой** из пронумерованных линков (группирует все нумерованные линки в один переход, когда для всех них нужна одинаковая ветка флоу вместо отдельного `Handle-link N` на каждый номер). AIO сначала проверяет пронумерованные `Handle-link N`; если ни один не подошёл — срабатывает базовый `Handle`. `Handle` обязателен на шаге с `Handle-link N` (даже клик по `{{link}}` под капотом — зашифрованная команда «перейди на следующий шаг»).
- **{{link:N}} + Link N (нумерованные переходы)** `[AIO, плейсхолдер]` — `{{link:1}}`, `{{link:2}}`, ... — несколько разных переходных ссылок с одного лэнда. Каждый номер — отдельный transition во флоу (`Link 1`, `Link 2`, ...), может вести в разные наборы офферов. Доступно **до 5 линков**. На шаге обязателен базовый `Handle` (см. ниже `Handle-link N / Handle all links / Handle (fallback)`).

## Кампании и запуск трафика в AIO

- **Кампания** `[AIO]` — контейнер запуска: флоу + источник + лэнды + интеграция + правила.
- **Левая часть окна создания кампании** — мета кампании: название, описание, цвет, страна, язык. **Это не настройки фильтра**, это удобство фильтрации внутри AIO.
- **Стратегии выбора** `[AIO]` — когда вариантов больше одного (несколько прилэндов, офферов, доменов и т.д.). **Четыре стратегии**: `First`, `Weights`, `Conversions AI`, `Metrics AI`:
  - **First** — проход сверху вниз. Пробует выбрать первый вариант; если он не прошёл свои правила — следующий, и так далее. Если ни один не подошёл — уходит по `No Payload`.
  - **Weights / Веса** — распределение по весам. Одинаковые веса = равномерное распределение.
  - **Conversions AI** — AI-оптимизация под конкретную целевую конверсию. Под капотом — `Thompson Sampling`, перераспределяет трафик к варианту с лучшей конверсией, не отключая остальные. Часто называется просто «AI» или «ML». *(Ключ в коде — `Machine Learning`.)*
  - **Metrics AI** — AI-оптимизация под произвольную числовую метрику (CTR, EPL, ROAS и т.п.) за окно `TimeFrame`. Под капотом — `Epsilon-Greedy`: с вероятностью ~10% исследует, выбирая вариант равномерно случайно среди всех вариантов (лучший может переизбраться), остальные ~90% — эксплуатирует вариант с наибольшим значением метрики. *(Ключ в коде — `Relative Machine Learning`.)*

  **Граница доступности:** в редакторе шага для дестинейшна/контента доступны только `First` / `Weights`; полный набор — в дереве Distribution.

- **Balance (кнопка)** `[AIO]` — **не отдельная стратегия**, а UI-кнопка, появляющаяся в контексте стратегии `Weights` у дистрибуций/сплитов (`Campaign Content`, `Direct Traffic`, `Fill Field`). Одним нажатием выставляет всем вариантам равные веса (равномерно балансирует распределение). **На стратегиях шага Flow (`Flow node`) кнопки `Balance` нет.** Не путать с `Conversions AI` — `Balance` просто уравнивает веса, без AI-оптимизации.

- **Generate Link / Link Generator** `[AIO]` — генератор tracking-ссылок для кампании. 3 способа открытия: Action Menu по кампании → Link Generator, Edit Campaign → Link Generator tab, Edit Campaign → Link Source. Атрибуты при генерации: Domain, Source, `Link Generation Name` (для удобства поиска в истории), Source-specific параметры. Toggle `Lock campaign to this domain` ограничивает кампанию одним доменом.
- **Link debugger** `[AIO, инструмент]` — инструмент отладки трекинговой ссылки: вставляешь ссылку → `Debug` → видишь расшифрованный query зашифрованной ссылки плюс параметры, подставляемые доменом (`Default Query`). Помогает понять, что реально приедет в визит с этой ссылки/домена. UI-подпись — `Link debugger`.

  Форматы ссылок:
  - **Дефолтная** — внутренние айдишники не спрятаны, для запуска не используется; только для проверки.
  - **Encrypted** — зашифрованная: внутренние идентификаторы в ссылке скрыты. Основной формат для запуска трафика.
  - **Slug / шорт-ссылка** — короткая; source-параметры (ad/adset/campaign names) дописываются хвостиком автоматически.

- **Pixel / FB Pixel** `[общий]` — пиксель Facebook для трекинга на стороне площадки.
- **CAPI (Conversion API)** `[общий]` — server-to-server передача конверсий в рекламную площадку. По дефолту в шаблоне работает.
- **Conversion API для Google: gtag vs offline-таблички** `[общий]` — два пути отдачи конверсий в Google:
  - **gtag** — дефолтный, передаёт только то, что произошло на самом лэнде.
  - **Offline conversions через CSV-таблицу** (External Report `Google Conversions CSV`) — параллельный путь: Google периодически сам подтягивает CSV по ссылке, обновляет данные. Позволяет передать Purchase и другие конверсии, которые произошли вне лэнда. Настройка — [how-to/api.md](../how-to/api.md).

  Оба пути шлются параллельно — это норма, а не дубль: и gtag, и offline-отчёт передают `gclid`, по нему Google у себя дедуплицирует конверсии. Глобальное включение gtag-макроса Facebook-трафик не задевает — срабатывает он только на трафике с Google.
- **gclid** `[общий]` — Google Click ID, параметр клика Google (аналог fbclid). Передаётся в обоих путях отдачи конверсий; по нему Google дедуплицирует конверсии между gtag и offline-CSV.
- **Lead Action** `[AIO, в кампании]` — какое событие отправлять в рекламную площадку при лиде по постбэку.
- **Purchase Action** `[AIO, в кампании]` — какое событие отправлять в рекламную площадку при целевой конверсии (например, покупке / первом целевом действии).
- **Cost Update Strategy** `[AIO, поле кампании]` — **устаревший путь; основной способ по костам/профиту FB — метрика `Meta Spend`** ([mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md)). Стратегия автоматического подтягивания costов из Meta (наполняет метрику `Costs` на визитах). Настраивается в Edit Campaign; также вынесена отдельной колонкой `Cost Strategy` в таблице кампаний (чтобы не заходить в Edit). **Два пути атрибуции:** Путь №1 — `AIO and Meta` (по `FB ad id`); Путь №2 — link кампании напрямую к Meta-аккаунту, применяется когда нельзя передать FB ad id в ссылке (запуск из текста/комментариев), все косты с Meta-аккаунта распределяются среди всех визитов кампании. Механизм живой, но не основной — трогай, когда нужен именно visit-level `Costs` для классического ROI.
- **Update Costs** `[AIO, экшен]` — ручное обновление costов кампании за период. Указывается time range, timezone, поле + значение для применения, значение Costs/CPC.
- **Replace Destination** `[AIO, экшен]` — массовая замена дестинейшна в кампании (From → To).
- **Change Owner / Change Ownership** `[AIO, экшен]` — передача владения сущностью (кампания, лэнд, домен и т.п.) другому юзеру. Прежний owner становится shared-юзером, новый — owner-ом. **Owner сущности ≠ Tenant Owner** — `Change Owner` на сущности на роль тенанта не влияет. Tenant Owner — тот, кто создал тенант; сменить его нельзя, можно лишь через `Manage Tenant` выдать роль `Owner` ещё одному юзеру. [models/permissions-model.md](../models/permissions-model.md).
- **Freeze top / Freeze bottom** `[AIO, экшен в таблицах]` — закрепить выбранную сущность вверху или внизу таблицы для быстрого доступа. Действие обратимо — `UnFreeze top` / `UnFreeze bottom` возвращает на изначальную позицию.
- **Meta Application** `[AIO]` — вкладка для подключения FB-приложения в системе. Подключается только основное приложение — используется официальная интеграция.
- **Budget Manager** `[AIO, Meta-модуль]` — экшен на FB-кампании для правки бюджета из AIO; сам подтягивает режим кампании (CBO или ABO) и рисует нужные поля. Разбор — [how-to/meta-ads.md](../how-to/meta-ads.md).
- **CBO (Campaign Budget Optimization)** `[Meta]` — бюджет задаётся на всю кампанию (одно поле `campaign_budget`), Meta сама раскидывает его по адсетам. Один из режимов Budget Manager.
- **ABO (Ad Set Budget Optimization)** `[Meta]` — бюджет задаётся по каждому адсету отдельно (`adset_budget:<uuid>`). Второй режим Budget Manager.
- **Social profiles (Meta)** `[AIO]` — раздел `Meta → Social profiles`: подключение FB-профилей для пуллинга. Разговорное: «Meta Social Profiles», «соцка».
- **Polling Interval** `[AIO]` — частота, с которой AIO пуллит данные из Meta Marketing API (Facebook → AIO). Дефолт — каждые 30 минут; можно триггерить вручную через `Pull data` (правый клик на соцке). Это **только** опрос Facebook → внутреннее хранилище AIO; отдельно от перелива в кампании — см. `AIO Meta — cost-перелив в кампании`. Косты пуллятся из меты каждые 30 минут, переливаются в кампании каждые 10 минут.
- **AIO Meta — cost-перелив в кампании** `[AIO]` — **устаревший путь; основной способ по костам/профиту FB — метрика `Meta Spend`** ([mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md)). Внутренний процесс AIO, который раз в **10 минут** переливает спулленные из Meta cost-данные **на визиты**, сопоставляя `FB Ad ID` Meta с полем `FB Ad ID` визита (Cost Spillover Level, дефолт — уровень `ad_id`). Это шаг **после** `Polling Interval` — не путать. **Ретро-окно атрибуции — 2 дня (фиксированное, не конфигурируется)**: атрибуция срабатывает только если есть визит за последние 2 дня по этому `FB Ad ID`; иначе спенды не атрибутируются. Наполняет метрику `Costs` на визитах (для ROI). Привязка **неточная** — если по `ad_id` нет ни одного визита, его spend не переливается (часть костов теряется). **Не путать** с `Meta Spend` — это отдельный report-time движок аллокации Meta-spend по visit-разрезам аналитики ([mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md)); механизмы **сосуществуют**, но `Meta Spend` — основной.
- **Connect (правый клик на соцке)** `[AIO]` — действие подключения рекламного аккаунта. Берётся OAuth-ссылка, открывается, даётся разрешение AIO-апке. После — соцка пулится автоматически. Пошагово — [how-to/campaigns.md](../how-to/campaigns.md). *(Слэнг: `соцка` (от **соц**иальные профили) — разговорная форма.)*
- **Costs Updated** `[AIO, поле в таблице кампаний]` — скрытое по дефолту поле в Tracker → Campaigns — время последнего перелива костов по кампании.
- **Generated Links (экшен на кампании)** `[AIO]` — экшен, показывающий все ранее сгенерированные ссылки кампании. По правой кнопке можно редактировать `Slug` существующей ссылки. Открывается через дропдаун справа от кнопки `+Campaign` на странице Tracker → Campaigns. Отличается от `Link Generator History`.
- **Pull data (кнопка ручного пуллинга)** `[AIO]` — UI-кнопка (`Pull data`), принудительно подтягивает свежие данные из Facebook между регулярными 30-мин пуллингами.
- **«Глазик» в Roll-Up (просмотр креатива)** `[AIO]` — иконка в строке `FB Ad ID` в Roll-Up Report — по клику открывает креатив объявления (статика/видео). **Не работает** на динамических объявлениях с гео-зависимым контентом.
- **AIO Meta (Cost Update Strategy)** `[AIO]` — **устаревший путь; основной способ по костам/профиту FB — метрика `Meta Spend`** ([mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md)). `AIO Meta` — значение Cost Update Strategy: косты обновляются автоматически через интеграцию (наполняет метрику `Costs` на визитах для классического ROI). `Pull Data` по рекламному аккаунту делится на два под-пула: **сущности** (campaigns/adsets/ads) и **insights** (клики/импрешны/косты/спенд — числа).
- **Streams (Money Streams)** `[AIO]` — механизм периодического обмена данными с внешними системами: два типа потока — `Visit Costs` (подтягивать косты визитов) и `Conversions Revenue` (подтягивать revenue конверсий); поток подключается к кампании (`Connect`), есть логи. Раздел **живой** (страница `Settings → Streams`, в билдах ERP и MTK), **но пока не в активном использовании** — перелив костов идёт через `Cost Update Strategy` (устаревший путь; основной способ по костам/профиту FB — метрика `Meta Spend`). Не deprecated: фича на месте, просто пока не основной путь.
- **Insights API (FB hourly aggregate)** `[AIO]` — официальная либа Facebook, через которую AIO пуллит расходы. Запрос с брейкдауном по часовой зоне кабинета и по `ad_id` — за каждый час, для каждого ad_id (нужна почасовая разбивка для сквозной аналитики «за сегодня» при разных тайм-зонах/валютах/сотнях кабинетов).
- **Agency Commission** `[AIO]` — поле при создании Social profile во вкладке Meta → Social Profiles — процент комиссии агентского кода, прибавляется к спенду при пуллинге.
- **Cost Spillover Level (уровень перелива костов)** `[AIO]` — настройка **устаревшего пути перелива костов** (основной способ по костам/профиту FB — метрика `Meta Spend`, [mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md)): уровень FB-иерархии, на котором AIO атрибуцирует косты на визиты: `ad_id` (дефолт), `adset_id`, `campaign_id`. Перелив с уровня выше — обходной путь для CPM, когда на объявлении не было визитов (косты размазываются среди визитов кампании/adset). Не путать с report-time аллокацией `Meta Spend` ([mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md)) — это разные сосуществующие механизмы (перелив пишет cost в таблицу кампаний; `Meta Spend` раскладывает spend по разрезам отчёта на лету).
- **Cost Refresh Cycle (10 минут / 2 дня назад)** `[AIO]` — внутренний цикл AIO Meta — каждые 10 минут смотрит косты за последние 2 дня и переливает.
- **Meta Spend (метрика) / AIO Attribution Engine** `[AIO, аналитика]` — метрика **`Meta Spend`** в отчёте = рекламный расход из Meta, разнесённый по visit-уровневым разрезам **в момент построения отчёта** (движок — `AIO Attribution Engine`): дневной расход объекта Meta на выбранном уровне (`campaign` / `adset` / `ad`) распределяется по визитам, у которых в этот день был этот объект, пропорционально их числу. **Уровень матчинга выбирается кнопкой с иконкой Meta в тулбаре таблицы** (`Campaign` / `Adset` / `Ad`), по умолчанию `campaign`; выбор общий для всех таблиц и хранится в браузере — другой браузер стартует с `campaign`. **Основной способ работать с костами и профитом по FB** — рядом с ней в отчёте стоит revenue, поэтому профит и ROI по FB читаются прямо в разрезе с колонкой `Meta Spend` (Source, Destination, гео, оффер). Инвариант: Σ по match-key = расход Meta по этому ключу. Не разложенный расход — **не отдельная колонка**: разбивка `Matched` / `Orphans` / `Out of scope` показана в подсказке ячейки — см. `orphans / scope-orphans / out-of-scope`, `status`. **Не путать** с `Cost Spillover Level` / `AIO Meta — cost-перелив` (перелив костов **на визиты** по `FB Ad ID`, неточный — другой механизм). Полностью — [mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md).
- **Meta Spend Allocation vs Cost Spillover (два механизма Meta-spend)** `[AIO]` — два **разных** сосуществующих механизма разнесения расхода Meta:
  - **`Meta Spend Allocation`** (новый) — атрибуция расхода Meta по визитам отчёта на лету, пропорционально визитам разреза. Матчит по объекту Meta выбранного уровня × день: `campaign` (дефолт) / `adset` / `ad`, уровень переключается кнопкой в тулбаре таблицы и хранится в браузере; **не зависит** от `Cost Update Strategy`. Ничего не теряет, сходится до копейки, помечает строки статусом (`fine` / `noisy` / `partial`).
  - **`Cost Spillover` / старый перелив костов** (старый) — переливает расход Meta на визиты, наполняя метрику `Costs` для ROI. **Три стратегии матчинга** по `Cost Update Strategy`: `Meta Ad` (`ad_id`), `Meta Adset` (`adset_id`), `Meta Campaign` (`campaign_id`). Неточный — теряет расход по `ad_id` без визита.
  - Полностью — [mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md).
- **match-key / result-key / scope-prefix (аллокация Meta-spend)** `[AIO]` — три ключа в аллокации `Meta Spend`. **match-key** связывает строки traffic и Meta: `<id объекта Meta выбранного уровня> × день` — по умолчанию meta-кампания × день, на уровне `adset` / `ad` — адсет или объявление × день (это сущности рекламного кабинета, а не кампания AIO). **result-key** — visit-уровневый разрез, в который складывается итог (лэнд, оффер, страна, движок); в спенде, который Meta отдаёт (агрегат по объекту кабинета × день), таких разрезов нет. **scope-prefix** — тот же id объекта Meta без дня; определяет «наше vs чужое» при разделении orphans. Один match-key раскладывается на много result-key пропорционально визитам. См. [mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md).
- **scope-prefix (аллокация Meta-spend)** `[AIO]` — id объекта Meta на уровне матчинга без дня (на дефолтном уровне — meta-кампания), берётся из **baseline**-трафика. Meta-строка, чей scope-prefix есть в baseline, — «наша» (её неразложенный spend → `scope-orphans`); чей нет — «чужая» (в скоупе запроса нет ни одного её визита → `out-of-scope`). Стабилен на любой глубине drilldown. См. [mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md).
- **baseline (знаменатель аллокации при drilldown)** `[AIO]` — приём, держащий суммы `Meta Spend` согласованными между уровнями drilldown: числители считаются по узкому (раскрытому) срезу, знаменатели — по более широкому baseline-набору без drilldown-фильтров. Без него знаменатель схлопывается и spend на уровне раздувается (`Σ детей > parent`). Из baseline же берётся и **scope** (`scope-prefix`-ы «наших» кампаний), и определение orphan (ноль визитов **в baseline**, а не в узком срезе). При раскрытии funnel-разреза (Destination / лэнд / оффер) по обычному разрезу условие «дошёл до этого шага» попадает и в знаменатель подгруппы — поэтому дети суммируются в родителя (Destination = сумма его источников). См. [mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md).
- **orphans / scope-orphans / out-of-scope** `[AIO]` — рекламный расход, который **не вышло** разложить (match-key есть, визитов в baseline нет — делить не на что). **Не отдельная колонка/метрика в таблице.** Делится по `scope-prefix`: **scope-orphans** — кампания наша, но визитов под match-key нет (реальный пробел атрибуции); если эту долю не удалось надёжно привязать к строке, строка получает статус `partial`, и непривязанная часть видна **в подсказке (tooltip) этой строки**. **out-of-scope** — спенд объектов Meta, у которых в скоупе запроса нет ни одного визита; под любым фильтром это норма (при фильтре по одной кампании AIO в `Out of scope` уходит спенд объектов Meta, чьи визиты шли в другие кампании). В итог и в формулы (`Profit`, `ROI`, экспорт) не входит; виден в подсказке ячейки строкой `Out of scope`, а клик по подчёркнутому значению переключает показ на `Total + out of scope` (переключатель общий для всех Meta-колонок, хранится в браузере). У строк всегда 0 — значим только в футере. Внутренний инвариант: привязанный `Meta Spend` + scope-orphans ≈ весь расход Meta в scope (отсюда «сходится до копейки»). Большой непривязанный → чинить атрибуцию; большой `Out of scope` на отфильтрованной странице — не поломка. См. [mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md).
- **Empty bucket (пустой result-key)** `[AIO]` — корзина для визитов, у которых match сработал, но result-key пустой (UA не распарсился → нет движка; IP-гео не сработало → нет страны). Spend на них аллоцирован **легитимно**, bucket **входит в footer** (видимая строка «Empty»). Не путать со scope-orphans (визитов нет, но кампания наша) и out-of-scope (чужая кампания). См. [mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md).
- **`status` (fine / noisy / partial)** `[AIO, аллокация Meta-spend]` — колонка доверия к строке `Meta Spend` в отчёте. `fine` — все проверки прошли, доверяй. `noisy` — `Meta Spend` может быть **завышен** (шумная экстраполяция на funnel-разрезе — мало визитов дошло до уровня). `partial` — часть расхода в строке **не показана** (orphan-долю не удалось надёжно привязать); полная цифра — в родителе/футере, а сколько именно не привязалось — видно в **подсказке (tooltip)** этой строки. При совпадении побеждает `partial` (недосчёт важнее неточности). У строк `noisy` бывает **только** на разрезах оффер/лэнд/Destination. **Статус футера** — худший по строкам, но дополнительно эскалируется долей `Out of scope` в полном спенде скоупа: ≥10 % → `noisy`, ≥50 % → `partial`. Поэтому значок на итоге при полностью чистых строках — не поломка аллокации, а «часть спенда Meta не привязалась к скоупу запроса». См. [mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md).
- **Destination-аппроксимация (экстраполяция spend на funnel-разрезы)** `[AIO, аллокация Meta-spend]` — на разрезах по funnel-уровню (лэнд, тип лэнда, роль `LP: <Тип>`, Destination, Advertiser/оффер, тип оффера) `Meta Spend` считается по доле визитов, **дошедших** до этого шага, а не по всем визитам объявы (иначе spend «утёк» бы в скрытую Empty-строку не дошедших). По сути экстраполяция: «не дошедшие распределились бы как дошедшие». Следствия: spend на оффере/лэнде может быть **больше**, чем «дошедшие визиты × цена»; шаткая экстраполяция → `status = noisy`; один Destination, шаренный между кампаниями, получает **полный credit от каждой** (суммы складываются). См. [mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md).
- **Custom Key / Custom Value (FB CAPI трекер)** `[AIO]` — пара полей в настройках FB CAPI трекера для отправки кастомного события в FB pixel (custom event, созданное руками в пикселе).
- **short-keys (зашифрованная часть ссылки)** `[AIO]` — параметры, шифруемые внутрь URL (encrypted-формат). Шифровать можно **только** параметры, полностью известные на момент генерации ссылки. Параметры от третьей системы (FB `{{ad.id}}`) — нельзя, иначе они не будут заменены.

### Автоправила Meta (раздел Automations)

- **`Automations` / Автоматизации** `[AIO, раздел]` — раздел `/app/automations` (в меню — `Automations`, RU `Автоматизации`) с автоправилами над Meta-сущностями: движок сам считает метрики кампании, адсета или объявления и делает то же, что руками делают экшены `Start` / `Stop` / `Change budget`. Четыре страницы: `Status` (обзор ассайнов и быстрая проверка вердиктов), `Assignments` (на какие сущности повешены шаблоны), `Rule Templates` (сами шаблоны правил), `History` (журнал вердиктов и очередь подтверждений). Права — своя ветка `automation.*`: доступ к Meta или к дистрибуциям её не даёт ([models/permissions-model.md](../models/permissions-model.md)). Только ERP. Настройка — [how-to/auto-rules.md](../how-to/auto-rules.md), что происходит между прогонами — [mechanics/auto-rules-engine.md](../mechanics/auto-rules-engine.md). (разг.: «автоправила», «автостоп», «правила по мете»)
- **`Rule Template` / шаблон автоправил** `[AIO, Automations]` — шаблон, по которому движок выносит вердикт сущности Meta. Технически это дистрибуция типа `Auto Rules`, но собирают и правят её в `Automations → Rule Templates` под правом `automation.templates.edit`. В шапке — ось фаз (`Phase axis`) и переменные, в дереве — только `Phase` в корне и `Auto Rule` листом внутри фазы. Разбор — [how-to/auto-rules.md](../how-to/auto-rules.md).
- **Вердикт автоправила (`Action`)** `[AIO, Automations]` — что правило постановляет сделать с сущностью Meta; шесть значений: `stop`, `start`, `keep`, `wait`, `change_budget`, `duplicate`. Как каждое подписано в интерфейсе и что у него настраивается — [how-to/auto-rules.md](../how-to/auto-rules.md); какие вердикты доезжают до Meta и почему подтверждение человека решает режим ассайна, а не отдельное правило — [mechanics/auto-rules-engine.md](../mechanics/auto-rules-engine.md).
- **Статус действия в журнале автоправил** `[AIO, Automations]` — в каком состоянии действие по вердикту; восемь значений: `observed`, `pending`, `approved`, `declined`, `executed`, `failed`, `expired`, `superseded`. Что означает каждый статус, какие из них ещё не финальные и какими цепочками идут переходы — [mechanics/auto-rules-engine.md](../mechanics/auto-rules-engine.md).

## Источники, трекеры и дистрибуции AIO

- **Distribution / Дистрибуция** `[AIO]` — централизованное дерево правил, автоматически распределяющее значения по визиту. Управляется в `Settings → Distributions`. Деревья состоят из **Folder + Strategy + Rule to pass + Payload-нод**. Strategy внутри Folder: First / Weights / Conversions AI / Metrics AI. Правила применяются сверху вниз. Исключение — тип `Auto Rules`: он работает над Meta-сущностями, а не над визитом, дерево у него собрано из других нод, а его дом — раздел `Automations` ([how-to/auto-rules.md](../how-to/auto-rules.md)).

  9 типов дистрибуций: **Payout** (payout по правилам) · **Revenue** (revenue по правилам) · **Campaign Content** (значения для одного шага кампании) · **Flow Content** (значения для нескольких шагов одного флоу) · **Fill Field** (заполняет поле визита, шаг `Fields by Distribution`) · **Direct Traffic** (голые ссылки без UTM, альтернатива `Default Query` на домене) · **Remarketing Content** (push-сценарии, которые собирают во флоу вручную — кастомный путь) · **Message Templates** (плитка выбора — `Message templates`; дерево нод-шаблонов сообщений для рассылок ремаркетинга) · **Auto Rules** (шаблон автоправил над Meta-сущностями; свой дом — `Automations → Rule Templates`, плитка `Auto rules` есть и в пикере `Settings → Distributions`).

  Что каждый тип делает, какие ноды и стратегии ему доступны — [models/distributions-model.md](../models/distributions-model.md).

- **Distribution Nodes** `[AIO]` — типы нод внутри distribution-дерева (доступность зависит от типа дистрибуции):
  - **Add Folder** — контейнер для правил.
  - **Add Strategy** — стратегия выбора внутри Folder (First / Weights / Conversions AI / Metrics AI).
  - **Add Destination** — нода дестинейшна.
  - **Add Landing** — нода лэнда.
  - **Add Redirect** — URL-редирект.
  - **Add Reflect** — reflect-ссылка.
  - **Add Query** — default query (привязать source+campaign к домену).
  - **Add Push Message** — ссылка на готовую запись-шаблон из `Marketing → Message templates`.
  - **Add Revenue** — revenue-значение.
  - **Add Payout** — payout-значение.
  - **Add Fill Field** — заполнение поля визита (с подтипами `Text / Image / Landing / Library / Destination`).
  - **`Email Template` / `Push Template` / `Sms Template` / `Telegram Template`** — четыре листа-шаблона, которые бывают **только** в деревьях типа `Message Templates` (в диалогах UI подписаны `Email template` / `Push template` / `SMS template` / `Telegram template`); текст сообщения лежит в самой ноде, а не ссылкой на запись из `Marketing → Message templates`. Из такого дерева сегодня реально отправляется только push-ветка — разбор в [models/distributions-model.md](../models/distributions-model.md).

  [models/distributions-model.md](../models/distributions-model.md).

- **`Phase` / `Auto Rule` (ноды дерева `Auto Rules`)** `[AIO]` — две ноды, которые бывают **только** в дистрибуции типа `Auto Rules`: `Phase` — фаза, разрешена в корне дерева; `Auto Rule` (в дереве подписана `Auto rule`) — правило-лист внутри фазы. Форма такого дерева, ограничения размещения и дословные тексты ошибок — [models/distributions-model.md](../models/distributions-model.md); что задаётся в фазе и в правиле — [how-to/auto-rules.md](../how-to/auto-rules.md).

- **Distribution Tree — управление** `[AIO]` — управляющие элементы дерева ([models/distributions-model.md](../models/distributions-model.md)):
  - **Rule to pass** — условие, при котором нода применяется.
  - **Toggle activity** — вкл/выкл ноду.
  - **Show children** — раскрыть/свернуть ноду.
  - **Toggle locked** — заблокировать (нельзя disable, пока заблочена).
  - **Move Up / Move down** — переставить порядок.
  - **Clear recursively** — очистить со всеми вложенными (требует disabled).
  - **Duplicate recursively** — дублировать со всеми вложенными.

- **Глобальная (системная) дистрибуция** `[AIO]` — дистрибуция без тенанта-владельца, одна и та же для всех тенантов; заводит её команда AIO. В списках `Settings → Distributions` и `Marketing → Template distributions` её нет — она появляется только в селектах выбора дистрибуции (тумблер `Show global only`). Из тенанта — только чтение: правка отбивается сообщением `System distribution is read-only`. Разбор — [models/distributions-model.md](../models/distributions-model.md).

- **Business Model** `[AIO]` — преднастроенный набор бизнес-правил, на котором строятся Payout и Revenue distributions. По дефолту тенант имеет `Arrived Revenue$` (revenue из постбэков). Создаются в Settings, нужны при настройке Payout/Revenue distribution-ов. [models/business-model.md](../models/business-model.md).

- **Buyer UTM Distribution** `[AIO]` — типовая `Fill Field` дистрибуция, которая по правилам (обычно `Campaign Owner UUID = <конкретный байер>`) автоматически записывает UTM-метку баера в поле визита `buyer_utm` через шаг `Fill Field` во флоу. Единственная `Fill Field`-дистрибуция в шаблоне тенанта; заполнение других полей (`aff_id`/Offer ID, API-токены) — кастомные дистрибуции, которые заводятся самостоятельно. [models/distributions-model.md](../models/distributions-model.md).
- **Campaign Content Distribution** `[AIO]` — централизованная дистрибуция, сопоставляющая каждому домену конкретный лэнд/вайт через правило на домен. «Вайт-дистрибуция» в схеме Dynamic White.
- **Dynamic White** `[AIO, методология]` — **подход** к централизованной маршрутизации вайт-страниц без выбора на уровне кампании (не тип вайта и не вариант Reflect). Отдельная `Campaign Content Distribution` маршрутизирует домены → специфичным вайтам, а шаг `White` во Flow переводится в режим `Flow Only`. Вайт-страница выбирается централизованно по правилам (домен, гео, путь), а не при создании кампании. Отличается от `Proxy-reflector / Reflect` (это тип payload для проксирования стороннего контента). См. [models/distributions-model.md](../models/distributions-model.md) → Direct Traffic Distribution, [how-to/distributions.md](../how-to/distributions.md) → Dynamic White (шаг White становится Flow-only).
- **Direct Traffic Distribution** `[AIO]` — тип Distribution для директивной маршрутизации трафика по домену+path: вход — голый домен (без UTM), выход — кампания и payload (лэнд, reflect, redirect). В дереве используется slash-path как ключ маршрутизации. [models/distributions-model.md](../models/distributions-model.md).
- **Fill Field Distribution** `[AIO]` — тип Distribution (`Settings → Distributions → +Distribution → Fill Field`) — централизованное дерево правил, как заполнить поля визита (см. список в `Distribution / Дистрибуция` выше, тип 5). Применяется через шаг `Fill Fields by Distribution` во флоу. **Не путать** с шагом `Fill Fields` (это шаг во флоу — применение результата дистрибуции) и с `Fill Field-нодой` (нода **внутри** дерева).
- **Select Strategy: Single Node / Multiple Nodes** `[AIO]` — настройка дистрибуции — режим записи payload-ноды. `Single Node` — заполняется только одна подходящая нода; `Multiple Nodes` — все найденные по дереву правил.
- **Multiple Strategy (Fill Field Distribution)** `[AIO]` — стратегия `Fill Field Distribution`, отличная от `First` / `Weights` / AI-стратегий. Идёт по каждому Fill Field-полю сверху вниз и применяет **все** подходящие правила (не выбирает один payload). **Не перезаписывает** уже заполненные поля — поэтому дефолтную папку ставят в самый низ дерева.
- **Offer-Name Distribution** `[AIO]` — Distribution для ротации офферов/брендов. Folder Strategy (`First` / `Weights` / `ML`) на уровне дерева. «Умной» ротации по конверсиям за последние N часов нет — только ML за всё время.
- **Offer Distribution** `[AIO]` — дистрибуция, централизованно распределяющая, какой оффер выбрать (вместо ручного выбора байером в кампании). После настройки у байера в кампании пропадает место выбора оффера — всё решает Offer Distribution по правилам (`Country Code` + `Campaign Owner` и т.п.). Родственно `Offer-Name Distribution`.
- **Push Distribution (применение Remarketing Content)** `[AIO]` — применение `Remarketing Content` distribution для пушей — дерево папок → подпапки по `country_code` → стратегия (`First` / `Weights` / `Conversions AI` / `Metrics AI`) на множестве Push Template-ов. [models/distributions-model.md](../models/distributions-model.md). Схема рассылки — [mechanics/notifications-flow.md](../mechanics/notifications-flow.md). Это **кастомный путь**: дефолтная рассылка собирается ремаркетинг-кампанией и берёт тексты из дистрибуции `Message Templates` ([how-to/remarketing-campaigns.md](../how-to/remarketing-campaigns.md)).
- **Arrived Revenue$ (Business Model)** `[AIO]` — дефолтная Business Model тенанта (на ней работает дефолтный Revenue Distribution). Берёт значение из поля `arrived_revenue` постбэка, конвертирует в USD по текущему курсу, пишет в поле конверсии `Revenue`. Момент фиксации курса — момент прихода постбэка. Конвертация — по курсам открытого внешнего источника (кэшируются, тот же источник использует превью в Postback generator). [models/business-model.md](../models/business-model.md).
- **Zero Payout (Business Model)** `[AIO]` — дефолтная Business Model, всегда возвращающая `Payout = 0`. Fallback «ничего не платим». [models/business-model.md](../models/business-model.md).
- **Third Party PWA Link Generator** `[AIO, Source]` — отдельный Source, генерирующий универсальные ссылки для подстановки внутрь PWA-шек сторонних сервисов. Ссылки **без идентификаторов кампании/юзера** — их цель только вернуть визит в AIO в тот же флоу. См. [mechanics/pwa.md](../mechanics/pwa.md).
- **Tracker → Trackers (вкладка)** `[AIO]` — место в UI, где заводятся постбэки и event-уведомления из AIO в сторонние системы (FB CAPI, Snapchat, TikTok, постбэки в партнёрки). По дефолту заведены только CAPI-постбэки.
- **Google Conversions CSV / External Report** `[AIO]` — тип `External Report` под загрузку конверсий в Google. Возвращает CSV на URL-запрос; Google сам ходит по URL и тащит конверсии.
- **Google Account ID / Conversion ID / Conversion Label** `[AIO, Google]` — параметры под Google-сетап. **Основной путь**: указываются при генерации трекинговой ссылки в `Link Generator` (поля рядом друг с другом — Account ID, Conversion ID, Conversion Label), вписываются прямо в URL и пишутся в визит автоматически. Google **не передаёт `Account ID`** в URL сам — AIO протаскивает его явно. **Альтернатива** (если ссылка уже разлита или айди не известен на момент генерации): маппинг `domain → Account ID` через `Fill Field` ноды во флоу. `Conversion ID` — идентификатор тэга. `Conversion Label` — ярлык конверсии. Основной путь — запись в ссылку при генерации.
- **campaign_country_code vs visit_country_code (мульти-гео)** `[AIO]` — `campaign_country_code` — country_code на уровне кампании; при мульти-гео содержит несколько кодов, но в правилах дистрибуции (Equal-оператор) сравнивается **только с первым** — поэтому для мульти-гео непригоден. `visit_country_code` — country_code конкретного визита, всегда одна страна — корректное поле для правил при мульти-гео. **Мульти-гео кампания** — кампания с несколькими country_code (DACH = DE+AT+CH); редкий нестандартный кейс.
- **Contains / Starts With / Ends With (операторы правил)** `[AIO]` — новые операторы сравнения для кастомных правил (Allowance Rules / Rule to pass).

## Marketing и Push-уведомления AIO

- **Remarketing Campaign / Ремаркетинг-кампания** `[AIO, Marketing]` — кампания, которая не принимает трафик, а рассылает сообщения по аудитории уже собранных визитов. **Дефолтный и основной способ рассылки пушей в AIO.** Отдельный тип кампании (`Notifications` против `Campaigns` у трафиковой), живёт в `Marketing → Campaigns` и обязана указывать на флоу типа `Notifications` — иначе форма не сохраняется (`Remarketing campaign requires a Notifications flow`). Права отдельные, `marketing.campaigns.*`: доступ к трафиковым кампаниям их не даёт. Только ERP. Процедура целиком — [how-to/remarketing-campaigns.md](../how-to/remarketing-campaigns.md). (разг.: «ремаркетинг-кампания», «рассылка», «пуш-кампания»)
- **`Launch trigger` (`Manual` / `Schedule` / `Conversion`)** `[AIO, ремаркетинг-кампания]` — блок формы кампании, задающий, чем запускается рассылка; в таблице кампаний тот же выбор виден колонкой `Trigger`. `Schedule` — по расписанию: у одной кампании их может быть несколько (кнопка `Add schedule`, потолок 50), время считается в UTC, по умолчанию не чаще раза в 30 минут. `Conversion` — по приходу конверсии выбранного типа (поле `Conversion type`); в фильтре таблицы тот же тип подписан `Conversion Trigger`. **`Manual` выбран в форме по умолчанию и не запускает ничего** — кнопки ручного запуска в продукте нет, поэтому кампания «из коробки» молча не отправляет ни одного сообщения. Разбор — [how-to/remarketing-campaigns.md](../how-to/remarketing-campaigns.md).
- **Аудитория ремаркетинг-кампании (`Audience`)** `[AIO, ремаркетинг]` — визиты, по которым кампания шлёт сообщения. Визит попадает в неё, когда проходит сущность трафика с привязкой к этой кампании; **гейта по подписке на push нет** — собирается любой нетрэшевый визит. Колонка `Audience` в таблице кампаний показывает пару чисел `In audience` / `Removed`; причин выбытия ровно две — `stop_conversion` (сработала стоп-конверсия) и `dead_endpoint` (push-подписка мертва). Колонка визита `RMK Audience` — **история попадания, а не текущий состав**: список кампаний на визите только пополняется. Как набирается — [how-to/remarketing-campaigns.md](../how-to/remarketing-campaigns.md).
- **`Drip schedule` / серия рассылок** `[AIO, узел флоу Notifications]` — узел, который держит всю серию отправок внутри себя: шаги со смещением от момента входа визита в узел. Смещение выбирается из фиксированного набора (`Now`, 15 минут, 1 / 3 / 5 / 12 часов, 1–5 суток), каждое значение используется один раз. Два режима наполнения: `Simple` — одна дистрибуция шаблонов на всё расписание, `Advanced` — своя на каждый шаг. Из выбранного дерева серия отправляет **только push**. В интерфейсе тип узла подписан именно `Drip schedule`; `Plan Drip` — внутреннее имя того же типа (встречается в английских подсказках). Механика — [mechanics/notifications-flow.md](../mechanics/notifications-flow.md). (разг.: «дрип», «серия», «follow-up пуши»)
- **`Stop conversion` / стоп-конверсия** `[AIO, поле узла Drip schedule]` — тип конверсии, приход которой означает «цель серии достигнута»: визит перестаёт получать шаги и **выводится из аудитории** кампании с причиной `stop_conversion`. Задаётся в форме узла `Drip schedule` во флоу, а не в форме кампании. Рядом лежит `Required conversions` — обратный гейт: шаг уходит, только если у визита есть конверсии всех выбранных типов, иначе серия завершается, но визит остаётся в аудитории. [how-to/remarketing-campaigns.md](../how-to/remarketing-campaigns.md).
- **`Template distributions` / дистрибуция шаблонов (`Message Templates`)** `[AIO, Marketing]` — раздел `Marketing → Template distributions` и одноимённый тип дистрибуции: дерево нод-шаблонов, откуда серия рассылок берёт текст сообщения. Листья — `Email Template` / `Push Template` / `Sms Template` / `Telegram Template`, и текст лежит **прямо в ноде**, а не ссылкой на запись из `Marketing → Message templates`. Подходящий лист выбирается на каждую отправку **равновероятно** среди прошедших свои правила; веса в этом дереве не работают. Если в дереве смешаны push- и не-push листья, не-push отбрасываются молча — серия шлёт только push-ветку. Разбор — [models/distributions-model.md](../models/distributions-model.md).
- **`Push Template`** `[AIO, Marketing]` — имя носят две разные вещи. (1) **Лист дерева `Message Templates`** — нода, в которой лежит сам текст: имя строки в дереве плюс поля `Push title`, `Push message`, `Push icon`. Отсюда берёт контент серия рассылок ремаркетинг-кампании. (2) **Запись в `Marketing → Message templates`** — отдельная сущность с теми же полями, на неё ссылаются ноды `Push Message` пуш-сценариев, которые собирают во флоу вручную. Каналы: из дерева `Message Templates` уходит только push, Telegram отправляется отдельным узлом флоу, а email и SMS не отправляются вообще — и отказывают **молча**, без ошибки и без следа в аналитике ([mechanics/notifications-flow.md](../mechanics/notifications-flow.md)).
- **Спинтакс в текстах рассылок (`{вариант 1|вариант 2}`, `{Random=(100,1500)}`)** `[AIO, Marketing]` — синтаксис случайного выбора прямо в тексте сообщения: на каждую отправку из фигурных скобок берётся один вариант, `{Random=(min,max)}` даёт случайное целое. Действует в push- и telegram-сообщениях Marketing — и в серии рассылок ремаркетинг-кампании, и в ноде `Push` флоу нотификаций; вне рассылок этот синтаксис не работает. Разбор синтаксиса — [reference/placeholders.md](placeholders.md), где задаётся сам текст — [mechanics/notifications-flow.md](../mechanics/notifications-flow.md).
- **`Notification Flow`** (синоним — `Marketing Flow`) `[AIO, Marketing]` — флоу типа `Notifications`: отвечает за «что и по какому расписанию» отправить, а «кому и когда» задаёт ремаркетинг-кампания, которая на него указывает. Заводится в `Marketing → Flows`, исполняется параллельно маршруту визита. В новой модели такой флоу вырождается в один узел: `Start` → `Drip schedule`, вся серия живёт внутри узла. Остальные узлы (`Push`, `Telegram`, `Wait`, `Check`, `Check conversion`, `Repeat`) остаются для сценариев, которые собирают вручную. Палитра узлов и транзишны — [mechanics/notifications-flow.md](../mechanics/notifications-flow.md), сборка кампании — [how-to/remarketing-campaigns.md](../how-to/remarketing-campaigns.md).
- **`Notifications flow` (нода в Campaign Flow)** `[AIO, кастомный путь]` — нода трафикового Campaign Flow, подключающая к воронке заранее созданный флоу типа `Notifications`. Из редактора нода не убрана и работает, но **новые рассылки так не собирают** — штатный путь это ремаркетинг-кампания ([how-to/remarketing-campaigns.md](../how-to/remarketing-campaigns.md)). Разбор — [mechanics/notifications-flow.md](../mechanics/notifications-flow.md).
- **Remarketing Distribution / `Remarketing Content`** `[AIO]` — тип дистрибуции для пуш-сценариев, которые собирают во флоу вручную: дерево `Folder` + `Strategy` (`First` / `Weights` / `Conversions AI` / `Metrics AI`) + ноды `Push Message` / `Telegram Message`, каждая ссылается на готовую запись из `Marketing → Message templates`. Создаётся в `Settings → Distributions`, применяется нодой `Push`. Это **кастомный путь**: дефолтная рассылка берёт тексты из дистрибуции `Message Templates` (см. `Template distributions`). [models/distributions-model.md](../models/distributions-model.md).
- **Push Subscribe Toggle** `[AIO, поле кампании]` — переключатель `Enabled / Disabled` на уровне кампании, включающий/выключающий **Push Subscribe Script** на лэнде.
- **Push Subscribe Script** `[AIO, скрипт]` — JS-скрипт, который на лэндах предлагает визиту подписаться на push-уведомления браузера. Включается/выключается через `Push Subscribe Toggle` на уровне кампании. После подписки факт фиксируется как конверсия типа `Push Subscribe`.
- **AIO Push Subscribe (макрос)** `[AIO]` — JS-макрос, выводящий браузерный prompt подписки на push. Управление вызовом (по клику / автоматически) — правкой JS внутри макроса.
- **Manual / Scheduled / Follow Up пуши** `[AIO, разговорная классификация]` — как в разговоре называют варианты рассылки. Все они сегодня собираются одной сущностью — ремаркетинг-кампанией: `Scheduled` = триггер `Schedule` (запуск по расписанию), `Follow Up` = шаги серии в узле `Drip schedule`, а `Manual` (запуск руками по кнопке) **не реализован** — одноимённый триггер стоит в форме по умолчанию и не запускает ничего. [how-to/remarketing-campaigns.md](../how-to/remarketing-campaigns.md).
- **Telegram-уведомления: Telegram (нода) / Sender Provider / Buyer TG Chat ID** `[AIO]` — стек отправки TG-сообщений из AIO. `Telegram` — нода-канал в Marketing Flow, отправляет сообщение в TG (нужен sender-провайдер, контакт, шаблон). `Sender Provider` (тип `Telegram`) — настраивается через API-ключ бота + имя бота; **используется и для рассылок, и для `Telegram Destination`**. Для acquisition-флоу Destination в провайдере задаются `Start`/`Joined Message`, приглашение в канал (`Join Channel` + header/button text), типы конверсий на старт/вступление и поля визита под `chat_id`/`username` (полная таблица — [how-to/push-notifications.md](../how-to/push-notifications.md); настройка Destination — [how-to/destinations.md](../how-to/destinations.md)). `Messages` — раздел с логами отправки. `Buyer TG Chat ID` — кастомное поле визита под TG chat_id владельца кампании; **имя — пример, по дефолту в шаблонах тенантов такого поля нет, заводится вручную**; заполняется через `Fill Fields` по правилу `Campaign Owner`. `Notification Flow` — Marketing Flow, запускается на каждую конверсию выбранного типа. См. [mechanics/notifications-flow.md](../mechanics/notifications-flow.md).
- **Telegram Destination / Behaviour (Bot -> Channel / Channel)** `[AIO]` — тип Destination, заводящий трафик в TG-бот/канал (целевое действие — подписка на канал, не форм-сабмит). Требует Sender Provider типа `Telegram` + `Behaviour`: `Bot -> Channel` (визит → бот с приветствием → приглашение вступить в канал) или `Channel` (редирект сразу в канал). Бот должен быть **админом канала**, иначе Telegram не отдаёт ему событие вступления и конверсия подписки не фиксируется. См. [how-to/destinations.md](../how-to/destinations.md).
- **PWA — определение (lander + manifest + Service Worker)** `[AIO]` — PWA-шка = обычный лэнд, у которого в `<head>` есть manifest для Chrome + Service Worker. Один и тот же Service Worker обрабатывает install и push. См. [mechanics/pwa.md](../mechanics/pwa.md). *(Слэнг: `PWA-шка`, `ПВАшка`, `пвашка` — все допустимы в разговорном тексте.)*
- **Create PWA / PWA Builder** `[AIO, экшен]` — создание PWA-шки живёт в отдельном разделе `Content → PWA` (своя страница рядом с `Content → Landings`): кнопка `+ PWA` (экшен `Create PWA`) сразу открывает встроенный PWA Builder. Правка уже созданной — экшен `Manage PWA` в её строке (у обычных лэндов — `Manage landing`). В списке `Content → Landings` PWA не видны: он жёстко ограничен лэндами режима `Editor`, а карточки `Create a PWA` в диалоге добавления лэнда больше нет. [how-to/pwa.md](../how-to/pwa.md).
- **PWA-макрос (превращение лэнда в PWA)** `[AIO]` — макрос в `Content → Macros`, превращающий лэнд в PWA. В настройках указывается ID кнопки-Install и div-элементы. Под капотом — manifest + Service Worker.
- **AIO внутренние PWA vs 3rd party PWA** `[AIO]` — `AIO внутренние PWA` — создаются и хостятся в самом тенанте; фичи поверх: Content Splits на любом элементе, запись сессий.
- **AIO Visit Session (Sub 1)** `[AIO]` — уникальный идентификатор визита, параметр, который AIO передаёт в PWA (в один из доступных сабов). Нужен, чтобы при возврате из PWA-сервиса визит «продолжился» в той же сессии.
- **Reverse Integration / PHP-интеграция** `[AIO]` — паттерн для внешних страниц, которые лежат вне AIO (например, на WordPress). Ставится либо WP-плагином, либо чистым PHP-скриптом на самой странице.
- **Monitoring User (как chat ID)** `[AIO]` — в поле Monitoring User юзера можно прописать **ID чата** (не личного юзера) — тогда уведомления `AIO-tech-bot` идут в общий чат. Делается через запрос к саппорту AIO.
- **Item List** `[AIO]` — листы для большого количества данных разного формата (IP / Phone). Создаются в `Settings → Item Lists`. Для использования в Condition-шагах / правилах.
- **Settings → Fields (+AddField) + slug поля** `[AIO]` — раздел AIO, где создаются кастомные поля визита (под маппинг ответов Traffic Filters, кастомные данные). `slug` поля автогенерируется из названия; используется для подстановки в Traffic Filter (`Visit Field Slug`).
- **User fields (секция в форме)** `[AIO]` — секция `User fields` (RU `Пользовательские поля`) в карточках настроечных сущностей: `Source`, `Campaign`, лендинг, `Destination`, а также их «родители» `Flow`, `Lander Type`, `Advertiser`. Поле добавляется в форму точечно кнопкой `Add field` (пул доступных полей определяется атрибутом `Type` поля), значение доезжает до визита, когда визит проходит через эту сущность, — писать для этого `window.aioBus.push` на лэнде не нужно. У родительских сущностей поле раздаётся дочерним в одном из трёх режимов (`Flow only` / `Campaign template` / `Campaign only` — и аналогичные пары у `Advertiser` и `Lander Type`). Разбор — [how-to/user-fields.md](../how-to/user-fields.md); само поле сначала заводится в `Settings → Fields` ([how-to/custom-fields.md](../how-to/custom-fields.md)).
- **Campaign field (`Type = Campaign`)** `[AIO]` — не отдельная сущность, а **поле визита**, у которого дефолт значения берётся не из ссылки, а из карточки кампании (задаётся один раз на кампанию, копируется на каждый её визит при заходе — напр. FB Pixel/CAPI Token, чтобы не светить в URL). Значение живёт на визите и может быть перезаписано для отдельного визита (в т.ч. целью шага `Fill Fields`) — это **не** одно общее неизменяемое значение на всю кампанию. Атрибут `Type` (Visit/Campaign) — источник дефолта, не место хранения. Концепт — [models/visit-field.md](../models/visit-field.md); создание — [how-to/custom-fields.md](../how-to/custom-fields.md).
- **Атрибуты поля (Settings → Fields)** `[AIO]` — boolean-флаги поля визита/конверсии:
  - **Is Visible** — поле видно в колонках по дефолту.
  - **Is Registry** — поле хранит **секвенцию значений** (история всех записей `1,2,3...`); выключено — каждый постбэк перезаписывает.
  - **Is Macro Visible** — доступность поля через объект `aio` на лендинге (JS-доступ в рантайме, **не плейсхолдеры**).
  - **2FA Protected** — значение скрыто в UI, нужен 2FA-код (`Unsecured Mode`).
  - **Is Used For Cost** — поле доступно для ручного апдейта костов на кампании (агрегация костов по визитам с одинаковым значением).

  Полное описание атрибутов — [how-to/custom-fields.md](../how-to/custom-fields.md).
- **Availability as Grouper** `[AIO, атрибут поля]` — настройка в `Settings → Fields` на поле визита — разрешает использовать его как `Grouper` в аналитике (Drilldowns / Roll Up Report). Включается отдельно для каждого поля.
- **Available Values (в Edit Field)** `[AIO]` — поле в Edit Field, превращающее поле (напр. Geo Code) в select-из-вариантов на уровне кампании. Задаётся как JSON: `"test": "test", "123": "321"`.
- **Data Source / Trigger (устаревшее поле)** `[AIO, deprecated]` — поле в форме создания поля визита/конверсии — значения не имеет, будет убрано. [how-to/custom-fields.md](../how-to/custom-fields.md).
- **Offer Name For Advertiser** `[AIO]` — поле внутри Content Item оффер-нейма, уходящее во внешние системы. Существует параллельно с `Offer Name For Visitor`.
- **PWA State / Offer State (поля визита)** `[AIO]` — поля визита, в которые автоматически пишется выбранный вариант на шаге флоу (`PWA State` — для шага PWA, `Offer State` — для шага оффера). Для аналитики «какая PWA/оффер показались». Формат — `variant`.
- **Linked Field / Link to Field** `[AIO]` — механика на уровне Flow для записи в поле визита: когда вариант выбран на `Content`/`Destination`-шаге, **UUID этого payload** пишется в указанное поле визита (поле формата `Variant`). Используется для аналитики «какой вариант показался». Механика только на **запись**, и запись происходит **только в момент выбора варианта на шаге**. Лежит в основе `PWA State` / `Offer State` — в гемблинг-сетапах для шага PWA и оффера пишут выбранный payload в эти поля.
- **Advertiser / Advertisers** `[AIO, сущность]` — сущность в `Settings` (шестерёнка → Advertisers), хранящая неизменяемый «хвостик» параметров (UUID, сабы, UTM-метки), общий для всех Destination-ов одной партнёрки/PWA-сервиса. Концептуальный аналог `Network` / `Affnetworks` в классических трекерах. Иерархия: **Advertiser Type → Advertiser → Destination**. (разг. про партнёрку: «ПП»)
- **Advertiser Type (иерархия)** `[AIO]` — уровень над `Advertiser`. Полная иерархия: **Advertiser Type → Advertiser → Destination**. Дефолтные типы: `default`, `Offer`, `PWA`.
- **`Advertiser type` (атрибут Content node)** `[AIO]` — фильтр, схлопывающий варианты payload на `Content`-шаге: ограничивает выбор Destination так же, как он работает на шаге `Destination`. Позволяет быстро выбрать только Destination нужного типа, не прокручивая полный список.
- **`Form fallback`** `[AIO, атрибут Content node]` — резервный путь выбора формы (deprecated). Используется на `Content`-шаге, если во Flow нет отдельного шага `Fill form` (или `Choose form`), но нужна конкретная форма из `Settings → Forms`. При отсутствии и `Fill form`, и `Form fallback` грузится дефолтная форма из SDK-конфига. Очень старая механика; вместо неё рекомендуется явный шаг `Fill form` во Flow.
- **Методы создания Destination: By Advertiser / By Integration** `[AIO]` — **два основных метода**: `By Advertiser` (рекомендуется) и `By Integration`. В модалке `+Destination` они разворачиваются в **4 варианта**:
  - `By Advertiser` (рекомендуется) — назначается Advertiser, его хвостик параметров подставляется автоматически.
  - `Simple Redirect` — голый редирект-URL, создаётся **без выбора Advertiser** (Advertiser не назначается, поэтому нет аналитики по Advertiser / `Offer Visits`). **Не штатный путь для офферов** — штатно оффер идёт через `By Advertiser` (ссылка) или `By Integration` (API); `Simple Redirect` под узкие случаи (быстрый редирект в TG-бота, разовый URL). Процедура — [how-to/destinations.md](../how-to/destinations.md).
  - `Telegram Destination` — специализированный вариант `By Integration` с типом интеграции Telegram.
  - `By Integration` — raw-интеграция через готовый API-шаблон (Bridge / IREV и др.).
  - **Не путать** `Simple Redirect` с `Direct Traffic` (это **другая** сущность — тип Distribution для голых ссылок без UTM, см. соответствующую запись).
- **Cap / Caps (на Destination)** `[AIO]` — лимит на уровне Destination. Капа одна — `Conversion Cap`: считает конверсии одного выбранного `Conversion Type`, и когда счётчик дошёл до лимита, пуш лида больше не уходит, визит идёт в fallback по переходу `Destination Full`. Настраивается экшеном `Edit conversion cap` (в диалоге — `Cap type`, `Limit`, `Current usage`, кнопка `Reset counter`). **Три типа (`Cap Type`):** `Infinity` (в диалоге подписан `Unlimited` — лимита нет, дефолт), `Daily` (счётчик обнуляется вскоре после **0:00 UTC**, не по локальной полуночи), `Lifetime` (счётчик не обнуляется никогда). Механика — [models/destination.md](../models/destination.md), настройка и симптомы — [how-to/destinations.md](../how-to/destinations.md).
- **`Lifetime` (тип капы Destination)** `[AIO]` — `Cap Type`, у которого счётчик не сбрасывается по расписанию: он копится всё время жизни дестинейшена, пока лимит не поднимут или счётчик не обнулят вручную (`Reset counter` в диалоге капы, экшен `Reset cap`). Подсказка в интерфейсе — `The counter never resets — the limit applies to the whole lifetime.`; в колонке таблицы такая капа подписана `Lifetime cap`. Переполненная `Lifetime`-капа гейтит выдачу дестинейшена ровно так же, как `Daily`, — разница только в сбросе. [models/destination.md](../models/destination.md).
- **Destination Full (транзишн)** `[AIO]` — transition шага Destination во флоу — срабатывает, когда у Destination переполнена капа. Визиты уходят в fallback.
- **Offer Visits (метрика)** `[AIO]` — метрика — визиты, попавшие в Destination с типом «оффер» (через `By Advertiser`, не Simple Redirect).
- **Proxy String** `[AIO]` — поле проксика в интеграции (`user:pass@ip:port`). Пускает исходящие запросы AIO по этой интеграции через один прокси; **назначение зависит от интеграции:** в `Destination`/брокере — показать получателю лида **один статический** исходящий IP (альтернатива whitelisting'у IP-пула AIO); в `Domain Provider` (напр. Namecheap) — API-запросы AIO к регистратору идут с IP прокси, который надо добавить в вайтлист регистратора ([how-to/domains.md](../how-to/domains.md)); у части `Traffic Filter`-ов (напр. Emailable) — обязательная API proxy-строка. Поле есть **не во всех** интеграциях — показывается по выбранному `Integration Type`.

## Метрики и аналитика AIO

- **Cohorts Report / Когорты** `[AIO, аналитика]` — отчёт эволюции метрики во времени (когорты по `day` / `week` / `month`). Три селектора: **`Size`** (размерная метрика когорты, напр. `Visits`), **`Target`** (целевая метрика — только событийные, список фильтрует бэк), **`Unit`** (day / week / month). Режимы отображения: значение ячейки `Rate` / `Value`, цветовая схема `Single` / `Gradient` / `Positive`, база нормализации `By row` / `Total`, тумблер `Skip +0` (исключить день +0 из нормализации цвета). Слева — сворачиваемый сайдбар metric-фильтров. Помогает увидеть реальный LTV, эффективность ремаркетинга, поздние конверсии. Полные контролы — [how-to/analytics.md](../how-to/analytics.md).
- **Compare Analytics / Сравнительная аналитика** `[AIO, аналитика]` — сравнение двух периодов side-by-side: **`First time range`** vs **`Second time range`** (свой date range у каждого), `Groupers` (Device, Location, OS, Browser, FB-fields и т.д.), `Metrics`, `Conditions` (фильтры). Поддерживает сохранение в Preset. **Структура одного `Condition`**: выбираешь `Field`, оператор `Contained in` (`Yes` / `No`) и значение `Value`; несколько условий комбинируются кнопками `And` / `Or` (кнопка добавления — `Add condition`).
- **Roll Up Report** `[AIO, аналитика]` — агрегированный отчёт по выбранным групёрам (Groupers). Группировка по нескольким уровням (например, `Destination → Campaign Owner`, `Advertiser → Destination`). Фильтры слева. Часто используется для анализа buyer-performance, оптимизации связки Advertiser+Destination, разбора по любым FB-параметрам. [how-to/analytics.md](../how-to/analytics.md).
- **BI Builder (Analytics)** `[AIO]` — конструктор кастомных дашбордов из чарт-виджетов (`Analytics → BI Builder`); разговорное «Builder». Не путать с `Form Builder` / `PWA Builder` — это другие сущности. [how-to/bi-builder.md](../how-to/bi-builder.md).
- **Live Pulse** `[AIO, аналитика]` — страница `Analytics → Live Pulse` (ERP-only) с живым потоком событий трафика: `init` (визит зарегистрирован), `handle` (дискретное событие флоу), `conversion` (создана конверсия). Счётчики копятся только пока страница открыта и обнуляются при перезагрузке — **это не отчёт**, сверять его цифры с таблицами и отчётами нельзя. [how-to/live-pulse.md](../how-to/live-pulse.md).
- **Session Analytics** `[AIO, аналитика]` — страница `Analytics → Session Analytics` (ERP-only): список записей сессий с плеером записи + сравнение scroll/click-карт нескольких лэндов рядом. [how-to/session-analytics.md](../how-to/session-analytics.md).

- **`Remarketing count`** `[AIO, метрика]` — метрика-счётчик событий рассылки: `Sent`, `Failed`, `Delivered`, `Opened` (мультиселект `Events`) с необязательным фильтром по каналу (`Channels` — `WebPush`, `Telegram`, `SMS`, `Email`). Сама не появляется: её заводят в `Settings → Metrics` карточкой `Remarketing count` (либо она приезжает из шаблона тенанта). Считает **события, а не визиты**. Каналы `SMS` и `Email` в фильтре есть, но событий по ним не бывает (эти каналы не отправляются), а `Delivered` / `Opened` приходят только с web-push ремаркетинг-кампании. На страницах раздела `Marketing` проходят только она и формулы целиком над ней — поэтому CTR и open-rate собираются метрикой `Computable metric` поверх неё. [models/metric.md](../models/metric.md).
- **`Send Result` (группировка вкладки `Remarketing`)** `[AIO, аналитика]` — разрез отправок по исходу: `Success` у доехавшего сообщения, `push_failed` (отправка не удалась — сюда же попадает визит без push-подписки), `dead_endpoint` (подписка мертва), плюс три платформенных лимита — `daily_limit`, `hourly_limit`, `min_interval`. Соседние группировки той же вкладки — `Campaign`, `Flow`, `Templates`, `Channel` и время (`Day` / `Hour` / `Month` / `Year`). Что делать с каждым исходом — [how-to/remarketing-campaigns.md](../how-to/remarketing-campaigns.md).

- **Valuable** `[AIO, признак визита]` — у визита есть конверсия с `revenue > 0`. Не то же самое, что «есть конверсия»: конверсия без выручки признак `Valuable` не даёт. Виден колонкой `Valuable` в таблице сессий и приходит признаком в `conversion`-событиях `Live Pulse`. [how-to/session-analytics.md](../how-to/session-analytics.md).
- **Qualified Visits** `[AIO, метрика]` — чистая база воронки: визиты, у которых точно загрузился JS на лэнде (значит, точно работают Heatmaps, Video Sessions, A/B-сплитование, антифрод-фингерпринт). Основные метрики построены на `Visits` (полная аналитика); Q.V. используют как срез качества. [mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md).
- **EPL / EPL$** `[AIO, метрика]` — earnings per lead (доход на лид). `EPL` и `EPL$` — **одна и та же метрика**, различаются только названием (приставкой), никакого отдельного показателя `EPL$` нет. Имена метрик задаются произвольно в `Settings → Metrics` (создаёт / переименовывает / редактирует свободно), поэтому расхождение в написании — норма, а не разные сущности. Механика метрик — [models/metric.md](../models/metric.md).
- **Visit Loss / Потеря визитов** `[AIO, метрика]` — разница между визитами и `Qualified Visits`. Высокая потеря — индикатор проблем со скоростью лэнда / сетью / клиентскими блокировщиками. Визиты, помеченные `Trash`, в Visit Loss **не входят** — они исключены из аналитики целиком. [mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md).
- **Trash / Trash Visits** `[AIO]` — визиты, исключённые из аналитики (`is_trash`); причина — в поле `Trash Reason`. Хранятся в отдельной таблице (не `Visits`); полей меньше — только нужные для понимания причины. Хранятся **всегда** (без ограничения по времени).
- **Attribute by events time** `[AIO, переключатель аналитики]` — тоггл в таблицах аналитики (подсказка: `Attribute by event time (Also known as conversion time attribution)`); переключает атрибуцию конверсии с «времени визита» (дефолт) на «время самого события». Влияет на распределение конверсий по дням. По дефолту выключен. Разговорное: «Attribution by Event Time», «атрибуция по времени события».
- **Colorize** `[AIO, аналитика]` — подсветка ячеек таблицы по значению метрики: градиентом или статичными порогами (красный/жёлтый/зелёный). Помогает быстро увидеть «хорошие» и «плохие» строки.
- **Highlight Row** `[AIO, экшен]` — экшен в таблице: добавить фильтр по текущей строке. Удобный способ быстро сужать отчёт без ручного добавления фильтра.
- **Unwrap tree view / Анврап дерева** `[AIO, аналитика]` — кнопка-иконка в `Roll Up report` (тултип `Unwrap tree view`, обратно — `Default tree view`; рядом `Collapse all` сворачивает ветки), которая разворачивает древовидную группировку в плоский список всех комбинаций. Удобно, когда нужно сразу видеть все сочетания, а не разворачивать ветки по одной. Разговорное: «развернуть дерево», «Expand Tree».
- **Build Roll-Up Report** `[AIO, экшен]` — экшен из таблицы аналитики (правая кнопка): открыть Roll Up Report с уже подставленным фильтром по выбранному элементу (кампании, источнику и т.п.). Сокращает количество кликов.
- **`Landing` (позиционный группер лэнда: `First` / `Second` / `Third`)** `[AIO, аналитика]` — группировка по лэнду на конкретной позиции воронки визита. В каталоге групперов это **одна строка `Landing`** с пикером позиции; отдельных строк `LP #1` / `LP #2` / `LP #3` там больше нет — подписи стали `Landing 1` / `Landing 2` / `Landing 3`. Сами ключи групперов не менялись — поменялись только подписи. В том же пикере под позициями, за разделителем, лежат роль-групперы по типам лэндов (см. `LP: <Тип>`). Какие ещё серии свёрнуты в строку с пикером — [how-to/analytics.md](../how-to/analytics.md).
- **`LP: <Тип>` (роль-группер: лэнд в роли типа на любой позиции)** `[AIO, аналитика]` — группер категории `Funnel`, по одному на каждый тип лэнда тенанта с включённым `Generate events?` (у типа без него группера нет — поэтому в пикере не все типы). Отвечает на «какой лэнд играл роль этого типа» независимо от позиции в воронке: значение строки — сам лэнд, а не тип; если у визита несколько лэндов одного типа, берётся первый; визит без лэнда этой роли в строки и футер не попадает, строки не пересекаются. В каталоге не отдельная строка: живёт в пикере строки `Landing` под позициями `First` / `Second` / `Third`, за разделителем, бейджем типа с его иконкой и цветом; на чипе подписан `Landing: <тип>`, в списке фильтров таблицы — `LP: <имя типа>` (тем же ключом таблицу можно и фильтровать). Ключ разбивки (он же в Pivot Report API) — `landing_of_type[<uuid типа>]`. Разбивки «лэнд в любой позиции» строкой на каждое участие или «весь путь визита одной строкой» в продукте нет. (разг.: «где лэнд участвовал», «лэнд как преленд», «лэнд в роли оффера») [how-to/analytics.md](../how-to/analytics.md).
- **External Reports** `[AIO]` — настраиваемые внешние отчёты в `Settings → External reports`. Типы: `Visits CSV`, `Google Conversions CSV`. Каждый отчёт имеет UUID + Secret (Secret защищён 2FA). Отчёт скачивается через URL вида `https://app.aio.tech/api/v1/external-reports/data?uuid=...&secret=...`. Для Google Conversions можно добавлять параметры `rename[Lead]=...`, `filters[FIELD_UUID]=value`, `gclid=GCLID_FIELD_UUID`, `deep=N` (дней назад), `timezone=...`.
- **Pivot Report API** `[AIO, API]` — `POST /api/v1/pivot-report/data?token=...`. Возвращает pivoted-датасет: группировки по 1..7 `definitions` + фильтры через `conditions` (AND) + пять обязательных булевых флагов тела (`event_time_attribution`, `back_fix_attribution`, `hide_bots`, `hide_trash`, `hide_empty_metrics`). В Pivot-пути реально влияют только `event_time_attribution` и `hide_empty_metrics`; `back_fix_attribution`/`hide_bots`/`hide_trash` — no-op, trash скрыт всегда (полярность и путь Tables Data — [how-to/api.md](../how-to/api.md)). Опциональный header `x-tenant-id` — для токенов с доступом к нескольким тенантам. Ответ — nested object с JSON-encoded ключами, где finalest leaf содержит `placeholders` (мапа `metric_<uuid>` → value) и `filters` (полный путь группировок).
- **Fields & Groupers Catalog — Tracker / Location / Browser / OS** `[AIO, API]` — ключи `clickhouse_key` для `definitions[].key` (группировка) и `conditions[].key` (фильтр) в Pivot Report API. Первые четыре категории:
  - **Tracker:** `visit_uuid`, `campaign_uuid`, `source_uuid`, `flow_uuid`, `split_group` (A/B-корзина, когда задана).
  - **Location:** `location_city`, `location_continent`, `location_country_code` (ISO country code), `location_time_zone` (IANA timezone).
  - **Browser & Device:** `browser_language_code` (напр. `en`, `fr`), `ua_client_engine/family/name/type/version` (`ua_client_engine` — Blink/Gecko и т.п.; `ua_client_type` — browser/app/bot), `ua_brand_name`, `ua_device_name`, `ua_model`, `user_agent`.
  - **OS:** `ua_os_name` (Windows/Android/iOS и т.п.), `os_combined` (нормализованный OS + версия), `ua_os_platform`, `ua_os_version`.
- **Fields & Groupers Catalog — Time / Web** `[AIO, API]` — продолжение каталога ключей Pivot Report API:
  - **Time:** `created_at_day/hour/month/week/year` (`created_at_hour` = `0–23`, `created_at_month` = `YYYY-MM`, `created_at_year` = `YYYY`, `created_at_week` = ISO week), `day_part` (Morning / Afternoon / Evening / Night), `week_part` (Weekday / Weekend, если настроено).
  - **Web:** `initial_domain` (первый замеченный домен), `initial_path` (первый замеченный path), `agent_version` (версия AIO JS-агента).
  **Attribution:** Time-групёры учитывают `event_time_attribution` из запроса (в Pivot-пути `back_fix_attribution` — no-op, см. [how-to/api.md](../how-to/api.md)).
- **Fields & Groupers Catalog — Landings / Destinations (funnel-ключи)** `[AIO, API]` — продолжение каталога ключей Pivot Report API:
  - **Landings & Types (positional):** `landing_uuids[1..3]`, `landing_type_uuids[1..3]`. `[N]` — порядковый номер в пути самого визита, а не номер ноды флоу: `landing_uuids[1]` = первый показанный лэнд, `[2]`/`[3]` — второй/третий отличающийся; повторный показ того же лэнда позицию не добавляет.
  - **Landing role (any position):** `landing_of_type[<uuid типа лэнда>]` — лэнд, сыгравший роль этого типа на любой позиции (при нескольких лэндах одного типа — первый); тот же ключ, что у группера `LP: <Тип>` в таблицах ([how-to/analytics.md](../how-to/analytics.md)). Аналогичного рабочего ключа по типам адвертайзеров нет.
  - **Destinations & Advertisers (positional):** `destination_uuids[1..3]`, `advertiser_uuids[1..3]` — `[N]` = N-й **успешный** пуш в отличающийся Destination (реджекты и повторные пуши в тот же Destination позицию не добавляют), а не позиция ноды во флоу; `advertiser_uuids[N]` — адвертайзер того же пуша.
- **Fields & Groupers Catalog — Custom / Facebook / Source** `[AIO, API]` — последняя часть каталога ключей Pivot Report API: `field_fb_ad_name`, `field_fb_campaign_name`, `field_fb_ad_set_id/name`, `field_fb_ad_id`, `field_fb_site_source_name`, `field_fb_campaign_id`, `field_fb_placement`, `referer`, `campaign_owner_uuid`, `form_uuid`, `field_launcher`. **Cardinality:** `visit_uuid`, `user_agent` и кастомные поля — высокая кардинальность, для дебага.

## Интеграции и постбэки AIO

- **Постбэк** `[общий]` — серверный callback от рекламодателя при конверсии. Используется не только для самого факта конверсии: типичный кейс — апдейты статусов лида (No Answer, Recall, целевое действие), которые рекламодатель шлёт постбэками. Статусы-апдейты сейл-цикла идут через **один** `Conversion Type` `Sale Status Update` (имя статуса — в поле `sale_status`, не в имени типа), см. [models/conversion-model.md](../models/conversion-model.md).
- **Postback generator / Генератор постбеков** `[AIO, экран]` — конструктор ссылки входящего постбэка: зелёная кнопка `Postback generator` в шапке таблицы `Tracker → Conversions`, есть и в ERP, и в MTK. В форме задаются тип конверсии и домен, при необходимости `Visit UUID`, `Destination`, `Delay, sec`, бизнес-модель, валюта и значения полей конверсии; на выходе — готовый URL приёмника, переключаемый между двумя форматами, `Path` и `Query` (у `Path` дополнительно раскрывается блок `Short links with slugs` — те же ссылки со слагом типа вместо UUID). Ничего не сохраняет — ссылку копируют и отдают рекламодателю. Доступ закрыт правом `Features: postback generator` ([models/permissions-model.md](../models/permissions-model.md)). Разбор полей и форматов — [how-to/postback-generator.md](../how-to/postback-generator.md).
- **`conversion-by-key` (формат постбэка)** `[AIO]` — третий формат приёмника конверсий, `https://<домен>/api/v1/trigger/conversion-by-key`, для рекламодателя, который не может переименовать свои параметры: он шлёт идентификаторы своими именами (по умолчанию `clickid` — визит, `goal` — тип конверсии), а параметры `visit_uuid_key` и `conversion_type_uuid_key` в той же ссылке сообщают приёмнику, как эти имена читать. В `Postback generator` этот формат не выводится — ссылка собирается руками. Разбор — [models/conversion-model.md](../models/conversion-model.md).
- **Sale Status Mapping** `[общий, НЕ в AIO]` — инструмент в **сторонних системах** (рекламодателях, CRM, партнёрках), который приводит разноимённые сейл-статусы к единому стандарту: `noanswer1` / `no_answer` / `no_ans` → `No Answer`. Используется на стороне клиента/рекламодателя **до** отправки постбэка в AIO. **В самой AIO такого инструмента нет** — статусы записываются как есть в **один** `Conversion Type` `Sale Status Update` (значение в поле `sale_status`, не отдельный тип под каждый статус). Если рекламодателей много и статусы у них разные — стандартизация делается на стороне клиента/рекламодателя, не в AIO (см. [models/conversion-model.md](../models/conversion-model.md)).
- **Auto-login link** `[AIO]` — ссылка автологина, которую интеграция (API-Destination) возвращает при успешном пуше. **Отдельного поля под неё нет** — она лежит в поле визита `destination_url`; форма после пуша редиректит юзера по ней (мгновенно или после задержки), чтобы тот сразу попал в личный кабинет. (Для Destination-редиректа в `destination_url` лежит ссылка, по которой ушёл визит.)
- **Поля визита по Destination** `[AIO, поля визита]` — результат пуша лида в Destination, видны в `Tracker → Visits`: `pushed` (boolean — запушился ли визит в Destination; колонка `Pushed`); `Destination` (куда визит запушился); `destination_url` (по какой ссылке визит ушёл в Destination; для API — ссылка автологина, для редиректа — ссылка с подставленными плейсхолдерами); `destination_external_id` (UI: `Destination External ID` — ID лида, возвращённый внешней системой). При реджекте от рекламодателя пишутся ещё три поля: `rejected_destination_uuid` (UI: `Rejected Destination` — какой Destination отклонил лид), `rejected_advertiser_uuid` (UI: `Rejected Advertiser` — его адвертайзер, если есть) и `last_rejection_reason` (UI: `Last Rejection Reason` — текст причины реджекта, записанный **прямо в поле визита**, так что логи ради причины открывать не обязательно). Сам запрос/ответ пуша — в `Settings → Logs` → namespace `Destination Handler`. [models/conversion-model.md](../models/conversion-model.md).
- **Webhook** `[общий]` — уведомления (Telegram, Slack) о ключевых событиях: достижение капы, падение сервера, кончился бюджет в рекламном аккаунте.
- **Add by Integration** `[AIO]` — кнопка добавления интеграции из публичного списка.
- **Generator** `[AIO, Settings]` — справочник записей-интеграций в `Settings → Generators` (ERP-only). Каждая запись — интеграция с атрибутами `Name` + `Integration Type` + settings (набор полей зависит от типа — per-integration settings). Дефолтный тип интеграции — внешний сервис генерации вайт-лэндингов. **Не путать с `Link Generator`** — тот генерирует трекинг-ссылки кампании (см. `Generate Link / Link Generator` ниже); `Generator` здесь — Settings-справочник интеграций.

- **Destination Integrations** `[AIO]` — партнёрские интеграции в `Destinations`. Все интеграции реализованы через единый механизм JSON Schema Builder: каждая интеграция имеет имя и свой набор обязательных полей (например, API URL, API Key + специфичные для платформы поля типа Offer ID / Affiliate ID / Username). Список интеграций постоянно расширяется. Примеры из коробки: IREV, Getlinked, Trackbox, LeadGreed, Elnopy. Наборы обязательных полей для самых частых:
  - **IREV** — API URL, API Key, `IREV Affiliate ID`, `IREV Offer ID`.
  - **Getlinked** — API URL, API Key, `Offer Name`, `Comment`.
  - **Trackbox** — API URL, API Key, API Username, API Password, `Ai`, `Ci`, `Gi`.

  Новая интеграция добавляется по запросу к support — нужно передать API-документацию + credentials, AIO добавляет шаблон. У `By Integration`-метода поля зависят от выбранного шаблона, в окне `Create New Destination` показываются параметры под конкретную платформу — сверяться с её API-документацией.
- **Destination Payload (типы)** `[AIO]` — конфигурация дестинейшна: либо API-интеграция (с полями, специфичными для платформы), либо `Simple Redirect` (только URL с placeholders). В Simple Redirect для передачи данных используются плейсхолдеры визита: `{{aio.visit.uuid}}`, `{{aio.visit.fields.phone}}`, `{{aio.visit.fields.email}}`, `{{aio.visit.fields.first_name}}`, `{{aio.visit.fields.last_name}}`.
- **Запрос новой интеграции** `[AIO, процесс]` — если интеграции нет в списке: запрос в чат → API-доки + креды для тестового пуша → дальше команда AIO добавляет шаблон интеграции. См. *уточните у поддержки*.
- **IPInfo** `[AIO, интеграция]` — внешний сервис обогащения данных по IP. Подключается как `Traffic Filter` с токеном; ответ пишется в поля визита, которые заранее **создаются вручную** в `Settings → Fields` со **snake_case** slug ([how-to/custom-fields.md](../how-to/custom-fields.md) → Пачка полей под IPInfo).
- **IPQuality / IPQuality Score** `[AIO]` — **отдельного сервиса `IPQuality` в AIO НЕТ**: подключить его как `Traffic Filter` нельзя, отдельным шагом во флоу он не используется. Единственный отдельный IP-сервис — `IPInfo` (см. запись выше).

## Команды и пермишены AIO

- **Folder sharing / Шаринг папки** `[AIO]` — шеринг сущностей прямо из папки: шеринг папки распространяется на все сущности внутри; смена типа шеринга папки меняет его и у сущностей; удаление сущности из папки снимает с неё связанный с папкой шеринг; вручную добавленный сущности шеринг при пересечении с шерингом папки не затрагивается.
- **Tenant / Тенант** `[AIO]` — см. раздел «Инфраструктура». Используется «Tenant», понятия «Workspace» нет.
- **Teams** `[AIO]` — команды внутри `Tenant`-а, помогают разделить юзеров и сущности (Campaigns, Landings, Domains и т.п.). Роли в команде:
  - **Team Member** — видит только то, что ему пошарили или что пошарили его команде.
  - **Team Leader** — видит всё, что создано Team Members и другими Team Leaders своей команды.
  - **Team Head** — видит всё в команде (включая сущности других Team Heads); Team Member и Team Leader его сущности не видят.

  Команды + Positions (см. ниже) дают полную модель пермишенов. Создаются в `Settings → Teams`. [models/permissions-model.md](../models/permissions-model.md).
- **Roles & Permissions / Positions & Imperatives** `[AIO]` — глубокая система пермишенов. Базовые роли: **Admin / Owner** (полный доступ), **Employee** (ограниченный, видит только пошаренное). Поверх ролей — кастомные **Positions** (наборы пермишенов), которые присваиваются юзерам. Внутри Position лежат **Imperatives** разных типов (см. ниже). Если у юзера несколько Positions — действует Priority (более высокий приоритет перекрывает более низкий).
- **Imperative Types** `[AIO]` — типы пермишенов внутри Position. По убыванию scope:
  - **Sections** — целые секции (Analytics, Content, Meta) со всеми subsections и actions.
  - **Subsections** — конкретные подсекции (Content: CDN files, Content: Landings, Settings: Distributions).
  - **Pages** — конкретные страницы (Content: CDN files Page и т.п.). Только просмотр, без actions.
  - **Actions** — конкретные действия (Edit, Archive, Assign to Folder, Create Version, Upload).
  - **Features** — спец-фичи, закрытые отдельно от раздела, где живут; всего семь: `Features: sessions`, `Features: heatmaps` и `Features: notes` (эти три — только в билде ERP), плюс `Features: conversions revenue`, `Features: conversions payout`, `Features: table export`, `Features: postback generator` (эти четыре — в ERP и MTK).
  - **Show Logs** — просмотр логов конкретной секции/страницы.
  - **Sharing & Ownership Change** — шеринг и смена owner-а.
  - **Scopes** — view-only доступ к sections/pages без шеринга.
  - **Editor Scopes** — правка и шаринг сущности без владения ею (видимости не даёт — её открывают `Scopes`); пока только для лэндов.

  В одной Position могут комбинироваться через **Allow/Deny** toggle. [models/permissions-model.md](../models/permissions-model.md).
- **Position Priority** `[AIO]` — числовой приоритет Position. Когда у юзера несколько Positions, при конфликте Allow/Deny одной и той же permission Win более высокий Priority.
- **Базовые роли** `[AIO]` — три базовые роли юзера в тенанте:
  - **Owner** — владелец тенанта, full access ко всем сущностям.
  - **Admin** — full access (как Owner) ко всем сущностям.
  - **Employee** — ограниченный доступ, видит только то, что ему пошарили или его команде.

  Поверх базовой роли — кастомные Positions для тонкой настройки. [models/permissions-model.md](../models/permissions-model.md).
- **Invite User / Invitation Link** `[AIO]` — добавление нового юзера в тенант через `Settings → Users → +User`. Поля: Name, Code, Usages (сколько раз можно использовать), Status, Type (User), Till Date, Role, Position, Team. Генерируется инвайт-линк; юзер регистрируется по ссылке. [models/permissions-model.md](../models/permissions-model.md).
- **Mass Sharing экшены** `[AIO]` — выделить несколько сущностей через чекбокс и применить:
  - **Share Also** — массово пошарить с юзером/командой.
  - **Unshare** — массово снять шеринг.
  - **Force Share** — снять предыдущие шеринги и пошарить только с новыми.
  - **Mass Change Owner** — массово сменить owner.

  [models/permissions-model.md](../models/permissions-model.md).
- **Логирование** `[AIO]` — по всем действиям пишется IP, User-Agent, timestamp. Аудит-след действий пользователей.

## Конверсии и метрики AIO

- **Trigger Conversion** `[AIO, действие]` — ручная быстрая отбивка конверсии на визит (экшн; выведен и колонкой в таблице визитов). Конверсии, отбитые этим экшеном, помечаются в БД как `manual` (отдельной колонкой это пока не выводится).
- **Conversion Type** `[AIO]` — кастомный тип конверсии. Создаётся через `+Conversion Type` в `Settings → Conversion Types`. Постбэки от внешних систем приходят на UUID или slug этого типа. Набор типов в шаблоне тенанта зависит от вертикали и кастомизации тенанта. Конкретные типы (`Lead`, `Sale Status Update` и т.п.) описаны как отдельные термины в этом глоссарии.
- **Conversion Type — атрибуты** `[AIO]` — поля при создании/редактировании Conversion Type:
  - **Name**, **Color**, **Description** — отображение (`Color` — цвет в `Tracker → Conversions`).
  - **Is Registry?** — toggle на самом Conversion Type. Не путать с `Is Registry` на уровне **поля** визита (см. `Атрибуты поля`).
  - **Slugs** — один или несколько slug'ов. Параметр `conversion_type_uuid` принимает UUID типа **либо** любой его slug — равнозначно.
  - **Uniqueness Strategy** — сколько раз конверсия этого типа может быть создана на один визит. См. отдельный термин.
  - **Business Value** — `Good` / `Neutral` / `Bad`. Влияет на `Reward` в AI-оптимизации.
  - **Reward Weight** — числовой вес для AI-оптимизации.
  - **Correction type** — при повторном постбэке с другим revenue спавнится correction-конверсия. Итог — в поле `Revenue` (не `Reward`).
  - **Payout Settings** / **Revenue Settings** — привязка к дистрибуциям Payout / Revenue.
  - **Notification Flow** — `Notification Flow` (синоним — `Marketing Flow`), запускается при поступлении конверсии этого типа.
  - **Поля конкретной конверсии:** Geolocation, Visit Date, Conversion Date, **Delta**, Revenue Amount, Campaign, Source, Destination + кастомные поля (например, `sale_status`).
- **Uniqueness Strategy** `[AIO, атрибут Conversion Type]` — определяет, сколько раз конверсия этого типа может быть создана для одного визита. Три варианта:
  - **Single Conversion** — одна на визит. Для событий, которые случаются один раз: `Lead`, `Registration`, `Install`, `Push Subscribe`, `Invalid`, `Rejected Lead`.
  - **Multiple Infinity** — без лимита. Для серий апдейтов: `Sale Status Update` принимает каждый новый статус от рекламодателя как отдельную конверсию, накапливая историю.
  - **Multiple By Unique** — несколько на визит, но с **дедупликацией по полю `unique`**. Постбэк должен передавать параметр `&unique=<значение>`. Конверсии с одинаковым `unique` для того же визита считаются дублями и повторно не создаются. Используется когда нужен ровно один уникальный ивент на какое-то значение (например, один пуш на один offer_id, или один Add to Cart на одну product_uuid в рамках визита).

  Полная механика — [models/conversion-model.md](../models/conversion-model.md).

- **Sale Status Update** `[AIO, Conversion Type]` — Conversion Type с `Uniqueness Strategy = Multiple Infinity`, обычно со slug `sale_status`. Используется для фиксации **истории сейл-статусов** лида у рекламодателя между моментом регистрации (`Lead`) и финальной конверсией (`Rejected Lead` / целевое действие). Каждый постбэк рекламодателя создаёт новую конверсию + одновременно перезаписывает поле визита `current_sale_status`. Механика SSU-постбэка — [models/conversion-model.md](../models/conversion-model.md).

- **current_sale_status** `[AIO, поле визита]` — последний актуальный сейл-статус лида от рекламодателя; обновляется через постбэк параметром `visit[current_sale_status]=<статус>` вместе с конверсией `Sale Status Update`. Используется для аналитики (фильтры/группировки по текущему статусу) и маршрутизации флоу (повторные касания только визитов в `No Answer`). [models/conversion-model.md](../models/conversion-model.md).

- **Conversion Postback URL** `[AIO]` — URL для приёма постбэков от внешних систем (рекламодателей, партнёрок) о конверсиях. Формат:
  ```
  https://<любой_домен_тенанта>/api/v1/trigger/conversion-request
    ?visit_uuid=<...>
    &conversion_type_uuid=<...>
    &<параметры>
  ```
  Тенант определяется по `visit_uuid` (UUID глобально уникален). Любой домен тенанта принимает постбэки.

  **Параметры:**
  - `visit_uuid` (обязательно) — UUID визита. Внешняя система подставляет через макрос (`{CLICK_ID}`, `{aff_sub}` и т.п. — зависит от системы).
  - `conversion_type_uuid` (обязательно) — UUID Conversion Type в AIO.
  - **Поля конверсии** — без префикса (`arrived_revenue=10`, `sale_status=...`). Пишутся в саму конверсию.
  - **Поля визита** — с префиксом `visit[]` (`visit[current_sale_status]=...`, `visit[<any_field>]=...`). Обновляют поле визита. Работает для любого существующего поля визита.

  **Пример полного URL** для Sale Status Update:
  ```
  https://app.aio.tech/api/v1/trigger/conversion-request
    ?visit_uuid={CLICK_ID}
    &conversion_type_uuid=<UUID-sale-status-update>
    &arrived_revenue={revenue}
    &visit[current_sale_status]={sale_status}
    &sale_status={sale_status}
  ```
  Эта строка передаётся внешней системе при настройке постбэков на её стороне. Механика постбэков — [models/conversion-model.md](../models/conversion-model.md).

- **Rejected (как Conversion Type)** `[AIO]` — отдельный кастомный тип конверсии под отказ дестинейшна (невалидный номер, дубль, не та страна и т.п.). Обычно `Single Conversion`, отрицательный `Business Value`. Конкретные имена/наборы таких типов зависят от шаблона тенанта и кастомизации тенанта.
- **Push Subscribe (как Conversion Type)** `[AIO]` — отдельный тип конверсии под факт подписки визита на push-уведомления. Заводится, чтобы отдельно мерить «сколько вообще подписалось на пуши». Идёт в паре с `Push Subscribe Toggle` на уровне кампании и `Push Subscribe Script` на лэнде.
- **Business Value** `[AIO]` — бизнес-ценность каждой конверсии. Лейблы — `Good` / `Neutral` / `Bad`:
  - **`Good`** — прибавляется к `Reward` варианта (хорошие конверсии: целевое действие, покупка).
  - **`Neutral`** — ничего не прибавляет (вспомогательные/аналитические конверсии).
  - **`Bad`** — вычитается из `Reward` (плохие исходы: Reject, отказ в платеже). AI-оптимизация направляет трафик туда, где суммарная ценность максимальна.
- **Select** `[AIO, метрика варианта]` — сколько раз вариант был выбран (показан визиту). Используется в `Conversions AI` вместе с `Reward` для расчёта вероятностей при `Thompson Sampling`.
- **Reward** `[AIO, метрика варианта]` — сколько раз для варианта получили целевую конверсию (или сумму ценностей конверсий, если используется `Business Value`). Используется в `Conversions AI` вместе с `Select` для расчёта вероятностей при `Thompson Sampling`.
- **Thompson Sampling** `[общий, алгоритм]` — вероятностный bandit-алгоритм. В AIO — основа `Conversions AI` и `MVT`: для каждого варианта сэмплирует бета-распределение по накопленным `Reward` и числу показов (`Select`) и на каждом выборе берёт вариант с наибольшим сэмплом. Балансирует разведку и эксплуатацию: лучшие варианты получают больше трафика, но остальные продолжают тестироваться.
- **Epsilon-Greedy** `[общий, алгоритм]` — bandit-алгоритм. В AIO — основа `Metrics AI`: с вероятностью ~10% исследует — выбирает вариант равномерно случайно среди всех вариантов (лучший может переизбраться), — а остальные ~90% эксплуатирует вариант с наибольшим значением выбранной метрики. Реагирует быстрее `Thompson Sampling`, но более «жадный».
- **TimeFrame** `[AIO, параметр Metrics AI]` — окно времени, за которое считается метрика для оптимизации (15 минут / час / день / неделя / месяц и т.д.). Чем меньше — тем быстрее адаптация, тем шумнее данные.
- **Retrigger trackers** `[AIO, действие на конверсии]` (синонимы: Retrigger, retrigger конверсии) — экшен на конверсиях, перезапускает их трекеры — повторно шлёт событие в FB CAPI / Google / партнёрку. В UI пишется `Retrigger trackers`. Работает и на одной конверсии (правый клик), и пакетно: отметить нужные конверсии чекбоксами → ПКМ → `Retrigger trackers` → `Confirm`. Используется, когда первый пуш не дошёл или настройка отбивки была сломана (не тот пиксель/токен). [models/tracker.md](../models/tracker.md).
- **Show Near (на конверсии)** `[AIO, экшен]` — экшен в Action Menu конверсии, показывает другие конверсии, произошедшие внутри того же визита (например, чтобы увидеть Lead → целевое действие как пару). В окне `Show Near` эти конверсии можно посмотреть или скопировать их UUID.
- **Update Revenue / Update Conversion Revenue** `[AIO, экшен]` — ручное изменение revenue конкретной конверсии.
- **Delta (на конверсии)** `[AIO, поле конверсии]` — время между Visit Date и Conversion Date. Используется для анализа скорости конвертации.
- **Trackers (раздел)** `[AIO]` — оборачивание конверсий в постбэки и передача рекламодателям + вебхуки.
- **Alpha-Beta Chart** `[AIO]` — визуализация Conversions AI: распределения CR по вариантам (насколько оттестирован, диапазон реального CR). Внизу карточки стратегии.
- **Show sessions (action)** `[AIO, экшен]` — экшен правой кнопкой в Tracker → Campaigns — список записанных сессий по кампании.
- **Visit timeline** `[AIO, экшен на визите]` — хронология событий одного визита (создание, смена нод флоу, приход на Destination, конверсии, изменения полей). НЕ путать с `Show sessions` (запись сессии) и с логами `Destination Handler` (`Settings → Logs`). Разбор — [how-to/visit-timeline.md](../how-to/visit-timeline.md).
- **Visit logs** `[AIO, экшен на визите]` — правый клик по визиту в `Tracker → Visits` → `Visit logs`: логи обработки одного визита, уже отфильтрованные по нему (быстрее, чем копировать `Visit UUID` и собирать фильтр в `Settings → Logs`). Таблица открывается **визуально пустой**, пока `Severity` не переключить на `Debug` — Debug-уровень скрыт по умолчанию, а вся детальная отладка визита пишется именно на нём. Внутри — все логи визита: проверки трафик-фильтров и антифрода, пуши в Destination (успешные и с ошибкой + причина реджекта). Разбор — [how-to/debug-with-logs.md](../how-to/debug-with-logs.md).
- **Changelog / What's New** `[AIO, меню профиля]` — список обновлений продукта (`Product updates`: Features / Common / Fixes) в меню профиля; при релизе приходит уведомление «AIO app has been updated». [reference/ui-map.md](ui-map.md).
- **Public Roadmap** `[AIO, меню профиля]` — публичный роадмап в меню профиля: канбан не-архивных задач продукта («в работе / planned»). Пункт `Public roadmap`. [reference/ui-map.md](ui-map.md).
- **AIO affiliate program (Become affiliate)** `[AIO, меню профиля]` — реферальная программа AIO: приводишь клиента → он оставляет заявку → сейл-звонок команды AIO → выплата после покупки. CPA-выплаты $60–$500 в зависимости от продукта, плюс бонус $100 за первую успешную продажу от $1000. Пункт в меню профиля (виден по флагу тенанта). **Не путать с AFF-билдом** (`Affiliate` — отдельный вид приложения, не ERP/MTK).
- **Tags (Settings → Tags)** `[AIO, справочник]` — управляемый справочник тегов (`Settings → Tags`, в ERP и MTK): теги заводятся здесь и вешаются на сущности (кампании и др.) для поиска и фильтрации. Сам тег как атрибут живёт на сущности; управление списком тегов — в этом разделе. **Заархивированный тег пропадает с сущностей**: он остаётся привязанным, но в списках и карточках объектов (кампании, лендинги, домены, серверы, флоу и др.) больше не показывается. Симптом «тег исчез у всех кампаний» — это архивация тега в справочнике, а не потеря данных; разархивируешь — вернётся. **Теги вешаются и снимаются массово:** выделяешь несколько строк в таблице сущностей (кампании, лэнды, дестинейшены, сорсы, флоу, формы, дистрибуции, адверты, шаблоны сообщений — в ERP и MTK), в контекстном меню выбираешь массовое редактирование тегов и задаёшь два списка — какие теги добавить и какие снять. Добавление НЕ затирает уже висящие теги; если один и тот же тег попал в оба списка, он будет снят.
- **User Behavior метрики (группа)** `[AIO]` — в группу объединяются: записи сессий, хитмапы, время на лэнде, скроллинг-метрики, Bounce Rate, Engagement Rate, Visit Loss.
- **Bounce Rate** `[AIO, метрика]` — процент визитов, которые **не** провели на лэнде >10 секунд И **не** прокрутили >10% страницы. Метрика алертинга аномалий, не основная; границы статичные (10/10). [models/metric.md](../models/metric.md).
- **Engagement Rate** `[AIO, метрика]` — обратная к Bounce Rate: процент визитов, которые провели >30 секунд И прокрутили >30% страницы. Метрика алертинга аномалий, не основная; границы статичные (30/30). [models/metric.md](../models/metric.md).
- **Approximate metrics (аппроксимированные метрики)** `[AIO]` — метрики, подчёркнутые в таблице — высчитываются как пропорция от более полной метрики (не у всех визитов есть реальные данные для целевого шага).
- **Conversions Count (тип метрики)** `[AIO]` — простой тип метрики в `Settings → Metrics` — считает **только количество** конверсий выбранного `Conversion Type` (штуки, не деньги). Для денежных сумм — `Data feed metric` с источником `Conversions By Type Revenue`/`Payout`. [models/metric.md](../models/metric.md).
- **Data feed metric (тип метрики)** `[AIO]` — тип метрики в `Settings → Metrics`, считающий по внутреннему фиду событий AIO (базовая метрика-источник + опц. `Flag`-фильтр). Денежные суммы конверсий делаются именно им: источник `Conversions By Type Revenue` (сумма Revenue) / `Conversions By Type Payout` (сумма Payout). Отдельного «денежного» типа метрики нет. [models/metric.md](../models/metric.md).
- **Money (формат метрики)** `[AIO]` — формат отображения метрики для финансовых значений.
- **Install / Open PWA (Conversion Types)** `[AIO]` — `Install` — тип конверсии под установку PWA. Для **AIO/cached PWA** — не по клику на кнопку установки, а по факту установки: на Android + Chrome — по подтверждению браузерного диалога установки (отказ в диалоге конверсию не создаёт), на iOS — при первом запуске установленного приложения с домашнего экрана (само добавление на домашний экран AIO не видит). Для **3rd party / External PWA** — только когда юзер вернулся в AIO («установил + открыл»). `Open PWA` — отдельная конверсия: юзер реально открыл cached PWA после установки. Метрика `Open PWA / Install` — процент. См. [mechanics/pwa.md](../mechanics/pwa.md).
- **Conversion Spawn (шаг флоу)** `[AIO]` — шаг флоу, автоматически создающий указанную конверсию, когда визит попадает в этот шаг.
- **Correction Conversion (деривативная конверсия)** `[AIO]` — конверсии в AIO неизменяемые; при повторном постбэке с другим revenue AIO не перезаписывает исходную конверсию, а создаёт новую конверсию-коррекцию. [models/conversion-model.md](../models/conversion-model.md).
- **Conversion-on-Postback-Date (&timestamp)** `[AIO]` — датировать конверсию не моментом прихода постбэка, а временем из параметра `&timestamp` (unix-время). Граница одна: значение должно быть **не раньше даты создания визита**. Раньше визита — параметр молча игнорируется, конверсия датируется временем прихода; при этом дата **позже текущего момента** принимается как есть.
- **Transaction Hash / Transaction ID** `[общий]` — стандартный плейсхолдер ПП — уникальный ID транзакции. Рекомендуется как `&unique=` при `Multiple By Unique` (защита от дублей).
- **Присвоение чужих лидов внутри команды** `[AIO]` — против этого работают два штатных механизма: модель прав (кто какие сущности вообще видит — [models/permissions-model.md](../models/permissions-model.md)) и логирование действий с IP, User-Agent и временем, по которому видно, кто что сделал.

## Сокращения и API-термины

- **API-токен / API-юзер** `[AIO]` — токен авторизации для AIO-апи. Бесконечный по сроку, наследует доступы своего юзера. Рекомендуется создавать **отдельного юзера под API**, чтобы по логам было видно, что делалось через автоматизацию. Одного токена мало: у юзера должен быть ещё и включён **API-доступ** — отдельный флаг, видный колонкой `API` в `Settings → Users`. По умолчанию он выключен, включает его команда AIO по запросу; без него любой запрос с токеном отвечает `401` `Auth Middleware: Unauthorized`. Где взять токен и что ещё ломает авторизацию — [how-to/api.md](../how-to/api.md).
- **Compact API (= API 2.0)** `[AIO]` — узкий публичный API AIO, описанный Postman-коллекцией с ограниченным набором endpoint'ов (своя документация прямо в продукте есть у `Data API` и у MCP-сервера — [how-to/api.md](../how-to/api.md)) (Campaigns, Sources, Lands, Types, Users, Pulled, Changes/upload). Покрывает не все запросы (напр. `Replace Domain` через него нельзя), но проще в интеграции.
- **Публичный API: Tables Data endpoint** `[AIO]` — общий API-эндпоинт `Tables Data`, через который фронт AIO общается с бэком для любых табличных запросов. Один и тот же запрос для `Tracker Visits`, `Tracker Meta` (Meta-метрики: spend / impressions / clicks / CTR по `ad ID`), `Tracker Conversions` — меняется только `Table` в payload. Забор по API структурно одинаков для любой таблицы.
- **broad API / front-API (= API 2)** `[AIO]` — путь интеграторов через тот же API, которым общается фронт `app.aio.tech` с бэком: любое действие в UI воспроизводится тем же запросом с API-токеном.
- **Heavy query limit** `[AIO]` — бюджет «тяжёлых» запросов к публичному API: **20 сек CPU на скользящее окно последних 60 сек** (запросы, исчерпавшие бюджет, троттлятся/обрываются). Общие rate-лимиты API: **60 запросов/мин**, **3 одновременно**.
- **MCP-сервер AIO (`MCP Server`)** `[AIO, API]` — `POST https://app.aio.tech/api/v1/mcp`: собственный MCP-сервер AIO, к которому внешний AI-агент (`Claude Code`, `Claude Desktop`, любой другой MCP-клиент) подключается одной ссылкой и дальше сам читает данные трекера — трафик, метрики, прогнозы, логи кампаний. Ссылку, готовую команду и JSON-конфиг собирает диалог `MCP Server` — кнопка `MCP` в окне `AIO Chat`. Только чтение: действия, требующие подтверждения человеком, через MCP отклоняются. Подключение, инструменты и лимиты — [how-to/mcp-server.md](../how-to/mcp-server.md). (разг.: «коннектор», «подключить Клода к трекеру», «пусть агент сам смотрит цифры»)
- **AIO Skill (MD-file для AI-агентов)** `[AIO, артефакт]` — markdown-файл-инструкция для внешнего AI-агента (Claude/GPT) — описывает, какие запросы к AIO API делать под какие задачи (аналитика, загрузка лэндов, паузить/запускать кампании, ставка, CAPI/пиксели, генерация ссылок). **Не часть AIO** — артефакт. Читающую половину этих задач (аналитика, метрики, логи кампаний) закрывает встроенный MCP-сервер — агента к нему подключают одной ссылкой, без скилла и без своего кода ([how-to/mcp-server.md](../how-to/mcp-server.md)). Скилл поверх broad API остаётся нужен там, где агент должен что-то **менять**: заводить и паузить кампании, править ставку, грузить лэнды.
- **AIO bus push trigger** `[AIO, SDK]` — конструкция в AIO SDK — записывает значение в указанное поле визита. Формат: `window.aioBus.push({type: "trigger", key: 'offer_name', value: offer_name});` где `key` — slug поля, `value` — значение из JS-скрипта.
- **intl-tel-input + параметры** `[AIO, SDK]` — `intl-tel-input` — JS-библиотека, через которую AIO SDK рендерит phone-input в SDK-форме (флаг + dial code по странам). Параметры в блоке `form` `AIO SDK Macros Collection`: `separateDialCode` (при `true` показывает `+49` отдельно слева от инпута); `strictMode` (жёсткая валидация формата по стране — может отказывать валидным немецким номерам, решение — выключить); `showFlags` (показывать ли иконки флагов) и прочие опции самой библиотеки — имена сверяйте с её версией в бандле. Тюнинг — per-тенант.
- **config.form.controls + Customize SDK form + глобальный SDK-конфиг** `[AIO, SDK]` — `config.form.controls` — массив объектов конфига SDK-формы, описывает каждый input (тип, `keyType`, валидация, атрибуты). Полный разбор параметров и стилей SDK-формы — [reference/sdk.md](sdk.md) (раздел «SDK-форма — полный разбор») и [how-to/forms.md](../how-to/forms.md). Чтобы применить форму ко всем лэндам сразу — отдельный глобальный макрос с дефолтным SDK-конфигом (один на тенант), а не локально на каждом лэнде.
