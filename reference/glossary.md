# AIO Glossary

Базовый справочник по терминам AIO: при ссылке на термин AIO имена пишутся **как здесь**.

**Условные обозначения:** `[AIO]` — внутренний термин системы AIO; `[общий]` — общая терминология аффилиейт-маркетинга.

---

## Воркфлоу запуска и базовые понятия AIO

- **Прилэнд** `[общий]` — прогревочный лэнд без формы, только ссылки на следующий шаг. (разг.: «прокла», «прокладка»)
- **Оффер** `[общий]` — лэнд с формой, push в интеграцию лида. (разг.: «money page», «мани пейдж», «блэк», «блэк-страница»)
- **Прилэнд с формой** `[AIO, тип лэнда]` — гибрид: прилэнд, но с формой прямо на нём. В шаге прилэнда можно выбирать оба типа.
- **Оффер-нейм / афернейм** `[общий]` — название оффера. В AIO может быть динамическим: один — для отображения на лэнде, другой — для пуша в интеграцию.
- **Бренд** `[общий]` — то же, что оффер-нейм, синоним в речи команд.
- **For Visitor / For Advertiser** `[AIO, атрибуты оффер-нейма]` — два дефолтных атрибута каждого оффер-нейма в библиотеке: что показываем визиту на лэнде vs что шлём в интеграцию рекламодателю. Структуру хранилища можно расширять — например, добавлять изображение/лого, которое тоже подставляется динамически.
- **Two-step / One-step воронка** `[общий]` — двухступенчатая (прилэнд + оффер) и одношаговая (через `Скип` шага прилэнда — сразу на оффер) воронки. В AIO можно опционально превратить дефолтный two-step в one-step без перенастройки флоу. В шаблонах тенанта флоу так и названы: `1/2Step | …` — двухшаговый, который запускается и одношагово, и `1Step | …` / `Default 1Step Flow` — сразу на оффер (состав по вертикалям — [context/architecture.md](../context/architecture.md)).
- **Спасибка** `[общий]` — лэнд после успешной отправки формы.
- **Backfix / Back-link** `[AIO]` — встроенная фишка: если юзер на прилэнде нажал «Назад», его принудительно перекидывает вперёд (на оффер). Работает через SDK-конфиг в `AIO SDK Macros Collection` (см. ниже `Backfix (конфиг)`). [reference/sdk.md](sdk.md).
- **Витрина** `[общий]` — воронка с множеством разных прилэндов (баннеров/креативов), которые сходятся к одному и тому же офферу. Куда юзер ни кликнул, попадает в один оффер.
- **Vertical / Вертикаль** `[общий]` — направление трафика клиента (финансы, нутра, iGaming, свипстейкс и т.п.). Выбирается при регистрации в профиле компании (не в Form Builder); полный список вертикалей — *Вертикали в арбитраже трафика*. Команды из шаблона тенанта — по функции, а не по вертикали: `Media Buying Team A`, `Media Buying Team B`, `Tech Department`.
- **Медиабаер / баер** `[общий]` — специалист, который запускает и ведёт рекламные кампании в трекере (закуп трафика, креативы, оптимизация связок). Подробнее о роли и моделях работы — *Медиабаинг и место AIO в нём*.
- **Связка** `[общий]` — комбинация элементов рекламной кампании (источник + крео + прилэнд + оффер + гео), которая в сумме даёт положительную конверсию и прибыль. Ключевой рабочий термин медиабаинга — *Медиабаинг и место AIO в нём*.
- **Human ID** `[AIO, системное поле]` — человекочитаемый (короткий числовой) идентификатор объекта, по которому объект удобно искать и называть вместо длинного UUID. Виден в окнах создания/редактирования кампаний и лэндов (`Campaign details`, Settings лэнда). **Создаётся и ассайнится автоматически при создании объекта** — руками задавать/менять его не нужно. **Общий для всех тенантов AIO** (не по тенанту): у каждого типа объектов (кампании, лэнды, домены, дестинейшены и др.) своя сквозная нумерация, а не отдельная в каждом тенанте. Своего Human ID у визита нет — визит хранит Human ID кампании и лэндов, через которые прошёл. Это уже существующее системное поле — вопрос «как добавить Human ID в тенант» некорректен: добавлять нечего, оно есть у объекта по умолчанию.

## Инфраструктура и серверы AIO

- **Tenant / Тенант** `[AIO]` — клиентский воркспейс в системе. Имеет name, description, billing email, country code. Один user может иметь несколько тенантов; один тенант может быть пошарен между юзерами. Базовая единица изоляции — `Tenant`; отдельного понятия «Workspace» нет — словом workspace в нескольких подписях интерфейса назван тот же тенант.
- **Шаблон тенанта** `[AIO]` — тенант-донор, одноразовой копией которого создаётся новый тенант: флоу вертикали, кампании-примеры, лэнды, формы, типы конверсий, метрики, пресеты, позиции и команды. Выбирается карточкой на шаге «Тенант» регистрации; публичных восемь — `ERP Finance` / `ERP iGaming` / `ERP Nutra` / `ERP Sweeps` и `MTK Finance` / `MTK iGaming` / `MTK Nutra` / `MTK Sweeps`; сами записи ведёт команда AIO. Сменить шаблон у созданного тенанта нельзя. Состав и что копируется — [context/architecture.md](../context/architecture.md).
- **Manage Tenant** `[AIO, интерфейс / экшен]` — пункт `Manage tenant` в меню профиля (аватар в правом верхнем углу): правит название тенанта, `Billing Email` и IP-вайтлист (`IP address`). Доступен только Owner / Admin. Юзеров, роли, деактивацию и назначение Position он не трогает — это `Settings → Users` (ПКМ по юзеру) и вкладка `Assigned users` у позиции. [how-to/permissions.md](../how-to/permissions.md).
- **Сервер** `[AIO]` — серверная единица в `Tech → Servers`, на которую AIO ставит свой агент через Deploy-скрипт. Сервера агностичны — лэнды хранятся на CDN, а не на сервере: агент проксирует их файлы с CDN (видео держит копией на диске сервера) и исполняет команды AIO по визитам. Можно добавить вручную (`Add Manually` — указать IP, deploy-скрипт ставится руками через SSH) или купить через `Server Provider` (DigitalOcean и т.п.). Атрибуты: Name, Description, Tags, Server Provider, Region, Droplets Size & Image, Deployment Script, `Monitoring User` (только юзер с включённой 2FA), `Repoint Group`.
- **Destroy Server** `[AIO, экшен]` — необратимое удаление сервера, после которого он не операционален.
- **Агент** `[AIO]` — серверный компонент AIO на сервере клиента. Отдаёт визитёру HTML лэнда из полученной от AIO команды и проксирует файлы лэнда с CDN через путь `/_cdn` домена ([context/architecture.md](../context/architecture.md)), исполняет команды AIO по визиту и сообщает AIO о событиях флоу (submit формы, переход по ссылке-шагу). Поведение пользователя (heatmaps, записи сессий) снимает не агент, а клиентский SDK на лэнде ([reference/sdk.md](sdk.md)).
- **Домен** `[общий]` — домен, ведущий на сервер. Можно репойнтить между серверами автоматически (защита от простоя, когда сервер недоступен).
- **Edit Domain (атрибуты)** `[AIO]` — у домена настраиваются: Description, Tags, `Monitoring user`, `Direct traffic distribution` (дистрибуция для трафика без `cuuid` / `suuid`), тоггл `Allow indexing by search engines` (разрешить поисковикам индексировать домен), `Default query` (дефолтные параметры запроса при прямом заходе на домен — используется в Direct Traffic).
- **Subdomain / Create Subdomain** `[AIO, экшен]` — экшен `Create subdomain` в Action Menu домена (в ERP — только у домена с DNS-провайдером). Позволяет создать саб-домен от существующего: указать имя, серверы, Monitoring User.
- **Clear Domain** `[AIO, экшен]` — экшен, который освобождает имя домена: стирает имя у записи (в описание пишется `Cleared: <домен>`) и отправляет её в архив. Связи с кампаниями не сбрасываются — они остаются на записи без имени. Что происходит с DNS-зоной (`Clear strategy`) и как вернуть домен — [how-to/domains.md](../how-to/domains.md).
- **Default query** `[AIO, опция домена]` — настройка домена, автоматически прикрепляющая Campaign + Source к визитам, которые пришли на голый домен без UTM-параметров. Используется при прямом трафике. Альтернатива — `Direct Traffic Distribution` (более централизованный).
- **Трекинговый домен** `[AIO]` — домен, который указан в рекламной кампании, до фильтра. Если во флоу есть шаг `Domain change`, трекинговый домен отличается от публичного, под которым у визита фактически открывается лэнд.
- **Публичный домен** `[AIO]` — домен, под которым у визита фактически открывается лэнд после шага `Domain change`. Его можно заменить, не трогая рекламную кампанию (через `Replace Domain`).
- **Lock campaign to this domain** `[AIO, toggle]` — переключатель в окне кампании (`Edit campaign`), привязывающий кампанию к её домену: заход по ссылке с другого домена кампанию не открывает. `Link Generator` только предупреждает, если кампания привязана к другому домену. По дефолту кампанию открывает любой домен её тенанта (или родительского тенанта).
- **Абузы доменов** `[общий]` — жалобы на домен (abuse). Трекинговый и публичный домены и шаг `Domain change` — [models/domain.md](../models/domain.md).
- **Repoint Group / Репойнт-группа** `[AIO]` — атрибут сервера: строка-группа. При падении сервера автоматический репойнт идёт **только в пределах этой группы**. Если живых серверов в группе нет — репойнт не сработает, и трафик с тех доменов остановится. Поэтому в одной группе важно держать минимум два сервера. Пример: связать в одну группу серверы по гео или по аккаунтам провайдеров.
- **Monitoring User / Мониторинг-юзер** `[AIO]` — юзер, которому AIO-tech-bot шлёт нотификации в Telegram, если сервер/домен падает или становится недоступен. Назначается отдельно для серверов, доменов и Destination (у Destination — алерт о заполненной капе). Можно использовать не отдельного юзера, а групповой чат (через бота-юзера на чат). Алерты идут только в Telegram — нужна привязка аккаунта к TG, иначе доставлять некуда.
- **AIO-tech-bot / `@aio_tech_bot`** `[AIO]` — Telegram-бот AIO для уведомлений и для включения 2FA. 2FA можно настроить через этот бот (Telegram) или через **Google Authenticator** (привязка к Telegram для 2FA необязательна с тех пор, как добавили Google Authenticator). Прямые сообщения бота (алерты мониторинга серверов и доменов, алерт о забитой капе, код 2FA) приходят только в Telegram: без привязки аккаунта к Telegram они не доходят, а 2FA через Google Authenticator такой привязки не даёт. Уведомления Notification Center приходят в колокольчик всегда, а наружу — в Telegram и / или Slack по Preferences ([mechanics/notification-center.md](../mechanics/notification-center.md)).
- **Pinging / мониторинг доступности** `[AIO]` — отдельная выделенная подсистема: AIO сам следит за доступностью серверов и доменов с включённым мониторингом, упавший объект переводит в `Danger` со строкой причины, восстановившийся — в `Running` со строкой `Fine`, и шлёт Monitoring User-у Telegram-отчёты `AIO Monitoring · Domains` / `AIO Monitoring · Servers`. [context/architecture.md](../context/architecture.md).
- **Repoint** `[AIO, действие]` — автоматическое перенаправление доменов с DNS-провайдером с упавшего сервера на случайный живой сервер в той же `Repoint Group` (гео/близость не учитываются); вручную — `Repoint to a new server`. Меняет DNS-записи, поэтому у домена без DNS-провайдера недоступен — там сервер меняют пунктом `Change server in AIO` («Изменить сервер в AIO»), а A-запись — у себя.
- **Assign under attack (Under Attack mode)** `[AIO, действие на доменах с Cloudflare]` — включает Cloudflare Under Attack mode для домена(ов). Пункт меню — `Assign under attack`, один и для одного домена, и для пачки (виден у доменов с DNS-провайдером). Cloudflare показывает «Verify you are human» captcha всем визитам. Первая ступень защиты от DDoS.
- **Item lists (IP) / Block-листы** `[AIO]` — списки IP в `Settings → Item lists` (ERP) для блокировки прямо на уровне AIO (не Cloudflare): список подставляют в условие правила по IP. Поддерживают CIDR (`x.x.x.x/24`) и диапазон через тире. Используется для жёсткого отсечения DDoS-источников. (разг.: «AS-Net Sites», «блок-лист IP»)
- **Deploy / Deploys** `[AIO]` — скрипт, который раскатывается на серверу при добавлении (ставит Docker, Squid, AIO-агент). Можно создавать кастомные Deploys — например, чтобы любой добавляемый сервер становился ещё и Squid-прокси (логин и пароль прокси задаются в Deploy-скрипте, порт фиксированный — `5145`).
- **Squid Proxy** `[общий]` — прокси-сервер, ставится по дефолту в Deploy-скрипте AIO. Позволяет любой добавленный сервер использовать как прокси.
- **Provider (общий зонтик)** `[AIO]` — внешний партнёр, через которого AIO покупает/использует ресурсы. Три типа: **Server Provider** (DigitalOcean и др.), **Domain Provider** (Namesilo, Namecheap и др.), **DNS Provider** (Cloudflare и др.). Каждый добавляется в свой раздел `Tech → ...` (`Tech → Server providers` / `Domain providers` / `DNS providers`), требует ключ API (у части провайдеров — ещё email или логин), имеет action `Test` (проверка коннекта); у Domain Provider есть ещё `Check balance`.
- **Records strategy / `Only IPv6`** `[AIO, настройка Cloudflare DNS Provider]` — какие записи ставить доменам провайдера: `Default IPv4` (по умолчанию, A-записи на IP сервера) или `Only IPv6` (AAAA-записи на `IPv6 address` сервера; только при `Proxied` = `Yes`, у каждого сервера домена должен быть IPv6). (разг.: «домен на IPv6», «AAAA-запись»). [how-to/domains-ipv6.md](../how-to/domains-ipv6.md).
- **Test Provider** `[AIO, экшен]` — экшен в Action Menu провайдера, отправляет API-запрос для проверки коннекта. Для DNS Provider — прогоняет права, нужные для работы с зоной (для Cloudflare успешный ответ выглядит как `Cloudflare OK — <тип ключа> (<аккаунт>), zone <зона>, all required permissions present`, разбор — [how-to/domains.md](../how-to/domains.md)); для DigitalOcean — `Auth as <email>, with N droplets limit`; для Domain Provider — может также показать баланс. Ошибка теста DigitalOcean означает проблему с ключом или неактивный аккаунт; у неактивного аккаунта текст начинается с `account is inactive - `, дальше — сообщение DigitalOcean (например `Your team has been locked due to lack of payment or improper use of the platform. Please open a ticket...`).
- **Proxies** `[AIO, Tech]` — справочник прокси в `Tech → Proxies` (в MTK — `Settings → Proxies`): у записи `Name` и прокси-строка; прокси выбирают в настройках интеграций (например, у DNS-провайдера).
- **Server-провайдер** `[AIO]` — внешний провайдер серверов (DigitalOcean и другие).
- **Domain-провайдер** `[AIO]` — внешний регистратор доменов (Namesilo, Namecheap и другие).
- **DNS-провайдер** `[AIO]` — внешний DNS-провайдер (Cloudflare и другие).
- **Чекеры доменов** `[AIO]` — интеграции для отслеживания бана доменов:
  - **Google Threat** — публичная (бесплатная) проверка на красный экран (в UI тип чекера так и называется — `Google Threat`).
  - **VirusTotal** — публичная апишка с лимитом запросов; AIO распределяет домены между несколькими VirusTotal-аккаунтами для увеличения общего лимита.
- **Replace Domain** `[AIO, действие]` — массовый экшен для замены одного домена на другой в настройках шагов `Domain change` выбранных кампаний.
- **Direct без Cloudflare** `[AIO]` — штатный способ добавить или купить домен с пустым DNS-провайдером (без Cloudflare; у купленного так домена остаются NS регистратора). SSL-сертификат можно выпустить кнопкой прямо из AIO. Запросы идут напрямую на сервер. Не привязан к вертикали — просто ещё одна фича; учитывать только, что без Cloudflare сервак уязвимее к DDoS (при бан-атаке может упасть весь). Полностью — [how-to/domains.md](../how-to/domains.md).
- **DNS-пропагация** `[общий]` — время, за которое DNS-записи распространяются после смены — единственный реальный даунтайм при репойнте сервера в AIO.
- **Multi A-record** `[AIO, DNS]` — несколько A-записей на одном домене: так AIO записывает DNS, если домену выбрать несколько серверов. Сессия визита между агентами не делится, поэтому на реальном трафике так не делают ([models/server.md](../models/server.md)).
- **Balance domains / Rebalance** `[AIO, экшен на сервере, ERP]` — пункт `Balance domains` в меню сервера: каждый домен этого сервера с DNS-провайдером переводится на случайный `Running`-сервер той же `Repoint Group` (сам исходный сервер тоже может выпасть), равномерности нет. **Не путать с `Repoint`** (тот — при падении сервера).
- **Domain Change Handler** `[AIO]` — обработчик шага `Domain Change` на стороне AIO (не агента): визит перенаправляется на `https://<новый домен><тот же путь>` со ссылкой, которая продолжает тот же визит, а новый домен дописывается в путь визита по доменам.
- **Domain string (payload type в шаге `Domain change`)** `[AIO]` — тип payload `Domain string` для шага `Domain change`: вместо домена-объекта вписывается **строка** (`test.com`), плейсхолдеры визита в ней подставляются; ротатор меняет строку. См. также `Parent-Tenant Domain Pool`.
- **Parent-Tenant Domain Pool** `[AIO]` — общий пул доменов между тенантами одного клиента через parent-тенант. В шаге Domain Change можно выбрать payload типа `Domain string` — туда вписывается название домена строкой. Если домен есть в Parent-тенанте (но нет в текущем) — он всё равно корректно применится и будет обрабатывать трафик, несмотря на защиты (сервера/домены одного тенанта работают только с кампаниями этого же тенанта).
- **Domain Checkers** `[AIO, интеграции]` — бесплатные интеграции для доп-проверки доменов: ловят флаги **VirusTotal** и **Google Safe Browsing «Red Screen»**.

- **Last checked / Last checked info** `[AIO, колонки таблицы доменов]` — `Last checked` — когда домен последний раз проверяли чекеры доменов; скрытая по умолчанию `Last checked info` — время последней проверки по каждому типу чекера. Если VirusTotal нашёл хоть один `suspicious` или `malicious`, домен уходит в `Danger` со статусом `<имя чекера> Incident: N Suspicious & M Malicious`, а Monitoring User получает уведомление в Telegram.
- **Tag на домене (для ротации доменов шага `Domain change`)** `[AIO, рабочий приём]` — вешать тег на домены, используемые в шагах `Domain change`, чтобы API-ротация по таблице доменов фильтровала только их.
- **Сервер-мониторинг чат** `[AIO]` — выделенный TG-чат, куда AIO может слать уведомления о перегрузке сервера (высокая загрузка CPU несколько минут подряд).
- **Self-update агента** `[AIO]` — агенты на серверах самообновляются — ручного обновления серверной части не требуется.
- **AIO Agent + Squid (deployment-скрипт)** `[AIO]` — стандартный bash-скрипт deployment, раскатывается при добавлении сервера: ставит **Squid** + **агент** + **сервис обновления**. По образу можно создавать кастомные. **Deployments вкладка** нужна для хранения bash-скриптов. [models/server.md](../models/server.md).
- **AIO-агент = конечный автомат** `[AIO]` — формальное определение: агент на сервере — это finite state machine, работающий по командам AIO: принимает запрос визитёра, на каждом шаге получает от AIO команду (что отдать визитёру, куда вести визит дальше), исполняет её и сообщает AIO о событиях флоу (submit формы, переход по ссылке-шагу). Решения флоу (переходы, фильтрация, сплит-выбор) вычисляет AIO. [models/server.md](../models/server.md).
- **CDN-streaming видео** `[AIO]` — видео с CDN стримится, а не загружается в память агента; перемотка работает (`Range` → `206`); агент отдаёт видео с `Cache-Control: no-store`, поэтому Cloudflare его не кэширует, а агент держит копию файла на диске сервера, если на диске хватает места.

## Трекинг и флоу

- **SEO-трафик** `[общий]` — органический трафик из поисковиков по брендовым запросам. В AIO заводится отдельным `Source`.
- **Direct Traffic** `[AIO]` — трафик, пришедший на голый домен без UTM/source-параметров. Привязывается либо через `Default query` на самом домене, либо централизованно через `Direct Traffic Distribution`. Внутри одного домена можно разделять между кампаниями по `initial_path`.
- **Source / Источник** `[AIO]` — источник трафика (Facebook, Google, Taboola, нативка). Pop-under платформы не поддерживаются.
- **Destination / Дестинейшн** `[AIO]` — конечная интеграция, куда пушится лид (рекламодатель, партнёрка, CRM).
- **Flow / Флоу** `[AIO]` — визуальный конструктор пути визита от Source до Destination. Стандартные шаги: Sources → Filters (AIO Filter, Antifraud) → Lands (Pre-land + Offer) → Destination.

### Flow States (основные типы шагов)

- **Flow States** `[AIO]` — основные типы шагов флоу (есть и другие: `Condition`, `Fill form`, `Fields by distribution`, `Spawn conversion` и др.):
  - **Start** — автоматическое начало флоу.
  - **Source** — точка входа визита.
  - **Content** — шаг с контентом. Имеет атрибуты `Lander Type` (Preland/Offer/White), `Payload Type` (Landing / Html / Redirect / Destination / Reflect / Proxy reflect / Skip / 404 Not found и др.), `Settings availability`, `Collapsed by default` (тумблер есть, `Edit campaign` его не читает), Info message.
  - **Destination** — финальная интеграция. Атрибуты: `Settings availability`, `Collapsed by default`, Info message.
  - **Domain Change** — смена домена между трекинговым и публичным (см. термин `Domain change` ниже).
  - **Fill Fields** — заполнение полей визита по правилам или из Content Library. Атрибуты: Fields, Placeholder Group, Payload Type (`Fill text` / `Fill content` / `Fill destination` / `Skip`), Compact/Control toggle. Невидим визиту.
  - **Filter** — шаг фильтрации трафика: в нём выбирается используемый `Traffic Filter`.
  - **SubFlow** — вставка ранее созданного SubFlow. SubFlow не работает самостоятельно; типичное применение — централизованный Fill Fields (шаги в нём те же, что в кампанийном флоу).
  - **Finish** — конец SubFlow, возврат в основной флоу.

  [models/flow-model.md](../models/flow-model.md).

### Flow Transitions (основные)

- **Flow Transitions** `[AIO]` — основные переходы между шагами флоу (в скобках — подпись в редакторе; ещё есть `Destination Full`, `Handle Form 1…5`, `Handle Link 1…5`; [models/flow-model.md](../models/flow-model.md)):
  - **Arrived** (`Visit Arrived`) — единственный transition из Source. Начало пути визита.
  - **Handle** (`Handle All`) — общий transition между шагами, выстраивающий путь визита.
  - **Handle-form** (`Handle All Forms`) — срабатывает только при submit формы.
  - **Handle-link** (`Handle All Links`) — срабатывает при клике на `{{link}}`; на шаге со `Skip` — сам, сразу при входе визита в шаг.
- **Flow Transitions по исходу шага** `[AIO]` — переходы, которые выбирает результат шага (`Destination`, `Filter` / `Condition`, подбор вариантов):
  - **Destination-rejected** (`Destination Rejected`) — обратный transition от Destination к предыдущему шагу, если Destination отклонил лид. Улучшает аналитику и разделение успешных/отклонённых.
  - **Destination-pushed** — позволяет визиту проходить через несколько Destinations подряд (например, PWA → Destination), для трекинга полного пути.
  - **Destination-interacted** — любой исход (Pushed или Rejected). Используется, когда логика после пуша одинаковая независимо от результата.
  - **Passed** — после Filter (и Condition), если визит прошёл шаг.
  - **Rejected** — после Filter (и Condition), если визит отклонён.
  - У `Filter` и `Condition` **Handle** — запасной выход: ветки нужного исхода (`passed` / `rejected`) нет, а `handle` нарисован — визит уходит по `handle`.
  - **No payload** (`No Payload`) — fallback. Если у шага не осталось вариантов после фильтрации правилами, визит уходит сюда (например, на вайт).

  [models/flow-model.md](../models/flow-model.md).

### Атрибуты Content step

- **Lander Type** `[AIO, атрибут лэнда]` — тип лэнда; **набор типов настраивается** (`Content → Landings ▾ → Manage landing types`), из шаблона приезжают **Preland** (прогрев без формы), **Offer** (с формой), **White** (вайт-фолбэк) во всех вертикалях, плюс `Preland w/ Form` и `Thank-You Page` в Finance и Nutra (в Nutra ещё `VSL`), `Thank-You Page` в Sweeps, `PWA` в iGaming. Это не просто метка, а **набор флагов поведения** (макросы/события/CDN) — см. [models/landing.md](../models/landing.md). Указывается при загрузке лэнда. Используется в Backfix-конфиге (где UUID типа лэнда определяет, должен ли срабатывать Backfix), в Content State флоу (можно ограничить шаг конкретными типами лэндов).
- **Payload Type** `[AIO, атрибут Content state]` — что именно делает Content step с визитом:
  - **Landing** — показ загруженного лэнда: ZIP с `index.html` из `Content → Landings` либо PWA-шка из `Content → PWA` (на шаге выбирается как обычный лэнд).
  - **HTML** — показ HTML-куска, который **пишется прямо в Code Editor на уровне кампании в настройках шага**. Не требует заливки лэнда. Удобно для простых вайтов / 404-замен / временных страниц — HTML пишется inline, без лишних файлов в `Content → Landings`.
  - **Redirect** — переход на стороннюю ссылку.
  - **Reflect / Proxy reflect** — показ стороннего сайта под текущим доменом кампании.
  - **Skip** — пропуск шага (например, чтобы из 2-step сделать 1-step): визит сразу уходит по `Handle-link`, если этот переход у шага есть, иначе по `Handle`.
  - **404 Not found** — отдать визиту страницу 404.
  - **Fill Text / Fill Content** — для Fill Fields step.
- **Settings availability** `[AIO, настройка шага флоу]` — уровень видимости/редактируемости настроек шага при создании кампании. Три варианта:
  - **Campaign template** — настройки берутся из флоу как дефолт, но баер может их менять в кампании.
  - **Campaign only** — настраивается только в кампании (на уровне флоу пропадает).
  - **Flow only** — настраивается только во флоу, в кампании опция скрыта; одна и та же штука применяется ко всем кампаниям этого флоу.

  [models/flow-model.md](../models/flow-model.md).

- **`Collapsed by default` (тумблер в `Visual settings` ноды флоу)** `[AIO, настройка шага флоу]` — переключатель в блоке `Visual settings` формы ноды (есть у шагов, которые показываются в `Edit campaign`), сохраняется в настройках ноды как `is_collapsed`. Интерфейс его не читает: карточки шагов в `Edit campaign` сворачиваются только кликом по шапке карточки, и это состояние хранится в браузере, а не во флоу; на канвасе редактора флоу флаг тоже не используется. Симптом «поставил `Collapsed by default`, а шаг в кампании открыт развёрнутым» — штатное поведение. [models/flow-model.md](../models/flow-model.md).

### Шаги, транзишны, маршрутизация

- **Transition / Транзишн** `[AIO]` — общий термин: переход между шагами флоу (по клику на ссылку / по сабмиту формы / по результату пуша). Полный список — см. блок Flow Transitions выше.
- **Domain change (шаг флоу)** `[AIO]` — дополнительный шаг во флоу для смены домена между трекинговым (тот, что в рекламной кампании) и публичным (тот, под которым открывается лэнд). [models/flow-model.md](../models/flow-model.md).
- **Condition / Кондишен** `[AIO, шаг во флоу]` — условный шаг: проверяет любое поле визита через билдер правил и ветвит флоу на `Passed` / `Rejected`. [models/flow-model.md](../models/flow-model.md); типовое применение после `AIO Antifraud`.
- **Fields by Distribution / Fill Fields by Distribution** `[AIO, шаг во флоу]` — шаг, на котором значения полей визита заполняются из централизованной дистрибуции по правилам (а не вручную в каждой кампании). Самый частый кейс — `Buyer UTM Distribution`: поле визита `buyer_utm` заполняется UTM-меткой баера по правилу `Campaign Owner`. Ставится в начале флоу до фильтра — в ERP-шаблонах она уже заведена и стоит шагом `Fill Buyer UTM` в флоу-примерах (в MTK-шаблонах её нет). Встречаются оба имени — `Fields by Distribution` (короткое) и `Fill Fields by Distribution` (полное); это **один и тот же шаг**. Не путать с типом дистрибуции `Fill Field Distribution` (см. раздел «Источники, трекеры и дистрибуции AIO» этого глоссария).
- **Split Groups / Сплит-группы** `[AIO, маршрутизация во флоу]` — цветные метки на вариантах шагов. Визит получает цвет на первом шаге с выбором — на следующих шагах он попадает только в варианты с тем же цветом. **Цвет визиту записывается на любой ноде-выборщике — `Content`, `Fill fields`, `Fill form`, `Fields by distribution`, `Destination`, `Domain Change`** (первый не-`Rainbow` цветной вариант локает цвет на весь остаток флоу). Пока цвета у визита нет, ему доступны варианты любого цвета; с цветом — только варианты этого цвета и `Rainbow`. Специальный цвет **Rainbow** принимает в себя любые цвета (используется на дестинейшне или там, где нужен «общий» вариант для всех групп). [models/flow-model.md](../models/flow-model.md).
- **Дефолтный флоу** `[AIO, разговорное]` — флоу-пример из шаблона тенанта, на котором сидит кампания-пример. В Finance это `1/2Step | Manual Offer Name` (прилэнд → оффер, оффер-нейм задаётся в кампании) и `1/2Step | Offer Name Distribution` (оффер-нейм из дистрибуции), в Sweeps — `Default 1Step Flow`, в Nutra — `1/2Step | Preland -> Order Page`; варианты с Domain Change есть в Finance (`… + TY + Domain Change`) и Sweeps (`Default 1Step Flow w/ Domain Change`). Полный список по вертикалям — [context/architecture.md](../context/architecture.md).

## Фильтр и антифрод в AIO

- **Traffic Filters** `[AIO]` — раздел `Settings → Traffic filters` (ERP), где подключаются интеграции фильтрации и обогащения трафика. Полная запись — см. ниже `Settings → Traffic filters`.
- **FB-click-id** `[общий]` — параметр клика из рекламной площадки; приезжает в поле визита и доступен в кастомных правилах.
- **AIO Antifraud** `[AIO]` — встроенный антифрод-чекер AIO. Срабатывает во флоу перед пушем в `Destination`: пишет в визит `fraud_score` и `triggered_rules`, сам визит не отсекает.

  **Внешние** интеграции (`IPInfo`, `Emailable`, проверки WhatsApp `2Chat` / `RapidApiWhatsApp` и т.д.) — **не часть AIO Antifraud**, а отдельные `Traffic Filter`-шаги во флоу. **Отдельного `Traffic Filter` для `IPQuality` / `IPQuality Score` в AIO НЕТ** — подключить его отдельной интеграцией нельзя. Отдельный `Traffic Filter`, который дописывает в визит IP-данные, — `IPInfo`.
- **Фрод-скор / fraud_score** `[AIO, поле визита]` — числовое поле визита, которое проставляет модуль `AIO Antifraud`; используется в правилах и `Condition`-шагах флоу.
- **Триггер-рулс / triggered_rules** `[AIO, поле визита]` — поле визита со списком сработавших чеков `AIO Antifraud`. *уточните у поддержки*.
- **Fingerprint** `[AIO, поле визита]` — уникальный отпечаток устройства визита.
- **Visit Status: WAIT / LIVE / LEFT** `[AIO]` — три значения колонки `Status` в `Tracker → Visits` (ERP), связанные **только с записью сессии** (AIO SDK). `WAIT` — доступных событий записи сессии от SDK нет (запись ещё не началась); `LIVE` — последнее событие записи не старше минуты; `LEFT` — последнее событие записи старше минуты (статус считается по давности последнего события, а не по «завершению» сессии). `WAIT` может быть единственным статусом, если ивентов от SDK так и не было — визит не дождался прогрузки JS, либо флоу используется без лендингов. Механика — [mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md).
- **Session flush interval = 10 секунд** `[AIO, SDK]` — запись сессии SDK отправляет пачкой раз в 10 секунд (`persist-session-record`; интервал зашит в макросе записи, досылки при уходе со страницы нет); меньше ~10 сек активности → первая пачка не успела уйти, визит остаётся в `WAIT`. Отдельно `aioExchange.flushInterval` = 10000 — интервал отправки полей визита (первая отправка сразу и при уходе со страницы). Механика — [mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md).
- **Sessions Recorder (AIO SDK)** `[AIO, SDK]` — JS-макрос AIO SDK, который пишет события на лэнде — heatmaps, video sessions, переходы, развитие визита. [mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md).
- **Сроки хранения записей сессий** `[AIO]` — записи сессий (основа scroll/click-карт и сводок) хранятся **7 суток**; запрос глубже по картам молча подтягивается к границе. Список сессий в интерфейсе отсекается более широким порогом — **14 суток**, но это порог интерфейса, а не срок хранения: глубже 7 суток список пуст. [mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md), [how-to/session-analytics.md](../how-to/session-analytics.md).
- **The session is unavailable because it has expired or contains insufficient events.** `[AIO, ошибка]` — сообщение плеера записи сессии: для воспроизведения нужно минимум два события записи (события уходят пачками раз в 10 секунд), а записи старше 7 суток уже удалены. [mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md).
- **options=new-session** `[AIO, дебаг-параметр]` — дебаг-параметр в ссылке — инициирует новую сессию визита при каждом клике. После теста убирать; **не для прод-трафика**. [mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md).
- **Сессия: init / Index Pages / Allowed paths** `[AIO]` — `init` — первое попадание визита/браузера в AIO на домене; AIO выбирает кампанию (UTM / Default query / Direct Traffic Distribution) и подставляет index при отсутствии подпути. `Allowed paths` — набор разрешённых под-путей лэнда; вне набора → `404`. `Index Pages`-логика — при отсутствии подпути возвращает `404` (не редирект), чтобы боты-краулеры не уходили в бесконечный луп. [mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md).
- **Initial Domain (поле визита)** `[AIO]` — с какого домена визит зашёл изначально (до `Domain change`). По нему разбивается нагрузка в метриках/логах.
- **Last Domain / путь визита по доменам** `[AIO, аналитика]` — визит записывает путь по доменам: начальный домен при регистрации плюс каждый новый домен шага `Domain Change` (повтор того же домена подряд не дописывается). Группер `Last Domain` (категория `Browser`, ключ `last_domain`) — последний домен пути, без `Domain Change` — начальный; позиционная серия `Domain` разбивает по первым трём позициям (`Domain #1` — начальный домен, ключи `domains[1..3]`); в ERP весь путь — колонка `Domains` в `Tracker → Visits` (скрыта по умолчанию). У старых визитов путь не записан. (разг.: «последний домен», «куда увёл Domain Change»). [mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md).
- **Launcher (поле визита)** `[AIO]` — UUID юзера, который сгенерировал ссылку и запускал трафик. Отличается от `Owner` (владелец кампании). В Pivot Report ключ `field_launcher` из старого каталога не работает — поле визита берут ключом `string_fields[<uuid поля>]` ([how-to/api.md](../how-to/api.md)).
- **Поля визита на стадии голого захода (initial_path и др.)** `[AIO]` — на моменте, когда визит приходит на голый домен без всего, доступны поля: `IP`, `city`, `country code`, ASN-организация (`asn_organization`), домен и `initial_path`. На них строятся правила Direct Traffic Distribution.
- **Antifraud Points / `Check Antifraud Points` (Condition-шаг)** `[AIO]` — `Condition`-шаг после `AIO Antifraud` в флоу-примерах Finance, Nutra и Sweeps; в шаблоне его условие `fraud_score < 999` пропускает всё, порог задаётся под себя.
- **Rainbow Split Group** `[AIO]` — спец-значение Split Group, **принимающее любой цвет**: вариант с `Rainbow` доступен визиту любого цвета наравне с вариантами его цвета и сам цвет визиту не записывает.
- **Trash reason** `[AIO, поле визита]` — поле визита с причиной, по которой ему проставлен `is_trash`. Поле живёт в отдельной таблице Trash (см. ниже `Trash / Trash Visits` в разделе «Аналитика»).
- **Emailable** `[AIO, интеграция]` — внешний email-чекер, подключается как `Traffic Filter`.
- **Проверка WhatsApp (`2Chat`, `RapidApiWhatsApp`, `RapidApiWhatsApp2`)** `[AIO, интеграция]` — внешние чекеры номера телефона, подключаются как `Traffic Filter`; ответ пишется в поле визита, выбранное в настройке `On WhatsApp`. (разг.: «WhatsAppCheck», «WaCheck») *уточните у поддержки*.
- **Traffic Filter** `[AIO]` — **единая сущность** в продукте для всех интеграций фильтрации/обогащения трафика. Подключается в `Settings → Traffic filters` и используется как шаг во флоу. Примеры: `IPInfo`, `Emailable`, `RapidApiWhatsApp` (проверка номера в WhatsApp — WhatsAppCheck), `AIO Filter`, `AIO Filter Service`, а также сторонние сервисы фильтрации и скоринга (набор доступных — в дропдауне `Integration type`). Генераторы сайтов и креативов — не `Traffic Filter`, а `Generator` в `Settings → Generators`.
- **`Traffic Enrichment` (условный ярлык, не отдельная сущность)** `[AIO]` — **не отдельный тип в продукте**, а условное название use-case'а, когда `Traffic Filter` дозаполняет поля визита. Технически — обычный `Traffic Filter`. *уточните у поддержки*.
- **Settings → Traffic filters** `[AIO, раздел UI]` — раздел, где подключаются все интеграции `Traffic Filter`. *уточните у поддержки*.
- **landing fingerprint** `[AIO, SDK]` — данные о визите, которые SDK скидывает батчем при первом заходе на лэнд: `timezone`, `landed`, скроллинги, разрешение экрана, landing fingerprint.
- **landing JS check** `[AIO]` — флаг, отправляемый в AIO при успешной прогрузке лэнда и работе JS. Индикатор для `Qualified Visits` / `Visit Loss`.

## Контент и лэндинги AIO

### Структура раздела Content

- **Content section (вкладки)** `[AIO]` — раздел Content имеет 8 вкладок: **Landings**, **PWA**, **Creatives**, **Generations**, **Content Library**, **Macros**, **Uploaded Files**, **CDN files**.
  - **Landings** — лэнды с метаданными (UUID, Tags, Type, Templates); только лэнды режима `Editor`.
  - **PWA** — PWA-шки, лэнды режимов `PWA` (PWA Builder) и `Custom PWA` (свой ZIP в PWA-шелле); отдельная страница рядом с `Landings` (в MTK — страница `PWA` платного модуля `PWA + Push`). [how-to/pwa.md](../how-to/pwa.md).
  - **Creatives** — медиатека рекламных креативов: картинки и видео, обработка файлов, кадрирование и видеоредактор (только ERP), см. `Creatives` ниже.
  - **Generations** — генерации лэндингов и креативов через AI-провайдеров (только ERP), см. `Generation` ниже.
  - **Content Library** — типизированные объекты с custom structure (см. ниже).
  - **Macros** — макросы тенанта (см. ниже).
  - **Uploaded Files** — личные файлы юзера (видит только свои).
  - **CDN files** — файлы на CDN (CSS, HTML, JS — редактируемы; остальное только просмотр).
- **Creatives** `[AIO, вкладка в Content]` — медиатека рекламных креативов (только ERP): креатив — одна идея с главным файлом и вариациями (картинки и видео до 1 GB). AIO сам обрабатывает файлы (постер, превью, MP4 H.264), есть `Make main`, `Set poster`, `Crop video` и `Video editor`; файлы креатива открывает экшен `Show creative items`. На лэнды и в кампании креативы не подставляются, но статистику по визитам собирают: UUID креатива передают параметром `creative_uuid` во входной ссылке (один или несколько через запятую), и аналитика разбивает визиты по креативам разрезом `Creative #1`…`Creative #3`. (разг.: «крео», «медиатека», «залить видео», «стата по крео»). [how-to/creatives.md](../how-to/creatives.md).
- **Uploaded Files** `[AIO, вкладка в Content]` — личные файлы пользователя. Каждый юзер видит только свои загрузки.
- **Generation / Генерация** `[AIO, сущность]` — один запуск генератора из AIO на странице `Content → Generations` (только ERP): тип `Landing` отдаёт готовый сайт ZIP-архивом, тип `Creative` — статичные картинки для рекламы. Запускается через подключение `Generator`, идёт асинхронно со статусами `Pending` / `Processing` / `Fine` / `Issues` / `Canceled` и одним уведомлением на каждый запуск (`Generate` или `Retry`); готовый сайт становится лэндом через пункт `Create landing`. Права — `content.generations.*`. (разг.: «сгенерировать лэндинг», «AI-генерация лендинга», «нагенерить креатив»). [how-to/generations.md](../how-to/generations.md).

### Лэнды и редактор

- **Manage landing** `[AIO]` — визуальный редактор лэндов. Без верстальщика правишь текст/визуал/структуру. 4 режима редактора:
  - **Code** — HTML-код.
  - **Visual** — визуальный редактор: выделение кликом, правка текста на месте, настройки вида, вставка блоков; есть в ERP и MTK ([how-to/landing-visual-editor.md](../how-to/landing-visual-editor.md)).
  - **Split** — два пана: код + визуал side-by-side.
  - **Full preview** — превью без редактирования.
- **Content settings (левая колонка Manage landing)** `[AIO]` — поля схемы `Lander type` лэнда; есть в обоих билдах ([how-to/landings.md](../how-to/landings.md)).
- **Comments / Комментарии** `[AIO]` — обсуждение кампании или лэнда (в т.ч. PWA) прямо в AIO: упоминания `@`, ответы, реакции, вложения; заменили заметки (`Notes`) лэнда. Открываются иконкой в строке таблицы, в шапке окна объекта и лентой `All comments`; право `Features: notes`, ERP и MTK. Не путать с блоком отзывов `Comments` в PWA Builder ([how-to/pwa.md](../how-to/pwa.md)). [how-to/comments.md](../how-to/comments.md). (разг.: «заметки», «notes», «упомянуть коллегу», «@mention»)

### Content Splits / LP-сплиты на лэнде

- **Content splits (правая колонка Manage landing)** `[AIO]` — правая колонка в Manage landing для управления Content Splits (LP-сплитами). Внутри: `+Create Split`, `Control` (выбор стратегии: Conversions AI / Weights / First), `Conversion` field (на какую конверсию оптимизироваться или `Any Conversion by business value`).
- **A/B тестирование (Split) / LP-сплиты** `[AIO]` — функция сплитирования контента на лэнде. Пишешь Split Key (например `cta`), добавляешь варианты, выставляешь вес и правила показа по любой переменной из клика. Варианты конкретного элемента лэнда (заголовок, изображение, любой HTML), управляемые на уровне кампании. Создаются на лэнде через выпадающее меню справа, типы: text / image / HTML. Дают байеру возможность тестировать варианты, не имея доступа к самому лэнду.
- **Color Groups (в Content Splits)** `[AIO]` — связывают сплиты между разными элементами лэнда. Если один сплит выбрал «зелёный» вариант, другой сплит с той же color group тоже покажет «зелёный». Аналог Split Groups на уровне Flow, но для контента лэнда.
- **MVT (Multivariate Testing)** `[AIO]` — мультивариативное тестирование. Алгоритм оптимизации Томпсона. Не отключает остальные варианты — ретестирует на новой аудитории. Метрики на элементе:
  1. Показ
  2. Reward (целевая конверсия)
  3. Эффективность (% из показа в конверсию)

### Аналитика и инструменты лэнда

- **Heatmaps** `[AIO]` — тепловые карты. Красная зона = наибольший интерес, синяя = где интерес пропадает. Облачное решение, без редиректа — работают на любом лэнде, где включена запись сессий SDK (`sessionRecords`). Смотреть — только в ERP: вкладка `Heatmap` лэнда (право `Features: heatmaps`) и `Analytics → Session Analytics`; все входы — [how-to/landings.md](../how-to/landings.md).
- **Video Sessions** `[AIO]` — видеозаписи сессий. Каждое действие на лэндинге. Смотреть — только в ERP.
- **Глобальные макросы** `[AIO]` — пиксели и кастомные куски кода, применяемые ко всем лэндам тенанта сразу (встают в `{{aio}}` / `{{aio:head}}`) (см. также `Macros`).
- **Загрузка лэнда** `[AIO]` — поддерживается ZIP-файл. **Корнем лэнда становится папка самого неглубокого `index.html` в архиве**, на любой глубине: обёртывающая папка («папка-в-папке») загрузку не ломает. Не загружается всё, что лежит выше папки с этим `index.html` или в соседних с ней папках. Ошибка `no index.html` — в архиве нет ни одного файла с точным именем `index.html`. Папка `__MACOSX` игнорируется. Альтернатива — создать PWA прямо в системе. При загрузке указывается `Lander template` (по дефолту `Simple`), Lander Type, опциональные Country и Language. [how-to/landings.md](../how-to/landings.md).
- **Lander Template** `[AIO]` — обёртка над лэндом, в которую можно вынести общие элементы (например, header / footer для серии новостных лэндов). По дефолту все лэнды используют шаблон `Simple` — пустую обёртку.
- **Sub-pages / Подстраницы** `[AIO]` — дополнительные `.html` файлы в архиве лэнда (кроме `index.html`). Доступны в редакторе через выпадающее меню Pages. Можно использовать для разных языковых версий или встроенной спасибки. **Возврат на главную страницу** — через корневой путь `href="/"` (возврат на index = пустой путь `""`). [how-to/landings.md](../how-to/landings.md).
- **Категоризация лэндов** `[AIO, рабочий приём]` — лэндам можно задавать страну/гео и язык, после чего фильтровать по тегам/гео в интерфейсе. Альтернатива папкам под разные истории/гео. Сразу важно: эта категоризация **не влияет на доступ трафика** к лэнду — это просто метаданные для скриптов и поиска.
- **Процессинг лэнда** `[AIO]` — обработка ZIP-архива при загрузке: AIO заменяет href-ы на CDN-пути и, если у типа лэнда включён `Auto place AIO macros?`, добавляет `{{aio:head}}` в `<head>` и `{{aio}}` перед `</body>`. Лэнд доступен мгновенно отовсюду — CDN решает географию. [models/landing.md](../models/landing.md).
- **Download Landing** `[AIO, действие]` — экшен по правой кнопке мыши на лэнде: собирает архив асинхронно, готовые ссылки приходят уведомлением в колокольчик — `Original upload` (изначально загруженный архив, без правок) и `Merged export` (с правками из редактора AIO). Ссылка живёт 7 дней. Механика уведомления — [mechanics/notification-center.md](../mechanics/notification-center.md), процедура — [how-to/landings.md](../how-to/landings.md).
- **CDN files** `[AIO]` — отдельная вкладка лэнда со всеми файлами, загруженными на CDN из архива. CSS/HTML/JS редактируемы; остальные форматы только на просмотр. Файл `index.html` здесь показан как **`<secret>.index.html`** (секрет лэнда, не его UUID) — это **оригинальный** index из архива, AIO его не трогает. **Визит этот файл НЕ открывает** — визиту отдаётся обработанный (processed) `index.html` из редактора `Manage landing → Code`. JS/CSS при этом не дублируются; в CSS / JS / JSON при загрузке заменяется только плейсхолдер `{{cdn}}`, остальная обработка — у HTML-файлов (index и подстраницы). *уточните у поддержки*.
- **Landing Quick Preview / Embed Preview** `[AIO, экшен]` — быстрый preview лэнда без открытия новой вкладки. Доступен:
  - В `Content → Landings` через иконку «глаз» или action `Embed Preview`;
  - В `Tracker → Campaigns` при наведении на лэнд внутри Content step;
  - В `Analytics → Roll Up report / Campaigns` через групёры с лэндами.

  Ссылка превью открывается только под активной сессией AIO: в инкогнито или у человека без доступа к рабочему пространству она отдаёт `404` вместо страницы лэнда. Показать лэнд снаружи через неё не выйдет — [how-to/landings.md](../how-to/landings.md).
- **Dummy Destination** `[AIO, мок]` — встроенный «дестинейшн» для тестов. Существует **два варианта**: `DummyApi` — фейк-API (в режиме `Push` отдаёт `success` + фейковый id лида + автологин на `google.com`); `DummyRedirect` — то же для redirect-интеграции. Режим задаёт настройка `Mode`: `Push` (все пуши успешны) / `Reject` (все пуши реджектятся). Удобно при настройке нового лэнда — прогнать форму, убедиться что она пушится, без отправки тестов в реальную партнёрку. В шаблонах Finance, Nutra и Sweeps дестинейшен-пример на `DummyApi` уже заведён (`Dummy API [ DEBUG ]`, `Dummy API - Flow Testing`, `Dummy API`); в iGaming его нет — там все дестинейшены-примеры `Simple Redirect`.

### Плейсхолдеры и макросы

- **Плейсхолдер `{{link}}`** `[AIO, плейсхолдер]` — placeholder для ссылки, ведущей на следующий шаг во флоу. На прилэнде — обычно на оффер, на оффере — в дестинейшн (или на любой другой шаг, если так настроено в Flow). Ставится значением атрибута `href` (`<a href="{{link}}">`) вместо статичного URL исходного лэнда — не заменяет сам тег `<a href>`, а подставляется внутрь него. Доп. параметров не нужно — AIO сам разруливает, куда вести по текущему флоу.
- **Плейсхолдер `{{form}}`** `[AIO, плейсхолдер]` — placeholder, в который подгружается AIO SDK-форма. Заменяет статичную HTML-форму. Привязка конкретной формы к кампании — через шаг флоу `Fill Form` либо через выбор формы в `Content` шаге флоу (`Settings → Forms` создаёт форму, `Tracker → Flows → Content` или `Fill Form` её выбирает). Пронумерованные формы `{{form:1}}`, `{{form:2}}` (до 5) поднимают отдельные транзишны флоу: `Handle Form 1`, `Handle Form 2`, 3, 4, 5, плюс `Handle All Forms` (пронумерованные формы работают, только если на странице есть и обычный `{{form}}`) — тот же паттерн, что у `{{link:N}}`. Как альтернатива, несколько плейсхолдеров `{{form}}` рендерят одну и ту же форму в разных местах лэнда (одна форма, несколько точек отображения).
- **AIO Head / AIO Body** `[AIO, плейсхолдеры]` — два служебных плейсхолдера, которые AIO автоматически добавляет в загруженный ZIP-лэнд при процессинге, если у типа лэнда включён `Auto place AIO macros?`:
  - `{{aio:head}}` — ставится в конец `<head>` лэнда; в него встают объект визита `window.aio` и глобальные макросы с `Prefer placement` = `Head`.
  - `{{aio}}` — ставится перед `</body>`; в него встают глобальные макросы с `Prefer placement` = `Footer` (по умолчанию), включая `AIO SDK Macros Collection`, а без `{{aio:head}}` на странице — и `window.aio` с `Head`-макросами.
- **Плейсхолдеры `{{cdn}}` / `{{cdn-lp-folder}}`** `[AIO, плейсхолдеры]` — два плейсхолдера для путей к файлам лэнда:
  - `{{cdn}}` — обрабатывается на этапе процессинга при загрузке ZIP, в CSS / JS / JSON заменяется на путь к папке лэнда через `/_cdn` текущего домена (в HTML — на адрес папки лэнда на CDN). Используется внутри JS / CSS файлов, когда из скрипта или стиля нужна ссылка на файл на CDN (например, `{{cdn}}/assets/image.png`).
  - `{{cdn-lp-folder}}` — подставляется AIO при отдаче HTML визиту (на сервере, не в браузере); работает в HTML лэнда — `index.html` и подстраницах. Используется внутри inline-скриптов прямо в `index.html`, которые сами обращаются к файлам и не должны вшивать конкретный путь.
  - Нужны только тогда, когда вызовы изображений / скриптов идут изнутри JS / CSS / inline-script'ов (в обычном HTML/CSS пути обрабатываются автоматически).
- **Macros** `[AIO, вкладка в Content]` — вкладка `Content → Macros` (в MTK — `Settings → Macros`), в которой лежат все макросы тенанта — куски HTML/JS, которые AIO вставляет в лэнд при отдаче (как написать свой — [how-to/macros.md](../how-to/macros.md)): и шаблонные (`AIO SDK Macros Collection` — конфиг SDK, `AIO Non-SDK Form Handler` и др.), и кастомные. У каждого макроса:
  - **Active** — включён/выключен.
  - **Global** — глобальный (AIO сам вставляет его в `{{aio}}` / `{{aio:head}}` на каждом лэнде тенанта) или локальный (вызывается на лэнде через `{{aio:macros:<slug>}}`).
  - **Prefer placement** — `Head` (глобальный макрос встаёт в `{{aio:head}}`, а без него на странице — в `{{aio}}`) или `Footer` (в `{{aio}}`, по умолчанию).
  - **Slug** — используется в локальном вызове.
- **AIO SDK Macros Collection** `[AIO, шаблонный макрос]` — главный шаблонный макрос из коробки, лежит в `Content → Macros`. Содержит JS-конфиг SDK: блок `features` (флаги фич) + блоки настроек для каждой включённой фичи (`backFix`, `form` и т.п.). Технически — обычный макрос в блоке `Macros`, просто с дефолтным содержимым. В шаблонах в `features` включены `landed`, `timeOnLandings`, `scrolling`, `windowDimensions`, `browserTimezone`, `sessionRecords`, `fingerprint`, `modal`, `hueChanger`, `backFix`, `fbPixel`, `fbCapi`, `form` (в iGaming и MTK Sweeps — ещё `pwa`); выключены `ttPixel`, `ttCapi`, `reverseIntegration`. При тонкой настройке (расширить Backfix, привязать `Push Subscribe Toggle`, добавить `beforeSubmitPromise` и т.п.) правки идут именно в этом макросе.
- **Backfix (конфиг)** `[AIO, SDK]` — внутри `AIO SDK Macros Collection`, блок `backFix: {...}`. Под-настройки:
  - `enabledBackFix: () => [...].includes(aio.landing.lander_type_uuid)` — функция-условие. Обычно проверяет, что текущий лэнд — preland (по UUID типа лэнда).
  - `enableStrangeUrlParameters: true` — на лэнде с включённым Backfix заменяет CUUID / SUUID в адресной строке набором случайных UTM-параметров, чтобы из расшаренной ссылки нельзя было достать параметры кампании.
  - `pathName`, `localStorageKey` — служебные.
  - `link: '{{link}}&backfix=true'` — куда уходит визит при срабатывании Backfix, с пометкой `backfix=true`.
  - У визитов, пришедших через Backfix, в `Tracker → Visits` отмечена колонка `Back fix` (категория `Forced steps`); в фильтрах аналитики — `Is Backfix`.

  [reference/sdk.md](sdk.md).
- **EnableStrangeURLParameters** `[AIO, фича SDK]` — под-настройка `backFix`. Если включена — на лэнде, где включён Backfix (`enabledBackFix`), параметры в адресной строке визита (CUUID / SUUID и др.) заменяются набором UTM-параметров со случайными значениями (`utm_id`, `utm_medium`, `utm_campaign`, `utm_content` и др.); набор запоминается в браузере и одинаков на следующих лэндах. Защита от шаринга ссылки: исходные параметры кампании из скопированного URL не достать.
- **landed** `[AIO, фича SDK]` — boolean-фича, фиксирует, что визит реально загрузил лэнд (используется в метрике `Qualified Visits`).
- **windowDimensions** `[AIO, фича SDK]` — записывает размеры окна визита (ширина/высота).
- **Static Language Country (макрос)** `[AIO]` — макрос `AIO Static Language Country for Form`, который фиксирует язык и страну SDK-формы по **лэнду**, а не по визиту (без него — берёт из браузера/гео визита; ломается под VPN). В шаблонах Finance, Nutra и Sweeps заведён **локальным** и вставлен в лэнды-примеры с формой; можно переключить в глобальный, чтобы действовал на все лэнды. [reference/sdk.md](sdk.md).

### Формы — конфигурация и макросы

- **Form Behavior settings (`config.form`)** `[AIO, SDK]` — дефолтная конфигурация формы (можно переопределить через `window.aioBus.push({type:"config", config:{form:{...}}})`):
  - `url`, `selector`, `defaultCss`
  - `successTimeoutSeconds` (по дефолту 5)
  - `language` (по дефолту `navigator.language.slice(0,2)`)
  - `defaultCountryCode` (по дефолту `GB`)
  - `stepsShowing`, `collectDataEvent` (`blur`)
  - `rejectedMessage` (по дефолту «We cant register you at this time.»)
  - `beforeSubmitPromise`, `submitPromises` (хуки SDK-формы)
  - `intlParameters` (для intl-tel-input — `nationalMode`, `autoPlaceholder`)
  - `templates` (HTML-шаблоны для каждого типа поля)
- **Non-SDK Form Handler / AIO Non-SDK Form Handler** `[AIO, макрос-фолбэк]` — макрос в `Content → Macros` для лэндов, где нужно оставить родную HTML-форму вместо SDK-формы. Подкручивает обработку сабмита, чтобы лид всё равно ушёл по флоу AIO. Вызывается на лэнде через `{{aio:macros:aio_nonsdk_form_handler}}` (слаг `aio_nonsdk_form_handler` во всех шаблонах, где он есть — Finance, Nutra, Sweeps; в iGaming макроса нет), ставится после закрывающего `{{aio}}`. Требует, чтобы slug-и инпутов кастомной формы совпадали с AIO-слагами: `first_name`, `last_name`, `email`, `phone`. Активно НЕ развивается, новые фичи не приезжают — использовать только в крайнем случае.
- **BeforeSubmit Promise** `[AIO, хук SDK-формы]` — асинхронный JS-хук: «форму проверили валидацией, но ещё не запушили в дестинейшн». Позволяет вставить дополнительную логику до пуша (например, проверку, показ модалки).
- **Submit Promise** `[AIO, хук SDK-формы]` — асинхронный JS-хук вокруг самого пуша в дестинейшн: можно отслеживать момент отправки и обработки ответа, переключать модалки по результату.
- **Pushing modal / Countdown** `[AIO, UX SDK-формы]` — модалка «идёт отправка» с обратным отсчётом; собирается хуком `submitPromises`, длительность задаётся в самом хуке. Если ответ не пришёл — модалка переключается на «обнови страничку / попробуй ещё». При успешном пуше — на success-модалку с редиректом на автологин-ссылку (её countdown — `form.successTimeoutSeconds`, дефолт 5 c).

### Формы — Form Builder и SDK-форма

- **SDK-форма** `[AIO]` — форма на оффере, подгружаемая из AIO-SDK (а не вшитый HTML на стороне клиента). Управляется через `Form Builder`. Отображение формы и пуш данных в интеграцию — на стороне AIO, на лэнде форма не «светится».
- **HTML-форма** `[общий]` — обычная HTML/JS-форма, прописанная прямо в коде лэнда. Основной путь AIO — `SDK-форма`; родная HTML-форма остаётся как третий путь через макрос `AIO Non-SDK Form Handler` — в шаблонах Finance, Nutra и Sweeps под него есть лэнд-пример (`… Custom HTML Form`), в Nutra и Sweeps — ещё и кампания-пример.
- **Form Builder / Билдер форм** `[AIO]` — UI настройки SDK-форм в `Settings → Forms`. Две вкладки — `Settings` и `Preview`; в `Settings` слева блок `Info`, справа режимы `Controls` / `Steps` / `Layouts` / `Languages`:
  - **Info** — имя, описание, цвет, иконка, `Base language`.
  - **Controls** — типы полей: text, email, phone, textarea, checkbox, select, submit, date, number; правила: required, minlength, maxlength, pattern.
  - **Steps** — массив массивов, порядок и группировка полей на шагах.
  - **Layouts** — визуальное расположение, поля на одной строке или разных.
  - **Languages** — мульти-язычные переводы: `Label` / `Placeholder`, варианты `Drop list` и строки кнопки Submit; один `Base language` + N дополнительных. Языки добавляются из диалога с двумя сегментами — `Auto-translated` (55 языков, приезжают с префилом) и `All languages` (справочник 186 языков, приезжает пустым).
  - **Preview** — превью формы на разных устройствах.

  [models/form.md](../models/form.md).
- **Controls** `[AIO, форма]` — input-элементы формы. Атрибуты: `key`, `placeholder`, `label`, `value`, `type` (text/email/phone/select/textarea/checkbox/submit/date/number), `rules` (required, minlength:X, maxlength:Y, pattern, type:url, type:number, pattern:no-local-emails).
- **Steps (форма)** `[AIO, форма]` — массив массивов: каждый внутренний массив — один шаг формы.
- **Layouts (форма)** `[AIO, форма]` — массив массивов: внутри одного массива поля идут side-by-side, между массивами — на новой строке.
- **Languages (форма)** `[AIO, форма]` — мульти-язычные переводы `Label` / `Placeholder`, вариантов поля `Drop list` и строк кнопки Submit; у `Tooltip` перевода нет. Один `Base language` + N дополнительных; форма авто-переключается по языку браузера визита. Языки добавляются из диалога с двумя сегментами: `Auto-translated` (55 языков) и `All languages` (справочник 186 языков) — префил определяет выбранный сегмент: из `Auto-translated` язык приходит частично заполненным, из `All languages` — пустым. Авто-перевод заполняет подпись и плейсхолдер только у контролов с ключом `first_name` / `last_name` / `email` / `phone`, смапленных на поле визита, плюс четыре строки кнопки Submit; кастомные контролы и варианты `Drop list` остаются пустыми. Непереведённая строка уже добавленного языка рендерится на лэнде **пустой** — фолбэка на английский нет. [how-to/forms.md](../how-to/forms.md).
- **CSS-переменные `--aio-sdk-form-*`** `[AIO, SDK-форма]` — кастомизация стилей формы через CSS-переменные, оверрайдятся в `<style>` блоке на лэнде или глобально через `AIO SDK Macros Collection`. Основные: `--aio-sdk-form-padding`, `--aio-sdk-input-bg/border/color/...`, `--aio-sdk-submit-bg/color/...`, `--aio-sdk-form-step-*`.

### SDK и aioBus

- **window.aioBus** `[AIO, SDK]` — глобальный массив-очередь команд для SDK. Через `window.aioBus.push({type, ...})` SDK получает команды:
  - `type: "config"` — конфигурация фич и формы (`features: {...}`, `form: {...}`, `backFix: {...}`).
  - `type: "trigger"` — заполнить визит-поле значением (`{type:"trigger", key:"...", value:"..."}`).
  - `type: "conversion"` — отправить конверсию (`{type:"conversion", type_uuid:"...", query:{revenue: 10}}`).
  - `type: "form-controls"` — заполнить controls формы.
  - `type: "vue-data-object"` — объявить data для Vue.js.
  - Используется как глобально (в `AIO SDK Macros Collection`), так и локально на лэнде (после `{{aio}}`).
- **Vue.js (на лэндах AIO)** `[AIO]` — кастомизация лэндов через Vue.js: `id="vue"` на корневом элементе включает Vue, плейсхолдеры доступны как `{{vue.aio.visit.<...>}}`. Работают директивы Vue 3 — например `v-if`, `v-else-if`, `v-else`, `v-for`, `@click`. Объекты для шаблонов объявляются через `window.aioBus.push({type:"vue-data-object", data:{...}})`. Используется для динамических переводов / условного рендера / списков.

### Content Library и поля визита

- **Content Library** `[AIO, вкладка в Content]` — хранилище объектов с настраиваемой структурой и атрибутами. Используется для оффер-неймов (с `For Visitor` / `For Advertiser`), для контент-персон (FirstName / LastName / FullName / image / GIF / Title / Description), для пикселей+токенов и т.п. Также **сюда кладётся `Showcase Site`** (массив `Showcase Item`-ов; *уточните у поддержки*); из управления самим объектом задаются только сторона/язык/название, остальное — атрибуты ноды. Объекты можно группировать по папкам.
- **Content Library → Edit structure** `[AIO, экшен]` — изменение структуры Content Type (атрибуты, поля, ключи).
- **Content Library → Manage data → + Content item** `[AIO, экшен]` — добавление конкретных Content Items внутри Content Type. Создаются с именем, заполняются поля из Edit Structure, выбираются Countries/Languages, Lander Placeholder Group, опционально — изображение.
- **Placeholder Group / Lander Placeholder Group** `[AIO]` — это сам Content Type в Content Library: у Content Item поле `Lander placeholder group` указывает, к какому типу он относится, а в шаге `Fill Fields` поле `Placeholder group` выбирает, из какого типа брать значения.
- **Key (в Content Type)** `[AIO]` — slug, используемый для формирования плейсхолдера на лэнде. Если у Content Type, привязанного к полю `offer_name`, создан key `for_visitor`, на лэнде доступен плейсхолдер `{{aio.visit.fields.offer_name.for_visitor}}` — он динамически вставляет значение из соответствующего Content Item. Частный случай для оффер-нейма: на лэнде используется `{{aio.visit.fields.offer_name.for_visitor}}` (For Visitor), при пуше в интеграцию — `for_advertiser` (For Advertiser).
- **`lp_header` / `lp_subheader` / `lp_header_image` (LP Split Content)** `[AIO, специальные поля визита]` — поля формата `Variant` группы `LP Split Content` из шаблона тенанта: в Finance, Nutra и Sweeps — `lp_header`, `lp_subheader`, `lp_header_image` (в Sweeps ещё `lp_split_price` — формата `String`), в iGaming — `lp_header`, `lp_image`, `lp_description`. Если `slug` сплита совпадает с одним из этих ключей, выбранный вариант записывается в это поле визита — и можно сводить аналитику разбивкой по нему (пресеты `LP splits [Campaign → …]` в шаблоне на этом и построены). При нехватке полей добавляются через `Settings → Fields`.
- **LP Variants Field** `[AIO]` — поле визита, slug которого совпадает с ключом сплита лэнда; в шаблонах это поля `lp_*` формата `Variant` группы `LP Split Content` (сам префикс не обязателен). Если slug сплита совпадает с slug-ом такого поля (`lp_header`, например) — выбранный вариант записывается в поле визита, и аналитику можно сводить разбивкой по этому полю.
- **Slug (в сплитах лэнда)** `[AIO]` — ключ сплита, должен совпадать со slug-ом `LP Variants Field` (например, `lp_header`). Тогда выбранный сплитом вариант записывается в поле визита, и аналитику можно сводить разбивкой по этому полю.
- **Showcase — паттерн, не отдельная фича** `[AIO]` — витрина-showcase собирается из существующих механик, отдельной фичи «Showcase» в продукте нет. `Showcase Site`, `Showcase Item`, `Link to Campaign`, `Vue Showcase Site`, `Type Block ID` — **НЕ отдельные термины/фичи AIO**, а произвольные имена объектов и атрибутов.
- **Showcase Send / Showcase Catch + Sessions per Domain** `[AIO]` — имена кампаний в двух-кампанийной схеме витрины. **Sessions per Domain** — в рамках одного домена визит может иметь только одну активную сессию (один State).
- **aio.visit.query** `[AIO, поле визита + плейсхолдер]` — поле визита со всеми параметрами ссылки, с которыми пришёл визит (захватываются при создании визита). В шаблонах: `{{aio.visit.query.<key>}}` — один параметр, `{{aio.visit.query}}` — все параметры одним JSON-объектом (не строкой `a=1&b=2`). В JS лэнда (`window.aio`) `aio.visit.query` — **строка**, поэтому `aio.visit.query.<key>` в JS даёт `undefined`: параметр в код лэнда подставляют плейсхолдером `{{aio.visit.query.<key>}}`. **Не зависит от** `enableStrangeUrlParameters` — содержит исходный набор даже при скрытых параметрах. Подробно — [reference/placeholders.md](placeholders.md).
- **Lander Templates** `[AIO]` — HTML-обёртка лэнда: шаблон выбирают у лэнда (один на лэнд) и меняют, не перезаливая сам лэнд. Дефолт — `Simple`.
- **Subpage Path (множественные пути)** `[AIO]` — поле `Path` в карточке подстраницы лэнда может содержать **несколько путей через запятую**. Подстраница отдаётся по любому из них.
- **Original / Merged HTML — деталь** `[AIO]` — в `Merged export` HTML-файлы лэнда (`index.html` и подстраницы) — текущая версия из редактора AIO: пути на CDN возвращены в относительные `./`, `{{aio:head}}` убран, `{{aio}}` остаётся; исходные HTML лежат рядом с суффиксом `_zip_original`. Остальные файлы берутся с CDN как есть. `Original upload` — исходный архив без правок.
- **Full CDN used / Temp CDN used** `[AIO, опции Landing Type]` — два флага типа лэнда, относящиеся к раздаче файлов лэнда. `Full CDN used` — неиспользуемая заготовка: читателей в рантайме у неё нет, на отдачу лэнда она не влияет. `Temp CDN used` влияет на то, как раздаются файлы лэнда.

- **Reflect vs Proxy Reflect** `[AIO, payload-типы Content / White шага]` — два payload-типа для показа стороннего сайта под текущим доменом кампании: `Reflect` (облегчённый) и `Proxy Reflect` (полное проксирование через агент).
- **Отдельный домен под лэнды (при Domain Change)** `[AIO]` — отдельный публичный домен, под которым после прохода фильтра открывается лэнд — в противовес tracking-домену залива. Появляется только если во флоу есть шаг Domain Change.
- **Спасибка как Flow only-шаг** `[AIO, паттерн]` — Content step с `Payload Type: Landing` и режимом `Flow only` как «динамическая спасибка», видная только во флоу, не торчит в кампаниях.
- **More variants / Variants (AI-варианты для сплита)** `[AIO]` — `More variants` в текстовом сплите: AI пишет до 5 новых вариантов по текущим, выбранные добавляются в сплит; `Variants` в визуальном редакторе сразу превращает выделенный блок в контент-сплит. Только ERP. [how-to/landing-visual-editor.md](../how-to/landing-visual-editor.md), [how-to/landings.md](../how-to/landings.md).
- **LP splits (campaign-level блок)** `[AIO]` — блок `Used splits:` в шаге кампании, появляется **только если на лэнде в payload настроены сплиты**. Режим `Landing` берёт варианты лэнда, `Campaign` — варианты, заданные только для этой кампании (своих нет — варианты лэнда). Правка — в окне `Landing splits` (бывшее `Personal MVT`), право `tracker.campaigns.edit.landing-splits`. [how-to/landings.md](../how-to/landings.md).
- **Split Group field (split groups MT)** `[AIO, поле визита]` — поле визита, в котором хранится сплит-группа (цвет). По дефолту визит приходит без сплит-группы. Цвет пишет любая нода-выборщик — **Content**, **Fill fields**, **Fill form**, **Fields by distribution**, **Destination**, **Domain Change** — первым не-`Rainbow` вариантом (см. также [models/flow-model.md](../models/flow-model.md), раздел «Split Groups — маршрутизация цветами»).
- **Fill Text (payload type шага Fill Fields)** `[AIO]` — режим payload для шага `Fill Fields`, ограничивающий контент только текстом (запись текста в поля визита).
- **Handle-link N / Handle all links / Handle (fallback)** `[AIO, transitions]` — `Handle Link <N>` — пронумерованный transition на клик, привязан к кнопке через `{{link:N}}`. Обычный `{{link}}` уходит в `Handle All Links`, а без него — в `Handle All` (базовый `Handle`). Пронумерованный `{{link:N}}` уходит в `Handle Link N` своего номера, а без неё — сразу в `Handle All`: ветку `Handle All Links` он не использует, поэтому на шаге с `{{link:N}}` держат `Handle All` или ветку на каждый номер. Если подходящей ветки у шага нет, переход не находится и визит остаётся на шаге.
- **{{link:N}} + Link N (нумерованные переходы)** `[AIO, плейсхолдер]` — `{{link:1}}`, `{{link:2}}`, ... — несколько разных переходных ссылок с одного лэнда. Каждый номер — отдельный transition во флоу (`Handle Link 1`, `Handle Link 2`, ...), может вести в разные наборы офферов. Доступно **до 5 линков**. Без своей ветки номер уходит в `Handle All` (базовый `Handle`), а не в `Handle All Links` (см. `Handle-link N / Handle all links / Handle (fallback)`).

## Кампании и запуск трафика в AIO

- **Кампания** `[AIO]` — контейнер запуска: флоу + источник + лэнды + интеграция + правила.
- **Левая часть окна создания кампании** — мета кампании: название, описание, цвет, страна, язык. **Это не настройки фильтра**, это удобство фильтрации внутри AIO.
- **Стратегии выбора** `[AIO]` — когда вариантов больше одного (несколько прилэндов, офферов, доменов и т.д.). **Четыре стратегии**: `First`, `Weights`, `Conversions AI`, `Metrics AI`:
  - **First** — проход сверху вниз. Пробует выбрать первый вариант; если он не прошёл свои правила — следующий, и так далее. Если ни один не подошёл — уходит по `No Payload`.
  - **Weights / Веса** — распределение по весам. Одинаковые веса = равномерное распределение.
  - **Conversions AI** — AI-оптимизация под конкретную целевую конверсию. Под капотом — `Thompson Sampling`, перераспределяет трафик к варианту с лучшей конверсией, не отключая остальные. Часто называется просто «AI» или «ML». *(Ключ в коде — `Machine Learning`.)*
  - **Metrics AI** — AI-оптимизация под произвольную числовую метрику (CTR, EPL, ROAS и т.п.) за окно `Timeframe`. Под капотом — `Epsilon-Greedy`: с вероятностью ~10% исследует, выбирая вариант равномерно случайно среди всех вариантов (лучший может переизбраться), остальные ~90% — эксплуатирует вариант с наибольшим значением метрики. *(Ключ в коде — `Relative Machine Learning`.)*

  **Граница доступности:** в настройках шага во Flow-редакторе доступны только `First` / `Weights`; все четыре — в сплите шага в ERP-форме кампании; узел `Strategy` в дереве Distribution предлагает `First` / `Weights` / `Machine Learning`.

- **Balance (кнопка)** `[AIO]` — **не отдельная стратегия**, а кнопка сплита вариантов в режиме `Weights` — в шаге Flow-редактора, в шаге кампании и в сплитах контента лэнда. Одним нажатием выставляет всем активным вариантам равные веса. **В деревьях Distribution кнопки `Balance` нет** — веса нод там правятся через `Edit weight` / `Edit weights`. Не путать с `Conversions AI` — `Balance` просто уравнивает веса, без AI-оптимизации.

- **Meta Spend (метрика) / AIO Attribution Engine** `[AIO, аналитика]` — метрика **`Meta Spend`** в отчёте = рекламный расход из Meta, разнесённый по visit-уровневым разрезам **в момент построения отчёта** (движок — `AIO Attribution Engine`): дневной расход объекта Meta на выбранном уровне (`campaign` / `adset` / `ad`) распределяется по визитам, у которых в этот день был этот объект, пропорционально их числу. **Уровень матчинга выбирается кнопкой с иконкой Meta в тулбаре таблицы** (`Campaign` / `Adset` / `Ad`), по умолчанию `campaign`; выбор общий для всех таблиц и хранится в браузере — другой браузер стартует с `campaign`. **Основной способ работать с костами и профитом по FB** — рядом с ней в отчёте стоит revenue, поэтому профит и ROI по FB читаются прямо в разрезе с колонкой `Meta Spend` (Source, Destination, гео, оффер). Инвариант: Σ по match-key = расход Meta по этому ключу. Не разложенный расход — **не отдельная колонка**: разбивка `Matched` / `Orphans` / `Out of scope` показана в подсказке ячейки — см. `orphans / out-of-scope`, `status`. **Не путать** с `Cost Spillover Level` / `AIO Meta — cost-перелив` (перелив костов **на визиты** по `FB Ad ID`, неточный — другой механизм). Полностью — [mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md).
- **Meta Spend Allocation vs Cost Spillover (два механизма Meta-spend)** `[AIO]` — два **разных** сосуществующих механизма разнесения расхода Meta:
  - **`Meta Spend Allocation`** (новый) — атрибуция расхода Meta по визитам отчёта на лету, пропорционально визитам разреза. Матчит по объекту Meta выбранного уровня × день: `campaign` (дефолт) / `adset` / `ad`, уровень переключается кнопкой в тулбаре таблицы и хранится в браузере; **не зависит** от `Cost Update Strategy`. Ничего не теряет, сходится до копейки, помечает строки статусом (`fine` / `noisy`), а футер — `fine` / `noisy` / `partial`.
  - **`Cost Spillover` / старый перелив костов** (старый) — переливает расход Meta на визиты, наполняя метрику `Costs` для ROI. **Четыре стратегии матчинга** в поле кампании `Costs update strategy`: `AIO Meta` (`ad_id`), `Meta AdSet` (`adset_id`), `Meta Campaign` (`campaign_id`), `Meta Account` (выбранные рекламные кабинеты целиком); по умолчанию `Manual` — перелива нет. Неточный — теряет расход по `ad_id` без визита.
  - Полностью — [mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md).
- **match-key / result-key (аллокация Meta-spend)** `[AIO]` — два ключа в аллокации `Meta Spend`. **match-key** связывает строки traffic и Meta: `<id объекта Meta выбранного уровня> × день` — по умолчанию meta-кампания × день, на уровне `adset` / `ad` — адсет или объявление × день (это сущности рекламного кабинета, а не кампания AIO). **result-key** — visit-уровневый разрез, в который складывается итог (лэнд, оффер, страна, движок); в спенде, который Meta отдаёт (агрегат по объекту кабинета × день), таких разрезов нет. Отдельного ключа «наше vs чужое» (`scope-prefix`) нет: «свой» спенд определяется тем же match-key — объект Meta × день. Один match-key раскладывается на много result-key пропорционально визитам. См. [mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md).
- **baseline (знаменатель аллокации при drilldown)** `[AIO]` — приём, держащий суммы `Meta Spend` согласованными между уровнями drilldown: числители считаются по узкому (раскрытому) срезу, знаменатели — по более широкому baseline-набору без drilldown-фильтров. Без него знаменатель схлопывается и spend на уровне раздувается (`Σ детей > parent`). Из baseline же берётся и определение orphan (ноль визитов **в baseline**, а не в узком срезе). При раскрытии funnel-разреза (Destination / лэнд / оффер) по обычному разрезу условие «дошёл до этого шага» попадает и в знаменатель подгруппы — поэтому дети суммируются в родителя (Destination = сумма его источников). См. [mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md).
- **orphans / out-of-scope** `[AIO]` — рекламный расход, который **не вышло** разложить: у Meta-объекта выбранного уровня за день есть spend, а визитов в baseline нет — делить не на что. **Не отдельная колонка/метрика в таблице.** Такой спенд не переносится ни на другие дни, ни на другие строки: целиком уходит в `Out of scope` итога (строки `Orphans` при посуточном расчёте нет, `Total` равен `Matched`). Туда же попадает спенд объектов Meta, у которых в скоупе запроса нет ни одного визита; под любым фильтром это норма (при фильтре по одной кампании AIO в `Out of scope` уходит спенд объектов Meta, чьи визиты шли в другие кампании). В итог и в формулы (`Profit`, `ROI`, экспорт) не входит; виден в подсказке ячейки строкой `Out of scope`, а клик по значению со знаком `≈` переключает показ на `Total + out of scope` (переключатель общий для всех Meta-колонок, хранится в браузере). У строк он 0, кроме строки `Empty` на funnel-разрезе (лэнд / Destination / оффер, поле тенанта): там виден спенд объектов, до которых никто не дошёл (в футер он уже входит). Большой `Out of scope` без фильтров — повод проверить метки и трекинг (клики не распознаны), на отфильтрованной странице — не поломка. См. [mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md).
- **Empty bucket (пустой result-key)** `[AIO]` — корзина для визитов, у которых match сработал, но result-key пустой (UA не распарсился → нет движка; IP-гео не сработало → нет страны). Spend на них аллоцирован **легитимно**, bucket **входит в footer** (видимая строка «Empty»). Не путать с orphans / out-of-scope (спенд объекта Meta без визитов за день — уходит в `Out of scope` футера). См. [mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md).
- **`status` (fine / noisy / partial)** `[AIO, аллокация Meta-spend]` — значок доверия к цифре `Meta Spend` у строки и у футера отчёта. `fine` — все проверки прошли, доверяй. `noisy` — `Meta Spend` может быть **завышен** (шумная экстраполяция на funnel-разрезе — мало визитов дошло до уровня). `partial` бывает **только у футера**: половина спенда и больше ушла в `Out of scope`, показанная сумма заметно меньше всего спенда Meta (полная — `Total + out of scope` в расшифровке). При совпадении у футера побеждает `partial` (недосчёт важнее неточности). У строк `noisy` бывает **только** там, где знаменатель — дошедшие до точки воронки: на funnel-разрезах (оффер / лэнд / Destination, поле тенанта) и в раскрытии funnel-строки по обычному разрезу. **Статус футера** — худший по строкам, но дополнительно эскалируется долей `Out of scope` в полном спенде скоупа: ≥10 % → `noisy`, ≥50 % → `partial`. Поэтому значок на итоге при полностью чистых строках — не поломка аллокации, а «часть спенда Meta не привязалась к скоупу запроса». См. [mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md).
- **Destination-аппроксимация (экстраполяция spend на funnel-разрезы)** `[AIO, аллокация Meta-spend]` — на разрезах по funnel-уровню (лэнд, тип лэнда, роль `LP: <Тип>`, Destination, Advertiser/оффер, тип оффера) `Meta Spend` считается по доле визитов, **дошедших** до этого шага, а не по всем визитам объявы (иначе spend «утёк» бы в скрытую Empty-строку не дошедших). По сути экстраполяция: «не дошедшие распределились бы как дошедшие». Следствия: spend на оффере/лэнде может быть **больше**, чем «дошедшие визиты × цена»; шаткая экстраполяция → `status = noisy`; один Destination, шаренный между кампаниями, получает **полный credit от каждой** (суммы складываются). См. [mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md).
- **Custom Key / Custom Value (FB CAPI трекер)** `[AIO]` — до пяти пар полей в настройках FB CAPI трекера: добавляют в `custom_data` события свойство с именем из `Custom Key` и значением из `Custom Value` (текст или плейсхолдер). Имя самого события (в том числе кастомного, заведённого в пикселе) задаёт поле `Event`. [how-to/source-trackers.md](../how-to/source-trackers.md).
- **short-keys (зашифрованная часть ссылки)** `[AIO]` — параметры, шифруемые внутрь URL (encrypted-формат). Шифровать можно **только** параметры, полностью известные на момент генерации ссылки. Параметры от третьей системы (FB `{{ad.id}}`) — нельзя, иначе они не будут заменены.

### Автоправила Meta (раздел Automations)

- **`Automations` / Автоматизации** `[AIO, раздел]` — раздел `/app/automations` (в меню — `Automations`, RU `Автоматизации`) с автоправилами над Meta-сущностями: движок сам считает метрики кампании, адсета или объявления и делает то же, что руками делают экшены `Start` / `Stop` / `Change budget`. Четыре страницы автоправил: `Status` (обзор ассайнов и быстрая проверка вердиктов), `Assignments` (на какие сущности повешены шаблоны), `Rule Templates` (сами шаблоны правил), `History` (журнал вердиктов и очередь подтверждений). Ниже в подменю раздела — `Processes` и `Process Flows`: к автоправилам они не относятся. Права — своя ветка `automation.*`: доступ к Meta или к дистрибуциям её не даёт ([models/permissions-model.md](../models/permissions-model.md)). Только ERP. Настройка — [how-to/auto-rules.md](../how-to/auto-rules.md), что происходит между прогонами — [mechanics/auto-rules-engine.md](../mechanics/auto-rules-engine.md). (разг.: «автоправила», «автостоп», «правила по мете»)
- **`Rule Template` / шаблон автоправил** `[AIO, Automations]` — шаблон, по которому движок выносит вердикт сущности Meta. Технически это дистрибуция типа `Auto Rules`, но собирают и правят её в `Automations → Rule Templates` под правом `automation.templates.edit`. В шапке — ось фаз (`Phase axis`) и переменные, в дереве — только `Phase` в корне и `Auto Rule` листом внутри фазы. Разбор — [how-to/auto-rules.md](../how-to/auto-rules.md).
- **Вердикт автоправила (`Action`)** `[AIO, Automations]` — что правило постановляет сделать с сущностью Meta; шесть значений: `stop`, `start`, `keep`, `wait`, `change_budget`, `duplicate`. Как каждое подписано в интерфейсе и что у него настраивается — [how-to/auto-rules.md](../how-to/auto-rules.md); какие вердикты доезжают до Meta и почему подтверждение человека решает режим ассайна, а не отдельное правило — [mechanics/auto-rules-engine.md](../mechanics/auto-rules-engine.md).
- **Статус действия в журнале автоправил** `[AIO, Automations]` — в каком состоянии действие по вердикту; восемь значений: `observed`, `pending`, `approved`, `declined`, `executed`, `failed`, `expired`, `superseded`. Что означает каждый статус, какие из них ещё не финальные и какими цепочками идут переходы — [mechanics/auto-rules-engine.md](../mechanics/auto-rules-engine.md).

## Источники, трекеры и дистрибуции AIO

- **Distribution / Дистрибуция** `[AIO]` — централизованное дерево правил, автоматически распределяющее значения по визиту. Управляется в `Settings → Distributions`. Деревья состоят из **Folder + Strategy + Rule to pass + Payload-нод**. Strategy внутри Folder: First / Weights / Machine Learning. Правила применяются сверху вниз. Исключение — тип `Auto Rules`: он работает над Meta-сущностями, а не над визитом, дерево у него собрано из других нод, а его дом — раздел `Automations` ([how-to/auto-rules.md](../how-to/auto-rules.md)).

  9 типов дистрибуций: **Payout** (payout по правилам) · **Revenue** (revenue по правилам) · **Campaign Content** (значения для одного шага кампании) · **Flow Content** (значения для нескольких шагов одного флоу) · **Fill Field** (заполняет поле визита, шаг `Fields by distribution`) · **Direct Traffic** (голые ссылки без UTM, альтернатива `Default query` на домене) · **Remarketing Content** (push-сценарии, которые собирают во флоу вручную — кастомный путь) · **Message Templates** (плитка выбора — `Message templates`; дерево нод-шаблонов сообщений для рассылок ремаркетинга) · **Auto Rules** (шаблон автоправил над Meta-сущностями; свой дом — `Automations → Rule Templates`, плитка `Auto rules` есть и в пикере `Settings → Distributions`).

  Что каждый тип делает, какие ноды и стратегии ему доступны — [models/distributions-model.md](../models/distributions-model.md).

- **Distribution Nodes** `[AIO]` — типы нод внутри distribution-дерева (доступность зависит от типа дистрибуции):
  - **Add Folder** — контейнер для правил.
  - **Add Strategy** — стратегия выбора внутри Folder (First / Weights / Machine Learning).
  - **Add Destination** — нода дестинейшна.
  - **Add Landing** — нода лэнда.
  - **Add Redirect** — URL-редирект.
  - **Add Reflect** — reflect-ссылка.
  - **Add Proxy reflect** — proxy-reflect.
  - **Add Query** — default query (привязать source+campaign к домену).
  - **Add Push Message** — ссылка на готовую запись-шаблон из `Marketing → Message templates`.
  - **Add Telegram message** — то же для Telegram-записи.
  - **Add Revenue** — revenue-значение.
  - **Add Payout** — payout-значение.
  - **Add Fill Field** — заполнение поля визита (с подтипами `Text / Image / Landing / Library / Destination`).
  - **`Email Template` / `Push Template` / `Sms Template` / `Telegram Template`** — четыре листа-шаблона, которые бывают **только** в деревьях типа `Message Templates` (в диалогах UI подписаны `Email template` / `Push template` / `SMS template` / `Telegram template`); текст сообщения лежит в самой ноде, а не ссылкой на запись из `Marketing → Message templates`. Из такого дерева сегодня реально отправляется только push-ветка — разбор в [models/distributions-model.md](../models/distributions-model.md).

  [models/distributions-model.md](../models/distributions-model.md).

- **`Phase` / `Auto Rule` (ноды дерева `Auto Rules`)** `[AIO]` — две ноды, которые бывают **только** в дистрибуции типа `Auto Rules`: `Phase` — фаза, разрешена в корне дерева; `Auto Rule` (в дереве подписана `Auto rule`) — правило-лист внутри фазы. Форма такого дерева, ограничения размещения и дословные тексты ошибок — [models/distributions-model.md](../models/distributions-model.md); что задаётся в фазе и в правиле — [how-to/auto-rules.md](../how-to/auto-rules.md).

- **Distribution Tree — управление** `[AIO]` — управляющие элементы дерева ([models/distributions-model.md](../models/distributions-model.md)):
  - **Rule to pass** — условие, при котором нода применяется.
  - **Toggle activity** — вкл/выкл ноду.
  - **Show children** — раскрыть/свернуть ноду.
  - **Toggle locked** — заблокировать (нельзя disable, пока заблочена).
  - **Move Up / Move down** — переставить порядок.
  - **Clear recursively** — очистить со всеми вложенными (требует disabled).
  - **Duplicate recursively** — дублировать со всеми вложенными.

- **Глобальная (системная) дистрибуция** `[AIO]` — дистрибуция без тенанта-владельца, одна и та же для всех тенантов; заводит её команда AIO. В списках `Settings → Distributions` и `Marketing → Template distributions` её нет — она появляется только в селектах выбора дистрибуции: в конце списка, после разделительной линии, с логотипом AIO. Из тенанта — только чтение: правка отбивается сообщением `System distribution is read-only`. Разбор — [models/distributions-model.md](../models/distributions-model.md).

- **Business Model** `[AIO]` — формула, по которой Payout и Revenue distributions пишут деньги в конверсию. Из шаблона тенанта приезжают восемь: `Arrived Revenue` (`AR`), `Arrived Payout` (`AP`), `Static Revenue` (`SR`), `Static Payout` (`SP`), `Zero Revenue` (`ZR`), `Zero Payout` (`ZP`), `Cancel Revenue` (`CREV`), `Cancel Payout` (`CPAY`); в засеянных деревьях работают `Arrived Revenue` (revenue из постбэков) и `Zero Payout`. Создаются в `Settings → Business models`, нужны при настройке Payout/Revenue distribution-ов. [models/business-model.md](../models/business-model.md).

- **Buyer UTM Distribution** `[AIO]` — типовая `Fill Field` дистрибуция, которая по правилам (обычно `Campaign Owner UUID = <конкретный байер>`) автоматически записывает UTM-метку баера в поле визита `buyer_utm` через шаг `Fill Field` во флоу. Заведена в четырёх ERP-шаблонах (в MTK — нет); в ERP Finance рядом лежит ещё `Fill Field`-дистрибуция `Offer Names Distribution` под динамический оффер-нейм. Заполнение других полей (`aff_id`/Offer ID, API-токены) — кастомные дистрибуции, которые заводятся самостоятельно. Метку команды (тимы) в дестинейшн проставляют так же: поле визита (например `team`) + папки по командам с правилом `Campaign Owner UUID` `in` [участники] либо второй лист в папке каждого баера (только в режиме `Multiple Nodes`). [models/distributions-model.md](../models/distributions-model.md).
- **Direct Traffic Distribution** `[AIO]` — тип Distribution для голых ссылок (домен без UTM): дерево из `Folder` и нод `Query`; нода задаёт кампанию и источник визита, а правило — по домену, пути захода (`{{aio.visit.initial_path}}`), гео и другим полям визита. Дальше визит идёт по флоу выбранной кампании. [models/distributions-model.md](../models/distributions-model.md).
- **Fill Field Distribution** `[AIO]` — тип Distribution (`Settings → Distributions → +Distribution → Fill Field`) — централизованное дерево правил, как заполнить поля визита (см. список в `Distribution / Дистрибуция` выше, тип 5). Применяется во флоу шагом типа `Fields by distribution` (в шаблонах шаг назван `Fill Fields by Distribution`). **Не путать** с шагом `Fill fields` (значения задаются в самом шаге, без дистрибуции) и с `Fill Field-нодой` (нода **внутри** дерева).
- **Select Strategy: Single Node / Multiple Nodes** `[AIO]` — настройка дистрибуции — режим записи payload-ноды. `Single Node` — заполняется только одна подходящая нода; `Multiple Nodes` — все найденные по дереву правил.
- **`Multiple Nodes` в Fill Field Distribution** `[AIO]` (разг. «Multiple Strategy») — режим `Select strategy` дистрибуции, а не стратегия узла `Strategy`: дерево обходится до конца, и применяются **все** прошедшие правила ноды. Если на одно поле визита подходят несколько нод, в этом проходе записывается первая сверху, остальные пропускаются — поэтому дефолтную папку ставят в самый низ дерева.
- **Offer-Name Distribution** `[AIO]` — Distribution для ротации офферов/брендов. Folder Strategy (`First` / `Weights` / `ML`) на уровне дерева. «Умной» ротации по конверсиям за последние N часов нет — только ML за всё время.
- **Offer Distribution** `[AIO]` — дистрибуция, централизованно распределяющая, какой оффер выбрать (вместо ручного выбора байером в кампании). После настройки у байера в кампании пропадает место выбора оффера — всё решает Offer Distribution по правилам (`Country Code` + `Campaign Owner` и т.п.). Родственно `Offer-Name Distribution`.
- **Push Distribution (применение Remarketing Content)** `[AIO]` — применение `Remarketing Content` distribution для пушей — дерево папок → подпапки по `country_code` → стратегия (`First` / `Weights` / `Machine Learning`) на множестве нод `Push Message`. [models/distributions-model.md](../models/distributions-model.md). Схема рассылки — [mechanics/notifications-flow.md](../mechanics/notifications-flow.md). Это **кастомный путь**: дефолтная рассылка собирается ремаркетинг-кампанией и берёт тексты из дистрибуции `Message Templates` ([how-to/remarketing-campaigns.md](../how-to/remarketing-campaigns.md)).
- **Arrived Revenue (Business Model)** `[AIO]` — Business Model `Arrived Revenue` (`AR`) — на ней стоит засеянный `Revenue Distribution` во всех шаблонах тенанта. Берёт значение из поля `arrived_revenue` постбэка, конвертирует в USD по текущему курсу, пишет в поле конверсии `Revenue`. Момент фиксации курса — момент прихода постбэка. Конвертация — по курсам открытого внешнего источника (кэшируются, тот же источник использует превью в Postback generator). [models/business-model.md](../models/business-model.md).
- **Zero Payout (Business Model)** `[AIO]` — Business Model `Zero Payout` (`ZP`), всегда возвращающая `Payout = 0`; на ней стоит засеянный `Payout Distribution` во всех шаблонах тенанта. Fallback «ничего не платим». [models/business-model.md](../models/business-model.md).
- **Third Party PWA Link Generator** `[AIO, Source]` — отдельный Source (в шаблонах iGaming заведён как `3rd Party PWA Link Generator`), генерирующий универсальные ссылки для подстановки внутрь PWA-шек сторонних сервисов. Ссылки **без идентификаторов кампании/юзера** — их цель только вернуть визит в AIO в тот же флоу. См. [mechanics/pwa.md](../mechanics/pwa.md).
- **Tracker → Trackers (вкладка)** `[AIO]` — место в UI, где заводятся постбэки и event-уведомления из AIO в сторонние системы (FB CAPI, Snapchat, TikTok, постбэки в партнёрки). Из шаблона приезжают трекеры `Facebook Conversion API` (`FB Lead` + трекер под целевое событие вертикали; в iGaming вместо `FB Lead` — `FB AIO Install` и `FB AIO Registration`, плюс трекер под целевое событие) и в iGaming пример HTTP-постбэка `Example - 3rd Party PWA Postback`.
- **Google Conversions CSV / External Report** `[AIO]` — тип `External Report` под загрузку конверсий в Google. Возвращает CSV на URL-запрос; Google сам ходит по URL и тащит конверсии.
- **Google Account ID / Conversion ID / Conversion Label** `[AIO, Google]` — параметры под Google-сетап. **Основной путь**: указываются при генерации трекинговой ссылки в `Link Generator` (у источника `Google` из шаблона — поля `Google Account ID`, `GTAG ID`, `GTAG Conversion ID`, `GTAG Conversion Label`), вписываются прямо в URL и пишутся в визит автоматически. Google **не передаёт `Account ID`** в URL сам — AIO протаскивает его явно. **Альтернатива** (если ссылка уже разлита или айди не известен на момент генерации): маппинг `domain → Account ID` через `Fill Field` ноды во флоу. `Conversion ID` — идентификатор тэга. `Conversion Label` — ярлык конверсии. Основной путь — запись в ссылку при генерации.
- **`Campaign Country Code` vs `Country Code` (мульти-гео)** `[AIO]` — `Campaign Country Code` (`{{aio.campaign.country_code}}`, разг. campaign_country_code) — **только первая** страна из `Countries` кампании (если список пуст — страна, которую AIO определил по трафику кампании); остальные страны мульти-гео кампании в правило не попадают, поэтому для мульти-гео поле непригодно. `Country Code` (`{{aio.visit.country_code}}`, разг. visit_country_code) — страна конкретного визита, всегда одна — корректное поле для правил при мульти-гео. **Мульти-гео кампания** — кампания с несколькими country_code (DACH = DE+AT+CH); редкий нестандартный кейс.
- **Contains / Has Prefix / Has Suffix (операторы правил)** `[AIO]` — строковые операторы кастомных правил (Allowance Rules / Rule to pass): `Contains` / `Does Not Contain` — подстрока, `Has Prefix` — начинается с, `Has Suffix` — заканчивается на; в тексте правила они показаны как `contains` / `does not contain` / `starts with` / `ends with`.

## Marketing и Push-уведомления AIO

- **Remarketing Campaign / Ремаркетинг-кампания** `[AIO, Marketing]` — кампания, которая не принимает трафик, а рассылает сообщения по аудитории уже собранных визитов. **Дефолтный и основной способ рассылки пушей в AIO.** Отдельный тип кампании (`Notifications` против `Campaigns` у трафиковой), живёт в `Marketing → Campaigns` и обязана указывать на флоу типа `Notifications` — иначе форма не сохраняется (`Remarketing campaign requires a Notifications flow`). Права отдельные, `marketing.campaigns.*`: доступ к трафиковым кампаниям их не даёт. В MTK — только с платным модулем `PWA + Push` (вкладка `PWA → Campaigns`). Процедура целиком — [how-to/remarketing-campaigns.md](../how-to/remarketing-campaigns.md). (разг.: «ремаркетинг-кампания», «рассылка», «пуш-кампания»)
- **`Launch trigger` (`Manual` / `Schedule` / `Conversion`)** `[AIO, ремаркетинг-кампания]` — блок формы кампании, задающий, чем запускается рассылка; в таблице кампаний тот же выбор виден колонкой `Trigger`. `Schedule` — по расписанию: у одной кампании их может быть несколько (кнопка `Add schedule`, потолок 50), время считается в UTC, по умолчанию не чаще раза в 30 минут. `Conversion` — по приходу конверсии выбранного типа (поле `Conversion type`); в фильтре таблицы тот же тип подписан `Conversion Trigger`. **`Manual` выбран в форме по умолчанию и не запускает ничего** — кнопки ручного запуска в продукте нет, поэтому кампания «из коробки» молча не отправляет ни одного сообщения. Разбор — [how-to/remarketing-campaigns.md](../how-to/remarketing-campaigns.md).
- **Аудитория ремаркетинг-кампании (`Audience`)** `[AIO, ремаркетинг]` — визиты, по которым кампания шлёт сообщения. Визит попадает в неё, когда проходит сущность трафика с привязкой к этой кампании; **гейта по подписке на push нет** — собирается любой нетрэшевый визит. Колонка `Audience` в таблице кампаний показывает пару чисел `In audience` / `Removed`; причин выбытия ровно две — `stop_conversion` (сработала стоп-конверсия) и `dead_endpoint` (push-подписка мертва). Колонка визита `RMK Audience` — **история попадания, а не текущий состав**: список кампаний на визите только пополняется. Как набирается — [how-to/remarketing-campaigns.md](../how-to/remarketing-campaigns.md).
- **`Drip schedule` / серия рассылок** `[AIO, узел флоу Notifications]` — узел, который держит всю серию отправок внутри себя: шаги со смещением от момента входа визита в узел. Смещение выбирается из фиксированного набора (`Now`, 3, 5 и 15 минут, 1 / 3 / 5 / 12 часов, 1–5 суток), каждое значение используется один раз. Два режима наполнения: `Simple` — одна дистрибуция шаблонов на всё расписание, `Advanced` — своя на каждый шаг. Из выбранного дерева серия отправляет **только push**. В интерфейсе тип узла подписан именно `Drip schedule`; `Plan Drip` — внутреннее имя того же типа (встречается в английских подсказках). Механика — [mechanics/notifications-flow.md](../mechanics/notifications-flow.md). (разг.: «дрип», «серия», «follow-up пуши»)
- **`Stop conversion` / стоп-конверсия** `[AIO, поле узла Drip schedule]` — тип конверсии, приход которой означает «цель серии достигнута»: визит перестаёт получать шаги и **выводится из аудитории** кампании с причиной `stop_conversion`. Задаётся в узле `Drip schedule` флоу; если режим узла не `Flow only`, кампания может перекрыть её в блоке этого узла в своей форме (там же `Required conversions`). Рядом лежит `Required conversions` — обратный гейт: шаг уходит, только если у визита есть конверсии всех выбранных типов, иначе серия завершается, но визит остаётся в аудитории. [how-to/remarketing-campaigns.md](../how-to/remarketing-campaigns.md).
- **`Template distributions` / дистрибуция шаблонов (`Message Templates`)** `[AIO, Marketing]` — раздел `Marketing → Template distributions` и одноимённый тип дистрибуции: дерево нод-шаблонов, откуда серия рассылок берёт текст сообщения. Листья — `Email Template` / `Push Template` / `Sms Template` / `Telegram Template`, и текст лежит **прямо в ноде**, а не ссылкой на запись из `Marketing → Message templates`. Подходящий лист выбирается на каждую отправку **равновероятно** среди прошедших свои правила; веса в этом дереве не работают. Если в дереве смешаны push- и не-push листья, не-push отбрасываются молча — серия шлёт только push-ветку. Разбор — [models/distributions-model.md](../models/distributions-model.md).
- **`Push Template`** `[AIO, Marketing]` — имя носят две разные вещи. (1) **Лист дерева `Message Templates`** — нода, в которой лежит сам текст: имя строки в дереве плюс поля `Push title`, `Push message`, `Push icon`. Отсюда берёт контент серия рассылок ремаркетинг-кампании. (2) **Запись в `Marketing → Message templates`** — отдельная сущность с теми же полями, на неё ссылаются ноды `Push Message` пуш-сценариев, которые собирают во флоу вручную. Каналы: из дерева `Message Templates` уходит только push, Telegram отправляется отдельным узлом флоу, а email и SMS не отправляются вообще — и отказывают **молча**, без ошибки и без следа в аналитике ([mechanics/notifications-flow.md](../mechanics/notifications-flow.md)).
- **Спинтакс в текстах рассылок (`{вариант 1|вариант 2}`, `{Random=(100,1500)}`)** `[AIO, Marketing]` — синтаксис случайного выбора прямо в тексте сообщения: на каждую отправку из фигурных скобок берётся один вариант, `{Random=(min,max)}` даёт случайное целое. Действует в push- и telegram-сообщениях Marketing — и в серии рассылок ремаркетинг-кампании, и в ноде `Push` флоу нотификаций; вне рассылок этот синтаксис не работает. Разбор синтаксиса — [reference/placeholders.md](placeholders.md), где задаётся сам текст — [mechanics/notifications-flow.md](../mechanics/notifications-flow.md).

- **`Notification Flow`** (синоним — `Marketing Flow`) `[AIO, Marketing]` — флоу типа `Notifications`: отвечает за «что и по какому расписанию» отправить, а «кому и когда» задаёт ремаркетинг-кампания, которая на него указывает. Заводится в `Marketing → Flows`, исполняется параллельно маршруту визита. В новой модели такой флоу вырождается в один узел: `Start` → `Drip schedule`, вся серия живёт внутри узла. Остальные узлы (`Push`, `Telegram`, `Wait`, `Check`, `Check conversion`, `Repeat`) остаются для сценариев, которые собирают вручную. Палитра узлов и транзишны — [mechanics/notifications-flow.md](../mechanics/notifications-flow.md), сборка кампании — [how-to/remarketing-campaigns.md](../how-to/remarketing-campaigns.md).
- **`Notifications flow` (нода в Campaign Flow)** `[AIO, кастомный путь]` — нода трафикового Campaign Flow, подключающая к воронке заранее созданный флоу типа `Notifications`. Из редактора нода не убрана и работает, но **новые рассылки так не собирают** — штатный путь это ремаркетинг-кампания ([how-to/remarketing-campaigns.md](../how-to/remarketing-campaigns.md)). Разбор — [mechanics/notifications-flow.md](../mechanics/notifications-flow.md).
- **Remarketing Distribution / `Remarketing Content`** `[AIO]` — тип дистрибуции для пуш-сценариев, которые собирают во флоу вручную: дерево `Folder` + `Strategy` (`First` / `Weights` / `Machine Learning`; внутри `Strategy` — только `Push Message`) + ноды `Push Message` / `Telegram Message`, каждая ссылается на готовую запись из `Marketing → Message templates`. Создаётся в `Settings → Distributions`, применяется нодой `Push`. Это **кастомный путь**: дефолтная рассылка берёт тексты из дистрибуции `Message Templates` (см. `Template distributions`). [models/distributions-model.md](../models/distributions-model.md).
- **Push Subscribe Toggle** `[AIO, поле кампании]` — переключатель `Enabled / Disabled` на уровне кампании (поле `push_subscribe_toggle`; заведено в шаблонах Finance, Nutra и Sweeps, в iGaming поля нет; при значении `disabled` макрос подписки prompt не показывает), включающий/выключающий **Push Subscribe Script** на лэнде.
- **Push Subscribe Script** `[AIO, скрипт]` — JS-скрипт, который на лэндах предлагает визиту подписаться на push-уведомления браузера. Включается/выключается через `Push Subscribe Toggle` на уровне кампании. После подписки факт фиксируется как конверсия типа `Push Subscribe`.
- **AIO Push Subscription (макрос)** `[AIO]` (разг. «AIO Push Subscribe») — JS-макрос `aio_push_subscription`, выводящий браузерный prompt подписки на push. В шаблонах ERP Finance / Nutra / Sweeps заведён глобальным, но **выключенным** — включается тумблером `Active?` в карточке макроса; в MTK-шаблонах и iGaming его нет ([mechanics/notifications-flow.md](../mechanics/notifications-flow.md)). Управление вызовом (по клику / автоматически) — правкой JS внутри макроса.
- **Manual / Scheduled / Follow Up пуши** `[AIO, разговорная классификация]` — как в разговоре называют варианты рассылки. Все они сегодня собираются одной сущностью — ремаркетинг-кампанией: `Scheduled` = триггер `Schedule` (запуск по расписанию), `Follow Up` = шаги серии в узле `Drip schedule`, а `Manual` (запуск руками по кнопке) **не реализован** — одноимённый триггер стоит в форме по умолчанию и не запускает ничего. [how-to/remarketing-campaigns.md](../how-to/remarketing-campaigns.md).
- **Telegram-уведомления: Telegram (нода) / Sender Provider / Buyer TG Chat ID** `[AIO]` — стек отправки TG-сообщений из AIO. `Telegram` — нода-канал в Marketing Flow, отправляет сообщение в TG (нужен sender-провайдер, контакт, шаблон). `Sender Provider` (тип `Telegram`) — настраивается через API-ключ бота + имя бота; **используется и для рассылок, и для `Telegram Destination`**. Для acquisition-флоу Destination в провайдере задаются `Start`/`Joined Message`, приглашение в канал (`Join Channel` + header/button text), типы конверсий на старт/вступление и поля визита под `chat_id`/`username` (полная таблица — [how-to/push-notifications.md](../how-to/push-notifications.md); настройка Destination — [how-to/destinations.md](../how-to/destinations.md)). `Messages` — раздел с логами отправки. `Buyer TG Chat ID` — кастомное поле визита под TG chat_id владельца кампании; **имя — пример, по дефолту в шаблонах тенантов такого поля нет, заводится вручную**; заполняется через `Fill Fields` по правилу `Campaign Owner`. `Notification Flow` — Marketing Flow, запускается на каждую конверсию выбранного типа. См. [mechanics/notifications-flow.md](../mechanics/notifications-flow.md).
- **ZM Apps Push** `[AIO, Sender provider]` — тип Sender provider канала Push: пуш передаётся сервису ZM Apps через его API для подписчика, которого задаёт настройка подключения `Click UUID` (плейсхолдер поля визита, например `{{aio.visit.fields.zm_click_uuid}}`); выбирается в поле `Sender provider` узла `Drip schedule`. [mechanics/notifications-flow.md](../mechanics/notifications-flow.md).
- **Telegram Destination / Behaviour (Bot -> Channel / Channel)** `[AIO]` — тип Destination, заводящий трафик в TG-бот/канал (целевое действие — подписка на канал, не форм-сабмит). Требует Sender Provider типа `Telegram` + `Behaviour`: `Bot -> Channel` (визит → бот с приветствием → приглашение вступить в канал) или `Channel` (редирект сразу в канал). Бот должен быть **админом канала**, иначе Telegram не отдаёт ему событие вступления и конверсия подписки не фиксируется. См. [how-to/destinations.md](../how-to/destinations.md).

- **PWA — определение (lander + manifest + Service Worker)** `[AIO]` — PWA-шка = обычный лэнд, у которого в `<head>` есть manifest для Chrome + Service Worker. Один и тот же Service Worker обрабатывает install и push. См. [mechanics/pwa.md](../mechanics/pwa.md). *(Слэнг: `PWA-шка`, `ПВАшка`, `пвашка` — все допустимы в разговорном тексте.)*
- **Create PWA / PWA Builder** `[AIO, экшен]` — создание PWA-шки живёт в отдельном разделе `Content → PWA` (своя страница рядом с `Content → Landings`): кнопка `+ PWA` (экшен `Create PWA`) открывает выбор: `PWA landing` — встроенный PWA Builder — или `Custom PWA` — свой лэнд из ZIP в готовом PWA-шелле ([how-to/custom-pwa.md](../how-to/custom-pwa.md)). Правка уже созданной — экшен `Manage PWA` в её строке (у `Custom PWA` — `Manage Custom PWA`, у обычных лэндов — `Manage landing`). В списке `Content → Landings` PWA не видны: он жёстко ограничен лэндами режима `Editor`, а карточки `Create a PWA` в диалоге добавления лэнда больше нет. В MTK та же страница и та же кнопка живут во вкладке `PWA` платного модуля `PWA + Push`. [how-to/pwa.md](../how-to/pwa.md).
- **PWA-макрос (превращение лэнда в PWA)** `[AIO]` — обычный макрос с конфигом фичи `pwa` в `Content → Macros`: id кнопки установки и контейнеров состояний. Управляет установкой и открытием приложения, но manifest не задаёт — его AIO собирает на сервере из настроек PWA-лэнда (`PWA Builder` / `Custom PWA`), поэтому обычный лэнд одним макросом в PWA не превращается. [reference/sdk.md](sdk.md), [how-to/pwa.md](../how-to/pwa.md).
- **AIO внутренние PWA vs 3rd party PWA** `[AIO]` — `AIO внутренние PWA` — создаются и хостятся в самом тенанте; фичи поверх: Content Splits на любом элементе, запись сессий.

- **AIO Visit Session (`{{aio.visit.session}}`)** `[AIO]` — идентификатор сессии визита, который AIO передаёт PWA-сервису в одном из сабов: у большинства PWA-адвертайзеров шаблона iGaming — `sub1`, у части — другой саб (`sub3`, `sub_id_1`). Нужен, чтобы при возврате из PWA-сервиса визит «продолжился» в той же сессии.
- **Monitoring user (алерты в общий чат)** `[AIO]` — `Monitoring user` домена, сервера или Destination — юзер тенанта, которому `@aio_tech_bot` шлёт алерты в его Telegram-чат. Чтобы алерты шли в общий чат команды, мониторинг-юзером назначают юзера, к которому вместо личного чата привязан групповой (такую привязку делает команда AIO по запросу). Уведомления центра уведомлений идут в групповой чат иначе — через привязку командой `/bind` ([mechanics/notification-center.md](../mechanics/notification-center.md)).

- **Item List** `[AIO]` — листы для большого количества данных разного формата (IP / Phone). Создаются в `Settings → Item lists`. Для использования в Condition-шагах / правилах.
- **Settings → Fields + slug поля** `[AIO]` — раздел AIO, где создаются кастомные поля визита (под маппинг ответов Traffic Filters, кастомные данные). `slug` поля автогенерируется из названия при создании и в `Edit field` не меняется; по slug у части Traffic Filter-ов задаются поля визита для результатов проверки (секция `Write results to visit fields`).
- **User fields (секция в форме)** `[AIO]` — секция `User fields` (RU `Пользовательские поля`) в карточках настроечных сущностей: `Source`, `Campaign`, лендинг, `Destination`, а также их «родители» `Flow`, `Lander Type`, `Advertiser`. Поле добавляется в форму точечно кнопкой `Add field` (пул доступных полей определяется атрибутом `Type` поля), значение доезжает до визита, когда визит проходит через эту сущность, — писать для этого `window.aioBus.push` на лэнде не нужно. У родительских сущностей поле раздаётся дочерним в одном из трёх режимов (`Flow only` / `Campaign template` / `Campaign only` — и аналогичные пары у `Advertiser` и `Lander Type`). Разбор — [how-to/user-fields.md](../how-to/user-fields.md); само поле сначала заводится в `Settings → Fields` ([how-to/custom-fields.md](../how-to/custom-fields.md)).
- **Campaign field (`Type = Campaign`)** `[AIO]` — не отдельная сущность, а **поле визита**, у которого дефолт значения берётся не из ссылки, а из карточки кампании (задаётся один раз на кампанию, копируется на каждый её визит при заходе — напр. FB Pixel/CAPI Token, чтобы не светить в URL). Значение живёт на визите и может быть перезаписано для отдельного визита (в т.ч. целью шага `Fill Fields`) — это **не** одно общее неизменяемое значение на всю кампанию. Атрибут `Type` (Visit/Campaign) — источник дефолта, не место хранения. Концепт — [models/visit-field.md](../models/visit-field.md); создание — [how-to/custom-fields.md](../how-to/custom-fields.md).
- **Атрибуты поля (Settings → Fields)** `[AIO]` — boolean-флаги поля визита/конверсии:
  - **`Is visible?`** — поле видно в колонках таблиц визитов и конверсий по дефолту.
  - **`Is registry?`** — поле копит **все разные значения** (`1,2,3...`; повтор уже записанного значения не добавляется); выключено — каждая новая запись заменяет прежнее значение.
  - **`Is macros visible?`** — доступность поля через объект `aio` на лендинге (JS-доступ в рантайме, **не плейсхолдеры**).
  - **`Is 2FA protected?`** — значение скрыто в таблице, когда у аккаунта включена защита данных и не активен `Unsecured Mode` (включается подтверждением 2FA-кодом).
  - **`is_used_for_costs`** — поле попадает в пункты `Update Costs by <поле>` у кампании (агрегация костов по визитам с одинаковым значением); переключателя в форме поля нет, флаг ставится только через API.

  Полное описание атрибутов — [how-to/custom-fields.md](../how-to/custom-fields.md).
- **Availability as grouper** `[AIO, атрибут поля]` — multi-select в форме поля (`Settings → Fields`) со значениями `Tables` / `Analytics`. В выборе группировки таблиц (Drilldowns / `Roll Up report`) поле появляется, только если выбрано `Tables`. Задаётся отдельно для каждого поля.
- **Available values (в форме поля)** `[AIO]` — JSON в форме поля (`Create field` / `Edit field`), превращающий поле (напр. Geo Code) в select-из-вариантов там, где значение задают руками, — в секции `User fields` карточек кампании, источника и других сущностей. Задаётся как JSON: `{"test": "test", "123": "321"}`.
- **Data source (поле формы создания)** `[AIO]` — select `Data source` в форме создания поля визита/конверсии (`Create manually`): на поведение поля выбор не влияет, в `Edit field` его нет. [how-to/custom-fields.md](../how-to/custom-fields.md).
- **Offer Name For Advertiser** `[AIO]` — поле внутри Content Item оффер-нейма, уходящее во внешние системы. Существует параллельно с `Offer Name For Visitor`.
- **PWA State / Offer State (поля визита)** `[AIO]` — поля визита `pwa_state` / `offer_state` (в шаблонах iGaming уже заведены, группа `Tracking`), в которые автоматически пишется выбранный вариант на шаге флоу (`PWA State` — для шага PWA, `Offer State` — для шага оффера). Для аналитики «какая PWA/оффер показались» — засеянные пресеты `Campaign → PWA`, `Campaign → Offer`, `PWA → Geo → Offer` группируют именно по ним. Формат — `Variant`.
- **Linked field (поле шага)** `[AIO]` — механика на уровне Flow (поле `Linked field` в настройках шага) для записи в поле визита: когда вариант выбран на `Content`/`Destination`-шаге, в указанное поле визита (формата `Variant`) пишется выбранный лэнд или дестинейшен — `{type, value: <uuid>}`; варианты `HTML` / `Redirect` / `Reflect` / `404` поле не заполняют, а при контенте из дистрибуции пишется конечный лэнд или дестинейшен ([models/flow-model.md](../models/flow-model.md)). Используется для аналитики «какой вариант показался». Механика только на **запись**, и запись происходит **только в момент выбора варианта на шаге**. Лежит в основе `PWA State` / `Offer State` — в гемблинг-сетапах для шага PWA и оффера пишут выбранный payload в эти поля.

- **Advertiser / Advertisers** `[AIO, сущность]` — сущность в `Settings` (шестерёнка → Advertisers), хранящая неизменяемый «хвостик» параметров (UUID, сабы, UTM-метки), общий для всех Destination-ов одной партнёрки/PWA-сервиса. Концептуальный аналог `Network` / `Affnetworks` в классических трекерах. Иерархия: **Advertiser Type → Advertiser → Destination**. (разг. про партнёрку: «ПП»)
- **Advertiser Type (иерархия)** `[AIO]` — уровень над `Advertiser`. Полная иерархия: **Advertiser Type → Advertiser → Destination**. Из шаблона тенанта приезжают два типа: `Offer` и `PWA`.

- **`Advertiser type` (атрибут Content node)** `[AIO]` — фильтр, схлопывающий варианты payload на `Content`-шаге: ограничивает выбор Destination так же, как он работает на шаге `Destination`. Позволяет быстро выбрать только Destination нужного типа, не прокручивая полный список.
- **`Form fallback`** `[AIO, атрибут Content node]` — резервный путь выбора формы (deprecated). Используется на `Content`-шаге, если во Flow нет отдельного шага `Fill form` (или `Choose form`), но нужна конкретная форма из `Settings → Forms`. При отсутствии и `Fill form`, и `Form fallback` грузится дефолтная форма из SDK-конфига. Очень старая механика; вместо неё рекомендуется явный шаг `Fill form` во Flow.

- **Методы создания Destination: By advertiser / By integration** `[AIO]` — **два основных метода**: `By advertiser` (рекомендуется) и `By integration`. В модалке `+Destination` они разворачиваются в **4 варианта**:
  - `By advertiser` (рекомендуется) — назначается Advertiser, его хвостик параметров подставляется автоматически.
  - `Simple redirect` — голый редирект-URL, создаётся **без выбора Advertiser** (Advertiser не назначается, поэтому нет аналитики по Advertiser / `Offer Visits`). **Не штатный путь для офферов** — штатно оффер идёт через `By advertiser` (ссылка) или `By integration` (API); `Simple Redirect` под узкие случаи (быстрый редирект в TG-бота, разовый URL). Процедура — [how-to/destinations.md](../how-to/destinations.md).
  - `Telegram` (Telegram Destination) — специализированный вариант `By integration` с типом интеграции Telegram.
  - `By integration` — raw-интеграция через готовый API-шаблон (Bridge / IREV и др.).
  - **Не путать** `Simple Redirect` с `Direct Traffic` (это **другая** сущность — тип Distribution для голых ссылок без UTM, см. соответствующую запись).

- **Cap / Caps (на Destination)** `[AIO]` — лимит на уровне Destination. Капа одна — `Conversion Cap`: считает конверсии одного выбранного `Conversion Type`, и когда счётчик дошёл до лимита, при стратегии `When the cap is full` = `Reject traffic` (дефолт) пуш лида больше не уходит и визит идёт в fallback по переходу `Destination Full`, при `Do nothing` капа только считает. Настраивается экшеном `Edit conversion cap` (в диалоге — `Cap type`, `Limit`, `Current usage`, кнопка `Reset counter`). **Четыре типа (`Cap Type`):** `Infinity` (в диалоге подписан `Unlimited` — лимита нет, дефолт), `Daily` (счётчик обнуляется в полночь таймзоны `Reset timezone`; пусто — UTC), `Monthly` (в полночь первого числа месяца по той же таймзоне), `Lifetime` (счётчик не обнуляется никогда). Механика — [models/destination.md](../models/destination.md), настройка и симптомы — [how-to/destinations.md](../how-to/destinations.md).
- **`Lifetime` (тип капы Destination)** `[AIO]` — `Cap Type`, у которого счётчик не сбрасывается по расписанию: он копится всё время жизни дестинейшена, пока лимит не поднимут или счётчик не обнулят вручную (`Reset counter` в диалоге капы, экшен `Reset cap`). Подсказка в интерфейсе — `The counter never resets — the limit applies to the whole lifetime.`; в колонке таблицы такая капа подписана `Lifetime cap`. Переполненная `Lifetime`-капа гейтит выдачу дестинейшена ровно так же, как `Daily` и `Monthly`, — разница только в сбросе. [models/destination.md](../models/destination.md).
- **Destination Full (транзишн)** `[AIO]` — transition шага Destination во флоу — срабатывает, когда у Destination переполнена капа. Визиты уходят в fallback.

- **Offer Visits (метрика)** `[AIO]` — метрика — визиты, попавшие в Destination с типом «оффер» (через `By advertiser`, не Simple Redirect).
- **Proxy to communicate / Proxy / Proxy String** `[AIO]` — поле прокси в интеграции (`user:pass@ip:port`). Лейбл зависит от интеграции: у большинства `Proxy to communicate` (подсказка `Proxy to communicate with API`) или `Proxy`, у доменного провайдера Namecheap — `Proxy String`. Пускает исходящие запросы AIO по этой интеграции через один прокси; **назначение зависит от интеграции:** в `Destination`/брокере — показать получателю лида **один статический** исходящий IP (альтернатива whitelisting'у IP-пула AIO); в `Domain Provider` (напр. Namecheap) — API-запросы AIO к регистратору идут с IP прокси, который надо добавить в вайтлист регистратора ([how-to/domains.md](../how-to/domains.md)); у части `Traffic Filter`-ов (напр. Emailable) — необязательное поле `Proxy` для API-запросов проверки. Поле есть **не во всех** интеграциях — показывается по выбранному `Integration Type`.

## Метрики и аналитика AIO

- **Cohorts Report / Когорты** `[AIO, аналитика]` — отчёт эволюции метрики во времени (когорты по `day` / `week` / `month`). Три селектора: **`Size`** (размерная метрика когорты, напр. `Visits`), **`Target`** (целевая метрика — в списке только событийные), **`Unit`** (day / week / month). Режимы отображения: значение ячейки `Rate` / `Value`, цветовая схема `Single` / `Gradient` / `Positive`, база нормализации `By row` / `Total`, тумблер `Skip +0` (исключить день +0 из нормализации цвета). Слева — сворачиваемый сайдбар metric-фильтров. Помогает увидеть реальный LTV, эффективность ремаркетинга, поздние конверсии. Полные контролы — [how-to/analytics.md](../how-to/analytics.md).
- **Compare Analytics / Comparative analytics / Сравнительная аналитика** `[AIO, аналитика]` — отчёт сравнения двух периодов в интерфейсе недоступен: пункта в меню `Analytics` нет. Разрезы за период — `Roll Up report`, динамика по когортам — `Cohorts report` ([how-to/analytics.md](../how-to/analytics.md)).
- **Roll Up report** `[AIO, аналитика]` — агрегированный отчёт по выбранным групёрам (Groupers). Группировка по нескольким уровням (например, `Destination → Campaign Owner`, `Advertiser → Destination`). Фильтры слева. Часто используется для анализа buyer-performance, оптимизации связки Advertiser+Destination, разбора по любым FB-параметрам. В MTK открывается пунктом `Pivot Reports` (в русском меню — «Сводные отчёты») вкладки `Analytics`. [how-to/analytics.md](../how-to/analytics.md).
- **BI Builder (Analytics)** `[AIO]` — конструктор кастомных дашбордов из чарт-виджетов (`Analytics → BI Builder`); разговорное «Builder». Не путать с `Form Builder` / `PWA Builder` — это другие сущности. [how-to/bi-builder.md](../how-to/bi-builder.md).
- **Live Pulse** `[AIO, аналитика]` — страница `Analytics → Live Pulse` (в MTK — `Analytics → Pulse`) с живым потоком событий трафика: `init` (визит зарегистрирован), `handle` (дискретное событие флоу), `conversion` (создана конверсия). Счётчики копятся только пока страница открыта и обнуляются при перезагрузке — **это не отчёт**, сверять его цифры с таблицами и отчётами нельзя. [how-to/live-pulse.md](../how-to/live-pulse.md).
- **Session Analytics** `[AIO, аналитика]` — страница `Analytics → Session Analytics` (ERP-only): список записей сессий с плеером записи + сравнение scroll/click-карт нескольких лэндов рядом. [how-to/session-analytics.md](../how-to/session-analytics.md).

- **`Remarketing count`** `[AIO, метрика]` — метрика-счётчик событий рассылки: `Sent`, `Failed`, `Delivered`, `Opened` (мультиселект `Events`) с необязательным фильтром по каналу (`Channels` — `WebPush`, `Telegram`, `SMS`, `Email`). Сама не появляется: в ERP её заводят в `Settings → Metrics` карточкой `Remarketing count` (в меню MTK этого раздела нет); в ERP-шаблонах и MTK iGaming она уже заведена четвёркой `Sent Pushes` / `Delivered Pushes` / `Opened Pushes` / `Failed Pushes` плюс формула `Push Open Rate %` (в MTK Finance, MTK Nutra и MTK Sweeps этих метрик нет). Считает **события, а не визиты**. Каналы `SMS` и `Email` в фильтре есть, но событий по ним не бывает (эти каналы не отправляются), а `Delivered` / `Opened` приходят только с web-push ремаркетинг-кампании. На страницах раздела `Marketing` проходят только она и формулы целиком над ней — поэтому CTR и open-rate собираются метрикой `Computable metric` поверх неё. [models/metric.md](../models/metric.md).
- **`Send Result` (группировка вкладки `Remarketing`)** `[AIO, аналитика]` — разрез отправок по исходу: `Success` у доехавшего сообщения, `push_failed` (отправка не удалась — сюда же попадает визит без push-подписки), `dead_endpoint` (подписка мертва), плюс три платформенных лимита — `daily_limit`, `hourly_limit`, `min_interval`. Соседние группировки той же вкладки — `Campaign`, `Flow`, `Templates`, `Channel` и время (`Day` / `Hour` / `Month` / `Year`). Что делать с каждым исходом — [how-to/remarketing-campaigns.md](../how-to/remarketing-campaigns.md).

- **Valuable** `[AIO, признак визита]` — у визита есть конверсия с `revenue > 0`. Не то же самое, что «есть конверсия»: конверсия без выручки признак `Valuable` не даёт. Виден колонкой `Valuable` в таблице сессий и приходит признаком в `conversion`-событиях `Live Pulse`. [how-to/session-analytics.md](../how-to/session-analytics.md).
- **Qualified Visits** `[AIO, метрика]` — чистая база воронки: визиты, у которых точно загрузился JS на лэнде (значит, точно работают Heatmaps, Video Sessions, A/B-сплитование, антифрод-фингерпринт). Основные метрики построены на `Visits` (полная аналитика); Q.V. используют как срез качества. [mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md).
- **EPL / EPL$** `[AIO, метрика]` — earnings per lead (доход на лид). `EPL` и `EPL$` — **одна и та же метрика**, различаются только названием (приставкой), никакого отдельного показателя `EPL$` нет. Имена метрик задаются произвольно в `Settings → Metrics` (создаёт / переименовывает / редактирует свободно), поэтому расхождение в написании — норма, а не разные сущности. Механика метрик — [models/metric.md](../models/metric.md).
- **Visit Loss / Потеря визитов** `[AIO, метрика]` — доля визитов, у которых не отработал JS лэнда: в шаблонах — `Visits Loss %` = `(Visits − Qualified Visits) / Visits` (в шаблонах iGaming этой метрики нет). Высокая потеря — индикатор проблем со скоростью лэнда / сетью / клиентскими блокировщиками. Визиты, помеченные `Trash`, в Visit Loss **не входят**: обычные метрики (кроме костов) trash-визиты не считают, их считает только метрика с флагом `Trash` (в шаблонах — `Trash Visits`). [mechanics/visit-lifecycle.md](../mechanics/visit-lifecycle.md).
- **Trash / Trash Visits** `[AIO]` — визиты с признаком `is_trash`: обычные метрики их не считают — только метрика с флагом `Trash` (в шаблонах — `Trash Visits`, в разрезах по кампании и источнику); причина — в поле `Trash reason`. Хранятся в отдельной таблице (не `Visits`); полей меньше — только нужные для понимания причины. Хранятся **всегда** (без ограничения по времени).
- **Attribute by events time** `[AIO, переключатель аналитики]` — тоггл в таблицах аналитики (подсказка: `Attribute by event time (Also known as conversion time attribution)`); переключает атрибуцию конверсии с «времени визита» (дефолт) на «время самого события». Влияет на распределение конверсий по дням. По дефолту выключен. Разговорное: «Attribution by Event Time», «атрибуция по времени события».
- **Colorize** `[AIO, аналитика]` — подсветка строк таблицы по значению метрики (`Colorize rows`): градиентом (`Gradient`) или диапазоном `Static` с границами `From` / `To` — ниже, внутри и выше диапазона строки красятся красным, жёлтым и зелёным с учётом того, лучше для метрики большее или меньшее значение. Помогает быстро увидеть «хорошие» и «плохие» строки.
- **Highlight Row** `[AIO, экшен]` — экшен в таблице: добавить фильтр по текущей строке. Удобный способ быстро сужать отчёт без ручного добавления фильтра.
- **Unwrap tree view / Анврап дерева** `[AIO, аналитика]` — кнопка-иконка в `Roll Up report` (тултип `Unwrap tree view`, обратно — `Default tree view`; рядом `Collapse all` сворачивает ветки), которая разворачивает древовидную группировку в плоский список всех комбинаций. Удобно, когда нужно сразу видеть все сочетания, а не разворачивать ветки по одной. Разговорное: «развернуть дерево», «Expand Tree».
- **Build Roll Up report** `[AIO, экшен]` — экшен из таблицы аналитики (правая кнопка): открыть Roll Up report с уже подставленным фильтром по выбранному элементу (кампании, источнику и т.п.). Сокращает количество кликов.
- **`Landing` (позиционный группер лэнда: `First` / `Second` / `Third`)** `[AIO, аналитика]` — группировка по лэнду на конкретной позиции воронки визита. В каталоге групперов это **одна строка `Landing`** с пикером позиции; отдельных строк `LP #1` / `LP #2` / `LP #3` там больше нет — подписи стали `Landing 1` / `Landing 2` / `Landing 3`. Сами ключи групперов не менялись — поменялись только подписи. В том же пикере под позициями, за разделителем, лежат роль-групперы по типам лэндов (см. `LP: <Тип>`). Какие ещё серии свёрнуты в строку с пикером — [how-to/analytics.md](../how-to/analytics.md).
- **`LP: <Тип>` (роль-группер: лэнд в роли типа на любой позиции)** `[AIO, аналитика]` — группер категории `Funnel`, по одному на каждый тип лэнда тенанта с включённым `Generate events?` (у типа без него группера нет — поэтому в пикере не все типы). Отвечает на «какой лэнд играл роль этого типа» независимо от позиции в воронке: значение строки — сам лэнд, а не тип; если у визита несколько лэндов одного типа, берётся первый; визит без лэнда этой роли в строки и футер не попадает, строки не пересекаются. В каталоге не отдельная строка: живёт в пикере строки `Landing` под позициями `First` / `Second` / `Third`, за разделителем, бейджем типа с его иконкой и цветом; на чипе подписан `Landing: <тип>`, в списке фильтров таблицы — `LP: <имя типа>` (тем же ключом таблицу можно и фильтровать). Ключ разбивки (он же в Pivot Report API) — `landing_of_type[<uuid типа>]`. Разбивки «лэнд в любой позиции» строкой на каждое участие или «весь путь визита одной строкой» в продукте нет. (разг.: «где лэнд участвовал», «лэнд как преленд», «лэнд в роли оффера») [how-to/analytics.md](../how-to/analytics.md).
- **External Reports** `[AIO]` — настраиваемые внешние отчёты в `Settings → External reports` (только ERP). Типы: `Visits CSV`, `Google Conversions CSV`. Каждый отчёт имеет UUID + Secret (Secret защищён 2FA). Отчёт скачивается через URL вида `https://app.aio.tech/api/v1/external-reports/data?uuid=...&secret=...`. Для Google Conversions в ссылке обязательны `gclid=GCLID_FIELD_UUID` (UUID поля с GCLID) и `deep=N` (сколько прошедших дней включить, от 1 до 31); необязательны `rename[Lead]=...`, `filters[FIELD_UUID]=value`, `timezone=...`.
- **Pivot Report API** `[AIO, API]` — `POST /api/v1/pivot-report/data?token=...`. Возвращает pivoted-датасет: группировки по `definitions` (порядок задаёт вложенность) + фильтры через `conditions` (AND) + пять обязательных булевых флагов тела (`event_time_attribution`, `back_fix_attribution`, `hide_bots`, `hide_trash`, `hide_empty_metrics`). В Pivot-пути реально влияют только `event_time_attribution` и `hide_empty_metrics`; `back_fix_attribution`/`hide_bots`/`hide_trash` — no-op, trash скрыт всегда (полярность и путь Tables Data — [how-to/api.md](../how-to/api.md)). Опциональный header `x-tenant-id` — для токенов с доступом к нескольким тенантам. Ответ — дерево значений группировок; в его листьях значения метрик лежат под UUID метрик — без префикса `metric_` и без обёртки `placeholders` ([how-to/api.md](../how-to/api.md)).
- **Fields & Groupers Catalog — Tracker / Location / Browser / OS** `[AIO, API]` — ключи `clickhouse_key` для `definitions[].key` (группировка) и `conditions[].key` (фильтр) в Pivot Report API. Первые четыре категории:
  - **Tracker:** `visit_uuid`, `campaign_uuid`, `source_uuid`, `flow_uuid`, `split_group` (A/B-корзина, когда задана).
  - **Location:** `location_city`, `location_continent`, `location_country_code` (ISO country code), `location_time_zone` (IANA timezone).
  - **Browser & Device:** `browser_language_code` (напр. `en`, `fr`), `ua_client_engine/family/name/type/version` (`ua_client_engine` — Blink/Gecko и т.п.; `ua_client_type` — browser/app/bot), `ua_brand_name`, `ua_device_name`, `ua_model`, `user_agent`.
  - **OS:** `ua_os_name` (Windows/Android/iOS и т.п.), `os_combined` (нормализованный OS + версия), `ua_os_platform`, `ua_os_version`.
- **Fields & Groupers Catalog — Time / Web** `[AIO, API]` — продолжение каталога ключей Pivot Report API:
  - **Time:** `created_at_day/hour/month/week/year` (`created_at_hour` — час конкретной даты, строка на каждый час каждого дня; `created_at_month` / `created_at_year` — дата начала месяца / года; `created_at_week` — дата начала недели: с понедельника или с воскресенья, по `Weekdays start` в профиле юзера токена), `day_part` — номер часа суток `0`–`23`, сумма за все дни периода, а не «утро / вечер» (в таблицах та же строка подписана `09:00 - 10:00`; в фильтр вводится тот же номер: `9` = `09:00 - 10:00`), `week_part` — номер дня недели, сумма за все такие дни периода, а не Weekday / Weekend (в таблицах подписан `Monday` … `Sunday`; нумерация зависит от `Weekdays start` в профиле; [how-to/analytics.md](../how-to/analytics.md)).
  - **Web:** `initial_domain` (первый замеченный домен), `last_domain` (последний домен пути визита — начальный или куда увёл `Domain Change`), `domains[1..3]` (домен на N-й позиции пути, `[1]` — начальный), `initial_path` (первый замеченный path), `agent_version` (версия AIO JS-агента).
  **Attribution:** Time-групёры учитывают `event_time_attribution` из запроса (в Pivot-пути `back_fix_attribution` — no-op, см. [how-to/api.md](../how-to/api.md)).
- **Fields & Groupers Catalog — Landings / Destinations (funnel-ключи)** `[AIO, API]` — продолжение каталога ключей Pivot Report API:
  - **Landings & Types (positional):** `landing_uuids[1..3]`, `landing_type_uuids[1..3]`. `[N]` — порядковый номер в пути самого визита, а не номер ноды флоу: `landing_uuids[1]` = первый показанный лэнд, `[2]`/`[3]` — второй/третий отличающийся; повторный показ того же лэнда позицию не добавляет.
  - **Landing role (any position):** `landing_of_type[<uuid типа лэнда>]` — лэнд, сыгравший роль этого типа на любой позиции (при нескольких лэндах одного типа — первый); тот же ключ, что у группера `LP: <Тип>` в таблицах ([how-to/analytics.md](../how-to/analytics.md)). Аналогичного рабочего ключа по типам адвертайзеров нет.
  - **Creatives (positional, ERP):** `creative_uuids[1..3]` — креатив на N-й позиции из параметра `creative_uuid` входной ссылки (в UI — `Creative #1`…`#3`, [how-to/creatives.md](../how-to/creatives.md)).
  - **Destinations & Advertisers (positional):** `destination_uuids[1..3]`, `advertiser_uuids[1..3]` — `[N]` = N-й **успешный** пуш в отличающийся Destination (реджекты и повторные пуши в тот же Destination позицию не добавляют), а не позиция ноды во флоу; `advertiser_uuids[N]` — адвертайзер того же пуша.
- **Fields & Groupers Catalog — Custom / Facebook / Source** `[AIO, API]` — последняя часть каталога ключей Pivot Report API. Ключи вида `field_*` (`field_fb_ad_name`, `field_fb_ad_id`, `field_launcher` и т.п.) API сейчас не принимает — поле визита задаётся ключом `string_fields[<uuid поля>]`, владелец кампании — `campaign_owner_uuid` в `definitions`; в `conditions` этот ключ не распознаётся — по владельцу фильтруют ключом `string_fields[780102b12-322c-4131-bf84-c292a8793f51]` ([how-to/api.md](../how-to/api.md)). **Cardinality:** `visit_uuid`, `ip_address`, `user_agent` и `ua_client_version` каталог групперов помечает как высокую кардинальность — это ключи для дебага, их ставят вместе с фильтрами.

## Интеграции и постбэки AIO

- **Постбэк** `[общий]` — серверный callback от рекламодателя при конверсии. Используется не только для самого факта конверсии: типичный кейс — апдейты статусов лида (No Answer, Recall, целевое действие), которые рекламодатель шлёт постбэками. Статусы-апдейты сейл-цикла идут через **один** `Conversion Type` `Sale Status Update` (имя статуса — в поле `sale_status`, не в имени типа), см. [models/conversion-model.md](../models/conversion-model.md).
- **Postback generator / Генератор постбеков** `[AIO, экран]` — конструктор ссылки входящего постбэка: зелёная кнопка `Postback generator` в шапке таблицы `Tracker → Conversions`, есть и в ERP, и в MTK. В форме задаются тип конверсии и домен, при необходимости `Visit UUID`, `Destination`, `Delay, sec`, бизнес-модель, валюта и значения полей конверсии; на выходе — готовый URL приёмника, переключаемый между двумя форматами, `Path` и `Query` (у `Path` дополнительно раскрывается блок `Short links with slugs` — те же ссылки со слагом типа вместо UUID). Ничего не сохраняет — ссылку копируют и отдают рекламодателю. Доступ закрыт правом `Features: postback generator` ([models/permissions-model.md](../models/permissions-model.md)). Разбор полей и форматов — [how-to/postback-generator.md](../how-to/postback-generator.md).
- **`conversion-by-key` (формат постбэка)** `[AIO]` — третий формат приёмника конверсий, `https://<домен>/api/v1/trigger/conversion-by-key`, для рекламодателя, который не может переименовать свои параметры: он шлёт идентификаторы своими именами (например, `clickid` — визит, `goal` — тип конверсии), а параметры `visit_uuid_key` и `conversion_type_uuid_key` в той же ссылке сообщают приёмнику, как эти имена читать. В `Postback generator` этот формат не выводится — ссылка собирается руками. Разбор — [models/conversion-model.md](../models/conversion-model.md).
- **Sale Status Mapping** `[общий, НЕ в AIO]` — инструмент в **сторонних системах** (рекламодателях, CRM, партнёрках), который приводит разноимённые сейл-статусы к единому стандарту: `noanswer1` / `no_answer` / `no_ans` → `No Answer`. Используется на стороне клиента/рекламодателя **до** отправки постбэка в AIO. **В самой AIO такого инструмента нет** — статусы записываются как есть в **один** `Conversion Type` `Sale Status Update` (значение в поле `sale_status`, не отдельный тип под каждый статус). Если рекламодателей много и статусы у них разные — стандартизация делается на стороне клиента/рекламодателя, не в AIO (см. [models/conversion-model.md](../models/conversion-model.md)).
- **Auto-login link** `[AIO]` — ссылка автологина, которую интеграция (API-Destination) возвращает при успешном пуше. **Отдельного поля под неё нет** — она лежит в поле визита `destination_url`; форма после пуша редиректит юзера по ней (мгновенно или после задержки), чтобы тот сразу попал в личный кабинет. (Для Destination-редиректа в `destination_url` лежит ссылка, по которой ушёл визит.)
- **Поля визита по Destination** `[AIO, поля визита]` — результат пуша лида в Destination, видны в `Tracker → Visits`: колонка `Pushed` (поле `is_destination_url_passed`, boolean — запушился ли визит в Destination); `Destination` (куда визит запушился); `destination_url` (по какой ссылке визит ушёл в Destination; для API — ссылка автологина, для редиректа — ссылка с подставленными плейсхолдерами); `destination_external_id` (UI: `Destination External ID` — ID лида, возвращённый внешней системой). При реджекте от рекламодателя пишутся ещё три поля: `rejected_destination_uuid` (UI: `Rejected Destination` — какой Destination отклонил лид), `rejected_advertiser_uuid` (UI: `Rejected Advertiser` — его адвертайзер, если есть) и `last_rejection_reason` (UI: `Last Rejection Reason` — текст причины реджекта, записанный **прямо в поле визита**, так что логи ради причины открывать не обязательно). Сам запрос/ответ пуша — в `Settings → Logs` → namespace `Destination Handler`. [models/conversion-model.md](../models/conversion-model.md).
- **Webhook** `[общий]` — входящий webhook Slack, через который Notification Center проксирует уведомления в Slack (задаётся в Preferences, [mechanics/notification-center.md](../mechanics/notification-center.md)). Алерты о падении сервера приходят только в Telegram через Monitoring User.
- **By integration** `[AIO]` — способ создания Destination по готовой интеграции из каталога (окно `Create destination by integration`); другие способы в том же выборе — `Simple redirect`, `Telegram`, `By advertiser`.
- **Generator** `[AIO, Settings]` — подключение к провайдеру генераций в `Settings → Generators` (только ERP): `Generator name` + `Integration type` (`AIO Site Generator`, `Higgsfield` или внешний генератор сайтов) + блок `Settings` под тип — у `Higgsfield` и внешнего генератора там `API Key`, у `AIO Site Generator` вписывать нечего. Через подключение запускаются генерации (`Generation`) на странице `Content → Generations`; у подключения есть владелец, `Access type`, шаринг и архив, права — `settings.generators.*`. [how-to/generations.md](../how-to/generations.md). **Не путать с `Link Generator`** — тот генерирует трекинг-ссылки кампании (см. `Generate Link / Link Generator` ниже).
- **AIO Site Generator** `[AIO, Generator]` — генератор сайтов AIO: тип подключения в `Settings → Generators` для генераций `Landing`. Три режима поля `Mode`: `Ready site` (готовый сайт из пула), `Generate to order` (сайт под заказ за минуты), `Huge site by brief` (большой сайт на 32–38 страниц по описанию бренда, до 60 минут). В `Ready site` без точного совпадения по `If no exact match` делается сайт под заказ (по умолчанию) или выдаётся ближайший готовый (`Closest ready site`, метка `closest match`); ключей вписывать не нужно. В форме запуска помечен `Free for now — we're testing AIO Site Generator before the paid launch.` [how-to/generations.md](../how-to/generations.md).
- **Higgsfield** `[AIO, Generator]` — сторонний AI-сервис картинок: тип подключения в `Settings → Generators` для генераций `Creative`, подключается `API Key` своего аккаунта Higgsfield; в форме запуска — `Model`, `Prompt`, `Aspect ratio`, `Quality`. Генерации оплачиваются кредитами этого аккаунта. [how-to/generations.md](../how-to/generations.md).

- **Destination Integrations** `[AIO]` — партнёрские интеграции в `Destinations`. Все интеграции реализованы через единый механизм JSON Schema Builder: каждая интеграция имеет имя и свой набор обязательных полей (например, API URL, API Key + специфичные для платформы поля типа Offer ID / Affiliate ID / Username). Список интеграций постоянно расширяется. Примеры из каталога: IREV, Getlinked, Trackbox, LeadGreed, Elnopy; в шаблонах Finance и Nutra заведены дестинейшены-примеры `Example IREV Integration` и `Example Bridge Integration`, в Nutra ещё примеры под четыре партнёрские интеграции. Наборы обязательных полей для самых частых:
  - **IREV** — API URL, API Key, `IREV Affiliate ID`, `IREV Offer ID`.
  - **Getlinked** — API URL, API Key; `Offer Name` и `Comment field` — необязательные.
  - **Trackbox** — API URL, API Key, API Username, API Password, `Ai`, `Ci`, `Gi`.

  Новая интеграция добавляется по запросу в чат с командой AIO — нужно передать API-документацию + credentials, команда AIO добавляет шаблон. У способа `By integration` поля зависят от выбранной интеграции: в окне `Create destination by integration` показываются параметры под конкретную платформу — сверяться с её API-документацией.
- **Destination Payload (типы)** `[AIO]` — конфигурация дестинейшна: API-интеграция (`By integration` или `By advertiser`, с полями под платформу), `Simple redirect` (URL с плейсхолдерами) или `Telegram`. В Simple Redirect для передачи данных используются плейсхолдеры визита: `{{aio.visit.uuid}}`, `{{aio.visit.fields.phone}}`, `{{aio.visit.fields.email}}`, `{{aio.visit.fields.first_name}}`, `{{aio.visit.fields.last_name}}`.
- **Запрос новой интеграции** `[AIO, процесс]` — если интеграции нет в списке: запрос в чат → API-доки + креды для тестового пуша → дальше команда AIO добавляет шаблон интеграции. См. *уточните у поддержки*.
- **IPInfo** `[AIO, интеграция]` — обогащение визита данными по IP (тип IP, geo, сеть, компания, анонимность). Подключается как `Traffic Filter` (раздел `Settings → Traffic filters` есть только в ERP); обогащение идёт силами AIO, токена в настройках нет. Ответ пишется в поля визита, которые заранее **создаются вручную** в `Settings → Fields` со **snake_case** slug ([how-to/custom-fields.md](../how-to/custom-fields.md) → Пачка полей под IPInfo).
- **IPQuality / IPQuality Score** `[AIO]` — **отдельного типа `Traffic Filter` под IPQuality в AIO нет**: отдельным шагом во флоу он не ставится. Отдельный `Traffic Filter`, который дописывает в визит IP-данные, — `IPInfo` (см. запись выше).

## Команды и пермишены AIO

- **Folder sharing / Шаринг папки** `[AIO]` — шаринг папки раздаёт доступ её содержимому: всё, что лежит в папке, получает роль папки (без `Can share further`), а лэнды и дестинейшены кампаний из папки — роль `Use`. Сущность, положенная в уже пошаренную папку, получает для каждого получателя папки ту же роль, `Can share further` и срок, что у его шары на папку; вынутая из папки — теряет шаринг этих получателей, включая выданный ей напрямую. Папки открываются кнопкой с иконкой папки в верхней панели таблицы (подсказка `Folders: …`, только ERP), шаринг — правый клик по папке в списке → `Share`. Шарить папку может Owner или Admin тенанта (и тот, кому они выдали на папку `Can share further`). [how-to/permissions.md](../how-to/permissions.md).
- **Tenant / Тенант** `[AIO]` — см. раздел «Инфраструктура». Сущность называется `Tenant`; отдельного понятия «Workspace» нет — словом workspace в нескольких подписях интерфейса назван тот же тенант (например, `Enter the name of your workspace` при регистрации).
- **Teams** `[AIO]` — команды внутри `Tenant`-а (`Settings → Teams`). У каждого участника — уровень `Level N`, целое число от 0 до 100: кто выше по уровню в команде, получает уровень доступа `Own` на объекты всех, кто ниже (видит, правит, шарит, меняет владельца, архивирует). Равные по уровню объекты друг друга по умолчанию не видят, а пошаренное нижестоящим вверх по умолчанию не поднимается — оба правила настраиваются на каждом уровне кнопками `Peers:` и `Below:`. Шара на команду достаётся всем её участникам независимо от уровня. Ролей `Team Member` / `Team Leader` / `Team Head` больше нет — они переведены в уровни 0 / 1 / 2. Создаёт команду Owner или Admin (или позиция, где есть и `settings.teams.edit`, и `Editor Scopes` на команды); править её может ещё и участник с самым высоким уровнем в ней (при том же праве Position `settings.teams.edit`). Сотрудник без `Scopes` на команды видит в `Settings → Teams` только команды, где состоит; колонки таблицы — `Managers` и `Regular Members`. [models/permissions-model.md](../models/permissions-model.md).
- **`Peers:` / `Below:` (настройки уровня команды)** `[AIO]` — две кнопки у каждого уровня в диалоге команды (RU `Равные:` / `Снизу:`). `Peers:` задаёт, что равные по уровню получают на объекты друг друга (`No access` по умолчанию, `Use`, `View`, `Edit` или `Own`), а `Below:` — что поднимается к уровню от нижестоящих сверх их собственных объектов (`Owned only` по умолчанию, `Owned and direct shares` или `Owned and all shares`). [models/permissions-model.md](../models/permissions-model.md).
- **Roles & Permissions / Positions & Imperatives** `[AIO]` — система прав. Базовые роли: **Owner / Admin** (полный доступ), **Employee** (доступ по правам своих Positions и по уровню доступа к каждому объекту). Кастомные **Positions** (наборы пермишенов) присваиваются юзерам; внутри Position лежат **Imperatives** разных типов (`Imperative Types`) — они решают, какие страницы и действия доступны. С каким конкретным объектом можно работать, решает уровень доступа `Use` / `View` / `Edit` / `Own`. Если у юзера несколько Positions — действует Priority (более высокий приоритет перекрывает более низкий).
- **Imperative Types** `[AIO]` — типы пермишенов внутри Position. По убыванию scope:
  - **Sections** — целые секции (`Analytics section`, `Content section`, `Meta section`) со всеми subsections и actions.
  - **Subsections** — конкретные подсекции (`Content: CDN files`, `Content: landings`, `Settings: distributions`).
  - **Pages** — конкретные страницы (`Content: CDN files page`, `Tracker: campaigns page`). Только просмотр, без actions.
  - **Actions** — конкретные действия (`Content: landings edit`, `Content: landings archive`, `Content: landings assign folder`, `Content: landings upload`).
  - **Features** — спец-фичи, закрытые отдельно от раздела, где живут (их восемь — статья «Feature-императивы»).
  - **Sharing & Ownership Change** — право шарить (`<раздел>.share`) и менять владельца (`<раздел>.share.ownership`, подпись вида `Tech: servers ownership change`) в разделе; на сам объект для шаринга нужен ещё уровень `Own` или шара с `Can share further`, для смены владельца — только `Own`.
  - **Scopes** / **Editor Scopes** — доступ ко всем объектам раздела без шаринга: уровень `View` / `Own` (статья «Scopes / Editor Scopes»).

  В одной Position могут комбинироваться через **Allow/Deny** toggle. Логи — не отдельный тип (статья «Право на логи»). [models/permissions-model.md](../models/permissions-model.md).
- **Право на логи (`settings.logs.view`)** `[AIO]` — отдельного типа императивов для логов нет: все пункты `Show logs` на сущностях и страница `Settings → Logs` открываются одним правом `settings.logs.view` (в списке императивов — `Settings: logs page`). [how-to/debug-with-logs.md](../how-to/debug-with-logs.md).
- **Feature-императивы** `[AIO]` — права Position на спец-фичи, закрытые отдельно от раздела, где они живут; их восемь: только в ERP — `Features: sessions`, `Features: heatmaps` и `Features: notes edit` (`features.notes.edit` — остался от заметок, на комментарии не влияет), в ERP и MTK — `Features: notes` (комментарии к кампаниям и лэндам, [how-to/comments.md](../how-to/comments.md)), `Features: conversions revenue`, `Features: conversions payout`, `Features: table export`, `Features: postback generator`. [models/permissions-model.md](../models/permissions-model.md).
- **Scopes / Editor Scopes** `[AIO]` — права Position на все объекты раздела без шаринга: `Scopes: <раздел>` (`scopes.<раздел>`, например `Scopes: tracker campaigns`) даёт уровень `View`, `Editor Scopes: <раздел>` (`edit-scopes.<раздел>`) — `Own`, то есть видимость, правку, шаринг, `Change ownership` и архив без отдельного `Scopes`. Сам раздел ветка не открывает и за ключи действий не засчитывается: её выдают вместе с ключами раздела (`Allow <раздел>`), иначе раздела нет в меню, а действия отказывают `Action access denied`. Ветки есть у большинства разделов с шарингом (часть — только в ERP), в матрице подписаны `Scopes: <раздел>` / `Editor Scopes: <раздел>`. [models/permissions-model.md](../models/permissions-model.md).

- **Position Priority** `[AIO]` — числовой приоритет Position. Когда у юзера несколько Positions, при конфликте Allow/Deny одной и той же permission Win более высокий Priority.
- **Базовые роли** `[AIO]` — три базовые роли юзера в тенанте:
  - **Owner** — владелец тенанта, полный доступ: уровень `Own` на все объекты тенанта, все права Positions, инвайты, смена ролей, `Log in as user`.
  - **Admin** — полный доступ, как у Owner (но войти под Owner через `Log in as user` не может).
  - **Employee** — доступ по правам своих Positions и по уровням доступа: свои объекты, объекты тех, кто ниже в его командах (и равных по уровню — если так настроено `Peers:`), объекты, открытые всем через `Access type`, пошаренное ему и любой его команде, все объекты разделов со `Scopes` / `Editor Scopes` (страницу раздела при этом открывает только её ключ).

  Поверх базовой роли — кастомные Positions для тонкой настройки. [models/permissions-model.md](../models/permissions-model.md).
- **Уровни доступа к объекту: `Use` / `View` / `Edit` / `Own`** `[AIO]` — лестница, по которой считается доступ юзера к каждому объекту, каждый уровень включает предыдущие: `Use` — объект виден в списках и селектах, карточка закрыта; `View` — карточка открывается на чтение; `Edit` — правка настроек и операционные действия; `Own` — плюс смена владельца и `Access type`, архив и раздача доступа. Итоговый уровень — максимум из источников: владение, команда, `Access type`, шаринг, `Scopes` / `Editor Scopes`, роль Owner / Admin. [models/permissions-model.md](../models/permissions-model.md).
- **Access type** `[AIO]` — поле шарящейся сущности, которое открывает объект всем в тенанте: `Private` (`Приватный`) — никому сверх обычных источников доступа, `Use` (`Использование`) — все видят объект в списках и селектах, `View` (`Просмотр`) — все открывают карточку на чтение. Править чужой объект `Access type` не позволяет ни при каком значении; меняется поле в диалоге `Change ownership`, а в данных и API значения записаны как `By Share` / `Everyone` / `View` (`Everyone` = `Use`). [models/permissions-model.md](../models/permissions-model.md).
- **Your access** `[AIO, интерфейс]` — нижняя строка меню правого клика в таблицах шарящихся сущностей и шапка диалога `Share`: `Your access: <уровень>` (`Use` / `View` / `Edit` / `Own` или `none`, RU `Ваш доступ`). Наведение показывает, откуда доступ (`owner`, `shared with you`, `subordinate’s object`, `position`, `full access` и другие источники), и что уровень разрешает, — это первое, что смотреть, когда в меню нет нужного пункта или карточка открывается только на чтение. [models/permissions-model.md](../models/permissions-model.md).
- **Share (диалог шаринга)** `[AIO, экшен]` — выдача доступа к конкретному объекту юзерам или командам: у каждого получателя роль `Use` (виден в списках и селектах, настройки закрыты), `Viewer` (плюс карточка на чтение) или `Editor` (правка), флаг `Can share further` и срок `Expires` (по умолчанию `No expiry`). Роль выше своего уровня выдать нельзя, ролей `Owner` и `Share` у шары больше нет, а сам пункт `Share` есть в меню строки, только если у вас на объект уровень `Own` или шара с `Can share further`. [how-to/permissions.md](../how-to/permissions.md).
- **Can share further** `[AIO]` — флаг шары в диалоге `Share` (`Может раздавать дальше`): получатель может сам шарить объект дальше с ролью не выше своей, но выдать кому-то этот флаг не может — его включает только тот, у кого на объект уровень `Own`. Старые шары с ролями `Share` и `Owner` означают `Editor` + `Can share further` и владельцем не делают. [how-to/permissions.md](../how-to/permissions.md).
- **Invite User / Invitation Link** `[AIO]` — добавление нового юзера в тенант через `Settings → Users → +User`: короткая форма — `Position` и `Team`, приглашает с ролью `Employee`; в ERP стрелка рядом с `+User` → `Invite user` открывает расширенную форму — Name, Description, Code, Usages (сколько раз можно использовать), Status, Type (User), Till Date, Role, Position, Team. Генерируется инвайт-линк; юзер регистрируется по ссылке и попадает в выбранную команду на уровень 0 (поднять уровень — в диалоге команды). Создавать инвайты может только Owner или Admin тенанта. [models/permissions-model.md](../models/permissions-model.md).
- **Mass Sharing экшены** `[AIO]` — действия группы `Teams & permissions` при выделении нескольких строк:
  - **Share also** — добавить доступ, где его нет; существующую шару не понижает (роль только повышается, срок не меняется).
  - **Force share** — перезаписать доступ: в диалоге заранее стоят все, у кого есть доступ хотя бы к одному выделенному объекту, и всем оставшимся роль, `Can share further` и срок выставляются одинаково на всех выделенных (по умолчанию `Viewer` без раздачи и без срока — у кого был `Editor`, понизится); убранные из списка теряют доступ.
  - **Unshare** — снять доступ у выбранных.
  - **Mass change ownership** — массово сменить владельца (тот же диалог, что `Change ownership`).

  Действие применяется к тем объектам, на которые хватает вашего доступа, остальные пропускаются: итог — тост `Applied: N` · `Skipped: M` с причиной (`no access`, `role above your level`, `not granted by you` и другие). [models/permissions-model.md](../models/permissions-model.md).
- **Log in as user** `[AIO, экшен]` — вход Owner или Admin тенанта под другого активного юзера того же тенанта (Admin — не под Owner), чтобы увидеть интерфейс и доступы его глазами: `Settings → Users` → правый клик по юзеру → `Log in as user` (`Войти под юзером`, только ERP). Сессия длится до 2 часов, выход — `Exit` на плашке `You are logged in as …` или `Exit impersonation` в меню профиля; всё сделанное пишется в логи от имени юзера с пометкой, кто зашёл. [how-to/permissions.md](../how-to/permissions.md).
- **Логирование** `[AIO]` — по каждому успешному действию (экшену из интерфейса или API) пишется запись с IP, User-Agent и временем (`Settings → Logs`, namespace `Actions`) — аудит-след действий пользователей.

## Конверсии и метрики AIO

- **Trigger Conversion** `[AIO, действие]` — ручная быстрая отбивка конверсии на визит: в ERP — правый клик по визиту в `Tracker → Visits` → `Trigger Conversion` (в MTK у таблицы визитов контекстного меню нет). Конверсии, отбитые этим экшеном, помечаются в БД как `manual` (отдельной колонкой это пока не выводится).
- **Conversion Type** `[AIO]` — кастомный тип конверсии. Создаётся в ERP кнопкой `+ Conversion type` в `Settings → Conversion Types` (в MTK этого раздела нет — типы приходят из шаблона или их заводит команда AIO). Постбэки от внешних систем приходят на UUID или slug этого типа. Набор типов в шаблоне тенанта зависит от вертикали: Finance — `Lead`, `Lead Rejected`, `Fraud Lead`, `Push Subscribe`, `Sale Status Update` и тип под целевое действие; Nutra — `Lead`, `Approved`, `Rejected`, `Trash`, `Push Subscribe`, `Upsell`; Sweeps — `Lead`, `Registration`, `Fraud Lead`, `Lead Rejected`, `Push Subscribe`; iGaming — `Install`, `Open PWA`, `Registration`, `Push Subscribe`, `Correction` и типы под целевые события ([context/architecture.md](../context/architecture.md)). Конкретные типы (`Lead`, `Sale Status Update` и т.п.) описаны как отдельные термины в этом глоссарии.
- **Conversion Type — атрибуты** `[AIO]` — поля при создании/редактировании Conversion Type:
  - **Name**, **Color**, **Description** — отображение (`Color` — цвет в `Tracker → Conversions`).
  - **Is registry?** — у Conversion Type такого переключателя нет: флаг `Is registry?` есть только у **поля** визита (см. `Атрибуты поля`).
  - **Slugs** — один или несколько slug'ов. Параметр `conversion_type_uuid` принимает UUID типа **либо** любой его slug — равнозначно.
  - **Uniqueness Strategy** — сколько раз конверсия этого типа может быть создана на один визит. См. отдельный термин.
  - **Business Value** — `Good` / `Neutral` / `Bad`. Влияет на `Reward` в AI-оптимизации.
  - **Reward Weight** — числовой вес для AI-оптимизации.
  - **Correction type** — тип для конверсий-коррекций (сам он должен быть `Multiple Infinity`): у типа со стратегией `Single Conversion` повторный постбэк с другим revenue создаёт конверсию-коррекцию на разницу. Итог — в поле `Revenue` (не `Reward`).
  - **Payout Settings** / **Revenue Settings** — привязка к дистрибуциям Payout / Revenue.
  - **Notification Flow** — `Notification Flow` (синоним — `Marketing Flow`), запускается при поступлении конверсии этого типа.
  - **Поля конкретной конверсии:** Geolocation, Visit Date, Conversion Date, **Delta**, Revenue Amount, Campaign, Source, Destination + кастомные поля (например, `sale_status`).
- **Uniqueness Strategy** `[AIO, атрибут Conversion Type]` — определяет, сколько раз конверсия этого типа может быть создана для одного визита. Три варианта:
  - **Single Conversion** — одна на визит. Для событий, которые случаются один раз: в шаблонах так заведены `Lead`, `Registration`, `Install`, `Open PWA`, `Push Subscribe`, `Approved`, а в Nutra и `Rejected` / `Trash`.
  - **Multiple Infinity** — без лимита. Для серий апдейтов: `Sale Status Update` принимает каждый новый статус от рекламодателя как отдельную конверсию, накапливая историю; в шаблонах Finance и Sweeps так же заведены `Lead Rejected` и `Fraud Lead`, в iGaming — `Correction`, в Nutra — `Upsell`.
  - **Multiple By Unique** — несколько на визит, но с **дедупликацией по полю `unique`**. Постбэк должен передавать параметр `&unique=<значение>`. Конверсии с одинаковым `unique` для того же визита считаются дублями и повторно не создаются. Используется когда нужен ровно один уникальный ивент на какое-то значение (например, один пуш на один offer_id, или один Add to Cart на одну product_uuid в рамках визита).

  Полная механика — [models/conversion-model.md](../models/conversion-model.md).

- **Sale Status Update** `[AIO, Conversion Type]` — Conversion Type с `Uniqueness Strategy = Multiple Infinity`; в шаблонах Finance заведён без slug (постбэк адресуется по UUID типа, slug вроде `sale_status` добавляют сами). Используется для фиксации **истории сейл-статусов** лида у рекламодателя между моментом регистрации (`Lead`) и финальной конверсией (`Lead Rejected` / целевое действие). Каждый постбэк рекламодателя создаёт новую конверсию; если в нём есть `visit[current_sale_status]` и такое поле визита заведено, он же перезаписывает поле `current_sale_status`. Механика SSU-постбэка — [models/conversion-model.md](../models/conversion-model.md).

- **current_sale_status** `[AIO, поле визита]` — последний актуальный сейл-статус лида от рекламодателя; обновляется через постбэк параметром `visit[current_sale_status]=<статус>` вместе с конверсией `Sale Status Update`. Используется для аналитики (фильтры/группировки по текущему статусу) и маршрутизации флоу (повторные касания только визитов в `No Answer`). [models/conversion-model.md](../models/conversion-model.md).

- **Conversion Postback URL** `[AIO]` — URL для приёма постбэков от внешних систем (рекламодателей, партнёрок) о конверсиях. Формат:
  ```
  https://<любой_домен_тенанта>/api/v1/trigger/conversion-request
    ?visit_uuid=<...>
    &conversion_type_uuid=<...>
    &<параметры>
  ```
  Тенант определяется по `visit_uuid` (UUID глобально уникален). Любой домен тенанта принимает постбэки.

  **Параметры:**
  - `visit_uuid` (обязательно) — UUID визита. Внешняя система подставляет через макрос (`{CLICK_ID}`, `{aff_sub}` и т.п. — зависит от системы).
  - `conversion_type_uuid` (обязательно) — UUID Conversion Type в AIO или любой его slug.
  - **Поля конверсии** — без префикса (`arrived_revenue=10`, `sale_status=...`). Пишутся в конверсию, если в тенанте есть поле с таким slug.
  - **Поля визита** — с префиксом `visit[]` (`visit[current_sale_status]=...`, `visit[<any_field>]=...`). Обновляют поле визита. Работает для любого существующего поля визита.

  **Пример полного URL** для Sale Status Update:
  ```
  https://app.aio.tech/api/v1/trigger/conversion-request
    ?visit_uuid={CLICK_ID}
    &conversion_type_uuid=<UUID-sale-status-update>
    &arrived_revenue={revenue}
    &visit[current_sale_status]={sale_status}
    &sale_status={sale_status}
  ```
  Эта строка передаётся внешней системе при настройке постбэков на её стороне. Механика постбэков — [models/conversion-model.md](../models/conversion-model.md).

- **Rejected (как Conversion Type)** `[AIO]` — отдельный тип конверсии под отказ дестинейшна (невалидный номер, дубль, не та страна и т.п.) с `Business Value = Bad`. В шаблонах он называется по-разному: `Lead Rejected` и `Fraud Lead` (Finance, Sweeps — `Multiple Infinity`), `Rejected` и `Trash` (Nutra — `Single Conversion`, с десятками slug-синонимов под статусы партнёрок вроде `declined`, `cancelled`, `spam`); в флоу-примерах `Fraud Lead` / `Trash` спавнит шаг `Spawn Fraud Lead` / `Spawn Trash Lead` после провала `Check Antifraud Points`.
- **Push Subscribe (как Conversion Type)** `[AIO]` — отдельный тип конверсии под факт подписки визита на push-уведомления. Заводится, чтобы отдельно мерить «сколько вообще подписалось на пуши». Идёт в паре с `Push Subscribe Toggle` на уровне кампании и `Push Subscribe Script` на лэнде.
- **Business Value** `[AIO]` — бизнес-ценность каждой конверсии. Лейблы — `Good` / `Neutral` / `Bad`:
  - **`Good`** — прибавляется к `Reward` варианта (хорошие конверсии: целевое действие, покупка).
  - **`Neutral`** — ничего не прибавляет (вспомогательные/аналитические конверсии).
  - **`Bad`** — вычитается из `Reward` (плохие исходы: Reject, отказ в платеже). AI-оптимизация направляет трафик туда, где суммарная ценность максимальна.
- **Select** `[AIO, метрика варианта]` — сколько раз вариант был выбран (показан визиту). Используется в `Conversions AI` вместе с `Reward` для расчёта вероятностей при `Thompson Sampling`.
- **Reward** `[AIO, метрика варианта]` — сколько раз для варианта получили целевую конверсию (или сумму ценностей конверсий, если используется `Business Value`). Используется в `Conversions AI` вместе с `Select` для расчёта вероятностей при `Thompson Sampling`.
- **Thompson Sampling** `[общий, алгоритм]` — вероятностный bandit-алгоритм. В AIO — основа `Conversions AI` и `MVT`: для каждого варианта сэмплирует бета-распределение по накопленным `Reward` и числу показов (`Select`) и на каждом выборе берёт вариант с наибольшим сэмплом. Балансирует разведку и эксплуатацию: лучшие варианты получают больше трафика, но остальные продолжают тестироваться.
- **Epsilon-Greedy** `[общий, алгоритм]` — bandit-алгоритм. В AIO — основа `Metrics AI`: с вероятностью ~10% исследует — выбирает вариант равномерно случайно среди всех вариантов (лучший может переизбраться), — а остальные ~90% эксплуатирует вариант с наибольшим значением выбранной метрики. Реагирует быстрее `Thompson Sampling`, но более «жадный».
- **Timeframe** `[AIO, параметр Metrics AI]` — окно времени, за которое считается метрика для оптимизации (15 минут / час / день / неделя / месяц и т.д.). Чем меньше — тем быстрее адаптация, тем шумнее данные.
- **Re trigger trackers** `[AIO, действие на конверсии]` (синонимы: Retrigger, retrigger конверсии, переотбить конверсию) — экшен на конверсиях, перезапускает их трекеры — повторно шлёт событие в площадку трекера (FB CAPI, TikTok Events API, HTTP Get-постбэк партнёрки и др.). В UI пишется `Re trigger trackers`. Работает и на одной конверсии (правый клик), и пакетно: отметить нужные конверсии чекбоксами → ПКМ → `Re trigger trackers` → `Confirm`. Используется, когда первый пуш не дошёл или настройка отбивки была сломана (не тот пиксель/токен). [models/tracker.md](../models/tracker.md).
- **Show nearby visits (на конверсии)** `[AIO, экшен]` — экшен в меню конверсии (разг. «Show Near»): показывает все конверсии того же визита (например, чтобы увидеть Lead → целевое действие как пару). В открывшемся окне эти конверсии можно посмотреть или скопировать их UUID.
- **Update revenue / Update payout** `[AIO, экшен]` — ручное изменение revenue или payout выбранных конверсий (одной или нескольких сразу).
- **Delta (на конверсии)** `[AIO, поле конверсии]` — время между Visit Date и Conversion Date. Используется для анализа скорости конвертации.
- **Trackers (раздел)** `[AIO]` — исходящая отбивка конверсий из AIO в рекламные площадки и внешние системы: FB CAPI, TikTok Events API, Reddit CAPI, HTTP Get, Slack Webhook и др. ([models/tracker.md](../models/tracker.md)).
- **Alpha-Beta Chart** `[AIO]` — визуализация Conversions AI: распределения CR по вариантам (насколько оттестирован, диапазон реального CR). Внизу карточки стратегии.
- **Show sessions (action)** `[AIO, экшен]` — экшен правой кнопкой в Tracker → Campaigns — список записанных сессий по кампании.
- **Visit timeline** `[AIO, экшен на визите]` — хронология событий одного визита (создание, смена нод флоу, приход на Destination, конверсии, изменения полей); только ERP, пункт видят роли с полным доступом (Owner / Admin). НЕ путать с `Show sessions` (запись сессии) и с логами `Destination Handler` (`Settings → Logs`). Разбор — [how-to/visit-timeline.md](../how-to/visit-timeline.md).
- **Visit logs** `[AIO, экшен на визите]` — в ERP правый клик по визиту в `Tracker → Visits` → `Visit logs` (в MTK — `Settings → Logs` с UUID визита в `Loggable UUID`): логи обработки одного визита, уже отфильтрованные по нему (быстрее, чем копировать `Visit UUID` и собирать фильтр в `Settings → Logs`). Если таблица пустая — проверьте `Severity`: по умолчанию `Debug` исключён, а детальная отладка фильтра и пуша пишется именно на нём. Внутри — все логи визита: проверки трафик-фильтров и антифрода, пуши в Destination (успешные и с ошибкой + причина реджекта). Разбор — [how-to/debug-with-logs.md](../how-to/debug-with-logs.md).
- **Changelog / What's New** `[AIO, меню профиля]` — список обновлений продукта (`Product updates`: Features / Common / Fixes) в меню профиля; при релизе приходит уведомление «AIO app has been updated». [reference/ui-map.md](ui-map.md).
- **Public Roadmap** `[AIO, меню профиля]` — публичный роадмап в меню профиля: канбан не-архивных задач продукта («в работе / planned»). Пункт `Public roadmap`. [reference/ui-map.md](ui-map.md).
- **AIO affiliate program (Become affiliate)** `[AIO, меню профиля]` — реферальная программа AIO: приводишь клиента → он оставляет заявку → сейл-звонок команды AIO → выплата после покупки. Пункт в меню профиля (виден по флагу тенанта). **Не путать с AFF-билдом** (`Affiliate` — отдельный вид приложения, не ERP/MTK).
- **Платные модули MTK: `Meta+` / `Distribution` / `PWA + Push`** `[AIO, биллинг]` — надбавки к плану на MTK-билде. `Distribution` и `PWA + Push` открывают свою вкладку верхнего меню. Вкладка `Meta` в MTK есть и без модуля — сокращённый раздел (в меню — `Data health`, `Social profiles`, `Ad accounts`); с `Meta+` пункт `Meta` ведёт на полный модуль Meta, как в ERP. `Meta+` — управление рекламой Meta (включает команда AIO); `Distribution` — дистрибуции + `Content Library` + группы плейсхолдеров; `PWA + Push` — PWA-лендинги с PWA Builder и рассылка пушей (remarketing-кампании, `Message templates`, аналитика `Other`). `Distribution` и `PWA + Push` включаются самостоятельно кнопкой `Enable` в секции `Modules` биллинг-модалки. Как модуль попадает в счёт — *Билды, тарифы, триал и статусы тенанта*, карта MTK — *Как устроен MTK-вид AIO: навигация, пресеты из шаблона и методы под типовые задачи*.
- **Tags (Settings → Tags)** `[AIO, справочник]` — управляемый справочник тегов (`Settings → Tags`, в ERP и MTK): теги заводятся здесь и вешаются на сущности (кампании и др.) для поиска и фильтрации. Сам тег как атрибут живёт на сущности; управление списком тегов — в этом разделе. **Заархивированный тег пропадает с сущностей**: он остаётся привязанным, но в списках и карточках объектов (кампании, лендинги, домены, серверы, флоу и др.) больше не показывается. Симптом «тег исчез у всех кампаний» — это архивация тега в справочнике, а не потеря данных; разархивируешь — вернётся. **Теги вешаются и снимаются массово:** выделяешь несколько строк в таблице сущностей (кампании, лэнды, дестинейшены, сорсы, флоу, формы, дистрибуции, адверты, шаблоны сообщений, домены, серверы и др.; в MTK — в тех из этих таблиц, что есть в его меню), в контекстном меню выбираешь массовое редактирование тегов и задаёшь два списка — какие теги добавить и какие снять. Добавление НЕ затирает уже висящие теги; если один и тот же тег попал в оба списка, он будет снят.
- **User Behavior метрики (группа)** `[AIO]` — поведенческие метрики из шаблона тенанта: время на лэнде (`LPs Time`, `LP1 Time`, `LP2 Time`), скролл (`LP1 Scroll`, `LP2 Scroll`), `Bounce Rate %` и `Engagement Rate %`. Записи сессий и хитмапы — отдельные инструменты, а не метрики группы. [models/metric.md](../models/metric.md).
- **Bounce Rate** `[AIO, метрика]` — в шаблонах `Bounce Rate %` = `1 − Active Visits / Visits`: доля визитов без флага `Interested`. Активным визит считается, если на первом лэнде провёл не меньше 10 секунд **и** прокрутил не меньше 20 %; не выполнено хотя бы одно условие — визит идёт в отказы. Метрика алертинга аномалий, не основная; границы зашиты во флаге (10 с / 20 %). [models/metric.md](../models/metric.md).
- **Engagement Rate** `[AIO, метрика]` — в шаблонах `Engagement Rate %` = `Engaged Visits / Visits`: доля визитов, которые провели на первом лэнде не меньше 30 секунд **и** прокрутили не меньше 30 %. С `Bounce Rate` не взаимодополняет: у них разные пороги. Метрика алертинга аномалий, не основная; границы зашиты во флаге (30 с / 30 %). [models/metric.md](../models/metric.md).
- **Знак `≈` (приблизительное значение)** `[AIO]` — перед значением аналитической колонки в строке раскрытой подгруппы означает приблизительное значение (тултип `Approximate metric`); перед Meta-итогом — переключатель `Total` / `Total + out of scope` ([mechanics/meta-spend-allocation.md](../mechanics/meta-spend-allocation.md)). [models/metric.md](../models/metric.md).
- **Conversions Count (тип метрики)** `[AIO]` — простой тип метрики в `Settings → Metrics` — считает **только количество** конверсий выбранного `Conversion Type` (штуки, не деньги). Для денежных сумм — `Data feed metric` с источником `Conversions By Type Revenue`/`Payout`. [models/metric.md](../models/metric.md).
- **Data feed metric (тип метрики)** `[AIO]` — тип метрики в `Settings → Metrics`, считающий по внутреннему фиду событий AIO (базовая метрика-источник + опц. `Flag`-фильтр). Денежные суммы конверсий делаются именно им: источник `Conversions By Type Revenue` (сумма Revenue) / `Conversions By Type Payout` (сумма Payout). Отдельного «денежного» типа метрики нет. Источник `Visit Field Sum` суммирует числовое поле визита (раз на визит, по дате визита). [models/metric.md](../models/metric.md).
- **Money (формат метрики)** `[AIO]` — формат отображения метрики для финансовых значений.
- **Install / Open PWA (Conversion Types)** `[AIO]` — `Install` — тип конверсии под установку PWA. Для **AIO/cached PWA** — не по клику на кнопку установки, а по факту установки: на Android + Chrome — по подтверждению браузерного диалога установки (отказ в диалоге конверсию не создаёт), на iOS — при первом запуске установленного приложения с домашнего экрана (само добавление на домашний экран AIO не видит). Для **3rd party / External PWA** — только когда юзер вернулся в AIO («установил + открыл»). `Open PWA` — отдельная конверсия: юзер реально открыл cached PWA после установки. В шаблонах iGaming доля открытий — метрика `PWA Open Rate %` = `PWA Opens / Installs`. См. [mechanics/pwa.md](../mechanics/pwa.md).
- **Conversion Spawn (шаг флоу)** `[AIO]` — шаг флоу, автоматически создающий указанную конверсию, когда визит попадает в этот шаг.
- **Correction Conversion (деривативная конверсия)** `[AIO]` — постбэк не перезаписывает уже записанную конверсию: если у типа со стратегией `Single Conversion` задан `Correction type`, повторный постбэк с другим revenue создаёт новую конверсию-коррекцию на разницу; без `Correction type` повтор игнорируется. Вручную revenue / payout конверсий меняют экшены `Update revenue` / `Update payout`. [models/conversion-model.md](../models/conversion-model.md).
- **Conversion-on-Postback-Date (&timestamp)** `[AIO]` — датировать конверсию не моментом прихода постбэка, а временем из параметра `&timestamp` (unix-время). Граница одна: значение должно быть **не раньше даты создания визита**. Раньше визита — параметр молча игнорируется, конверсия датируется временем прихода; при этом дата **позже текущего момента** принимается как есть.
- **Transaction Hash / Transaction ID** `[общий]` — стандартный плейсхолдер ПП — уникальный ID транзакции. Рекомендуется как `&unique=` при `Multiple By Unique` (защита от дублей).
- **Присвоение чужих лидов внутри команды** `[AIO]` — против этого работают два штатных механизма: модель прав (кто какие сущности вообще видит — [models/permissions-model.md](../models/permissions-model.md)) и логирование действий с IP, User-Agent и временем, по которому видно, кто что сделал.

## Сокращения и API-термины

- **API-токен / API-юзер** `[AIO]` — токен авторизации для AIO-апи. Бесконечный по сроку, наследует доступы своего юзера. Рекомендуется создавать **отдельного юзера под API**, чтобы по логам было видно, что делалось через автоматизацию. Одного токена мало: у юзера должен быть ещё и включён **API-доступ** — отдельный флаг, видный колонкой `API` в `Settings → Users`. По умолчанию он выключен, включает его команда AIO по запросу; без него любой запрос с токеном отвечает `401` `Auth Middleware: Unauthorized`. Где взять токен и что ещё ломает авторизацию — [how-to/api.md](../how-to/api.md).
- **Compact API (= API 2.0)** `[AIO]` — разговорное имя ограниченной Postman-коллекции запросов к API AIO. Документация прямо в продукте есть у узкого `Data API` (`/api/v1/data/*`, меню профиля → `Data API Docs`) и у MCP-сервера — [how-to/api.md](../how-to/api.md).
- **Публичный API: Tables Data endpoint** `[AIO]` — общий API-эндпоинт `Tables Data` (`POST /api/v1/tables/data`), через который фронт AIO запрашивает табличные данные. Структура запроса общая для `Tracker\Visits`, `Tracker\Conversions` и Meta-таблиц (`Facebook\Ads`, `Facebook\AdSets` — spend / impressions / clicks / CTR): меняется ключ `table` (`Namespace\Entity`), а набор полей подстраивается под таблицу ([how-to/api.md](../how-to/api.md)).
- **broad API / front-API (= API 2)** `[AIO]` — путь интеграторов через тот же API, которым общается фронт `app.aio.tech` с бэком: любое действие в UI воспроизводится тем же запросом с API-токеном.
- **Heavy query limit** `[AIO]` — бюджет «тяжёлых» запросов к публичному API: **20 сек времени обработки у запросов, начатых за последние 60 сек** (сверх бюджета — `429 Heavy-usage…`). Общие лимиты API по умолчанию: **60 запросов/мин**, **3 одновременно**; эти значения и бюджет тяжёлых запросов команда AIO может задать юзеру индивидуально. Подробно — [reference/limits.md](limits.md).
- **MCP-сервер AIO (`MCP Server`)** `[AIO, API]` — `POST https://app.aio.tech/api/v1/mcp`: собственный MCP-сервер AIO, к которому внешний AI-агент (`Claude Code`, `Claude Desktop` или другой MCP-клиент с HTTP-транспортом) подключается одной ссылкой и дальше сам читает данные трекера — трафик, метрики, прогнозы, логи кампаний. Ссылку, готовую команду и JSON-конфиг собирает диалог `MCP Server` — кнопка `MCP` в окне `AIO Chat`. Только чтение: действия, требующие подтверждения человеком, через MCP отклоняются. Подключение, инструменты и лимиты — [how-to/mcp-server.md](../how-to/mcp-server.md). (разг.: «коннектор», «подключить Клода к трекеру», «пусть агент сам смотрит цифры»)
- **AIO Skill (MD-file для AI-агентов)** `[AIO, артефакт]` — markdown-файл-инструкция для внешнего AI-агента (Claude/GPT) — описывает, какие запросы к AIO API делать под какие задачи (аналитика, загрузка лэндов, паузить/запускать кампании, ставка, CAPI/пиксели, генерация ссылок). **Не часть AIO** — артефакт. Читающую половину этих задач (аналитика, метрики, логи кампаний) закрывает встроенный MCP-сервер — агента к нему подключают одной ссылкой, без скилла и без своего кода ([how-to/mcp-server.md](../how-to/mcp-server.md)). Скилл поверх broad API остаётся нужен там, где агент должен что-то **менять**: заводить и паузить кампании, править ставку, грузить лэнды.
- **AIO bus push trigger** `[AIO, SDK]` — конструкция в AIO SDK — записывает значение в указанное поле визита. Формат: `window.aioBus.push({type: "trigger", key: 'offer_name', value: offer_name});` где `key` — slug поля, `value` — значение из JS-скрипта.
- **intl-tel-input + параметры** `[AIO, SDK]` — `intl-tel-input` — JS-библиотека, через которую AIO SDK рендерит phone-input в SDK-форме (флаг + dial code по странам). Параметры библиотеки передаются блоком `form.intlParameters` конфига SDK (в шаблонном макросе `AIO SDK Macros Collection` этого блока нет — его добавляют сами): `separateDialCode` (при `true` показывает `+49` отдельно слева от инпута); `strictMode` (жёсткая валидация формата по стране — может отказывать валидным немецким номерам, решение — выключить); `showFlags` (показывать ли иконки флагов) и прочие опции самой библиотеки — имена сверяйте с её версией в бандле. Настраивается в макросе тенанта ([how-to/forms.md](../how-to/forms.md)).
- **config.form.controls + Customize SDK form + глобальный SDK-конфиг** `[AIO, SDK]` — `config.form.controls` — массив объектов конфига SDK-формы, описывает каждый input (тип, `keyType`, валидация, атрибуты). Полный разбор параметров и стилей SDK-формы — [reference/sdk.md](sdk.md) (раздел «SDK-форма — полный разбор») и [how-to/forms.md](../how-to/forms.md). Набор полей формы целиком задаёт команда `form-controls` (`window.aioBus.push({type: "form-controls", controls: [...]})`): `config.form.controls` сливается с дефолтным конфигом по номеру элемента, поэтому лишние дефолтные поля так не убираются. Чтобы применить форму ко всем лэндам сразу — глобальный макрос (`Global?`; AIO вставляет его в `{{aio}}` / `{{aio:head}}` на каждом лэнде тенанта), а не вызов на каждом лэнде.
